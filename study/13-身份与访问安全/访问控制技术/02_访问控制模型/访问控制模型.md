# 访问控制模型

### 2.1 访问控制模型分类

访问控制模型是定义访问控制规则的抽象框架，主要分为以下几类：

| 模型 | 全称 | 核心思想 | 安全性 | 灵活性 | 典型应用 |
|------|------|----------|--------|--------|----------|
| DAC | 自主访问控制 | 资源所有者决定访问权限 | 低 | 高 | 文件系统（Linux/Windows） |
| MAC | 强制访问控制 | 系统根据安全标签强制控制 | 很高 | 很低 | 军用系统、SELinux |
| RBAC | 基于角色的访问控制 | 按角色分配权限 | 中 | 中 | 企业应用、管理系统 |
| ABAC | 基于属性的访问控制 | 基于多属性动态决策 | 高 | 很高 | 零信任、云环境 |
| RB-RBAC | 基于规则的访问控制 | 根据规则引擎决策 | 高 | 高 | 复杂业务场景 |

### 2.2 自主访问控制（DAC）

**核心思想**：资源的所有者（Owner）有权自主决定谁可以访问该资源，以及访问的权限级别。

**DAC 的特点**：
- 权限由资源所有者分配
- 所有者可以将权限传递给其他用户
- 管理分散，每个所有者管理自己的资源
- 灵活性高，但安全性较弱

**典型实现：Linux 文件权限**
```bash
# 文件权限分为三组：所有者、所属组、其他用户
-rw-r--r-- 1 alice dev 1024 Sep 10 10:00 report.txt
 │  │  │
 │  │  └─ 其他用户权限：r-- (只读)
 │  └──── 所属组权限：r-- (只读)
 └─────── 所有者权限：rw- (读写)

# 所有者可以修改权限
chmod g+w report.txt  # 给组增加写权限
chmod o-r report.txt  # 移除其他用户的读权限
```

**DAC 的安全问题**：
1. **权限传递问题**：用户可能将权限意外或恶意传递给不该拥有的人
2. **特洛伊木马问题**：恶意程序可以利用用户的权限进行破坏
3. **管理混乱**：权限分散管理，难以全局掌控
4. **权限泛滥**：随着时间推移，权限越积越多

### 2.3 强制访问控制（MAC）

**核心思想**：系统（而非用户）根据安全标签强制控制访问，用户无法自行更改权限。

**MAC 的特点**：
- 所有主体和客体都有安全标签（Security Label）
- 访问决策由系统严格按照标签匹配规则执行
- 用户不能修改安全标签
- 安全性极高，但灵活性差

**典型模型：Bell-LaPadula 模型（保密性模型）**

Bell-LaPadula 模型是最经典的 MAC 模型，主要保护机密性。

**安全等级示例**：
```
绝密 (Top Secret)
机密 (Secret)
秘密 (Confidential)
公开 (Unclassified)
```

**两条核心规则**：
1. **简单安全规则（向下读）**：主体只能读取安全等级低于或等于自身的客体
   - 机密级用户可以读机密级、秘密级、公开级文档
   - 秘密级用户不能读机密级文档

2. **星号规则（向上写）**：主体只能写入安全等级高于或等于自身的客体
   - 秘密级用户只能写秘密级、机密级、绝密级文档
   - 防止高密级信息被写入低密级文件

**典型实现：SELinux**

SELinux 是 Linux 内核中的 MAC 实现：
```bash
# 查看 SELinux 状态
getenforce

# 查看文件安全上下文
ls -Z /etc/passwd
# system_u:object_r:passwd_file_t:s0 /etc/passwd

# 查看进程安全上下文
ps -Z
# system_u:system_r:sshd_t:s0-s0:c0.c1023 1234 ? ... sshd
```

**MAC 的优缺点**：

| 优点 | 缺点 |
|------|------|
| 安全性极高，不可绕过 | 配置复杂，管理成本高 |
| 防止权限滥用和泄露 | 灵活性差，难以适应变化 |
| 适合高安全需求场景 | 用户体验差 |
| 强制实施安全策略 | 初始实施难度大 |

### 2.4 基于角色的访问控制（RBAC）

**核心思想**：权限不直接分配给用户，而是分配给角色，用户通过获得角色来继承权限。

**RBAC 核心元素**：

```
用户 (User) ←分配→ 角色 (Role) ←分配→ 权限 (Permission)
```

| 元素 | 说明 | 示例 |
|------|------|------|
| 用户 | 系统使用者 | 张三、李四 |
| 角色 | 具有相同职责的用户集合 | 管理员、财务、HR |
| 权限 | 对资源的操作许可 | 查看报表、审批请假 |
| 会话 | 用户与角色的激活关系 | 张三当前以"财务"角色登录 |

#### RBAC 三个层次模型

**RBAC0（核心 RBAC）**：
- 最基本的 RBAC 模型
- 用户-角色-权限 多对多关系
- 支持会话

```
用户 (User) ──多对多── 角色 (Role) ──多对多── 权限 (Permission)
```

**RBAC1（角色层次 RBAC）**：
- 在 RBAC0 基础上增加角色继承
- 高级角色继承低级角色的权限
- 支持权限复用

```
超级管理员
    └── 部门管理员
        ├── 财务主管
        ├── 人事主管
        └── 技术主管
```

**RBAC2（约束 RBAC）**：
- 在 RBAC0 基础上增加约束
- 职责分离（SoD）约束
- 基数约束（角色成员数量限制）
- 先决条件约束（获得某角色前必须先有另一角色）

**RBAC3（统一 RBAC）**：
- 结合 RBAC1 和 RBAC2
- 同时支持角色层次和约束

#### RBAC 设计示例

**某公司 RBAC 角色设计**：

| 角色 | 说明 | 权限 |
|------|------|------|
| 超级管理员 | 系统最高权限 | 所有权限 |
| 部门经理 | 部门管理 | 查看部门数据、审批部门申请 |
| 财务人员 | 财务相关 | 查看财务报表、处理报销 |
| 财务主管 | 财务审批 | 财务人员权限 + 审批财务 |
| HR 专员 | 人事相关 | 查看员工信息、办理入职 |
| 普通员工 | 基础权限 | 查看个人信息、提交申请 |

**RBAC 权限分配示例表**：

```
角色\权限      查看报表    审批申请    用户管理    系统设置
────────────────────────────────────────────────────────
普通员工          ✅          ❌          ❌          ❌
部门经理          ✅          ✅          ❌          ❌
财务人员          ✅          ❌          ❌          ❌
HR专员           ✅          ❌          ✅(部分)     ❌
管理员            ✅          ✅          ✅          ✅
```

#### RBAC 的优缺点

| 优点 | 缺点 |
|------|------|
| 简化权限管理 | 角色爆炸问题（角色数量失控） |
| 易于理解和实施 | 难以处理细粒度权限 |
| 符合企业组织结构 | 上下文不敏感（无法基于时间/地点） |
| 权限变更高效 | 跨部门权限分配复杂 |
| 便于审计 | 角色定义需要持续维护 |

#### RBAC 常见问题：角色爆炸

**问题描述**：随着系统复杂度增加，角色数量急剧增长，管理变得困难。

**原因**：
- 每个新需求就创建一个新角色
- 角色定义粒度不一致
- 缺乏角色治理

**解决方案**：
1. **角色工程**：科学地设计和维护角色体系
2. **角色挖掘**：从现有权限分配中分析归纳角色
3. **混合模型**：RBAC + ABAC，减少角色数量
4. **角色生命周期管理**：定期审查和清理角色

### 2.5 基于属性的访问控制（ABAC）

**核心思想**：根据主体属性、资源属性、环境属性和操作属性，通过策略规则动态决定是否授权访问。

**ABAC 核心概念**：

| 概念 | 说明 | 示例 |
|------|------|------|
| 主体属性 | 用户的属性 | 部门、职位、级别、安全等级 |
| 资源属性 | 被访问资源的属性 | 文件密级、所属部门、创建者 |
| 环境属性 | 访问时的环境上下文 | 时间、地点、设备、网络 |
| 操作属性 | 要执行的操作 | 读、写、删除、审批 |
| 策略 | 访问控制规则 | "部门经理可以在工作时间访问本部门机密文件" |

**ABAC 决策模型**：
```
策略评估引擎
      │
      ├── 主体属性：{部门: 财务部, 职位: 经理, 级别: L3}
      ├── 资源属性：{类型: 报表, 密级: 机密, 部门: 财务部}
      ├── 环境属性：{时间: 工作日 10:00, IP: 公司内网, 设备: 公司电脑}
      └── 操作属性：{动作: 读取}
      │
      ▼
  访问决策：允许 / 拒绝
```

#### ABAC 策略示例

**策略语言：XACML（eXtensible Access Control Markup Language）**

```xml
<!-- 策略：部门经理可以在工作时间访问本部门的机密文件 -->
<Policy RuleCombiningAlgId="...">
  <Target>
    <AnyOf>
      <AllOf>
        <Match MatchId="string-equal">
          <AttributeValue DataType="string">document</AttributeValue>
          <AttributeDesignator AttributeId="resource-type" DataType="string"/>
        </Match>
      </AllOf>
    </AnyOf>
  </Target>
  
  <Rule Effect="Permit" RuleId="allow-dept-manager">
    <Target>
      <AnyOf>
        <AllOf>
          <Match MatchId="string-equal">
            <AttributeValue DataType="string">read</AttributeValue>
            <AttributeDesignator AttributeId="action-id" DataType="string"/>
          </Match>
        </AllOf>
      </AnyOf>
    </Target>
    
    <Condition>
      <Apply FunctionId="and">
        <!-- 主体是部门经理 -->
        <Apply FunctionId="string-equal">
          <AttributeValue DataType="string">manager</AttributeValue>
          <AttributeDesignator AttributeId="user-role" DataType="string"/>
        </Apply>
        <!-- 主体部门与资源部门相同 -->
        <Apply FunctionId="string-equal">
          <AttributeDesignator AttributeId="user-dept" DataType="string"/>
          <AttributeDesignator AttributeId="resource-dept" DataType="string"/>
        </Apply>
        <!-- 资源密级不高于机密 -->
        <Apply FunctionId="integer-less-than-or-equal">
          <AttributeDesignator AttributeId="resource-classification" DataType="integer"/>
          <AttributeValue DataType="integer">2</AttributeValue>
        </Apply>
        <!-- 工作时间（9:00-18:00） -->
        <Apply FunctionId="time-in-range">
          <AttributeDesignator AttributeId="current-time" DataType="time"/>
          <AttributeValue DataType="time">09:00:00</AttributeValue>
          <AttributeValue DataType="time">18:00:00</AttributeValue>
        </Apply>
      </Apply>
    </Condition>
  </Rule>
</Policy>
```

**更简洁的策略表达（伪代码）**：
```
规则1：允许部门经理在工作时间读取本部门机密及以下文件
IF  user.role == "manager"
AND user.dept == resource.dept
AND resource.classification <= "confidential"
AND action == "read"
AND current_time.between("09:00", "18:00")
THEN PERMIT

规则2：允许HR专员在公司网络内修改员工信息
IF  user.role == "hr_specialist"
AND resource.type == "employee_record"
AND action in ["read", "update"]
AND request.ip.in_company_network()
THEN PERMIT

默认规则：拒绝所有未明确允许的访问
```

#### ABAC vs RBAC 对比

| 维度 | RBAC | ABAC |
|------|------|------|
| 决策依据 | 角色 | 属性（多维） |
| 灵活性 | 中 | 高 |
| 细粒度 | 中 | 高 |
| 动态性 | 静态 | 动态 |
| 实现复杂度 | 低 | 高 |
| 性能 | 好 | 一般 |
| 可审计性 | 好 | 复杂 |
| 适用场景 | 简单企业应用 | 零信任、云环境、复杂场景 |

#### ABAC 的优势

1. **细粒度控制**：可以基于多个维度精确控制访问
2. **动态决策**：访问决策基于实时上下文
3. **易于扩展**：新增属性即可扩展控制维度
4. **减少角色爆炸**：用属性替代大量细分角色
5. **支持零信任**：持续验证、动态评估的基础

#### ABAC 的挑战

1. **策略复杂**：策略数量多了难以维护
2. **性能开销**：每次决策需要收集和评估大量属性
3. **属性来源**：需要可靠的属性提供方
4. **策略冲突**：多个策略可能产生矛盾
5. **审计困难**：动态决策的审计追溯更复杂

### 2.6 其他访问控制模型

#### 基于规则的访问控制（Rule-Based Access Control）
- 预定义一系列规则，根据规则匹配结果决策
- 常用于网络设备（防火墙ACL）
- 规则按顺序匹配，第一条命中即生效

```
防火墙规则示例：
规则1：允许 192.168.1.0/24 访问 10.0.0.0/8 的 443 端口
规则2：拒绝 192.168.1.100 访问任何外部地址
规则3：允许所有已建立的连接
规则4：默认拒绝所有
```

#### 基于任务的访问控制（TBAC）
- Task-Based Access Control
- 权限与任务绑定，任务完成后权限自动回收
- 适用于工作流系统

#### 基于团队的访问控制（TMAC）
- Team-Based Access Control
- 以团队为单位分配权限
- 适用于协作型工作场景

#### 基于风险的访问控制（Risk-Adaptive Access Control）
- 根据风险评估结果动态调整访问权限
- 风险低时权限大，风险高时权限小
- 零信任架构的重要组成部分

```
风险评估示例：
正常登录（常用设备 + 常用地点 + 工作时间）→ 低风险 → 完全访问
异地登录（新设备 + 异常地点）→ 中风险 → 限制敏感操作 + 二次验证
高风险登录（异常IP + 多次失败）→ 高风险 → 拒绝访问 + 告警
```
