# 访问控制技术

> 访问控制是身份安全的核心，决定了"谁能访问什么资源、能做什么操作"。本文详细介绍各类访问控制模型、核心原则和最佳实践。

---

## 一、访问控制基础

### 1.1 访问控制概念

**访问控制（Access Control）**：指系统对用户或进程访问资源的行为进行限制和管理的安全机制，确保只有经过授权的主体才能访问相应的客体资源。

**访问控制三要素**：

| 要素 | 英文 | 说明 | 示例 |
|------|------|------|------|
| 主体 | Subject | 发起访问请求的实体 | 用户、进程、服务、设备 |
| 客体 | Object | 被访问的资源 | 文件、数据库、API、功能模块 |
| 操作 | Action | 主体对客体执行的动作 | 读、写、执行、删除、管理 |

**访问控制决策过程**：
```
主体发起请求 → 身份认证（你是谁？）
              → 授权检查（你有权限吗？）
              → 允许/拒绝访问
              → 审计记录（你做了什么？）
```

### 1.2 访问控制的目标

| 目标 | 说明 |
|------|------|
| 机密性 | 防止未授权的信息泄露 |
| 完整性 | 防止未授权的数据篡改 |
| 可用性 | 确保授权用户能正常访问资源 |
| 可追溯性 | 所有操作可审计、可追溯 |
| 最小权限 | 用户只拥有完成工作所需的最少权限 |

### 1.3 访问控制与 AAA

访问控制是 AAA 框架的重要组成部分：

```
认证 (Authentication) → 确认身份
    ↓
授权 (Authorization) → 访问控制决策
    ↓
审计 (Accounting) → 记录访问行为
```

## 二、访问控制模型

### 2.1 访问控制模型分类

访问控制模型是定义访问控制规则的抽象框架，主要分为以下几类：

| 模型 | 全称 | 核心思想 | 安全性 | 灵活性 | 典型应用 |
|------|------|----------|--------|--------|----------|
| DAC | 自主访问控制 | 资源所有者决定访问权限 | 低 | 高 | 文件系统（Linux/Windows） |
| MAC | 强制访问控制 | 系统根据安全标签强制控制 | 很高 | 很低 | 军用系统、SELinux |
| RBAC | 基于角色的访问控制 | 按角色分配权限 | 中 | 中 | 企业应用、管理系统 |
| ABAC | 基于属性的访问控制 | 基于多属性动态决策 | 高 | 很高 | 零信任、云环境 |
| RB-RBAC | 基于规则的访问控制 | 根据规则引擎决策 | 高 | 高 | 复杂业务场景 |

### 2.2 自主访问控制（DAC）

**核心思想**：资源的所有者（Owner）有权自主决定谁可以访问该资源，以及访问的权限级别。

**DAC 的特点**：
- 权限由资源所有者分配
- 所有者可以将权限传递给其他用户
- 管理分散，每个所有者管理自己的资源
- 灵活性高，但安全性较弱

**典型实现：Linux 文件权限**
```bash
# 文件权限分为三组：所有者、所属组、其他用户
-rw-r--r-- 1 alice dev 1024 Sep 10 10:00 report.txt
 │  │  │
 │  │  └─ 其他用户权限：r-- (只读)
 │  └──── 所属组权限：r-- (只读)
 └─────── 所有者权限：rw- (读写)

# 所有者可以修改权限
chmod g+w report.txt  # 给组增加写权限
chmod o-r report.txt  # 移除其他用户的读权限
```

**DAC 的安全问题**：
1. **权限传递问题**：用户可能将权限意外或恶意传递给不该拥有的人
2. **特洛伊木马问题**：恶意程序可以利用用户的权限进行破坏
3. **管理混乱**：权限分散管理，难以全局掌控
4. **权限泛滥**：随着时间推移，权限越积越多

### 2.3 强制访问控制（MAC）

**核心思想**：系统（而非用户）根据安全标签强制控制访问，用户无法自行更改权限。

**MAC 的特点**：
- 所有主体和客体都有安全标签（Security Label）
- 访问决策由系统严格按照标签匹配规则执行
- 用户不能修改安全标签
- 安全性极高，但灵活性差

**典型模型：Bell-LaPadula 模型（保密性模型）**

Bell-LaPadula 模型是最经典的 MAC 模型，主要保护机密性。

**安全等级示例**：
```
绝密 (Top Secret)
机密 (Secret)
秘密 (Confidential)
公开 (Unclassified)
```

**两条核心规则**：
1. **简单安全规则（向下读）**：主体只能读取安全等级低于或等于自身的客体
   - 机密级用户可以读机密级、秘密级、公开级文档
   - 秘密级用户不能读机密级文档

2. **星号规则（向上写）**：主体只能写入安全等级高于或等于自身的客体
   - 秘密级用户只能写秘密级、机密级、绝密级文档
   - 防止高密级信息被写入低密级文件

**典型实现：SELinux**

SELinux 是 Linux 内核中的 MAC 实现：
```bash
# 查看 SELinux 状态
getenforce

# 查看文件安全上下文
ls -Z /etc/passwd
# system_u:object_r:passwd_file_t:s0 /etc/passwd

# 查看进程安全上下文
ps -Z
# system_u:system_r:sshd_t:s0-s0:c0.c1023 1234 ? ... sshd
```

**MAC 的优缺点**：

| 优点 | 缺点 |
|------|------|
| 安全性极高，不可绕过 | 配置复杂，管理成本高 |
| 防止权限滥用和泄露 | 灵活性差，难以适应变化 |
| 适合高安全需求场景 | 用户体验差 |
| 强制实施安全策略 | 初始实施难度大 |

### 2.4 基于角色的访问控制（RBAC）

**核心思想**：权限不直接分配给用户，而是分配给角色，用户通过获得角色来继承权限。

**RBAC 核心元素**：

```
用户 (User) ←分配→ 角色 (Role) ←分配→ 权限 (Permission)
```

| 元素 | 说明 | 示例 |
|------|------|------|
| 用户 | 系统使用者 | 张三、李四 |
| 角色 | 具有相同职责的用户集合 | 管理员、财务、HR |
| 权限 | 对资源的操作许可 | 查看报表、审批请假 |
| 会话 | 用户与角色的激活关系 | 张三当前以"财务"角色登录 |

#### RBAC 三个层次模型

**RBAC0（核心 RBAC）**：
- 最基本的 RBAC 模型
- 用户-角色-权限 多对多关系
- 支持会话

```
用户 (User) ──多对多── 角色 (Role) ──多对多── 权限 (Permission)
```

**RBAC1（角色层次 RBAC）**：
- 在 RBAC0 基础上增加角色继承
- 高级角色继承低级角色的权限
- 支持权限复用

```
超级管理员
    └── 部门管理员
        ├── 财务主管
        ├── 人事主管
        └── 技术主管
```

**RBAC2（约束 RBAC）**：
- 在 RBAC0 基础上增加约束
- 职责分离（SoD）约束
- 基数约束（角色成员数量限制）
- 先决条件约束（获得某角色前必须先有另一角色）

**RBAC3（统一 RBAC）**：
- 结合 RBAC1 和 RBAC2
- 同时支持角色层次和约束

#### RBAC 设计示例

**某公司 RBAC 角色设计**：

| 角色 | 说明 | 权限 |
|------|------|------|
| 超级管理员 | 系统最高权限 | 所有权限 |
| 部门经理 | 部门管理 | 查看部门数据、审批部门申请 |
| 财务人员 | 财务相关 | 查看财务报表、处理报销 |
| 财务主管 | 财务审批 | 财务人员权限 + 审批财务 |
| HR 专员 | 人事相关 | 查看员工信息、办理入职 |
| 普通员工 | 基础权限 | 查看个人信息、提交申请 |

**RBAC 权限分配示例表**：

```
角色\权限      查看报表    审批申请    用户管理    系统设置
────────────────────────────────────────────────────────
普通员工          ✅          ❌          ❌          ❌
部门经理          ✅          ✅          ❌          ❌
财务人员          ✅          ❌          ❌          ❌
HR专员           ✅          ❌          ✅(部分)     ❌
管理员            ✅          ✅          ✅          ✅
```

#### RBAC 的优缺点

| 优点 | 缺点 |
|------|------|
| 简化权限管理 | 角色爆炸问题（角色数量失控） |
| 易于理解和实施 | 难以处理细粒度权限 |
| 符合企业组织结构 | 上下文不敏感（无法基于时间/地点） |
| 权限变更高效 | 跨部门权限分配复杂 |
| 便于审计 | 角色定义需要持续维护 |

#### RBAC 常见问题：角色爆炸

**问题描述**：随着系统复杂度增加，角色数量急剧增长，管理变得困难。

**原因**：
- 每个新需求就创建一个新角色
- 角色定义粒度不一致
- 缺乏角色治理

**解决方案**：
1. **角色工程**：科学地设计和维护角色体系
2. **角色挖掘**：从现有权限分配中分析归纳角色
3. **混合模型**：RBAC + ABAC，减少角色数量
4. **角色生命周期管理**：定期审查和清理角色

### 2.5 基于属性的访问控制（ABAC）

**核心思想**：根据主体属性、资源属性、环境属性和操作属性，通过策略规则动态决定是否授权访问。

**ABAC 核心概念**：

| 概念 | 说明 | 示例 |
|------|------|------|
| 主体属性 | 用户的属性 | 部门、职位、级别、安全等级 |
| 资源属性 | 被访问资源的属性 | 文件密级、所属部门、创建者 |
| 环境属性 | 访问时的环境上下文 | 时间、地点、设备、网络 |
| 操作属性 | 要执行的操作 | 读、写、删除、审批 |
| 策略 | 访问控制规则 | "部门经理可以在工作时间访问本部门机密文件" |

**ABAC 决策模型**：
```
策略评估引擎
      │
      ├── 主体属性：{部门: 财务部, 职位: 经理, 级别: L3}
      ├── 资源属性：{类型: 报表, 密级: 机密, 部门: 财务部}
      ├── 环境属性：{时间: 工作日 10:00, IP: 公司内网, 设备: 公司电脑}
      └── 操作属性：{动作: 读取}
      │
      ▼
  访问决策：允许 / 拒绝
```

#### ABAC 策略示例

**策略语言：XACML（eXtensible Access Control Markup Language）**

```xml
<!-- 策略：部门经理可以在工作时间访问本部门的机密文件 -->
<Policy RuleCombiningAlgId="...">
  <Target>
    <AnyOf>
      <AllOf>
        <Match MatchId="string-equal">
          <AttributeValue DataType="string">document</AttributeValue>
          <AttributeDesignator AttributeId="resource-type" DataType="string"/>
        </Match>
      </AllOf>
    </AnyOf>
  </Target>
  
  <Rule Effect="Permit" RuleId="allow-dept-manager">
    <Target>
      <AnyOf>
        <AllOf>
          <Match MatchId="string-equal">
            <AttributeValue DataType="string">read</AttributeValue>
            <AttributeDesignator AttributeId="action-id" DataType="string"/>
          </Match>
        </AllOf>
      </AnyOf>
    </Target>
    
    <Condition>
      <Apply FunctionId="and">
        <!-- 主体是部门经理 -->
        <Apply FunctionId="string-equal">
          <AttributeValue DataType="string">manager</AttributeValue>
          <AttributeDesignator AttributeId="user-role" DataType="string"/>
        </Apply>
        <!-- 主体部门与资源部门相同 -->
        <Apply FunctionId="string-equal">
          <AttributeDesignator AttributeId="user-dept" DataType="string"/>
          <AttributeDesignator AttributeId="resource-dept" DataType="string"/>
        </Apply>
        <!-- 资源密级不高于机密 -->
        <Apply FunctionId="integer-less-than-or-equal">
          <AttributeDesignator AttributeId="resource-classification" DataType="integer"/>
          <AttributeValue DataType="integer">2</AttributeValue>
        </Apply>
        <!-- 工作时间（9:00-18:00） -->
        <Apply FunctionId="time-in-range">
          <AttributeDesignator AttributeId="current-time" DataType="time"/>
          <AttributeValue DataType="time">09:00:00</AttributeValue>
          <AttributeValue DataType="time">18:00:00</AttributeValue>
        </Apply>
      </Apply>
    </Condition>
  </Rule>
</Policy>
```

**更简洁的策略表达（伪代码）**：
```
规则1：允许部门经理在工作时间读取本部门机密及以下文件
IF  user.role == "manager"
AND user.dept == resource.dept
AND resource.classification <= "confidential"
AND action == "read"
AND current_time.between("09:00", "18:00")
THEN PERMIT

规则2：允许HR专员在公司网络内修改员工信息
IF  user.role == "hr_specialist"
AND resource.type == "employee_record"
AND action in ["read", "update"]
AND request.ip.in_company_network()
THEN PERMIT

默认规则：拒绝所有未明确允许的访问
```

#### ABAC vs RBAC 对比

| 维度 | RBAC | ABAC |
|------|------|------|
| 决策依据 | 角色 | 属性（多维） |
| 灵活性 | 中 | 高 |
| 细粒度 | 中 | 高 |
| 动态性 | 静态 | 动态 |
| 实现复杂度 | 低 | 高 |
| 性能 | 好 | 一般 |
| 可审计性 | 好 | 复杂 |
| 适用场景 | 简单企业应用 | 零信任、云环境、复杂场景 |

#### ABAC 的优势

1. **细粒度控制**：可以基于多个维度精确控制访问
2. **动态决策**：访问决策基于实时上下文
3. **易于扩展**：新增属性即可扩展控制维度
4. **减少角色爆炸**：用属性替代大量细分角色
5. **支持零信任**：持续验证、动态评估的基础

#### ABAC 的挑战

1. **策略复杂**：策略数量多了难以维护
2. **性能开销**：每次决策需要收集和评估大量属性
3. **属性来源**：需要可靠的属性提供方
4. **策略冲突**：多个策略可能产生矛盾
5. **审计困难**：动态决策的审计追溯更复杂

### 2.6 其他访问控制模型

#### 基于规则的访问控制（Rule-Based Access Control）
- 预定义一系列规则，根据规则匹配结果决策
- 常用于网络设备（防火墙ACL）
- 规则按顺序匹配，第一条命中即生效

```
防火墙规则示例：
规则1：允许 192.168.1.0/24 访问 10.0.0.0/8 的 443 端口
规则2：拒绝 192.168.1.100 访问任何外部地址
规则3：允许所有已建立的连接
规则4：默认拒绝所有
```

#### 基于任务的访问控制（TBAC）
- Task-Based Access Control
- 权限与任务绑定，任务完成后权限自动回收
- 适用于工作流系统

#### 基于团队的访问控制（TMAC）
- Team-Based Access Control
- 以团队为单位分配权限
- 适用于协作型工作场景

#### 基于风险的访问控制（Risk-Adaptive Access Control）
- 根据风险评估结果动态调整访问权限
- 风险低时权限大，风险高时权限小
- 零信任架构的重要组成部分

```
风险评估示例：
正常登录（常用设备 + 常用地点 + 工作时间）→ 低风险 → 完全访问
异地登录（新设备 + 异常地点）→ 中风险 → 限制敏感操作 + 二次验证
高风险登录（异常IP + 多次失败）→ 高风险 → 拒绝访问 + 告警
```

## 三、最小权限原则

### 3.1 什么是最小权限原则

**定义**：最小权限原则（Principle of Least Privilege，PoLP）规定每个用户、程序或进程只应拥有完成其预定任务所必需的**最少权限**。

**核心思想**：
- "够用即可"，不要过度授权
- 权限是一种风险，多余的权限就是多余的风险
- 默认拒绝，按需授予

**最小权限的三个层面**：

| 层面 | 说明 | 示例 |
|------|------|------|
| 用户权限 | 用户只拥有工作需要的权限 | 普通员工没有管理员权限 |
| 进程权限 | 程序只运行在必要的权限下 | Web服务器不以root运行 |
| 系统权限 | 系统组件间权限隔离 | 数据库账号只有SELECT权限 |

### 3.2 为什么需要最小权限

**安全收益**：

1. **减少攻击面**：权限越小，被攻破后的影响范围越小
2. **限制横向移动**：攻击者难以从一个系统跳到另一个系统
3. **减少误操作**：权限受限，误操作的破坏也有限
4. **降低内部威胁**：内部人员也无法滥用权限

**真实案例**：
> 2013年 Target 数据泄露事件中，攻击者最初通过钓鱼获取了一个 HVAC（暖通空调）供应商的账号。该供应商账号本应只有有限的访问权限，但实际上却拥有广泛的网络访问权，导致攻击者能够横向移动到POS系统，窃取了4000万张信用卡信息。
>
> **教训**：第三方账号也应遵循最小权限原则，严格限制其访问范围。

### 3.3 最小权限实践

#### 用户权限管理

| 实践 | 说明 |
|------|------|
| 默认无权限 | 新用户默认没有任何权限，按需申请 |
| 按需申请 | 用户根据工作需要申请具体权限 |
| 定期审查 | 每季度/半年审查一次权限，回收不再需要的 |
| 离职清理 | 员工离职时立即回收所有权限 |
| 权限分级 | 普通权限/敏感权限/特权权限分级管理 |

#### 系统服务配置

**错误做法**：
```bash
# 以 root 身份运行 Nginx（危险！）
nginx: master process /usr/sbin/nginx  # root 运行
```

**正确做法**：
```bash
# 主进程以 root 运行（绑定80端口需要），工作进程以 nobody 运行
nginx: master process /usr/sbin/nginx     # root (仅绑定端口)
nginx: worker process                     # nobody (处理请求)
```

#### 数据库权限

**错误做法**：
```sql
-- 应用使用 root 账号（危险！）
GRANT ALL PRIVILEGES ON *.* TO 'app'@'%' IDENTIFIED BY 'password';
```

**正确做法**：
```sql
-- 只授予必要的权限
GRANT SELECT, INSERT, UPDATE ON mydb.* TO 'app'@'app-server' IDENTIFIED BY 'strong_password';

-- 删除权限用单独的账号
GRANT DELETE ON mydb.* TO 'app_delete'@'app-server' IDENTIFIED BY 'another_password';
```

### 3.4 最小权限的常见误区

| 误区 | 正确做法 |
|------|----------|
| "图省事"给多一点权限 | 严格按职责分配，宁可少给也不多给 |
| 权限分配后从不审查 | 定期审查权限，及时回收 |
| 一个账号用到底 | 按场景使用不同权限的账号 |
| 第三方/供应商权限宽松 | 第三方权限更要严格限制 |
| 测试环境无所谓 | 测试环境也可能有真实数据 |

## 四、权限分离（职责分离）

### 4.1 什么是权限分离

**定义**：权限分离（Separation of Duties，SoD），也叫职责分离，指将关键任务拆分为多个步骤，分别由不同的人或角色负责，以防止单个人能够独立完成舞弊行为。

**核心思想**：
- 权力制衡，相互监督
- 任何人都不能独立完成高风险操作
- "两个人才能开金库"

### 4.2 常见的职责分离场景

| 场景 | 应分离的职责 | 原因 |
|------|-------------|------|
| 财务 | 申请人 ≠ 审批人 ≠ 出纳 | 防止虚报冒领 |
| IT运维 | 开发 ≠ 测试 ≠ 生产部署 | 防止代码后门 |
| 采购 | 采购员 ≠ 验收员 ≠ 付款员 | 防止虚假采购 |
| 系统管理 | 系统管理员 ≠ 安全管理员 ≠ 审计员 | 防止滥用权限 |
| 数据库 | DBA ≠ 业务用户 ≠ 审计员 | 防止数据篡改 |

### 4.3 SoD 在访问控制中的实现

#### 静态职责分离（Static SoD）
- 在角色分配阶段就实施分离
- 用户不能同时拥有两个互斥角色

```
互斥角色对示例：
- "采购申请" 和 "采购审批" 互斥
- "记账" 和 "审计" 互斥
- "系统管理员" 和 "安全审计员" 互斥

规则：
IF 用户有角色A AND 角色A与角色B互斥
THEN 用户不能被分配角色B
```

#### 动态职责分离（Dynamic SoD）
- 用户可以拥有多个互斥角色，但不能在同一会话中同时激活

```
示例：
用户张三同时拥有"采购员"和"审批员"两个角色
但在同一会话中，他只能激活其中一个角色
不能既以采购员身份申请，又以审批员身份审批
```

#### 基于操作的职责分离
- 同一用户不能对同一记录执行两个互斥操作

```
示例：
创建合同的人不能审批同一份合同
发起转账的人不能审核同一笔转账
```

### 4.4 SoD 冲突检测

**SoD 矩阵示例**：

| 角色 | 采购申请 | 采购审批 | 财务付款 | 合同审核 |
|------|----------|----------|----------|----------|
| 采购申请 | - | ✅冲突 | ❌ | ❌ |
| 采购审批 | ✅冲突 | - | ✅冲突 | ❌ |
| 财务付款 | ❌ | ✅冲突 | - | ❌ |
| 合同审核 | ❌ | ❌ | ❌ | - |

**冲突检测算法**：
```
检查用户是否同时拥有互斥角色对中的两个角色：
1. 获取用户的所有角色列表
2. 遍历所有互斥角色对
3. 检查互斥对中的两个角色是否都在用户角色列表中
4. 如果存在冲突，阻止分配或触发告警
```

## 五、特权账号管理（PAM）

### 5.1 什么是特权账号

**特权账号（Privileged Account）**：指拥有超出普通用户权限的账号，通常可以访问敏感资源、执行管理操作、修改系统配置。

**常见特权账号类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| 超级管理员 | 系统最高权限 | root、Administrator、域管理员 |
| 系统管理员 | 操作系统管理 | Linux sudo用户、Windows管理员组 |
| 数据库管理员 | 数据库管理 | DBA、sa、sys |
| 网络管理员 | 网络设备管理 | 路由器、交换机、防火墙管理员 |
| 应用管理员 | 应用系统管理 | ERP管理员、邮件管理员 |
| 服务账号 | 应用/服务运行账号 | 应用池账号、定时任务账号 |
| 应急账号 | 紧急情况下使用 | break-glass账号 |
| 测试账号 | 测试环境使用 | test_admin |

**为什么特权账号需要特殊管理**：
- 权限最大，攻击价值最高
- 是攻击者的首要目标
- 一旦泄露，影响范围最广
- 内部人员滥用风险高

### 5.2 PAM 核心功能

**PAM（Privileged Access Management，特权访问管理）**是一套用于管理、控制和审计特权账号访问的安全解决方案。

**PAM 核心功能模块**：

```
┌─────────────────────────────────────────────────┐
│              特权访问管理 (PAM)                   │
├─────────────┬─────────────┬───────────┬─────────┤
│  密码金库    │  会话管理    │  命令控制  │  审计   │
│  (Vault)    │  (Session)  │  (Command)│ (Audit) │
└─────────────┴─────────────┴───────────┴─────────┘
```

#### 1. 特权账号金库（Password Vault）

**功能**：
- 集中存储所有特权账号密码
- 加密存储（AES-256等）
- 严格的访问控制
- 自动密码轮换

**密码轮换**：
```
传统方式：密码手动管理，可能几年不改
PAM方式：每次使用后自动轮换，密码随机生成
```

#### 2. 会话管理（Session Management）

**功能**：
- 用户不直接接触密码
- 通过PAM系统代理连接
- 会话录制（录像/键盘记录）
- 实时监控和会话中断

**工作原理**：
```
用户 → PAM系统 → 目标服务器
        │
        ├── 用户不知道真实密码
        ├── PAM记录所有操作
        └── 管理员可以实时监控和中断
```

#### 3. 命令控制（Command Control）

**功能**：
- 命令白名单/黑名单
- 危险命令拦截
- 高风险命令需要审批
- 命令级别的细粒度控制

**示例规则**：
```
允许：ls, cd, cat, grep, systemctl status
禁止：rm -rf /, fdisk, mkfs, useradd, passwd root
需审批：reboot, shutdown, yum update, 修改防火墙规则
```

#### 4. 即时权限（Just-In-Time，JIT）

**核心思想**：特权权限不常驻，按需申请、即时授权、用完即收。

**JIT 工作流程**：
```
1. 用户申请特权权限（选择服务器、时长、原因）
2. 审批人审批
3. 审批通过后，临时授予权限（如30分钟）
4. 用户在有效期内使用特权
5. 到期后自动回收权限
6. 操作记录归档审计
```

**JIT 的优势**：
- 大幅减少特权账号的暴露时间
- 符合最小权限原则
- 所有特权使用都有申请和审批记录
- 降低持久化特权的风险

### 5.3 PAM 实施最佳实践

1. **发现和盘点**：找出所有特权账号，包括服务账号、应急账号
2. **集中管理**：所有特权账号纳入金库管理
3. **自动轮换**：密码定期自动更换，使用后立即更换
4. **MFA保护**：访问PAM系统必须经过多因素认证
5. **最小权限**：只授予必要的特权，能用普通权限就不用特权
6. **会话审计**：所有特权会话全程录制
7. **即时权限**：尽量用JIT替代常驻特权
8. **定期审查**：定期审查特权账号和访问权限

## 六、访问控制审计

### 6.1 审计的目的

访问控制审计是对访问控制机制的有效性进行审查和评估，确保：
- 访问控制策略正确实施
- 权限分配合理合规
- 异常访问行为被发现
- 满足合规要求（等保、ISO27001、GDPR等）

### 6.2 审计类型

| 审计类型 | 说明 | 频率 |
|----------|------|------|
| 实时审计 | 实时监控访问行为，异常告警 | 持续 |
| 定期审计 | 定期审查权限分配和访问日志 | 月度/季度 |
| 专项审计 | 针对特定事件或问题的审计 | 按需 |
| 合规审计 | 为满足合规要求的审计 | 年度 |

### 6.3 审计内容

#### 权限分配审计
- 检查是否有权限过大的用户
- 检查离职人员权限是否回收
- 检查角色分配是否合理
- 检查职责分离是否违反

#### 访问行为审计
- 特权账号使用情况
- 异常时间的访问
- 异常地点的访问
- 敏感资源的访问
- 失败的登录尝试

#### 策略合规审计
- 访问控制策略是否符合安全要求
- 策略执行是否到位
- 例外情况是否有审批

### 6.4 关键审计指标（KRI）

| 指标 | 说明 | 关注阈值 |
|------|------|----------|
| 特权账号数量 | 拥有特权的账号数 | 应保持最小化 |
| 孤儿账号 | 无主账号、离职未回收 | 应为0 |
| 权限超标率 | 权限超出岗位需求的比例 | 应<5% |
| SoD冲突数 | 职责分离违规数量 | 应为0 |
| 失败登录率 | 登录失败/总登录 | 异常升高告警 |
| 特权操作数 | 特权命令执行数量 | 异常升高告警 |
| 权限审查覆盖率 | 定期审查覆盖的比例 | 应100% |

### 6.5 审计日志要求

**日志应记录的内容**：

| 字段 | 说明 | 示例 |
|------|------|------|
| 时间戳 | 事件发生时间 | 2024-01-15 14:30:25 |
| 主体 | 谁发起的 | 用户ID、IP地址 |
| 客体 | 访问了什么 | 资源路径、文件名 |
| 操作 | 执行了什么动作 | 登录、读取、修改、删除 |
| 结果 | 成功还是失败 | 成功/失败/拒绝 |
| 详情 | 额外信息 | 失败原因、数据量 |

**日志管理要求**：
- 日志不可篡改（WORM存储、区块链等）
- 日志保留足够时间（如6个月-1年）
- 日志集中管理（SIEM）
- 定期备份
- 访问日志本身也需要权限控制

## 七、零信任架构基础

### 7.1 零信任的核心理念

**零信任（Zero Trust）**：一种安全理念，核心是"永不信任，始终验证"（Never Trust, Always Verify），不基于网络位置自动授予信任，每次访问都需要验证。

**传统网络安全 vs 零信任**：

| 维度 | 传统边界安全 | 零信任 |
|------|-------------|--------|
| 信任基础 | 网络位置（内网=可信） | 身份和设备 |
| 假设 | 内部用户可信 | 所有人都不可信 |
| 防护重点 | 边界防护（防火墙） | 身份和数据 |
| 访问控制 | 粗粒度（网段级） | 细粒度（每次访问） |
| 验证方式 | 一次验证，长期有效 | 持续验证，动态评估 |

### 7.2 零信任的核心原则

1. **永不信任，始终验证**：无论来自内网还是外网，每次访问都要验证
2. **最小权限**：只授予完成任务所需的最少权限
3. **假设 breach**：假设已经被入侵，设计防御纵深
4. **持续验证**：不是一次性认证，而是持续评估信任度
5. **动态访问控制**：基于实时风险动态调整权限
6. **全面审计**：所有访问行为都记录和监控
7. **微隔离**：网络分段，限制横向移动

### 7.3 零信任与访问控制

零信任架构下的访问控制特点：

| 特点 | 说明 |
|------|------|
| 身份为中心 | 身份是新的安全边界 |
| 动态策略 | ABAC为主，基于多属性动态决策 |
| 持续评估 | 访问过程中持续评估风险 |
| 自适应 | 风险变化时自动调整权限 |
| 细粒度 | 应用级、API级的细粒度控制 |
| 上下文感知 | 考虑设备状态、环境、行为等上下文 |

> **详细内容请参考《零信任安全.md》**

## 八、实际案例分析

### 案例一：越权访问导致数据泄露

**事件**：某电商平台存在水平越权漏洞，攻击者通过修改用户ID参数，可以查看任意用户的订单信息。

**技术细节**：
```
正常请求：
GET /api/order?user_id=1001
返回：用户1001的订单

攻击请求：
GET /api/order?user_id=1002
返回：用户1002的订单（本不应被查看）
```

**根本原因**：
- 后端只验证了用户是否登录（认证）
- 没有验证当前用户是否有权访问该订单（授权）
- 访问控制缺失

**修复方案**：
1. 服务端校验资源归属：`order.user_id == current_user.id`
2. 实施RBAC/ABAC权限检查
3. 使用对象级授权（Object-Level Authorization）
4. 安全测试覆盖越权场景

### 案例二：权限过大的服务账号被利用

**事件**：某公司被入侵，攻击者利用一个配置文件泄露的数据库服务账号密码登录数据库，该账号拥有所有数据库的全部权限。

**攻击过程**：
1. 攻击者通过SQL注入获取Web应用配置文件
2. 配置文件中包含数据库服务账号密码
3. 该服务账号拥有 `ALL PRIVILEGES ON *.*`
4. 攻击者登录数据库，导出所有用户数据
5. 进一步获取了管理员后台权限

**问题分析**：
- 服务账号权限过大（违反最小权限原则）
- 密码硬编码在配置文件中
- 数据库可以从公网直接访问

**改进措施**：
1. 为每个应用创建独立的数据库账号
2. 只授予必要的权限（如只SELECT/INSERT/UPDATE特定表）
3. 使用密钥管理系统存储密码（如Vault）
4. 限制数据库访问来源（只允许应用服务器IP）
5. 数据库开启审计日志

### 案例三：职责分离缺失导致舞弊

**事件**：某公司财务人员利用职务之便，虚构供应商并虚假报销，累计侵占公司资金500万元。

**问题分析**：
- 该财务人员同时负责供应商管理和报销审批
- 违反了职责分离原则
- 没有定期审计和对账机制

**改进措施**：
1. 实施严格的职责分离：
   - 供应商录入和审批分离
   - 报销申请和审批分离
   - 付款执行和审计分离
2. 建立SoD冲突检测机制
3. 定期进行财务审计
4. 供应商准入需要多部门审核
