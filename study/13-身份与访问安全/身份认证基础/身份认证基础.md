# 身份认证基础

> 身份认证是网络安全的第一道防线，验证"你是谁"是所有安全机制的起点。本文详细介绍身份认证的核心概念、各类认证技术及其安全实践。

---

## 一、身份认证概述

### 1.1 认证、授权与审计（AAA）

身份安全的核心是 **AAA 框架**，三者构成了完整的访问控制闭环：

| 概念 | 英文 | 说明 | 核心问题 |
|------|------|------|----------|
| 认证 | Authentication | 验证用户身份的真实性 | 你是谁？ |
| 授权 | Authorization | 决定用户可访问的资源和操作 | 你能做什么？ |
| 审计 | Accounting | 记录用户的所有操作行为 | 你做了什么？ |

**三者关系**：
```
用户请求 → 【认证】验证身份 → 【授权】检查权限 → 【审计】记录操作 → 返回结果
```

**实际案例**：
- 员工登录公司系统（认证）→ 只能访问自己部门的文件（授权）→ 所有文件操作被记录（审计）
- 银行APP登录（认证）→ 只能查看自己的账户（授权）→ 每笔交易都有日志（审计）

### 1.2 身份认证的定义

身份认证是指**通过一定的手段确认用户身份真实性的过程**，确保当前请求者确实是其所声称的身份。

**认证的本质**：
- 证明你拥有某种**唯一且难以伪造**的东西
- 认证强度取决于伪造该东西的难度

**常见认证场景**：
- 系统登录（用户名+密码）
- 门禁刷卡
- 手机解锁（指纹/面容）
- 网银U盾
- 邮箱验证链接

## 二、认证因素（Authentication Factors）

### 2.1 五大认证因素

| 因素类型 | 英文 | 说明 | 示例 | 安全等级 |
|----------|------|------|------|----------|
| 知识因素 | Something you know | 你知道的信息 | 密码、PIN码、安全问题 | ★★☆ |
| 持有因素 | Something you have | 你拥有的物品 | 手机、硬件令牌、U盾、智能卡 | ★★★ |
| 特征因素 | Something you are | 你的生物特征 | 指纹、人脸、虹膜、声纹 | ★★★★ |
| 位置因素 | Somewhere you are | 你所在的位置 | IP地址、GPS定位、基站信息 | ★★☆ |
| 时间因素 | Sometime you do it | 行为时间特征 | 登录时间、操作习惯、击键动力学 | ★★☆ |

### 2.2 知识因素详解

**特点**：
- 最容易实现和使用
- 最容易被窃取或破解
- 用户记忆负担重

**常见形式**：
1. **静态密码**：固定不变的字符串
2. **PIN码**：数字密码，常用于ATM、手机
3. **安全问题**：母亲的 maiden name、小学名称等
4. **图形密码**：Android 解锁图案

**安全风险**：
- 弱密码：123456、password、qwerty
- 密码复用：多个网站使用同一密码
- 社会工程学：钓鱼、社工库
- 键盘记录器：木马记录按键
- 肩窥：他人偷窥输入

### 2.3 持有因素详解

**特点**：
- 需要物理介质
- 丢失后存在安全风险
- 安全性高于知识因素

**常见形式**：
1. **手机**：短信验证码、推送通知、TOTP应用
2. **硬件令牌**：RSA SecurID、动态口令牌
3. **智能卡**：银行卡、门禁卡、员工卡
4. **安全密钥**：YubiKey、Google Titan（U2F/WebAuthn）
5. **数字证书**：存储在USB Key或智能卡中

**安全风险**：
- 设备丢失或被盗
- SIM卡劫持（SIM Swap）
- 令牌克隆
- 中间人攻击

### 2.4 特征因素详解

**特点**：
- 随身携带，不会遗忘
- 无法更改（泄露后永久风险）
- 存在隐私问题

**常见形式**：
1. **指纹识别**：最普及的生物识别
2. **人脸识别**：Face ID、刷脸支付
3. **虹膜识别**：准确率最高
4. **声纹识别**：远程身份验证
5. **静脉识别**：手掌/手指静脉
6. **步态识别**：走路姿势

**安全风险**：
- 生物特征数据库泄露（不可撤销）
- 欺骗攻击（假指纹、3D人脸面具）
- 误识率（FAR）和拒识率（FRR）
- 隐私与合规问题（GDPR、个人信息保护法）

### 2.5 位置与时间因素

**位置因素**：
- IP地址地理位置
- GPS定位（移动端）
- WiFi/蓝牙信标
- 常用地点白名单

**时间/行为因素**：
- 登录时间异常检测
- 击键动力学（打字节奏）
- 鼠标移动轨迹
- 常用设备识别

> **注意**：位置和时间因素通常作为**辅助认证**或**风险评估**的依据，不单独作为主认证因素。

## 三、密码认证技术

### 3.1 密码存储的演进

#### 明文存储（已淘汰）
```
数据库中直接存储密码明文
user: admin | password: 123456
```
**风险**：数据库泄露即密码全部泄露。

#### 哈希存储（不安全）
```
使用 MD5/SHA1 等哈希算法存储
user: admin | password_hash: e10adc3949ba59abbe56e057f20f883e
```
**风险**：彩虹表攻击、相同密码哈希值相同。

#### 加盐哈希（改进）
```
每个用户使用不同的随机盐值
salt = random_string()
password_hash = hash(salt + password)
存储: salt + password_hash
```
**优点**：相同密码产生不同哈希，彩虹表失效。

#### 慢哈希算法（当前最佳实践）
```
使用 bcrypt / Argon2 / PBKDF2 等故意设计得很慢的算法
password_hash = bcrypt(password, cost_factor)
```
**优点**：大幅提高暴力破解的时间成本。

### 3.2 加盐哈希原理

**什么是盐（Salt）**：
- 盐是一个随机生成的字符串
- 每个用户的盐都不同
- 盐和密码哈希一起存储

**工作流程**：
```python
# 注册时
salt = generate_random_salt()  # 如: "x7$kL9#mP2"
hash_value = sha256(salt + password)  # 加盐后哈希
存储: salt + ":" + hash_value

# 登录验证时
salt, stored_hash = 从数据库读取
computed_hash = sha256(salt + input_password)
if computed_hash == stored_hash:
    登录成功
```

**为什么加盐有效**：
- 相同密码 + 不同盐 = 不同哈希值
- 攻击者无法使用预先计算的彩虹表
- 必须逐个用户破解，成本大幅提升

**盐的安全要求**：
- 长度足够（至少16字节）
- 密码学安全的随机数
- 每个用户独立的盐
- 盐不需要保密，但必须唯一

### 3.3 bcrypt 算法详解

**bcrypt 简介**：
- 由 Niels Provos 和 David Mazieres 于1999年设计
- 基于 Blowfish 密码算法
- 专门为密码存储设计的慢哈希算法
- 内置盐值生成和管理

**bcrypt 哈希格式**：
```
$2b$12$x7kL9mP2qR8sT5vYw3zA1u$.Kp3J9nM8w7xQ4rT6yU9iO2pA1sD5fG7
 └─┘ └┘ └───────────────────────┘ └─────────────────────────────┘
  |   |           |                               |
  |   |         salt                            hash
  |  cost factor (2^12 = 4096 次迭代)
 版本标识 (2a/2b/2y)
```

**成本因子（Cost Factor）**：
- 控制计算速度，值越大越慢
- 取值范围：4-31
- 实际是 2^cost 次迭代
- 推荐值：12（约250ms/次）
- 应根据硬件性能调整，确保单次计算耗时约100-500ms

**bcrypt 的局限性**：
- 最大密码长度：72字节
- 内存使用较少，GPU/ASIC加速效果明显
- 已被 Argon2 超越，但仍广泛使用

### 3.4 Argon2 算法详解

**Argon2 简介**：
- 2015年密码哈希竞赛（PHC）获胜者
- 现代密码哈希算法标准
- 三种变体：Argon2d、Argon2i、Argon2id

**三种变体对比**：

| 变体 | 特点 | 适用场景 |
|------|------|----------|
| Argon2d | 最快，抗GPU攻击强，但侧信道风险高 | 加密货币、密码学货币 |
| Argon2i | 抗侧信道攻击，但抗GPU较弱 | 密码存储（旧版推荐） |
| Argon2id | 结合两者优点，平衡安全性 | 密码存储（当前推荐） |

**Argon2 参数**：

| 参数 | 说明 | 推荐值 |
|------|------|--------|
| memory | 内存使用量（KB） | 65536 (64MB) |
| iterations | 迭代次数 | 3 |
| parallelism | 并行度（线程数） | 4 |
| salt length | 盐长度 | 16字节 |
| hash length | 哈希长度 | 32字节 |

**Argon2 哈希格式**：
```
$argon2id$v=19$m=65536,t=3,p=4$c29tZXNhbHQ$RdescudvJCsgt3ub+b+dWRWJTmaaJObG
```

**为什么 Argon2 更安全**：
- 内存硬函数（Memory-Hard Function）：需要大量内存
- GPU/ASIC 难以并行加速
- 可配置内存、时间、并行度三个维度

### 3.5 PBKDF2 算法

**PBKDF2 简介**：
- Password-Based Key Derivation Function 2
- RSA 实验室 PKCS #5 标准定义
- NIST 推荐的标准算法

**工作原理**：
```
DK = PBKDF2(PRF, Password, Salt, c, dkLen)

其中：
- PRF: 伪随机函数（通常是 HMAC-SHA256）
- Password: 用户密码
- Salt: 盐值
- c: 迭代次数
- dkLen: 派生密钥长度
```

**推荐参数**：
- HMAC-SHA256 作为 PRF
- 迭代次数：至少 100,000 次（随硬件提升）
- 盐长度：至少 16 字节
- 输出长度：至少 32 字节

**对比总结**：

| 算法 | 抗GPU | 抗侧信道 | 标准地位 | 推荐程度 |
|------|-------|----------|----------|----------|
| MD5/SHA | 极差 | 好 | 已淘汰 | ❌ 不推荐 |
| 加盐SHA | 差 | 好 | 常见但不安全 | ❌ 不推荐 |
| PBKDF2 | 一般 | 好 | NIST标准 | ⚠️ 兼容用 |
| bcrypt | 较好 | 好 | 工业界广泛使用 | ✅ 推荐 |
| Argon2id | 最好 | 好 | PHC冠军 | ✅✅ 首选 |

### 3.6 密码攻击与防护

#### 常见密码攻击方式

| 攻击方式 | 原理 | 防护措施 |
|----------|------|----------|
| 暴力破解 | 尝试所有可能组合 | 强密码策略、登录限流、慢哈希 |
| 字典攻击 | 使用常用密码字典 | 强密码策略、密码复杂度检查 |
| 彩虹表 | 预计算哈希对照表 | 加盐哈希、使用bcrypt/Argon2 |
| 凭证填充 | 使用其他网站泄露的密码 | MFA、异常登录检测、密码泄露检测 |
| 社会工程学 | 欺骗用户透露密码 | 安全意识培训、钓鱼防护 |
| 键盘记录 | 木马记录键盘输入 | 反病毒软件、软键盘、硬件令牌 |
| 肩窥 | 偷窥用户输入 | 隐私屏、遮挡输入 |

#### 密码安全最佳实践

**密码策略**：
- 最小长度：至少12位（NIST最新建议关注长度而非复杂度）
- 允许使用所有字符（包括空格、emoji）
- 禁止使用常见弱密码（与泄露密码库比对）
- 不强制定期更换密码（NIST已取消此建议）
- 不强制密码复杂度规则（大小写+数字+符号）

**系统防护**：
- 使用 Argon2id 或 bcrypt 存储密码
- 限制登录尝试次数（如5次后锁定15分钟）
- 登录异常检测（异地登录、新设备登录）
- 验证码防止自动化攻击
- HTTPS 传输加密
- 密码哈希使用常数时间比较（防止时序攻击）

**用户侧建议**：
- 使用密码管理器（1Password、Bitwarden、KeePass）
- 每个网站使用唯一密码
- 启用多因素认证（MFA）
- 定期检查密码是否泄露（haveibeenpwned.com）

## 四、多因素认证（MFA / 2FA）

### 4.1 MFA 基础概念

**定义**：多因素认证（Multi-Factor Authentication）要求用户提供**两种或以上不同类型**的认证因素。

**为什么需要 MFA**：
- 单一因素认证（如密码）容易被攻破
- MFA 大幅提高攻击成本
- 即使密码泄露，攻击者仍无法登录

**MFA 认证强度对比**：

| 认证方式 | 安全等级 | 说明 |
|----------|----------|------|
| 仅密码 | ★☆☆☆☆ | 极易被攻破 |
| 密码+短信 | ★★☆☆☆ | SIM劫持可绕过 |
| 密码+TOTP | ★★★★☆ | 较安全，需手机 |
| 密码+推送 | ★★★☆☆ | 疲劳攻击风险 |
| 密码+U2F | ★★★★★ | 最安全，防钓鱼 |

### 4.2 短信认证与安全

**工作原理**：
```
用户登录 → 系统发送验证码短信 → 用户输入验证码 → 验证通过
```

**优点**：
- 用户接受度高，普及广泛
- 实现简单
- 不需要额外安装应用

**安全风险**：

| 风险 | 说明 |
|------|------|
| **SIM劫持** | 攻击者通过社工让运营商补办SIM卡，接管手机号 |
| **短信嗅探** | 通过伪基站拦截短信 |
| **SS7漏洞** | 利用信令网漏洞拦截短信 |
| **钓鱼攻击** | 假网站诱导输入验证码 |
| **号码转移** | 手机号转网/过户导致 |

**真实案例**：
> 2019年，Twitter CEO Jack Dorsey 的Twitter账号被黑客通过 SIM Swap 攻击劫持，发布了多条种族歧视言论。黑客通过社工攻击运营商，将Dorsey的手机号转移到自己的SIM卡上，从而绕过了短信验证。

**短信验证防护建议**：
- 关键账号不要仅依赖短信验证
- 使用 TOTP 或硬件密钥作为更强的MFA方式
- 手机号设置运营商PIN码保护
- 监控手机号异常活动

### 4.3 TOTP 基于时间的一次性密码

**TOTP 简介**：
- Time-based One-Time Password
- 基于时间的一次性密码算法
- RFC 6238 标准
- 基于 HOTP（RFC 4226）发展而来

**工作原理**：
```
密钥 (Secret Key) + 当前时间戳 → HMAC-SHA1 → 截断 → 6位数字验证码

验证码每30秒刷新一次
```

**TOTP 算法步骤**：
```python
# 1. 获取当前时间步长（每30秒为一步）
time_step = floor(current_timestamp / 30)

# 2. 将时间步长转为8字节
time_bytes = time_step.to_bytes(8, byteorder='big')

# 3. 使用密钥计算HMAC-SHA1
hmac_result = hmac.new(secret_key, time_bytes, sha1).digest()

# 4. 动态截断（DT）
offset = hmac_result[19] & 0x0F  # 取最后一个字节的低4位作为偏移
binary_code = ((hmac_result[offset] & 0x7F) << 24) |
              ((hmac_result[offset+1] & 0xFF) << 16) |
              ((hmac_result[offset+2] & 0xFF) << 8) |
              (hmac_result[offset+3] & 0xFF)

# 5. 取模得到6位数字
otp = binary_code % 1000000
```

**常用 TOTP 应用**：
- Google Authenticator
- Microsoft Authenticator
- Authy
- 1Password（内置）
- Bitwarden（内置）

**TOTP 的安全风险**：
- 密钥泄露（手机丢失、备份泄露）
- 钓鱼攻击（假网站诱导输入验证码）
- 时间偏移问题
- 无法防止中间人攻击

### 4.4 推送通知认证

**工作原理**：
```
用户登录 → 服务器推送通知到用户手机App → 用户确认/拒绝
```

**优点**：
- 用户体验好，一键确认
- 比TOTP更便捷
- 可显示登录详情（位置、设备、时间）

**安全风险 — MFA 疲劳攻击（MFA Fatigue Attack）**：

> **攻击原理**：攻击者不断发送MFA推送请求，直到用户不堪其扰而误点确认。

**真实案例**：
> 2022年 Uber 被黑客入侵，黑客获取了一名员工的密码后，不断向该员工发送 Duo MFA 推送请求，最终员工不堪其扰点击了"接受"，黑客成功登录系统。

**防护措施**：
- 限制推送频率
- 增加"拒绝并阻止"选项
- 显示详细登录信息
- 异常推送自动告警
- 使用号码匹配（Number Matching）

### 4.5 生物识别认证

**生物识别系统组成**：
```
采集 → 预处理 → 特征提取 → 特征匹配 → 结果输出
```

**关键指标**：

| 指标 | 英文 | 说明 |
|------|------|------|
| 误识率 | FAR (False Acceptance Rate) | 把假的认成真的概率 |
| 拒真率 | FRR (False Rejection Rate) | 把真的当成假的概率 |
| 等错误率 | EER (Equal Error Rate) | FAR=FRR时的错误率，越小越好 |

**常见生物识别技术对比**：

| 技术 | 准确率 | 便利性 | 抗欺骗性 | 隐私风险 | 成本 |
|------|--------|--------|----------|----------|------|
| 指纹 | 高 | 高 | 中 | 中 | 低 |
| 人脸 | 中 | 很高 | 低 | 高 | 低 |
| 虹膜 | 很高 | 中 | 高 | 高 | 高 |
| 声纹 | 低 | 高 | 低 | 中 | 低 |
| 静脉 | 很高 | 中 | 高 | 中 | 中 |

**生物识别安全风险**：

1. **不可逆性**：生物特征泄露后无法更改（密码可以改，指纹改不了）
2. **欺骗攻击**：
   - 指纹：硅胶假指纹、打印指纹
   - 人脸：3D面具、照片、视频
   - 声纹：语音合成、录音
3. **隐私问题**：生物特征属于敏感个人信息
4. **偏见问题**：对不同种族/性别准确率不同

**生物识别最佳实践**：
- 存储特征模板而非原始生物数据
- 本地比对，不上传原始数据（如iPhone Face ID）
- 作为多因素之一，不单独使用
- 提供备用认证方式（如密码）
- 遵守相关法规（个人信息保护法、GDPR）

## 五、硬件令牌与 FIDO / WebAuthn

### 5.1 硬件令牌概述

**硬件令牌**：一种物理设备，用于生成或存储认证凭证，提供强身份认证。

**硬件令牌类型**：

| 类型 | 原理 | 示例 |
|------|------|------|
| 时间型令牌 | 基于时间生成动态密码 | RSA SecurID |
| 事件型令牌 | 基于事件计数生成密码 | HOTP令牌 |
| 挑战-响应型 | 接收挑战码，计算响应 | 银行U盾 |
| 公钥型令牌 | 非对称加密，私钥不出设备 | YubiKey（U2F/FIDO2） |

### 5.2 U2F 通用第二因素

**U2F 简介**：
- Universal 2nd Factor
- 由 Google 和 Yubico 联合开发
- FIDO 联盟标准
- 基于公钥密码学

**U2F 工作原理**：

**注册流程**：
```
1. 用户访问网站，点击注册U2F设备
2. 网站生成挑战（challenge）
3. 用户插入U2F设备并按下按钮
4. 设备生成新的密钥对（私钥存在设备中，公钥发给网站）
5. 网站存储公钥和Key Handle
```

**认证流程**：
```
1. 用户登录，网站发送挑战 + Key Handle
2. 用户插入U2F设备并按下按钮
3. 设备用对应私钥签名挑战
4. 网站用公钥验证签名
5. 验证通过，登录成功
```

**U2F 的优势**：
- 防钓鱼：绑定域名，假网站无法验证通过
- 防中间人攻击
- 物理设备，无法远程窃取
- 使用简单，一键操作
- 一个设备可绑定多个网站

### 5.3 WebAuthn / FIDO2

**WebAuthn 简介**：
- Web Authentication API
- W3C 推荐标准（2019年）
- FIDO2 规范的核心组件
- 浏览器内置支持

**WebAuthn vs U2F**：

| 特性 | U2F | WebAuthn |
|------|-----|----------|
| 仅第二因素 | ✅ | ✅ |
| 无密码登录 | ❌ | ✅ |
| 平台认证器 | ❌ | ✅（Touch ID、Face ID、Windows Hello） |
| 跨平台认证器 | ✅ | ✅（YubiKey等） |
| 用户验证 | 可选 | 支持 |

**WebAuthn 核心概念**：

| 概念 | 说明 |
|------|------|
| 认证器（Authenticator） | 生成和存储密钥的设备 |
| 平台认证器 | 内置在设备中（Touch ID、Face ID） |
| 跨平台认证器 | 可移除的硬件设备（YubiKey） |
| 依赖方（Relying Party） | 使用WebAuthn的网站/应用 |
| 凭证（Credential） | 公钥密钥对 |
| 用户验证（User Verification） | 验证用户本人（指纹、PIN） |

**WebAuthn 认证流程**：
```
客户端（浏览器）                    服务器（Relying Party）
     |                                     |
     |-------- 请求认证挑战 ---------------->|
     |                                     | 生成挑战
     |<------- 返回挑战 + 凭证ID ----------|
     |
     | 调用 WebAuthn API
     | → 提示用户操作（按按钮/指纹）
     | → 认证器签名
     |
     |-------- 签名结果 ------------------->|
     |                                     | 验证签名
     |<------- 认证结果 -------------------|
```

**支持情况**：
- 浏览器：Chrome、Firefox、Safari、Edge 均已支持
- 平台：Windows Hello、Apple Touch ID/Face ID、Android指纹
- 硬件：YubiKey、Google Titan Key、Solo Key

## 六、单点登录（SSO）

### 6.1 SSO 基础概念

**定义**：单点登录（Single Sign-On）允许用户**一次登录**，即可访问**多个相互信任的应用系统**，无需重复认证。

**SSO 的核心价值**：

| 价值 | 说明 |
|------|------|
| 用户体验 | 只需记住一个密码，减少登录次数 |
| 安全提升 | 减少密码数量，降低泄露风险；集中管理认证策略 |
| 管理效率 | 统一身份管理，降低IT支持成本 |
| 合规审计 | 集中审计所有访问行为 |

### 6.2 SSO 架构模型

#### 集中式认证架构
```
┌─────────┐     ┌──────────────┐     ┌─────────┐
│ 应用A   │     │  认证中心     │     │ 应用B   │
│ (SP)    │<───>│  (IdP)       │<───>│ (SP)    │
└─────────┘     └──────────────┘     └─────────┘
                       │
                       v
                  ┌─────────┐
                  │ 应用C   │
                  │ (SP)    │
                  └─────────┘

IdP: Identity Provider（身份提供者）
SP: Service Provider（服务提供者）
```

### 6.3 SSO 主要协议对比

| 协议 | 发布时间 | 数据格式 | 主要用途 | 适用场景 |
|------|----------|----------|----------|----------|
| SAML | 2005 | XML | 企业级SSO | 企业内部、B2B |
| OAuth 2.0 | 2012 | JSON | 授权框架 | API授权、第三方登录 |
| OIDC | 2014 | JSON/JWT | 身份层（基于OAuth） | 现代Web/移动应用 |
| CAS | 2004 | XML/JSON | 高校SSO | 教育行业 |
| Kerberos | 1980s | 二进制 | 域环境SSO | Windows AD、企业内网 |

### 6.4 SAML 协议详解

**SAML 简介**：
- Security Assertion Markup Language
- 基于 XML 的开放标准
- OASIS 组织制定
- 企业级 SSO 的事实标准

**SAML 核心角色**：
- **主体（Principal）**：最终用户
- **身份提供者（IdP）**：负责认证和断言用户身份
- **服务提供者（SP）**：提供服务的应用，信任IdP的断言

**SAML 断言（Assertion）**：
- IdP 签发的 XML 文档
- 包含用户身份信息
- 包含认证信息（何时、如何认证）
- 数字签名保证真实性

**SAML 工作流程（SP 发起）**：

```
1. 用户访问 SP 受保护资源
   ↓
2. SP 生成 SAML AuthnRequest
   ↓
3. 用户浏览器重定向到 IdP
   ↓
4. 用户在 IdP 完成认证（如用户名密码）
   ↓
5. IdP 生成 SAML Assertion（签名）
   ↓
6. 用户浏览器 POST 到 SP 的 ACS URL
   ↓
7. SP 验证 SAML Assertion 签名
   ↓
8. SP 创建用户会话，授权访问
```

**SAML 安全风险**：
- XML 签名包装攻击（Signature Wrapping）
- 断言伪造
- 重放攻击
- 属性注入
- 未加密的断言内容

### 6.5 OAuth 2.0 简介

**OAuth 2.0 是什么**：
- 授权框架（Authorization Framework）
- **不是认证协议**
- 允许第三方应用在用户授权下访问其资源
- 使用令牌而非凭证

**OAuth 2.0 四个角色**：

| 角色 | 说明 | 示例 |
|------|------|------|
| 资源所有者 | 用户 | 你 |
| 客户端 | 第三方应用 | 某网站想用微信登录 |
| 授权服务器 | 颁发令牌的服务器 | 微信授权服务器 |
| 资源服务器 | 存储用户资源的服务器 | 微信用户信息服务器 |

**OAuth 2.0 授权码模式流程**：
```
1. 用户点击"用XX登录"
   ↓
2. 重定向到授权服务器
   ?response_type=code
   &client_id=xxx
   &redirect_uri=xxx
   &scope=xxx
   ↓
3. 用户授权（登录并确认）
   ↓
4. 重定向回客户端，携带授权码
   redirect_uri?code=xxx
   ↓
5. 客户端用授权码换取令牌
   POST /token
   grant_type=authorization_code
   &code=xxx
   &redirect_uri=xxx
   &client_id=xxx
   &client_secret=xxx
   ↓
6. 返回 Access Token
```

### 6.6 OpenID Connect (OIDC)

**OIDC 简介**：
- OpenID Connect
- 基于 OAuth 2.0 的身份层
- 提供用户认证信息
- 使用 JWT 格式的 ID Token

**OIDC 在 OAuth 2.0 基础上增加了什么**：
- **ID Token**：身份令牌，包含用户身份信息（JWT格式）
- **UserInfo 端点**：获取更多用户信息的API
- **标准化的用户信息**：sub（用户ID）、name、email等

**OIDC 三种 Token**：

| Token | 作用 | 格式 |
|-------|------|------|
| ID Token | 证明用户身份 | JWT |
| Access Token | 访问资源服务器 | 任意（通常JWT） |
| Refresh Token | 刷新Access Token | 字符串 |

## 七、实际案例分析

### 案例一：密码泄露导致的大规模账户入侵

**事件**：某社交平台数据库泄露，包含5亿用户的密码哈希（MD5，未加盐）。

**攻击过程**：
1. 攻击者获取数据库备份
2. 使用彩虹表快速破解了90%以上的弱密码
3. 使用破解的密码尝试登录其他网站（凭证填充）
4. 大量用户在其他平台的账户也被入侵

**根本原因**：
- 使用了不安全的 MD5 哈希算法
- 没有加盐
- 没有强制强密码策略

**改进措施**：
1. 立即将密码哈希算法升级为 Argon2id
2. 所有用户强制重置密码
3. 强制启用 MFA
4. 接入密码泄露检测 API（如 HIBP）
5. 实施凭证填充防护

### 案例二：SIM 劫持攻击盗取加密货币

**事件**：某加密货币投资者手机号被 SIM 劫持，价值100万的加密货币被盗。

**攻击过程**：
1. 攻击者通过社交媒体收集受害者个人信息
2. 打电话给运营商，冒充受害者要求补办SIM卡
3. 运营商客服被社工，成功补办SIM卡
4. 攻击者使用短信验证码登录交易所
5. 重置密码，转走所有加密货币

**教训**：
- 不要仅依赖短信作为MFA方式
- 交易所应提供更强的MFA选项（TOTP/U2F）
- 用户应设置运营商服务密码/PIN
- 大额资产应使用硬件钱包

### 案例三：MFA 疲劳攻击入侵企业

**事件**：某企业遭到勒索软件攻击，最初入口是通过 MFA 疲劳攻击获取的员工VPN账号。

**攻击过程**：
1. 攻击者通过钓鱼获取了一名员工的密码
2. 攻击者开始不断尝试VPN登录，触发MFA推送
3. 员工在深夜被持续的推送打扰，不慎点击了"接受"
4. 攻击者成功登录VPN，进入内网
5. 横向移动，部署勒索软件

**改进措施**：
1. 限制MFA推送频率（如每小时最多5次）
2. 启用号码匹配（Number Matching）
3. 显示登录详情（地理位置、设备信息）
4. 异常登录自动告警
5. 员工安全意识培训
