# 身份管理体系（IAM）

> 身份与访问管理（Identity and Access Management，IAM）是企业安全的基础设施，负责管理"谁能访问什么"的全生命周期。本文详细介绍 IAM 体系架构、核心组件和关键技术。

---

## 一、IAM 概念与架构

### 1.1 什么是 IAM

**IAM（Identity and Access Management）**：身份与访问管理，是一套用于管理数字身份、控制访问权限、确保合规审计的技术体系、流程和策略的组合。

**IAM 的核心目标**：
- 确保正确的人（身份）
- 在正确的时间（时机）
- 以正确的理由（业务需要）
- 访问正确的资源（权限）
- 并且所有操作可审计

**IAM 覆盖的范围**：
```
┌─────────────────────────────────────────────────┐
│                  IAM 体系                         │
├──────────┬──────────┬──────────┬────────────────┤
│  身份管理  │  认证管理  │  授权管理  │  审计与治理    │
│ (Identity)│(Authentication)│(Authorization)│(Governance)│
├──────────┼──────────┼──────────┼────────────────┤
│ 用户管理  │ 密码认证  │ RBAC     │ 权限审查       │
│ 目录服务  │ MFA     │ ABAC     │ 合规报告       │
│ 生命周期  │ SSO     │ 策略管理  │ 身份分析       │
│ 身份联邦  │ 生物识别  │ 特权管理  │ 风险评估       │
└──────────┴──────────┴──────────┴────────────────┘
```

### 1.2 IAM 的业务价值

| 价值维度 | 说明 |
|----------|------|
| **安全提升** | 统一身份管理，减少身份泄露和越权访问风险 |
| **合规保障** | 满足等保、GDPR、SOX等合规要求 |
| **效率提升** | 自动化身份生命周期管理，减少人工操作 |
| **用户体验** | SSO单点登录，减少密码记忆负担 |
| **成本降低** | 集中管理降低运维成本 |
| **业务赋能** | 快速支撑新业务上线，敏捷交付 |

### 1.3 IAM 架构模型

#### 传统 IAM 架构

### 1.4 IAM 核心组件

| 组件 | 功能 | 典型产品/技术 |
|------|------|--------------|
| 目录服务 | 存储身份信息 | Active Directory、OpenLDAP |
| 身份管理 | 用户生命周期管理 | IdM、IGA 平台 |

| 审计治理 | 合规与审计 | IGA、SIEM、身份分析 |

## 二、目录服务

### 2.1 目录服务概述

**目录服务（Directory Service）**：一种专门用于存储、检索和管理分布式信息的数据库服务，主要存储用户、设备、应用等身份相关信息。

**目录服务的特点**：
- 读多写少的优化（查询频繁，修改较少）
- 树形层次结构
- 支持复杂查询
- 分布式架构，可复制
- 标准协议访问（LDAP）

### 2.2 LDAP 协议

**LDAP（Lightweight Directory Access Protocol）**：轻量级目录访问协议，是访问目录服务的标准协议。

**LDAP 数据模型**：

| 概念 | 说明 | 类比 |
|------|------|------|
| 条目（Entry） | 目录中的基本单元 | 数据库中的一行记录 |
| 属性（Attribute） | 条目的特性 | 数据库中的字段 |
| 对象类（ObjectClass） | 属性的集合，定义条目类型 | 数据库中的表结构 |
| DN（Distinguished Name） | 条目的唯一标识 | 主键 + 完整路径 |
| RDN（Relative DN） | 相对唯一标识 | 相对路径 |

**LDAP 目录树示例**：
```
dc=example,dc=com
├── ou=people
│   ├── uid=alice
│   │   ├── cn: Alice Wang
│   │   ├── mail: alice@example.com
│   │   ├── telephoneNumber: 12345
│   │   └── objectClass: inetOrgPerson
│   └── uid=bob
│       ├── cn: Bob Li
│       └── ...
├── ou=groups
│   ├── cn=developers
│   │   ├── member: uid=alice,ou=people,...
│   │   └── member: uid=bob,ou=people,...
│   └── cn=admins
│       └── ...
└── ou=devices
    └── ...
```

**常用 LDAP 操作**：

| 操作 | 说明 |
|------|------|
| Bind | 认证连接 |
| Search | 搜索查询条目 |
| Add | 添加新条目 |
| Modify | 修改条目属性 |
| Delete | 删除条目 |
| Compare | 比较属性值 |

**LDAP 搜索过滤器示例**：
```
# 查找所有用户
(objectClass=person)

# 查找用户名为alice的用户
(&(objectClass=person)(uid=alice))

# 查找开发部门的所有用户
(&(objectClass=person)(ou=developers))

# 查找姓"王"且邮箱在example.com的用户
(&(objectClass=person)(sn=王*)(mail=*@example.com))
```

### 2.3 Active Directory (AD)

**Active Directory**：微软的目录服务，是 Windows 域环境的核心，广泛应用于企业 IT 基础设施。

#### AD 核心概念

| 概念 | 说明 |
|------|------|
| 域（Domain） | 安全边界，一组计算机和用户的集合 |
| 域控制器（DC） | 运行 AD 服务的服务器 |
| 林（Forest） | 一个或多个域树的集合，最高安全边界 |
| 域树（Tree） | 共享连续命名空间的域集合 |
| OU（组织单元） | 域内的管理单元，用于组织对象 |
| 组（Group） | 用户/计算机的集合，用于分配权限 |
| GPO（组策略） | 批量配置计算机和用户设置 |

**AD 逻辑结构**：
```
Forest: example.com
├── Tree: example.com
│   ├── Domain: example.com
│   │   ├── OU: HQ
│   │   │   ├── OU: Users
│   │   │   ├── OU: Computers
│   │   │   └── OU: Groups
│   │   └── OU: Servers
│   └── Domain: child.example.com
│       └── ...
└── Tree: otherdomain.com
    └── ...
```

#### AD 对象类型

| 对象类型 | 说明 | 安全标识符（SID） |
|----------|------|-------------------|
| 用户（User） | 人员账号 | 用户SID |
| 计算机（Computer） | 加入域的计算机 | 计算机SID |
| 组（Group） | 用户/计算机的集合 | 组SID |
| OU | 组织单元 | 无SID（不是安全主体） |
| 联系人（Contact） | 外部联系人信息 | 无SID |
| 打印机 | 共享打印机 | 无SID |

#### AD 组类型与作用域

**组类型**：
- **安全组**：用于分配权限，也可用于邮件
- **通讯组**：仅用于邮件分发，无安全功能

**组作用域**：

| 作用域 | 成员来源 | 权限范围 | 可嵌套 |
|--------|---------|----------|--------|
| 本地域组（Domain Local） | 所有信任域 | 本域 | 不能嵌套全局组 |
| 全局组（Global） | 本域 | 所有信任域 | 可嵌套到本地域组 |
| 通用组（Universal） | 林中所有域 | 林中所有域 | 可互相嵌套 |

**AGDLP 原则**（推荐的组策略使用方式）：
```
用户账户 (Accounts)
   → 加入全局组 (Global Groups)
      → 加入本地域组 (Domain Local Groups)
         → 分配权限 (Permissions)
```

#### AD 认证协议

| 协议 | 说明 | 用途 |
|------|------|------|
| Kerberos | 票据认证协议 | 域内主要认证协议 |
| NTLM | 挑战-响应认证 | 旧系统兼容、工作组环境 |
| LDAP Bind | LDAP绑定认证 | 应用集成 |
| Certificate | 证书认证 | 智能卡等 |

### 2.4 AD 安全 - Kerberos 协议

#### Kerberos 简介

**Kerberos**：一种网络认证协议，使用票据机制，无需在网络上传输密码，是 AD 域环境的核心认证协议。

**Kerberos 三个角色**：

| 角色 | 名称 | 说明 |
|------|------|------|
| 客户端 | Client | 请求访问的用户/服务 |
| 服务端 | Server | 提供资源的服务 |
| KDC | Key Distribution Center | 密钥分发中心（AS + TGS） |

**KDC 的两个组件**：
- **AS（Authentication Service）**：认证服务，颁发 TGT
- **TGS（Ticket Granting Service）**：票据授予服务，颁发 ST

#### Kerberos 认证流程

```
用户登录阶段：
1. 客户端 → AS: 认证请求 (预认证数据)
2. AS → 客户端: TGT (票据授予票据，用krbtgt哈希加密)

服务访问阶段：
3. 客户端 → TGS: 请求服务票据 + TGT
4. TGS → 客户端: ST (服务票据，用服务账号哈希加密)
5. 客户端 → 服务端: ST + Authenticator
6. 服务端 → 客户端: 验证响应 (可选)
```

**详细步骤**：

**第一步：获取 TGT（AS-REQ / AS-REP）**
```
AS-REQ (客户端 → KDC)：
- 用户Principal名称
- 服务Principal名称: krbtgt/域
- 时间戳（用用户密码哈希加密，用于预认证）

AS-REP (KDC → 客户端)：
- TGT (包含：会话密钥、用户信息、有效期)
  TGT 使用 krbtgt 账号的密码哈希加密
- 登录会话密钥 (用用户密码哈希加密)
```

**第二步：获取 ST（TGS-REQ / TGS-REP）**
```
TGS-REQ (客户端 → KDC)：
- TGT
- 认证符 (Authenticator，用会话密钥加密)
- 请求的服务Principal名称

TGS-REP (KDC → 客户端)：
- 服务票据 ST (包含：服务会话密钥、用户信息、有效期)
  ST 使用服务账号的密码哈希加密
- 服务会话密钥 (用登录会话密钥加密)
```

**第三步：访问服务（AP-REQ / AP-REP）**
```
AP-REQ (客户端 → 服务端)：
- ST
- 认证符 (用服务会话密钥加密)

服务端验证：
1. 用自己的密码哈希解密ST，获得服务会话密钥
2. 用服务会话密钥解密认证符
3. 验证时间戳（防重放）
4. 验证用户权限

AP-REP (服务端 → 客户端)：
- 可选，用于双向认证
```

#### Kerberos 安全特性

| 特性 | 说明 |
|------|------|
| 不传输密码 | 网络中没有明文或哈希密码 |
| 对称加密 | 使用对称加密（通常AES） |
| 时间敏感 | 票据有有效期，防重放 |
| 单点登录 | 一次认证，访问多个服务 |
| 相互认证 | 客户端和服务端互相验证 |

### 2.5 AD 攻击与防护

#### 常见 AD 攻击技术

| 攻击名称 | 原理 | 风险等级 |
|----------|------|----------|
| Pass-the-Hash (PtH) | 传递NTLM哈希进行认证 | 高 |
| Pass-the-Ticket (PtT) | 传递Kerberos票据进行认证 | 高 |
| 黄金票据（Golden Ticket） | 伪造TGT，拥有域内所有权限 | 极高 |
| 白银票据（Silver Ticket） | 伪造ST，访问特定服务 | 高 |
| Kerberoasting | 请求服务票据，离线破解服务账号密码 | 中高 |
| AS-REP Roasting | 对不需要预认证的用户，离线破解密码 | 中 |
| DCSync | 模拟DC同步，获取域内所有密码哈希 | 极高 |
| DCShadow | 伪造DC，注入恶意对象 | 极高 |

#### 攻击详解：黄金票据（Golden Ticket）

**原理**：
- 攻击者获取 krbtgt 账号的密码哈希
- 使用 krbtgt 哈希伪造任意用户的 TGT
- 拥有伪造的 TGT 就可以访问域内任何资源

**攻击步骤**：
```
1. 获取域管理员权限（或krbtgt哈希）
2. 提取krbtgt账号的NTLM哈希
3. 使用Mimikatz等工具伪造TGT：
   mimikatz "kerberos::golden /user:Administrator /domain:example.com /sid:S-1-5-21-... /krbtgt:哈希值 /ptt"
4. 注入伪造的TGT到内存
5. 以域管理员身份访问任意服务
```

**防护措施**：
- 保护 krbtgt 账号（强密码、定期更改）
- 限制域管理员登录范围
- 实施分层架构（Tier Model）
- 监控异常的 Kerberos 票据
- 定期轮换 krbtgt 密码（建议每半年）

#### 攻击详解：白银票据（Silver Ticket）

**原理**：
- 攻击者获取服务账号的密码哈希
- 伪造针对该服务的 ST（服务票据）
- 只能访问特定服务，比黄金票据范围小

**与黄金票据对比**：

| 特性 | 黄金票据 | 白银票据 |
|------|----------|----------|
| 所需哈希 | krbtgt 哈希 | 服务账号哈希 |
| 票据类型 | TGT | ST |
| 访问范围 | 所有服务 | 特定服务 |
| 与KDC交互 | 不需要 | 不需要 |
| 检测难度 | 较难（流量少） | 较难（流量少） |

#### 攻击详解：Kerberoasting

**原理**：
- 任何域用户都可以请求任意服务的服务票据（ST）
- ST 使用服务账号的密码哈希加密
- 攻击者可以请求 ST 后离线破解服务账号密码

**攻击步骤**：
```
1. 查找SPN（服务主体名称）对应的服务账号
2. 请求该服务的ST（不需要特殊权限）
3. 导出ST
4. 使用Hashcat等工具离线破解
5. 获得服务账号明文密码
```

**防护措施**：
- 服务账号使用强密码（越长越好）
- 定期轮换服务账号密码
- 监控异常的 TGS 请求
- 使用托管服务账号（MSA/组MSA）
- 限制普通用户可请求的SPN

#### 攻击详解：Pass-the-Hash

**原理**：
- NTLM 认证使用密码哈希
- 攻击者不需要明文密码，只要哈希就能认证

**攻击步骤**：
```
1. 从内存或SAM数据库中获取用户NTLM哈希
2. 使用Mimikatz或其他工具进行PtH攻击
3. 直接使用哈希进行认证，访问目标系统
```

**防护措施**：
- 限制管理员登录范围（防止哈希被窃取）
- 实施 LSA 保护（RunAsPPL）
- 使用 Windows Defender Credential Guard
- 禁用 NTLM，改用 Kerberos
- 管理员账号使用受保护的用户组

#### 攻击详解：DCSync

**原理**：
- 利用 AD 复制功能
- 模拟域控制器向其他DC请求同步数据
- 获取域内所有用户的密码哈希

**前提条件**：
- 拥有以下权限之一：
  - 域管理员权限
  - 复制目录更改（DS-Replication-Get-Changes）
  - 复制目录更改全部（DS-Replication-Get-Changes-All）

**防护措施**：
- 严格控制复制权限
- 监控域控制器之间的复制流量
- 监控异常的复制请求来源
- 实施分层架构

#### AD 防护体系：分层架构（Tier Model）

**微软推荐的 AD 分层安全模型**：

```
Tier 0: 管理员层（最高权限）
├── 域控制器
├── 域管理员
├── 企业管理员
└── 关键基础设施
    │
    │ 严格隔离，只能从专用管理工作站访问
    ▼
Tier 1: 服务器/应用层
├── 成员服务器
├── 应用服务器
├── 数据库服务器
└── 服务器管理员
    │
    ▼
Tier 2: 工作站/用户层
├── 用户计算机
├── 普通用户
└── 帮助台
```

**分层原则**：
- 高层级账号不能登录低层级设备
- 低层级账号不能管理高层级资源
- 各层之间使用独立的管理员账号
- Tier 0 账号只能在专用管理工作站使用

## 三、身份生命周期管理

### 3.1 什么是身份生命周期

**身份生命周期（Identity Lifecycle）**：指一个身份从创建到删除的整个过程，涵盖身份存在的所有阶段。

**生命周期阶段**：
```
创建 → 变更 → 停用 → 删除
  │      │      │
  └──────┴──────┴──→ 审计（贯穿始终）
```

### 3.2 各阶段详细说明

#### 阶段一：创建（Create）

**触发事件**：
- 新员工入职
- 新合作伙伴接入
- 新应用系统上线
- 临时人员加入

**关键活动**：
1. **身份创建**：在目录系统中创建账号
2. **属性维护**：填写姓名、部门、职位等信息
3. **权限分配**：根据角色分配初始权限
4. **账号开通**：开通相关系统访问权限
5. **通知**：通知用户和相关人员

**最佳实践**：
- 自动化：与HR系统集成，入职自动创建账号
- 标准化：统一命名规则、初始密码策略
- 最小权限：只分配岗位必需的初始权限
- 审核：关键账号需要审批

#### 阶段二：变更（Change）

**触发事件**：
- 岗位调整、晋升
- 部门调动
- 职位变更
- 姓名变更

**关键活动**：
1. **属性更新**：更新部门、职位、上级等信息
2. **权限调整**：增加/移除权限
3. **角色变更**：分配新角色，回收旧角色
4. **权限审查**：确保新权限合理

**常见问题**：
- 权限只加不减（权限累积）
- 调动后原部门权限未回收
- 角色变更没有审批

**最佳实践**：
- 基于角色的权限调整
- 自动触发：HR系统变更自动同步
- 权限变更需要审批
- 定期清理过期权限

#### 阶段三：停用（Disable/Suspend）

**触发事件**：
- 员工离职
- 长期休假
- 账号异常
- 合同到期

**关键活动**：
1. **禁用账号**：立即禁用登录权限
2. **回收权限**：回收所有访问权限
3. **数据处理**：处理用户数据（转交、归档）
4. **通知**：通知相关人员和系统管理员

**离职流程关键控制点**：
```
离职申请 → HR确认 → 直属经理确认
    ↓
IT账号回收（邮件、系统、VPN等）
    ↓
物理权限回收（门禁、钥匙等）
    ↓
资产回收（电脑、手机等）
    ↓
最终确认 → 账号归档/删除
```

**重要原则**：离职即停用，零时差！

#### 阶段四：删除（Delete）

**触发事件**：
- 离职一段时间后
- 确认不再需要该身份
- 合规要求的清理

**关键活动**：
1. **数据归档**：必要数据归档保存
2. **权限清理**：清理所有关联权限
3. **账号删除**：从目录系统中删除
4. **审计记录**：保留操作日志

**保留策略**：
- 账号可以删除，但审计日志应长期保留
- 员工邮件和数据按法规要求保留
- 建议保留30-90天后再永久删除

### 3.3 身份生命周期自动化

#### HR 驱动的身份管理

```
HR系统 (数据源)
    │
    ├── 入职 → 自动创建账号 + 分配角色权限
    ├── 调岗 → 自动调整属性 + 权限变更
    ├── 离职 → 自动禁用账号 + 回收权限
    └── 信息更新 → 自动同步属性
```

**自动化的价值**：
- 减少人工操作错误
- 提高效率，缩短账号开通时间
- 确保权限及时回收
- 满足合规要求

#### 工作流驱动

| 操作 | 审批流程 |
|------|----------|
| 新账号创建 | 直属经理审批 → IT执行 |
| 权限申请 | 资源所有者审批 → IT执行 |
| 特权权限申请 | 多级审批 → 安全团队审核 |
| 账号删除 | HR确认 → IT执行 |

## 四、联合身份（Federated Identity）

### 4.1 什么是身份联邦

**身份联邦（Identity Federation）**：在不同的安全域（组织、系统）之间建立信任关系，使得一个域中的身份可以被另一个域信任和使用。

**核心价值**：
- 跨组织访问无需创建新账号
- 用户体验好（一次登录多处访问）
- 减少身份管理成本
- 企业间合作更便捷

**联邦模型**：

```
模型1：一对多（一个IdP，多个SP）
┌──────┐
│ IdP  │ ←── 统一身份源
└──┬───┘
   ├──→ SP1 (应用A)
   ├──→ SP2 (应用B)
   └──→ SP3 (应用C)

模型2：多对多（联邦枢纽）
┌──────┐        ┌──────┐
│ IdP1 │ ←────→ │      │
├──────┤        │ 联邦  │ ←────→ SP1
│ IdP2 │ ←────→ │ 枢纽  │ ←────→ SP2
├──────┤        │      │ ←────→ SP3
│ IdP3 │ ←────→ │      │
└──────┘        └──────┘
```

### 4.2 联邦身份标准协议

#### SAML 2.0

**SAML（Security Assertion Markup Language）**：基于 XML 的联邦身份标准，企业级 SSO 的主流协议。

**核心组件**：
- **断言（Assertion）**：IdP 签发的身份声明（XML格式）
- **协议（Protocol）**：请求和响应的格式
- **绑定（Binding）**：如何传输消息（HTTP重定向、POST等）
- **配置文件（Profile）**：特定场景的使用方式

**SAML 断言内容**：
```xml
<saml:Assertion>
  <!-- 断言签发者 -->
  <saml:Issuer>https://idp.example.com</saml:Issuer>
  
  <!-- 主体（用户） -->
  <saml:Subject>
    <saml:NameID>user@example.com</saml:NameID>
  </saml:Subject>
  
  <!-- 认证声明 -->
  <saml:AuthnStatement AuthnInstant="2024-01-15T10:00:00Z">
    <saml:AuthnContext>
      <saml:AuthnContextClassRef>PasswordProtectedTransport</saml:AuthnContextClassRef>
    </saml:AuthnContext>
  </saml:AuthnStatement>
  
  <!-- 属性声明 -->
  <saml:AttributeStatement>
    <saml:Attribute Name="cn">
      <saml:AttributeValue>张三</saml:AttributeValue>
    </saml:Attribute>
    <saml:Attribute Name="email">
      <saml:AttributeValue>zhangsan@example.com</saml:AttributeValue>
    </saml:Attribute>
    <saml:Attribute Name="department">
      <saml:AttributeValue>IT部门</saml:AttributeValue>
    </saml:Attribute>
  </saml:AttributeStatement>
</saml:Assertion>
```

#### OAuth 2.0

**OAuth 2.0**：授权框架，用于第三方应用授权，也是现代联邦身份的基础。

**四种授权模式**：

| 模式 | 适用场景 | 安全性 |
|------|----------|--------|
| 授权码模式 | 服务端Web应用 | 高 |
| 隐式模式 | 纯前端应用（已不推荐） | 中 |
| 密码模式 | 高度信任的客户端 | 低 |
| 客户端模式 | 服务间调用（无用户） | 中 |

**授权码模式流程详解**：
```
┌──────────┐          ┌──────────┐          ┌──────────┐
│  用户浏览器 │          │  客户端   │          │ 授权服务器 │
└────┬─────┘          └────┬─────┘          └────┬─────┘
     │                     │                     │
     │ 1. 点击登录按钮      │                     │
     │────────────────────→│                     │
     │                     │                     │
     │ 2. 重定向到授权页面  │                     │
     │←────────────────────│                     │
     │                     │                     │
     │ 3. 用户授权          │                     │
     │─────────────────────────────────────────→│
     │                     │                     │
     │ 4. 返回授权码        │                     │
     │←─────────────────────────────────────────│
     │                     │                     │
     │ 5. 携带授权码回调    │                     │
     │────────────────────→│                     │
     │                     │                     │
     │ 6. 用授权码换令牌    │                     │
     │                     │────────────────────→│
     │                     │                     │
     │                     │ 7. 返回令牌         │
     │                     │←────────────────────│
     │                     │                     │
     │ 8. 登录成功          │                     │
     │←────────────────────│                     │
```

#### OpenID Connect (OIDC)

**OIDC**：在 OAuth 2.0 之上构建的身份层，提供认证功能。

**OIDC 新增内容**：
- **ID Token**：身份令牌（JWT格式），包含用户身份信息
- **UserInfo 端点**：获取更多用户信息的API
- **标准的用户声明**：sub、name、email、picture等

**ID Token 示例（JWT Payload）**：
```json
{
  "iss": "https://idp.example.com",      // 签发者
  "sub": "user-12345",                   // 用户唯一标识
  "aud": "client-app-1",                 // 受众
  "exp": 1705312800,                     // 过期时间
  "iat": 1705309200,                     // 签发时间
  "name": "张三",                        // 姓名
  "email": "zhangsan@example.com",       // 邮箱
  "email_verified": true,                // 邮箱是否验证
  "picture": "https://.../avatar.jpg",   // 头像
  "amr": ["pwd", "mfa"]                  // 认证方法
}
```

### 4.3 SCIM

**SCIM（System for Cross-domain Identity Management）**：跨域身份管理系统，用于身份信息的自动化同步。

**SCIM 的作用**：
- 自动化用户和组的创建、更新、删除
- 标准化的 REST API
- 减少手工操作和配置错误

**SCIM 资源模型**：
```
/User          用户资源
/Group         组资源
/Schemas       模式定义
/ResourceTypes 资源类型
```

**SCIM API 示例**：
```
# 创建用户
POST /scim/v2/Users
Content-Type: application/scim+json

{
  "schemas": ["urn:ietf:params:scim:schemas:core:2.0:User"],
  "userName": "zhangsan",
  "name": {
    "givenName": "三",
    "familyName": "张"
  },
  "emails": [
    { "value": "zhangsan@example.com", "primary": true }
  ],
  "active": true
}
```

## 五、身份治理与合规

### 5.1 什么是身份治理

**身份治理（Identity Governance）**：通过制定政策、流程和控制措施，确保身份和访问权限的分配、使用和审查符合企业安全策略和合规要求。

**身份治理的核心问题**：
- 谁拥有什么权限？
- 这些权限是否合理？
- 权限是否经过审批？
- 是否存在过度授权？
- 是否满足合规要求？

### 5.2 IGA 核心功能

**IGA（Identity Governance and Administration）**：身份治理与管理，是身份管理的高级阶段。

| 功能模块 | 说明 |
|----------|------|
| 身份生命周期管理 | 用户创建、变更、停用的自动化流程 |
| 访问请求与审批 | 用户自助申请权限，审批流 |
| 权限认证（Access Certification） | 定期审查权限的合理性 |
| 职责分离（SoD） | 检测和预防权限冲突 |
| 权限分析 | 分析权限分配，识别风险 |
| 合规报告 | 生成合规审计报告 |

### 5.3 权限认证（Access Certification）

**定义**：定期让管理者确认下属用户的权限是否仍然合理，回收不再需要的权限。

**认证流程**：
```
1. 发起认证 campaign
   ↓
2. 生成待审查项（每个用户的权限）
   ↓
3. 发送给评审人（通常是部门经理）
   ↓
4. 评审人逐项确认：
   - 保留：该权限仍然需要
   - 撤销：该权限不再需要
   - 转交：转交给其他评审人
   ↓
5. 自动执行撤销操作
   ↓
6. 生成认证报告
```

**认证类型**：

| 类型 | 说明 | 频率 |
|------|------|------|
| 用户认证 | 评审用户拥有的所有权限 | 季度/半年 |
| 角色认证 | 评审角色的成员是否合理 | 季度/半年 |
| 特权认证 | 重点审查特权账号 | 月度/季度 |
| 应用认证 | 评审应用的访问权限 | 半年/年度 |

### 5.4 合规与审计

#### 常见合规要求

| 法规/标准 | 相关要求 |
|-----------|----------|
| **等保2.0** | 身份鉴别、访问控制、安全审计 |
| **ISO 27001** | 访问控制（A.9）、权限管理 |
| **GDPR** | 数据主体权利、访问控制、审计 |
| **SOX** | 职责分离、访问控制、变更管理 |
| **PCI-DSS** | 唯一ID、最小权限、审计日志 |

#### 身份合规审计要点

1. **身份生命周期**：
   - 入职是否及时开通账号？
   - 离职是否及时回收权限？
   - 调岗是否调整权限？

2. **权限管理**：
   - 是否遵循最小权限原则？
   - 是否有职责分离冲突？
   - 特权账号是否受控？

3. **访问审计**：
   - 是否有完整的访问日志？
   - 日志是否安全存储？
   - 是否定期审查日志？

4. **认证强度**：
   - 关键系统是否启用MFA？
   - 密码策略是否合规？
   - 特权账号是否有特殊保护？

## 六、实际案例分析

### 案例一：AD 域被入侵导致企业全面沦陷

**事件**：某企业内网被黑客入侵，攻击者通过一台Web服务器的漏洞进入内网，然后利用各种AD攻击手段横向移动，最终获取了域管理员权限。

**攻击路径**：
```
1. 外网Web服务器SQL注入 → 获取WebShell
2. 提取本地管理员哈希 → Pass-the-Hash登录其他服务器
3. 在服务器内存中找到域管理员票据 → Pass-the-Ticket
4. Kerberoasting破解服务账号 → 获取更多权限
5. DCSync获取域内所有用户哈希 → 全面沦陷
```

**暴露的问题**：
- Web服务器权限过大（本地管理员权限过高）
- 域管理员账号登录普通服务器（导致票据泄露）
- 没有分层架构
- 服务账号密码强度不够
- 缺乏AD安全监控

**改进措施**：
1. 实施 Tier Model 分层架构
2. 限制域管理员登录范围（只在DC和管理工作站登录）
3. 服务账号使用强密码并定期轮换
4. 启用 LSA 保护和 Credential Guard
5. 部署 AD 安全监控方案
6. 定期进行 AD 安全评估

### 案例二：权限累积导致的数据泄露

**事件**：某公司发现一名已经调岗到市场部的员工，仍然能够访问研发部的源代码库。

**根本原因**：
- 员工从研发部调到市场部时，只增加了市场部的权限
- 研发部的权限没有回收
- 没有定期权限审查机制
- 违反了最小权限原则

**改进措施**：
1. 实施身份生命周期自动化：
   - 调岗时自动移除原部门权限
   - HR系统变更触发权限调整
2. 建立权限认证制度：
   - 每季度进行一次权限审查
   - 部门经理确认下属权限
3. 启用权限过期机制：
   - 临时权限自动过期
   - 特权权限需要定期重新申请

### 案例三：供应商账号被利用实施供应链攻击

**事件**：攻击者入侵了某IT供应商的系统，利用供应商的VPN账号进入客户企业内网，实施了数据窃取。

**问题分析**：
- 供应商账号权限过大（几乎与内部员工相同）
- 供应商账号没有定期审查
- 没有限制供应商的访问范围
- 供应商账号没有启用MFA

**改进措施**：
1. **第三方身份治理**：
   - 建立第三方账号生命周期管理流程
   - 第三方账号使用单独的OU和组
2. **最小权限**：
   - 严格限制供应商的访问范围
   - 只允许访问必要的系统和数据
   - 使用JIT（即时权限）模式
3. **加强认证**：
   - 第三方账号必须启用MFA
   - 使用单独的认证流程
4. **监控审计**：
   - 第三方访问行为全程监控
   - 定期审查第三方权限
   - 异常访问告警
