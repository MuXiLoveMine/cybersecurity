# 实际案例分析

### 案例一：AD 域被入侵导致企业全面沦陷

**事件**：某企业内网被黑客入侵，攻击者通过一台Web服务器的漏洞进入内网，然后利用各种AD攻击手段横向移动，最终获取了域管理员权限。

**攻击路径**：
```
1. 外网Web服务器SQL注入 → 获取WebShell
2. 提取本地管理员哈希 → Pass-the-Hash登录其他服务器
3. 在服务器内存中找到域管理员票据 → Pass-the-Ticket
4. Kerberoasting破解服务账号 → 获取更多权限
5. DCSync获取域内所有用户哈希 → 全面沦陷
```

**暴露的问题**：
- Web服务器权限过大（本地管理员权限过高）
- 域管理员账号登录普通服务器（导致票据泄露）
- 没有分层架构
- 服务账号密码强度不够
- 缺乏AD安全监控

**改进措施**：
1. 实施 Tier Model 分层架构
2. 限制域管理员登录范围（只在DC和管理工作站登录）
3. 服务账号使用强密码并定期轮换
4. 启用 LSA 保护和 Credential Guard
5. 部署 AD 安全监控方案
6. 定期进行 AD 安全评估

### 案例二：权限累积导致的数据泄露

**事件**：某公司发现一名已经调岗到市场部的员工，仍然能够访问研发部的源代码库。

**根本原因**：
- 员工从研发部调到市场部时，只增加了市场部的权限
- 研发部的权限没有回收
- 没有定期权限审查机制
- 违反了最小权限原则

**改进措施**：
1. 实施身份生命周期自动化：
   - 调岗时自动移除原部门权限
   - HR系统变更触发权限调整
2. 建立权限认证制度：
   - 每季度进行一次权限审查
   - 部门经理确认下属权限
3. 启用权限过期机制：
   - 临时权限自动过期
   - 特权权限需要定期重新申请

### 案例三：供应商账号被利用实施供应链攻击

**事件**：攻击者入侵了某IT供应商的系统，利用供应商的VPN账号进入客户企业内网，实施了数据窃取。

**问题分析**：
- 供应商账号权限过大（几乎与内部员工相同）
- 供应商账号没有定期审查
- 没有限制供应商的访问范围
- 供应商账号没有启用MFA

**改进措施**：
1. **第三方身份治理**：
   - 建立第三方账号生命周期管理流程
   - 第三方账号使用单独的OU和组
2. **最小权限**：
   - 严格限制供应商的访问范围
   - 只允许访问必要的系统和数据
   - 使用JIT（即时权限）模式
3. **加强认证**：
   - 第三方账号必须启用MFA
   - 使用单独的认证流程
4. **监控审计**：
   - 第三方访问行为全程监控
   - 定期审查第三方权限
   - 异常访问告警
