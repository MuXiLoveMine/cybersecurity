# 动态调试进阶

### 3.1 高级调试技巧

#### 3.1.1 条件断点

条件断点只在满足特定条件时才中断，可以大大提高调试效率。

**x64dbg条件断点：**
```
// 当EAX等于特定值时中断
eax == 0x12345678

// 当字符串等于特定值时中断
strcmp(addr, "flag{") == 0

// 当函数返回特定值时中断
// 在函数返回处设置条件
rax == 0

// 内存比较
memcmp(addr, "CTF", 3) == 0
```

**GDB条件断点：**
```gdb
# 基本条件断点
break *0x401234 if $eax == 0x12345678

# 字符串条件
break *0x401234 if strcmp((char*)$rdi, "password") == 0

# 条件断点 + 命令
break *0x401234
commands
  printf "EAX = 0x%x\n", $eax
  continue
end

# 观察点（内存断点）
watch *0x602000        # 写入时中断
rwatch *0x602000       # 读取时中断
awatch *0x602000       # 读写都中断
```

**条件断点实战应用：**

1. **过滤循环中的特定迭代**
   ```gdb
   # 在循环中，只在第100次迭代时中断
   break *0x401200 if $i == 100
   ```

2. **捕获特定参数的函数调用**
   ```gdb
   # 当strcmp比较flag相关字符串时中断
   break strcmp
   condition 1 strcmp((char*)$rdi, "flag") == 0 || strcmp((char*)$rsi, "flag") == 0
   ```

3. **监控数据变化**
   ```gdb
   # 监控某个关键变量何时被修改
   watch *(int*)0x602080
   ```

#### 3.1.2 硬件断点

硬件断点使用CPU的调试寄存器（DR0-DR7），不会修改代码，特别适合：
- 自修改代码的调试
- 代码完整性校验的绕过
- ROM/Flash中的代码调试

**x64dbg硬件断点：**
- 在反汇编窗口右键 → Breakpoint → Hardware, on execute
- 支持最多4个硬件断点

**GDB硬件断点：**
```gdb
# 设置硬件执行断点
hbreak *0x401234

# 设置硬件观察点（默认使用硬件）
watch *0x602000
```

#### 3.1.3 内存断点

内存断点在访问特定内存时中断，用于追踪数据流向。

**常用场景：**
1. **追踪关键数据**：监控flag或密钥何时被访问
2. **查找解密位置**：监控加密数据何时被解密
3. **检测内存破坏**：发现哪里修改了不该修改的内存
4. **分析数据流**：追踪数据在函数间的传递

### 3.2 反调试与绕过

#### 3.2.1 常见反调试技术

**1. 系统API检测**

Windows下常见的反调试API：
- `IsDebuggerPresent()`：最基础的检测
- `CheckRemoteDebuggerPresent()`：检测远程调试器
- `NtQueryInformationProcess()`：查询进程调试信息
- `OutputDebugString()`：通过输出检测
- `GetTickCount()` / `QueryPerformanceCounter()`：时间差检测

**Linux下常见检测：**
- 读取`/proc/self/status`中的`TracerPid`
- `ptrace(PTRACE_TRACEME, ...)`：检测是否已被追踪
- 读取`/proc/self/maps`检查异常映射

**2. 时间差检测**

通过测量代码执行时间，判断是否被调试（单步执行会显著增加执行时间）。

```c
// 时间差检测示例
DWORD start = GetTickCount();
// 执行一些计算
DWORD end = GetTickCount();
if (end - start > THRESHOLD) {
    // 可能正在被调试
    exit(1);
}
```

**3. 进程/窗口检测**

- 枚举进程，查找调试器进程名
- 枚举窗口，查找调试器窗口标题
- 检查父进程是否是调试器

**4. 硬件断点检测**

检查调试寄存器（DR0-DR7）是否被设置：

```asm
; 检测硬件断点
push dr0
pop eax
test eax, eax
jnz debug_detected
```

**5. 软件断点检测**

检查内存中是否有`0xCC`（INT 3）指令：

```c
// 检测软件断点
if (*(unsigned char*)func_addr == 0xCC) {
    // 发现断点
    exit(1);
}
```

**6. 代码完整性校验**

计算代码段的哈希或校验和，与预期值比较：

```c
// 代码校验示例
DWORD hash = calculate_hash((BYTE*)0x401000, 0x1000);
if (hash != EXPECTED_HASH) {
    // 代码被修改（可能下了断点）
    exit(1);
}
```

#### 3.2.2 反调试绕过方法

**1. API Hook法**

Hook反调试相关的API，使其返回正常结果：

```python
# Frida脚本示例：绕过IsDebuggerPresent
import frida

def on_message(message, data):
    print(message)

session = frida.attach("target.exe")
script = session.create_script("""
Interceptor.attach(Module.findExportByName("kernel32.dll", "IsDebuggerPresent"), {
    onEnter: function(args) {
        // 直接修改返回值
    },
    onLeave: function(retval) {
        retval.replace(0);  // 返回0表示没有调试器
    }
});
""")
script.on('message', on_message)
script.load()
```

**2. 系统调用篡改**

直接Hook底层系统调用（如`NtQueryInformationProcess`）。

**3. 手动修补**

在反调试检查处修改代码，跳过检查或修改检查结果：
- 将条件跳转改为无条件跳转
- 用NOP填充检查代码
- 修改返回值

**4. 调试器插件**

使用调试器插件自动处理常见的反调试：
- **ScyllaHide**：x64dbg插件，强大的反反调试
- **PhantOm**：OllyDbg插件
- **HideDebugger**：IDA调试器插件

**5. 动态二进制插桩**

使用Pin、DynamoRIO等工具，在指令层面绕过反调试。

#### 3.2.3 实战绕过流程

1. **检测反调试手段**
   - 静态分析：搜索反调试相关字符串和API
   - 动态分析：观察程序在调试和非调试状态下的行为差异
   - 使用工具：x64dbg的ScyllaHide可以检测大部分反调试

2. **制定绕过策略**
   - 简单的反调试：直接patch
   - 复杂的反调试：使用插件或脚本
   - 内核态反调试：可能需要驱动级别的绕过

3. **验证绕过效果**
   - 确保程序正常运行
   - 检查是否还有其他反调试
   - 验证核心功能不受影响

### 3.3 多线程/多进程调试

#### 3.3.1 多线程调试挑战

多线程程序的调试难度远高于单线程：
- 多个线程同时执行，难以追踪
- 线程间同步和竞态条件复杂
- 断点可能被任何线程触发
- 调试行为可能影响线程调度

#### 3.3.2 调试技巧

**1. 线程切换**

GDB中操作线程：
```gdb
info threads              # 列出所有线程
thread 2                  # 切换到线程2
thread apply all bt       # 所有线程打印调用栈
thread apply 1-3 print $eax  # 线程1-3打印EAX
```

x64dbg中操作线程：
- 查看线程窗口（View → Threads）
- 双击切换到指定线程
- 可以暂停/恢复特定线程

**2. 线程特定断点**

只在特定线程中断：
```gdb
# GDB中设置线程特定断点
break *0x401234 thread 2
```

**3. 冻结线程**

暂停其他线程，只让目标线程运行：
```gdb
# GDB中设置调度器锁定
set scheduler-locking on   # 只运行当前线程
set scheduler-locking off  # 恢复所有线程
```

x64dbg中：
- 在线程窗口右键 → Suspend/Resume
- 可以冻结除当前线程外的所有线程

### 3.4 内核态调试

#### 3.4.1 内核调试基础

**什么时候需要内核调试：**
- 逆向分析驱动程序（.sys文件）
- 分析内核级Rootkit
- 绕过用户态无法绕过的反调试
- 分析内核漏洞利用

**内核调试环境搭建（Windows）：**

1. **虚拟机设置**
   - 目标机：Windows虚拟机（被调试）
   - 宿主机：运行调试器（WinDbg/x64dbg+内核插件）

2. **配置目标机**
   ```cmd
   # 启用调试模式
   bcdedit /debug on
   bcdedit /dbgsettings serial debugport:1 baudrate:115200
   # 或使用网络调试
   bcdedit /dbgsettings net hostip:192.168.1.100 port:50000 key:1.2.3.4
   ```

3. **连接调试器**
   - WinDbg: File → Kernel Debug → 设置连接参数
   - 连接成功后可以中断内核

**常用WinDbg命令：**
```
g                     # 继续运行
bp <address>          # 设置断点
bl                    # 列出断点
bc <index>            # 清除断点
dt <type> <address>   # 显示数据类型
!process 0 0          # 列出进程
!thread               # 显示当前线程
kv                    # 显示调用栈
u <address>           # 反汇编
db <address>          # 显示内存字节
```

#### 3.4.2 Linux内核调试

**QEMU + GDB调试内核：**

```bash
# 编译带调试信息的内核
make menuconfig  # 启用CONFIG_DEBUG_INFO

# 使用QEMU启动内核，开启GDB服务
qemu-system-x86_64 \
    -kernel bzImage \
    -initrd initramfs.cpio.gz \
    -append "root=/dev/ram rdinit=/init console=ttyS0" \
    -nographic \
    -gdb tcp::1234 \
    -S  # 启动时暂停，等待GDB连接

# 另开终端，启动GDB
gdb vmlinux
(gdb) target remote :1234
(gdb) hbreak start_kernel  # 硬件断点
(gdb) c
```
