# 钓鱼邮件技术分析

### 1.1 邮件协议与安全基础

#### 1.1.1 SMTP协议工作流程

```
邮件发送流程：

发件人 ────SMTP────▶ 发件服务器 ────SMTP────▶ 收件服务器 ────IMAP/POP3────▶ 收件人

关键问题：SMTP协议设计之初未考虑身份验证
- 任何人都可以声称自己是任意域名
- 邮件头中的From字段可被任意伪造
- 这就是邮件欺骗（Email Spoofing）的根本原因

为弥补这一缺陷，发展出了三个邮件认证协议：
├── SPF（发件人策略框架） - 验证发件IP
├── DKIM（域名密钥识别邮件） - 验证邮件签名
└── DMARC（域消息认证报告一致性） - 统一策略
```

#### 1.1.2 SPF（Sender Policy Framework）

**工作原理**：

```
1. 域名所有者在DNS中发布SPF TXT记录
   示例: v=spf1 include:spf.protection.outlook.com include:_spf.google.com ~all

2. 收件服务器收到邮件时：
   a) 提取邮件的Mail From地址（信封发件人）的域名
   b) 查询该域名的SPF记录
   c) 检查发件服务器IP是否在SPF记录允许的范围内
   d) 根据结果采取行动：
      - Pass: IP在允许范围内，通过
      - Fail: IP不在允许范围内，拒绝
      - SoftFail (~all): 标记但不拒绝
      - Neutral (?all): 不做判断
      - None: 无SPF记录

SPF记录语法：
v=spf1                          SPF版本
ip4:192.168.1.0/24              允许的IPv4范围
ip6:2001:db8::/32               允许的IPv6范围
include:spf.protection.outlook.com  包含其他域名的SPF记录
a                               包含域名的A记录
mx                              包含域名的MX记录
-all                            拒绝所有未列出的IP（最严格）
~all                            软失败（标记但不拒绝）
?all                            中性（不做判断）
```

**SPF绕过技术**：

```python
# SPF验证绕过场景分析

# 场景1：SPF配置为软失败（~all）
# 发件人伪造邮件不会被拒绝，只会被标记
# 攻击者仍可成功投递钓鱼邮件
# 示例SPF: v=spf1 include:spf.protection.outlook.com ~all
# 绕过方式：直接从任意IP发送伪造邮件，邮件仍可到达收件箱

# 场景2：SPF未配置
# 域名没有SPF记录，任何IP都可以代表该域名发送邮件
# 这是最容易被利用的情况

# 场景3：利用Mail From与Header From不一致
# SPF验证的是Mail From（信封发件人），而非显示在邮件客户端的Header From
# 攻击者可以设置：
#   Mail From: legitimate@attacker-controlled-domain.com（通过SPF验证）
#   Header From: ceo@target-company.com（显示给收件人）

# 场景4：SPF记录过于宽松
# 示例: v=spf1 ip4:0.0.0.0/0 ~all（允许任何IP）
# 或包含过多include导致DNS查询超限（SPF查询限制10次DNS查询）
```

#### 1.1.3 DKIM（DomainKeys Identified Mail）

**工作原理**：

```
DKIM签名验证流程：

┌──────────────┐                        ┌──────────────┐
│   发件服务器  │                        │   收件服务器  │
├──────────────┤                        ├──────────────┤
│              │                        │              │
│ 1. 用私钥对   │────邮件+DKIM签名────▶│ 2. 从DKIM签名 │
│    邮件内容   │                        │    提取域名和 │
│    生成签名   │                        │    选择器     │
│              │                        │              │
│              │                        │ 3. 查询DNS中  │
│              │                        │    的公钥     │
│              │                        │    selector._domainkey.domain │
│              │                        │              │
│              │                        │ 4. 用公钥验证 │
│              │                        │    签名       │
│              │                        │              │
│              │                        │ 5. 验证通过   │
│              │                        │    = 邮件确实 │
│              │                        │    来自该域名 │
└──────────────┘                        └──────────────┘

DKIM签名头示例：
DKIM-Signature: v=1; a=rsa-sha256; d=company.com; s=selector1;
    t=1694390400; c=relaxed/relaxed;
    h=From:Subject:To:Date:Message-ID;
    bh=...body hash...;
    b=...signature...
```

**DKIM绕过技术**：

```python
# DKIM绕过场景分析

# 场景1：DKIM未配置
# 大量域名未配置DKIM签名，攻击者可以自由伪造这些域名的邮件

# 场景2：利用DKIM签名的可选性
# DKIM不是强制性的，没有DKIM签名的邮件仍然可以被投递
# 攻击者发送无DKIM签名的伪造邮件

# 场景3：利用已有DKIM签名重放
# 攻击者获取一封合法的DKIM签名邮件
# 转发该邮件到新的目标（DKIM签名仍然有效）
# 利用合法签名增加邮件可信度

# 场景4：利用子域名DKIM缺失
# 父域名company.com有DKIM，但子域名news.company.com可能没有
# 攻击者伪造子域名发件人

# 场景5：弱密钥
# 某些域名的DKIM密钥长度不足（如512位RSA）
# 理论上可以被破解
```

#### 1.1.4 DMARC（Domain-based Message Authentication, Reporting & Conformance）

**工作原理**：

```
DMARC = SPF + DKIM + 策略 + 报告

DMARC验证流程：
1. 检查SPF是否通过（且Mail From域名与Header From域名对齐）
2. 检查DKIM是否通过（且d=域名与Header From域名对齐）
3. SPF或DKIM至少一个通过且对齐 → DMARC验证通过
4. 根据DMARC策略处理验证失败的邮件

DMARC策略：
p=none       不采取行动（仅监控）
p=quarantine 隔离（发送到垃圾邮件文件夹）
p=reject     拒绝（直接拒绝投递）

DMARC DNS记录示例：
_dmarc.company.com. IN TXT "v=DMARC1; p=reject; rua=mailto:dmarc@company.com; ruf=mailto:forensics@company.com; pct=100; adkim=s; aspf=s"

参数说明：
v=DMARC1      DMARC版本
p=reject      策略：拒绝
rua           聚合报告接收地址
ruf           取证报告接收地址
pct=100       应用策略的邮件百分比
adkim=s       DKIM对齐模式：严格（s）或宽松（r）
aspf=s        SPF对齐模式：严格（s）或宽松（r）
```

**DMARC绕过技术**：

```python
# DMARC绕过场景分析

# 场景1：DMARC策略为none或未配置
# p=none意味着即使验证失败也不采取行动
# 攻击者可以自由伪造这些域名

# 场景2：利用对齐模式差异
# DMARC要求SPF或DKIM的域名与Header From域名"对齐"
# 宽松模式（r）下，子域名与父域名视为对齐
# 严格模式（s）下，必须完全匹配
# 攻击者寻找使用宽松模式的域名

# 场景3：利用合法邮件服务
# 使用合法的邮件发送服务（如SendGrid、Mailgun）
# 攻击者注册这些服务，利用其良好的信誉发送钓鱼邮件
# 因为邮件通过合法服务的SPF和DKIM验证

# 场景4：Display Name欺骗（不受DMARC保护）
# DMARC验证的是域名，而非显示名
# 攻击者使用不同域名但相同显示名
# 发件人: "CEO 张伟 <ceo@attacker-domain.com>"
# DMARC验证通过（因为确实是attacker-domain.com的合法邮件）

# 场景5：子域名策略继承
# 如果company.com有DMARC，但sub.company.com没有
# sub.company.com不会继承父域名的DMARC策略
# 攻击者可以伪造子域名
```

### 1.2 Display Name欺骗

```
Display Name欺骗是最高频使用的钓鱼邮件欺骗手法

原理：邮件客户端通常优先显示发件人的"显示名"而非邮箱地址
      特别是在移动设备、邮件列表预览中

攻击方式：
1. 完全冒充品牌
   显示名: "Microsoft 365"
   邮箱:   random@freemail-service.com

2. 冒充内部人员
   显示名: "张伟 [IT运维部]"
   邮箱:   zhang.wei@attacker-domain.com

3. 冒充外部合作伙伴
   显示名: "ABC供应商管理系统"
   邮箱:   noreply@abc-supplier-portal.com（注册了相似域名）

4. 利用Unicode/RLO字符
   显示名: "CEO 张伟‮gn.vib.tta@moc‬"
   利用Right-to-Left Override字符反转显示

防范：
- 邮件安全网关配置Display Name检测规则
- 培训用户查看完整邮箱地址
- 内部邮件添加标记（如[内部]标签）
- 外部邮件添加警告横幅
```

### 1.3 子域名滥用

```
子域名滥用攻击手法：

1. 子域名层级混淆
   合法: https://login.microsoftonline.com
   钓鱼: https://microsoft.com.login.evil-attacker.com
   解析: evil-attacker.com的子域名microsoft.com.login

2. 路径混淆
   合法: https://www.paypal.com/login
   钓鱼: https://www.evil-attacker.com/paypal.com/login
   利用路径中的域名迷惑用户

3. 子域名接管
   攻击者发现目标组织的子域名CNAME指向已过期的云服务
   注册该云服务接管子域名
   在合法子域名上部署钓鱼页面

4. 利用合法云服务
   https://company.sharepoint.com → 合法
   https://company.sharepoint.com.evil.com → 钓鱼
   https://evil-company.sharepoint.com → 利用SharePoint创建的钓鱼
```
