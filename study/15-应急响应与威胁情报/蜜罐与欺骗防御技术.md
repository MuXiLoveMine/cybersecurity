# 蜜罐与欺骗防御技术

> 本文档对应审计报告模块15缺口，系统讲解蜜罐与欺骗防御技术的理论框架、工具体系、部署方案与实战案例，旨在帮助安全从业者掌握主动防御技术，构建企业级欺骗防御体系。

---

## 1. 蜜罐与欺骗防御概述

### 1.1 蜜罐定义与分类

蜜罐（Honeypot）是一种安全资源，其价值在于被攻击、探测或入侵。蜜罐本身没有合法的生产用途，任何与蜜罐的交互都意味着可疑或恶意行为。

**蜜罐的核心特征：**

- **无生产价值**：蜜罐不承载任何合法业务流量，所有访问均为异常。
- **高信噪比**：不同于IDS/IPS需要从海量正常流量中过滤攻击，蜜罐的每次告警都值得关注。
- **主动诱捕**：通过伪装成真实服务吸引攻击者，而非被动等待检测。
- **情报收集**：记录攻击者的行为、工具、技术和意图，产出高价值威胁情报。

**蜜罐的价值定位：**

| 维度 | 传统防御（IDS/IPS） | 蜜罐 |
|------|---------------------|------|
| 检测方式 | 特征匹配/异常检测 | 任何交互即为告警 |
| 误报率 | 较高（正常流量干扰） | 极低（无合法流量） |
| 情报深度 | 网络/系统层面 | 攻击者行为/动机层面 |
| 防御姿态 | 被动检测 | 主动诱捕 |
| 部署成本 | 中-高 | 低-中 |

### 1.2 欺骗防御概念

欺骗防御（Deception Defense）是蜜罐概念的扩展与升华，不再局限于单一蜜罐系统，而是构建一个覆盖整个企业网络的虚假信息生态：

- **虚假服务**：模拟不存在的Web、SSH、数据库等服务
- **虚假凭证**：投放假的用户名/密码、API Key
- **虚假文件**：放置诱饵文档（Canary文件）
- **虚假网络**：构造不存在的子网和主机
- **虚假端点**：模拟不存在的终端设备

欺骗防御的核心理念是：在攻击者的每一步行动路径上布设陷阱，使其在侦察、入侵、横向移动、数据外传的每个阶段都踩中诱饵，从而实现攻击者行为的全链路检测。

**欺骗防御 vs 传统蜜罐：**

| 对比项 | 传统蜜罐 | 欺骗防御 |
|--------|----------|----------|
| 覆盖范围 | 单点部署 | 全网络覆盖 |
| 诱饵类型 | 主要是服务 | 服务+凭证+文件+网络 |
| 部署方式 | 独立部署 | 嵌入现有环境 |
| 自动化 | 手动配置 | 自动化投放与管理 |
| 与SOC集成 | 较弱 | 深度集成SIEM/SOAR |

### 1.3 蜜罐的价值与局限

**蜜罐的核心价值：**

1. **早期预警**：在攻击者到达真实系统之前即触发告警，实现攻击早期发现。
2. **攻击者行为分析**：记录完整的攻击链路，分析攻击者的TTP（战术、技术和程序）。
3. **威胁情报生产**：提取IOC（IP、域名、Payload、指纹），丰富威胁情报库。
4. **攻击者拖延**：高交互蜜罐可消耗攻击者时间和资源，为防御方争取响应窗口。
5. **内网检测**：在内部网络部署蜜罐可有效发现横向移动和内部威胁。
6. **合规支持**：满足等保2.0、ISO 27001等标准中"主动防御"要求。

**蜜罐的局限性：**

1. **风险引入**：高交互蜜罐可能成为攻击者进一步攻击的跳板。
2. **维护成本**：蜜罐需要持续维护和更新伪装内容，否则容易被识别。
3. **绕过风险**：高级攻击者可通过指纹识别绕过蜜罐。
4. **法律风险**：蜜罐可能涉及隐私监听、未经授权的计算机访问等法律问题。
5. **非全面防御**：蜜罐只能检测到与它交互的攻击，不能替代传统防御。

### 1.4 蜜罐在威胁情报中的作用

蜜罐是威胁情报的重要生产源：

- **战略情报**：攻击趋势分析、大规模扫描活动监测、0day漏洞利用捕获。
- **战术情报**：攻击者TTP分析、攻击链路重建、ATT&CK技术映射。
- **运营情报**：IOC提取（恶意IP、域名、文件哈希、C2地址）、Payload采集。
- **技术情报**：漏洞利用细节、恶意软件分析样本、攻击工具指纹。

蜜罐产出的威胁情报可直接输入：
- SIEM平台（增强检测规则）
- 威胁情报平台（TIP，丰富IOC库）
- SOAR平台（触发自动响应剧本）
- 防火墙/IPS（动态封堵恶意IP）

## 2. 蜜罐分类体系

### 2.1 按交互级别分类

#### 低交互蜜罐（Low-Interaction Honeypot）

低交互蜜罐仅模拟服务的网络端口和基本协议响应，不提供真实的操作系统环境。

- **特点**：安全风险低，部署简单，维护成本低
- **局限**：信息收集有限，容易被高级攻击者识别
- **适用**：大规模部署、内网快速检测、扫描活动监测
- **代表工具**：Honeyd、Dionaea（部分模式）

#### 中交互蜜罐（Medium-Interaction Honeypot）

中交互蜜罐模拟更复杂的协议交互，能回应一定深度的攻击请求，但不提供真实OS。

- **特点**：平衡了信息收集与安全风险，可捕获Payload
- **局限**：仍可能被指纹识别，不支持完整攻击链
- **适用**：恶意软件样本采集、漏洞利用Payload捕获
- **代表工具**：Cowrie、Dionaea

#### 高交互蜜罐（High-Interaction Honeypot）

高交互蜜罐提供真实的操作系统和服务环境，允许攻击者完全交互。

- **特点**：信息收集最丰富，能记录完整攻击链，难以被识别
- **局限**：安全风险最高，需要严格隔离，维护成本高
- **适用**：APT追踪、高级攻击者行为研究、0day捕获
- **代表工具**：T-Pot（组合平台）、自定义真实环境

### 2.2 按部署位置分类

#### 生产网络蜜罐

部署在生产网络内部，与真实服务器混布，用于检测内网入侵和横向移动。

- 优势：能直接捕获针对生产环境的攻击
- 风险：攻击者可能从蜜罐跳转到真实系统
- 要求：严格的网络隔离和出口控制

#### 隔离网络蜜罐

部署在隔离的DMZ或专用网络中，用于互联网威胁监测和研究。

- 优势：安全风险可控，不影响生产网络
- 局限：可能无法吸引针对性攻击
- 要求：隔离网络、专用监控通道

### 2.3 按目标对象分类

| 类型 | 诱饵对象 | 典型场景 | 代表工具 |
|------|----------|----------|----------|
| 服务蜜罐 | 网络服务（SSH/Web/DB） | 暴力破解检测、漏洞利用捕获 | Cowrie、Glastopf |
| 客户端蜜罐 | 客户端应用（浏览器/Office） | 恶意网站/文档探测 | HoneyC、PhoneyC |
| 系统蜜罐 | 完整操作系统 | APT追踪、完整攻击链 | Honeynet |
| Web蜜罐 | Web应用 | Web攻击检测、SQL注入分析 | Glastopf、Snare |
| 数据库蜜罐 | 数据库服务 | 数据窃取检测 | Sticky honeypot |
| IoT蜜罐 | 物联网设备协议 | IoT僵尸网络监测 | HoneyIoT、Cowrie |

### 2.4 按攻击阶段分类

```
攻击者行为链路与蜜罐映射：

侦察阶段 → 扫描蜜罐（端口监听诱饵）
    ↓
入侵阶段 → 服务蜜罐（漏洞利用诱饵）
    ↓
横向移动 → 内网蜜罐（虚假主机/服务）
    ↓
权限提升 → 凭证蜜罐（假凭证/假管理员账户）
    ↓
数据外传 → 文件蜜罐（诱饵数据/Canary文件）
```

## 3. 常见蜜罐工具与部署

### 3.1 Honeyd（虚拟蜜罐框架）

Honeyd是最经典的开源虚拟蜜罐框架，可同时模拟上千台不同操作系统的主机。

**核心功能：**
- 模拟任意IP地址的虚拟主机
- 支持模拟多种操作系统指纹（通过TCP/IP栈指纹）
- 可配置模拟开放端口和服务的响应
- 支持网络拓扑模拟

**部署示例配置：**

```
# honeyd.conf 示例
create linux_server
set linux_server personality "Linux 2.4.20"
set linux_server default tcp action reset
add linux_server tcp port 22 "sh /usr/share/honeyd/scripts/sshd.sh"
add linux_server tcp port 80 "sh /usr/share/honeyd/scripts/web.sh"
set linux_server uptime 328320

create windows_server
set windows_server personality "Microsoft Windows XP Professional SP1"
set windows_server default tcp action reset
add windows_server tcp port 135 open
add windows_server tcp port 139 open
add windows_server tcp port 445 open

bind 192.168.1.100 linux_server
bind 192.168.1.101 windows_server
```

**适用场景：** 大规模网络伪装、攻击者扫描行为研究。

### 3.2 Cowrie（SSH/Telnet蜜罐）

Cowrie是目前最流行的中交互SSH/Telnet蜜罐，由Michau Oosterhout开发。

**核心功能：**
- 模拟SSH和Telnet服务
- 提供模拟Shell环境（支持常见命令）
- 记录攻击者的完整会话（输入命令、文件传输）
- 支持SFTP文件上传捕获
- 输出JSON格式日志，便于SIEM集成
- 支持Docker容器部署

**关键配置：**

```ini
# cowrie.cfg 关键配置
[honeypot]
hostname = server-prod-01
log_path = /cowrie/cowrie-git/var/log/cowrie
download_path = /cowrie/cowrie-git/var/lib/cowrie/downloads
interactive_timeout = 180
simulation_technology = full

[ssh]
enabled = true
listen_port = 2222

[telnet]
enabled = true
listen_port = 2223

[output_json]
enabled = true
logfile = var/log/cowrie/cowrie.json
```

**数据输出示例（JSON）：**

```json
{
  "eventid": "cowrie.command.input",
  "timestamp": "2024-01-15T10:30:45.123456Z",
  "src_ip": "203.0.113.50",
  "session": "a1b2c3d4",
  "message": "cat /etc/passwd",
  "input": "cat /etc/passwd"
}
```

**适用场景：** SSH暴力破解趋势分析、IoT僵尸网络监测、恶意软件下载样本采集。

### 3.3 Dionaea（多协议蜜罐）

Dionaea是一个多协议蜜罐，支持SMB、HTTP、FTP、TFTP、MSSQL、MySQL等多种协议。

**核心功能：**
- 多协议模拟（SMB/HTTP/FTP/MSSQL等）
- 恶意软件样本自动下载与存储
- 支持协议级漏洞利用检测
- 集成对恶意软件的自动分析（提交至Cuckoo沙箱）
- 支持威胁情报上报（Niccoll）

**部署（Docker）：**

```bash
docker run -d \
  --name dionaea \
  -p 21:21 -p 23:23 -p 80:80 \
  -p 135:135 -p 443:443 -p 445:445 \
  -p 1433:1433 -p 3306:3306 \
  -v /data/dionaea:/opt/dionaea/var \
  dinotools/dionaea-docker
```

**适用场景：** Windows蠕虫传播监测（如WannaCry的SMB利用）、数据库攻击监测。

### 3.4 HFish（轻量级蜜罐框架）

HFish是国内开发的一款轻量级、跨平台蜜罐框架，支持多种协议快速部署。

**核心功能：**
- Web管理界面，可视化管理
- 支持SSH、Redis、MySQL、Telnet、Web等多种协议蜜罐
- 内置威胁情报分析
- 支持企业级集中管理（多节点部署）
- 告警推送（邮件、钉钉、企业微信、Webhook）

**部署架构：**

```
┌─────────────────────────────────┐
│        HFish管理中心            │
│   Web Dashboard + 告警引擎      │
└──────────┬──────────────────────┘
           │
    ┌──────┼──────┐
    │      │      │
  节点1   节点2   节点3
  (SSH)  (Web)  (Redis)
```

**适用场景：** 企业内网快速蜜罐部署、中小型组织威胁检测、国产化合规需求场景。

### 3.5 T-Pot（一体化蜜罐平台）

T-Pot是由德国电信安全团队开发的一体化蜜罐平台，集成了20+种蜜罐和分析工具。

**集成组件：**
- 蜜罐：Cowrie、Dionaea、Honeytrap、Conpot、ElasticPot、Glastopf、Heralding等
- 数据分析：Elasticsearch、Kibana、Logstash（ELK）
- 网络安全监控：Suricata（IDS）
- 文件分析：FATT（文件类型分析工具）
- 可视化：Kibana Dashboard（攻击态势可视化）

**部署要求：**
- 至少8GB内存，推荐16GB+
- 100GB存储空间
- Ubuntu Server环境

**优势：** 一键部署，开箱即用，社区活跃，持续更新。

**局限：** 资源消耗大，不适合资源受限环境。

**适用场景：** 研究型蜜罐部署、全面威胁情报收集、安全实验室/教学环境。

### 3.6 Honeytrap（动态蜜罐）

Honeytrap是一个动态蜜罐框架，特点是能动态监听任意端口并模拟服务。

**核心功能：**
- 动态端口监听（攻击者连接任意端口均可触发）
- 支持TCP/UDP协议
- Web界面管理
- 支持自定义服务响应脚本
- 与Elasticsearch集成

**适用场景：** 全端口覆盖检测、未知服务攻击探测。

### 3.7 Web蜜罐（Glastopf、Snare、Tanner）

#### Glastopf

- Python开发的轻量级Web蜜罐
- 模拟Web应用漏洞（SQL注入、LFI、RFI、RCE）
- 自动采集攻击Payload
- 适用于Web攻击趋势监测

#### Snare + Tanner

- Snare是Web蜜罐前端（模拟Web应用）
- Tanner是后端分析引擎（决策引擎）
- 支持动态生成Web页面内容
- 更真实地模拟Web应用行为

**Snare部署示例：**

```bash
# 使用Docker部署Snare
docker run -d --name snare \
  -p 80:80 \
  -e SNARE_HOST=0.0.0.0 \
  -e SNARE_PORT=80 \
  -e TANNER_HOST=tanner \
  -e TANNER_PORT=8090 \
  mushorg/snare
```

## 4. 高交互蜜罐

### 4.1 高交互蜜罐架构

高交互蜜罐提供真实的操作系统和运行服务，攻击者可以进行完整的攻击活动。

**架构要点：**

```
┌──────────────────────────────────────────┐
│           互联网（攻击者）               │
└──────────────┬───────────────────────────┘
               │
    ┌──────────┴──────────┐
    │   防火墙（入口控制） │
    └──────────┬──────────┘
               │
    ┌──────────┴──────────────────────┐
    │        蜜罐网络（VLAN隔离）     │
    │  ┌────────┐  ┌────────┐         │
    │  │ Honeypot│  │ Honeypot│        │
    │  │  Host 1│  │  Host 2 │        │
    │  └────────┘  └────────┘         │
    └──────────┬──────────────────────┘
               │
    ┌──────────┴──────────┐
    │  Sebek/数据收集层   │ ← 隐蔽监控
    └─────────────────────┘
               │
    ┌──────────┴──────────┐
    │   日志/分析服务器   │ ← 安全网络
    └─────────────────────┘
```

**关键设计原则：**
1. **严格隔离**：蜜罐网络与生产网络物理/VLAN隔离
2. **隐蔽监控**：数据收集不能被攻击者发现
3. **出口控制**：限制蜜罐向外发起连接的能力（防止跳板攻击）
4. **数据完整性**：确保收集的攻击数据完整且不可篡改

### 4.2 Sebek内核模块

Sebek是Honeynet项目开发的高交互蜜罐数据收集工具，以内核模块方式隐蔽运行。

**Sebek工作原理：**
- 以Linux内核模块加载，运行在Ring 0（内核层）
- Hook系统调用（read、write、execve等）
- 在内核层捕获攻击者的输入输出
- 通过隐蔽通道将数据传输到远程日志服务器
- 攻击者在用户层无法检测到Sebek的存在

**Sebek数据收集范围：**
- 按键记录（SSH会话中的命令输入）
- 文件读写内容
- 网络数据包
- 进程创建信息

**现代替代方案：**
由于Sebek的内核模块方式在新版Linux中维护困难，现代高交互蜜罐更多采用：
- 容器级监控（eBPF程序）
- 虚拟机自省（VMI）技术
- 系统审计框架（auditd、sysmon）

### 4.3 数据收集与分析

**高交互蜜罐数据收集层次：**

| 层次 | 数据类型 | 收集工具 | 分析目标 |
|------|----------|----------|----------|
| 网络层 | 全流量PCAP | tcpdump/Bro | 网络行为、C2通信 |
| 系统层 | 进程/文件/注册表 | auditd/sysmon | 系统级行为 |
| 内核层 | 系统调用/按键 | Sebek/eBPF | 隐蔽行为捕获 |
| 应用层 | 日志/会话 | 应用日志 | 应用层攻击细节 |
| 数据层 | 文件传输/下载 | 自动归档 | 恶意软件样本 |

### 4.4 高交互蜜罐的风险

**风险清单与缓解措施：**

| 风险 | 描述 | 缓解措施 |
|------|------|----------|
| 跳板攻击 | 攻击者利用蜜罐攻击其他系统 | 严格出口控制防火墙 |
| 数据泄露 | 蜜罐上可能存在敏感信息 | 蜜罐上不放置真实数据 |
| 识别风险 | 蜜罐被识别导致攻击者回避 | 定期更新伪装内容 |
| 法律风险 | 可能涉及监听和隐私问题 | 法律审查、免责声明 |
| 维护风险 | 蜜罐被攻陷后需重建 | 快速重建脚本/镜像 |
| 运营风险 | 资源消耗大，影响稳定 | 专用资源、监控告警 |

## 5. 企业蜜罐部署方案

### 5.1 部署架构设计

**企业级蜜罐部署架构（分层部署）：**

```
┌─────────────────────────────────────────────────┐
│                 互联网边界                        │
│   ┌──────────┐  ┌──────────┐                     │
│   │ DMZ蜜罐  │  │ DMZ蜜罐  │  ← 外部威胁检测     │
│   │ (Cowrie) │  │(Glastopf)│                     │
│   └──────────┘  └──────────┘                     │
└───────────────────┬─────────────────────────────┘
                    │
┌───────────────────┴─────────────────────────────┐
│                   核心网络                        │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐      │
│   │ 内网蜜罐 │  │ 内网蜜罐 │  │ 内网蜜罐 │      │
│   │ (SSH)    │  │ (Redis)  │  │ (MySQL)  │      │

│                   数据中心                        │
│   ┌──────────┐  ┌──────────┐                     │

│   └──────────┘  └──────────┘                     │
└──────────────────────────────────────────────────┘

         ┌──────────────────────────┐
         │     管理中心（集中管理）   │
         │  SIEM + 蜜罐管理平台     │
         └──────────────────────────┘
```

### 5.2 网络位置选择

**蜜罐部署位置策略：**

| 网络位置 | 蜜罐类型 | 检测目标 | 风险等级 |
|----------|----------|----------|----------|
| 互联网边界 | 低交互服务蜜罐 | 外部扫描、自动化攻击 | 低 |
| DMZ区 | 中交互Web蜜罐 | 针对Web服务攻击 | 中 |
| 办公网 | 低交互多协议蜜罐 | 内网横向移动 | 低 |
| 核心网 | 低交互服务蜜罐 | 核心区入侵检测 | 低 |
| 数据中心 | 数据库蜜罐+诱饵文件 | 数据窃取检测 | 中 |
| VPN入口 | SSH蜜罐 | VPN后入侵检测 | 低 |

**部署原则：**
- 蜜罐的IP地址应与真实服务器在同一网段，但不与真实服务器IP重叠
- 蜜罐不应出现在DNS或服务发现协议中（攻击者主动扫描才能发现）
- 真实用户不应能访问到蜜罐（确保所有交互均为攻击行为）
- 出口流量必须受控（防止跳板攻击）

### 5.3 蜜罐伪装策略

**有效伪装的Checklist：**

- [ ] 蜜罐主机名符合命名规范（如srv-prod-03）
- [ ] 开放端口与服务符合该位置正常服务画像
- [ ] SSH Banner版本信息真实（不过新也不过旧）
- [ ] 文件系统中存在合理的业务数据文件
- [ ] 系统运行时间合理（不要显示刚启动）
- [ ] 网络流量特征与真实服务器一致
- [ ] 错误信息（404/500等）与真实应用一致
- [ ] SSL证书与真实域名匹配
- [ ] 时区和系统语言设置合理

### 5.4 与SIEM/SOC集成

**蜜罐告警集成SIEM流程：**

```
蜜罐事件 → 日志转发（Syslog/CEF/JSON）→ SIEM（Splunk/ELK/QRadar）
    → 关联分析（与威胁情报/其他日志关联）
    → 告警生成 → SOC分析师研判
    → SOAR自动响应（封堵IP/隔离主机/触发IR）
```

**Splunk集成示例（inputs.conf）：**

```ini
[monitor:///var/log/cowrie/cowrie.json]
sourcetype = cowrie:json
index = honeypot
disabled = false

[monitor:///var/log/dionaea/*.log]
sourcetype = dionaea:log
index = honeypot
disabled = false
```

**Splunk告警规则示例：**

```spl
# 检测同一IP对多个蜜罐的扫描
index=honeypot sourcetype=cowrie:json
| stats dc(dest_ip) as honeypot_count by src_ip
| where honeypot_count > 3
```

### 5.5 告警配置与响应

**告警分级矩阵：**

| 事件类型 | 告警级别 | 响应时效 | 响应动作 |
|----------|----------|----------|----------|
| 蜜罐被扫描（单次） | 低 | 24小时 | 记录、加入观察列表 |
| 蜜罐被暴力破解 | 中 | 4小时 | 封堵源IP、分析攻击模式 |
| 蜜罐被成功登录 | 高 | 30分钟 | 立即响应、全流量分析 |
| 蜜罐文件被访问 | 高 | 30分钟 | 排查攻击路径、关联溯源 |
| 蜜罐对外发起连接 | 紧急 | 立即 | 紧急隔离、全面IR |
| 多个蜜罐同时被访问 | 高 | 1小时 | 大规模攻击研判、启动应急预案 |

### 6.2 Canary文件与令牌

**Canary文件（诱饵文件）：**
- 在文件服务器、共享目录、用户桌面投放虚假的诱饵文件
- 文件名具有诱惑性（如"员工薪资表.xlsx"、"数据库配置.ini"、"客户名单.docx"）
- 文件被打开、复制、修改时触发告警
- 文件内嵌追踪令牌（Canarytoken）

**Canarytoken类型：**

| 令牌类型 | 触发方式 | 部署位置 | 检测场景 |
|----------|----------|----------|----------|
| Web Bug token | 文件被打开并联网 | 文档中 | 数据窃取检测 |
| DNS token | DNS查询触发 | 任意文件 | 内网渗透检测 |
| AWS API Key token | API Key被使用 | 配置文件中 | 云凭据窃取 |
| SQL token | SQL查询执行 | 数据库中 | 数据外泄检测 |
| Slack token | API调用 | 配置文件 | 凭据盗用检测 |
| Microsoft Word token | 宏执行 | Office文档 | 文档钓鱼 |
| PDF token | 链接点击 | PDF文件 | 文档分发追踪 |

**Canarytoken部署示例（Thinkst Canary）：**

```python
# 生成DNS Canarytoken
import canarytokens
token = canarytokens.generate(
    type='dns',
    domain='canarytokens.com',
    memo='财务共享目录诱饵-2024Q1'
)
# 生成结果：xxx.canarytokens.com
# 将此域名嵌入诱饵文件中
```

### 6.3 假数据与假凭证

**假凭证投放策略：**

- 在配置文件中放置假的数据库连接字符串
- 在代码仓库中放置假的API Key
- 在密码管理器中放置假的特权账号
- 在SSH known_hosts中添加虚假主机条目

**设计原则：**
1. 假凭证看起来必须真实（符合命名规范和格式）
2. 假凭证不能与任何真实系统关联（确保误用时可追溯）
3. 假凭证的使用必须在监控系统中设置唯一告警规则
4. 定期轮换假凭证（保持新鲜度）

## 7. 蜜罐数据分析与威胁情报

### 7.1 攻击者行为分析

**行为分析框架（基于ATT&CK）：**

1. **入口分析**：攻击者从哪个入口进入蜜罐（SSH爆破、Web扫描、漏洞利用）
2. **动机分析**：攻击者的目标是什么（加密货币挖矿、数据窃取、横向移动跳板）
3. **能力分析**：使用的工具和技术水平（自动化脚本、手动操作、商用工具）
4. **持久化分析**：是否尝试建立持久化后门
5. **横向移动分析**：是否尝试访问蜜罐所在网络的其他主机

**Cowrie会话行为分析示例：**

```python
# 分析攻击者在Cowrie中的行为序列
sessions = parse_cowrie_log("cowrie.json")

for session in sessions:
    src_ip = session["src_ip"]
    commands = session["commands"]
    
    # 行为分类
    if "wget" in commands or "curl" in commands:
        # 下载恶意软件
        classify_as(src_ip, "MALWARE_DOWNLOAD")
    if "nmap" in commands or "masscan" in commands:
        # 内网扫描
        classify_as(src_ip, "INTERNAL_SCAN")
    if "/etc/shadow" in commands or "cat /etc/passwd" in commands:
        # 信息收集
        classify_as(src_ip, "INFO_GATHERING")
    if "useradd" in commands:
        # 创建后门账户
        classify_as(src_ip, "PERSISTENCE")
```

### 7.2 IOC提取

**从蜜罐数据提取的IOC类型：**

| IOC类型 | 提取方法 | 用途 |
|---------|----------|------|
| 恶意IP | 蜜罐日志中的源IP | 防火墙封堵 |
| 恶意域名 | DNS日志中的查询域名 | DNS过滤 |
| 恶意URL | Web蜜罐中的请求URL | WAF规则 |
| Payload哈希 | 文件上传的MD5/SHA256 | AV/EDR规则 |
| C2地址 | 网络流量中的C2通信 | IPS规则 |
| SSH密钥 | 攻击者使用的公钥 | 入侵检测 |
| 用户名/密码 | 暴力破解字典 | 密码策略 |
| UA指纹 | HTTP User-Agent | WAF规则 |

**IOC提取脚本示例：**

```python
import hashlib
import json
from collections import Counter

def extract_iocs(cowrie_log_path):
    iocs = {
        "malicious_ips": set(),
        "credentials": set(),
        "payloads": [],
        "commands": Counter()
    }
    
    with open(cowrie_log_path) as f:
        for line in f:
            event = json.loads(line)
            if event.get("eventid") == "cowrie.session.connect":
                iocs["malicious_ips"].add(event["src_ip"])
            elif event.get("eventid") == "cowrie.login":
                iocs["credentials"].add(
                    f"{event['username']}:{event['password']}"
                )
            elif event.get("eventid") == "cowrie.command.input":
                iocs["commands"][event["input"]] += 1
            elif event.get("eventid") == "cowrie.session.file_download":
                with open(event["shasum"], "rb") as payload:
                    data = payload.read()
                    iocs["payloads"].append({
                        "sha256": hashlib.sha256(data).hexdigest(),
                        "size": len(data),
                        "url": event.get("url")
                    })
    
    return iocs
```

## 8. 实战案例

### 案例1：企业内网蜜罐捕获攻击者

**背景**：某大型企业部署了HFish蜜罐框架，在内网核心区部署了SSH蜜罐、Redis蜜罐和MySQL蜜罐，用于检测内网横向移动。

**事件经过：**

某日凌晨2:15，HFish管理平台发出高优先级告警——内网SSH蜜罐（10.10.20.50）被成功登录，攻击者使用了弱口令"admin123"。

**SOC团队调查过程：**

1. **确认告警有效性**：该IP为蜜罐专用IP，无合法用户会访问，告警确认为真实攻击行为。
2. **溯源攻击源IP**：攻击来自10.10.10.35，是办公网一台开发人员工作站。
3. **关联其他蜜罐告警**：查看HFish日志发现，同一IP在2:10先扫描了10.10.20.0/24网段，2:15尝试登录SSH蜜罐成功，2:20尝试连接Redis蜜罐（6379端口）。
4. **工作站取证**：安全团队对该工作站进行取证，发现该机器感染了Emotet木马，攻击者通过C2通道远程控制该机器进行内网横向移动。
5. **影响评估**：由于蜜罐及时告警，攻击者在到达真实核心系统之前即被发现，未造成数据泄露。

**处置措施：**
- 立即从网络隔离感染工作站
- 对该用户账户重置所有凭据
- 全网扫描相同的Emotet变种
- 增加更多内网蜜罐节点覆盖
- 检查所有使用"admin123"弱口令的账户

**经验总结：**
- 内网蜜罐是检测横向移动的有效手段，且误报率极低
- 蜜罐部署在核心区入口（如10.10.20.0/24网段）效果最佳
- 蜜罐告警应设置最高优先级，因为任何蜜罐交互都是真实攻击
- 与终端EDR联动可快速定位攻击源机器

### 案例2：利用Cowrie分析SSH暴力破解趋势

**背景**：某安全研究团队部署了多个公网Cowrie蜜罐，分布在不同云区域，持续运行6个月收集SSH攻击数据。

**数据分析发现：**

**发现1：攻击源地理分布**
- TOP3攻击源国家：中国（18%）、俄罗斯（15%）、美国（12%）
- 但需注意：攻击源IP所在国不等于攻击者所在国

**发现2：暴力破解字典趋势**
```
TOP 10 密码（6个月统计）：
1. admin       - 32,156次
2. 123456      - 28,987次
3. password    - 25,432次
4. root        - 22,108次
5. 1q2w3e      - 18,765次
6. admin123    - 15,321次
7. test        - 14,876次
8. user        - 12,543次
9. default     - 11,234次
10. P@ssw0rd   - 10,876次
```

**发现3：攻击模式演变**
- 第1-2月：以传统字典攻击为主（每IP尝试10-50个密码）
- 第3-4月：出现高并发攻击（单IP短时间尝试上千次）
- 第5-6月：出现精准攻击（针对特定用户名+密码组合，疑似使用泄露凭据库）

**发现4：攻击后行为**
- 约15%的成功登录后执行了"uname -a"命令（系统信息收集）
- 约10%尝试下载并执行恶意软件（加密货币挖矿程序）
- 约5%尝试添加SSH公钥到authorized_keys（持久化）
- 约2%尝试修改防火墙规则
- 约1%执行了内网扫描命令

**威胁情报产出：**
- 向MISP上传了3,200+个恶意IP
- 提取了42个恶意软件样本
- 生成了SSH暴力破解趋势报告
- 向社区共享了暴力破解密码字典

**经验总结：**
- 公网蜜罐是低成本的威胁情报生产手段
- 攻击趋势在持续演变，安全策略需要同步更新
- 暴力破解密码字典可直接用于内部密码审计
- 捕获的恶意软件样本可用于AV规则更新

### 案例3：欺骗防御阻止横向移动

**背景**：某金融机构部署了商业欺骗防御平台（AttackerTrap），在内部网络投放了虚假的数据库服务、文件共享和域控服务。

**事件经过：**

某日，攻击者通过钓鱼邮件获取了一个员工的VPN访问权限，进入内网后开始横向移动侦察。

**攻击者行为与欺骗防御触发：**

**T+0小时**：攻击者通过VPN进入内网，开始nmap扫描10.0.0.0/16网段。
- 欺骗防御平台自动检测到扫描行为，动态部署了3个虚假主机

**T+1小时**：攻击者发现并尝试登录虚假的SMB文件共享（\\DECOY-FS01\shared）。
- Canary文件"财务季度报告.xlsx"被访问
- 系统立即触发紧急告警

**T+1.5小时**：攻击者使用mimikatz提取了该员工工作站的凭据，发现了一个假的管理员凭据。
- 假凭据被使用时触发Canarytoken告警
- SOAR平台自动将该凭据使用行为关联到之前的SMB告警

**T+2小时**：SOC团队收到告警，开始响应。
- 确认攻击者VPN会话
- 识别被攻陷的员工工作站
- 隔离受影响主机
- 重置相关凭据

**T+2.5小时**：攻击者尝试使用假凭据登录虚假域控。
- 虚假域控记录了攻击者的完整LDAP查询
- 获取了攻击者关注的AD对象列表（高权限用户、计算机列表）

**T+3小时**：安全团队完成全面隔离和清除。

**关键经验：**
1. **动态欺骗效果显著**：欺骗防御平台动态生成的虚假主机成功引诱了攻击者，使攻击者在虚假目标上花费了大量时间。
2. **多层诱饵协同**：SMB共享+Canary文件+假凭据的多层部署形成了完整的检测链。
3. **自动化响应关键**：SOAR平台自动关联多源告警，大幅缩短了MTTD（平均检测时间）。
4. **攻击者画像完整**：通过虚假域控记录的LDAP查询，完整了解了攻击者的侦察目标，为后续防御加固提供了情报。
5. **欺骗防御不影响业务**：整个过程中，真实业务系统未受影响，攻击者在虚假环境中活动。

**改进措施：**
- 增加虚假云资源（假S3存储桶、假IAM角色）
- 部署虚假Kubernetes服务，吸引容器环境攻击
- 增加Canarytoken在代码仓库中的覆盖
- 将欺骗防御告警与EDR自动响应联动

## 总结与Checklist

蜜罐与欺骗防御技术是安全防御从"被动检测"向"主动防御"转变的关键技术。在当今攻击者技术日益精进、攻击链路日益复杂的背景下，传统被动防御已无法满足检测需求，蜜罐和欺骗防御以其极低的误报率和丰富的情报产出，成为现代安全运营中心不可或缺的组件。

**蜜罐部署决策Checklist：**

- [ ] 明确蜜罐部署目标（威胁情报采集/内网入侵检测/攻击者研究）
- [ ] 评估部署风险（跳板攻击风险/法律合规风险）
- [ ] 选择合适蜜罐工具（低交互/中交互/高交互）
- [ ] 设计部署架构（网络位置/隔离方案/管理方式）
- [ ] 配置伪装策略（主机名/服务/Banner/文件）
- [ ] 部署出口控制防火墙
- [ ] 配置日志转发到SIEM
- [ ] 设置告警规则和分级
- [ ] 建立蜜罐运维SOP
- [ ] 制定法律合规审查流程
- [ ] 规划数据分析与威胁情报产出
- [ ] 定期评估蜜罐有效性并更新

> **核心理念**：欺骗防御的最高境界是让攻击者在虚假世界中花费所有时间，而真实系统安然无恙。不是用更多的墙来阻挡攻击，而是用更聪明的陷阱来捕获攻击者。
