# PDCERF 模型/生命周期

### 3.1 PDCERF 模型概述

PDCERF 模型是应急响应的经典生命周期模型，包含六个阶段：

| 阶段 | 英文 | 说明 |
|------|------|------|
| **P** - 准备 | Preparation | 事件发生前的准备工作 |
| **D** - 检测 | Detection | 发现和确认安全事件 |
| **C** - 遏制 | Containment | 控制事件扩散范围 |
| **E** - 根除 | Eradication | 清除威胁根源 |
| **R** - 恢复 | Recovery | 恢复系统和业务正常运行 |
| **F** - 跟踪 | Follow-up | 总结改进和后续跟踪 |

### 3.2 准备阶段（Preparation）

**目标**：在事件发生前做好充分准备，确保能够快速有效地响应。

**主要工作：**

1. **组织准备**
   - 建立应急响应团队
   - 明确职责分工
   - 建立沟通机制
   - 制定汇报流程

2. **技术准备**
   - 部署安全监控系统（SIEM、IDS/IPS、EDR等）
   - 建立日志收集和分析体系
   - 准备应急响应工具包
   - 建立备份和恢复机制

3. **流程准备**
   - 制定应急预案
   - 制定事件分级标准
   - 制定响应流程和操作手册
   - 建立升级机制

4. **人员准备**
   - 应急响应培训
   - 应急演练
   - 技能认证
   - 知识管理

5. **资源准备**
   - 硬件资源（备用服务器、网络设备等）
   - 软件资源（安全工具、操作系统镜像等）
   - 外部资源（安全厂商、服务商等）
   - 预算保障

**准备阶段的重要性：**
> "平时多流汗，战时少流血。" 准备工作做得越充分，事件响应就越高效。统计表明，准备充分的组织在安全事件中的损失平均减少 60% 以上。

### 3.3 检测阶段（Detection）

**目标**：及时发现安全事件，并确认事件的真实性和严重程度。

**主要工作：**

1. **事件发现**
   - 安全设备告警（IDS/IPS、WAF、EDR等）
   - SIEM 关联分析告警
   - 用户报告和投诉
   - 系统异常现象
   - 第三方通知（合作伙伴、监管部门等）
   - 威胁情报匹配

2. **事件验证**
   - 确认告警是否为真实事件（排除误报）
   - 初步判断事件性质和类型
   - 评估事件影响范围
   - 确定事件严重等级

3. **事件上报**
   - 按规定流程上报事件
   - 通知相关人员和部门
   - 启动相应级别的应急响应

**检测阶段的关键指标：**
- **MTTD（Mean Time To Detect）**：平均检测时间
  - 从攻击发生到被检测到的时间
  - 越短越好，优秀水平应在几小时内
- **误报率**：错误告警的比例
  - 过高的误报率会导致告警疲劳
  - 应通过规则优化降低误报率

**案例：某企业勒索软件检测过程**

> **时间线：**
> - 08:00 - EDR 检测到某终端出现异常文件加密行为，触发告警
> - 08:02 - L1 分析师收到告警，进行初步核查
> - 08:05 - L1 分析师确认不是误报，判断为勒索软件攻击
> - 08:07 - L1 分析师升级给 L2 分析师，同时通知终端用户断网
> - 08:10 - L2 分析师确认事件，评估影响范围（目前1台终端）
> - 08:15 - 启动三级应急响应，通知应急响应负责人
>
> **MTTD：约5分钟（从攻击发生到确认事件）**

### 3.4 遏制阶段（Containment）

**目标**：快速控制事件扩散，防止事态扩大，最小化损失。

**主要工作：**

1. **短期遏制**
   - 隔离受感染主机（断网、禁用账号等）
   - 阻断攻击流量（封禁IP、阻断域名等）
   - 关闭受影响服务（防止进一步利用）
   - 保护关键数据（防止被篡改或删除）

2. **长期遏制**
   - 修补已知漏洞
   - 加强访问控制
   - 部署临时防护措施
   - 扩大监控范围

**遏制策略选择：**

| 策略 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| 完全隔离 | 严重事件，威胁扩散风险高 | 最安全，彻底阻止扩散 | 业务影响大 |
| 部分隔离 | 中等事件，可精确定位 | 业务影响较小 | 可能存在漏网之鱼 |
| 监控观察 | 低风险事件，需要收集更多信息 | 不影响业务，可获取更多攻击信息 | 风险较高，可能扩大损失 |

**遏制阶段的注意事项：**
- 优先保护证据，不要破坏现场
- 记录所有操作，便于后续分析
- 评估遏制措施对业务的影响
- 与业务部门沟通确认
- 做好准备再行动，避免忙中出错

**案例：Webshell 入侵的遏制措施**

> **事件**：攻击者通过文件上传漏洞获取了 Web 服务器权限，并植入了 Webshell。
>
> **遏制措施：**
> 1. 立即将 Web 服务器从负载均衡中摘除（防止更多用户访问被篡改页面）
> 2. 保留服务器网络连接但限制访问（保留日志和内存数据用于取证）
> 3. 备份服务器日志和相关文件
> 4. 对 Webshell 文件进行哈希计算和备份
> 5. 修改相关账号密码（防止攻击者继续利用）
> 6. 检查同网段其他服务器是否被入侵

### 3.5 根除阶段（Eradication）

**目标**：彻底清除威胁根源，确保系统安全。

**主要工作：**

1. **清除恶意代码**
   - 删除病毒、木马、后门等恶意程序
   - 清除 Webshell
   - 清除 Rootkit
   - 清除挖矿程序

2. **清除后门账号**
   - 删除攻击者创建的账号
   - 禁用被窃取的账号
   - 重置所有可能泄露的密码
   - 检查并修复被篡改的权限配置

3. **清除持久化机制**
   - 删除恶意计划任务
   - 删除恶意服务
   - 修复被篡改的启动项
   - 修复被篡改的注册表项

4. **修补安全漏洞**
   - 修复被利用的漏洞
   - 排查同类漏洞
   - 安装安全补丁
   - 加强安全配置

5. **全面排查**
   - 检查是否还有其他被入侵的系统
   - 检查数据是否被窃取
   - 检查横向移动痕迹
   - 确保威胁被彻底清除

**根除阶段的注意事项：**
- 确保所有后门都被清除，防止攻击者再次进入
- 进行全面排查，不要遗漏任何被入侵的系统
- 修补漏洞，防止再次被入侵
- 保留所有操作记录
- 确认根除效果后再进入恢复阶段

### 3.6 恢复阶段（Recovery）

**目标**：恢复系统和业务的正常运行。

**主要工作：**

1. **系统恢复**
   - 从干净的备份恢复系统
   - 或在清除威胁后重新启用系统
   - 验证系统完整性
   - 安装安全补丁和加固

2. **数据恢复**
   - 从备份恢复数据
   - 验证数据完整性
   - 确保数据没有被篡改

3. **服务恢复**
   - 逐步恢复各项服务
   - 验证服务功能正常
   - 监控服务运行状态

4. **业务验证**
   - 业务部门验证业务功能
   - 用户测试验证
   - 确认业务正常运行

**恢复策略：**

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| 全面恢复 | 从备份完全恢复系统 | 系统被严重破坏，无法修复 |
| 修复恢复 | 在现有系统基础上修复 | 系统损坏较轻，可清除威胁 |
| 重建恢复 | 重新部署系统和数据 | 系统被深度感染，无法信任 |

**恢复阶段的注意事项：**
- 确保系统已经安全后再恢复
- 逐步恢复，密切监控
- 做好回滚准备
- 保留恢复前的快照/备份
- 加强恢复后的监控

### 3.7 跟踪阶段（Follow-up）

**目标**：总结经验教训，持续改进安全能力。

**主要工作：**

1. **事件复盘**
   - 回顾事件处理全过程
   - 分析做得好的地方
   - 分析存在的问题和不足
   - 找出改进点

2. **报告编写**
   - 编写事件报告
   - 记录事件详情
   - 记录响应过程
   - 记录损失和影响
   - 提出改进建议

3. **改进措施**
   - 修补发现的安全漏洞
   - 完善安全防护措施
   - 更新应急预案
   - 优化检测规则
   - 加强安全培训

4. **后续跟踪**
   - 监控改进措施的执行情况
   - 评估改进效果
   - 关注攻击者是否再次尝试
   - 持续优化安全防护

**事件报告的主要内容：**
- 事件概述（时间、地点、影响）
- 事件详情（攻击手法、入侵路径、损失情况）
- 响应过程（各阶段的时间线和措施）
- 原因分析（根本原因、薄弱环节）
- 改进建议（技术、管理、流程）
- 经验教训

**案例：某企业数据泄露事件复盘报告（摘要）**

> **事件概述**：2024年3月15日，攻击者通过某Web应用的SQL注入漏洞，窃取了约10万条用户信息。
>
> **响应时间线**：
> - 3月15日 14:30 - WAF 检测到SQL注入攻击告警
> - 3月15日 14:35 - L1 分析师确认告警
> - 3月15日 14:40 - 启动应急响应，联系开发人员
> - 3月15日 15:00 - 漏洞修复完成
> - 3月15日 16:00 - 完成初步影响评估
>
> **存在的问题：**
> 1. 漏洞检测不及时，攻击者已成功窃取数据
> 2. 数据库权限过大，一次注入获取了大量数据
> 3. 数据没有加密，泄露后直接可用
> 4. 告警响应流程不够顺畅
>
> **改进措施：**
> 1. 全面排查所有Web应用的SQL注入漏洞（3天内完成）
> 2. 数据库最小权限配置（1周内完成）
> 3. 敏感数据加密存储（1个月内完成）
> 4. 优化告警响应流程，缩短响应时间（持续改进）
> 5. 加强开发人员安全培训（每季度一次）

### 3.8 PDCERF 模型的特点

1. **顺序执行但可迭代**
   - 各阶段按顺序进行
   - 但实际中可能需要反复迭代
   - 例如根除阶段发现新的问题，可能需要重新遏制

2. **准备阶段贯穿始终**
   - 准备工作不仅在事件前
   - 每次事件后都要改进准备工作
   - 准备工作是持续的

3. **检测和响应是核心**
   - 检测能力决定了能否及时发现事件
   - 响应能力决定了损失大小
   - 两者缺一不可

4. **持续改进是目标**
   - 应急响应的最终目标是提升安全能力
   - 每次事件都是学习和改进的机会
   - 跟踪阶段是实现持续改进的关键
