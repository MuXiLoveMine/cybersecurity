## 1. 蓝牙协议栈架构

### 1.1 蓝牙技术双模架构

蓝牙技术自 4.0 版本开始分为两种模式，它们共享 2.4 GHz 频段但协议栈架构不同：

```
蓝牙双模架构：

                    +-----------------------+
                    |     Application       |
                    |   (Profiles/Services) |
                    +-----------------------+
                              |
              +---------------+---------------+
              |                               |
    +---------+---------+         +-----------+-----------+
    | Classic Bluetooth |         |  Bluetooth Low Energy  |
    |    (BR/EDR)      |         |        (BLE)           |
    +------------------+         +------------------------+
    |   L2CAP          |         |    ATT (Attribute      |
    |   RFCOMM         |         |    Protocol)           |
    |   SDP            |         |    SMP (Security Mgr)  |
    |   OBEX           |         |    L2CAP (LE)          |
    +------------------+         +------------------------+
    |          HCI (Host Controller Interface)            |
    +-----------------------------------------------------+
    |          Link Manager (LM) / Link Layer (LL)        |
    +-----------------------------------------------------+
    |          Physical Layer (PHY)                       |
    +-----------------------------------------------------+
    |          2.4 GHz ISM Band (79/40 channels)          |
    +-----------------------------------------------------+
```

### 1.2 经典蓝牙协议栈（BR/EDR）

经典蓝牙使用 79 个信道（每信道 1 MHz），采用 FHSS（跳频扩频）技术：

```
经典蓝牙协议栈各层详解：

1. 射频层（Radio, RF）
   ├── 频段: 2.402 - 2.480 GHz
   ├── 79 个信道，每信道 1 MHz
   ├── 调制: GFSK（BR）/ π/4-DQPSK 或 8DPSK（EDR）
   ├── 速率: 1 Mbps (BR) / 3 Mbps (EDR)
   └── 跳频速率: 1600 次/秒

2. 基带层（Baseband）
   ├── 物理链路管理
   ├── 链路类型:
   │   ├── SCO (Synchronous Connection-Oriented): 语音
   │   └── ACL (Asynchronous Connection-Less): 数据
   ├── 时分双工（TDD）
   ├── 时隙: 625 us
   └── 包类型: DM1/DM3/DM5, DH1/DH3/DH5, 2-DH3, 3-DH3 等

3. 链路管理器协议（LMP）
   ├── 链路建立和维护
   ├── 认证和配对
   ├── 加密协商
   ├── 密钥生成
   ├── 功率控制
   └── 多时隙包协商

4. 主机控制器接口（HCI）
   ├── 主机和控制器之间的接口
   ├── 命令接口: HCI Command
   ├── 事件接口: HCI Event
   ├── 数据接口: ACL/SCO Data
   └── 传输层: USB/UART/SDIO

5. 逻辑链路控制和适配协议（L2CAP）
   ├── 协议复用
   ├── 分段和重组（SAR）
   ├── 流量控制
   ├── QoS 支持
   └── 信道复用（CID）

6. 串行端口仿真协议（RFCOMM）
   ├── 模拟 RS-232 串口
   ├── 提供虚拟串口
   ├── 支持多路复用（最多 60 个连接）
   └── 为上层协议提供可靠传输

7. 服务发现协议（SDP）
   ├── 发现远程设备的服务
   ├── 查询服务属性
   ├── 服务类 UUID
   └── 服务记录数据库

8. 高层协议
   ├── OBEX: 对象交换（文件传输）
   ├── AVDTP: 音视频分发传输
   ├── AVCTP: 音视频控制传输
   ├── PPP: 点对点协议
   ├── TCP/IP: 网络协议栈
   └── 各种 Profile: A2DP, HFP, SPP, DUN 等
```

### 1.3 BLE 协议栈

BLE 使用 40 个信道（每信道 2 MHz），设计目标是超低功耗：

```
BLE 协议栈详解：

1. 物理层（PHY）
   ├── 频段: 2.402 - 2.480 GHz
   ├── 40 个信道，每信道 2 MHz
   ├── 调制: GFSK
   ├── 速率: 1 Mbps (BLE 4.0) / 2 Mbps (BLE 5.0)
   ├── 信道分类:
   │   ├── 广播信道: 37, 38, 39（用于广播/扫描）
   │   └── 数据信道: 0-36（用于连接后数据传输）
   └── 发射功率: -20 to +10 dBm

2. 链路层（Link Layer, LL）
   ├── 状态机:
   │   ├── Standby: 空闲
   │   ├── Advertising: 广播（广播者）
   │   ├── Scanning: 扫描（扫描者）
   │   ├── Initiating: 发起连接（主设备）
   │   └── Connection: 已连接（主/从设备）
   ├── 设备角色:
   │   ├── Master (Central): 扫描并发起连接
   │   └── Slave (Peripheral): 广播并接受连接
   ├── 广播类型:
   │   ├── ADV_IND: 可连接可扫描
   │   ├── ADV_DIRECT_IND: 定向连接
   │   ├── ADV_NONCONN_IND: 不可连接
   │   └── ADV_SCAN_IND: 可扫描不可连接
   ├── LL 控制 PDU:
   │   ├── LL_CONNECTION_PARAM_REQ
   │   ├── LL_CHANNEL_MAP_REQ
   │   ├── LL_TERMINATE_IND
   │   ├── LL_ENC_REQ/LL_ENC_RSP (加密)
   │   ├── LL_START_ENC_REQ/LL_START_ENC_RSP
   │   ├── LL_PHY_REQ/LL_PHY_RSP (PHY 更新)
   │   └── LL_PING_REQ/LL_PING_RSP (LE Ping)
   └── 自适应跳频: 根据信道质量调整跳频表

3. 主机控制器接口（HCI）
   ├── 与经典蓝牙共享 HCI 接口
   ├── BLE 特有命令
   └── HCI 事件和命令

4. 逻辑链路控制（L2CAP - LE）
   ├── LE 信号信道（CID=0x0005）
   ├── 属性协议（ATT）信道（CID=0x0004）
   ├── 安全管理协议（SMP）信道（CID=0x0006）
   ├── 连接参数更新
   ├── 信道模式:
   │   └── LE 基本连接模式（无重传）
   └── 固定信道支持

5. 安全管理协议（Security Manager Protocol, SMP）
   ├── 配对（Pairing）
   ├── 密钥生成
   ├── 加密设置
   └── 密钥分发

6. 属性协议（Attribute Protocol, ATT）
   ├── 客户端/服务器模型
   ├── 属性（Attribute）:
   │   ├── Handle: 属性句柄（16位）
   │   ├── Type: UUID（16/32/128位）
   │   ├── Value: 属性值
   │   └── Permissions: 读/写/通知权限
   ├── ATT PDU:
   │   ├── Request/Response
   │   ├── Command
   │   ├── Notification
   │   └── Indication/Confirmation
   └── 最大传输单元（MTU）协商

7. 通用属性协议（GATT）
   ├── 定义在 ATT 之上的数据模型
   ├── 层次结构:
   │   ├── Profile: 最高层（如心率、血压）
   │   ├── Service: 服务（一组相关功能）
   │   ├── Characteristic: 特征值（数据项）
   │   └── Descriptor: 描述符（元数据）
   ├── 服务类型:
   │   ├── Primary Service (UUID=0x2800)
   │   └── Secondary Service (UUID=0x2801)
   ├── 特征值:
   │   ├── 声明（Properties + Handle + UUID）
   │   └── 值
   ├── 特征属性:
   │   ├── Read (0x02)
   │   ├── Write (0x08)
   │   ├── Write Without Response (0x04)
   │   ├── Notify (0x10)
   │   ├── Indicate (0x20)
   │   └── Broadcast (0x01)
   └── 常见服务:
       ├── 0x1800: Generic Access
       ├── 0x1801: Generic Attribute
       ├── 0x180A: Device Information
       ├── 0x180D: Heart Rate
       ├── 0x180F: Battery Service
       └── 0x1810: Blood Pressure

8. 通用访问协议（GAP）
   ├── 设备发现
   ├── 连接建立
   ├── 安全管理
   ├── 广播数据格式:
   │   ├── Flags
   │   ├── Complete/Incomplete Service UUIDs
   │   ├── Shortened/Complete Local Name
   │   ├── TX Power Level
   │   ├── Manufacturer Specific Data
   │   └── Service Data
   └── 设备角色:
       ├── Broadcaster: 仅广播
       ├── Observer: 仅扫描
       ├── Peripheral: 广播+连接
       └── Central: 扫描+连接
```

## 2. BLE 安全机制

### 2.1 BLE 配对模式

BLE 配对是设备之间建立安全连接的过程，分为两个阶段：

```
BLE 配对流程：

阶段1: 配对请求交换
├── Initiator -> Responder: Pairing Request
│   ├── IO Capability
│   ├── OOB Data Flag
│   ├── Bonding Flags
│   ├── MITM Flag
│   ├── SC Flag (Secure Connections)
│   └── Max Encryption Key Size
└── Responder -> Initiator: Pairing Response

阶段2: 密钥生成（Legacy 或 Secure Connections）

阶段3: 密钥分发
├── 分发 LTK, IRK, CSRK 等密钥
└── 用于后续连接的加密和签名

配对方法（取决于 IO 能力）：

1. Just Works（无认证）
   ├── 无用户输入/显示
   ├── 无 MITM 保护
   ├── TK = 0（Legacy）/ 使用 ECDH（SC）
   └── 安全性最低

2. Passkey Entry（6位数字）
   ├── 一方显示6位数字，另一方输入
   ├── 提供 MITM 保护
   ├── TK = Passkey（Legacy）
   └── 多轮确认（SC）

3. Numeric Comparison（仅 SC）
   ├── 双方显示6位数字
   ├── 用户确认是否一致
   ├── 提供 MITM 保护
   └── 仅 Secure Connections 支持

4. Out of Band（OOB）
   ├── 通过其他通道（NFC等）交换配对信息
   ├── 最高安全性
   ├── 传递: 随机数、确认值、公钥
   └── 提供 MITM 保护
```

### 2.2 Legacy 配对密钥派生

```
Legacy 配对密钥生成流程：

1. 临时密钥（TK）生成
   ├── Just Works: TK = 0
   ├── Passkey: TK = Passkey (6位数字, 128位表示)
   └── OOB: TK = OOB Data (128位)

2. 短期密钥（STK）生成
   ├── 交换随机数 Srand 和 Irand
   ├── STK = s1(TK, Srand, Irand)
   └── s1: AES-CMAC 生成 128 位 STK

3. 长期密钥（LTK）分发
   ├── EDIV (16位): 加密分集标识
   ├── Rand (64位): 随机数
   └── LTK (128位): 长期加密密钥

Legacy 配对安全弱点：
├── TK 过短（6位数字 = 20位有效空间）
├── Just Works 模式 TK=0
├── STK 可被暴力破解
├── 无前向保密
└── 密钥可能在空中传输
```

### 2.3 Secure Connections（LE SC）

```
BLE 4.2 引入的 Secure Connections：

核心改进：
├── 使用 ECDH (P-256) 密钥交换
├── 前向保密（Forward Secrecy）
├── 不再使用 TK/STK
├── 直接生成 LTK
└── 抵抗被动窃听

配对流程：

1. 公钥交换
   ├── 双方生成 ECDH 密钥对 (PKa, SKa) 和 (PKb, SKb)
   └── 交换公钥 PKa 和 PKb

2. DH 密钥计算
   └── DHKey = ECDH(SKa, PKb) = ECDH(SKb, PKa)

3. 认证阶段（根据配对方法）：
   ├── Just Works: 无额外认证
   ├── Numeric Comparison:
   │   ├── 计算 Na, Nb (32位随机数)
   │   ├── 计算确认值
   │   └── 显示 6 位数字供用户确认
   ├── Passkey:
   │   ├── 20 轮交互（每轮1位Passkey）
   │   └── 每轮交换随机数和确认值
   └── OOB:
       ├── 通过带外通道传递
       └── 交换随机数和确认值

4. 确认阶段
   ├── 交换确认值
   └── 使用 DHKey + 随机数计算

5. LTK 生成
   ├── LTK = f5(DHKey, Na, Nb, IOCap_a, IOCap_b)
   ├── MacKey (用于签名)
   └── Session Key Diversifier

安全分析：
├── ECDH-P256 提供 128 位安全强度
├── 前向保密: 即使 LTK 泄露，过去会话安全
├── MITM 保护: 通过用户确认/输入
└── KNOB 攻击仍可降级密钥长度
```

### 2.4 BLE 密钥类型

```
BLE 密钥体系：

1. LTK (Long Term Key)
   ├── 128 位长期加密密钥
   ├── 存储在设备中用于后续连接
   ├── 用于链路层加密
   └── 每次连接生成会话密钥

2. IRK (Identity Resolving Key)
   ├── 16 字节密钥
   ├── 用于生成可解析私有地址（RPA）
   ├── RPA = hash(IRK, random) || random
   ├── 防止设备被追踪
   └── 已配对设备可用 IRK 解析 RPA

3. CSRK (Connection Signature Resolving Key)
   ├── 16 字节密钥
   ├── 用于数据签名
   ├── 签名 = mac(CSRK, data) || counter
   └── 用于未加密连接的完整性保护

4. STK (Short Term Key) - 仅 Legacy
   ├── 临时加密密钥
   ├── 配对后立即使用
   └── 分发 LTK 后被替换

5. Session Key
   ├── 每次连接动态生成
   ├── Session Key = f5(LTK, ...)
   └── 用于当前会话的数据加密

隐私特性：
├── 可解析私有地址（RPA）
│   ├── 每隔一定时间更换地址
│   ├── 格式: hash(IRK, prand) || prand
│   └── 已配对设备可解析身份
├── 不可解析私有地址
│   └── 随机地址，无法解析
└── 公共地址
    └── 固定地址，可被追踪
```

## 3. 经典蓝牙安全

### 3.1 蓝牙认证与加密

```
经典蓝牙安全机制：

1. 认证流程
   ├── 基于共享链路密钥的挑战-响应
   ├── 设备A 发送随机数 AU_RAND_A
   ├── 设备B 计算认证响应:
   │   SRES = E1(LinkKey, AU_RAND_A, COF, 0)
   └── 设备A 验证 SRES

2. 链路密钥类型
   ├── Kinit: 初始化密钥（基于 PIN）
   │   └── Kinit = E22(PIN, PIN_LEN, BD_ADDR, IN_RAND)
   ├── Kunit: 单元密钥（设备自身密钥）
   ├── Kcomb: 组合密钥（两设备共享）
   │   ├── 基于双方随机数和 BD_ADDR
   │   └── 每对设备唯一
   ├── Kmaster: 主密钥
   └── KAB: 临时链路密钥

3. 加密流程
   ├── 加密密钥 Kc = E3(LinkKey, EN_RAND, COF)
   ├── Kc 长度协商 (1-16 字节)
   ├── 密钥流: E0(Kc, clock, BD_ADDR)
   └── E0: 流加密算法

4. 安全模式
   ├── 安全模式1: 无安全
   ├── 安全模式2: 服务级安全
   └── 安全模式4: 服务级安全（SSP）
```

### 3.2 PIN 码破解

```
蓝牙 PIN 码破解：

攻击原理：
├── 配对过程中 PIN 用于生成 Kinit
├── Kinit = E22(PIN, PIN_LEN, BD_ADDR, IN_RAND)
├── 如果捕获配对流量
├── 可以离线暴力破解 PIN
└── 多数设备使用 4 位 PIN（仅 10000 种可能）

攻击工具: Bluetooth Cracker / btcrack

攻击条件：
├── 捕获配对过程的数据包
├── 知道主从设备的 BD_ADDR
├── 需要 Ubertooth 或类似抓包设备
└── PIN 长度越短越容易

防御措施：
├── 使用 8 位以上 PIN
├── 使用 SSP（Secure Simple Pairing）
├── 在私密环境中配对
└── 避免使用默认 PIN（0000/1234）
```

### 3.3 Bluejacking

```
Bluejacking（蓝牙垃圾信息）：

定义：
├── 向蓝牙设备发送未授权的 vCard 消息
├── 利用 OBEX Push 服务
├── 通常无害但令人困扰
└── 不涉及数据窃取

攻击条件：
├── 目标设备蓝牙可见
├── 目标设备启用 OBEX Push
├── 距离 10 米以内
└── 无需配对

攻击流程：
1. 扫描附近蓝牙设备
   hcitool scan

2. 查找 OBEX Push 通道
   sdptool browse <BD_ADDR>
   → 查找 "OBEX Object Push" 服务

3. 发送 vCard
   # 使用 obexftp
   obexftp -b <BD_ADDR> -B <channel> -p message.vcf

4. 消息内容（vCard 格式）
   BEGIN:VCARD
   VERSION:2.1
   N:;Alert;;
   FN:Security Alert
   TEL;CELL:1234567890
   END:VCARD

防御措施：
├── 设置蓝牙不可见（不可发现模式）
├── 关闭 OBEX Push 服务
├── 拒绝未知文件传输请求
└── 不接受未知来源的消息
```

### 3.4 Bluesnarfing

```
Bluesnarfing（蓝牙数据窃取）：

定义：
├── 利用 OBEX Push 漏洞
├── 未经授权访问设备数据
├── 可读取通讯录、日历、短信等
└── 严重侵犯隐私

漏洞原理：
├── OBEX Push 服务设计缺陷
├── 某些实现允许无认证访问
├── 通过特定 OBEX 请求读取文件
└── 影响多种旧版手机

攻击工具：
├── bluesnarfer
├── btscanner
└── 自定义脚本

攻击命令示例：
# 扫描目标
hcitool scan

# 测试 Bluesnarfing
bluesnarfer -b <BD_ADDR> -r phonebook

# 读取日历
bluesnarfer -b <BD_ADDR> -r calendar

防御措施：
├── 更新设备固件
├── 设置蓝牙不可见
├── 关闭不需要的服务
├── 使用新版本蓝牙协议
└── 定期检查设备数据
```

### 3.5 BlueBorne 漏洞

```
BlueBorne（2017年披露）：

漏洞概述：
├── 影响: 蓝牙协议栈实现漏洞
├── 范围: Android/iOS/Windows/Linux
├── 严重性: 严重（CVSS 8+）
├── 无需配对即可利用
└── 可远程代码执行

漏洞链分析：

1. CVE-2017-1000250 (Linux)
   ├── Linux 内核蓝牙 L2CAP 解析漏洞
   ├── 恶意 L2CAP 配置请求导致内存损坏
   └── 可触发内核代码执行

2. CVE-2017-1000251 (Linux BlueZ)
```

### 3.6 KNOB 攻击

```
KNOB Attack (Key Negotiation of Bluetooth, 2019)：

攻击原理：
├── 利用蓝牙密钥长度协商漏洞
├── 攻击者在配对过程中间人介入
├── 强制加密密钥长度 = 1 字节（8位）
├── 1 字节密钥空间仅 256 种
└── 可在几秒内暴力破解

影响范围：
├── 影响所有蓝牙版本
├── 包括 BR/EDR 和 BLE
├── 需要中间人位置
└── 影响 Intel/Apple/Qualcomm 等厂商

攻击条件：
├── 目标设备正在进行配对
├── 攻击者可拦截蓝牙信号
├── 在双方之间中继消息
├── 修改密钥长度字段
└── 无需物理接触

攻击流程：
1. 监听配对过程
2. 截获密钥长度协商消息
3. 修改 Max Encryption Key Size = 1
4. 双方接受降级的密钥长度
5. 捕获加密数据
6. 暴力破解 1 字节密钥（256次）
7. 解密所有后续通信

防御措施：
├── 更新蓝牙固件
├── 强制最小密钥长度为 7 字节
├── 使用 BLE Secure Connections
├── 在安全环境配对
└── 避免公共场所配对
```

### 3.7 BIAS 攻击

```
BIAS (Bluetooth Impersonation AttackS, 2020)：

攻击原理：
├── 蓝牙认证状态机缺陷
├── 利用角色切换机制
├── 绕过双向认证
├── 使用已绑定的链路密钥
└── 伪装成已配对设备

攻击条件：
├── 目标设备之前配对过
├── 知道目标 BD_ADDR
├── 可进行蓝牙通信
└── 支持角色切换

攻击类型：

1. 认证绕过
   ├── 利用 legacy 认证的弱点
   ├── 伪装成已配对设备
   └── 无需知道链路密钥

2. 角色切换攻击
   ├── 利用主从角色切换
   ├── 绕过认证流程
   └── 在认证后切换角色

3. 链路密钥降级
   ├── 将安全链路密钥降级
   └── 使用不安全密钥

防御措施：
├── 更新蓝牙固件
├── 禁用不必要的服务
├── 使用 SSP 配对
├── 限制已知设备连接
└── 监控蓝牙连接日志
```

## 6. Zigbee 安全

### 6.1 Zigbee 安全架构

```
Zigbee 安全架构：

安全层级：
├── MAC 层安全（IEEE 802.15.4）
│   ├── AES-128 对称加密
│   ├── CCM* 操作模式
│   ├── 帧计数器防重放
│   └── 可选安全等级
├── 网络层安全（NWK）
│   ├── 网络密钥（Network Key）
│   ├── 所有设备共享
│   ├── 用于网络层帧加密
│   └── 信任中心分发
├── 应用层安全（APS）
│   ├── 链接密钥（Link Key）
│   ├── 设备间专用密钥
│   ├── 应用层帧加密
│   └── 端到端安全
└── 信任中心（Trust Center）
    ├── 密钥管理
    ├── 设备入网控制
    └── 密钥更新

Zigbee 密钥体系：

1. 网络密钥（Network Key）
   ├── 128 位 AES 密钥
   ├── 网络中所有设备共享
   ├── 用于网络层加密
   ├── 定期更新
   └── 信任中心生成和分发

2. 链接密钥（Link Key）
   ├── 128 位 AES 密钥
   ├── 设备与信任中心之间
   ├── 用于 APS 层加密
   ├── 全局链接密钥（默认）
   └── 个体链接密钥（推荐）

3. 应用密钥（Application Key）
   ├── 应用层端到端密钥
   ├── 两个应用之间共享
   └── 通过 APS 传输

4. 安装码（Install Code）
   ├── 用于设备入网
   ├── 防止伪造设备加入
   ├── 厂商预置或现场输入
   └── 用于派生链接密钥
```

### 6.2 Zigbee 安全流程

```
Zigbee 设备入网安全流程：

1. 设备发现
   ├── 新设备发送 Beacon Request
   ├── 路由器/协调器响应 Beacon
   └── 设备选择网络加入

2. 关联请求
   ├── 新设备发送 Association Request
   ├── 包含设备能力信息
   └── 协调器/路由器决定是否允许

3. 密钥协商
   ├── 方式A: 预配置链接密钥
   │   ├── 设备出厂预置
   │   ├── 安装码派生
   │   └── 直接使用预共享密钥
   ├── 方式B: 信任中心分发
   │   ├── 信任中心生成密钥
   │   ├── 通过 APS Transport Key 命令分发
   │   └── 使用链接密钥加密传输

4. 网络密钥分发
   ├── 信任中心发送网络密钥
   ├── 使用链接密钥加密
   ├── 设备存储网络密钥
   └── 开始加密通信

5. 密钥更新
   ├── 信任中心定期更新网络密钥
   ├── 帧计数器防止重放
   └── 平滑过渡到新密钥

安全等级：
├── 无安全 (None): 无加密无认证
├── 认证 (MIC-32/64/128): 仅完整性
├── 加密 (ENC-MIC-32/64/128): 加密+完整性
```

### 7.4 BLE 安全审计报告

```python
#!/usr/bin/env python3
"""
BLE 安全审计报告生成器
自动化审计 BLE 设备安全配置
"""

from bluepy.btle import Peripheral, Scanner, UUID
import json
import datetime

class BLESecurityAuditor:
    """BLE 设备安全审计工具"""
    
    def __init__(self, target_addr):
        self.target_addr = target_addr
        self.device = None
        self.findings = []
        self.services = []
    
    def scan_device(self):
        """扫描目标设备"""
        scanner = Scanner()
        devices = scanner.scan(10.0)
        
        for dev in devices:
            if dev.addr == self.target_addr:
                return {
                    'address': dev.addr,
                    'rssi': dev.rssi,
                    'name': dev.getValueText(9),  # Complete Local Name
                    'tx_power': dev.getValueText(10),
                }
        return None
    
    def connect_and_enum(self):
        """连接并枚举设备"""
        try:
            self.device = Peripheral(self.target_addr)
            services = self.device.getServices()
            
            for svc in services:
                svc_info = {
                    'uuid': str(svc.uuid),
                    'characteristics': []
                }
                
                for char in svc.getCharacteristics():
                    char_info = {
                        'uuid': str(char.uuid),
                        'handle': char.getHandle(),
                        'properties': self._get_props(char),
                        'value': None,
                        'writable_no_auth': False,
                    }
                    
                    # 尝试读取
                    if 'READ' in char_info['properties']:
                        try:
                            val = char.read()
                            char_info['value'] = val.hex()
                        except Exception as e:
                            char_info['read_error'] = str(e)
                    
                    # 检查是否需要认证
                    if 'WRITE' in char_info['properties']:
                        try:
                            descs = self.device.getDescriptors(
                                char.getHandle(),
                                char.getHandle() + 1
                            )
                            for d in descs:
                                if d.uuid == 0x2902:
                                    char_info['ccc_handle'] = d.handle
                        except:
                            pass
                    
                    svc_info['characteristics'].append(char_info)
                
                self.services.append(svc_info)
            
            return True
        except Exception as e:
            self.findings.append({
                'severity': 'ERROR',
                'finding': f'连接失败: {str(e)}'
            })
            return False
    
    def _get_props(self, char):
        """获取特征属性"""
        props = []
        val = char.properties
        if val & 0x01: props.append('BROADCAST')
        if val & 0x02: props.append('READ')
        if val & 0x04: props.append('WRITE_NO_RESP')
        if val & 0x08: props.append('WRITE')
        if val & 0x10: props.append('NOTIFY')
        if val & 0x20: props.append('INDICATE')
        if val & 0x40: props.append('SIGNED_WRITE')
        if val & 0x80: props.append('EXTENDED')
        return props
    
    def check_security(self):
        """检查安全问题"""
        for svc in self.services:
            for char in svc['characteristics']:
                # 检查无认证写入
                if 'WRITE' in char['properties']:
                    # 尝试无认证写入
                    if not self._check_write_auth(char):
                        self.findings.append({
                            'severity': 'HIGH',
                            'finding': f"可无认证写入: {char['uuid']} "
                                      f"(handle 0x{char['handle']:04x})"
                        })
                
                # 检查敏感数据暴露
                if char['value'] and self._is_sensitive(char):
                    self.findings.append({
                        'severity': 'MEDIUM',
                        'finding': f"敏感数据可读: {char['uuid']} "
                                  f"value={char['value']}"
                    })
    
    def _check_write_auth(self, char):
        """检查写入是否需要认证"""
        # 在实际实现中需要检查描述符
        return False  # 简化版
    
    def _is_sensitive(self, char):
        """判断是否为敏感特征"""
        sensitive_uuids = [
            '2a00',  # Device Name
            '2a01',  # Appearance
            '2a04',  # Connection Parameters
            '2a25',  # Serial Number
            '2a27',  # Firmware Revision
        ]
        uuid_short = char['uuid'].split('-')[0][-4:]
        return uuid_short.lower() in sensitive_uuids
    
    def generate_report(self):
        """生成审计报告"""
        report = {
            'target': self.target_addr,
            'timestamp': datetime.datetime.now().isoformat(),
            'services_enumerated': len(self.services),
            'findings': self.findings,
            'services': self.services,
        }
        return json.dumps(report, indent=2, ensure_ascii=False)


# 使用示例
if __name__ == '__main__':
    auditor = BLESecurityAuditor('aa:bb:cc:dd:ee:ff')
    
    print("[*] 扫描设备...")
    dev_info = auditor.scan_device()
    if dev_info:
        print(f"[+] 发现设备: {dev_info['name']}")
    
    print("[*] 枚举服务和特征...")
    if auditor.connect_and_enum():
        print("[*] 检查安全问题...")
        auditor.check_security()
        
        print("\n=== 审计报告 ===")
        print(auditor.generate_report())
```
