# 测试范围界定与授权

### 3.1 测试范围确定方法

准确界定测试范围是无线渗透测试成功的关键，也是控制法律风险的核心手段。范围界定不清是导致测试事故和法律纠纷的最常见原因。

#### 3.1.1 物理范围界定

物理范围界定明确测试人员可以在哪些区域内进行无线测试活动。

**物理范围要素：**

1. **建筑物范围**
   - 具体哪些建筑物在测试范围内
   - 建筑物内的哪些楼层和区域
   - 是否包括地下停车场、天台等区域

2. **外部范围**
   - 是否允许在建筑物外部进行测试
   - 允许的最远距离
   - 是否包括周边公共区域

3. **物理访问权限**
   - 测试人员是否需要进入建筑物
   - 需要哪些区域的门禁权限
   - 是否需要陪同人员

**物理范围界定方法：**
- 使用建筑物平面图标注测试区域
- 使用GPS坐标标注外部测试范围
- 现场踏勘确认边界
- 签署物理访问授权书

#### 3.1.2 频率范围界定

无线测试涉及不同的频段和信道，需要明确测试的频率范围。

**频率范围要素：**

1. **WiFi频段**
   - 2.4GHz频段（中国：1-13信道）
   - 5GHz频段（中国：36-64、149-165信道）
   - 6GHz频段（WiFi 6E，如适用）

2. **其他无线协议**
   - 蓝牙（2.4GHz ISM频段）
   - Zigbee（2.4GHz，不同信道划分）
   - RFID/NFC（13.56MHz、UHF等）

3. **发射功率限制**
   - 测试设备的最大发射功率
   - 是否需要遵守无线电管理规定
   - 避免对合法用户造成干扰

#### 3.1.3 设备清单管理

建立详细的测试目标设备清单，确保测试活动只针对授权设备。

**设备清单应包含：**

| 设备类型 | 标识信息 | 备注 |
|---------|---------|------|
| 无线AP | BSSID、IP地址、位置 | 确认是否在测试范围内 |
| 无线控制器 | 型号、IP地址、管理地址 | 后渗透测试目标 |
| 认证服务器 | RADIUS服务器地址 | 认证攻击目标 |
| 客户端设备 | MAC地址范围、设备类型 | 用于客户端攻击测试 |
| IoT设备 | 设备类型、通信协议 | IoT安全测试目标 |
| 蓝牙设备 | BD_ADDR、设备名称 | 蓝牙测试目标 |

**设备清单确认流程：**
1. 客户提供初步设备清单
2. 侦察阶段验证和补充清单
3. 与客户确认最终清单
4. 超出清单的设备需额外授权

### 3.2 授权书与法律文件模板

正式的无线渗透测试必须签署书面授权文件，明确双方的权利和义务。

#### 3.2.1 授权书核心要素

一份完整的渗透测试授权书应包含以下内容：

1. **双方信息**
   - 委托方（客户）的公司名称、地址、联系方式
   - 受托方（测试方）的公司名称、地址、资质信息
   - 双方授权代表的姓名、职务、联系方式

2. **测试目的**
   - 明确说明测试的目的和预期成果
   - 说明测试是为了提升安全防护能力

3. **测试范围**
   - 详细列出测试的目标系统和设备
   - 明确物理范围和时间范围
   - 列出允许的测试方法和禁止的测试方法

4. **权利与义务**
   - 委托方的权利和义务
   - 受托方的权利和义务
   - 保密义务

5. **责任条款**
   - 免责声明（在授权范围内的测试活动）
   - 赔偿条款（超出授权范围造成的损失）
   - 保密责任

6. **生效与终止**
   - 授权的生效日期和终止日期
   - 提前终止的条件
   - 争议解决方式

5.3 测试完成后，乙方应妥善处理所有测试数据

### 3.3 风险告知与应急预案

#### 3.3.1 风险告知

在测试开始前，测试方应向客户充分告知测试可能带来的风险：

1. **业务中断风险**
   - 某些测试可能导致AP或客户端断连
   - 后渗透测试可能影响内网系统可用性
   - 建议在业务低谷期进行测试

2. **数据安全风险**
   - 测试过程中可能接触到敏感数据
   - 已采取的保密措施说明
   - 数据处理和销毁方式

3. **设备损坏风险**
   - 极端情况下可能导致设备配置损坏
   - 已准备的备份和恢复方案

4. **第三方影响风险**
   - 无线信号可能影响周边设备
   - 控制措施和应急预案

#### 3.3.2 应急预案

制定详细的应急预案，确保在发生意外情况时能够快速响应：

**应急响应流程：**

```
发现异常情况
    │
    ├─→ 立即停止相关测试活动
    │
    ├─→ 评估影响范围和严重程度
    │
    ├─→ 通知客户紧急联系人
    │   （15分钟内）
    │
    ├─→ 执行恢复操作
    │   - 恢复配置
    │   - 重启服务
    │   - 切换备用系统
    │
    ├─→ 监控恢复状态
    │
    └─→ 事后分析与报告
```

**应急联系清单：**

| 角色 | 姓名 | 电话 | 邮箱 | 职责 |
|------|------|------|------|------|
| 客户项目负责人 | | | | 总体协调 |
| 客户网络管理员 | | | | 网络故障处理 |
| 客户系统管理员 | | | | 系统故障处理 |
| 测试项目负责人 | | | | 测试团队协调 |
| 测试技术负责人 | | | | 技术问题处理 |

### 3.4 时间窗口与干扰控制

#### 3.4.1 时间窗口选择

无线渗透测试的时间窗口选择非常重要，需要平衡测试效果和业务影响：

1. **非工作时间测试**
   - 优点：对业务影响最小
   - 缺点：客户端数量少，某些攻击无法充分测试
   - 适用场景：高风险攻击、可能影响业务的测试

2. **工作时间测试**
   - 优点：客户端活跃，测试更接近真实场景
   - 缺点：对业务影响较大，容易被员工察觉
   - 适用场景：社会工程测试、低风险侦察

3. **混合时间安排**
   - 侦察阶段：工作时间进行（客户端多，信息全）
   - 攻击阶段：非工作时间进行（降低业务影响）
   - 后渗透阶段：根据具体情况安排

#### 3.4.2 干扰控制措施

为了最大程度减少测试对合法用户的干扰，应采取以下措施：

1. **功率控制**
   - 使用最低必要的发射功率
   - 优先使用定向天线，减少信号泄露
   - 避免在人员密集区域使用大功率设备

2. **频率控制**
   - 避开公共安全、应急通信等专用频段
   - 选择相对空闲的信道进行测试
   - 监控信道使用情况，及时调整

3. **流量控制**
   - 限制数据包注入的速率
   - 避免大规模的洪泛攻击
   - 控制Deauth等攻击的频率和范围

4. **实时监控**
   - 持续监控目标网络的运行状态
   - 设置异常告警阈值
   - 发现异常立即暂停测试

### 3.5 紧急联系与升级机制

建立清晰的沟通和升级机制，确保测试过程中出现问题时能够及时处理。

#### 3.5.1 沟通渠道

1. **日常沟通**
   - 项目微信群/即时通讯群
   - 每日进度汇报邮件
   - 定期电话会议

2. **紧急沟通**
   - 24小时紧急联系电话
   - 短信通知
   - 逐级上报机制

#### 3.5.2 升级机制

```
Level 1 - 一般问题
├── 测试人员自行处理
├── 记录在案
└── 日报中说明

Level 2 - 重要问题
├── 测试技术负责人处理
├── 项目负责人知晓
└── 客户技术联系人知晓

Level 3 - 严重问题
├── 项目负责人协调处理
├── 立即通知客户项目负责人
├── 暂停相关测试活动
└── 2小时内提交书面说明

Level 4 - 紧急事故
├── 立即启动应急预案
├── 双方高层介入
├── 全面暂停测试活动
└── 24小时内提交事故报告
```

**升级判定标准：**
- Level 1：不影响测试进度和业务运行的技术问题
- Level 2：可能影响测试进度，但不影响业务运行的问题
- Level 3：可能对业务造成轻微影响，或发现高危漏洞
- Level 4：已经对业务造成实际影响，或发现紧急安全事件
