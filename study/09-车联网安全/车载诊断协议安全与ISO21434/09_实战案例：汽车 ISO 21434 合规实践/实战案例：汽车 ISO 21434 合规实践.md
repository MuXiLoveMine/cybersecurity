# 实战案例：汽车 ISO 21434 合规实践

### 9.1 案例背景

某车企开发新款智能网联汽车，需要按照 ISO 21434 完成全流程网络安全合规。以下展示关键阶段的实践。

### 9.2 概念阶段：TARA 实践

以"远程无钥匙进入系统（RKES）"为例进行 TARA：

```
TARA 实施步骤：

步骤 1：资产识别
  资产：RKES 控制模块
  接口：BLE 5.0, UWB, NFC
  数据：钥匙认证令牌、车辆位置

步骤 2：损害场景
  DS-RKE-01: 攻击者远程解锁车辆并启动引擎 → 车辆被盗
  DS-RKE-02: 钥匙认证令牌泄露 → 隐私泄露
  Impact: 安全=Severe, 财产=High

步骤 3：威胁场景
  TS-RKE-01: BLE 中继攻击放大钥匙信号
  TS-RKE-02: 钥匙固件逆向提取密钥
  TS-RKE-03: NFC 通信劫持

步骤 4：攻击可行性评估
  TS-RKE-01: 运行时间=低(2), 专业知识=高(2), 窗口=极高(3) → 高可行性
  TS-RKE-02: 运行时间=中(1), 专业知识=中(1), 窗口=高(2) → 中可行性
  TS-RKE-03: 运行时间=中(1), 专业知识=高(2), 窗口=极高(3) → 高可行性

步骤 5：风险评级
  TS-RKE-01: Impact(5) × Feasibility(2) = 10 → 极高风险
  TS-RKE-02: Impact(3) × Feasibility(1) = 3  → 中等风险
  TS-RKE-03: Impact(4) × Feasibility(2) = 8  → 高风险

步骤 6：安全目标
  CSG-RKE-01: RKES 必须使用距离绑定（UWB 测距）防止中继攻击
  CSG-RKE-02: 钥匙固件必须使用安全存储保护密钥
  CSG-RKE-03: NFC 通信必须双向认证
```

### 9.3 开发阶段：安全需求与实现

根据安全目标制定具体安全需求并实现：

```
安全目标 → 安全需求 → 实现措施

CSG-RKE-01 (防中继攻击)
  ├── CSR-001: BLE 认证必须配合 UWB 精确测距，距离 > 2m 拒绝解锁
  ├── CSR-002: BLE 认证响应必须包含挑战值，超时 < 100ms 拒绝
  └── CSR-003: 系统必须检测中继攻击模式（延迟异常检测）

  实现措施：
  ├── UWB 双向测距 (TWR) 模块集成
  ├── BLE 认证协议升级为挑战-响应 + 时间戳
  └── 延迟检测：BLE 响应延迟 > 50ms 触发告警
```

```c
// BLE + UWB 防中继认证实现
typedef struct {
    uint8_t  challenge[16];   // 随机挑战值
    uint32_t timestamp;        // 时间戳
    uint8_t  signature[32];    // HMAC-SHA256 签名
} rke_auth_request_t;

int verify_rke_authentication(rke_auth_request_t *req, uint8_t *ble_rssi,
                               float uwb_distance) {
    // 1. UWB 距离验证（防中继核心）
    if (uwb_distance > MAX_UNLOCK_DISTANCE) {  // MAX = 2.0 米
        log_security_event("RKE: distance too far (%.2fm)", uwb_distance);
        return AUTH_REJECTED_DISTANCE;
    }

    // 2. 时间戳验证（防重放）
    uint32_t current_time = get_secure_timestamp();
    if (abs(current_time - req->timestamp) > MAX_AUTH_DELAY) {  // MAX = 100ms
        log_security_event("RKE: timestamp delay exceeded");
        return AUTH_REJECTED_TIMEOUT;
    }

    // 3. 签名验证
    uint8_t computed_sig[32];
    hmac_sha256(req->challenge, 16, stored_secret, SECRET_LEN, computed_sig);
    if (memcmp(computed_sig, req->signature, 32) != 0) {
        log_security_event("RKE: signature verification failed");
        return AUTH_REJECTED_SIGNATURE;
    }

    // 4. BLE RSSI 一致性检查（辅助验证）
    if (*ble_rssi < MIN_RSSI_THRESHOLD) {
        log_security_event("RKE: RSSI too low, possible relay");
        return AUTH_REJECTED_RSSI;
    }

    return AUTH_SUCCESS;
}
```

### 9.4 验证阶段：渗透测试

针对 RKES 系统执行渗透测试，验证安全需求有效性：

```
渗透测试计划与执行：

测试项 1：BLE 中继攻击测试
  方法：使用两个 SDR 设备，一个靠近钥匙，一个靠近车辆
  预期：UWB 测距检测到距离异常，拒绝解锁
  结果：PASS ✓（UWT 距离 15m > 2m 阈值，拒绝解锁）

测试项 2：BLE 认证重放攻击
  方法：捕获认证报文，延迟 200ms 后重放
  预期：时间戳验证失败，拒绝认证
  结果：PASS ✓（延迟 200ms > 100ms 阈值，拒绝认证）

测试项 3：SecurityAccess 暴力破解
  方法：发送 100 次 27 02 随机密钥
  预期：3 次失败后锁定
  结果：PASS ✓（第 4 次返回 NRC 0x36，锁定 2 小时）

测试项 4：固件刷写签名绕过
  方法：构造篡改固件，跳过完整性校验
  预期：RSA 签名验证失败，拒绝刷写
  结果：PASS ✓（签名验证失败，返回 NRC 0x71）

测试项 5：UDS 协议模糊测试
  方法：对 0x22/0x2E/0x31 服务发送畸形 Payload
  预期：ECU 返回 NRC 或忽略，不崩溃
  结果：FAIL ✗（0x31 服务畸形 Payload 导致 ECU 复位）
  修复：增加 Payload 长度和内容校验
  复测：PASS ✓（修复后返回 NRC 0x13）
```

### 9.5 合规文档体系

ISO 21434 要求建立完整的文档体系以证明合规：

```
合规文档清单：

概念阶段：
  ├── 网络安全管理计划 (CSMP)
  ├── TARA 报告
  ├── 网络安全目标 (CSG) 清单
  └── 网络安全需求规范 (CSR)

开发阶段：
  ├── 网络安全架构设计文档
  ├── 安全设计评审记录
  ├── 代码安全分析报告 (SAST)
  ├── 软件组成分析报告 (SCA)
  └── 单元测试报告

验证阶段：
  ├── 渗透测试报告
  ├── 模糊测试报告
  ├── 网络安全验证报告
  └── 网络安全声明 (Cybersecurity Claim)

运维阶段：
  ├── 漏洞管理流程
  ├── 事件响应预案
  ├── OTA 安全更新流程
  └── 持续监控方案
```
