# ISO 21434 标准详解

### 7.1 标准概述

ISO/SAE 21434《道路车辆 网络安全工程》是 2021 年正式发布的国际标准，为道路车辆整个生命周期的网络安全工程提供系统化框架。该标准覆盖从概念阶段到生产、运维和退役的全流程。

**标准结构：**

```
ISO 21434 标准章节结构：

第 1-7 章：通用要求与管理框架
  ├── 第 1 章: 范围
  ├── 第 2 章: 引用文件
  ├── 第 3 章: 术语和定义
  ├── 第 4 章: 概述（结构说明）
  ├── 第 5 章: 网络安全管理（CSMS）     ← 组织级管理框架
  ├── 第 6 章: 项目依赖的网络安全管理   ← 项目级管理
  └── 第 7 章: 分布式网络安全活动       ← 供应链协同

第 8-10 章：核心工程流程
  ├── 第 8 章: 持续的网络安全活动       ← 持续监控
  ├── 第 9 章: 概念阶段的网络安全工程   ← 需求与目标定义
  └── 第 10 章: 产品开发阶段的网络安全工程

第 11-14 章：生产、运维与退役
  ├── 第 11 章: 网络安全验证             ← 系统级验证
  ├── 第 12 章: 生产                     ← 生产环节安全
  ├── 第 13 章: 运维                     ← 运行维护安全
  └── 第 14 章: 退役                     ← 退役安全

附录
  ├── 附录 A: 信息安全评估
  └── 附录 B: TARA 示例
```

### 7.2 网络安全管理（CSMS）

CSMS（Cybersecurity Management System，网络安全管理体系）是组织级的网络安全治理框架，对应 ISO 21434 第 5 章。

**CSMS 核心要素：**

```
CSMS 管理框架：

┌─────────────────────────────────────────────┐
│              网络安全治理 (Governance)        │
│  - 网络安全政策与策略                          │
│  - 管理层承诺与资源分配                        │
│  - 角色与职责定义                              │
│  - 网络安全文化培养                            │
├─────────────────────────────────────────────┤
│              资质与能力 (Competence)           │
│  - 网络安全人员培训                            │
│  - 供应商网络安全能力评估                      │
│  - 安全专家认证要求                            │
├─────────────────────────────────────────────┤
│           持续改进 (Continuous Improvement)    │
│  - 网络安全绩效指标 (KPI)                      │
│  - 管理评审                                    │
│  - 经验教训库                                  │
│  - 审计与合规检查                              │
├─────────────────────────────────────────────┤
│         工具与资源 (Tooling & Resources)       │
│  - 安全需求管理工具                            │
│  - 渗透测试环境                                │
│  - 漏洞数据库                                  │
│  - 源代码安全分析工具                          │
└─────────────────────────────────────────────┘
```

**CSMS 关键活动时间轴：**

```
组织级活动（持续）：
  ┌─────────────────────────────────────────────────────────────────┐
  │  制定安全政策 → 分配资源 → 培训人员 → 监控绩效 → 持续改进         │
  └─────────────────────────────────────────────────────────────────┘

项目级活动（按车型项目）：
  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ 概念阶段  │──▶│ 开发阶段  │──▶│ 生产阶段  │──▶│ 运维阶段  │
  │ TARA     │   │ 安全设计  │   │ 生产线   │   │ OTA/事件  │
  │ 需求定义  │   │ 验证确认  │   │ 配置管理  │   │ 响应     │
  └──────────┘   └──────────┘   └──────────┘   └──────────┘
```

### 7.3 网络安全风险评估（TARA）

TARA（Threat Analysis and Risk Assessment，威胁分析与风险评估）是 ISO 21434 第 9 章的核心活动，用于系统化识别和评估车辆网络安全风险。

**TARA 方法论流程：**

```
TARA 完整流程：

1. 资产识别 (Asset Identification)
   ├── 功能资产：车辆功能（如远程解锁、制动控制）
   ├── 信息资产：敏感数据（VIN、位置、用户隐私）
   └── 物理资产：ECU、传感器、通信接口

2. 损害场景识别 (Damage Scenario)
   ├── 财产损失：车辆被盗、损坏
   ├── 人身伤害：碰撞、失控
   ├── 隐私泄露：用户数据暴露
   └── 运营影响：车队瘫痪、品牌损害

3. 威胁场景识别 (Threat Scenario)
   ├── 基于攻击面分析：OBD、WiFi、蓝牙、蜂窝、CAN
   ├── 基于攻击树推演：从入口点到损害场景的路径
   └── 基于已知漏洞库：CVE、行业漏洞情报

4. 攻击可行性评估 (Attack Feasibility Rating)
   ├── 运行时间 (Elapsed Time)：攻击耗时
   ├── 专业知识 (Expertise)：所需技能
   ├── 设计知识 (Knowledge of Design)：系统内部信息
   ├── 计算资源 (Computing Resources)
   └── 窗口机会 (Window of Opportunity)：物理/逻辑可达性

5. 风险评估 (Risk Assessment)
   Risk = Impact × Attack Feasibility
```

**攻击可行性评级矩阵：**

```
攻击可行性评估（ISO 21434 Clause 15）：

维度          │ 低 (0)        │ 中 (1)         │ 高 (2)          │ 极高 (3)
─────────────┼───────────────┼────────────────┼─────────────────┼──────────
运行时间      │ > 1个月       │ 1周-1月        │ 1天-1周         │ < 1天
专业知识      │ 多领域专家     │ 精通单一领域    │ 熟练技术人员     │ 业余水平
设计知识      │ 需逆向工程     │ 有部分文档      │ 有公开文档      │ 完全公开
计算资源      │ 专用设备       │ 高性能工作站    │ 普通PC         │ 智能手机
机会窗口      │ < 1分钟/天     │ 10分钟/天      │ 1小时/天        │ 随时
```

**TARA 输出示例：**

```yaml
# TARA 评估结果示例
threat_scenario:
  id: TS-001
  name: "通过 OBD 接口绕过 SecurityAccess 刷写恶意固件"
  
  asset:
    type: "ECU - 动力控制模块 (PCM)"
    interfaces: ["OBD-II", "CAN-B"]
  
  damage_scenario:
    id: DS-001
    description: "攻击者通过恶意固件控制发动机输出，导致车辆异常加速"
    impact:
      safety: "Severe"      # 严重人身伤害
      financial: "High"     # 召回成本
      operational: "High"   # 车辆功能丧失
      privacy: "None"
    impact_rating: 4        # 1-5 级
  
  attack_feasibility:
    elapsed_time: 2         # 1天-1周 → 中
    expertise: 2            # 熟练技术人员 → 高
    knowledge_of_design: 1  # 有部分文档 → 中
    it_resources: 1         # 普通PC → 高
    window_of_opportunity: 3  # 随时（OBD 物理可达）→ 极高
    feasibility_rating: 2   # 综合评级 = 高
  
  risk:
    value: 8                # Impact(4) × Feasibility(2) = 8
    level: "High"           # 高风险
    treatment: "Risk Reduction"
    
  security_measures:
    - "SecurityAccess 使用 AES-CMAC 算法"
    - "固件数字签名验证 (RSA-2048)"
    - "OBD 接口速率限制"
    - "网关防火墙规则：禁止 OBD → PCM 直接刷写"
    - "IDS 规则：检测 SecurityAccess 暴力破解"
```

### 7.4 网络安全目标与声明

**网络安全目标（Cybersecurity Goals）：**

在 TARA 完成后，针对每个需要处置的风险制定网络安全目标（CSG）。网络安全目标是高层安全需求，后续转化为具体的网络安全需求（CSR）。

```
风险 → 目标 → 需求的转化链：

TARA 风险 TS-001 (高风险)
  └── 网络安全目标 CSG-001:
      "PCM 固件刷写必须经过认证且固件必须经过完整性验证"
          └── 网络安全需求 CSR-001:
              "SecurityAccess 必须使用 HMAC-SHA256，种子长度 ≥ 8 字节"
          └── 网络安全需求 CSR-002:
              "固件刷写前必须验证 RSA-2048 数字签名"
          └── 网络安全需求 CSR-003:
              "SecurityAccess 失败 3 次后锁定 2 小时"
          └── 网络安全需求 CSR-004:
              "IDS 必须检测 SecurityAccess 暴力破解行为"
```

**网络安全声明（Cybersecurity Claims）：**

网络安全声明是在开发完成后对安全目标的达成情况的确认声明，证明安全需求已实现并验证通过。

```yaml
# 网络安全声明示例
cybersecurity_claim:
  project: "Vehicle_X_2026"
  claim_id: CC-001
  related_goal: CSG-001
  statement: >
    "PCM 固件刷写认证和完整性验证机制已实现并通过验证。
    SecurityAccess 使用 HMAC-SHA256，种子长度 8 字节。
    固件验证使用 RSA-2048 签名。
    IDS 规则 FW-004 已部署并测试通过。"
  
  verification_evidence:
    - document: "TARA_Report_V2.docx"
    - document: "Security_Requirements_Spec.xlsx"
    - document: "Penetration_Test_Report.pdf"
    - test_report: "IDS_Rule_FW004_Test_Results.txt"
    - code_review: "PCM_SecurityAccess_Module_Review.md"
  
  status: "Verified"
  approver: "Cybersecurity Manager"
  date: "2026-09-01"
```

### 7.5 网络安全验证

ISO 21434 第 11 章要求对网络安全措施进行系统验证，确保安全需求在实际系统中有效：

```
网络安全验证层次：

1. 需求验证 (Requirements Review)
   └── 检查 CSR 是否可测试、无歧义、可追溯

2. 设计验证 (Design Review)
   └── 安全架构评审、威胁模型更新

3. 实现验证 (Implementation Verification)
   ├── 静态分析 (SAST)
   │   └── MISRA C / CERT C / CWE 规则集
   ├── 软件组成分析 (SCA)
   │   └── 第三方组件漏洞扫描
   └── 代码审查 (Code Review)

4. 系统验证 (System Testing)
   ├── 渗透测试 (Penetration Testing)
   │   └── 模拟攻击者视角的实际攻击
   ├── 模糊测试 (Fuzz Testing)
   │   └── UDS/DoIP/SOME-IP 协议 Fuzz
   └── 安全功能测试
       └── 验证安全需求逐条实现

5. 车辆级验证 (Vehicle-level Testing)
   └── 整车安全测试场验证
```

### 7.6 持续运维与事件响应

ISO 21434 第 8 章和第 13 章规定了车辆运行期间的持续网络安全活动：

```
持续网络安全活动闭环：

┌──────────────────────────────────────────────┐
│              车辆运行期间 (In-Service)         │
├──────────────────────────────────────────────┤
│                                              │
│  1. 持续监控 (Continuous Monitoring)          │
│     ├── IDS/IPS 事件监控                      │
│     ├── 车辆异常行为上报                       │
│     └── 第三方漏洞情报收集                     │
│                                              │
│  2. 漏洞管理 (Vulnerability Management)       │
│     ├── 漏洞报告接收与分类                     │
│     ├── CVSS 评分与优先级排序                  │
│     └── 补丁开发与 OTA 分发                    │
│                                              │
│  3. 事件响应 (Incident Response)              │
│     ├── 检测 → 分析 → 遏制 → 消除 → 恢复       │
│     ├── 影响评估与监管报告                      │
│     └── 根因分析 (RCA)                         │
│                                              │
│  4. 安全更新 (Security Updates)               │
│     ├── OTA 固件更新                           │
│     ├── 安全配置更新                           │
│     └── IDS 规则更新                           │
│                                              │
└──────────────────────────────────────────────┘
```

**事件响应流程示例：**

```python
# 车载安全事件响应流程
class VehicleSecurityIncidentResponse:
    def __init__(self):
        self.severity_matrix = {
            "CRITICAL": {"sla_hours": 1,  "actions": ["isolate", "patch", "notify_regulator"]},
            "HIGH":     {"sla_hours": 24, "actions": ["patch", "notify_oem"]},
            "MEDIUM":   {"sla_hours": 72, "actions": ["patch"]},
            "LOW":      {"sla_hours": 168,"actions": ["monitor"]}
        }

    def handle_incident(self, incident):
        severity = self.classify_severity(incident)
        response = self.severity_matrix[severity]

        # 1. 检测与确认
        self.log_detection(incident)

        # 2. 分析与分类
        self.analyze_incident(incident)

        # 3. 遏制
        if severity in ["CRITICAL", "HIGH"]:
            self.contain_incident(incident)
            # 例如：远程禁用受影响功能、推送紧急配置

        # 4. 根因分析
        root_cause = self.root_cause_analysis(incident)

        # 5. 修复
        patch = self.develop_patch(root_cause)
        self.deploy_ota_update(patch)

        # 6. 通知
        if severity == "CRITICAL":
            self.notify_regulator(incident, patch)
        self.notify_customers(incident, patch)

        # 7. 经验总结
        self.update_threat_intelligence(incident)
        self.update_tara(incident)
```
