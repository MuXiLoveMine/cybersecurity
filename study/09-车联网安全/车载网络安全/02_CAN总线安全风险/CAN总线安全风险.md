# CAN总线安全风险

### 2.1 CAN协议设计缺陷

CAN协议设计于1980年代，主要考虑功能和可靠性，未考虑安全问题。

#### 2.1.1 缺乏认证机制

**问题：** CAN报文中没有发送者身份标识，接收节点无法验证报文是否来自合法节点。

**后果：** 攻击者只要接入总线，就可以伪造任何节点发出的报文。

```
正常情况:  BCM发送→ [ID=0x300, 数据: 解锁指令] → 车门ECU执行
攻击情况:  攻击者→ [ID=0x300, 数据: 解锁指令] → 车门ECU执行（无法区分）
```

#### 2.1.2 缺乏加密机制

**问题：** CAN报文以明文传输，没有加密保护。

**后果：** 攻击者接入总线后可以嗅探所有通信内容，获取敏感信息。

```
总线上的报文都是明文:
  ID=0x100: [转速数据]  ← 直接可读
  ID=0x300: [门锁指令]  ← 直接可读
  ID=0x500: [定位数据]  ← 直接可读
```

#### 2.1.3 广播通信模式

**问题：** 所有节点都能收到所有报文，信息泄露面大。

**后果：** 一个节点被攻破，就能监听所有总线通信。

#### 2.1.4 优先级仲裁可被利用

**问题：** 高优先级ID可以抢占总线，攻击者可利用高优先级ID进行拒绝服务攻击。

**后果：** 持续发送高优先级（ID值小）的报文可以独占总线。

### 2.2 CAN总线攻击分类

#### 2.2.1 嗅探攻击（Eavesdropping）

**原理：** 攻击者接入CAN总线，被动监听所有报文。

**目的：**
- 了解车辆通信模式
- 获取敏感数据（车速、位置、状态）
- 分析报文格式，为后续攻击做准备

**工具：**
- CAN适配器 + can-utils / CANoe / Wireshark
- OBD-II接口接入

**检测难度：** 极难（被动监听不影响总线正常通信）

#### 2.2.2 重放攻击（Replay Attack）

**原理：** 先录制正常的CAN报文，再在合适时机重新发送。

**攻击场景示例：**

```
① 录制：攻击者通过OBD接入，录制"解锁车门"的CAN报文序列
② 等待：车主锁车离开
③ 重放：攻击者重新发送录制的解锁报文，车门打开
```

**典型目标：**
- 车门解锁/上锁
- 后备箱开启
- 车窗升降
- 车辆启动

**防御难点：** 重放的报文是完全合法的，接收方无法区分

#### 2.2.3 注入攻击（Injection Attack）

**原理：** 攻击者主动向总线发送伪造的CAN报文，欺骗其他ECU执行操作。

**攻击场景示例：**

```
① 攻击者接入CAN总线
② 伪造刹车控制报文 ID=0x200, 数据=[刹车指令]
③ 刹车ECU接收到报文，执行刹车动作
```

**与重放攻击的区别：**
- 重放攻击：发送之前录制的真实报文
- 注入攻击：构造并发送伪造的报文

**危害程度：** 极高（可直接控制车辆）

#### 2.2.4 拒绝服务攻击（DoS）

**原理：** 攻击者大量发送CAN报文占用总线带宽，或使总线进入错误状态。

**攻击方式：**

**方式一：总线洪泛（Bus Flooding）**
```
持续发送高优先级ID（如0x000）的报文
→ 正常报文无法获得总线使用权
→ 系统通信受阻，功能失效
```

**方式二：错误触发（Error Triggering）**
```
持续发送错误帧
→ 其他节点错误计数器增加
→ 节点进入总线关闭状态
→ 节点脱离总线，功能失效
```

#### 2.2.5 模糊测试（Fuzzing）

**原理：** 向ECU发送各种畸形、异常的CAN报文，观察是否出现异常。

**目的：** 发现ECU软件中的漏洞（缓冲区溢出、空指针引用等）

**方法：**
- 随机Fuzz：随机生成数据
- 变异Fuzz：在正常报文基础上变异
- 智能Fuzz：基于协议规范生成测试用例

### 2.3 攻击接入方式

| 接入方式 | 攻击距离 | 难度 | 说明 |
|---------|---------|------|------|
| OBD-II接口 | 物理接触 | 低 | 最直接的接入方式，16针接口 |
| 拆解焊接 | 物理接触 | 中 | 直接焊接到CAN总线上 |
| IVI系统攻破 | 近场/远程 | 中高 | 通过IVI漏洞进入车内网络 |
| T-Box攻破 | 远程 | 高 | 通过蜂窝网络远程接入 |
| 蓝牙/Wi-Fi | 近场 | 中高 | 通过无线接口渗透 |
| OTA攻击 | 远程 | 很高 | 通过OTA注入恶意固件 |
