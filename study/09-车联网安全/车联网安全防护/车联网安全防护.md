# 车联网安全防护体系

> 本文档详细介绍车联网安全防护体系，包括纵深防御、ECU加固、CAN总线防护、车云通信安全、安全启动、OTA安全和安全运营等内容。

---

## 一、纵深防御体系

### 1.1 纵深防御理念

**纵深防御（Defense in Depth）** 是信息安全的基本原则，在车联网安全中同样适用。其核心思想是：**不依赖单一防护措施，而是构建多层防护体系，即使某一层被突破，还有其他层提供保护。**

#### 1.1.1 为什么车联网需要纵深防御

- **攻击面广泛**：从物理接口到远程网络，攻击途径多样
- **单一防护不足**：任何技术都不是万能的
- **安全与功能平衡**：某些安全机制会影响性能和成本
- **安全演进需求**：攻击手段不断进化，防护也需要多层次

### 1.2 车联网纵深防御架构

```
┌──────────────────────────────────────────────────────┐
│                  第7层：安全运营与应急响应              │ ← 监测、响应、恢复
├──────────────────────────────────────────────────────┤
│                  第6层：云平台与数据安全                │ ← 云安全、数据保护
├──────────────────────────────────────────────────────┤
│                  第5层：车云通信安全                   │ ← 通信加密、身份认证
├──────────────────────────────────────────────────────┤
│                  第4层：车载网关防护                   │ ← 防火墙、IDS/IPS
├──────────────────────────────────────────────────────┤
│                  第3层：车载网络安全                   │ ← CAN总线安全、认证
├──────────────────────────────────────────────────────┤
│                  第2层：ECU安全加固                   │ ← 安全启动、TEE、HSM
├──────────────────────────────────────────────────────┤
│                  第1层：物理安全防护                   │ ← 接口防护、防拆、调试关闭
└──────────────────────────────────────────────────────┘
```

### 1.3 各层防护要点

| 防护层级 | 核心目标 | 主要措施 |
|---------|---------|---------|
| 物理安全 | 防止物理接触攻击 | 防拆设计、调试接口关闭、芯片读保护 |
| ECU安全 | 确保ECU自身安全 | 安全启动、可信执行、内存保护、HSM |
| 车载网络 | 保护车内通信 | CAN认证、报文加密、入侵检测 |
| 网关防护 | 域间安全隔离 | 安全网关、防火墙、报文过滤 |
| 车云通信 | 保护车云数据传输 | TLS/DTLS、双向认证、消息认证 |
| 云平台安全 | 保护云端系统和数据 | 身份认证、访问控制、数据加密 |
| 安全运营 | 持续监控与响应 | SOC、威胁情报、应急响应、漏洞管理 |

### 1.4 安全设计原则

#### 1.4.1 基本原则

1. **最小权限原则**：每个组件只拥有完成功能所需的最小权限
2. **纵深防御原则**：多层防护，避免单点失效
3. **安全默认原则**：系统默认配置应是最安全的
4. ** fail-safe 原则**：系统故障时进入安全状态
5. **最小攻击面原则**：尽可能减少暴露的攻击面
6. **深度检测原则**：多层次、多维度的安全检测

#### 1.4.2 车联网特有原则

1. **功能安全优先**：网络安全不能影响功能安全
2. **实时性保障**：安全机制不能过度影响实时性能
3. **长生命周期**：考虑10~15年使用周期的安全维护
4. **供应链安全**：确保供应商的安全能力
5. **可更新性**：安全机制应支持在线更新

## 二、ECU安全加固

### 2.1 ECU安全架构

#### 2.1.1 安全启动（Secure Boot）

**概念：** ECU启动时验证固件的完整性和真实性，确保只有经过授权的固件才能运行。

**启动流程：**

```
┌─────────────┐
│   复位启动   │
└──────┬──────┘
       │
┌──────▼──────┐    ┌──────────────┐
│  Boot ROM   │───→│ 验证Bootloader │  ← 验证Bootloader签名
│  (不可变)   │    │   签名        │
└──────┬──────┘    └──────────────┘
       │ 验证通过
┌──────▼──────┐    ┌──────────────┐
│ Bootloader  │───→│ 验证应用固件   │  ← 验证应用程序签名
│             │    │   签名        │
└──────┬──────┘    └──────────────┘
       │ 验证通过
┌──────▼──────┐
│  应用程序    │  ← 正常运行
│  (App)      │
└─────────────┘
```

**关键要素：**
- **信任根（RoT, Root of Trust）**：Boot ROM，硬件实现，不可修改
- **签名算法**：通常使用RSA或ECC非对称加密
- **证书链**：逐级验证，建立信任链
- **失败处理**：验证失败时拒绝启动或进入恢复模式

**常见实现：**
- ARM TrustZone
- 硬件安全模块（HSM）
- 安全元件（SE）

#### 2.1.2 可信执行环境（TEE）

**概念：** 在主处理器中划分出一个安全区域，与普通操作系统隔离，提供安全的执行环境。

**ARM TrustZone架构：**

```
┌─────────────────────────────────────────┐
│            应用层                        │
│  Normal World            Secure World    │
│  ┌──────────┐          ┌──────────┐     │
│  │  Rich OS  │          │  TEE OS  │     │
│  │ (Linux/  │          │ (安全OS) │     │
│  │  Android)│          │          │     │
│  └────┬─────┘          └────┬─────┘     │
│       │                     │           │
│  ┌────▼─────┐          ┌────▼─────┐     │
│  │  内核    │          │  安全内核 │     │
│  └────┬─────┘          └────┬─────┘     │
└───────┼─────────────────────┼───────────┘
        │    Monitor Mode     │
        └─────────────────────┘
              CPU硬件隔离
```

**TEE中的安全服务：**
- 密钥存储与管理
- 加密/解密运算
- 安全启动验证
- 安全认证
- 敏感数据处理
- 支付安全

**车载应用场景：**
- 数字钥匙安全存储
- V2X消息签名
- 车云通信密钥管理
- 车内支付安全
- 生物识别数据处理

#### 2.1.3 硬件安全模块（HSM）

**HSM（Hardware Security Module）** 是专门的硬件安全模块，提供加密运算和密钥管理功能。

**车载HSM功能：**
- **密钥生成与存储**：安全生成和存储密钥，密钥不可导出
- **加密运算加速**：硬件实现AES、SHA、ECC等算法
- **安全启动验证**：验证固件签名
- **消息认证码生成**：生成/验证CAN报文MAC
- **真随机数生成**：提供高质量随机数

**常见车载HSM：**
- Infineon HSM（集成在AURIX系列MCU中）
- NXP HSE（Hardware Security Engine）
- 独立安全芯片（如ATAES、ATECC系列）

### 2.2 内存安全

#### 2.2.1 常见内存漏洞

| 漏洞类型 | 说明 | 防护措施 |
|---------|------|---------|
| 缓冲区溢出 | 写入数据超过缓冲区大小 | 栈保护、边界检查 |
| 整数溢出 | 整数运算结果超出表示范围 | 输入校验、安全函数 |
| 格式化字符串 | 格式化字符串参数可被控制 | 代码审计、编译选项 |
| 堆溢出 | 堆内存越界写入 | 堆保护、隔离 |
| Use-After-Free | 释放后继续使用内存 | 内存安全检查 |
| 空指针引用 | 引用空指针 | 代码审计、静态分析 |

#### 2.2.2 防护技术

**编译期防护：**
- **Stack Canary（栈金丝雀）**：栈帧中插入保护值，检测栈溢出
- **ASLR（地址空间随机化）**：随机化内存布局，增加攻击难度
- **DEP/NX（数据执行保护）**：数据页不可执行，防止shellcode执行
- **FORTIFY_SOURCE**：强化库函数的安全检查
- **Control Flow Integrity（CFI）**：控制流完整性保护

**运行期防护：**
- **MPU（内存保护单元）**：隔离不同内存区域的访问权限
- **MMU（内存管理单元）**：虚拟内存隔离
- **Watchdog**：监控程序运行状态，异常时复位
- **内存ECC**：错误检测与纠正

### 2.3 ECU固件安全

#### 2.3.1 固件加密

**目的：** 防止固件被提取和分析。

**实现方式：**
- Flash中的固件加密存储
- 运行时解密到RAM执行
- 由HSM或安全启动流程解密

**注意：** 单纯的固件加密不能防止运行时攻击，需要配合其他安全机制。

#### 2.3.2 固件更新安全

详见第六章"OTA升级安全"。

#### 2.3.3 调试接口安全

**防护措施：**
1. **量产时禁用调试接口**：关闭JTAG/SWD/UART等调试接口
2. **调试保护机制**：启用MCU的调试保护功能
3. **安全调试**：如需保留调试功能，应增加认证机制
4. **芯片级保护**：启用Flash读保护、写保护

## 三、CAN总线防护

### 3.1 CAN总线安全方案概览

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 入侵检测（IDS） | 监控异常行为 | 部署简单，不影响正常通信 | 只能检测，不能阻止 |
| 入侵防御（IPS） | 过滤恶意报文 | 可主动阻止攻击 | 误判可能影响正常功能 |
| 报文认证（MAC） | 附加认证码验证报文 | 从根源防止伪造 | 增加开销，需要密钥管理 |
| 报文加密 | 加密数据内容 | 防止嗅探和数据泄露 | 增加延迟，ECU负载大 |
| 安全网关 | 域间隔离与过滤 | 保护关键域 | 网关自身成为目标 |
| 总线监控 | 集中监控总线状态 | 全局视角 | 无法阻止攻击 |

### 3.2 CAN报文认证

#### 3.2.1 认证原理

在CAN报文中附加消息认证码（MAC），接收方验证MAC的正确性，确保报文来自合法节点且未被篡改。

```
发送方:
  原始报文: [ID | 数据]
  计算MAC: MAC = AES-CMAC(密钥, ID + 数据 + 新鲜值)
  发送: [ID | 数据 | MAC]

接收方:
  收到报文: [ID | 数据 | MAC]
  计算MAC: MAC' = AES-CMAC(密钥, ID + 数据 + 新鲜值)
  验证: MAC == MAC' ? 合法 : 丢弃
```

#### 3.2.2 新鲜值（Freshness Value）

**作用：** 防止重放攻击。

**实现方式：**
- **计数器方式**：每个报文包含递增的计数器
- **时间戳方式**：使用同步的时间戳
- **随机数方式**：每次使用新的随机数

**计数器方式的问题：**
- 需要同步计数器值
- 计数器溢出处理
- 丢包时的处理

#### 3.2.3 常见CAN认证方案

**1. CANAuth（CAN Authentication）**
- 基于分组密码的认证方案
- 使用CMAC生成认证码
- 支持新鲜值计数器

**2. VeCure（Vehicle Security）**
- 提供认证和加密
- 适用于CAN和FlexRay

**3. SecOC（Secure On-board Communication）**
- AUTOSAR标准中的安全通信方案
- 使用CMAC进行报文认证
- 支持新鲜值管理
- 已成为行业主流方案

**4. CANsec（CAN Security Protocol）**
- 由CAN总线创始公司Bosch等推动
- 提供认证和可选加密
- 兼容CAN FD

#### 3.2.4 SecOC详解（AUTOSAR标准）

**SecOC（Secure On-board Communication）** 是AUTOSAR标准定义的车载安全通信方案。

**核心组件：**
```
┌─────────────────────────────────────────┐
│          应用层（SWC）                    │
├─────────────────────────────────────────┤
│          PDU Router                     │
├─────────────────────────────────────────┤
│          SecOC模块                       │
│  ┌─────────┐  ┌──────────┐  ┌────────┐ │
│  │ 认证/验证│  │ 新鲜值管理│  │密钥管理 │ │
│  └─────────┘  └──────────┘  └────────┘ │
├─────────────────────────────────────────┤
│          CAN/LIN/以太网                  │
└─────────────────────────────────────────┘
```

**认证数据（Authenticator）：**
- 通常使用CMAC（Cipher-based MAC）
- MAC长度可配置（8位、16位、32位、64位等）
- 权衡：MAC越长越安全，但占用数据空间越大

**新鲜值管理：**
- 发送方维护计数器，每次发送递增
- 接收方维护期望的计数器值
- 收到的计数器必须大于期望值（防止重放）
- 支持计数器同步机制

**数据截断：**
- CAN数据场只有8字节（CAN FD 64字节）
- 认证数据需要占用部分数据空间
- 可配置认证数据的长度和位置
- 有时需要将认证数据放在单独的报文中

### 3.3 CAN总线加密

#### 3.3.1 加密的挑战

- **带宽限制**：CAN 8字节数据，加密后数据膨胀
- **实时性要求**：加密解密需要计算时间
- **资源限制**：低端ECU算力不足
- **密钥管理**：多节点密钥分发和更新困难
- **向后兼容**：不能影响现有ECU的正常工作

#### 3.3.2 适用场景

CAN加密通常不用于所有报文，只保护敏感报文：
- 安全相关的控制指令
- 敏感数据（如位置、个人信息）
- 诊断通信
- 固件更新

### 3.4 入侵检测与防御系统（IDPS）

#### 3.4.1 CAN IDS/IPS部署位置

```
                    ┌──────────┐
                    │ 安全网关  │  ← 集中式IDPS，全局监控
                    └────┬─────┘
         ┌───────────────┼───────────────┐
    ┌────▼────┐     ┌───▼───┐      ┌────▼────┐
    │  动力域  │     │ 车身域 │      │ 信息域  │
    └────┬────┘     └───┬───┘      └────┬────┘
         │              │               │
    ┌────▼────┐    ┌────▼────┐     ┌───▼─────┐
    │关键ECU  │    │ 普通ECU │     │  IVI    │
    │内置IDS  │    │         │     │         │
    └─────────┘    └─────────┘     └─────────┘
```

**集中式部署（网关）：**
- 优点：全局视角，统一管理
- 缺点：网关性能瓶颈，单点故障

**分布式部署（各ECU）：**
- 优点：就近检测，响应快
- 缺点：资源占用大，管理复杂

**混合部署：**
- 关键ECU本地检测 + 网关集中监控
- 兼顾性能和安全

#### 3.4.2 检测技术对比

| 检测方法 | 原理 | 可检测的攻击 | 误报率 | 实现难度 |
|---------|------|-------------|--------|---------|
| 频率/周期检测 | 监控报文发送频率 | 洪泛DoS、异常注入 | 低 | 低 |
| 未知ID检测 | 检测白名单外的ID | 未知报文注入 | 低 | 很低 |
| 数据范围检测 | 检查信号值是否在合法范围 | 数据伪造 | 中 | 中 |
| 数据跳变检测 | 检查信号变化速率 | 数据篡改 | 中 | 中 |
| 时钟指纹检测 | 基于ECU时钟偏移识别身份 | 报文伪造 | 低 | 高 |
| 基于规则检测 | 预定义安全规则 | 已知攻击 | 低 | 中 |
| 机器学习检测 | AI模型检测异常 | 未知攻击 | 中高 | 高 |

#### 3.4.3 响应策略

| 响应级别 | 动作 | 适用场景 |
|---------|------|---------|
| 日志记录 | 记录异常事件 | 低风险异常 |
| 告警上报 | 上报网关/云端 | 中等风险 |
| 报文过滤 | 丢弃恶意报文 | 明确的攻击 |
| 速率限制 | 限制异常ID的发送速率 | 洪泛攻击 |
| 总线隔离 | 断开受影响的网段 | 严重攻击 |
| 功能降级 | 进入安全运行模式 | 影响安全功能 |
| 安全停车 | 控制车辆安全停下 | 危及驾驶安全 |

### 3.5 安全网关

#### 3.5.1 安全网关的作用

安全网关是车载网络的"安全枢纽"，负责不同域之间的安全通信。

**核心功能：**
- **域间隔离**：防止一个域被攻破后渗透到其他域
- **报文过滤**：基于白名单/黑名单过滤跨域报文
- **协议转换**：不同网络协议之间的转换
- **入侵检测**：监控各域的异常行为
- **访问控制**：控制跨域访问的权限
- **安全审计**：记录跨域通信日志

#### 3.5.2 网关安全规则示例

```
规则1：信息域 → 动力域
  允许的CAN ID：0x100, 0x200 （仅仪表显示用的状态数据）
  禁止：所有控制类ID（刹车、油门、转向等）
  方向：单向（只读）

规则2：诊断接口 → 各域
  允许：诊断相关ID（0x7DF, 0x7E0~0x7EF）
  限制：需要安全访问认证
  速率：限制诊断报文的发送频率

规则3：T-Box → 各域
  允许：特定的数据采集和控制ID
  限制：需要身份认证和权限校验
  审计：所有操作记录日志
```

## 四、车云通信安全

### 4.1 通信安全架构

#### 4.1.1 安全通信模型

```
车辆端（T-Box/IVI）              云端（平台）
     │                              │
     │── 1. 身份认证 ────────────→ │
     │←── 2. 认证响应 ──────────── │
     │                              │
     │── 3. 密钥协商 ────────────→ │
     │←── 4. 会话密钥 ──────────── │
     │                              │
     │── 5. 加密数据传输 ────────→ │
     │←── 6. 加密数据传输 ──────── │
     │                              │
```

#### 4.1.2 常用安全协议

| 协议 | 层级 | 用途 | 说明 |
|------|------|------|------|
| TLS 1.2/1.3 | 传输层 | HTTPS、MQTT over TLS | 最常用，安全性高 |
| DTLS | 传输层 | UDP应用、CoAP | TLS的UDP版本 |
| IPSec | 网络层 | VPN、端到端安全 | 网络层加密 |
| MQTT TLS | 应用层 | 消息队列遥测传输 | 车云消息常用 |
| CoAP DTLS | 应用层 | 受限设备通信 | 轻量级协议 |

### 4.2 身份认证

#### 4.2.1 设备身份认证

**认证方式：**

**1. 基于预共享密钥（PSK）**
```
车辆端存储密钥K ←──────────→ 云端存储密钥K
认证: 双方使用K进行身份验证
```
- 优点：简单、高效
- 缺点：密钥分发和管理困难，扩展性差

**2. 基于证书的认证（PKI）**
```
车辆端证书 + 私钥 ←──────→ 根CA证书
认证: 双向证书认证，验证对方身份
```
- 优点：安全性高，扩展性好
- 缺点：实现复杂，需要PKI体系

**3. 基于令牌的认证**
```
车辆端登录获取Token ←──────→ 认证服务签发Token
通信: 携带Token进行身份验证
```
- 优点：灵活，可控制有效期
- 缺点：Token泄露风险

#### 4.2.2 双向认证

车云通信应使用双向认证（Mutual Authentication）：
- 车辆验证云端身份（防止连接到伪基站/伪服务器）
- 云端验证车辆身份（防止伪造设备接入）

### 4.3 数据传输安全

#### 4.3.1 传输加密

**加密算法选择：**
- **对称加密**：AES-128/256-GCM（推荐，提供加密+完整性）
- **非对称加密**：RSA-2048/3072、ECC-256（用于密钥交换）
- **哈希算法**：SHA-256/384
- **密钥交换**：ECDHE（前向安全）

#### 4.3.2 消息完整性与认证

- **MAC（消息认证码）**：确保消息未被篡改
- **数字签名**：确保消息来源可信
- **时间戳/序列号**：防止重放攻击

#### 4.3.3 常见安全问题

| 问题 | 风险 | 防护措施 |
|------|------|---------|
| 明文传输 | 数据泄露、篡改 | 启用TLS/DTLS |
| 不验证证书 | 中间人攻击 | 严格验证服务器证书 |
| 弱加密算法 | 加密被破解 | 使用强加密算法 |
| 硬编码密钥 | 密钥泄露 | 安全存储密钥（HSM/TEE） |
| 无重放防护 | 重放攻击 | 时间戳、序列号 |
| 不安全的TLS配置 | 降级攻击 | 禁用弱密码套件 |

### 4.4 MQTT安全

MQTT是车云通信最常用的协议之一。

#### 4.4.1 MQTT安全措施

```
┌─────────────────────────────────────┐
│         应用层安全                   │
│  Topic权限控制 | 消息过滤 | Payload加密 │
├─────────────────────────────────────┤
│         会话层安全                   │
│  客户端认证 | 会话管理 | 遗嘱消息     │
├─────────────────────────────────────┤
│         传输层安全                   │
│  TLS/DTLS加密 | 双向认证             │
├─────────────────────────────────────┤
│         网络层安全                   │
│  防火墙 | VPN | IP白名单             │
└─────────────────────────────────────┘
```

#### 4.4.2 关键安全配置

1. **启用TLS**：使用8883端口（MQTT over TLS）
2. **客户端认证**：每个设备独立的用户名/密码或证书
3. **Topic权限**：严格控制每个客户端的发布/订阅权限
4. **QoS级别**：重要消息使用QoS 1或2
5. **遗嘱消息**：异常断开时通知系统
6. **Keep Alive**：合理设置心跳间隔

## 五、安全启动与可信执行

### 5.1 安全启动（Secure Boot）

#### 5.1.1 信任链

安全启动建立了一条从硬件到应用的信任链：

```
硬件信任根 (Boot ROM)
    │ 验证签名
    ▼
第一级Bootloader (BL1)
    │ 验证签名
    ▼
第二级Bootloader (BL2)
    │ 验证签名
    ▼
操作系统内核 (OS Kernel)
    │ 验证签名
    ▼
应用程序 (Applications)
```

每一级都验证下一级的签名，确保整个启动过程的完整性和真实性。

#### 5.1.2 签名验证过程

```
固件包结构：
┌───────────────┐
│  固件数据      │
├───────────────┤
│  数字签名      │  ← 使用厂商私钥签名
├───────────────┤
│  公钥证书      │  ← 由根证书签发
└───────────────┘

验证过程：
  1. 使用根公钥验证证书签名
  2. 使用证书中的公钥验证固件签名
  3. 计算固件数据的哈希值
  4. 解密签名得到预期哈希
  5. 比较两个哈希值是否一致
```

#### 5.1.3 安全启动的关键要素

1. **信任根（RoT）不可篡改**：Boot ROM在硬件中实现，无法修改
2. **签名算法安全**：使用安全的签名算法（RSA-2048+、ECC-256+）
3. **密钥安全存储**：私钥严格保密，使用HSM存储
4. **版本管理**：防止版本回退（降级攻击）
5. **失败处理**：验证失败时进入安全恢复模式

### 5.2 可信执行环境（TEE）

#### 5.2.1 车载TEE应用场景

| 应用 | 说明 |
|------|------|
| 数字钥匙 | 安全存储车钥匙凭证，执行认证协议 |
| V2X安全 | V2X消息的签名和验证 |
| 车内支付 | 支付密钥存储和交易处理 |
| 生物识别 | 人脸/指纹数据处理和存储 |
| 数据加密 | 敏感数据的加密解密 |
| 安全启动 | 启动过程中的验证逻辑 |
| 密钥管理 | 车辆密钥的生成、存储和更新 |

#### 5.2.2 主流TEE方案

| 方案 | 厂商 | 特点 |
|------|------|------|
| TrustZone | ARM | 硬件隔离，广泛使用 |
| QNX Safe Kernel | 黑莓 | 安全微内核，车规级 |
| OP-TEE | Linaro | 开源，ARM TrustZone上实现 |
| Trusty | Google | Android系统配套 |
| T6 / i.MX | NXP | 车载芯片内置安全模块 |

### 5.3 安全元件（SE）

**SE（Secure Element）** 是独立的安全芯片，提供更高的安全级别。

**特点：**
- 独立的CPU和内存
- 防物理攻击（防篡改、防侧信道）
- 安全存储密钥
- 硬件加密加速
- 通过高等级安全认证（如CC EAL5+）

**车载应用：**
- eSIM安全
- 数字钥匙安全
- V2X安全证书存储
- 支付安全

## 六、OTA升级安全

### 6.1 OTA安全威胁

#### 6.1.1 威胁模型

```
攻击者可能的攻击点：
    │
    ├── 攻击OTA服务器
    │       ├── 控制升级服务器，下发恶意固件
    │       ├── 获取固件包进行分析
    │       └── 篡改升级策略
    │
    ├── 攻击传输通道
    │       ├── 中间人攻击，篡改固件包
    │       ├── 劫持DNS，连接伪服务器
    │       └── 重放攻击，重复发送旧版本
    │
    ├── 攻击终端设备
    │       ├── 绕过签名验证
    │       ├── 降级攻击（安装有漏洞的旧版本）
    │       └── 利用升级过程中的漏洞
    │
    └── 供应链攻击
            ├── 在固件开发阶段植入后门
            └── 第三方组件漏洞
```

### 6.2 OTA安全机制

#### 6.2.1 固件安全

**1. 固件签名验证**
- 每个固件包都有厂商的数字签名
- 车辆端验证签名后才安装
- 使用强签名算法（RSA-2048/3072 或 ECC-256/384）
- 支持多级证书链

**2. 固件加密**
- 固件包加密存储和传输
- 防止固件泄露和分析
- 密钥安全分发

**3. 完整性校验**
- SHA-256/SHA-384哈希校验
- 确保固件完整未被篡改
- 分块校验（增量升级时）

**4. 版本管理与防降级**
- 每个固件有版本号
- 禁止安装版本号低于当前版本的固件
- 版本号防篡改（签名包含版本号）

#### 6.2.2 传输安全

**1. 加密传输**
- 使用TLS 1.2+加密传输
- 双向身份认证
- 强密码套件

**2. 断点续传安全**
- 分块传输，每块都有校验
- 断点续传时验证已下载部分
- 防止部分篡改

**3. 防重放攻击**
- 升级请求带有时效性
- 使用随机数/时间戳

#### 6.2.3 升级过程安全

**完整的OTA升级流程：**

```
① 升级检查
   ├── 车辆端向OTA平台查询新版本
   ├── 平台返回升级包信息（版本、大小、签名）
   └── 车辆端验证信息合法性
       ↓
② 固件下载
   ├── 建立安全连接（TLS双向认证）
   ├── 下载加密的固件包
   ├── 分块下载，每块校验
   └── 下载完成后整体校验（签名+哈希）
       ↓
③ 升级准备
   ├── 检查升级条件（电量、车速、停车状态）
   ├── 备份当前固件（AB分区方案）
   ├── 通知用户升级事项
   └── 进入升级模式
       ↓
④ 固件安装
   ├── 验证固件签名（最终验证）
   ├── 写入新固件到备用分区
   ├── 验证写入完整性
   └── 更新启动配置
       ↓
⑤ 升级验证
   ├── 重启系统，从新固件启动
   ├── 运行自检程序
   ├── 验证各功能正常
   └── 成功：确认使用新分区
       失败：回滚到旧分区
       ↓
⑥ 升级完成
   ├── 上报升级结果
   ├── 清理旧固件
   └── 记录升级日志
```

#### 6.2.4 A/B分区升级方案

**原理：** 系统有两个分区（A和B），当前运行的分区不动，升级写入另一个分区，升级成功后切换启动分区。

```
┌─────────────┐    ┌─────────────┐
│  分区A（运行）│    │  分区B（备用）│  ← 升级前
│  v1.0       │    │  v0.9       │
└─────────────┘    └─────────────┘

        ↓  升级v2.0，写入分区B

┌─────────────┐    ┌─────────────┐
│  分区A（旧）  │    │  分区B（新） │  ← 升级后
│  v1.0       │    │  v2.0       │
└─────────────┘    └─────────────┘
                       ↑
                    从分区B启动

        ↓  如果升级失败

┌─────────────┐    ┌─────────────┐
│  分区A（回滚）│    │  分区B（坏） │  ← 回滚后
│  v1.0       │    │  v2.0       │
└─────────────┘    └─────────────┘
     ↑
  从分区A启动（回滚）
```

**优点：**
- 升级失败可快速回滚
- 升级过程不影响当前系统
- 升级可以在后台进行
- 不会因升级中断导致变砖

### 6.3 差分升级安全

#### 6.3.1 差分升级原理

差分升级（增量升级）只传输新旧版本之间的差异，减少升级包大小。

```
旧版本 (v1.0)     差分包 (patch)      新版本 (v2.0)
    100MB    +     10MB    =       100MB
```

#### 6.3.2 安全要点

1. **差分包也要签名**：差分包同样需要数字签名
2. **基准版本验证**：确保应用差分包的基准版本正确
3. **应用后校验**：差分应用后验证整体完整性
4. **防回滚**：差分包也受版本控制


#### 7.4.2 车联网特殊的应急响应考虑

1. **驾驶安全优先**：任何响应措施不能影响驾驶安全
2. **车辆分布广**：大量车辆分布在各地，响应困难
3. **OTA更新慢**：补丁推送和安装需要时间
4. **用户参与**：可能需要车主配合升级
5. **法规要求**：需要按法规要求上报安全事件
6. **影响评估**：评估对驾驶安全的影响程度

#### 7.4.3 不同级别的响应措施

| 级别 | 事件类型 | 响应措施 |
|------|---------|---------|
| 低 | 信息泄露、非关键系统漏洞 | 记录、分析、计划修复 |
| 中 | 普通功能被控制、数据泄露 | 通知用户、远程修复、监控 |
| 高 | 可远程控制非安全相关功能 | 紧急修复、OTA推送、加强监控 |
| 严重 | 可远程控制动力系统 | 紧急响应、车辆召回、公开通报 |
| 灾难 | 大规模车辆被控制、危及公共安全 | 应急响应启动、政府协调、全面排查 |

## 八、学习要点与思考题

### 8.1 核心知识点总结

1. **纵深防御**：多层次防护，从物理层到运营层，避免单点失效
2. **ECU安全**：安全启动、TEE、HSM、内存保护是ECU加固的核心
3. **CAN安全**：SecOC报文认证是行业标准方案，IDPS是重要补充
4. **安全网关**：域间隔离的关键，是纵深防御的重要一环
5. **车云通信**：TLS双向认证、数据加密、消息认证是基础
6. **安全启动**：建立信任链，确保固件完整性和真实性
7. **OTA安全**：签名验证、防降级、A/B分区、安全回滚
8. **安全运营**：VSOC持续监控，漏洞管理和应急响应保障

### 8.2 思考题

1. 为什么车联网安全需要纵深防御？单一的防护措施为什么不够？
2. CAN总线安全中，报文认证（SecOC）和入侵检测（IDS）各有什么优缺点？为什么需要同时部署？
3. 安全启动和可信执行环境（TEE）有什么区别和联系？
4. OTA升级中的A/B分区方案有什么优点？它解决了什么问题？
5. 车联网安全运营和传统互联网安全运营最大的区别是什么？
