# OTA升级安全

### 6.1 OTA安全威胁

#### 6.1.1 威胁模型

```
攻击者可能的攻击点：
    │
    ├── 攻击OTA服务器
    │       ├── 控制升级服务器，下发恶意固件
    │       ├── 获取固件包进行分析
    │       └── 篡改升级策略
    │
    ├── 攻击传输通道
    │       ├── 中间人攻击，篡改固件包
    │       ├── 劫持DNS，连接伪服务器
    │       └── 重放攻击，重复发送旧版本
    │
    ├── 攻击终端设备
    │       ├── 绕过签名验证
    │       ├── 降级攻击（安装有漏洞的旧版本）
    │       └── 利用升级过程中的漏洞
    │
    └── 供应链攻击
            ├── 在固件开发阶段植入后门
            └── 第三方组件漏洞
```

### 6.2 OTA安全机制

#### 6.2.1 固件安全

**1. 固件签名验证**
- 每个固件包都有厂商的数字签名
- 车辆端验证签名后才安装
- 使用强签名算法（RSA-2048/3072 或 ECC-256/384）
- 支持多级证书链

**2. 固件加密**
- 固件包加密存储和传输
- 防止固件泄露和分析
- 密钥安全分发

**3. 完整性校验**
- SHA-256/SHA-384哈希校验
- 确保固件完整未被篡改
- 分块校验（增量升级时）

**4. 版本管理与防降级**
- 每个固件有版本号
- 禁止安装版本号低于当前版本的固件
- 版本号防篡改（签名包含版本号）

#### 6.2.2 传输安全

**1. 加密传输**
- 使用TLS 1.2+加密传输
- 双向身份认证
- 强密码套件

**2. 断点续传安全**
- 分块传输，每块都有校验
- 断点续传时验证已下载部分
- 防止部分篡改

**3. 防重放攻击**
- 升级请求带有时效性
- 使用随机数/时间戳

#### 6.2.3 升级过程安全

**完整的OTA升级流程：**

```
① 升级检查
   ├── 车辆端向OTA平台查询新版本
   ├── 平台返回升级包信息（版本、大小、签名）
   └── 车辆端验证信息合法性
       ↓
② 固件下载
   ├── 建立安全连接（TLS双向认证）
   ├── 下载加密的固件包
   ├── 分块下载，每块校验
   └── 下载完成后整体校验（签名+哈希）
       ↓
③ 升级准备
   ├── 检查升级条件（电量、车速、停车状态）
   ├── 备份当前固件（AB分区方案）
   ├── 通知用户升级事项
   └── 进入升级模式
       ↓
④ 固件安装
   ├── 验证固件签名（最终验证）
   ├── 写入新固件到备用分区
   ├── 验证写入完整性
   └── 更新启动配置
       ↓
⑤ 升级验证
   ├── 重启系统，从新固件启动
   ├── 运行自检程序
   ├── 验证各功能正常
   └── 成功：确认使用新分区
       失败：回滚到旧分区
       ↓
⑥ 升级完成
   ├── 上报升级结果
   ├── 清理旧固件
   └── 记录升级日志
```

#### 6.2.4 A/B分区升级方案

**原理：** 系统有两个分区（A和B），当前运行的分区不动，升级写入另一个分区，升级成功后切换启动分区。

```
┌─────────────┐    ┌─────────────┐
│  分区A（运行）│    │  分区B（备用）│  ← 升级前
│  v1.0       │    │  v0.9       │
└─────────────┘    └─────────────┘

        ↓  升级v2.0，写入分区B

┌─────────────┐    ┌─────────────┐
│  分区A（旧）  │    │  分区B（新） │  ← 升级后
│  v1.0       │    │  v2.0       │
└─────────────┘    └─────────────┘
                       ↑
                    从分区B启动

        ↓  如果升级失败

┌─────────────┐    ┌─────────────┐
│  分区A（回滚）│    │  分区B（坏） │  ← 回滚后
│  v1.0       │    │  v2.0       │
└─────────────┘    └─────────────┘
     ↑
  从分区A启动（回滚）
```

**优点：**
- 升级失败可快速回滚
- 升级过程不影响当前系统
- 升级可以在后台进行
- 不会因升级中断导致变砖

### 6.3 差分升级安全

#### 6.3.1 差分升级原理

差分升级（增量升级）只传输新旧版本之间的差异，减少升级包大小。

```
旧版本 (v1.0)     差分包 (patch)      新版本 (v2.0)
    100MB    +     10MB    =       100MB
```

#### 6.3.2 安全要点

1. **差分包也要签名**：差分包同样需要数字签名
2. **基准版本验证**：确保应用差分包的基准版本正确
3. **应用后校验**：差分应用后验证整体完整性
4. **防回滚**：差分包也受版本控制
