# SSDLC 概述

### 1.1 为什么需要 SSDLC

**传统开发模式的安全困境**
- 安全在开发后期才被考虑，修复成本高
- 安全测试依赖人工，成为交付瓶颈
- 漏洞在上线后才被发现，暴露面大
- 缺乏系统性的安全流程和度量

**SSDLC 的价值**
- 越早发现漏洞修复成本越低（需求阶段 vs 生产环境成本比可达 1:100）
- 系统化覆盖各阶段安全风险
- 自动化安全活动减少人工瓶颈
- 可度量、可追溯、可改进
- 满足合规要求（等保、ISO 27001、PCI DSS）

**漏洞修复成本随阶段变化**
```
需求阶段   设计阶段   编码阶段   测试阶段   生产阶段
  █         ███       ████      ██████    █████████
  1x        5x        10x       30x       100x
```

### 1.2 主流 SSDLC 框架

#### 1.2.1 Microsoft SDL（Security Development Lifecycle）

微软安全开发生命周期是业界最早系统化的 SSDLC 框架，包含以下阶段：

**SDL 七个阶段**
1. 培训阶段：安全意识培训
2. 需求阶段：安全需求分析、风险评估
3. 设计阶段：威胁建模、攻击面分析
4. 实现阶段：安全编码、静态分析
5. 验证阶段：模糊测试、动态分析
6. 发布阶段：最终安全审查
7. 响应阶段：漏洞响应计划

**SDL 核心活动**
- 安全需求定义
- 威胁建模（STRIDE 方法）
- 安全编码规范
- SAST/DAST 工具使用
- 模糊测试
- 攻击面分析
- 安全事件响应计划

#### 1.2.2 OWASP SAMM（Software Assurance Maturity Model）

OWASP 软件保证成熟度模型是一个开放框架，帮助组织评估和改进软件安全实践。

**SAMM 五个业务功能**
| 业务功能 | 安全实践 | 成熟度等级 |
|---------|---------|-----------|
| 治理 | 策略与合规、教育与指导、质量保证 | 0-3 |
| 设计 | 威胁评估、安全需求、安全架构 | 0-3 |
| 实现 | 安全构建、安全部署、缺陷管理 | 0-3 |
| 验证 | 架构评估、需求驱动测试、安全测试 | 0-3 |
| 运营 | 事件管理、运营管理、环境管理 | 0-3 |

**SAMM 成熟度等级**
- 级别 0：未实施 - 完全缺失安全实践
- 级别 1：初始级 - 基础实践已建立
- 级别 2：可重复级 - 实践可重复执行
- 级别 3：优化级 - 实践持续优化

**SAMM 评估流程**
1. 确定评估范围
2. 进行访谈和文档审查
3. 对每个安全实践评分
4. 制定改进路线图
5. 定期重新评估

#### 1.2.3 NIST SSDF（Secure Software Development Framework）

NIST 安全软件开发框架，为联邦机构提供安全开发指导。

**SSDF 四个实践族**
| 实践族 | 关键任务 | 说明 |
|-------|---------|------|
| PO（准备组织） | 策略、角色、工具链 | 组织安全开发准备 |
| PS（保护软件） | 安全设计、安全配置 | 保护软件及其组件 |
| PS | 获取第三方组件 | 第三方安全验证 |
| PW（生产良好软件） | 安全编码、安全测试 | 开发安全软件 |
| PW | 代码审查 | 安全代码审查 |
| PW | 测试配置 | 安全配置测试 |
| RV（响应漏洞） | 漏洞识别与响应 | 持续漏洞管理 |
| RV | 漏洞修复与发布 | 快速安全修复 |

**SSDF 与 SSDF SP 800-218**
- SP 800-218V2：SSDF 推荐实践
- 与 Executive Order 14028 对齐
- 适用于联邦供应链安全要求
