# 第4章 数据流图（DFD）绘制

### 4.1 DFD基本元素

数据流图（Data Flow Diagram）是威胁建模的核心可视化工具。它通过简洁的图形符号描述系统中数据的流动、处理和存储情况，帮助团队系统性地识别威胁。

#### 4.1.1 外部实体（External Entity）

**符号：** 矩形

**定义：** 位于系统边界之外，与系统进行数据交互的人、组织或其他系统。外部实体是数据的来源或目的地。

**示例：**
- 用户（Web用户、移动端用户、管理员）
- 第三方系统（支付网关、短信服务、OAuth提供商）
- 外部数据库或服务
- 运维人员

**标识要点：**
- 给每个外部实体一个清晰的名称
- 明确外部实体与系统的交互方式
- 标注外部实体的信任级别（可信/不可信）

#### 4.1.2 过程（Process）

**符号：** 圆形或圆角矩形（微软TMT中使用圆角矩形）

**定义：** 对数据进行处理、转换或计算的功能模块。过程接收输入数据，经过处理后产生输出数据。

**示例：**
- 用户认证过程
- 订单处理过程
- 数据加密过程
- API请求处理

**标识要点：**
- 过程名称应使用动词+名词的形式（如"验证用户身份"）
- 每个过程应有明确的输入和输出
- 过程的粒度要适中，既不过粗也不过细
- 可以编号（如P1、P2）便于引用

#### 4.1.3 数据存储（Data Store）

**符号：** 两条平行横线（或开口矩形）

**定义：** 数据持久化存储的地方，如数据库、文件系统、缓存等。数据存储是数据的"静止"状态。

**示例：**
- 用户数据库
- 订单表
- 配置文件
- 消息队列
- 缓存（Redis等）

**标识要点：**
- 标注数据存储的名称和类型（如"用户数据库（MySQL）"）
- 标识存储的敏感数据
- 标注数据存储的访问方式
- 可以编号（如D1、D2）便于引用

#### 4.1.4 数据流（Data Flow）

**符号：** 带箭头的直线

**定义：** 数据在外部实体、过程和数据存储之间的流动。箭头表示数据流动的方向。

**示例：**
- 登录请求（用户名、密码）
- 查询结果（用户信息）
- 支付请求（订单号、金额）
- API响应（JSON数据）

**标识要点：**
- 每个数据流都要有明确的描述
- 标注数据流包含的具体数据项
- 标识敏感数据（用特殊颜色或标记）
- 标注数据传输协议（HTTP/HTTPS、TCP等）
- 双向数据流可以用双向箭头

### 4.2 信任边界（Trust Boundary）

#### 4.2.1 什么是信任边界

**符号：** 虚线矩形或阴影区域

**定义：** 信任边界是分隔不同信任级别的区域的边界线。在边界一侧的数据是可信的，另一侧的数据是不可信的或信任级别不同。

**为什么信任边界重要：**
- 威胁最常发生在信任边界处
- 跨越信任边界的数据需要验证和检查
- 信任边界是部署安全控制的关键位置

#### 4.2.2 常见的信任边界类型

| 信任边界类型 | 描述 | 示例 |
|-------------|------|------|
| **网络边界** | 不同安全级别的网络之间 | 互联网→DMZ、DMZ→内网 |
| **用户-系统边界** | 用户输入与系统处理之间 | Web浏览器→Web服务器 |
| **应用-数据边界** | 应用逻辑与数据存储之间 | 应用服务器→数据库 |
| **进程边界** | 不同进程或服务之间 | 微服务A→微服务B |
| **权限边界** | 不同权限级别之间 | 普通用户→管理员功能 |

#### 4.2.3 信任边界的识别方法

1. **找输入点**：所有来自外部的输入都是信任边界的穿越点
2. **找权限变化**：普通用户访问管理员功能时跨越权限边界
3. **找网络分段**：防火墙两侧是不同的信任区域
4. **找数据流向**：数据从低可信区流向高可信区时需要验证
5. **问"信任吗？"**：对每个数据源问"我们信任这些数据吗？"

#### 4.2.4 信任边界的标注规范

- 使用虚线框表示信任边界
- 给信任边界命名，说明其含义
- 标注边界两侧的信任级别
- 确保所有跨越边界的数据流都被识别

### 4.3 DFD层次结构

DFD采用分层的方式绘制，从宏观到微观逐步细化。

#### 4.3.1 上下文图（Context Diagram）

**又称：** 0层图（Level 0）的上一级，有时也称为-1层图

**描述：** 最高层次的DFD，将整个系统表示为一个单一的过程，展示系统与外部实体之间的交互。

**用途：**
- 明确系统边界
- 识别所有外部交互方
- 展示系统的宏观输入输出

**示例：**
```
          ┌─────────────┐
   用户 →  │             │ → 支付系统
          │  电商系统    │
  管理员 → │             │ → 物流系统
          └─────────────┘
```

#### 4.3.2 0层图（Level 0 DFD）

**描述：** 将上下文图中的单一过程展开为主要的子过程和数据存储，展示系统的主要功能模块和核心数据流。

**用途：**
- 展示系统的主要组成部分
- 识别核心业务流程
- 为进一步细化提供框架

**示例：**
```
  用户 ──→ ┌──────────┐    ┌──────────┐    ┌──────────┐ ←── 支付系统
           │ 用户认证  │ →  │ 订单管理  │ →  │ 支付处理  │
           └──────────┘    └────┬─────┘    └──────────┘
                                │
                                ↓
                           ┌──────────┐
                           │ 用户数据库│
                           └──────────┘
```

#### 4.3.3 1层图及细化图（Level 1+）

**描述：** 将0层图中的每个过程进一步展开，展示更详细的内部处理逻辑和数据流。

**细化原则：**
- 每个复杂的过程都可以展开为一张子图
- 子图的输入输出应与父过程保持一致（平衡原则）
- 细化到足够识别威胁的程度即可
- 简单的过程不需要再细化

**细化程度判断：**
- 当你能针对每个过程识别STRIDE威胁时，粒度就合适了
- 如果某个过程涉及多种不同的安全处理逻辑，应该继续细化
- 如果细化后不能发现更多威胁，就停止细化

### 4.5 绘制最佳实践

#### 4.5.1 DFD绘制原则

1. **从简到繁，逐步细化**
   - 先画上下文图，再画0层图，最后细化
   - 避免一开始就陷入细节

2. **保持图的平衡**
   - 子图的输入输出必须与父过程一致
   - 数据流必须有起点和终点

3. **命名清晰准确**
   - 过程使用"动词+名词"结构
   - 数据流描述具体的数据内容
   - 避免模糊的名称（如"处理数据"）

4. **每个图元素数量适中**
   - 单张图的过程数量控制在5-9个
   - 太多则需要分层或分组

5. **标注敏感数据**
   - 用特殊颜色或标记标注敏感数据流
   - 标注数据存储中的敏感数据

#### 4.5.2 常见错误

| 错误类型 | 示例 | 修正方法 |
|---------|------|---------|
| **控制流与数据流混淆** | 画了if-else分支 | DFD只画数据流，不画控制流 |
| **数据流没有方向** | 无箭头的连线 | 所有数据流都必须有箭头 |
| **过程命名不规范** | "用户管理"（太泛） | 改为"验证用户身份"等具体名称 |
| **遗漏信任边界** | 没有标注信任边界 | 识别所有外部输入和权限变化点 |
| **粒度过粗或过细** | 一个过程包含所有功能 | 按功能模块合理拆分 |
| **数据存储与过程混淆** | 把数据库画成过程 | 数据存储用平行四边形/双线 |

#### 4.5.3 效率提升技巧

- **使用模板**：建立常用架构的DFD模板
- **复用组件**：常见模块（如认证模块）可以复用
- **团队协作**：多人协作绘制，互相审查
- **版本管理**：对DFD文件进行版本控制
- **持续更新**：架构变化时及时更新DFD

### 4.6 常见架构的DFD示例

#### 4.6.1 典型Web应用架构

```
信任边界：互联网
┌─────────────────────────────────────────────────────────┐
│  外部实体          过程              数据存储           │
│                                                       │
│  ┌──────┐     ┌────────────┐     ┌──────────────┐    │
│  │ 用户  │ →→  │ Web前端     │ →→  │ 用户会话存储  │    │
│  └──────┘     └─────┬──────┘     └──────────────┘    │
│                      │                                │
│                      ↓                                │
│                ┌────────────┐     ┌──────────────┐    │
│                │ 应用服务器  │ →→  │ 用户数据库    │    │
│                └─────┬──────┘     └──────────────┘    │
│                      │                                │
│                      ↓                                │
│                ┌────────────┐                         │
│                │ 缓存层     │                         │
│                └────────────┘                         │
└─────────────────────────────────────────────────────────┘
信任边界：内部网络
```

**关键信任边界：**
- 用户与Web前端之间（互联网边界）
- Web前端与应用服务器之间
- 应用服务器与数据库之间

#### 4.6.2 微服务架构

```
           ┌─────────┐
           │  用户    │
           └────┬────┘
                ↓
        ┌───────────────┐
        │   API网关      │ ← 信任边界1
        └───────┬───────┘
                │
    ┌───────────┼───────────┐
    ↓           ↓           ↓
┌───────┐  ┌───────┐  ┌───────┐
│用户服务│  │订单服务│  │支付服务│
└───┬───┘  └───┬───┘  └───┬───┘
    │          │          │
    ↓          ↓          ↓
┌───────┐  ┌───────┐  ┌───────┐
│用户DB  │  │订单DB  │  │支付DB  │
└───────┘  └───────┘  └───────┘
```

**关键威胁点：**
- API网关的认证与授权
- 服务间通信的安全
- 服务间的信任边界
- 数据一致性与完整性

#### 4.6.3 移动应用架构

```
┌──────────┐     ┌──────────────┐     ┌──────────────┐
│ 移动App  │ →→  │  API服务器    │ →→  │  后端数据库   │
└──────────┘     └──────────────┘     └──────────────┘
     ↑                  ↑
     │                  │
┌──────────┐     ┌──────────────┐
│ 推送服务  │     │ 第三方服务    │
└──────────┘     └──────────────┘
```

**关键威胁点：**
- App本地存储安全
- API接口认证（防止重放、篡改）
- 反编译与代码篡改
- 不安全的第三方SDK
