# 第3章 威胁建模完整流程

### 3.1 第1步：明确安全目标

威胁建模的第一步是明确"我们要保护什么"和"保护到什么程度"。没有明确的安全目标，威胁建模就会失去方向。

#### 3.1.1 业务目标识别

首先要理解系统的业务目标，因为安全是为业务服务的。

**需要回答的问题：**
- 系统提供什么核心业务功能？
- 哪些功能是业务关键功能？
- 系统服务的用户群体是谁？
- 业务连续性要求是什么？
- 最大的业务风险是什么？

**输出物：**
- 业务功能清单
- 关键业务流程
- 业务优先级排序

#### 3.1.2 安全需求定义

基于业务目标，推导出安全需求。

**常见安全需求类别：**

| 安全需求类别 | 示例 |
|-------------|------|
| **身份认证** | 用户必须通过多因素认证才能登录 |
| **访问控制** | 普通用户不能访问管理后台 |
| **数据保密** | 用户密码必须加密存储 |
| **数据完整** | 交易数据必须防篡改 |
| **审计日志** | 所有敏感操作必须记录日志 |
| **可用性** | 系统可用性需达到99.9% |
| **不可否认** | 关键操作需要电子签名确认 |

**方法：**
- 参考安全需求框架（如NIST SP 800-53）
- 从历史安全事件中提炼需求
- 参照行业最佳实践

#### 3.1.3 合规要求梳理

不同行业有不同的合规要求，这些都是安全目标的重要来源。

**常见合规标准：**
- **网络安全等级保护2.0**（中国）
- **PCI DSS**（支付卡行业）
- **HIPAA**（医疗健康）
- **GDPR**（欧盟数据保护）
- **ISO 27001**（信息安全管理体系）
- **SOC 2**（服务组织控制）

**梳理方法：**
1. 确定适用的合规标准
2. 提取与待建系统相关的控制要求
3. 将合规要求转化为具体的安全需求
4. 标注合规要求的优先级（必须/建议/可选）

#### 3.1.4 资产价值评估

识别系统中的关键资产，并评估其价值，为后续风险评估提供依据。

**资产分类：**

| 资产类型 | 示例 |
|---------|------|
| **数据资产** | 用户信息、交易数据、知识产权、配置信息 |
| **功能资产** | 核心业务功能、管理功能、API接口 |
| **系统资产** | 服务器、数据库、网络设备 |
| **声誉资产** | 品牌形象、用户信任 |

**评估维度：**
- **机密性价值**：数据泄露造成的损失
- **完整性价值**：数据被篡改造成的损失
- **可用性价值**：服务不可用造成的损失

**资产价值分级示例：**
- **极高（Critical）**：泄露或损坏将造成重大业务损失，如用户密码、支付信息
- **高（High）**：重要业务数据，如用户个人信息、交易记录
- **中（Medium）**：一般业务数据，如用户偏好设置、日志数据
- **低（Low）**：公开信息，如产品介绍、帮助文档

### 3.2 第2步：系统图与架构图绘制

在明确安全目标后，需要清晰地描述系统的结构和数据流动，为威胁识别提供基础。

#### 3.2.1 数据流图（DFD）绘制方法

数据流图（Data Flow Diagram, DFD）是威胁建模的核心工具。它展示了数据如何在系统中流动、处理和存储。

**DFD的四种基本元素：**

| 元素 | 符号 | 含义 | 示例 |
|------|------|------|------|
| **外部实体** | 矩形 | 系统外部的人或系统 | 用户、第三方支付系统 |
| **过程** | 圆形/圆角矩形 | 对数据进行处理的功能模块 | 登录验证、订单处理 |
| **数据存储** | 两条平行线 | 数据持久化存储的地方 | 用户数据库、文件存储 |
| **数据流** | 箭头 | 数据在各元素之间的流动 | 登录请求、查询结果 |

**绘制步骤：**
1. 从上下文图（Context Diagram）开始，展示系统与外部实体的交互
2. 展开0层DFD，将系统分解为主要的过程和数据存储
3. 逐步细化，对复杂的过程绘制更详细的子图
4. 标注每个数据流的数据内容
5. 识别并标注信任边界

#### 3.2.2 信任边界识别

信任边界（Trust Boundary）是指不同信任级别的区域之间的分界线。在信任边界两侧，数据的可信度不同。

**常见的信任边界：**
- 互联网与内部网络之间（防火墙）
- 用户与系统之间（用户输入不可信）
- 前端与后端之间（客户端数据不可信）
- 应用服务器与数据库之间
- 内部系统与第三方系统之间

**为什么信任边界重要：**
- 威胁通常发生在信任边界处
- 跨越信任边界的数据需要进行验证
- 信任边界是安全控制的部署点

**识别方法：**
- 问"数据从哪里来？可信吗？"
- 检查不同权限等级的区域之间的交互
- 识别所有外部输入点

#### 3.2.3 系统组件与数据流标识

**组件标识要点：**
- 列出所有的系统组件（服务、模块、数据库等）
- 标注每个组件的功能和职责
- 标注组件的技术栈和版本
- 标识组件的部署位置（内网/外网/云端）

**数据流标识要点：**
- 每个数据流都要有明确的起点和终点
- 标注数据流包含的数据内容
- 标识敏感数据（PII、支付信息、密码等）
- 标注数据传输协议（HTTP/HTTPS、TCP等）

#### 3.2.4 外部依赖与接口

**外部依赖清单：**
- 第三方API服务（支付、短信、地图等）
- 第三方库和框架
- 外部系统集成
- 云服务（OSS、CDN、数据库服务等）

**接口梳理：**
- 对外提供的API接口
- 调用外部系统的接口
- 内部各模块之间的接口
- 管理接口和运维接口

**每个接口需要记录：**
- 接口名称和功能
- 通信协议和方式
- 认证方式
- 输入输出数据格式
- 敏感数据标识

### 3.3 第3步：威胁识别与枚举

基于系统图和架构图，系统性地识别可能存在的威胁。

#### 3.3.1 基于STRIDE的威胁枚举

使用STRIDE方法，对每个数据流图元素逐一分析可能存在的威胁。

**STRIDE-per-Element方法：**

| DFD元素 | Spoofing | Tampering | Repudiation | Information Disclosure | DoS | Elevation of Privilege |
|---------|----------|-----------|-------------|----------------------|-----|----------------------|
| **外部实体** | ✓ | | ✓ | | | |
| **过程** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| **数据存储** | | ✓ | ✓ | ✓ | ✓ | |
| **数据流** | | ✓ | | ✓ | ✓ | |
| **信任边界** | ✓ | ✓ | | ✓ | | ✓ |

**操作步骤：**
1. 取一个DFD元素（如"用户登录"过程）
2. 对照STRIDE的六个类别，逐一思考是否存在对应的威胁
3. 记录识别到的威胁
4. 对下一个元素重复上述过程

**威胁描述模板：**
```
威胁ID：T-001
威胁名称：SQL注入导致用户数据泄露
威胁类型：Information Disclosure（信息泄露）
涉及元素：登录过程（过程P1）、用户数据库（数据存储D1）
威胁描述：攻击者在登录表单中注入恶意SQL语句，绕过认证并获取用户表中的所有数据
影响资产：用户账号信息、密码哈希
```

#### 3.3.2 威胁库与检查清单

除了STRIDE方法，还可以参考以下威胁库和检查清单来补充威胁识别：

**OWASP Top 10：**
- 注入（Injection）
- 失效的身份认证（Broken Authentication）
- 敏感数据泄露（Sensitive Data Exposure）
- XML外部实体（XXE）
- 失效的访问控制（Broken Access Control）
- 安全配置错误（Security Misconfiguration）
- 跨站脚本（XSS）
- 不安全的反序列化（Insecure Deserialization）
- 使用含有已知漏洞的组件（Using Components with Known Vulnerabilities）
- 不足的日志记录和监控（Insufficient Logging & Monitoring）

**CWE（Common Weakness Enumeration）：**
- CWE-79：跨站脚本（XSS）
- CWE-89：SQL注入
- CWE-78：OS命令注入
- CWE-287：不正确的身份认证
- CWE-352：跨站请求伪造（CSRF）

**检查清单示例：**
- [ ] 所有用户输入是否都经过验证？
- [ ] 敏感数据是否加密存储？
- [ ] 密码是否使用了安全的哈希算法？
- [ ] 是否存在水平越权和垂直越权的可能？
- [ ] 错误信息是否会泄露系统内部信息？
- [ ] 会话管理是否安全？
- [ ] 是否有CSRF防护措施？
- [ ] 第三方组件是否存在已知漏洞？

#### 3.3.3 攻击树方法

攻击树（Attack Tree）是一种树形结构，用于描述攻击目标和实现该目标的各种可能路径。

**攻击树的结构：**
- **根节点**：攻击目标（如"获取管理员权限"）
- **中间节点**：子目标或中间步骤
- **叶子节点**：具体的攻击方法

**示例：获取用户账号密码的攻击树**
```
获取用户账号密码
├── 网络窃取
│   ├── 中间人攻击窃取明文密码
│   ├── 嗅探未加密的登录请求
│   └── 钓鱼网站诱导用户输入
├── 数据库获取
│   ├── SQL注入获取密码哈希
│   ├── 直接访问数据库（弱口令）
│   └── 备份文件泄露
├── 本地获取
│   ├── 键盘记录器
│   ├── 浏览器密码管理器窃取
│   └── 社会工程学
└── 暴力破解
    ├── 字典攻击
    ├── 暴力破解弱密码
    └── 密码重用攻击
```

**攻击树的价值：**
- 可视化攻击路径，便于理解和沟通
- 帮助识别系统的薄弱环节
- 可以计算攻击的成本和概率
- 为缓解措施设计提供依据

### 3.4 第4步：风险评估与排序

识别出所有威胁后，需要评估每个威胁的风险等级，确定处理优先级。

#### 3.4.1 风险计算方法

**风险 = 可能性 × 影响**

**可能性（Likelihood）评估：**

| 等级 | 描述 | 评分 |
|------|------|------|
| 几乎确定 | 大多数情况下都会发生 | 5 |
| 很可能 | 多数情况下可能发生 | 4 |
| 可能 | 在某些情况下会发生 | 3 |
| 不太可能 | 在特殊情况下才会发生 | 2 |
| 罕见 | 几乎不可能发生 | 1 |

**影响（Impact）评估：**

| 等级 | 描述 | 评分 |
|------|------|------|
| 灾难性 | 系统瘫痪、重大数据泄露、巨额财务损失 | 5 |
| 严重 | 重要功能不可用、敏感数据泄露、重大业务影响 | 4 |
| 中等 | 部分功能受影响、一般数据泄露、中等业务影响 | 3 |
| 轻微 | 轻微影响、非敏感数据泄露、有限业务影响 | 2 |
| 可忽略 | 几乎无影响 | 1 |

**风险矩阵：**

| 可能性\影响 | 可忽略(1) | 轻微(2) | 中等(3) | 严重(4) | 灾难性(5) |
|------------|----------|---------|---------|---------|----------|
| **罕见(1)** | 1 | 2 | 3 | 4 | 5 |
| **不太可能(2)** | 2 | 4 | 6 | 8 | 10 |
| **可能(3)** | 3 | 6 | 9 | 12 | 15 |
| **很可能(4)** | 4 | 8 | 12 | 16 | 20 |
| **几乎确定(5)** | 5 | 10 | 15 | 20 | 25 |

#### 3.4.2 优先级排序

**风险等级划分：**

| 风险值 | 等级 | 颜色 | 处理要求 |
|--------|------|------|---------|
| 20-25 | 极高（Critical） | 红色 | 必须立即修复，否则系统不能上线 |
| 13-19 | 高（High） | 橙色 | 必须在上线前修复，或有明确的补偿控制 |
| 7-12 | 中（Medium） | 黄色 | 应在合理时间内修复，可排入开发计划 |
| 2-6 | 低（Low） | 蓝色 | 可接受或安排修复 |
| 1 | 可忽略（Negligible） | 绿色 | 无需处理 |

**排序输出示例：**

| 威胁ID | 威胁名称 | 可能性 | 影响 | 风险值 | 等级 | 优先级 |
|--------|---------|--------|------|--------|------|--------|
| T-001 | SQL注入获取用户数据 | 4 | 5 | 20 | 极高 | P0 |
| T-002 | 未授权访问管理接口 | 3 | 5 | 15 | 高 | P1 |
| T-003 | 密码明文传输 | 4 | 4 | 16 | 高 | P1 |
| T-004 | 暴力破解用户账号 | 3 | 3 | 9 | 中 | P2 |
| T-005 | 错误信息泄露版本号 | 5 | 1 | 5 | 低 | P3 |

#### 3.4.3 风险接受准则

并非所有风险都需要缓解。对于某些风险，可以根据以下准则决定是否接受：

**可接受风险的条件：**
1. 风险等级为低或可忽略
2. 缓解成本远高于风险造成的损失
3. 有其他补偿控制措施
4. 业务需求优先，且管理层知情并批准

**风险接受流程：**
- 记录风险接受的原因
- 评估剩余风险
- 获得管理层批准
- 定期回顾接受的风险

**风险处置策略：**
- **缓解（Mitigate）**：采取措施降低风险
- **转移（Transfer）**：将风险转移给第三方（如保险、外包）
- **接受（Accept）**：知情并接受风险
- **避免（Avoid）**：放弃导致风险的功能或活动

### 3.5 第5步：缓解措施设计

针对识别出的威胁，设计相应的缓解措施。

#### 3.5.1 对应每个威胁的缓解策略

**STRIDE威胁对应的通用缓解策略：**

| 威胁类型 | 缓解策略 | 具体措施示例 |
|---------|---------|-------------|
| **Spoofing（仿冒）** | 强身份认证 | 多因素认证、证书认证、OAuth |
| **Tampering（篡改）** | 完整性保护 | 数字签名、消息认证码、哈希校验 |
| **Repudiation（抵赖）** | 审计追踪 | 详细日志、数字签名、时间戳 |
| **Information Disclosure（信息泄露）** | 保密控制 | 加密、访问控制、数据脱敏 |
| **Denial of Service（拒绝服务）** | 可用性保护 | 限流、熔断、冗余、DDoS防护 |
| **Elevation of Privilege（权限提升）** | 授权控制 | 最小权限原则、权限校验、RBAC |

#### 3.5.2 安全控制选择

**安全控制的类型：**

| 控制类型 | 作用 | 示例 |
|---------|------|------|
| **预防性控制** | 防止威胁发生 | 防火墙、输入验证、访问控制 |
| **检测性控制** | 检测威胁的发生 | 入侵检测系统、日志监控、告警 |
| **纠正性控制** | 减轻威胁的影响 | 备份恢复、应急响应、漏洞修复 |

**控制选择原则：**
1. **深度防御**：多层防护，避免单点失效
2. **最小权限**：只授予必要的权限
3. **纵深防御**：技术控制+管理控制+物理控制
4. **成本效益**：控制成本不超过风险损失

#### 3.5.3 缓解有效性评估

在设计缓解措施后，需要评估其有效性：

**评估维度：**
- **有效性**：能在多大程度上降低风险？
- **可行性**：技术上是否可行？开发成本如何？
- **性能影响**：对系统性能有多大影响？
- **用户体验**：对用户体验有多大影响？
- **可维护性**：后续维护是否方便？

**残留风险评估：**
```
原始风险：极高（20分）
缓解措施：输入验证 + 参数化查询 + WAF
缓解后风险：低（3分）
残留风险：可接受
```

### 3.6 第6步：验证与迭代

威胁建模不是一次性的活动，而是一个持续迭代的过程。

#### 3.6.1 威胁建模评审

**评审内容：**
- 系统图是否完整准确？
- 威胁识别是否全面？
- 风险评估是否合理？
- 缓解措施是否有效可行？
- 是否有遗漏的威胁？

**评审方式：**
- 团队内部评审
- 安全团队评审
- 跨部门评审
- 外部专家评审

#### 3.6.2 实施验证

**验证缓解措施是否落地：**
- 安全代码审查（SAST）
- 安全测试（DAST、渗透测试）
- 配置核查
- 日志审计

**验证方法：**
- 针对每个威胁，设计测试用例验证缓解措施
- 对比威胁建模报告和实际实现
- 定期抽查和回归测试

#### 3.6.3 定期更新

**触发更新的条件：**
- 新功能上线
- 架构重大调整
- 发现新的威胁类型
- 发生安全事件
- 定期回顾（每季度/每半年）

**更新流程：**
1. 评估变化对威胁模型的影响
2. 更新系统图和架构图
3. 重新识别和评估威胁
4. 更新缓解措施
5. 记录变更历史
