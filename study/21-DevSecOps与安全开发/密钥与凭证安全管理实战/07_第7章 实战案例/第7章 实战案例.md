# 第7章 实战案例

### 7.1 案例1：使用HashiCorp Vault统一管理密钥

#### 7.1.1 场景描述

某中型互联网公司面临以下问题：
- 各项目团队独立管理凭证，缺乏统一标准
- 多个项目存在硬编码凭证的情况
- 人员流动时凭证轮换困难
- 缺乏完整的审计追踪
- 合规审计无法通过

#### 7.1.2 解决方案设计

**架构设计：**
```
┌─────────────────────────────────────────────────────────┐
│                    HashiCorp Vault                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌─────────┐ │
│  │  KV v2   │  │ Database │  │  AWS     │  │  PKI    │ │
│  │ Secrets  │  │ Secrets  │  │  Secrets │  │  Secrets│ │
│  └──────────┘  └──────────┘  └──────────┘  └─────────┘ │
│  ┌──────────────────────────────────────────────────┐   │
│  │              Auth Methods                        │   │
│  │  AppRole  OIDC  LDAP  Kubernetes  Token         │   │
│  └──────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
           │              │              │
     ┌─────▼─────┐  ┌────▼─────┐  ┌─────▼──────┐
     │  Web应用   │  │ CI/CD    │  │  运维工具   │
     │  (AppRole)│  │ (JWT/OIDC)│  │  (LDAP)    │
     └───────────┘  └──────────┘  └────────────┘
```

**实施步骤：**

**Step 1：部署Vault集群**
```bash
# 使用Raft存储后端部署3节点集群
# 生产环境配置
cat > vault-config.hcl << 'EOF'
cluster_name = "prod-vault"

storage "raft" {
  path = "/opt/vault/data"
  node_id = "vault-01"
  retry_join {
    leader_api_addr = "https://vault-02.example.com:8200"
  }
  retry_join {
    leader_api_addr = "https://vault-03.example.com:8200"
  }
}

listener "tcp" {
  address       = "0.0.0.0:8200"
  tls_cert_file = "/etc/vault/tls/vault.crt"
  tls_key_file  = "/etc/vault/tls/vault.key"
}

api_addr = "https://vault-01.example.com:8200"
cluster_addr = "https://vault-01.example.com:8201"
ui = true
EOF
```

**Step 2：配置认证方式**
```bash
# 启用AppRole认证（用于服务/应用）
vault auth enable approle

# 创建应用角色
vault write auth/approle/role/payment-service \
  token_policies="payment-service-policy" \
  token_ttl=1h \
  token_max_ttl=4h \
  secret_id_ttl=24h \
  secret_id_num_uses=0

# 获取RoleID和SecretID
vault read auth/approle/role/payment-service/role-id
vault write -f auth/approle/role/payment-service/secret-id

# 启用Kubernetes认证（用于K8s Pod）
vault auth enable kubernetes

vault write auth/kubernetes/config \
  kubernetes_host="https://k8s-api.example.com:6443" \
  kubernetes_ca_cert=@ca.crt
```

**Step 3：定义策略**
```hcl
# payment-service-policy.hcl
path "kv/data/payment/*" {
  capabilities = ["read"]
}

path "database/creds/payment-readonly" {
  capabilities = ["read"]
}

path "transit/encrypt/payment-data" {
  capabilities = ["update"]
}

path "transit/decrypt/payment-data" {
  capabilities = ["update"]
}
```

**Step 4：应用集成**
```python
# vault_integration.py
import hvac
import os

class VaultClient:
    def __init__(self):
        self.client = hvac.Client(
            url=os.environ.get('VAULT_ADDR', 'https://vault.example.com:8200'),
            verify='/etc/ssl/certs/ca-bundle.crt'
        )
        self._authenticate()
    
    def _authenticate(self):
        """使用AppRole认证"""
        role_id = os.environ['VAULT_ROLE_ID']
        secret_id = os.environ['VAULT_SECRET_ID']
        self.client.auth.approle.login(
            role_id=role_id,
            secret_id=secret_id
        )
    
    def get_secret(self, path: str) -> dict:
        """读取KV密钥"""
        response = self.client.secrets.kv.v2.read_secret_version(path=path)
        return response['data']['data']
    
    def get_db_credentials(self, role: str) -> tuple:
        """获取动态数据库凭证"""
        response = self.client.secrets.database.generate_credentials(name=role)
        return response['data']['username'], response['data']['password']
    
    def encrypt(self, plaintext: str, key_name: str) -> str:
        """使用Transit引擎加密"""
        response = self.client.secrets.transit.encrypt_data(
            name=key_name,
            plaintext=plaintext.encode().hex()
        )
        return response['data']['ciphertext']
```

#### 7.1.3 实施效果

- 实现了全公司凭证的统一管理
- 所有凭证访问有完整审计记录
- 应用凭证实现动态生成和自动过期
- 支持人员流动时的快速凭证回收
- 顺利通过等保三级和ISO 27001审计

### 7.2 案例2：GitHub Actions凭证安全配置

#### 7.2.1 场景描述

某公司使用GitHub Actions作为CI/CD工具，需要部署到AWS和多个云环境。最初使用静态AWS Access Key存储在GitHub Secrets中，存在以下风险：
- 密钥长期有效，泄露风险大
- 无法精细控制权限
- 缺乏使用审计

#### 7.2.2 OIDC联邦配置

**AWS端配置：**
```terraform
# 配置GitHub OIDC Provider
resource "aws_iam_openid_connect_provider" "github" {
  url             = "https://token.actions.githubusercontent.com"
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = ["6938fd4d98bab03faadb97b34396831e3780aea1"]
}

# 创建部署角色
resource "aws_iam_role" "github_actions_deploy" {
  name = "github-actions-deploy-role"
  
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Principal = {
          Federated = aws_iam_openid_connect_provider.github.arn
        }
        Action = "sts:AssumeRoleWithWebIdentity"
        Condition = {
          StringEquals = {
            "token.actions.githubusercontent.com:aud" = "sts.amazonaws.com"
            "token.actions.githubusercontent.com:sub" = "repo:myorg/myrepo:environment:production"
          }
        }
      }
    ]
  })
}

# 附加部署权限策略
resource "aws_iam_role_policy_attachment" "deploy" {
  role       = aws_iam_role.github_actions_deploy.name
  policy_arn = aws_iam_policy.deploy_policy.arn
}
```

**GitHub Actions工作流配置：**
```yaml
name: Production Deployment

on:
  push:
    branches: [main]

permissions:
  contents: read
  id-token: write    # 必须有这个权限才能获取OIDC令牌

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Configure AWS credentials via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-deploy-role
          aws-region: us-east-1
          role-session-name: github-actions-deploy
      
      - name: Deploy to ECS
        run: |
          aws ecs update-service \
            --cluster production \
            --service myapp \
            --force-new-deployment
```

#### 7.2.3 额外安全措施

1. **环境保护规则**：生产环境部署需要手动审批
2. **分支保护**：只有main分支可以部署到生产环境
3. **最小权限**：部署角色只拥有部署所需的最小权限
4. **审计日志**：所有角色假设操作记录在CloudTrail中
5. **会话时间限制**：设置合理的角色会话时长（如1小时）

### 7.3 案例3：凭证泄露事件应急响应

#### 7.3.1 事件背景

某SaaS公司安全团队收到GitGuardian告警，发现公司内部GitHub仓库的一个私有仓库中泄露了生产环境的AWS Access Key。该密钥具有S3全量访问权限，而公司的用户数据存储在S3中。

#### 7.3.2 应急响应过程

**T+0分钟：发现与确认**
- GitGuardian自动告警，安全团队收到通知
- 确认泄露的密钥ID：AKIAIOSFODNN7EXAMPLE
- 确认密钥权限：AmazonS3FullAccess
- 确认泄露位置：开源的内部工具项目中的config.py文件

**T+5分钟：遏制措施**
```bash
# 立即禁用泄露的AWS密钥
aws iam update-access-key \
  --access-key-id AKIAIOSFODNN7EXAMPLE \
  --status Inactive \
  --user-name prod-deployment-user

# 查看该密钥的最近使用记录
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIAIOSFODNN7EXAMPLE \
  --start-time $(date -d '7 days ago' +%s) \
  --max-results 50
```

**T+15分钟：影响评估**
- 检查CloudTrail日志，确认该密钥在过去24小时内的使用情况
- 发现来自陌生IP（45.x.x.x）的多次S3 List和Get操作
- 确认攻击者访问了约5个存储桶
- 初步估计可能泄露的数据量约100GB用户数据

**T+30分钟：深度遏制**
- 立即删除泄露的IAM用户密钥
- 创建新的密钥并更新所有合法使用点
- 临时限制S3访问，只允许白名单IP访问
- 启用S3访问日志的实时分析
- 保存所有相关日志用于取证

**T+1小时：调查分析**
- 追溯代码提交历史，确认凭证是在3个月前的一次重构中被提交
- 提交者为已离职员工，当时未做代码审查
- 仓库是在1周前被意外设为公开（原因为配置错误）
- 攻击者通过GitHub搜索功能发现了该密钥

**T+2小时：根因分析**
- 直接原因：代码中硬编码AWS密钥 + 仓库意外公开
- 根本原因：
  - 缺乏代码凭证扫描机制
  - 仓库权限管理不严格
  - 新员工安全培训不到位
  - 缺乏基础设施即代码的权限管理

**T+24小时：恢复与改进**
- 确认数据泄露范围，通知受影响用户
- 全面审查所有代码仓库的凭证情况
- 部署Gitleaks到所有CI/CD流水线
- 实施最小权限策略，缩减AWS密钥权限
- 建立代码审查流程和安全检查卡点
- 加强员工安全意识培训

#### 7.3.3 经验总结

1. **预防胜于治疗**：建立前置的凭证扫描机制远比事后响应更有效
2. **最小权限原则**：即使密钥泄露，限制权限也能降低损失
3. **监控与告警**：快速发现是减少损失的关键
4. **流程保障**：不能依赖个人意识，必须有流程和工具保障
5. **定期演练**：定期进行应急响应演练，确保团队熟悉流程
