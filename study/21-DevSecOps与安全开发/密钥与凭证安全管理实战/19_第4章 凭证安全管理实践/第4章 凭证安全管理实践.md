# 第4章 凭证安全管理实践

### 4.1 环境变量与配置管理

#### 4.1.1 环境变量的安全使用

环境变量是将配置与代码分离的常用方式，但如果处理不当，仍然存在安全风险。

**最佳实践：**

1. **使用.env文件 + .gitignore**
   ```
   # .gitignore
   .env
   .env.local
   .env.*.local
   *.key
   *.pem
   ```

2. **提供.env.example模板**
   ```
   # .env.example - 只包含键名和占位符，不包含真实值
   DB_HOST=localhost
   DB_PORT=5432
   DB_USER=your_username
   DB_PASSWORD=your_secure_password
   API_KEY=your_api_key_here
   ```

3. **环境变量分级管理**
   - 开发环境（development）：使用本地开发凭证
   - 测试环境（staging）：使用测试环境专用凭证
   - 生产环境（production）：使用生产环境凭证，严格控制访问

#### 4.1.2 配置文件加密方案

对于必须存储在文件中的敏感配置，应采用加密保护。

**方案一：git-crypt**
```bash
# 安装git-crypt
brew install git-crypt  # macOS
apt install git-crypt   # Ubuntu

# 初始化仓库
git-crypt init

# 配置加密规则（.gitattributes）
secretfile filter=git-crypt diff=git-crypt
*.key filter=git-crypt diff=git-crypt
.env.prod filter=git-crypt diff=git-crypt

# 添加GPG密钥授权
git-crypt add-gpg-user user@example.com
```

**方案二：SOPS（Secrets OPerationS）**
```bash
# 使用AWS KMS加密配置文件
sops --encrypt --kms arn:aws:kms:us-east-1:123456789:key/abc123 secrets.yaml > secrets.enc.yaml

# 解密并编辑
sops secrets.enc.yaml

# 集成到CI/CD
sops --decrypt secrets.enc.yaml > secrets.yaml
```

#### 4.1.3 应用启动时的凭证注入

**Docker容器凭证注入：**
```bash
# 危险：在镜像构建时嵌入凭证
ENV DB_PASSWORD=super_secret  # 会保存在镜像历史中

# 安全：运行时注入环境变量
docker run -e DB_PASSWORD=$(vault read -field=password secret/db) myapp

# 更安全：使用Docker Secrets（Swarm模式）
docker secret create db_password password.txt
docker service create --secret db_password myapp
```

**Kubernetes凭证管理：**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp
spec:
  containers:
  - name: myapp
    image: myapp:latest
    env:
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: password
    volumeMounts:
    - name: secret-volume
      mountPath: /etc/secrets
      readOnly: true
  volumes:
  - name: secret-volume
    secret:
      secretName: app-secrets
```

### 4.2 密钥管理服务详解

#### 4.2.1 AWS KMS实战

**创建客户托管密钥：**
```python
import boto3

kms = boto3.client('kms', region_name='us-east-1')

# 创建对称加密密钥
response = kms.create_key(
    Description='Application data encryption key',
    KeyUsage='ENCRYPT_DECRYPT',
    Origin='AWS_KMS',
    Tags=[
        {'TagKey': 'Environment', 'TagValue': 'Production'},
        {'TagKey': 'Application', 'TagValue': 'PaymentService'}
    ]
)

key_id = response['KeyMetadata']['KeyId']
print(f"Created key: {key_id}")

# 启用自动轮换
kms.enable_key_rotation(KeyId=key_id)
```

**使用KMS加密数据：**
```python
# 加密数据
ciphertext = kms.encrypt(
    KeyId=key_id,
    Plaintext=b'Sensitive data to encrypt',
    EncryptionContext={'Purpose': 'customer_data'}
)['CiphertextBlob']

# 解密数据
plaintext = kms.decrypt(
    CiphertextBlob=ciphertext,
    EncryptionContext={'Purpose': 'customer_data'}
)['Plaintext']
```

**信封加密（Envelope Encryption）：**
```python
# 生成数据密钥（DEK）
data_key = kms.generate_data_key(
    KeyId=key_id,
    KeySpec='AES_256'
)

# 明文DEK用于加密数据（本地加密）
plaintext_dek = data_key['Plaintext']
encrypted_dek = data_key['CiphertextBlob']

# 用DEK加密实际数据（使用AES等对称算法）
# encrypted_data = aes_encrypt(data, plaintext_dek)

# 存储：加密后的数据 + 加密后的DEK
# 下次使用时：先用KMS解密DEK，再用DEK解密数据
```

**KMS密钥策略配置：**
```json
{
  "Version": "2012-10-17",
  "Id": "key-policy-1",
  "Statement": [
    {
      "Sid": "Enable IAM policies",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::123456789012:root"},
      "Action": "kms:*",
      "Resource": "*"
    },
    {
      "Sid": "Allow application role to encrypt/decrypt",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::123456789012:role/app-role"},
      "Action": ["kms:Encrypt", "kms:Decrypt", "kms:GenerateDataKey"],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "kms:EncryptionContext:Purpose": "customer_data"
        }
      }
    }
  ]
}
```

#### 4.2.2 Azure Key Vault实战

**创建Key Vault并配置访问策略：**
```azurecli
# 创建Key Vault
az keyvault create \
  --name my-production-vault \
  --resource-group prod-rg \
  --location eastus \
  --enable-soft-delete true \
  --enable-purge-protection true \
  --sku premium

# 设置访问策略（为服务主体授予密钥权限）
az keyvault set-policy \
  --name my-production-vault \
  --spn http://my-app-service \
  --secret-permissions get list \
  --key-permissions encrypt decrypt sign verify
```

**在应用中使用Key Vault：**
```csharp
// 使用Azure.Identity和Azure.Security.KeyVault.Secrets
using Azure.Identity;
using Azure.Security.KeyVault.Secrets;

var client = new SecretClient(
    new Uri("https://my-production-vault.vault.azure.net/"),
    new DefaultAzureCredential()
);

// 读取密钥
KeyVaultSecret secret = client.GetSecret("DatabasePassword");
string password = secret.Value;

// 使用托管标识（Managed Identity）
// 部署到Azure资源时自动获取身份，无需配置凭证
```

#### 4.2.3 HashiCorp Vault实战部署

**Vault服务器部署：**
```bash
# 启动开发模式Vault（仅用于测试）
vault server -dev -dev-root-token-id=root

# 生产环境部署配置（config.hcl）
storage "raft" {
  path    = "./vault/data"
  node_id = "node1"
}

listener "tcp" {
  address     = "0.0.0.0:8200"
  tls_cert_file = "/etc/vault/tls/cert.pem"
  tls_key_file  = "/etc/vault/tls/key.pem"
}

api_addr = "https://vault.example.com:8200"
cluster_addr = "https://vault-node1.example.com:8201"

# 初始化Vault（生成解封密钥和Root Token）
vault operator init -key-shares=5 -key-threshold=3

# 解封Vault
vault operator unseal <key1>
vault operator unseal <key2>
vault operator unseal <key3>
```

**KV Secrets Engine使用：**
```bash
# 启用KV v2 Secrets Engine
vault secrets enable -version=2 kv

# 写入密钥
vault kv put kv/database/prod username=admin password=SuperSecret123!

# 读取密钥
vault kv get kv/database/prod

# 列出密钥
vault kv list kv/database/

# 查看密钥版本历史
vault kv metadata get kv/database/prod
```

**动态数据库凭证：**
```bash
# 启用数据库Secret Engine
vault secrets enable database

# 配置数据库连接
vault write database/config/my-postgresql \
  plugin_name=postgresql-database-plugin \
  allowed_roles="readonly,readwrite" \
  connection_url="postgresql://{{username}}:{{password}}@db.example.com:5432/appdb" \
  username="vault-admin" \
  password="admin-password"

# 创建只读角色
vault write database/roles/readonly \
  db_name=my-postgresql \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
  default_ttl="1h" \
  max_ttl="24h"

# 生成动态凭证
vault read database/creds/readonly
```

### 4.3 密码保险箱

#### 4.3.1 企业密码管理方案

密码保险箱是团队和企业管理共享凭证的重要工具。

**主流企业密码管理工具对比：**

| 特性 | 1Password Business | LastPass Enterprise | Bitwarden Enterprise |
|------|-------------------|---------------------|---------------------|
| 端到端加密 | 是（AES-256 + PBKDF2） | 是（AES-256 + PBKDF2） | 是（AES-256 + Argon2） |
| SSO集成 | 支持 | 支持 | 支持 |
| 多因素认证 | 支持 | 支持 | 支持 |
| 共享保险箱 | 支持 | 支持 | 支持 |
| 审计日志 | 完整 | 完整 | 完整 |
| API接口 | 丰富 | 丰富 | 开源友好 |
| 部署方式 | SaaS | SaaS | SaaS + 自托管 |

#### 4.3.2 1Password企业版实践

**1Password CLI集成到开发流程：**
```bash
# 安装1Password CLI
brew install --cask 1password-cli

# 登录账户
op signin mycompany.1password.com user@example.com

# 创建安全笔记存储服务器凭证
op item create --category=server --title="Production DB Server" \
  --vault="Engineering" \
  --url="db.prod.example.com" \
  --username="admin" \
  --password="SuperSecret123!"

# 从脚本中安全获取凭证
DB_PASSWORD=$(op item get "Production DB Server" --fields password)
```

#### 4.3.3 密码保险箱最佳实践

- **个人密码库与共享密码库分离**：个人凭证存入个人库，团队共享凭证存入专用共享库
- **最小权限共享**：只向需要的人授予访问权限，定期审查共享成员
- **强制MFA**：所有账户必须启用多因素认证
- **主密码策略**：设置强主密码要求，定期更换提醒
- **紧急访问机制**：设置紧急联系人，应对人员突发状况
- **离职流程自动化**：员工离职时自动撤销所有密码库访问权限

### 4.4 CI/CD流水线凭证管理

#### 4.4.1 CI/CD凭证风险点

CI/CD流水线通常拥有访问代码仓库、云平台、部署环境等多种高权限凭证，是攻击者的重点目标。

**常见风险：**
- 凭证硬编码在CI配置文件中
- Pipeline日志中泄露敏感信息
- 不安全的缓存配置导致凭证泄露
- 第三方CI插件窃取凭证
- 流水线权限过大，缺乏最小权限控制

#### 4.4.2 GitHub Actions凭证安全

**使用GitHub Secrets管理凭证：**
```yaml
name: Deploy to Production

on:
  push:
    branches: [main]

env:
  AWS_REGION: us-east-1

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production  # 环境保护规则
    permissions:
      contents: read
      id-token: write        # OIDC联邦所需权限
    
    steps:
      - uses: actions/checkout@v4
      
      # 使用OIDC方式获取AWS凭证（无需存储AK/SK）
      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-deploy
          aws-region: ${{ env.AWS_REGION }}
      
      # 使用GitHub Secrets
      - name: Deploy application
        env:
          DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
          API_KEY: ${{ secrets.PRODUCTION_API_KEY }}
        run: |
          ./deploy.sh
```

**GitHub Actions安全最佳实践：**
1. 使用OIDC（OpenID Connect）代替长期凭证
2. 为不同环境配置独立的Secrets和环境保护规则
3. 限制GITHUB_TOKEN的默认权限
4. 对敏感操作启用环境审批
5. 定期轮换存储的密钥
6. 审计Secrets的使用情况

#### 4.4.3 Jenkins凭证管理

**Jenkins凭证安全配置：**
1. 安装Credentials Binding Plugin
2. 使用凭据存储管理所有敏感信息
3. 配置凭据的访问范围和可见性
4. 启用Mask Passwords Plugin防止日志泄露
5. 定期审计凭据的使用情况

```groovy
// Jenkinsfile中安全使用凭证
pipeline {
    agent any
    
    environment {
        // 使用凭据ID引用，不在Jenkinsfile中明文存储
        AWS_CREDENTIALS = credentials('aws-prod-credentials')
        DOCKER_REGISTRY = credentials('docker-registry')
    }
    
    stages {
        stage('Build and Push') {
            steps {
                sh '''
                    docker login -u $DOCKER_REGISTRY_USR -p $DOCKER_REGISTRY_PSW
                    docker build -t myapp:latest .
                    docker push myapp:latest
                '''
            }
        }
    }
}
```
