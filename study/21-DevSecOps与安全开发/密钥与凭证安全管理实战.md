## 第1章 密钥与凭证安全概述

### 1.1 密钥与凭证的定义与分类

#### 1.1.1 基本定义

在现代IT系统中，密钥（Key）和凭证（Credential）是身份认证与数据保护的核心基石。理解它们的定义与分类是建立安全管理体系的第一步。

**密钥（Key）**：密钥是密码学运算中的关键参数，用于加密、解密、签名、验证等操作。密钥本身是一串随机或伪随机的二进制数据，其安全性直接决定了密码系统的安全强度。

**凭证（Credential）**：凭证是用于证明身份或获取访问权限的信息载体。凭证的范围比密钥更广，包括密码、API密钥、令牌、证书、生物特征信息等。

#### 1.1.2 密钥的分类

根据密码学体制分类：

| 类别 | 典型算法 | 密钥长度 | 主要用途 |
|------|----------|----------|----------|
| 对称密钥 | AES、DES、3DES、SM4 | 128/256位 | 数据加密、磁盘加密、通信加密 |
| 非对称密钥 | RSA、ECC、SM2 | 2048/4096位(RSA)、256位(ECC) | 身份认证、数字签名、密钥交换 |
| 哈希密钥 | HMAC-SHA256 | 可变 | 消息认证、完整性校验 |

根据密钥功能分类：

- **数据加密密钥（DEK）**：直接用于加密用户数据的密钥
- **密钥加密密钥（KEK）**：用于加密保护其他密钥的密钥
- **主密钥（Master Key）**：密钥层次结构的根密钥，保护整个密钥体系
- **会话密钥（Session Key）**：单次通信会话中临时使用的密钥
- **签名密钥（Signing Key）**：用于数字签名的私钥
- **验证密钥（Verification Key）**：用于验证数字签名的公钥

#### 1.1.3 凭证的分类

按凭证形态分类：

1. **知识类凭证**：密码、PIN码、安全问题答案
2. **持有类凭证**：智能卡、USB Key、硬件令牌
3. **生物特征凭证**：指纹、面部识别、虹膜扫描
4. **数字凭证**：API密钥、访问令牌、数字证书、SSH密钥

按使用场景分类：

- **用户凭证**：用户名密码、多因素认证因子
- **服务凭证**：API密钥、服务账户密码、数据库连接串
- **机器凭证**：SSH密钥、TLS证书、服务账户令牌
- **基础设施凭证**：云平台访问密钥、K8s Secret、CI/CD令牌

### 1.2 凭证泄露的风险与影响

#### 1.2.1 凭证泄露的典型场景

凭证泄露是企业安全事件中最常见也是最危险的类型之一。根据Verizon DBIR 2024报告，超过80%的数据泄露事件与凭证被盗或滥用有关。

**常见泄露场景：**

1. **硬编码凭证**：开发者将API密钥、数据库密码直接写入源代码
2. **配置文件泄露**：敏感配置文件（如.env、application.yml）被意外提交到代码仓库
3. **日志泄露**：应用日志中打印了完整的请求头、连接字符串等敏感信息
4. **内存dump泄露**：进程内存转储文件中包含明文凭证
5. **供应链攻击**：第三方依赖库或服务中的凭证泄露
6. **社交工程**：钓鱼邮件、假冒网站骗取用户凭证
7. **内部人员泄露**：离职员工带走敏感凭证，或内部人员恶意窃取

#### 1.2.2 凭证泄露的危害等级

| 泄露凭证类型 | 影响范围 | 潜在损失 | 紧急程度 |
|-------------|----------|----------|----------|
| 管理员密码 | 系统全量访问 | 极高 | P0 |
| 云平台AK/SK | 云资源全量控制 | 极高 | P0 |
| 数据库密码 | 数据泄露/篡改 | 高 | P1 |
| API密钥 | 服务滥用、数据泄露 | 高 | P1 |
| SSH私钥 | 服务器接管 | 高 | P1 |
| 普通用户密码 | 账户被盗 | 中 | P2 |
| 内部服务令牌 | 横向移动风险 | 中 | P2 |

#### 1.2.3 真实案例警示

**案例：2022年Uber数据泄露事件**

攻击者通过社交工程手段获取了Uber员工的Slack账户凭证，进而在Slack消息历史中发现了AWS访问密钥。利用这些密钥，攻击者访问了Uber的AWS环境，窃取了约5700万用户和司机的个人信息，最终Uber支付了1.48亿美元的和解金。

**案例：2023年Okta支持系统入侵事件**

攻击者通过窃取Okta客户支持团队员工的凭证，访问了Okta的支持案例管理系统，导致包括Cloudflare、1Password在内的多家知名企业客户数据被泄露。事件影响了超过134家Okta客户。

### 1.3 密钥管理生命周期

#### 1.3.1 生命周期模型

密钥管理遵循完整的生命周期管理模型，涵盖从生成到销毁的全过程。NIST SP 800-57标准定义了密钥生命周期的各个阶段。

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│  密钥生成 │───▶│ 密钥注册 │───▶│ 密钥分发 │───▶│ 密钥存储 │
└─────────┘    └─────────┘    └─────────┘    └────┬────┘
                                                  │
                                                  ▼
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│  密钥销毁 │◀───│ 密钥撤销 │◀───│ 密钥轮换 │◀───│ 密钥使用 │
└─────────┘    └─────────┘    └─────────┘    └─────────┘
```

#### 1.3.2 各阶段关键控制点

**密钥生成阶段：**
- 使用经过认证的随机数生成器（CSPRNG）
- 密钥长度符合当前安全标准（AES-256、RSA-3072+、ECC-256+）
- 密钥生成过程必须在安全环境中进行
- 生成后立即进行密钥质量检测

**密钥分发阶段：**
- 采用安全信道传输（TLS、SSH、加密邮件）
- 密钥分片分发（Shamir秘密共享）
- 双人控制原则（Dual Control）
- 分发过程全程审计记录

**密钥使用阶段：**
- 最小权限原则，按需授权
- 使用时解密，使用后立即从内存清除
- 禁止将密钥打印到日志或输出到控制台
- 密钥使用操作必须可审计

**密钥轮换阶段：**
- 制定明确的轮换周期策略
- 支持密钥版本管理，平滑过渡
- 轮换后旧密钥进入退役状态
- 数据重加密策略规划

**密钥销毁阶段：**
- 安全删除所有密钥副本
- 验证销毁的完整性
- 记录销毁操作的审计日志
- 通知相关系统和人员

## 第2章 凭证安全威胁与风险

### 2.1 硬编码凭证风险

#### 2.1.1 硬编码凭证的表现形式

硬编码凭证是指将敏感的认证信息直接写入源代码或配置文件中。这是软件开发中最常见的安全反模式之一，也是导致凭证泄露的主要原因。

**常见硬编码形式：**

```python
# 反模式：数据库密码硬编码
db_config = {
    "host": "db.prod.example.com",
    "user": "admin",
    "password": "SuperSecret123!",  # 硬编码密码
    "database": "production"
}
```

```javascript
// 反模式：API密钥硬编码
const API_KEY = "sk_live_abcdefghijklmnop1234567890"; // 生产环境密钥
const stripe = require('stripe')(API_KEY);
```

```java
// 反模式：连接字符串硬编码
String connectionString = "Server=prod-db;Database=main;User Id=sa;Password=Admin@2024;";
```

#### 2.1.2 硬编码凭证的危害路径

1. **代码仓库泄露**：代码推送到公共仓库（GitHub、GitLab）后被搜索引擎索引
2. **代码共享泄露**：内部代码在团队间共享时扩散
3. **备份泄露**：代码备份文件中包含敏感凭证
4. **反编译泄露**：编译后的二进制文件中仍可提取硬编码字符串
5. **日志泄露**：调试日志中意外输出配置信息

#### 2.1.3 统计数据与趋势

根据GitGuardian 2024年State of Secrets Sprawl报告：
- 公共GitHub上新增的硬编码秘密封面超过1280万个
- 平均每个泄露的密钥在发现前已暴露约18天
- 约50%的泄露密钥在被发现后仍处于活跃状态
- 金融和科技行业是硬编码凭证泄露的重灾区

### 2.2 凭证泄露常见途径

#### 2.2.1 代码仓库泄露

代码仓库是凭证泄露的高发区域。开发者在日常开发中经常会不小心将包含凭证的文件提交到版本控制系统。

**高风险文件类型：**
- `.env` 文件：环境变量配置文件
- `application.yml` / `application.properties`：Spring Boot配置
- `config.json` / `config.js`：前端配置文件
- `terraform.tfvars`：Terraform变量文件
- `kubeconfig`：Kubernetes配置文件
- `.aws/credentials`：AWS凭证文件
- `id_rsa` / `id_ed25519`：SSH私钥文件

**泄露传播路径：**
1. 开发者本地提交包含凭证的代码
2. 代码推送到内部Git仓库
3. 仓库镜像或Fork到公共平台
4. 第三方代码扫描工具或搜索引擎抓取
5. 攻击者发现并滥用凭证

#### 2.2.2 日志泄露

应用日志是另一个容易被忽视的凭证泄露渠道。开发人员在调试过程中经常会打印完整的请求信息，无意中将敏感凭证输出到日志文件。

**常见日志泄露场景：**

```java
// 危险：打印完整请求头
log.info("Request headers: {}", request.getHeaders());
// Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

// 危险：打印数据库连接信息
log.debug("Connecting to database with URL: {}", jdbcUrl);
// jdbc:mysql://user:password@host:3306/dbname
```

**防护措施：**
- 配置日志脱敏规则，对敏感字段进行掩码处理
- 使用结构化日志，明确标记敏感字段
- 禁止在生产环境开启DEBUG级别日志
- 定期审计日志内容，检查是否存在敏感信息

#### 2.2.3 配置文件泄露

配置文件泄露通常发生在以下场景：

1. **Web服务器配置错误**：`.env`、`.git`等文件可被直接访问
2. **容器镜像泄露**：Docker镜像中包含敏感配置文件
3. **备份文件泄露**：配置文件的备份副本未妥善保护
4. **文档泄露**：技术文档、部署手册中包含真实凭证

### 2.3 内部人员威胁

#### 2.3.1 内部威胁的类型

内部人员威胁是凭证安全的重要挑战。根据IBM 2024年数据泄露成本报告，内部威胁导致的数据泄露平均成本高达1500万美元。

**恶意内部人员：**
- 离职员工带走客户数据和系统凭证
- 不满员工蓄意破坏或窃取信息
- 内鬼与外部攻击者勾结

**无意内部人员：**
- 被钓鱼攻击欺骗的员工
- 安全意识薄弱的开发人员
- 误操作导致的配置泄露

#### 2.3.2 内部凭证滥用的常见手法

1. **凭证复用**：员工在多个系统使用相同密码，一个系统泄露导致全线失守
2. **共享账户**：团队共用一个账户，无法追溯具体操作人员
3. **权限过大**：开发人员拥有生产环境的完全访问权限
4. **离职未清理**：员工离职后账户和凭证未及时吊销
5. **特权凭证滥用**：管理员利用特权账户进行未授权操作

#### 2.3.3 内部威胁防护策略

- 实施最小权限原则（PoLP）
- 部署特权访问管理（PAM）系统
- 建立用户行为分析（UEBA）系统
- 强制实施多因素认证（MFA）
- 定期进行权限审查和清理
- 关键操作实施双人审批机制

### 2.4 供应链凭证风险

#### 2.4.1 供应链攻击面

软件供应链已成为攻击者的重点目标。通过攻击供应链中的薄弱环节，攻击者可以间接入侵大量目标组织。

**供应链凭证风险点：**

1. **第三方依赖库**：开源库中可能包含恶意代码，用于窃取环境变量和配置文件
2. **CI/CD工具**：构建工具和流水线配置中存储了大量敏感凭证
3. **外包开发**：外包团队接触到核心系统凭证
4. **SaaS服务集成**：第三方SaaS应用持有访问内部系统的API密钥
5. **设备固件**：网络设备、IoT设备固件中的硬编码凭证

#### 2.4.2 典型供应链攻击案例

**SolarWinds攻击（2020）**：
攻击者通过篡改SolarWinds Orion平台的软件更新，植入后门程序，最终入侵了包括美国政府机构在内的约18000个组织。攻击的关键一步是获取了SolarWinds的代码签名证书和构建系统访问权限。

**Codecov攻击（2021）**：
攻击者通过获取Codecov的Docker镜像创建凭证，篡改了Bash Uploader脚本，使其能够窃取用户环境变量中的敏感信息。此次事件影响了数千家企业的CI/CD流水线。

## 第3章 密钥管理体系

### 3.1 密钥生成与分发

#### 3.1.1 安全的密钥生成

密钥的安全性首先取决于生成过程的随机性和不可预测性。弱密钥是密码系统的致命弱点。

**密钥生成原则：**

1. **使用密码学安全随机数生成器（CSPRNG）**
   - Linux：`/dev/urandom` 或 `getrandom()` 系统调用
   - Windows：`CryptGenRandom()` 或 `BCryptGenRandom()`
   - 避免使用非安全随机函数（如C语言的rand()）

2. **足够的密钥长度**
   - 对称加密：AES-256（256位）
   - 非对称加密：RSA-3072位以上，ECC-256位以上
   - 哈希算法：SHA-256及以上

3. **密钥熵检测**
   生成密钥后应进行熵值检测，确保密钥具有足够的随机性。

```python
import os
import secrets
import math

def generate_secure_key(length=32):
    """生成安全的随机密钥"""
    return secrets.token_bytes(length)

def calculate_entropy(data):
    """计算数据的熵值"""
    if not data:
        return 0
    freq = {}
    for byte in data:
        freq[byte] = freq.get(byte, 0) + 1
    length = len(data)
    entropy = 0
    for count in freq.values():
        p = count / length
        entropy -= p * math.log2(p)
    return entropy * length  # 总熵（位）

# 生成256位密钥
key = generate_secure_key(32)
print(f"密钥熵值: {calculate_entropy(key):.2f} bits")
```

#### 3.1.2 密钥分发机制

密钥分发是密钥管理中最具挑战性的环节。安全的密钥分发机制包括：

**1. 公钥密码体制分发**
- 使用接收方的公钥加密对称密钥
- 接收方使用私钥解密获取对称密钥
- 适用于跨组织、跨网络的密钥交换

**2. Diffie-Hellman密钥交换**
- 双方在不安全信道上协商出共享密钥
- 密钥本身不在信道上传输
- 需结合身份认证防止中间人攻击

**3. 密钥分片与门限方案**
- 使用Shamir秘密共享算法将密钥分成n份
- 需要至少k份才能恢复完整密钥
- 适用于高安全等级的主密钥保护

**4. 带外分发（Out-of-Band）**
- 通过物理介质（USB Key、智能卡）分发
- 通过独立通信渠道（电话、纸质文档）分发
- 安全性高但效率低，适用于初始密钥建立

#### 3.1.3 密钥分层架构

企业级密钥管理通常采用分层架构，不同层级的密钥承担不同职责：

```
┌─────────────────────────────┐
│      主密钥 (Master Key)     │  最高安全等级，HSM保护，极少更换
└──────────────┬──────────────┘
               │ 加密
┌──────────────▼──────────────┐
│   密钥加密密钥 (KEK)         │  用于加密数据加密密钥，定期轮换
└──────────────┬──────────────┘
               │ 加密
┌──────────────▼──────────────┐
│   数据加密密钥 (DEK)         │  直接加密用户数据，频繁轮换
└─────────────────────────────┘
```

**分层优势：**
- 不同层级密钥采用不同的安全保护策略
- 数据密钥泄露不影响全局安全
- 密钥轮换成本更低，对业务影响更小

### 3.2 密钥存储与保护

#### 3.2.1 硬件安全模块（HSM）

硬件安全模块（Hardware Security Module，HSM）是专门用于密钥管理和密码运算的硬件设备，提供最高级别的密钥保护。

**HSM核心能力：**
- 密钥安全生成：内置真随机数生成器
- 密钥安全存储：密钥永不明文出现在HSM外部
- 密码运算加速：硬件加速加密/解密/签名操作
- 访问控制：严格的身份认证和权限管理
- 审计日志：完整记录所有密钥操作
- 防篡改：物理攻击检测和自毁机制

**主流HSM产品：**
- Thales nShield系列
- Entrust nShield（原Thalte）
- AWS CloudHSM
- Azure Dedicated HSM
- 国产品牌：江南天安、渔翁信息、三未信安

**HSM部署模式：**
1. **本地HSM**：部署在企业数据中心，物理可控性强
2. **云HSM**：云服务商提供的托管HSM服务，弹性扩展
3. **混合模式**：主密钥存储在本地HSM，工作密钥使用云KMS

#### 3.2.2 密钥管理服务（KMS）

云厂商提供的密钥管理服务（Key Management Service）是HSM的托管形式，简化了密钥管理的复杂度。

**KMS核心功能：**
- 密钥的创建、启用、禁用、轮换、删除
- 基于IAM的细粒度访问控制
- 与云服务深度集成（存储、数据库、计算）
- 自动密钥轮换支持
- 完整的审计日志（CloudTrail/Azure Monitor）

**AWS KMS vs Azure Key Vault vs GCP KMS对比：**

| 特性 | AWS KMS | Azure Key Vault | GCP Cloud KMS |
|------|---------|-----------------|---------------|
| 密钥类型 | 对称、非对称 | 对称、非对称、证书 | 对称、非对称 |
| 自动轮换 | 支持（每年） | 支持（可配置） | 支持（可配置） |
| 导入密钥 | 支持 | 支持 | 支持 |
| HSM backing | FIPS 140-2 Level 2 | FIPS 140-2 Level 2 | FIPS 140-2 Level 3 |
| 定价 | 按API调用计费 | 按密钥+操作计费 | 按密钥版本计费 |

#### 3.2.3 秘密管理工具（Vault）

HashiCorp Vault是一款开源的秘密管理工具，专注于动态凭证管理和访问控制。

**Vault核心特性：**
- **动态秘密**：按需生成临时凭证，使用后自动过期
- **加密即服务**：应用通过API进行加密操作，密钥由Vault管理
- **租赁与续租**：凭证有生命周期，可自动续期
- **撤销机制**：可立即撤销特定凭证的访问权限
- **审计日志**：记录所有Vault操作
- **多认证方式**：Token、用户名密码、LDAP、OIDC、AppRole等

### 3.3 密钥轮换与撤销

#### 3.3.1 密钥轮换策略

密钥轮换是密钥管理的重要环节，定期轮换可以限制密钥泄露后的影响窗口。

**轮换周期建议：**

| 密钥类型 | 建议轮换周期 | 强制轮换场景 |
|---------|-------------|-------------|
| 主密钥 | 1-2年 | 安全事件、人员变动 |
| 密钥加密密钥 | 6-12个月 | 安全事件、算法升级 |
| 数据加密密钥 | 90天 | 安全事件、数据迁移 |
| API密钥 | 90天 | 人员离职、项目结束 |
| 会话密钥 | 单次会话 | 会话结束 |
| TLS证书 | 90天（建议） | 证书过期、私钥泄露 |

**密钥轮换实施步骤：**
1. 生成新版本密钥
2. 新数据使用新密钥加密
3. 逐步迁移旧数据（重加密）
4. 旧密钥进入退役状态（仅解密）
5. 确认所有数据迁移完成
6. 安全销毁旧密钥

#### 3.3.2 密钥版本管理

支持多版本密钥是实现平滑轮换的关键。每个密钥可以有多个版本，不同版本有不同的状态：

- **启用（Enabled）**：可用于加密和解密
- **禁用（Disabled）**：不可用，但可重新启用
- **计划删除（Pending Deletion）**：等待删除的窗口期
- **已销毁（Destroyed）**：已被永久删除

**AWS KMS密钥版本示例：**
```json
{
  "KeyId": "1234abcd-12ab-34cd-56ef-1234567890ab",
  "KeyMetadata": {
    "KeyId": "1234abcd-12ab-34cd-56ef-1234567890ab",
    "KeyState": "Enabled",
    "KeyUsage": "ENCRYPT_DECRYPT",
    "KeySpec": "SYMMETRIC_DEFAULT",
    "Origin": "AWS_KMS",
    "KeyManager": "CUSTOMER",
    "RotationEnabled": true,
    "LastRotatedDate": "2024-01-15T10:30:00Z"
  }
}
```

#### 3.3.3 密钥撤销机制

密钥撤销是在密钥泄露或不再可信时立即停止其使用的机制。

**撤销触发条件：**
- 检测到密钥泄露
- 相关人员离职
- 安全事件响应需要
- 密钥使用异常
- 合规要求

**撤销实施要点：**
- 建立快速撤销通道，确保分钟级响应
- 记录撤销原因和操作人
- 通知所有依赖该密钥的系统
- 评估受影响的数据范围
- 制定恢复和重加密计划

### 3.4 密钥审计与监控

#### 3.4.1 审计日志要求

完整的审计日志是密钥管理合规性的基础要求。

**审计日志应包含的信息：**
- 操作时间戳
- 操作用户/服务身份
- 操作类型（创建、使用、轮换、删除）
- 操作的密钥标识
- 操作结果（成功/失败）
- 来源IP地址
- 请求的详细参数（不包含密钥值本身）

**日志存储与保护：**
- 日志不可篡改（WORM存储、区块链存证）
- 日志保留期限符合合规要求（通常1-7年）
- 日志访问需严格控制和审计
- 定期进行日志完整性校验

#### 3.4.2 密钥使用监控

**关键监控指标：**
- 密钥使用频率和模式
- 异常访问行为（时间异常、位置异常、量级异常）
- 密钥生命周期状态
- 即将到期的密钥数量
- 密钥访问权限变更

**告警规则示例：**
- 短时间内大量解密操作（可能是数据窃取）
- 非工作时间的密钥管理操作
- 从未知IP地址访问密钥
- 密钥创建/删除操作
- 权限策略变更

```python
)['Plaintext']
```

```python
# 用DEK加密实际数据（使用AES等对称算法）
# encrypted_data = aes_encrypt(data, plaintext_dek)

# 存储：加密后的数据 + 加密后的DEK
# 下次使用时：先用KMS解密DEK，再用DEK解密数据
```

### 5.3 凭证泄露应急响应

#### 5.3.1 应急响应流程

**凭证泄露事件响应六步法：**

```
┌──────────┐    ┌──────────┐    ┌──────────┐
│  1.发现  │───▶│  2.遏制  │───▶│  3.根除  │
└──────────┘    └──────────┘    └────┬─────┘
                                     │
┌──────────┐    ┌──────────┐    ┌───▼──────┐
│  6.总结  │◀───│  5.恢复  │◀───│  4.调查  │
└──────────┘    └──────────┘    └──────────┘
```

**步骤1：发现与确认**
- 确认泄露凭证的类型和范围
- 评估凭证的权限等级和影响范围
- 确认泄露时间和泄露渠道

**步骤2：遏制（立即执行）**
- 立即吊销/轮换泄露的凭证
- 阻止未授权访问（IP封禁、会话终止）
- 保护关键系统和数据
- 保存取证证据

**步骤3：调查与分析**
- 追溯泄露源头（代码仓库、日志、配置文件）
- 分析攻击者的活动记录
- 评估数据泄露范围
- 识别其他可能受影响的凭证

**步骤4：根除**
- 修复泄露源头（删除硬编码凭证、修复配置漏洞）
- 全面轮换相关凭证
- 修复安全漏洞
- 加强访问控制

**步骤5：恢复**
- 逐步恢复系统正常运行
- 验证新凭证的有效性
- 加强监控，防止再次入侵

**步骤6：总结与改进**
- 编写事件报告
- 更新安全策略和流程
- 加强安全培训
- 改进检测和防护措施

#### 5.3.2 不同类型凭证的应急措施

| 凭证类型 | 立即措施 | 后续措施 |
|---------|---------|---------|
| 云平台AK/SK | 立即禁用或删除泄露的密钥 | 创建新密钥并更新所有使用点；审计该密钥的历史操作 |
| 数据库密码 | 修改密码；限制数据库访问IP | 审计数据库访问日志；检查是否有数据被窃取 |

## 第6章 API密钥与令牌安全

### 6.1 API密钥最佳实践

#### 6.1.1 API密钥设计原则

**密钥命名规范：**
- 使用前缀标识环境和用途：`sk_live_`、`sk_test_`、`pk_prod_`
- 密钥长度建议：至少32字节的随机数据（base64编码后约43字符）
- 包含可校验前缀，便于快速识别

**安全设计：**
1. **服务端只存储哈希值**：类似密码，API密钥也应哈希存储
2. **密钥指纹**：使用密钥的前几位或哈希值作为标识
3. **过期机制**：设置密钥有效期，支持自动过期
4. **速率限制**：每个密钥独立的速率限制
5. **IP白名单**：高安全等级的密钥可绑定IP

#### 6.1.2 API密钥存储与传输

**传输安全：**
- 必须使用HTTPS传输
- 禁止在URL参数中传递API密钥（会被日志记录）
- 使用Authorization请求头传递
- 避免在客户端（浏览器、移动APP）存储长期API密钥

**正确方式：**
```http
GET /api/v1/users HTTP/1.1
Host: api.example.com
Authorization: Bearer sk_live_abc123def456...
```

**错误方式：**
```http
GET /api/v1/users?api_key=sk_live_abc123... HTTP/1.1
Host: api.example.com
```

**服务端存储：**
```python
import hashlib
import secrets
import hmac

def generate_api_key(prefix: str = "sk") -> tuple[str, str]:
    """生成API密钥，返回(明文密钥, 哈希值)"""
    raw_key = secrets.token_bytes(32)
    api_key = f"{prefix}_{raw_key.hex()}"
    # 使用SHA-256哈希存储
    key_hash = hashlib.sha256(api_key.encode()).hexdigest()
    return api_key, key_hash

def verify_api_key(api_key: str, stored_hash: str) -> bool:
    """验证API密钥"""
    computed_hash = hashlib.sha256(api_key.encode()).hexdigest()
    return hmac.compare_digest(computed_hash, stored_hash)
```

#### 6.1.3 API密钥生命周期管理

**创建阶段：**
- 明确密钥的用途和所有者
- 设置适当的权限范围（Scope）
- 设置过期时间
- 记录创建人和创建时间

**使用阶段：**
- 监控每个密钥的使用情况
- 检测异常使用模式
- 定期审查密钥的必要性

**轮换阶段：**
- 支持双密钥并行（新旧密钥同时有效）
- 提供轮换过渡期（建议7-30天）
- 通知密钥所有者进行更新

**撤销阶段：**
- 支持立即撤销和定时撤销
- 记录撤销原因
- 审计撤销前的使用记录

### 6.2 OAuth令牌安全管理

#### 6.2.1 OAuth 2.0令牌类型

**Access Token（访问令牌）：**
- 用于访问受保护资源
- 生命周期短（通常15分钟到1小时）
- 应使用短有效期减少泄露风险
- 泄露后影响范围受限于权限和有效期

**Refresh Token（刷新令牌）：**
- 用于获取新的访问令牌
- 生命周期长（天/周/月级别）
- 必须安全存储（服务端安全存储）
- 泄露危害更大，需严格保护

**ID Token（身份令牌）：**
- JWT格式，包含用户身份信息
- 仅用于身份认证，不用于授权
- 有明确的受众（audience）限制

#### 6.2.2 令牌安全最佳实践

**Access Token安全：**
- 使用短有效期（15-30分钟）
- 遵循令牌受众（audience）限制
- 验证令牌签名和有效期
- 实现令牌撤销机制（Token Revocation）

**Refresh Token安全：**
- 服务端安全存储（加密存储）
- 绑定客户端信息（IP、User-Agent）
- 使用旋转刷新令牌（Rotation Refresh Token）
- 设置合理的有效期和闲置超时
- 支持立即撤销

**前端应用令牌安全：**
- 单页应用（SPA）使用Authorization Code + PKCE流程
- 避免在localStorage中存储令牌（XSS风险）
- 使用HttpOnly + Secure Cookie存储刷新令牌
- 实现令牌自动续期和过期处理

#### 6.2.3 令牌泄露应对

**检测令牌泄露：**
- 异常的地理位置访问
- 同一令牌多处同时使用
- 令牌使用量异常增加
- 异常的API调用模式

**应对措施：**
1. 立即撤销泄露的令牌
2. 撤销关联的刷新令牌
3. 通知用户重新认证
4. 审计令牌使用记录
5. 加强安全措施（MFA、设备绑定）

### 6.3 JWT安全配置

#### 6.3.1 JWT结构回顾

JWT（JSON Web Token）由三部分组成：Header.Payload.Signature

**Header：**
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

**Payload：**
```json
{
  "sub": "user123",
  "iss": "https://auth.example.com",
  "aud": "https://api.example.com",
  "exp": 1704067200,
  "iat": 1704063600,
  "scope": "read write"
}
```

#### 6.3.2 JWT常见安全问题

**1. 算法混淆攻击（Alg=none）**
攻击者将alg设置为none，服务器如果支持none算法就会接受无签名的令牌。

**防护：**
```python
# 明确指定允许的算法，禁用none
import jwt

decoded = jwt.decode(
    token,
    public_key,
    algorithms=["RS256", "ES256"],  # 白名单方式
    options={"verify_signature": True}
)
```

**2. 弱密钥（HS256 + 弱密钥）**
使用HS256算法时，如果密钥强度不足，攻击者可以暴力破解。

**防护：**
- HS256密钥长度至少256位（32字节随机字符串）
- 优先使用非对称算法（RS256、ES256）
- 定期轮换签名密钥

**3. 未验证所有声明（Claims）**
只验证签名而不验证exp、iss、aud等声明。

**必须验证的声明：**
- `exp`：过期时间
- `nbf`：生效时间
- `iss`：签发者
- `aud`：受众
- `iat`：签发时间（用于检测异常早的令牌）

#### 6.3.3 JWT安全最佳实践

```python
import jwt
import time
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.backends import default_backend

def create_jwt(user_id: str, private_key_path: str) -> str:
    """安全创建JWT"""
    with open(private_key_path, "rb") as f:
        private_key = serialization.load_pem_private_key(
            f.read(), password=None, backend=default_backend()
        )
    
    now = int(time.time())
    payload = {
        "sub": user_id,
        "iss": "https://auth.example.com",
        "aud": "https://api.example.com",
        "iat": now,
        "exp": now + 900,  # 15分钟过期
        "nbf": now,
        "jti": generate_unique_id(),  # 令牌唯一标识，用于撤销
    }
    
    return jwt.encode(payload, private_key, algorithm="RS256")

def verify_jwt(token: str, public_key_path: str) -> dict:
    """安全验证JWT"""
    with open(public_key_path, "rb") as f:
        public_key = serialization.load_pem_public_key(
            f.read(), backend=default_backend()
        )
    
    return jwt.decode(
        token,
        public_key,
        algorithms=["RS256"],
        audience="https://api.example.com",
        issuer="https://auth.example.com",
        options={
            "require": ["exp", "iat", "sub", "iss", "aud"],
            "verify_exp": True,
            "verify_iss": True,
            "verify_aud": True,
        }
    )
```

```python
import os

class VaultClient:

            url=os.environ.get('VAULT_ADDR', 'https://vault.example.com:8200'),

    def get_secret(self, path: str) -> dict:
        """读取KV密钥"""
        response = self.client.secrets.kv.v2.read_secret_version(path=path)
        return response['data']['data']
    
    def get_db_credentials(self, role: str) -> tuple:
        """获取动态数据库凭证"""
        response = self.client.secrets.database.generate_credentials(name=role)
        return response['data']['username'], response['data']['password']
    
    def encrypt(self, plaintext: str, key_name: str) -> str:
        """使用Transit引擎加密"""
        response = self.client.secrets.transit.encrypt_data(
            name=key_name,
            plaintext=plaintext.encode().hex()
        )
        return response['data']['ciphertext']
```

#### 7.1.3 实施效果

- 实现了全公司凭证的统一管理
- 所有凭证访问有完整审计记录
- 应用凭证实现动态生成和自动过期
- 支持人员流动时的快速凭证回收
- 顺利通过等保三级和ISO 27001审计

### 7.3 案例3：凭证泄露事件应急响应

#### 7.3.1 事件背景

某SaaS公司安全团队收到GitGuardian告警，发现公司内部GitHub仓库的一个私有仓库中泄露了生产环境的AWS Access Key。该密钥具有S3全量访问权限，而公司的用户数据存储在S3中。

#### 7.3.2 应急响应过程

**T+0分钟：发现与确认**
- GitGuardian自动告警，安全团队收到通知
- 确认泄露的密钥ID：AKIAIOSFODNN7EXAMPLE
- 确认密钥权限：AmazonS3FullAccess
- 确认泄露位置：开源的内部工具项目中的config.py文件

**T+5分钟：遏制措施**
```bash
# 立即禁用泄露的AWS密钥
aws iam update-access-key \
  --access-key-id AKIAIOSFODNN7EXAMPLE \
  --status Inactive \
  --user-name prod-deployment-user

# 查看该密钥的最近使用记录
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIAIOSFODNN7EXAMPLE \
  --start-time $(date -d '7 days ago' +%s) \
  --max-results 50
```

**T+15分钟：影响评估**
- 检查CloudTrail日志，确认该密钥在过去24小时内的使用情况
- 发现来自陌生IP（45.x.x.x）的多次S3 List和Get操作
- 确认攻击者访问了约5个存储桶
- 初步估计可能泄露的数据量约100GB用户数据

**T+30分钟：深度遏制**
- 立即删除泄露的IAM用户密钥
- 创建新的密钥并更新所有合法使用点
- 临时限制S3访问，只允许白名单IP访问
- 启用S3访问日志的实时分析
- 保存所有相关日志用于取证

**T+1小时：调查分析**
- 追溯代码提交历史，确认凭证是在3个月前的一次重构中被提交
- 提交者为已离职员工，当时未做代码审查
- 仓库是在1周前被意外设为公开（原因为配置错误）
- 攻击者通过GitHub搜索功能发现了该密钥

**T+2小时：根因分析**
- 直接原因：代码中硬编码AWS密钥 + 仓库意外公开
- 根本原因：
  - 缺乏代码凭证扫描机制
  - 仓库权限管理不严格
  - 新员工安全培训不到位
  - 缺乏基础设施即代码的权限管理

**T+24小时：恢复与改进**
- 确认数据泄露范围，通知受影响用户
- 全面审查所有代码仓库的凭证情况
- 部署Gitleaks到所有CI/CD流水线
- 实施最小权限策略，缩减AWS密钥权限
- 建立代码审查流程和安全检查卡点
- 加强员工安全意识培训

#### 7.3.3 经验总结

1. **预防胜于治疗**：建立前置的凭证扫描机制远比事后响应更有效
2. **最小权限原则**：即使密钥泄露，限制权限也能降低损失
3. **监控与告警**：快速发现是减少损失的关键
4. **流程保障**：不能依赖个人意识，必须有流程和工具保障
5. **定期演练**：定期进行应急响应演练，确保团队熟悉流程

## 第4章 凭证安全管理实践

### 4.1 环境变量与配置管理

#### 4.1.1 环境变量的安全使用

环境变量是将配置与代码分离的常用方式，但如果处理不当，仍然存在安全风险。

**最佳实践：**

1. **使用.env文件 + .gitignore**
   ```
   # .gitignore
   .env
   .env.local
   .env.*.local
   *.key
   *.pem
   ```

2. **提供.env.example模板**
   ```
   # .env.example - 只包含键名和占位符，不包含真实值
   DB_HOST=localhost
   DB_PORT=5432
   DB_USER=your_username
   DB_PASSWORD=your_secure_password
   API_KEY=your_api_key_here
   ```

3. **环境变量分级管理**
   - 开发环境（development）：使用本地开发凭证
   - 测试环境（staging）：使用测试环境专用凭证
   - 生产环境（production）：使用生产环境凭证，严格控制访问

#### 4.1.2 配置文件加密方案

对于必须存储在文件中的敏感配置，应采用加密保护。

**方案一：git-crypt**
```bash
# 安装git-crypt
brew install git-crypt  # macOS
apt install git-crypt   # Ubuntu

# 初始化仓库
git-crypt init

# 配置加密规则（.gitattributes）
secretfile filter=git-crypt diff=git-crypt
*.key filter=git-crypt diff=git-crypt
.env.prod filter=git-crypt diff=git-crypt

# 添加GPG密钥授权
git-crypt add-gpg-user user@example.com
```

**方案二：SOPS（Secrets OPerationS）**
```bash
# 使用AWS KMS加密配置文件
sops --encrypt --kms arn:aws:kms:us-east-1:123456789:key/abc123 secrets.yaml > secrets.enc.yaml

# 解密并编辑
sops secrets.enc.yaml

# 集成到CI/CD
sops --decrypt secrets.enc.yaml > secrets.yaml
```

#### 4.2.1 AWS KMS实战

**创建客户托管密钥：**
```python
import boto3

kms = boto3.client('kms', region_name='us-east-1')

# 创建对称加密密钥
response = kms.create_key(
    Description='Application data encryption key',
    KeyUsage='ENCRYPT_DECRYPT',
    Origin='AWS_KMS',
    Tags=[
        {'TagKey': 'Environment', 'TagValue': 'Production'},
        {'TagKey': 'Application', 'TagValue': 'PaymentService'}
    ]
)

key_id = response['KeyMetadata']['KeyId']
print(f"Created key: {key_id}")

# 启用自动轮换
kms.enable_key_rotation(KeyId=key_id)
```

**使用KMS加密数据：**
```python
# 加密数据
ciphertext = kms.encrypt(
    KeyId=key_id,
    Plaintext=b'Sensitive data to encrypt',
    EncryptionContext={'Purpose': 'customer_data'}
)['CiphertextBlob']

# 解密数据
plaintext = kms.decrypt(
    CiphertextBlob=ciphertext,
    EncryptionContext={'Purpose': 'customer_data'}
)['Plaintext']
```

**信封加密（Envelope Encryption）：**
```python
# 生成数据密钥（DEK）
data_key = kms.generate_data_key(
    KeyId=key_id,
    KeySpec='AES_256'
)

# 明文DEK用于加密数据（本地加密）
plaintext_dek = data_key['Plaintext']
encrypted_dek = data_key['CiphertextBlob']

# 用DEK加密实际数据（使用AES等对称算法）
# encrypted_data = aes_encrypt(data, plaintext_dek)

# 存储：加密后的数据 + 加密后的DEK
# 下次使用时：先用KMS解密DEK，再用DEK解密数据
```

## 第6章 API密钥与令牌安全

### 6.1 API密钥最佳实践

#### 6.1.1 API密钥设计原则

**密钥命名规范：**
- 使用前缀标识环境和用途：`sk_live_`、`sk_test_`、`pk_prod_`
- 密钥长度建议：至少32字节的随机数据（base64编码后约43字符）
- 包含可校验前缀，便于快速识别

**安全设计：**
1. **服务端只存储哈希值**：类似密码，API密钥也应哈希存储
2. **密钥指纹**：使用密钥的前几位或哈希值作为标识
3. **过期机制**：设置密钥有效期，支持自动过期
4. **速率限制**：每个密钥独立的速率限制
5. **IP白名单**：高安全等级的密钥可绑定IP

#### 6.1.2 API密钥存储与传输

**传输安全：**
- 必须使用HTTPS传输
- 禁止在URL参数中传递API密钥（会被日志记录）
- 使用Authorization请求头传递
- 避免在客户端（浏览器、移动APP）存储长期API密钥

**正确方式：**
```http
GET /api/v1/users HTTP/1.1
Host: api.example.com
Authorization: Bearer sk_live_abc123def456...
```

**错误方式：**
```http
GET /api/v1/users?api_key=sk_live_abc123... HTTP/1.1
Host: api.example.com
```

**服务端存储：**
```python
import hashlib
import secrets
import hmac

def generate_api_key(prefix: str = "sk") -> tuple[str, str]:
    """生成API密钥，返回(明文密钥, 哈希值)"""
    raw_key = secrets.token_bytes(32)
    api_key = f"{prefix}_{raw_key.hex()}"
    # 使用SHA-256哈希存储
    key_hash = hashlib.sha256(api_key.encode()).hexdigest()
    return api_key, key_hash

def verify_api_key(api_key: str, stored_hash: str) -> bool:
    """验证API密钥"""
    computed_hash = hashlib.sha256(api_key.encode()).hexdigest()
    return hmac.compare_digest(computed_hash, stored_hash)
```

#### 6.1.3 API密钥生命周期管理

**创建阶段：**
- 明确密钥的用途和所有者
- 设置适当的权限范围（Scope）
- 设置过期时间
- 记录创建人和创建时间

**使用阶段：**
- 监控每个密钥的使用情况
- 检测异常使用模式
- 定期审查密钥的必要性

**轮换阶段：**
- 支持双密钥并行（新旧密钥同时有效）
- 提供轮换过渡期（建议7-30天）
- 通知密钥所有者进行更新

**撤销阶段：**
- 支持立即撤销和定时撤销
- 记录撤销原因
- 审计撤销前的使用记录

### 6.2 OAuth令牌安全管理

#### 6.2.1 OAuth 2.0令牌类型

**Access Token（访问令牌）：**
- 用于访问受保护资源
- 生命周期短（通常15分钟到1小时）
- 应使用短有效期减少泄露风险
- 泄露后影响范围受限于权限和有效期

**Refresh Token（刷新令牌）：**
- 用于获取新的访问令牌
- 生命周期长（天/周/月级别）
- 必须安全存储（服务端安全存储）
- 泄露危害更大，需严格保护

**ID Token（身份令牌）：**
- JWT格式，包含用户身份信息
- 仅用于身份认证，不用于授权
- 有明确的受众（audience）限制

#### 6.2.2 令牌安全最佳实践

**Access Token安全：**
- 使用短有效期（15-30分钟）
- 遵循令牌受众（audience）限制
- 验证令牌签名和有效期
- 实现令牌撤销机制（Token Revocation）

**Refresh Token安全：**
- 服务端安全存储（加密存储）
- 绑定客户端信息（IP、User-Agent）
- 使用旋转刷新令牌（Rotation Refresh Token）
- 设置合理的有效期和闲置超时
- 支持立即撤销

**前端应用令牌安全：**
- 单页应用（SPA）使用Authorization Code + PKCE流程
- 避免在localStorage中存储令牌（XSS风险）
- 使用HttpOnly + Secure Cookie存储刷新令牌
- 实现令牌自动续期和过期处理

#### 6.2.3 令牌泄露应对

**检测令牌泄露：**
- 异常的地理位置访问
- 同一令牌多处同时使用
- 令牌使用量异常增加
- 异常的API调用模式

**应对措施：**
1. 立即撤销泄露的令牌
2. 撤销关联的刷新令牌
3. 通知用户重新认证
4. 审计令牌使用记录
5. 加强安全措施（MFA、设备绑定）

### 6.3 JWT安全配置

#### 6.3.1 JWT结构回顾

JWT（JSON Web Token）由三部分组成：Header.Payload.Signature

**Header：**
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

**Payload：**
```json
{
  "sub": "user123",
  "iss": "https://auth.example.com",
  "aud": "https://api.example.com",
  "exp": 1704067200,
  "iat": 1704063600,
  "scope": "read write"
}
```

#### 6.3.2 JWT常见安全问题

**1. 算法混淆攻击（Alg=none）**
攻击者将alg设置为none，服务器如果支持none算法就会接受无签名的令牌。

**防护：**
```python
# 明确指定允许的算法，禁用none
import jwt

decoded = jwt.decode(
    token,
    public_key,
    algorithms=["RS256", "ES256"],  # 白名单方式
    options={"verify_signature": True}
)
```

**2. 弱密钥（HS256 + 弱密钥）**
使用HS256算法时，如果密钥强度不足，攻击者可以暴力破解。

**防护：**
- HS256密钥长度至少256位（32字节随机字符串）
- 优先使用非对称算法（RS256、ES256）
- 定期轮换签名密钥

**3. 未验证所有声明（Claims）**
只验证签名而不验证exp、iss、aud等声明。

**必须验证的声明：**
- `exp`：过期时间
- `nbf`：生效时间
- `iss`：签发者
- `aud`：受众
- `iat`：签发时间（用于检测异常早的令牌）

#### 6.3.3 JWT安全最佳实践

```python
import jwt
import time
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.backends import default_backend

def create_jwt(user_id: str, private_key_path: str) -> str:
    """安全创建JWT"""
    with open(private_key_path, "rb") as f:
        private_key = serialization.load_pem_private_key(
            f.read(), password=None, backend=default_backend()
        )
    
    now = int(time.time())
    payload = {
        "sub": user_id,
        "iss": "https://auth.example.com",
        "aud": "https://api.example.com",
        "iat": now,
        "exp": now + 900,  # 15分钟过期
        "nbf": now,
        "jti": generate_unique_id(),  # 令牌唯一标识，用于撤销
    }
    
    return jwt.encode(payload, private_key, algorithm="RS256")

def verify_jwt(token: str, public_key_path: str) -> dict:
    """安全验证JWT"""
    with open(public_key_path, "rb") as f:
        public_key = serialization.load_pem_public_key(
            f.read(), backend=default_backend()
        )
    
    return jwt.decode(
        token,
        public_key,
        algorithms=["RS256"],
        audience="https://api.example.com",
        issuer="https://auth.example.com",
        options={
            "require": ["exp", "iat", "sub", "iss", "aud"],
            "verify_exp": True,
            "verify_iss": True,
            "verify_aud": True,
        }
    )
```

```python
import os

class VaultClient:
    def __init__(self):
        self.client = hvac.Client(
            url=os.environ.get('VAULT_ADDR', 'https://vault.example.com:8200'),
            verify='/etc/ssl/certs/ca-bundle.crt'

        role_id = os.environ['VAULT_ROLE_ID']
        secret_id = os.environ['VAULT_SECRET_ID']
        self.client.auth.approle.login(
            role_id=role_id,
            secret_id=secret_id
        )
    
    def get_secret(self, path: str) -> dict:
        """读取KV密钥"""
        response = self.client.secrets.kv.v2.read_secret_version(path=path)
        return response['data']['data']
    
    def get_db_credentials(self, role: str) -> tuple:
        """获取动态数据库凭证"""
        response = self.client.secrets.database.generate_credentials(name=role)
        return response['data']['username'], response['data']['password']
    
    def encrypt(self, plaintext: str, key_name: str) -> str:
        """使用Transit引擎加密"""
        response = self.client.secrets.transit.encrypt_data(
            name=key_name,
            plaintext=plaintext.encode().hex()
        )
        return response['data']['ciphertext']
```

### 7.3 案例3：凭证泄露事件应急响应

#### 7.3.1 事件背景

某SaaS公司安全团队收到GitGuardian告警，发现公司内部GitHub仓库的一个私有仓库中泄露了生产环境的AWS Access Key。该密钥具有S3全量访问权限，而公司的用户数据存储在S3中。

#### 7.3.2 应急响应过程

**T+0分钟：发现与确认**
- GitGuardian自动告警，安全团队收到通知
- 确认泄露的密钥ID：AKIAIOSFODNN7EXAMPLE
- 确认密钥权限：AmazonS3FullAccess
- 确认泄露位置：开源的内部工具项目中的config.py文件

**T+5分钟：遏制措施**
```bash
# 立即禁用泄露的AWS密钥
aws iam update-access-key \
  --access-key-id AKIAIOSFODNN7EXAMPLE \
  --status Inactive \
  --user-name prod-deployment-user

# 查看该密钥的最近使用记录
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIAIOSFODNN7EXAMPLE \
  --start-time $(date -d '7 days ago' +%s) \
  --max-results 50
```

**T+15分钟：影响评估**
- 检查CloudTrail日志，确认该密钥在过去24小时内的使用情况
- 发现来自陌生IP（45.x.x.x）的多次S3 List和Get操作
- 确认攻击者访问了约5个存储桶
- 初步估计可能泄露的数据量约100GB用户数据

**T+30分钟：深度遏制**
- 立即删除泄露的IAM用户密钥
- 创建新的密钥并更新所有合法使用点
- 临时限制S3访问，只允许白名单IP访问
- 启用S3访问日志的实时分析
- 保存所有相关日志用于取证

**T+1小时：调查分析**
- 追溯代码提交历史，确认凭证是在3个月前的一次重构中被提交
- 提交者为已离职员工，当时未做代码审查
- 仓库是在1周前被意外设为公开（原因为配置错误）
- 攻击者通过GitHub搜索功能发现了该密钥

**T+2小时：根因分析**
- 直接原因：代码中硬编码AWS密钥 + 仓库意外公开
- 根本原因：
  - 缺乏代码凭证扫描机制
  - 仓库权限管理不严格
  - 新员工安全培训不到位
  - 缺乏基础设施即代码的权限管理

**T+24小时：恢复与改进**
- 确认数据泄露范围，通知受影响用户
- 全面审查所有代码仓库的凭证情况
- 部署Gitleaks到所有CI/CD流水线
- 实施最小权限策略，缩减AWS密钥权限
- 建立代码审查流程和安全检查卡点
- 加强员工安全意识培训

#### 7.3.3 经验总结

1. **预防胜于治疗**：建立前置的凭证扫描机制远比事后响应更有效
2. **最小权限原则**：即使密钥泄露，限制权限也能降低损失
3. **监控与告警**：快速发现是减少损失的关键
4. **流程保障**：不能依赖个人意识，必须有流程和工具保障
5. **定期演练**：定期进行应急响应演练，确保团队熟悉流程

## 第4章 凭证安全管理实践

### 4.1 环境变量与配置管理

#### 4.1.1 环境变量的安全使用

环境变量是将配置与代码分离的常用方式，但如果处理不当，仍然存在安全风险。

**最佳实践：**

1. **使用.env文件 + .gitignore**
   ```
   # .gitignore
   .env
   .env.local
   .env.*.local
   *.key
   *.pem
   ```

2. **提供.env.example模板**
   ```
   # .env.example - 只包含键名和占位符，不包含真实值
   DB_HOST=localhost
   DB_PORT=5432
   DB_USER=your_username
   DB_PASSWORD=your_secure_password
   API_KEY=your_api_key_here
   ```

3. **环境变量分级管理**
   - 开发环境（development）：使用本地开发凭证
   - 测试环境（staging）：使用测试环境专用凭证
   - 生产环境（production）：使用生产环境凭证，严格控制访问

#### 4.1.2 配置文件加密方案

对于必须存储在文件中的敏感配置，应采用加密保护。

**方案一：git-crypt**
```bash
# 安装git-crypt
brew install git-crypt  # macOS
apt install git-crypt   # Ubuntu

# 初始化仓库
git-crypt init

# 配置加密规则（.gitattributes）
secretfile filter=git-crypt diff=git-crypt
*.key filter=git-crypt diff=git-crypt
.env.prod filter=git-crypt diff=git-crypt

# 添加GPG密钥授权
git-crypt add-gpg-user user@example.com
```

**方案二：SOPS（Secrets OPerationS）**
```bash
# 使用AWS KMS加密配置文件
sops --encrypt --kms arn:aws:kms:us-east-1:123456789:key/abc123 secrets.yaml > secrets.enc.yaml

# 解密并编辑
sops secrets.enc.yaml

# 集成到CI/CD
sops --decrypt secrets.enc.yaml > secrets.yaml
```

#### 4.1.3 应用启动时的凭证注入

**Docker容器凭证注入：**

```bash
# 危险：在镜像构建时嵌入凭证
```

### 4.2 密钥管理服务详解

#### 4.2.1 AWS KMS实战

**创建客户托管密钥：**
```python
import boto3

kms = boto3.client('kms', region_name='us-east-1')

# 创建对称加密密钥
response = kms.create_key(
    Description='Application data encryption key',
    KeyUsage='ENCRYPT_DECRYPT',
    Origin='AWS_KMS',
    Tags=[
        {'TagKey': 'Environment', 'TagValue': 'Production'},
        {'TagKey': 'Application', 'TagValue': 'PaymentService'}
    ]
)

key_id = response['KeyMetadata']['KeyId']
print(f"Created key: {key_id}")

# 启用自动轮换
kms.enable_key_rotation(KeyId=key_id)
```

### 5.3 凭证泄露应急响应

#### 5.3.1 应急响应流程

**凭证泄露事件响应六步法：**

```
┌──────────┐    ┌──────────┐    ┌──────────┐
│  1.发现  │───▶│  2.遏制  │───▶│  3.根除  │
└──────────┘    └──────────┘    └────┬─────┘
                                     │
┌──────────┐    ┌──────────┐    ┌───▼──────┐
│  6.总结  │◀───│  5.恢复  │◀───│  4.调查  │
└──────────┘    └──────────┘    └──────────┘
```

**步骤1：发现与确认**
- 确认泄露凭证的类型和范围
- 评估凭证的权限等级和影响范围
- 确认泄露时间和泄露渠道

**步骤2：遏制（立即执行）**
- 立即吊销/轮换泄露的凭证
- 阻止未授权访问（IP封禁、会话终止）
- 保护关键系统和数据
- 保存取证证据

**步骤3：调查与分析**
- 追溯泄露源头（代码仓库、日志、配置文件）
- 分析攻击者的活动记录
- 评估数据泄露范围
- 识别其他可能受影响的凭证

**步骤4：根除**
- 修复泄露源头（删除硬编码凭证、修复配置漏洞）
- 全面轮换相关凭证
- 修复安全漏洞
- 加强访问控制

**步骤5：恢复**
- 逐步恢复系统正常运行
- 验证新凭证的有效性
- 加强监控，防止再次入侵

**步骤6：总结与改进**
- 编写事件报告
- 更新安全策略和流程
- 加强安全培训
- 改进检测和防护措施

## 第6章 API密钥与令牌安全

### 6.1 API密钥最佳实践

#### 6.1.1 API密钥设计原则

**密钥命名规范：**
- 使用前缀标识环境和用途：`sk_live_`、`sk_test_`、`pk_prod_`
- 密钥长度建议：至少32字节的随机数据（base64编码后约43字符）
- 包含可校验前缀，便于快速识别

**安全设计：**
1. **服务端只存储哈希值**：类似密码，API密钥也应哈希存储
2. **密钥指纹**：使用密钥的前几位或哈希值作为标识
3. **过期机制**：设置密钥有效期，支持自动过期
4. **速率限制**：每个密钥独立的速率限制
5. **IP白名单**：高安全等级的密钥可绑定IP

#### 6.1.2 API密钥存储与传输

**传输安全：**
- 必须使用HTTPS传输
- 禁止在URL参数中传递API密钥（会被日志记录）
- 使用Authorization请求头传递
- 避免在客户端（浏览器、移动APP）存储长期API密钥

**正确方式：**
```http
GET /api/v1/users HTTP/1.1
Host: api.example.com
Authorization: Bearer sk_live_abc123def456...
```

**错误方式：**
```http
GET /api/v1/users?api_key=sk_live_abc123... HTTP/1.1
Host: api.example.com
```

**服务端存储：**
```python
import hashlib
import secrets
import hmac

def generate_api_key(prefix: str = "sk") -> tuple[str, str]:
    """生成API密钥，返回(明文密钥, 哈希值)"""
    raw_key = secrets.token_bytes(32)
    api_key = f"{prefix}_{raw_key.hex()}"
    # 使用SHA-256哈希存储
    key_hash = hashlib.sha256(api_key.encode()).hexdigest()
    return api_key, key_hash

def verify_api_key(api_key: str, stored_hash: str) -> bool:
    """验证API密钥"""
    computed_hash = hashlib.sha256(api_key.encode()).hexdigest()
    return hmac.compare_digest(computed_hash, stored_hash)
```

#### 6.1.3 API密钥生命周期管理

**创建阶段：**
- 明确密钥的用途和所有者
- 设置适当的权限范围（Scope）
- 设置过期时间
- 记录创建人和创建时间

**使用阶段：**
- 监控每个密钥的使用情况
- 检测异常使用模式
- 定期审查密钥的必要性

**轮换阶段：**
- 支持双密钥并行（新旧密钥同时有效）
- 提供轮换过渡期（建议7-30天）
- 通知密钥所有者进行更新

**撤销阶段：**
- 支持立即撤销和定时撤销
- 记录撤销原因
- 审计撤销前的使用记录

### 6.2 OAuth令牌安全管理

#### 6.2.1 OAuth 2.0令牌类型

**Access Token（访问令牌）：**
- 用于访问受保护资源
- 生命周期短（通常15分钟到1小时）
- 应使用短有效期减少泄露风险
- 泄露后影响范围受限于权限和有效期

**Refresh Token（刷新令牌）：**
- 用于获取新的访问令牌
- 生命周期长（天/周/月级别）
- 必须安全存储（服务端安全存储）
- 泄露危害更大，需严格保护

**ID Token（身份令牌）：**
- JWT格式，包含用户身份信息
- 仅用于身份认证，不用于授权
- 有明确的受众（audience）限制

#### 6.2.2 令牌安全最佳实践

**Access Token安全：**
- 使用短有效期（15-30分钟）
- 遵循令牌受众（audience）限制
- 验证令牌签名和有效期
- 实现令牌撤销机制（Token Revocation）

**Refresh Token安全：**
- 服务端安全存储（加密存储）
- 绑定客户端信息（IP、User-Agent）
- 使用旋转刷新令牌（Rotation Refresh Token）
- 设置合理的有效期和闲置超时
- 支持立即撤销

**前端应用令牌安全：**
- 单页应用（SPA）使用Authorization Code + PKCE流程
- 避免在localStorage中存储令牌（XSS风险）
- 使用HttpOnly + Secure Cookie存储刷新令牌
- 实现令牌自动续期和过期处理

#### 6.2.3 令牌泄露应对

**检测令牌泄露：**
- 异常的地理位置访问
- 同一令牌多处同时使用
- 令牌使用量异常增加
- 异常的API调用模式

**应对措施：**
1. 立即撤销泄露的令牌
2. 撤销关联的刷新令牌
3. 通知用户重新认证
4. 审计令牌使用记录
5. 加强安全措施（MFA、设备绑定）

### 6.3 JWT安全配置

#### 6.3.1 JWT结构回顾

JWT（JSON Web Token）由三部分组成：Header.Payload.Signature

**Header：**
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

**Payload：**
```json
{
  "sub": "user123",
  "iss": "https://auth.example.com",
  "aud": "https://api.example.com",
  "exp": 1704067200,
  "iat": 1704063600,
  "scope": "read write"
}
```

#### 6.3.2 JWT常见安全问题

**1. 算法混淆攻击（Alg=none）**
攻击者将alg设置为none，服务器如果支持none算法就会接受无签名的令牌。

**防护：**
```python
# 明确指定允许的算法，禁用none
import jwt

decoded = jwt.decode(
    token,
    public_key,
    algorithms=["RS256", "ES256"],  # 白名单方式
    options={"verify_signature": True}
)
```

**2. 弱密钥（HS256 + 弱密钥）**
使用HS256算法时，如果密钥强度不足，攻击者可以暴力破解。

**防护：**
- HS256密钥长度至少256位（32字节随机字符串）
- 优先使用非对称算法（RS256、ES256）
- 定期轮换签名密钥

**3. 未验证所有声明（Claims）**
只验证签名而不验证exp、iss、aud等声明。

**必须验证的声明：**
- `exp`：过期时间
- `nbf`：生效时间
- `iss`：签发者
- `aud`：受众
- `iat`：签发时间（用于检测异常早的令牌）

#### 6.3.3 JWT安全最佳实践

```python
import jwt
import time
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.backends import default_backend

def create_jwt(user_id: str, private_key_path: str) -> str:
    """安全创建JWT"""
    with open(private_key_path, "rb") as f:
        private_key = serialization.load_pem_private_key(
            f.read(), password=None, backend=default_backend()
        )
    
    now = int(time.time())
    payload = {
        "sub": user_id,
        "iss": "https://auth.example.com",
        "aud": "https://api.example.com",
        "iat": now,
        "exp": now + 900,  # 15分钟过期
        "nbf": now,
        "jti": generate_unique_id(),  # 令牌唯一标识，用于撤销
    }
    
    return jwt.encode(payload, private_key, algorithm="RS256")

def verify_jwt(token: str, public_key_path: str) -> dict:
    """安全验证JWT"""
    with open(public_key_path, "rb") as f:
        public_key = serialization.load_pem_public_key(
            f.read(), backend=default_backend()
        )
    
    return jwt.decode(
        token,
        public_key,
        algorithms=["RS256"],
        audience="https://api.example.com",
        issuer="https://auth.example.com",
        options={
            "require": ["exp", "iat", "sub", "iss", "aud"],
            "verify_exp": True,
            "verify_iss": True,
            "verify_aud": True,
        }
    )
```

```python
import hvac
import os

class VaultClient:
    def __init__(self):
        self.client = hvac.Client(
            url=os.environ.get('VAULT_ADDR', 'https://vault.example.com:8200'),
            verify='/etc/ssl/certs/ca-bundle.crt'
        )
        self._authenticate()
    
    def _authenticate(self):
        """使用AppRole认证"""
        role_id = os.environ['VAULT_ROLE_ID']
        secret_id = os.environ['VAULT_SECRET_ID']
        self.client.auth.approle.login(
            role_id=role_id,
            secret_id=secret_id
        )
    
    def get_secret(self, path: str) -> dict:
        """读取KV密钥"""
        response = self.client.secrets.kv.v2.read_secret_version(path=path)
        return response['data']['data']
    
    def get_db_credentials(self, role: str) -> tuple:
        """获取动态数据库凭证"""
        response = self.client.secrets.database.generate_credentials(name=role)
        return response['data']['username'], response['data']['password']
    
    def encrypt(self, plaintext: str, key_name: str) -> str:
        """使用Transit引擎加密"""
        response = self.client.secrets.transit.encrypt_data(
            name=key_name,
            plaintext=plaintext.encode().hex()
        )
        return response['data']['ciphertext']
```

```terraform
# 配置GitHub OIDC Provider
resource "aws_iam_openid_connect_provider" "github" {
  url             = "https://token.actions.githubusercontent.com"
```

### 7.3 案例3：凭证泄露事件应急响应

#### 7.3.1 事件背景

某SaaS公司安全团队收到GitGuardian告警，发现公司内部GitHub仓库的一个私有仓库中泄露了生产环境的AWS Access Key。该密钥具有S3全量访问权限，而公司的用户数据存储在S3中。

#### 7.3.2 应急响应过程

**T+0分钟：发现与确认**
- GitGuardian自动告警，安全团队收到通知
- 确认泄露的密钥ID：AKIAIOSFODNN7EXAMPLE
- 确认密钥权限：AmazonS3FullAccess
- 确认泄露位置：开源的内部工具项目中的config.py文件

**T+5分钟：遏制措施**
```bash
# 立即禁用泄露的AWS密钥
aws iam update-access-key \
  --access-key-id AKIAIOSFODNN7EXAMPLE \
  --status Inactive \
  --user-name prod-deployment-user

# 查看该密钥的最近使用记录
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIAIOSFODNN7EXAMPLE \
  --start-time $(date -d '7 days ago' +%s) \
  --max-results 50
```

**T+15分钟：影响评估**
- 检查CloudTrail日志，确认该密钥在过去24小时内的使用情况
- 发现来自陌生IP（45.x.x.x）的多次S3 List和Get操作
- 确认攻击者访问了约5个存储桶
- 初步估计可能泄露的数据量约100GB用户数据

**T+30分钟：深度遏制**
- 立即删除泄露的IAM用户密钥
- 创建新的密钥并更新所有合法使用点
- 临时限制S3访问，只允许白名单IP访问
- 启用S3访问日志的实时分析
- 保存所有相关日志用于取证

**T+1小时：调查分析**
- 追溯代码提交历史，确认凭证是在3个月前的一次重构中被提交
- 提交者为已离职员工，当时未做代码审查
- 仓库是在1周前被意外设为公开（原因为配置错误）
- 攻击者通过GitHub搜索功能发现了该密钥

**T+2小时：根因分析**
- 直接原因：代码中硬编码AWS密钥 + 仓库意外公开
- 根本原因：
  - 缺乏代码凭证扫描机制
  - 仓库权限管理不严格
  - 新员工安全培训不到位
  - 缺乏基础设施即代码的权限管理

**T+24小时：恢复与改进**
- 确认数据泄露范围，通知受影响用户
- 全面审查所有代码仓库的凭证情况
- 部署Gitleaks到所有CI/CD流水线
- 实施最小权限策略，缩减AWS密钥权限
- 建立代码审查流程和安全检查卡点
- 加强员工安全意识培训

#### 7.3.3 经验总结

1. **预防胜于治疗**：建立前置的凭证扫描机制远比事后响应更有效
2. **最小权限原则**：即使密钥泄露，限制权限也能降低损失
3. **监控与告警**：快速发现是减少损失的关键
4. **流程保障**：不能依赖个人意识，必须有流程和工具保障
5. **定期演练**：定期进行应急响应演练，确保团队熟悉流程

### 4.1 环境变量与配置管理

#### 4.1.1 环境变量的安全使用

环境变量是将配置与代码分离的常用方式，但如果处理不当，仍然存在安全风险。

**最佳实践：**

1. **使用.env文件 + .gitignore**
   ```
   # .gitignore
   .env
   .env.local
   .env.*.local
   *.key
   *.pem
   ```

2. **提供.env.example模板**
   ```
   # .env.example - 只包含键名和占位符，不包含真实值
   DB_HOST=localhost
   DB_PORT=5432
   DB_USER=your_username
   DB_PASSWORD=your_secure_password
   API_KEY=your_api_key_here
   ```

3. **环境变量分级管理**
   - 开发环境（development）：使用本地开发凭证
   - 测试环境（staging）：使用测试环境专用凭证
   - 生产环境（production）：使用生产环境凭证，严格控制访问

#### 4.1.2 配置文件加密方案

对于必须存储在文件中的敏感配置，应采用加密保护。

### 4.2 密钥管理服务详解

#### 4.2.1 AWS KMS实战

**创建客户托管密钥：**
```python
import boto3

kms = boto3.client('kms', region_name='us-east-1')

# 创建对称加密密钥
response = kms.create_key(
    Description='Application data encryption key',
    KeyUsage='ENCRYPT_DECRYPT',
    Origin='AWS_KMS',
    Tags=[
        {'TagKey': 'Environment', 'TagValue': 'Production'},
        {'TagKey': 'Application', 'TagValue': 'PaymentService'}
    ]
)

key_id = response['KeyMetadata']['KeyId']
print(f"Created key: {key_id}")

# 启用自动轮换
kms.enable_key_rotation(KeyId=key_id)
```

**使用KMS加密数据：**
```python
# 加密数据
ciphertext = kms.encrypt(
    KeyId=key_id,
    Plaintext=b'Sensitive data to encrypt',
    EncryptionContext={'Purpose': 'customer_data'}
)['CiphertextBlob']

# 解密数据
plaintext = kms.decrypt(
    CiphertextBlob=ciphertext,
    EncryptionContext={'Purpose': 'customer_data'}
)['Plaintext']
```

**信封加密（Envelope Encryption）：**
```python
# 生成数据密钥（DEK）
data_key = kms.generate_data_key(
    KeyId=key_id,
    KeySpec='AES_256'
)

# 明文DEK用于加密数据（本地加密）
plaintext_dek = data_key['Plaintext']
encrypted_dek = data_key['CiphertextBlob']

# 用DEK加密实际数据（使用AES等对称算法）
# encrypted_data = aes_encrypt(data, plaintext_dek)

# 存储：加密后的数据 + 加密后的DEK
# 下次使用时：先用KMS解密DEK，再用DEK解密数据
```

### 4.4 CI/CD流水线凭证管理

#### 4.4.1 CI/CD凭证风险点

CI/CD流水线通常拥有访问代码仓库、云平台、部署环境等多种高权限凭证，是攻击者的重点目标。

#### 4.4.2 GitHub Actions凭证安全

```yaml
name: Deploy to Production

on:
  push:
    branches: [main]

env:
  AWS_REGION: us-east-1

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production  # 环境保护规则
    permissions:
      contents: read
      id-token: write        # OIDC联邦所需权限

      - uses: actions/checkout@v4

      - name: Configure AWS credentials
```

## 第6章 API密钥与令牌安全

### 6.1 API密钥最佳实践

#### 6.1.1 API密钥设计原则

**密钥命名规范：**
- 使用前缀标识环境和用途：`sk_live_`、`sk_test_`、`pk_prod_`
- 密钥长度建议：至少32字节的随机数据（base64编码后约43字符）
- 包含可校验前缀，便于快速识别

**安全设计：**
1. **服务端只存储哈希值**：类似密码，API密钥也应哈希存储
2. **密钥指纹**：使用密钥的前几位或哈希值作为标识
3. **过期机制**：设置密钥有效期，支持自动过期
4. **速率限制**：每个密钥独立的速率限制
5. **IP白名单**：高安全等级的密钥可绑定IP

#### 6.1.2 API密钥存储与传输

**传输安全：**
- 必须使用HTTPS传输
- 禁止在URL参数中传递API密钥（会被日志记录）
- 使用Authorization请求头传递
- 避免在客户端（浏览器、移动APP）存储长期API密钥

**正确方式：**
```http
GET /api/v1/users HTTP/1.1
Host: api.example.com
Authorization: Bearer sk_live_abc123def456...
```

**错误方式：**
```http
GET /api/v1/users?api_key=sk_live_abc123... HTTP/1.1
Host: api.example.com
```

**服务端存储：**
```python
import hashlib
import secrets
import hmac

def generate_api_key(prefix: str = "sk") -> tuple[str, str]:
    """生成API密钥，返回(明文密钥, 哈希值)"""
    raw_key = secrets.token_bytes(32)
    api_key = f"{prefix}_{raw_key.hex()}"
    # 使用SHA-256哈希存储
    key_hash = hashlib.sha256(api_key.encode()).hexdigest()
    return api_key, key_hash

def verify_api_key(api_key: str, stored_hash: str) -> bool:
    """验证API密钥"""
    computed_hash = hashlib.sha256(api_key.encode()).hexdigest()
    return hmac.compare_digest(computed_hash, stored_hash)
```

#### 6.1.3 API密钥生命周期管理

**创建阶段：**
- 明确密钥的用途和所有者
- 设置适当的权限范围（Scope）
- 设置过期时间
- 记录创建人和创建时间

**使用阶段：**
- 监控每个密钥的使用情况
- 检测异常使用模式
- 定期审查密钥的必要性

**轮换阶段：**
- 支持双密钥并行（新旧密钥同时有效）
- 提供轮换过渡期（建议7-30天）
- 通知密钥所有者进行更新

**撤销阶段：**
- 支持立即撤销和定时撤销
- 记录撤销原因
- 审计撤销前的使用记录

### 6.2 OAuth令牌安全管理

#### 6.2.1 OAuth 2.0令牌类型

**Access Token（访问令牌）：**
- 用于访问受保护资源
- 生命周期短（通常15分钟到1小时）
- 应使用短有效期减少泄露风险
- 泄露后影响范围受限于权限和有效期

**Refresh Token（刷新令牌）：**
- 用于获取新的访问令牌
- 生命周期长（天/周/月级别）
- 必须安全存储（服务端安全存储）
- 泄露危害更大，需严格保护

**ID Token（身份令牌）：**
- JWT格式，包含用户身份信息
- 仅用于身份认证，不用于授权
- 有明确的受众（audience）限制

#### 6.2.2 令牌安全最佳实践

**Access Token安全：**
- 使用短有效期（15-30分钟）
- 遵循令牌受众（audience）限制
- 验证令牌签名和有效期
- 实现令牌撤销机制（Token Revocation）

**Refresh Token安全：**
- 服务端安全存储（加密存储）
- 绑定客户端信息（IP、User-Agent）
- 使用旋转刷新令牌（Rotation Refresh Token）
- 设置合理的有效期和闲置超时
- 支持立即撤销

**前端应用令牌安全：**
- 单页应用（SPA）使用Authorization Code + PKCE流程
- 避免在localStorage中存储令牌（XSS风险）
- 使用HttpOnly + Secure Cookie存储刷新令牌
- 实现令牌自动续期和过期处理

#### 6.2.3 令牌泄露应对

**检测令牌泄露：**
- 异常的地理位置访问
- 同一令牌多处同时使用
- 令牌使用量异常增加
- 异常的API调用模式

**应对措施：**
1. 立即撤销泄露的令牌
2. 撤销关联的刷新令牌
3. 通知用户重新认证
4. 审计令牌使用记录
5. 加强安全措施（MFA、设备绑定）

### 6.3 JWT安全配置

#### 6.3.1 JWT结构回顾

JWT（JSON Web Token）由三部分组成：Header.Payload.Signature

**Header：**
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

**Payload：**
```json
{
  "sub": "user123",
  "iss": "https://auth.example.com",
  "aud": "https://api.example.com",
  "exp": 1704067200,
  "iat": 1704063600,
  "scope": "read write"
}
```

#### 6.3.2 JWT常见安全问题

**1. 算法混淆攻击（Alg=none）**
攻击者将alg设置为none，服务器如果支持none算法就会接受无签名的令牌。

**防护：**
```python
# 明确指定允许的算法，禁用none
import jwt

decoded = jwt.decode(
    token,
    public_key,
    algorithms=["RS256", "ES256"],  # 白名单方式
    options={"verify_signature": True}
)
```

**2. 弱密钥（HS256 + 弱密钥）**
使用HS256算法时，如果密钥强度不足，攻击者可以暴力破解。

**防护：**
- HS256密钥长度至少256位（32字节随机字符串）
- 优先使用非对称算法（RS256、ES256）
- 定期轮换签名密钥

**3. 未验证所有声明（Claims）**
只验证签名而不验证exp、iss、aud等声明。

**必须验证的声明：**
- `exp`：过期时间
- `nbf`：生效时间
- `iss`：签发者
- `aud`：受众
- `iat`：签发时间（用于检测异常早的令牌）

#### 6.3.3 JWT安全最佳实践

```python
import jwt
import time
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.backends import default_backend

def create_jwt(user_id: str, private_key_path: str) -> str:
    """安全创建JWT"""
    with open(private_key_path, "rb") as f:
        private_key = serialization.load_pem_private_key(
            f.read(), password=None, backend=default_backend()
        )
    
    now = int(time.time())
    payload = {
        "sub": user_id,
        "iss": "https://auth.example.com",
        "aud": "https://api.example.com",
        "iat": now,
        "exp": now + 900,  # 15分钟过期
        "nbf": now,
        "jti": generate_unique_id(),  # 令牌唯一标识，用于撤销
    }
    
    return jwt.encode(payload, private_key, algorithm="RS256")

def verify_jwt(token: str, public_key_path: str) -> dict:
    """安全验证JWT"""
    with open(public_key_path, "rb") as f:
        public_key = serialization.load_pem_public_key(
            f.read(), backend=default_backend()
        )
    
    return jwt.decode(
        token,
        public_key,
        algorithms=["RS256"],
        audience="https://api.example.com",
        issuer="https://auth.example.com",
        options={
            "require": ["exp", "iat", "sub", "iss", "aud"],
            "verify_exp": True,
            "verify_iss": True,
            "verify_aud": True,
        }
    )
```

```python
        response = self.client.secrets.kv.v2.read_secret_version(path=path)

    def encrypt(self, plaintext: str, key_name: str) -> str:
```

```bash
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIAIOSFODNN7EXAMPLE \
  --start-time $(date -d '7 days ago' +%s) \
  --max-results 50
```

**T+15分钟：影响评估**
- 检查CloudTrail日志，确认该密钥在过去24小时内的使用情况
- 发现来自陌生IP（45.x.x.x）的多次S3 List和Get操作
- 确认攻击者访问了约5个存储桶
- 初步估计可能泄露的数据量约100GB用户数据

**T+30分钟：深度遏制**
- 立即删除泄露的IAM用户密钥
- 创建新的密钥并更新所有合法使用点
- 临时限制S3访问，只允许白名单IP访问
- 启用S3访问日志的实时分析
- 保存所有相关日志用于取证

**T+1小时：调查分析**
- 追溯代码提交历史，确认凭证是在3个月前的一次重构中被提交
- 提交者为已离职员工，当时未做代码审查
- 仓库是在1周前被意外设为公开（原因为配置错误）
- 攻击者通过GitHub搜索功能发现了该密钥

**T+2小时：根因分析**
- 直接原因：代码中硬编码AWS密钥 + 仓库意外公开
- 根本原因：
  - 缺乏代码凭证扫描机制
  - 仓库权限管理不严格
  - 新员工安全培训不到位
  - 缺乏基础设施即代码的权限管理

**T+24小时：恢复与改进**
- 确认数据泄露范围，通知受影响用户
- 全面审查所有代码仓库的凭证情况
- 部署Gitleaks到所有CI/CD流水线
- 实施最小权限策略，缩减AWS密钥权限
- 建立代码审查流程和安全检查卡点
- 加强员工安全意识培训

#### 7.3.3 经验总结

1. **预防胜于治疗**：建立前置的凭证扫描机制远比事后响应更有效
2. **最小权限原则**：即使密钥泄露，限制权限也能降低损失
3. **监控与告警**：快速发现是减少损失的关键
4. **流程保障**：不能依赖个人意识，必须有流程和工具保障
5. **定期演练**：定期进行应急响应演练，确保团队熟悉流程
