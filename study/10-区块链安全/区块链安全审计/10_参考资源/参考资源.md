#### 3. Slither 高级用法

```bash
# 1. 打印合约摘要
slither . --print contract-summary --json - | jq

# 2. 打印函数摘要
slither . --print function-summary

# 3. 打印继承关系图（需要 graphviz）
slither . --print inheritance-graph
dot -Tpng inheritance-graph.dot -o inheritance-graph.png

# 4. 打印调用图
slither . --print call-graph
dot -Tpng call-graph.dot -o call-graph.png

# 5. 导出所有发现为 JSON
slither . --json slither_results.json 2>/dev/null

# 6. 与 GitHub CI 集成
# .github/workflows/slither.yml
# - uses: crytic/slither-action@v0.3.0
#   with:
#     fail-on: high

# 7. 使用 Slitherin 插件（增强检测器）
pip install slitherin
slither . --checklist --plugin slitherin

# 8. 对比两个版本的合约差异
slither . --compare-to old_contract.sol

# 9. 检查特定合约的特定问题
slither contracts/Token.sol \
  --detect reentrancy-eth,reentrancy-no-eth,reentrancy-benign,reentrancy-events \
  --high-mediums
```

### 二、审计方法与流程实操

#### 1. 标准审计流程脚本

```bash
#!/bin/bash
# 智能合约审计启动脚本
# 用法: ./audit_setup.sh <项目目录>

PROJECT_DIR=$1
AUDIT_DIR="audit_output"

cd $PROJECT_DIR

# 创建审计输出目录
mkdir -p $AUDIT_DIR/{reports,findings,notes,poCs}

echo "=========================================="
echo "智能合约审计 - 启动流程"
echo "=========================================="

# 阶段1：信息收集
echo ""
echo "[1/6] 信息收集..."
echo "  - 项目名称: $(basename $PROJECT_DIR)"
echo "  - Solidity 版本: $(grep -r "pragma solidity" contracts/ 2>/dev/null | head -1 | grep -oP '\d+\.\d+\.\d+' | head -1)"
echo "  - 合约数量: $(find contracts -name "*.sol" | wc -l)"
echo "  - 代码行数: $(find contracts -name "*.sol" -exec cat {} \; | wc -l)"

# 阶段2：编译检查
echo ""
echo "[2/6] 编译检查..."
if [ -f "foundry.toml" ]; then
    forge build 2>&1 | tail -5
    echo "  Foundry 项目 ✓"
elif [ -f "hardhat.config.js" ] || [ -f "hardhat.config.ts" ]; then
    npx hardhat compile 2>&1 | tail -5
    echo "  Hardhat 项目 ✓"
fi

# 阶段3：Slither 扫描
echo ""
echo "[3/6] Slither 静态分析..."
slither . \
  --filter-paths "node_modules|test|mock|interface" \
  --json $AUDIT_DIR/reports/slither.json \
  2>/dev/null
echo "  报告: $AUDIT_DIR/reports/slither.json"

# 阶段4：生成审计清单
echo ""
echo "[4/6] 生成审计清单..."
slither . --checklist 2>/dev/null > $AUDIT_DIR/reports/checklist.md
echo "  清单: $AUDIT_DIR/reports/checklist.md"

# 阶段5：可视化分析
echo ""
echo "[5/6] 生成可视化图表..."
slither . --print inheritance 2>/dev/null > $AUDIT_DIR/reports/inheritance.md
slither . --print contract-summary 2>/dev/null > $AUDIT_DIR/reports/contract-summary.md
echo "  继承关系: $AUDIT_DIR/reports/inheritance.md"

# 阶段6：测试覆盖率
echo ""
echo "[6/6] 测试覆盖率分析..."
if [ -f "foundry.toml" ]; then
    forge coverage --report summary 2>&1 | tail -10
fi

echo ""
echo "=========================================="
echo "审计准备完成，开始人工审核"
echo "=========================================="
echo ""
echo "建议审核顺序："
echo "  1. 先看 Slither 高风险发现"
echo "  2. 理解合约架构（继承图）"
echo "  3. 从核心业务逻辑入手"
echo "  4. 检查访问控制和权限管理"
echo "  5. 检查外部调用和资金流转"
echo "  6. 编写 PoC 验证漏洞"
```

### 三、审计检查清单

#### 1. 通用安全检查清单

```markdown
## 智能合约审计检查清单

### 🔐 访问控制
- [ ] 是否存在未授权的关键函数（mint/burn/withdraw/pause）
- [ ] owner / admin 权限是否合理分配
- [ ] 是否使用 tx.origin 进行身份验证（应避免）
- [ ] 是否存在权限升级路径（selfdestruct → 控制权转移）
- [ ] 多签钱包配置是否正确
- [ ] 时间锁（Timelock）配置是否合理
- [ ] 是否有暂停机制（Pausable），暂停后哪些功能被禁用

### 💰 资金安全
- [ ] 所有转账函数是否检查返回值或使用 safeTransfer
- [ ] 是否存在重入风险（Checks-Effects-Interactions 模式）
- [ ] 是否使用 ReentrancyGuard
- [ ] 资金是否可以被正确提取（不会永久锁定）
- [ ] 手续费计算是否正确（精度损失）
- [ ] 是否存在闪电贷攻击风险

### 📊 数学运算
- [ ] 是否存在溢出/下溢风险（Solidity 0.8+ 自动检查）
- [ ] 除法是否有精度损失问题
- [ ] 乘法是否可能溢出（先乘后除 vs 先除后乘）
- [ ] 百分比计算是否正确（basis points 处理）
- [ ] 是否存在舍入误差被利用的可能

### 🔄 逻辑正确性
- [ ] 业务逻辑是否与白皮书/文档一致
- [ ] 边界条件是否正确处理（0 值、最大值、空数组）
- [ ] 状态机转换是否正确
- [ ] 时间依赖是否可被操纵（block.timestamp）
- [ ] 随机数是否可预测（blockhash, block.timestamp）

### 📦 外部调用
- [ ] 外部调用是否处理了失败情况
- [ ] 是否存在 DoS 风险（外部调用失败导致卡住）
- [ ] 是否使用 Pull Payment 模式
- [ ] delegatecall 是否安全（目标合约可信）
- [ ] call 调用是否有重入风险
- [ ] 低级别调用（assembly call）是否安全

### 🎭 代币标准
- [ ] ERC20 是否完全符合标准（返回值、approve 竞态）
- [ ] ERC721/ERC1155 是否正确实现
- [ ] 是否存在代币通胀漏洞
- [ ] 铸币/销毁权限是否受控
- [ ] 转账手续费机制是否正确
- [ ] fee-on-transfer 代币是否正确处理

### 🏗️ 合约架构
- [ ] 继承关系是否合理（继承顺序、菱形继承）
- [ ] 初始化函数是否可被多次调用
- [ ] 代理合约实现是否正确（存储冲突、初始化）
- [ ] 升级机制是否安全（透明代理/UUPS）
- [ ] 是否存在自毁风险（selfdestruct 强制转入 ETH）
- [ ] 接口是否正确定义（函数选择器冲突）

### 📝 代码质量
- [ ] 是否有未使用的变量/导入/函数
- [ ] 命名是否清晰一致
- [ ] 是否有注释说明复杂逻辑
- [ ] 是否有重复代码（应抽取为内部函数）
- [ ] Shadow 变量是否存在
- [ ] Gas 优化是否引入安全问题
```

#### 3. 严重程度评估标准

| 级别 | 定义 | 示例 |
|------|------|------|
| **Critical** | 可直接盗取/冻结大量资金，或完全破坏协议 | 无限铸币、重入盗取全部资金、权限绕过 |
| **High** | 可盗取部分资金，或严重破坏功能 | 单用户资金被盗、预言机操纵、逻辑错误导致损失 |
| **Medium** | 有一定利用条件的资金损失，或功能受限 | 需要特定条件的 DoS、精度损失导致小量损失 |
| **Low** | 影响较小的问题，一般无直接资金损失 | 信息泄露、Gas 优化、最佳实践违反 |
| **Info** | 代码风格、建议、无实际安全影响 | 命名规范、注释、未使用代码 |
