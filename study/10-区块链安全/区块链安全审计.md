# 区块链安全审计指南

> 本文档详细介绍区块链安全审计的完整流程、检查清单、常见漏洞模式、报告撰写、工具使用和漏洞分级标准，帮助审计人员系统地开展智能合约安全审计工作。

---

## 一、智能合约审计概述

### 1.1 什么是智能合约审计

智能合约审计是由专业安全人员对智能合约代码进行系统性审查，发现其中的安全漏洞、逻辑缺陷和潜在风险，并提供修复建议的过程。

**审计的目的：**
- 发现并修复安全漏洞
- 降低被攻击风险
- 保护用户资产安全
- 提高项目可信度
- 符合行业标准和监管要求

### 1.2 为什么需要审计

| 原因 | 说明 |
|------|------|
| **代码即法律** | 智能合约一旦部署不可篡改，漏洞无法在线修复 |
| **资产价值高** | 合约中往往锁定巨额资产，攻击收益巨大 |
| **攻击成本低** | 攻击者只需找到一个漏洞即可获利 |
| **不可逆** | 被盗资金几乎无法追回 |
| **行业惯例** | 头部 DeFi 项目都会进行多次审计 |
| **用户信任** | 审计报告是用户评估项目安全性的重要参考 |

### 1.3 审计类型

| 类型 | 说明 | 适用场景 |
|------|------|---------|
| **首次审计** | 项目上线前的全面审计 | 新项目上线 |
| **迭代审计** | 代码更新后的增量审计 | 功能升级 |
| **紧急审计** | 发现漏洞后的快速审查 | 紧急修复 |
| **竞赛审计** | 通过赏金竞赛众包审计 | 提高安全性 |
| **形式化验证** | 使用数学方法证明正确性 | 高价值核心合约 |

### 2.2 各阶段详细说明

#### 阶段一：审计准备

**1. 项目接入**
- 签署保密协议（NDA）
- 确定审计范围和时间
- 明确交付物和沟通方式

**2. 资料收集**
- 项目白皮书/技术文档
- 智能合约源代码
- 架构设计文档
- 业务逻辑说明
- 已有的审计报告（如有）

**3. 审计范围确认**
- 明确审计的合约列表
- 确认代码版本（commit hash）
- 确定审计重点和优先级
- 确认是否包含经济模型审计

#### 阶段二：代码审查

**4. 架构分析**
- 理解整体架构设计
- 梳理合约继承关系
- 分析合约间交互关系
- 识别核心模块和风险点
- 绘制合约关系图

**5. 工具扫描**
- 使用 Slither 进行静态分析
- 使用 Mythril 进行符号执行
- 运行 linter 检查代码规范
- 记录工具发现的问题
- 对工具结果进行人工验证

**6. 人工逐行审查**
- 逐行阅读代码
- 检查常见漏洞模式
- 验证业务逻辑正确性
- 检查权限控制
- 分析数学运算安全性
- 检查外部调用处理

#### 阶段三：漏洞验证

**7. 漏洞发现**
- 整理所有发现的问题
- 分类记录漏洞类型
- 确认每个漏洞的触发条件
- 评估影响范围

**8. PoC 编写**
- 为每个关键漏洞编写概念验证代码
- 在测试环境中复现漏洞
- 验证漏洞的真实性
- 记录复现步骤

**9. 风险评估**
- 评估每个漏洞的严重程度
- 评估利用难度
- 评估影响范围
- 确定修复优先级

#### 阶段四：报告与修复

**10. 初步报告**
- 撰写详细的审计发现
- 提供修复建议
- 提交给项目方
- 与项目方沟通确认

**11. 修复验证**
- 审核项目方的修复代码
- 验证漏洞是否已修复
- 检查是否引入新漏洞
- 对修复进行回归测试

**12. 最终报告**
- 更新审计报告
- 添加修复验证结果
- 给出最终安全评估
- 发布正式审计报告

## 三、审计检查清单

### 3.1 通用安全检查清单

#### 3.1.1 权限控制

| 检查项 | 说明 | 风险等级 |
|--------|------|---------|
| 敏感函数是否有权限修饰符 | mint、burn、withdraw 等函数是否有 onlyOwner 等 | 高危 |
| 权限检查是否正确 | 是否使用 msg.sender 而非 tx.origin | 高危 |
| 权限是否最小化 | 是否每个角色只有必要的权限 | 中危 |
| 权限转移是否安全 | 所有权转移是否有安全确认 | 中危 |
| 初始化函数是否受保护 | initialize 函数是否只能调用一次 | 高危 |
| 构造函数是否正确 | 是否有拼写错误（旧版本） | 高危 |

#### 3.1.2 数学运算

| 检查项 | 说明 | 风险等级 |
|--------|------|---------|
| 是否有溢出风险 | 0.8 以下版本是否使用 SafeMath | 高危 |
| 除法精度问题 | 除法是否先乘后除避免精度损失 | 中危 |
| 舍入方向是否正确 | 舍入是否对用户有利而非对合约有利 | 中危 |
| 零除保护 | 除数是否可能为零 | 高危 |
| 数组越界 | 数组访问是否有边界检查 | 高危 |

#### 3.1.3 外部调用

| 检查项 | 说明 | 风险等级 |
|--------|------|---------|
| 是否检查返回值 | call/send 的返回值是否检查 | 高危 |
| 重入风险 | 外部调用前是否已更新状态 | 高危 |
| 调用顺序 | 是否遵循 Checks-Effects-Interactions | 高危 |
| Gas 限制 | 是否控制外部调用的 Gas 量 | 中危 |
| 可信合约 | 外部调用的合约是否可信 | 中危 |
| delegatecall 安全 | delegatecall 的目标合约是否可信 | 高危 |

#### 3.1.4 状态管理

| 检查项 | 说明 | 风险等级 |
|--------|------|---------|
| 状态更新顺序 | 是否先更新状态后外部调用 | 高危 |
| 状态变量可见性 | 敏感变量是否设为 private | 低危 |
| 初始化顺序 | 继承合约的初始化顺序是否正确 | 中危 |
| 存储布局 | 代理合约的存储布局是否一致 | 高危 |

### 3.2 业务逻辑检查清单

#### 3.2.1 代币合约（ERC20）

| 检查项 | 说明 |
|--------|------|
| 精度计算 | decimals 是否正确处理 |
| 总量控制 | totalSupply 是否与实际铸造量一致 |

| 销毁逻辑 | burn 函数是否正确减少总量 |
| 黑白名单 | 黑白名单机制是否正确实现 |

#### 3.2.2 借贷协议

| 检查项 | 说明 |
|--------|------|
| 价格预言机 | 价格来源是否安全，是否可被操纵 |
| 抵押率计算 | LTV 计算是否正确 |
| 清算逻辑 | 清算触发条件和奖励是否正确 |
| 利率模型 | 利率计算是否正确 |
| 流动性风险 | 是否可能发生挤兑 |
| 闪电贷风险 | 是否能抵御闪电贷攻击 |

#### 3.2.3 DEX/AMM

| 检查项 | 说明 |
|--------|------|
| 定价公式 | xy=k 等定价公式是否正确实现 |
| 滑点保护 | 是否有最小输出量检查 |
| 手续费计算 | 手续费收取和分配是否正确 |
| LP 代币 | 流动性凭证的铸造和销毁是否正确 |
| 无常损失 | 是否有相关机制缓解 |
| 前置交易 | 是否有防抢跑机制 |

### 3.3 合约升级检查清单

## 四、常见漏洞模式

| **SWC-105** | Unprotected Ether Withdrawal | 未保护的 ETH 提取 |

### 4.3 漏洞模式识别指南

#### 4.3.1 快速识别重入攻击

**搜索关键词：** `.call{value:`、`send(`、`transfer(`、`.value(`

**检查要点：**
1. 外部调用前是否更新了状态？
2. 是否使用了 nonReentrant 修饰符？
3. 是否遵循 Checks-Effects-Interactions 模式？

#### 4.3.2 快速识别权限问题

**搜索关键词：** `onlyOwner`、`require(msg.sender`、`tx.origin`、`function mint`、`function burn`

**检查要点：**
1. 敏感函数是否有权限修饰符？
2. 是否使用了 tx.origin 做验证？
3. 初始化函数是否只能调用一次？

#### 4.3.3 快速识别溢出问题

**搜索关键词：** `+`、`-`、`*`、`/`、`SafeMath`、`unchecked`

**检查要点：**
1. Solidity 版本是否低于 0.8？
2. 是否使用了 SafeMath？
3. 循环中是否有 i++ 的边界检查？

#### 4.3.4 快速识别预言机问题

**搜索关键词：** `price`、`oracle`、`getReserves`、`spot`、`twap`

**检查要点：**
1. 价格来源是现货还是 TWAP？
2. 是否可以被闪电贷操纵？
3. 是否有多重价格源？

## 五、审计报告撰写

### 5.1 审计报告结构

一份标准的智能合约审计报告通常包含以下部分：

```
1. 执行摘要（Executive Summary）
   ├─ 项目概述
   ├─ 审计范围
   ├─ 审计时间
   ├─ 整体评价
   └─ 漏洞统计

2. 审计方法（Audit Methodology）
   ├─ 静态分析
   ├─ 动态分析
   ├─ 人工审查
   ├─ 工具列表
   └─ 测试环境

3. 审计发现（Findings）
   ├─ 高危漏洞（Critical）
   ├─ 中危漏洞（High）
   ├─ 低危漏洞（Medium）
   ├─ 信息提示（Low）
   └─ 代码优化建议（Informational）

4. 详细漏洞分析
   └─ 每个漏洞包含：
      ├─ 漏洞标题
      ├─ 风险等级
      ├─ 影响范围
      ├─ 漏洞描述
      ├─ 漏洞代码
      ├─ 利用方式 / PoC
      ├─ 修复建议
      └─ 修复状态

5. 附录
   ├─ 合约文件列表
   ├─ 参考资料
   └─ 审计团队介绍
```

### 5.2 单个漏洞描述模板

```markdown
## [漏洞编号] 漏洞标题

**风险等级：** Critical / High / Medium / Low / Informational

**影响合约：** 合约名.sol（行号范围）

**漏洞描述：**
详细描述漏洞的原理和触发条件。

**漏洞代码：**
```solidity
// 有问题的代码片段
function vulnerableFunction() public {
    // ...
}
```

**利用方式：**
描述攻击者如何利用这个漏洞，可能造成的最大损失。

**概念验证（PoC）：**
```solidity
// PoC 代码
contract Attacker {
    // ...
}
```

**修复建议：**
```solidity
// 修复后的代码
function secureFunction() public {
    // ...
}
```

**修复状态：** 待修复 / 修复中 / 已修复 / 已验证

**参考链接：**
- SWC-XXX: ...
- 相关案例...
```

### 5.3 撰写注意事项

1. **客观准确**：基于事实，不夸大不缩小
2. **清晰易懂**：让开发人员能够理解并复现
3. **可操作**：提供具体的修复建议，而非泛泛而谈
4. **完整**：包含所有必要的信息（位置、代码、PoC）
5. **专业**：使用规范的术语和格式
6. **保密**：报告发布前严格保密

### 5.4 常见的报告质量问题

| 问题 | 说明 |
|------|------|
| 描述模糊 | 漏洞描述不清，开发人员无法理解 |
| 缺少 PoC | 只有理论分析，没有实际验证 |
| 修复建议空泛 | 只说「修复这个问题」不说怎么修 |
| 风险等级不准确 | 高估或低估漏洞严重程度 |
| 代码引用错误 | 引用的代码行号或版本不对 |
| 遗漏重要信息 | 缺少影响范围、利用条件等 |

### 6.2 Slither 使用指南

**简介：** Trail of Bits 开发的 Solidity 静态分析工具，基于 Python，速度快，可扩展性强。

#### 安装

```bash
# 使用 pip 安装
pip install slither-analyzer

# 验证安装
slither --version
```

#### 常用命令

```bash
# 1. 基本分析（分析当前目录的所有合约）
slither .

# 2. 分析指定文件
slither contracts/MyContract.sol

# 3. 指定 Solidity 版本
slither . --solc-remaps '@openzeppelin=node_modules/@openzeppelin'

# 4. 只检测特定类型的漏洞
slither . --detect reentrancy
slither . --detect reentrancy-eth,reentrancy-no-eth
slither . --detect tx-origin
slither . --detect overflow

# 5. 排除特定检测器
slither . --exclude naming-convention,assembly

# 6. 输出 JSON 格式报告
slither . --json slither-report.json

# 7. 输出详细信息
slither . --print human-summary
slither . --print contract-summary
slither . --print function-summary
slither . --print inheritance
slither . --print call-graph

# 8. 与 Truffle/Hardhat 集成
slither . --truffle
slither . --hardhat

# 9. 检查代码规范
slither . --checklist > audit-checklist.md
```

#### 常用检测器列表

| 检测器 | 检测内容 | 风险 |
|--------|---------|------|
| `reentrancy` | 重入攻击 | 高 |
| `reentrancy-eth` | ETH 重入 | 高 |
| `reentrancy-no-eth` | 非 ETH 重入 | 中 |
| `reentrancy-benign` | 良性重入 | 低 |
| `reentrancy-events` | 重入事件顺序 | 低 |
| `overflow` | 整数溢出（0.8 以下） | 高 |
| `underflow` | 整数下溢 | 高 |
| `tx-origin` | tx.origin 滥用 | 高 |
| `assembly` | 内联汇编使用 | 中 |
| `unchecked-lowlevel` | 未检查底层调用 | 高 |
| `unchecked-send` | 未检查 send 返回值 | 中 |
| `incorrect-equality` | 不正确的相等比较 | 中 |
| `different-erc20` | 不符合 ERC20 标准 | 中 |
| `naming-convention` | 命名规范 | 信息 |
| `constable-states` | 可设为 constant 的变量 | 优化 |
| `external-function` | 可设为 external 的函数 | 优化 |

#### 实战技巧

1. **先跑全量扫描**：`slither .` 获取整体情况
2. **过滤噪音**：用 `--exclude` 排除不重要的检测器
3. **人工验证**：工具结果可能有误报，需要人工确认
4. **结合代码理解**：理解业务逻辑才能判断真正的风险
5. **集成 CI/CD**：每次提交自动运行 Slither

### 6.3 Mythril 使用指南

**简介：** ConsenSys 开发的符号执行工具，可以检测多种智能合约漏洞。

#### 安装

```bash
pip install mythril
myth version
```

#### 常用命令

```bash
# 1. 分析本地合约
myth analyze contracts/MyContract.sol

# 2. 指定 Solidity 版本
myth analyze MyContract.sol --solv 0.8.0

# 3. 分析已部署的合约
myth analyze -a 0xContractAddress --rpc-infura mainnet
myth analyze -a 0xContractAddress --rpc http://localhost:8545

# 4. 设置超时时间
myth analyze MyContract.sol --execution-timeout 60

# 5. 输出详细信息
myth analyze MyContract.sol -v4

# 6. 指定检测的漏洞类型
myth analyze MyContract.sol -t 3

# 7. 输出 JSON 报告
myth analyze MyContract.sol -o json > mythril-report.json
```

#### 检测能力

Mythril 可以检测以下类型的漏洞：
- 整数溢出/下溢
- 重入攻击
- 未检查返回值
- 交易顺序依赖
- 时间戳依赖
- 断言失败
- 任意存储写入
- delegatecall 风险
- 等等

#### 实战技巧

1. **速度较慢**：符号执行比较耗时，建议先跑 Slither
2. **针对关键函数**：可以只分析特定函数提高速度
3. **配合 Slither**：Slither 快速发现，Mythril 深入验证
4. **调整超时**：复杂合约可能需要更长的执行时间

### 6.4 Foundry 测试指南

**简介：** 新一代智能合约开发和测试框架，基于 Rust，速度极快，支持模糊测试。

#### 安装

```bash
# 使用 foundryup 安装
curl -L https://foundry.paradigm.xyz | bash
foundryup

# 验证安装
forge --version
```

#### 测试示例

```solidity
// test/MyContract.t.sol
pragma solidity ^0.8.19;

import "forge-std/Test.sol";
import "../src/MyContract.sol";

contract MyContractTest is Test {
    MyContract public myContract;

    function setUp() public {
        myContract = new MyContract();
    }

    // 单元测试
    function testDeposit() public {
        myContract.deposit{value: 1 ether}();
        assertEq(myContract.balances(address(this)), 1 ether);
    }

    // 预期 revert 的测试
    function testWithdrawFail() public {
        vm.expectRevert("Insufficient balance");
        myContract.withdraw(1 ether);
    }

    // 模糊测试（fuzzing）
    function testFuzzDeposit(uint256 amount) public {
        // 假设 amount 不超过 100 ether
        amount = bound(amount, 0, 100 ether);
        
        uint256 balanceBefore = myContract.balances(address(this));
        myContract.deposit{value: amount}();
        assertEq(myContract.balances(address(this)), balanceBefore + amount);
    }

    // 不变量测试（invariant testing）
    function invariant_totalSupply() public {
        // 总供应量应该等于所有余额之和
        assertEq(myContract.totalSupply(), myContract.calculateTotalBalance());
    }
}
```

#### 常用命令

```bash
# 运行测试
forge test

# 查看详细输出
forge test -vvvv

# 只运行特定测试
forge test --match-test testDeposit
forge test --match-contract MyContractTest

# 显示覆盖率
forge coverage

# 生成 gas 报告
forge test --gas-report

# 部署合约
forge create MyContract --private-key <PRIVATE_KEY>
```

### 6.5 工具使用最佳实践

#### 推荐的工具组合

```
1. Slither：快速静态分析
   ↓
2. 人工审查：理解业务逻辑，检查常见漏洞
   ↓
3. Mythril/Manticore：符号执行深入分析
   ↓
4. Foundry/Echidna：单元测试 + 模糊测试
   ↓
5. 人工验证：确认所有发现，编写 PoC
```

#### 工具使用原则

1. **工具是辅助，不是替代**：人工审查始终是最重要的
2. **理解误报和漏报**：
   - 误报（False Positive）：工具报告了漏洞，但实际不存在
   - 漏报（False Negative）：实际有漏洞，但工具没发现
3. **结合业务逻辑**：工具只能发现模式化的漏洞，逻辑漏洞需要人工
4. **持续学习**：新的漏洞类型不断出现，工具也需要更新

## 七、漏洞分级标准

### 7.1 分级维度

漏洞的严重程度通常从以下几个维度评估：

| 维度 | 说明 | 权重 |
|------|------|------|
| **影响范围** | 漏洞可能造成的最大损失 | 高 |
| **利用难度** | 攻击者利用漏洞的难易程度 | 高 |
| **触发条件** | 触发漏洞需要的特殊条件 | 中 |
| **用户交互** | 是否需要用户配合（如钓鱼） | 中 |
| **前置条件** | 利用前需要满足的条件 | 中 |

### 7.2 五级分级标准

#### 严重（Critical）

**定义：** 可以直接导致巨额资金损失的漏洞，利用难度低，影响范围广。

**判定标准：**
- 可以直接窃取合约中的所有/大部分资金
- 利用条件简单，无需特殊权限
- 可被普通攻击者利用
- 造成的损失巨大（项目资金的 50% 以上）

**典型示例：**
- 无权限的 mint 函数（任何人可以无限铸币）
- 无权限的 withdraw 函数（任何人可以提取所有资金）
- 代理合约初始化漏洞（任何人可以成为 owner）
- 严重的重入漏洞（可提取全部资金）

#### 高危（High）

**定义：** 可能导致重大资金损失，但有一定利用条件。

**判定标准：**
- 可以导致显著的资金损失
- 利用需要一定条件（如持有一定代币、特定时机等）
- 或者影响范围有限
- 造成的损失较大（项目资金的 10%-50%）

**典型示例：**
- 价格预言机可被操纵（需闪电贷配合）
- 有权限控制但权限可被绕过
- 特定条件下的重入攻击
- 逻辑漏洞导致资金损失
- 签名重放漏洞

#### 中危（Medium）

**定义：** 可能造成一定损失，或利用难度较高的漏洞。

**判定标准：**
- 可以造成有限的资金损失
- 利用难度较高（需要特殊条件或用户配合）
- 或者影响范围较小
- 造成的损失中等（项目资金的 1%-10%）

**典型示例：**
- 整数溢出但需要特定数值
- 特定场景下的拒绝服务
- 有限的权限绕过
- 时间戳依赖（矿工可操纵）
- 交易顺序依赖（抢跑）

#### 低危（Low）

**定义：** 对资金安全影响较小，更多是代码质量或最佳实践问题。

**判定标准：**
- 很难直接导致资金损失
- 需要非常特殊的条件才能利用
- 主要影响用户体验或效率
- 造成的损失很小（< 1%）

**典型示例：**
- Gas 优化问题
- 代码规范问题
- 事件参数缺失
- 多余的代码
- 未使用的变量

#### 信息（Informational）

**定义：** 不影响安全性的代码优化建议或最佳实践提醒。

**判定标准：**
- 不影响合约安全性
- 纯粹是代码风格或优化建议
- 可读性、可维护性问题

**典型示例：**
- 命名不规范
- 缺少注释
- 可以使用更高效的写法
- 代码结构优化建议

### 7.3 风险矩阵

| 影响 \ 难度 | 容易利用 | 中等难度 | 难以利用 |
|------------|---------|---------|---------|
| **严重影响** | Critical | Critical | High |
| **较大影响** | High | High | Medium |
| **一般影响** | Medium | Medium | Low |
| **较小影响** | Low | Low | Informational |

### 7.4 修复优先级

| 等级 | 修复优先级 | 修复时限建议 |
|------|-----------|-------------|
| Critical | 立即修复 | 24 小时内 |
| High | 尽快修复 | 3-7 天 |
| Medium | 计划修复 | 1-2 周 |
| Low | 择机修复 | 下次迭代 |
| Informational | 可选修复 | 无要求 |

## 八、审计实战技巧

### 8.1 审计前准备

1. **环境搭建**
   - 安装 Node.js、Python、Foundry 等工具
   - 配置 Solidity 编译器版本管理
   - 安装 Slither、Mythril 等安全工具

2. **资料阅读**
   - 先读白皮书和技术文档，理解业务逻辑
   - 了解项目的核心功能和设计目标
   - 查看是否有已有的审计报告和已知问题

3. **代码获取**
   - 确认代码版本（commit hash）
   - 安装依赖（npm install / forge install）
   - 确保代码能正常编译

### 8.2 审计技巧

#### 技巧一：从架构入手

- 先画合约关系图
- 理解每个合约的职责
- 找出核心合约和边缘合约
- 优先审计核心合约

#### 技巧二：关注资金流向

- 追踪 ETH 和代币的流动路径
- 检查所有涉及资金转移的函数
- 重点关注 mint、burn、transfer、withdraw 等函数

#### 技巧三：检查权限边界

- 列出所有的权限角色
- 检查每个角色能做什么
- 验证权限检查是否在每个敏感函数上都正确

#### 技巧四：寻找边界情况

- 数值为 0 的情况
- 数值为最大值的情况
- 数组为空的情况
- 第一次调用的情况
- 合约余额为 0 的情况

#### 技巧五：假设攻击者视角

- 如果我是攻击者，我会怎么攻击？
- 哪里是最薄弱的环节？
- 攻击收益是否大于攻击成本？

### 8.3 常见陷阱

1. **只看代码不理解业务**：业务逻辑漏洞往往是最严重的
2. **过度依赖工具**：工具只能发现已知模式的漏洞
3. **忽略经济模型**：很多 DeFi 攻击是经济模型问题
4. **只看单个合约**：漏洞可能在合约交互中产生
5. **忽略继承关系**：漏洞可能在父合约中
6. **不写 PoC**：不验证就无法确认漏洞是否真实存在
