## 一、区块链安全概述

### 1.1 区块链信任模型

传统系统依赖中心化信任，区块链通过密码学和共识机制实现去信任化：

```
传统信任模型:
  用户 --> 中心化机构 --> 数据库
  信任点: 中心化机构

区块链信任模型:
  用户 --> P2P网络 --> 分布式账本
         |          |
         v          v
    密码学验证   共识机制
  信任点: 数学(密码学) + 经济激励(共识)
```

### 1.2 安全属性

| 安全属性 | 实现机制 | 威胁 |
|----------|----------|------|
| 不可篡改 | 哈希链 + 共识 | 51%攻击、长程攻击 |
| 去中心化 | P2P网络 | 女巫攻击、日蚀攻击 |
| 匿名性 | 地址+签名 | 交易追踪、侧信道 |
| 可用性 | 分布式节点 | DDoS、网络分区 |
| 一致性 | 共识协议 | 分叉、双花 |

## 二、PoW安全分析

### 2.1 PoW共识机制

```
PoW (Proof of Work) 工作流程:

  1. 交易广播到内存池
  2. 矿工选择交易构造区块
  3. 计算哈希: SHA256(SHA256(block_header))
  4. 调整nonce直到哈希 < 目标值
  5. 找到有效哈希 -> 广播区块
  6. 其他节点验证 -> 接受区块
  7. 矿工获得区块奖励

  区块头结构:
  +---------------------------+
  | 版本号 (4 bytes)          |
  | 前一区块哈希 (32 bytes)    |
  | Merkle根 (32 bytes)       |
  | 时间戳 (4 bytes)          |
  | 难度目标 (4 bytes)        |
  | Nonce (4 bytes)           |
  +---------------------------+
```

### 2.2 51%攻击

**攻击原理**

当攻击者控制超过50%的算力时，可以：

```
51%攻击流程:

  T0: 正常链: ... -> Block N -> Block N+1
  攻击者开始私下挖矿

  T1: 正常链: ... -> Block N -> Block N+1 -> Block N+2
  攻击者链: ... -> Block N -> Block N+1' -> Block N+2' (包含双花交易)

  T2: 正常链继续延伸
  攻击者链也继续延伸(因为算力>50%，会追上)

  T3: 攻击者链长度超过正常链
  -> 发布攻击者链
  -> 根据最长链原则，攻击者链成为主链
  -> 双花交易被确认
  -> 原始交易被回滚
```

**攻击条件**

```
算力要求: > 50% 网络总算力
实际安全: 需要 60-70% 算力才有把握

攻击成本估算:
  - 租用算力: NiceHash等平台
  - 购买矿机: 硬件+电力成本
  - 时间窗口: 需要足够时间追赶

  示例(BTC):
  网络算力: ~400 EH/s
  51%算力: ~200 EH/s
  每日电力成本: ~数百万美元
  -> BTC的51%攻击在经济上不可行

  示例(小币种):
  网络算力很低
  攻击成本可能低于数万美元
  -> ETC等小币种多次遭受51%攻击
```

**攻击影响**

```
1. 双花: 已经确认的交易被回滚
2. 拒绝服务: 攻击者可以审查特定交易
3. 信任危机: 导致币价暴跌
4. 链重组: 历史区块被替换
```

**防御措施**

```
1. 使用 checkpoint 机制
   - 定期固化区块
   - 防止深度重组

2. 等待足够确认数
   - 大额交易等待6+确认
   - 商家可设置更长等待时间

3. 合并挖矿
   - 与BTC共用算力
   - 提高攻击成本

4. 算力监控
   - 监控网络算力变化
   - 检测算力异常转移

5. 惩罚机制
   - 惩罚恶意矿工
   - 削减恶意出块者奖励
```

### 2.3 自私挖矿

**攻击原理**

自私挖矿（Selfish Mining）不需要51%算力，攻击者通过战略性隐瞒区块来获取超额收益：

```
正常挖矿:
  矿工A找到区块 -> 立即广播 -> 获得奖励

自私挖矿:
  矿工A找到区块 -> 隐瞒不广播
  其他矿工继续在旧链上挖矿(浪费算力)
  当其他矿工快要找到区块时:
    矿工A广播隐瞒的区块 -> 使其他矿工的区块作废
  -> 矿工A获得超额奖励比例
```

**收益分析**

```
攻击者算力占比: α

  α < 0.25: 无利可图(不考虑网络优势)
  α = 0.33: 盈亏平衡(假设网络传播优势)
  α > 0.33: 有利可图
  α = 0.50: 接近51%攻击收益

  关键因素: 网络传播优势
  - 攻击者需要快速传播区块
  - 需要网络延迟优势
```

**防御措施**

```
1. 区块时间戳验证
   - 检测异常区块发布时间

2. 叔块(uncle block)奖励
   - 给予被作废区块部分奖励
   - 降低自私挖矿收益

3. 观察网络行为
   - 统计孤块率异常
   - 检测矿工发布模式

4. 调整共识参数
   - 增加区块确认要求
   - 改进分叉解决策略
```

### 2.4 双花攻击

```
双花攻击类型:

1. 赛跑攻击 (Race Attack)
   - 向商家和不同节点同时发送冲突交易
   - 利用网络传播延迟
   - 需要0确认接受

2. 芬尼攻击 (Finney Attack)
   - 矿工预先挖好包含双花交易的区块
   - 在收到付款后立即发布预挖区块
   - 需要0确认接受

3. 替代历史攻击 (Alternative History Attack)
   - 需要51%算力
   - 构造替代链替换主链

4.矢量76攻击 (Vector76 Attack)
   - 结合赛跑和芬尼攻击
   - 利用确认数和时间差
```

**防御措施**

```
1. 等待足够确认数
   小额: 1-3确认
   中额: 3-6确认
   大额: 6+确认

2. 监控网络
   - 检测双花交易
   - 警告冲突交易

3. 多路传播
   - 通过多个节点验证交易
   - 确认全网已接收

4. 时间锁
   - 大额交易设置时间锁
   - 延迟确认增加安全
```

## 三、PoS安全分析

### 3.1 PoS共识机制

```
PoS (Proof of Stake) 核心思想:
  - 持币越多，出块概率越高
  - 投入经济价值替代算力
  - 不需要大量能源消耗

PoS变体:
  - 链上PoS (Ethereum 2.0, Cardano)
  - 委托PoS (DPoS - EOS, Tron)
  - 租赁PoS (LPoS - Waves)
  - 权威PoS (AuPoS - xDai)

Ethereum 2.0 PoS流程:
  1. 验证者质押32 ETH
  2. 随机选择出块验证者
  3. 验证者出块并获得奖励
  4. 其他验证者 attest (证明)
  5. 区块达到2/3 attest -> 最终确认
```

### 3.2 Nothing at Stake

**问题原理**

```
PoW中的分叉:
  矿工只能在一个链上挖矿(算力不可复制)
  -> 在最长的链上挖矿是理性选择

PoS中的分叉:
  验证者可以在所有分叉上同时出块(币可以"复制"投票)
  -> 没有成本在所有链上投票
  -> 如果分叉链最终胜出，验证者获益
  -> 理性策略：在所有分叉上投票
```

**防御措施**

```
1. 削减机制 (Slashing)
   - 检测到在多个分叉上签名
   - 削减验证者质押的ETH
   - 驱逐验证者

  削减条件:
  - 双签 (同一slot在两个分叉签名)
  - 环绕投票 (surround vote)
  - 削减金额: 1/32 质押 -> 全部质押(重复违规)

2. 检查点 (Checkpoint)
   - 定期设置检查点
   - 防止长程重组

3. 弱主观性 (Weak Subjectivity)
   - 新节点需要从可信源获取最近的检查点
   - 防止从创世区块同步导致的攻击
```

### 3.3 长程攻击

**攻击原理**

```
长程攻击 (Long Range Attack):

  1. 攻击者获取旧私钥(曾持有大量币的地址)
  2. 从该地址活跃的早期区块开始分叉
  3. 利用旧私钥在分叉链上签名
  4. 构造一条很长的替代链
  5. 发布替代链替代主链

  与51%攻击区别:
  - 不需要持续的大量算力/币权
  - 利用历史私钥
  - 从早期区块分叉
```

**防御措施**

```
1. 检查点机制
   - 社区或协议定期固化检查点
   - 检查点之前的区块不可重组

2. 密钥轮换
   - 验证者定期更新签名密钥
   - 旧密钥失去效力

3. 时间戳验证
   - 区块时间戳不能过远
   - 限制分叉链的构造

4. 弱主观性
   - 新节点从可信检查点同步
   - 不从创世区块完全同步

5. 削减机制
   - 检测异常的分叉签名行为
```

### 3.4 币权集中风险

```
PoS集中度问题:

  - 富者愈富: 大额质押者获得更多奖励
  - 交易所集中: 大量用户币存交易所
  - 质押池集中: LSD协议集中质押
  - 验证者集中: 专业节点运营商集中

  风险:
  - 中心化导致审查
  - 监管压力下可能强制配合
  - 单点故障
  - 治理被少数人控制

  缓解:
  - 去中心化质押池
  - 限制单验证者最大质押
  - 随机出块选择
  - DVT分布式验证者技术
```

## 四、P2P网络攻击

### 4.1 女巫攻击

**攻击原理**

攻击者在P2P网络中创建大量虚假节点身份，控制网络通信：

```
正常网络:
  节点A <--> 节点B <--> 节点C
  每个节点是真实的

女巫攻击:
  节点A <--> [Sybil1, Sybil2, Sybil3, ...] <--> 节点B
  攻击者创建大量假节点
  - 影响路由
  - 影响投票
  - 实施审查
```

**区块链中的影响**

```
1. 交易审查
   - 女巫节点拒绝转发特定交易
   - 阻断合法交易传播

2. 区块传播延迟
   - 延迟区块传播
   - 增加分叉概率

3. 路由控制
   - 控制节点间通信路径
   - 配合日蚀攻击

4. 投票影响(在DPoS等)
   - 影响出块者选举
   - 影响治理投票
```

**防御措施**

```
1. 身份成本
   - PoW: 创建节点需要算力(挖矿成本)
   - PoS: 创建验证者需要质押
   - 许可链: 需要准入认证

2. 信任计算
   - 基于声誉的信任模型
   - 随机选择连接节点

3. 网络层防护
   - 限制单IP连接数
   - 随机化节点选择
   - 使用多样化网络层
```

### 4.2 日蚀攻击

**攻击原理**

日蚀攻击（Eclipse Attack）将目标节点与网络的连接完全隔离，使其只能与攻击者节点通信：

```
正常状态:
  受害者 <--> 网络中多个节点
  受害者获得全网信息

日蚀攻击后:
  受害者 <--> 攻击者控制的节点(看似多个)
  受害者只能获得攻击者提供的信息

  攻击效果:
  - 0确认双花: 受害者看到虚假交易
  - 区块延迟: 受害者获取区块延迟
  - 算力浪费: 矿工在旧链上挖矿
```

**攻击步骤**

```
1. 信息收集
   - 获取目标节点的出站连接IP
   - 分析目标节点的连接模式

2. 节点占位
   - 攻击者在目标节点地址池中填入攻击者IP
   - 等待目标节点重启或连接超时

3. 隔离
   - 目标节点重启后连接到攻击者节点
   - 攻击者节点拒绝其他节点连接
   - 目标完全被隔离

4. 利用
   - 向受害者提供虚假信息
   - 实施双花或延迟攻击
```

**防御措施**

```
1. 随机化连接
   - 随机选择出站连接节点
   - 不信任单一路径

2. 地址表多样性
   - 维护多样化的地址表
   - 不全部替换为新地址

3. 连接验证
   - 验证节点提供的区块是否与已知一致
   - 检测信息不一致

4. 锚定连接
   - 保持与已知可信节点的连接
   - 定期验证连接有效性

5. 感知延迟
   - 检测异常的网络延迟
   - 怀疑被隔离的情况
```

### 4.3 DDoS攻击

```
区块链DDoS攻击类型:

1. 交易泛洪
   - 大量低价值交易占用内存池
   - 提高交易费用
   - 延迟合法交易确认

2. 区块泛洪
   - 发送大量无效区块
   - 占用节点验证资源

3. 连接耗尽
   - 占满节点连接槽位
   - 阻止合法连接

4. 计算密集攻击
   - 发送复杂智能合约调用
   - 消耗节点计算资源

防御措施:
  - 交易费用市场机制
  - 内存池大小限制
  - 连接数限制
  - 请求频率限制
  - 验证难度调整
```

### 4.4 网络分区攻击

```
网络分区攻击:

  正常网络:
    A <---> B <---> C <---> D
    所有节点同步

  分区后:
    A <---> B     C <---> D
    两个分区独立运行

  危害:
  - 双花: 不同分区确认不同交易
  - 分叉: 合并时产生重组
  - 拒绝服务: 部分节点无法正常交易

  防御:
  - 监控网络分区
  - 检测分区合并
  - 延长确认时间
  - 分区检测和自动暂停
```

## 五、密码学风险

### 5.1 哈希碰撞

```
区块链哈希函数安全:

  SHA-256 (Bitcoin)
  - 输出: 256位
  - 碰撞阻力: 2^128 (生日攻击)
  - 当前安全

  Keccak-256 (Ethereum)
  - 输出: 256位
  - 与SHA-3标准不同
  - 当前安全

  风险:
  - 量子计算: Grover算法将碰撞搜索降低到2^(n/2)但SHA-256仍有128位安全
  - 算法缺陷: 发现哈希函数弱点可能影响
  - 历史教训: MD5已被攻破，SHA-1已被攻破
```

### 5.2 签名漏洞

```
ECDSA签名风险:

1. 随机数重用 (K重用)
   - 如果两个签名使用相同的随机数k
   - 可以推导出私钥

   攻击公式:
   r = (k * G).x mod n
   s = k^(-1)(z + r * d) mod n
   其中 z = hash(message), d = private key

   如果两个签名使用相同k:
   s1 = k^(-1)(z1 + r * d)
   s2 = k^(-1)(z2 + r * d)
   -> d = (s1*z2 - s2*z1) / (s2*r - s1*r)

   历史案例:
   - 2012 Android Bitcoin钱包随机数问题
   - 2015 Sony PlayStation 3 ECDSA密钥泄露

2. 签名延展性
   - ECDSA签名有多种有效形式
   - 攻击者修改签名但不改变验证结果
   - 导致交易ID变化 -> 影响交易链

3. 侧信道攻击
   - 通过功耗分析推导k值
   - 通过时间分析推导私钥

防御:
  - 使用RFC 6979确定性ECDSA
  - 使用Ed25519(确定性签名)
  - 硬件钱包保护密钥
  - 防止侧信道
```

### 5.3 随机数问题

```
区块链中的随机数用途:
  - 出块者选择
  - 密码学签名
  - 智能合约中的随机数
  - 彩票/博彩应用

随机数安全风险:

1. 区块时间戳作为随机数
   - 矿工可以微调时间戳
   - 影响随机数结果
   - 不安全

2. 区块哈希作为随机数
   - 矿工可以通过不发布区块影响哈希
   - "住手(Grinding)"攻击

3. RANDAO + VRF
   - 多方提交哈希承诺
   - VRF生成可验证随机数
   - 更安全但仍需防住手

4. 链外随机数
   - 使用Oraclize获取外部随机数
   - 信任Oracle
   - 可能被操纵

安全方案:
  - commit-reveal方案
  - VRF (Verifiable Random Function)
  - 多方随机数生成
  - 外部安全随机数源
```

### 5.4 量子计算威胁

```
量子计算对区块链的威胁:

1. Shor算法
   - 可以高效分解大整数 -> RSA不安全
   - 可以高效求解离散对数 -> ECDSA不安全
   - 影响所有基于ECC的签名

2. Grover算法
   - 将哈希碰撞搜索从2^n降低到2^(n/2)
   - SHA-256仍有128位安全(可接受)
   - 但签名安全受影响

时间线估算:
  - 当前: 量子计算能力有限
  - 5-10年: 可能出现对RSA-2048的威胁
  - 15-20年: 可能对ECC-256构成威胁

防御方案:
  - 后量子密码学(PQC)
  - 基于格的签名 (Dilithium, Falcon)
  - 基于哈希的签名 (Lamport, XMSS)
  - 基于编码的签名 (McEliece)

  具体措施:
  - 使用抗量子签名替代ECDSA
  - 增加哈希输出长度
  - 一次性签名(防量子)
  - 密钥轮换减少暴露
```

## 六、共识协议安全分析

### 6.1 PBFT安全

```
PBFT (Practical Byzantine Fault Tolerance):

  容错能力: n >= 3f + 1 (n为节点总数，f为恶意节点数)
  即: 需要2/3+的节点诚实

  流程:
  1. 客户端发送请求给主节点
  2. Pre-prepare: 主节点广播给副本节点
  3. Prepare: 副本节点广播prepare消息
  4. 当收到2f+1个prepare -> 进入commit
  5. Commit: 广播commit消息
  6. 当收到2f+1个commit -> 执行请求
  7. 回复客户端

  安全保证:
  - 最终性: 区块一旦确认不可逆
  - 活性: 只要f < n/3，系统持续运行
  - 一致性: 所有诚实节点状态一致
```

### 6.2 拜占庭容错

```
BFT共识安全边界:

  同步网络: 容忍 f < n 节点(但实际不可能完全同步)
  部分同步: 容忍 f < n/3 节点(PBFT等)
  异步网络: 不可能(FLP不可能定理)

  FLP不可能定理:
  - 在异步网络中
  - 即使只有一个节点故障
  - 也不可能达成确定性共识

  实际解决方案:
  - 假设部分同步(最终同步)
  - 引入随机性
  - 或接受概率性最终性
```

### 6.3 最终性与概率性

```
最终性类型:

1. 概率性最终性 (Bitcoin/Ethereum PoW)
   - 区块越深，被回滚概率越低
   - 没有绝对最终性
   - 确认数增加安全性

2. 经济最终性 (Ethereum PoS)
   - 区块被回滚需要大量ETH被削减
   - 经济上不可行
   - 半确定性

3. 即时最终性 (Tendermint/PBFT)
   - 区块确认后立即最终
   - 不可回滚
   - 高安全性但低灵活性

混合最终性:
  - Ethereum: Casper FFG (checkpoint)
  - 检查点之前: 概率性
  - 检查点之后: 确定性

  安全分析:
  - 概率性: 适合开放网络，但大额交易需等待
  - 即时性: 适合联盟链，快速确认
  - 混合: 平衡安全性和性能
```

## 八、自私挖矿策略深度分析

### 8.1 自私挖矿数学模型

```
自私挖矿收益模型:

定义:
  α = 攻击者算力占比 (0 < α < 1)
  β = 诚实矿工选择攻击者区块的概率 (0 ≤ β ≤ 1)
  γ = 1 - β (诚实矿工选择诚实链的概率)

攻击者相对收益 R(α, β):
  R(α, β) = [α(1-α)(1+β)] / [1 - α + αβ]

无利可图边界:
  α < α* = β / (1-β) 时无利可图

关键阈值:
  β = 0.5 (无网络优势): α* = 1 (理论不可行)
  β = 0.75 (强网络优势): α* = 0.33
  β = 1.0 (完全网络优势): α* = 0 (总是有利)

实际考量:
  - β取决于网络传播优势
  - 攻击者需要低延迟连接
  - 与矿池/节点的拓扑有关
  - 实际中α=0.25-0.33可能有利润
```

### 8.2 自私挖矿实施策略

```python
class SelfishMiner:
    """自私挖矿策略模拟"""

    def __init__(self, alpha=0.33, gamma=0.5):
        """
        alpha: 攻击者算力占比
        gamma: 诚实矿工跟随攻击者链的概率
        """
        self.alpha = alpha
        self.gamma = gamma
        self.private_chain = 0  # 攻击者私有链长度
        self.public_chain = 0   # 公开链长度
        self.revenue = 0        # 攻击者累计收益
        self.honest_revenue = 0 # 诚实矿工累计收益

    def mine_round(self):
        """模拟一轮挖矿"""
        import random
        if random.random() < self.alpha:
            # 攻击者找到区块
            self._attacker_found_block()
        else:
            # 诚实矿工找到区块
            self._honest_found_block()

    def _attacker_found_block(self):
        """攻击者找到新区块"""
        self.private_chain += 1
        lead = self.private_chain - self.public_chain

        if lead == 0:
            # 平局: 公开私有链(竞争)
            self._publish_private_chain()
        elif lead == 1 and self.public_chain > 0:
            # 领先1且公开链有区块: 等待
            pass
        # lead >= 2: 继续隐瞒

    def _honest_found_block(self):
        """诚实矿工找到新区块"""
        self.public_chain += 1
        lead = self.private_chain - self.public_chain

        if lead < 0:
            # 诚实链领先,放弃私有链
            self.honest_revenue += 1
            self.private_chain = self.public_chain
        elif lead == 0:
            # 平局: 公开私有链竞争
            import random
            if random.random() < self.gamma:
                self.revenue += 1  # 诚实矿工跟随攻击者链
            else:
                self.honest_revenue += 1
            self.private_chain = self.public_chain
        elif lead == 1:
            # 领先1: 公开私有链(使诚实矿工的区块作废)
            self._publish_private_chain()
            self.revenue += 1
        elif lead >= 2:
            # 领先2+: 公开一个区块(保持领先)
            self.private_chain -= 1
            self.revenue += 1

    def _publish_private_chain(self):
        """公开私有链"""
        self.private_chain = self.public_chain

    def simulate(self, rounds=10000):
        """模拟多轮"""
        for _ in range(rounds):
            self.mine_round()
        total = self.revenue + self.honest_revenue
        if total > 0:
            share = self.revenue / total
            print(f"算力占比: α={self.alpha}")
            print(f"跟随概率: γ={self.gamma}")
            print(f"攻击者收益占比: {share:.4f}")
            print(f"期望收益占比: {self.alpha:.4f}")
            print(f"超额收益: {(share - self.alpha)/self.alpha * 100:.2f}%")
            print(f"攻击者区块数: {self.revenue}")
            print(f"诚实矿工区块数: {self.honest_revenue}")

# 模拟不同场景
for alpha in [0.1, 0.2, 0.25, 0.33, 0.4, 0.5]:
    for gamma in [0.0, 0.5, 0.75, 1.0]:
        miner = SelfishMiner(alpha, gamma)
        miner.simulate(50000)
        print()
```

```python
class SelfishMiningDetector:
    """自私挖矿检测器"""

    def __init__(self):
        self.block_arrivals = []  # (block_hash, timestamp, miner)
        self.orphans = []         # 孤块记录
        self.stats = {
            'total_blocks': 0,
            'orphan_rate': 0,
            'miner_distribution': {},
            'inter_block_times': [],
            'unexpected_publishes': [],
        }

    def record_block(self, block_hash, timestamp, miner, is_orphan=False):
        """记录新区块"""
        self.block_arrivals.append({
            'hash': block_hash,
            'time': timestamp,
            'miner': miner,
            'orphan': is_orphan,
        })
        self.stats['total_blocks'] += 1
        if is_orphan:
            self.orphans.append(block_hash)

    def analyze(self):
        """分析自私挖矿迹象"""
        findings = []

        # 1. 孤块率异常
        orphan_rate = len(self.orphans) / max(self.stats['total_blocks'], 1)
        self.stats['orphan_rate'] = orphan_rate
        if orphan_rate > 0.05:  # 正常<3-5%
            findings.append({
                'type': 'high_orphan_rate',
                'severity': 'HIGH',
                'value': orphan_rate,
                'detail': f'孤块率{orphan_rate:.2%}异常偏高(正常<5%)'
            })

        # 2. 矿工发布模式异常
        miner_blocks = {}
        for b in self.block_arrivals:
            miner_blocks[b['miner']] = miner_blocks.get(b['miner'], 0) + 1

        for miner, count in miner_blocks.items():
            share = count / self.stats['total_blocks']
            self.stats['miner_distribution'][miner] = share
            # 如果矿工份额远超算力声明
            if share > 0.33:
                findings.append({
                    'type': 'excessive_block_share',
                    'severity': 'MEDIUM',
                    'value': share,
                    'detail': f'矿工{miner}出块份额{share:.2%}偏高'
                })

        # 3. 区块发布时间分析
        # 自私挖矿的特征: 紧接着诚实矿工出块后立即发布
        times = sorted([b['time'] for b in self.block_arrivals if not b['orphan']])
        for i in range(1, len(times)):
            delta = times[i] - times[i-1]
            self.stats['inter_block_times'].append(delta)

        # 极短间隔(可能是在竞争发布)
        if self.stats['inter_block_times']:
            short_intervals = sum(
                1 for t in self.stats['inter_block_times']
                if t < 2  # 小于2秒
            )
            if short_intervals > len(self.stats['inter_block_times']) * 0.15:
                findings.append({
                    'type': 'frequent_rapid_publishing',
                    'severity': 'MEDIUM',
                    'detail': f'频繁快速发布区块({short_intervals}次)'
                })

        # 4. 特定矿工的孤块率
        for miner in miner_blocks:
            miner_orphans = sum(
                1 for b in self.block_arrivals
                if b['miner'] == miner and b['orphan']
            )
            miner_total = miner_blocks[miner]
            if miner_total > 10:
                miner_orphan_rate = miner_orphans / miner_total
                if miner_orphan_rate > 0.1:
                    findings.append({
                        'type': 'high_miner_orphan_rate',
                        'severity': 'HIGH',
                        'detail': f'矿工{miner}孤块率{miner_orphan_rate:.2%}异常'
                    })

        return findings
```

## 九、Eclipse攻击实施分析

### 9.1 Eclipse攻击详细步骤

```
Eclipse攻击实施流程(以比特币为例):

Phase 1: 准备阶段
  ├── 创建大量节点/IP
  ├── 获取目标节点的出站连接IP
  │   ├── 通过网络监听
  │   ├── 通过节点的addr消息
  │   └── 通过DNS种子记录
  └── 准备替代地址表

Phase 2: 地址表污染
  ├── 向目标节点发送大量addr消息
  │   ├── 每条消息包含攻击者IP
  │   └── 持续发送直到地址表被污染
  ├── 等待目标节点重启
  │   ├── 地址表持久化到onion_peer.dat
  │   └── 重启后使用被污染的地址表
  └── 也可通过DDoS迫使目标重启

Phase 3: 连接劫持
  ├── 目标重启后尝试出站连接
  ├── 所有候选IP都是攻击者IP
  ├── 目标连接到攻击者节点
  └── 攻击者拒绝其他节点入站连接

Phase 4: 隔离与利用
  ├── 目标完全被隔离
  ├── 攻击者控制目标所见的信息
  │   ├── 发送虚假区块
  │   ├── 发送虚假交易
  │   └── 0确认双花
  ├── 矿工:浪费算力在旧链上
  └── 交易所:显示虚假余额

攻击参数:
  比特币节点默认出站连接数: 8
  需要污染的地址数: 数百
  地址表大小: ~10000
  污染成功率: 需要覆盖>50%的地址表
```

### 9.2 Eclipse攻击防御实现

```python
# Eclipse攻击防御策略实现

class EclipseDefense:
    """节点级Eclipse攻击防御"""

    def __init__(self):
        self.connection_manager = ConnectionManager()
        self.anchor_connections = set()  # 锚定连接
        self.address_table = AddressTable()
        self.outbound_count = 8

    def select_outbound_peers(self):
        """防御性出站连接选择"""
        selected = []

        # 1. 优先使用锚定连接(长期稳定的可信节点)
        for addr in self.anchor_connections:
            if len(selected) < 2:  # 至少2个锚定连接
                selected.append(addr)

        # 2. 随机选择(避免确定性选择被预测)
        candidates = self.address_table.get_random(self.outbound_count * 3)
        import random
        random.shuffle(candidates)

        for addr in candidates:
            if len(selected) >= self.outbound_count:
                break
            if self._is_diverse_enough(addr, selected):
                selected.append(addr)

        # 3. DNS种子兜底(当地址表不足时)
        if len(selected) < self.outbound_count:
            dns_seeds = self._get_dns_seeds()
            for addr in dns_seeds:
                if len(selected) >= self.outbound_count:
                    break
                if addr not in selected:
                    selected.append(addr)

        return selected

    def _is_diverse_enough(self, addr, selected):
        """确保连接的多样性(不同IP段/ASN)"""
        addr_asn = get_asn(addr)
        selected_asns = [get_asn(s) for s in selected]
        # 同一ASN不超过2个连接
        if selected_asns.count(addr_asn) >= 2:
            return False
        # 同一/24子网不超过1个连接
        addr_subnet = '.'.join(addr.split('.')[:3])
        for s in selected:
            if '.'.join(s.split('.')[:3]) == addr_subnet:
                return False
        return True

    def validate_connection(self, peer_info):
        """验证连接的有效性"""
        # 1. 检查提供的区块是否与已知一致
        if not self._verify_chain_consistency(peer_info):
            return False

        # 2. 检查网络延迟是否异常
        latency = self.connection_manager.get_latency(peer_info)
        if latency > 5000:  # 5秒以上延迟异常
            return False

        # 3. 检查是否所有连接都指向同一ASN
        all_asns = [get_asn(p) for p in self.connection_manager.get_outbound_peers()]
        if len(set(all_asns)) == 1 and len(all_asns) > 2:
            # 所有连接在同一ASN，疑似被日蚀
            return False

        return True

    def periodic_anchor_check(self):
        """定期验证锚定连接"""
        for addr in list(self.anchor_connections):
            if not self._verify_peer_alive(addr):
                self.anchor_connections.discard(addr)
                # 从新连接中选出稳定的作为新锚
                self._promote_to_anchor()

    def detect_eclipse(self):
        """检测是否被日蚀"""
        indicators = 0

        # 所有出站连接在同一子网
        peers = self.connection_manager.get_outbound_peers()
        subnets = set('.'.join(p.split('.')[:3]) for p in peers)
        if len(subnets) == 1:
            indicators += 3

        # 所有连接延迟相似(可能通过同一中继)
        latencies = [self.connection_manager.get_latency(p) for p in peers]
        if max(latencies) - min(latencies) < 10:  # 延迟过于均匀
            indicators += 2

        # 接收到的区块时间戳异常
        recent_blocks = self.connection_manager.get_recent_blocks()
        if recent_blocks:
            avg_time = sum(b['timestamp'] for b in recent_blocks) / len(recent_blocks)
            expected_time = time.time()
            if abs(avg_time - expected_time) > 3600:  # 偏差1小时
                indicators += 2

        # 无法连接到新的外部节点
        test_addrs = self._get_test_addresses()
        connected = sum(
            1 for a in test_addrs
            if self.connection_manager.try_connect(a, timeout=5)
        )
        if connected == 0:
            indicators += 3

        if indicators >= 5:
            return True
        return False
```

### 11.1 ECDSA随机数重用漏洞

```python
# ECDSA随机数重用导致私钥恢复
# 历史案例: 2012 Android Bitcoin钱包

def recover_ecdsa_private_key(r, s1, s2, z1, z2):
    """
    当两个签名使用相同的随机数k时恢复私钥
    
    参数:
        r: 两个签名的r值(相同，因为k相同)
        s1, s2: 两个签名的s值
        z1, z2: 两个消息的哈希值
    返回:
        d: 私钥
    """
    # ECDSA签名方程:
    # s1 = k^(-1) * (z1 + r * d) mod n
    # s2 = k^(-1) * (z2 + r * d) mod n
    #
    # 两式相减:
    # s1 - s2 = k^(-1) * (z1 - z2) mod n
    # k = (z1 - z2) / (s1 - s2) mod n
    #
    # 代入原式求d:
    # d = (s1 * k - z1) / r mod n

    # 需要模运算库
    from sympy import mod_inverse

    n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141  # secp256k1阶

    # 恢复k
    delta_s = (s1 - s2) % n
    delta_z = (z1 - z2) % n
    k = (delta_z * mod_inverse(delta_s, n)) % n

    # 恢复私钥d
    d = ((s1 * k - z1) * mod_inverse(r, n)) % n

    return d

# 示例: 两个使用相同k的签名
# 这些是模拟值，实际攻击需要真实的签名数据
r  = 0x79BE667EF9DCBBAC55A06295CE870B07029BFCDB2DCE28D959F2815B16F81798
s1 = 0x381F5B1C8B89F8B8E0E2A6C8D0F3E5B7A1C2D3E4F5A6B7C8D9E0F1A2B3C4D5E6
s2 = 0x4A5B6C7D8E9F0A1B2C3D4E5F6A7B8C9D0E1F2A3B4C5D6E7F8A9B0C1D2E3F4A5B
z1 = 0x1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF
```

### 11.2 交易延展性攻击(MT.Gox案例)

```
交易延展性攻击 - MT.Gox事件(2014)

攻击原理:
  ECDSA签名(s, r)中，s可以取 s 或 n-s(n为曲线阶)
  两者都验证通过，但产生不同的交易ID(TXID)

  原始签名: (r, s) -> TXID_1
  修改签名: (r, n-s) -> TXID_2
  同一笔交易，不同TXID

MT.Gox利用:
  1. 用户在MT.Gox提现BTC
  2. MT.Gox广播交易(TXID_1)
  3. 攻击者(或MT.Gox自己)修改签名
  4. 修改后的交易(TXID_2)被打包
  5. MT.Gox查找TXID_1 -> 找不到
  6. 认为提现未成功 -> 重复提现
  7. 用户的BTC实际已转出

影响:
  - MT.Gox声称丢失85万BTC
  - 部分可能是内部利用延展性
  - 2014年MT.Gox破产
  - 促使比特币引入SegWit(修复延展性)

防御:
  - SegWit(隔离见证): 签名数据移到witness字段
  - TXID不再包含签名数据
  - 签名修改不影响TXID
  - 彻底解决延展性问题
```

```
重入攻击与底层机制关系:
```

```python
class NetworkPartitionDetector:
    """区块链网络分区检测"""

    def __init__(self):
        self.peer_blocks = {}  # peer -> latest block height
        self.our_height = 0
        self.peer_count = 0
        self.active_peers = 0
        self.partition_history = []

    def update_peer_status(self, peer, block_height, timestamp):
        """更新对等节点状态"""
        self.peer_blocks[peer] = {
            'height': block_height,
            'time': timestamp,
        }

    def check_partition(self):
        """检测网络分区"""
        if len(self.peer_blocks) < 3:
            return None  # 节点太少无法判断

        heights = [p['height'] for p in self.peer_blocks.values()]
        max_height = max(heights)
        min_height = min(heights)

        # 高度差异过大
        height_gap = max_height - min_height
        if height_gap > 10:  # 超过10个区块差异
            # 分析分区
            high_group = [p for p, info in self.peer_blocks.items()
                         if info['height'] >= max_height - 2]
            low_group = [p for p, info in self.peer_blocks.items()
                        if info['height'] <= min_height + 2]

            partition = {
                'type': 'height_discrepancy',
                'gap': height_gap,
                'high_group': high_group,
                'low_group': low_group,
                'severity': 'HIGH' if height_gap > 50 else 'MEDIUM',
            }
            self.partition_history.append(partition)
            return partition

        # 检查连接数下降
        active = len(self.peer_blocks)
        if active < self.peer_count * 0.5:  # 连接数下降50%
            partition = {
                'type': 'connectivity_loss',
                'active_peers': active,
                'previous_peers': self.peer_count,
                'severity': 'HIGH',
            }
            self.partition_history.append(partition)
            return partition

        self.peer_count = active
        return None

    def handle_partition(self, partition):
        """处理分区事件"""
        if partition['type'] == 'height_discrepancy':
            # 不要立即接受更高链(可能是攻击)
            # 等待更多确认
            print(f"[WARNING] 检测到高度差异: {partition['gap']}")
            print(f"  高链组: {len(partition['high_group'])}个节点")
            print(f"  低链组: {len(partition['low_group'])}个节点")
            print("  建议: 等待更多区块确认再决定")

        elif partition['type'] == 'connectivity_loss':
            print(f"[WARNING] 连接数骤降: {partition['active_peers']}/{partition['previous_peers']}")
            print("  可能原因: 网络分区或DDoS")
            print("  建议: 暂停出块/交易确认")
```
