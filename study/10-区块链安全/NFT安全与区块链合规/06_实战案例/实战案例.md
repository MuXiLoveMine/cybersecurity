# 实战案例

### 6.1 案例1：NFT合约漏洞利用分析

**项目背景**：某NFT项目使用ERC-721标准，具有公开mint功能和版税分配机制。

**漏洞描述**：mint函数中使用了`_safeMint`（会触发onERC721Received回调），但在回调执行后才更新用户已铸币数量。攻击者部署一个恶意合约，在onERC721Received回调中再次调用mint函数，绕过每地址铸币限制。

**漏洞代码模式**：
```solidity
function mint(uint256 quantity) external payable {
    require(mintedPerAddress[msg.sender] + quantity <= MAX_PER_ADDRESS);
    require(msg.value == price * quantity);

    for (uint256 i = 0; i < quantity; i++) {
        _tokenIds.increment();
        uint256 newTokenId = _tokenIds.current();
        _safeMint(msg.sender, newTokenId); // 触发回调
        // 状态在safeMint之后更新，可被重入利用
    }
    mintedPerAddress[msg.sender] += quantity;
}
```

**攻击流程**：
1. 攻击者部署恶意合约，实现onERC721Received接口。
2. 调用mint(1)，_safeMint触发回调。
3. 在回调中再次调用mint(1)，此时mintedPerAddress尚未更新，检查通过。
4. 递归调用，绕过MAX_PER_ADDRESS限制，铸造大量NFT。
5. 以远低于市场成本获取NFT，在市场抛售获利。

**修复方案**：
```solidity
function mint(uint256 quantity) external payable {
    require(mintedPerAddress[msg.sender] + quantity <= MAX_PER_ADDRESS);
    require(msg.value == price * quantity);

    // 先更新状态（检查-生效-交互模式）
    mintedPerAddress[msg.sender] += quantity;

    for (uint256 i = 0; i < quantity; i++) {
        _tokenIds.increment();
        uint256 newTokenId = _tokenIds.current();
        _safeMint(msg.sender, newTokenId);
    }
}
```

**教训**：NFT合约的_safeMint引入了外部调用，必须遵循检查-生效-交互模式；使用ReentrancyGuard作为额外保护；审计应重点关注mint、transfer等涉及外部调用的函数。

### 6.2 案例2：NFT钓鱼攻击还原

**攻击场景**：知名NFT项目Bored Ape Yacht Club（BAYC）持有者遭遇钓鱼攻击。

**攻击流程**：

1. **准备阶段**：攻击者注册与BAYC官网极其相似的域名（如boredapeyatchclub.com，少一个字母）。部署恶意NFT合约和钓鱼网站。

2. **诱导阶段**：攻击者在Twitter/Discord上发布"免费铸造BAYC伴侣NFT"的信息，附带钓鱼网站链接。通过机器人点赞和转发增加可信度。部分受害者通过搜索引擎广告投放获得流量。

3. **连接钱包**：受害者点击链接访问钓鱼网站。网站弹窗提示"连接钱包领取空投"。受害者点击MetaMask连接，授权网站访问钱包。

4. **签名陷阱**：网站提示"领取您的免费NFT"，但实际生成的交易请求是调用恶意合约的`setApprovalForAll(attackerAddress, true)`。MetaMask显示的是合约调用信息，普通用户难以识别恶意意图。如果用户使用"盲签"（不显示具体参数），更难发现。

5. **资产转移**：攻击者获得setApprovalForAll授权后，通过自己管理的另一个地址调用transferFrom，将受害者持有的所有BAYC NFT转移到攻击者地址。

6. **销赃**：攻击者立即在OpenSea以低于地板价的价格挂卖，快速成交获利。或通过混币器（Tornado Cash）转移ETH收益。

**防范措施**：
- 仅通过官方渠道（官网、认证社交媒体）获取信息。
- 签名前仔细核对待执行交易的合约地址和函数名。
- 不随意授权setApprovalForAll，使用限额授权。
- 使用硬件钱包+盲签保护（Ledger显示交易详情）。
- 定期使用revoke.cash清理不必要的授权。
- 安装浏览器安全插件（如PocketUniverse、Blowater）在签名前警示风险。

### 6.3 案例3：交易所合规建设实践

**背景**：某加密货币交易所计划在欧盟市场运营，需要满足MiCA法规和AML要求。

**合规建设路线图**：

#### 阶段1：法律架构设计（1-3月）

- 聘请欧盟金融法律顾问，评估MiCA合规要求。
- 选择注册地（考虑立陶宛、德国等对加密资产友好的国家）。
- 设计公司治理架构，明确董事会和合规委员会职责。
- 制定合规政策框架：AML政策、KYC政策、数据保护政策、制裁合规政策。

#### 阶段2：技术合规建设（3-6月）

- **KYC系统部署**：集成Sumsub或Jumio，实现自动身份验证+活体检测。设置分级验证流程（基础→标准→增强）。
- **链上监控系统**：部署Chainalysis KYT，实时监控所有充值和提币交易的风险评分。高风险交易自动标记并暂停处理。
- **制裁筛查系统**：接入实时OFAC、UN、EU制裁名单数据库。新用户注册和每次交易进行制裁名单比对。
- **旅行规则系统**：部署Notabene，与合作VASP建立信息交换通道。提币超过1000 EUR时自动收集和传递发送方/接收方信息。
- **可疑交易报告系统**：建立SAR/STR管理流程。合规分析师审核标记的交易后提交给金融情报机构（FIU）。

#### 阶段3：运营合规建设（6-9月）

- **合规团队组建**：招聘首席合规官（CCO）、AML官、合规分析师。
- **AML/CFT合规计划**：基于FATF建议和欧盟指令制定详细的AML程序。包含风险评估、KYC、监控、报告、培训、审计等模块。
- **员工培训**：全员合规培训+岗位专项培训。定期模拟测试和更新培训。
- **审计和测试**：独立第三方进行AML审计。渗透测试安全系统。

#### 阶段4：牌照申请（9-12月）

- 准备申请材料：商业计划、合规手册、技术架构描述、风险管理系统描述、管理层背景调查。
- 向选择国的监管机构提交CASP授权申请。
- 配合监管机构审查和问答。
- 获得授权后开始运营，接受持续监管。

#### 阶段5：持续合规运营

- **定期审查**：每年更新风险评估，审查AML政策有效性。
- **监管报告**：定期向监管机构提交合规报告、SAR统计、运营数据。
- **系统更新**：根据法规更新（如FATF新指南）及时调整系统。
- **事件响应**：建立合规事件响应流程，发现违规行为及时处理并报告。

**成本估算**：合规建设总投入约50-100万欧元，年运营合规成本约20-50万欧元（视规模和业务复杂度）。

**教训**：合规不是一次性工程，而是持续的运营体系；合规成本是Web3企业不可回避的固定成本；合规能力本身可成为竞争优势。
