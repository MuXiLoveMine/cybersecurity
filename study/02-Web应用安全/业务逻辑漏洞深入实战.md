## 1. 业务逻辑漏洞概述

### 1.1 什么是业务逻辑漏洞

业务逻辑漏洞（Business Logic Vulnerability）是指由于应用程序在业务规则设计或实现上存在缺陷，导致攻击者能够绕过正常业务流程、获取未授权数据或造成业务损失的漏洞。这类漏洞不依赖于代码层面的语法错误或通用框架缺陷，而是根植于业务流程设计的疏漏。

典型示例：一个电商系统在创建订单时只校验前端传入的商品数量是否为正数，却未在服务端二次校验，攻击者将数量改为 `-1` 即可实现"反向加钱"。

### 1.2 与技术漏洞的区别

| 维度 | 技术漏洞（如 SQL 注入、XSS） | 业务逻辑漏洞 |
|------|------------------------------|--------------|
| 成因 | 代码层输入未过滤/转义 | 业务流程设计缺陷 |
| 检测 | 自动化扫描器可发现 | 需理解业务语义 |
| 普适性 | 跨站点普遍存在 | 特定业务特有 |
| WAF 防护 | 规则可拦截 | 难以用规则拦截 |
| 利用特征 | Payload 含恶意字符 | 请求参数合法但语义异常 |

### 1.3 为什么自动化扫描器难以发现

自动化扫描器（如 AWVS、Nessus）主要基于特征匹配和模糊测试，存在以下盲区：

- **缺乏业务上下文**：扫描器无法理解"订单金额应为正数""优惠券只能用一次"这类业务约束。
- **多步骤流程**：业务漏洞往往需要完整走完注册→登录→下单→支付链路才能触发，扫描器难以编排。
- **状态依赖**：漏洞触发依赖特定账户状态（如 VIP 等级），黑盒扫描无法预置。
- **合法参数滥用**：攻击请求参数值完全合法（如 `price=0.01`），不触发任何 WAF 规则。

正因如此，OWASP 将业务逻辑漏洞列为"无法自动发现但可手动发现"的高风险类别。

### 1.4 业务逻辑漏洞分类

```
业务逻辑漏洞
├── 权限控制类
│   ├── 水平越权（IDOR）
│   └── 垂直越权
├── 交易支付类
│   ├── 金额篡改
│   ├── 数值边界
│   ├── 并发竞争
│   └── 优惠滥用
├── 认证逻辑类
│   ├── 验证码绕过
│   ├── 密码找回缺陷
│   ├── 注册登录绕过
│   └── 会话固定
├── 数据完整性类
│   ├── 关键参数篡改
│   └── 重放攻击
└── 接口滥用类
    ├── 短信轰炸
    └── 接口频率失控
```

## 2. 越权漏洞（IDOR）

### 2.1 原理

越权漏洞（Insecure Direct Object Reference，IDOR）是指应用程序在处理对象引用时未做归属校验，导致用户可以访问不属于自己权限范围内的数据或功能。OWASP 将其归类于访问控制失效（Broken Access Control，A01:2021）。

### 2.2 水平越权

同一级别用户之间越权访问彼此数据。例如用户 A 通过修改 URL 中的用户 ID 参数查看用户 B 的订单。

请求示例：

```http
GET /api/orders?order_id=10234 HTTP/1.1
Cookie: session=userA
```

攻击者将 `order_id` 遍历为 `10235`、`10236` 即可查看他人订单，无需任何特殊 Payload。

### 2.3 垂直越权

低权限用户访问高权限功能。例如普通用户直接请求管理员接口：

```http
POST /admin/users/delete HTTP/1.1
Cookie: session=normal_user
Content-Type: application/json

{"user_id": 1001}
```

若后端仅依靠前端隐藏菜单项而非服务端鉴权，则删除操作成功执行。

### 2.4 实战案例：电商订单越权查看

某电商平台订单详情接口：

```
GET /order/detail?orderId=500123
```

服务端代码（PHP，漏洞版本）：

```php
// 漏洞代码：只验证登录，未校验订单归属
$order_id = $_GET['orderId'];
$order = $db->query("SELECT * FROM orders WHERE id = {$order_id}");
echo json_encode($order);
```

攻击者只需遍历 `orderId` 即可拉取全站订单数据。

### 2.5 漏洞代码对比（Java）

```java
// 漏洞版本：直接用请求参数查询，无归属校验
@GetMapping("/order/{id}")
public Order getOrder(@PathVariable Long id) {
    return orderRepository.findById(id).orElse(null);
}

// 安全版本：校验订单归属于当前用户
@GetMapping("/order/{id}")
public Order getOrder(@PathVariable Long id, @AuthenticationPrincipal UserDetails user) {
    Order order = orderRepository.findById(id)
        .orElseThrow(() -> new NotFoundException("订单不存在"));
    if (!order.getUserId().equals(user.getId())) {
        throw new ForbiddenException("无权访问该订单");
    }
    return order;
}
```

### 2.6 防御方案

1. **权限校验中间件**：在所有涉及对象访问的接口统一拦截，校验 `object.owner == current_user`。
2. **RBAC 模型**：基于角色的访问控制，角色-权限映射集中管理，避免散落的 `if (isAdmin)` 判断。
3. **使用不可枚举 ID**：用 UUID 替代自增 ID，提高遍历成本（但不可作为唯一防护）。
4. **默认拒绝原则**：无明确授权即拒绝访问。

RBAC 权限校验中间件示例（Python/Flask）：

```python
from functools import wraps
from flask import request, g, abort

def require_permission(permission):
    def decorator(f):
        @wraps(f)
        def wrapper(*args, **kwargs):
            user = g.current_user
            if not user or not user.has_permission(permission):
                abort(403)
            return f(*args, **kwargs)
        return wrapper
    return decorator

@app.route('/admin/users/delete', methods=['POST'])
@require_permission('user:delete')
def delete_user():
    # 仅拥有 user:delete 权限的角色可执行
    ...
```

### 2.7 Python 越权检测脚本

```python
import requests
from concurrent.futures import ThreadPoolExecutor

class IDORDetector:
    """越权漏洞检测器：遍历对象ID，判断是否返回他人数据"""
    def __init__(self, base_url, session_cookie):
        self.base_url = base_url.rstrip('/')
        self.cookies = {'session': session_cookie}
        self.findings = []

    def check_idor(self, endpoint, param, id_range, baseline_id):
        """
        endpoint: 接口路径，如 /api/orders/{id}
        param: 参数占位符，如 {id}
        baseline_id: 当前用户自身的ID，用于基准对比
        """
        # 获取基准响应（自己的数据）
        baseline = requests.get(
            f"{self.base_url}{endpoint.replace(param, str(baseline_id))}",
            cookies=self.cookies, timeout=10
        )
        baseline_data = baseline.json()

        def test_one(obj_id):
            url = f"{self.base_url}{endpoint.replace(param, str(obj_id))}"
            try:
                resp = requests.get(url, cookies=self.cookies, timeout=10)
                if resp.status_code == 200:
                    data = resp.json()
                    # 响应与基准不同且成功返回 => 疑似越权
                    if data != baseline_data and self._contains_user_data(data):
                        return {
                            'id': obj_id,
                            'status': resp.status_code,
                            'evidence': '返回了非自身对象数据'
                        }
            except Exception:
                pass
            return None

        with ThreadPoolExecutor(max_workers=10) as pool:
            results = list(pool.map(test_one, id_range))
        self.findings.extend([r for r in results if r])
        return self.findings

    def _contains_user_data(self, data):
        """判断响应是否包含敏感字段"""
        sensitive_keys = {'phone', 'email', 'address', 'id_card', 'password'}
        text = str(data).lower()
        return any(k in text for k in sensitive_keys)

# 使用示例
detector = IDORDetector('https://target.com', 'userA_session_cookie')
results = detector.check_idor('/api/orders/{id}', '{id}', range(10200, 10300), 10234)
for r in results:
    print(f"[!] IDOR: order_id={r['id']} -> {r['evidence']}")
```

## 3. 支付漏洞

### 3.1 原理

支付逻辑漏洞是业务逻辑漏洞中危害最大的类型之一，直接造成资金损失。常见手法包括篡改支付金额、利用数值边界、并发条件竞争、优惠券重复使用。

### 3.2 金额篡改（前端价格修改）

下单流程中价格由前端传至后端：

```http
POST /api/pay HTTP/1.1
Content-Type: application/json

{"product_id": "P1001", "quantity": 1, "price": 0.01}
```

攻击者通过抓包将 `price` 从 `99.00` 改为 `0.01`，若后端直接信任该值则支付 1 分钱购买商品。

漏洞代码（PHP）：

```php
$amount = $_POST['price'];          // 直接信任前端
$gateway->charge($amount, $user);   // 以篡改金额发起支付
```

### 3.3 数量负数/小数/超大值

- **负数**：`quantity=-1`，`total = price * quantity` 变为负值，账户余额反增。
- **小数**：`quantity=0.5`，绕过"整数"预期，部分系统计费混乱。
- **超大值**：`quantity=999999999`，触发整数溢出 `total = price * qty` 回绕为小值。

### 3.4 并发支付（条件竞争）

优惠券或余额扣减逻辑采用"先查后扣"模式：

```java
// 漏洞逻辑：检查余额与扣款非原子操作
Integer balance = walletDao.getBalance(userId);
if (balance >= orderAmount) {
    // 时间窗口：多个请求同时通过 if 判断
    walletDao.deduct(userId, orderAmount);
}
```

攻击者用同一账户在极短时间内发起 10 个并发支付请求，全部通过 `if (balance >= amount)` 判断后依次扣款，实现超额消费。

### 3.5 优惠券重复使用

优惠券核销未做唯一性约束：

```php
$coupon = $_POST['coupon_code'];
$discount = $db->query("SELECT discount FROM coupons WHERE code='{$coupon}'");
// 未检查该用户是否已使用过此优惠券
applyDiscount($discount);
```

攻击者对同一优惠券码发起多次请求，每次均享受折扣。

### 3.6 防御方案

1. **服务端金额校验**：支付金额一律由服务端根据 `product_id` 查库计算，禁止信任前端传入的 `price`。
2. **订单号唯一性约束**：数据库层面对订单号加唯一索引，防止重放。
3. **原子扣款**：使用 `UPDATE wallet SET balance = balance - ? WHERE id = ? AND balance >= ?` 一条 SQL 实现条件扣款。
4. **优惠券幂等**：以 `(user_id, coupon_id)` 为唯一键，核销时 `INSERT ... ON CONFLICT DO NOTHING`。
5. **数量边界校验**：服务端强制 `1 <= quantity <= MAX_ORDER_QTY` 且为整数。

安全扣款代码（Go）：

```go
func chargeOrder(db *sql.DB, userID int, orderID string, amount float64) error {
    // 原子条件扣款：余额不足直接失败
    res, err := db.Exec(
        `UPDATE wallets SET balance = balance - ? WHERE user_id = ? AND balance >= ?`,
        amount, userID, amount,
    )
    if err != nil {
        return err
    }
    rows, _ := res.RowsAffected()
    if rows == 0 {
        return errors.New("余额不足或并发扣款冲突")
    }
    return nil
}
```

### 3.7 Python 支付逻辑测试脚本

```python
import requests
import threading
import time

class PaymentLogicTester:
    """支付逻辑漏洞测试器"""
    def __init__(self, base_url, session_cookie):
        self.base_url = base_url.rstrip('/')
        self.headers = {'Cookie': f'session={session_cookie}'}

    def test_price_tamper(self, pay_url, product_id, original_price):
        """金额篡改测试"""
        tampered = original_price * 0.01
        resp = requests.post(f"{self.base_url}{pay_url}", headers=self.headers,
                             json={'product_id': product_id, 'quantity': 1, 'price': tampered})
        if resp.status_code == 200 and 'success' in resp.text.lower():
            return f"[!] 金额篡改成功: {original_price} -> {tampered}"
        return "[+] 金额篡改被拦截"

    def test_negative_quantity(self, pay_url, product_id, price):
        """负数数量测试"""
        resp = requests.post(f"{self.base_url}{pay_url}", headers=self.headers,
                             json={'product_id': product_id, 'quantity': -1, 'price': price})
        if resp.status_code == 200:
            return f"[!] 负数数量被接受: {resp.json()}"
        return "[+] 负数数量被拒绝"

    def test_race_condition(self, pay_url, coupon_code, threads=20):
        """并发条件竞争测试"""
        results = []
        barrier = threading.Barrier(threads)

        def attempt():
            barrier.wait()  # 所有线程同时释放
            resp = requests.post(f"{self.base_url}{pay_url}", headers=self.headers,
                                 json={'coupon_code': coupon_code})
            results.append(resp.status_code)

        t_list = [threading.Thread(target=attempt) for _ in range(threads)]
        for t in t_list: t.start()
        for t in t_list: t.join()

        success_count = sum(1 for s in results if s == 200)
        if success_count > 1:
            return f"[!] 条件竞争: {success_count}/{threads} 次优惠券核销成功"
        return f"[+] 优惠券幂等性正常: {success_count}/1 次成功"

# 使用示例
tester = PaymentLogicTester('https://shop.target', 'attacker_session')
print(tester.test_price_tamper('/api/pay', 'P1001', 99.00))
print(tester.test_negative_quantity('/api/pay', 'P1001', 99.00))
print(tester.test_race_condition('/api/apply_coupon', 'SAVE50'))
```

## 4. 验证码漏洞

### 4.1 验证码复用（不过期）

服务端将验证码存入 Session 但不设置过期时间，攻击者用同一验证码值反复提交：

```
POST /login  -> 验证码: a8Xk (服务端记录)
POST /login  -> 验证码: a8Xk (再次提交，仍通过)
```

### 4.2 验证码客户端校验

验证码校验逻辑写在 JavaScript 前端代码中：

```javascript
// 漏洞：前端校验验证码
function checkCaptcha(input) {
    return input === sessionStorage.getItem('captcha');
}
```

攻击者直接绕过前端，用 Burp 发包即可，验证码字段填任意值或空值。

### 4.3 验证码绕过（空值/万能验证码）

```php
// 漏洞：未校验空值
if ($_POST['captcha'] == $_SESSION['captcha']) { ... }
// 当两者均为空字符串时 0==0 为 true
```

部分系统存在调试遗留的万能验证码（如 `0000`、`admin`），硬编码在后端。

### 4.4 短信验证码轰炸

短信发送接口无频率限制：

```http
POST /api/sms/send  HTTP/1.1
{"phone": "13800000000"}
```

攻击者循环请求，导致目标手机号被短信轰炸，产生资费骚扰。

### 4.5 防御方案

| 漏洞 | 防御措施 |
|------|----------|
| 验证码复用 | 服务端校验后立即销毁，设置 5 分钟 TTL |
| 客户端校验 | 所有校验必须在服务端执行 |
| 空值绕过 | 显式校验 `if (captcha == null \|\| captcha.isEmpty()) reject` |
| 万能码 | 删除所有硬编码后门，使用标准库生成 |
| 短信轰炸 | 同一手机号 60 秒内限 1 次，同一 IP 10 分钟限 5 次，图形验证码前置 |

安全验证码校验（Python）：

```python
import random, string, time

class CaptchaManager:
    def __init__(self, redis_client):
        self.redis = redis_client

    def generate(self, session_id):
        code = ''.join(random.choices(string.digits, k=6))
        self.redis.setex(f"captcha:{session_id}", 300, code)  # 5分钟过期
        return code

    def verify(self, session_id, user_input):
        key = f"captcha:{session_id}"
        stored = self.redis.get(key)
        if not stored:
            return False, "验证码已过期"
        # 一次性使用：校验后立即删除
        self.redis.delete(key)
        if not user_input or not user_input.strip():
            return False, "验证码不能为空"
        return user_input == stored.decode(), "校验结果"
```

## 5. 密码找回漏洞

### 5.1 重置链接 Token 可预测

部分系统的重置 Token 基于可预测信息生成：

```php
// 漏洞：Token 基于时间戳和用户名MD5
$token = md5($username . time());
$reset_url = "https://example.com/reset?token={$token}";
```

攻击者已知目标用户名和大致时间戳即可爆破 Token。

### 5.2 验证码返回在响应包中

短信验证码接口将验证码直接返回在 JSON 响应中：

```http
POST /api/reset/send_code  HTTP/1.1
{"phone": "138****0000"}

HTTP/1.1 200 OK
{"msg": "发送成功", "debug_code": "729184"}
```

攻击者抓包即可获取验证码，无需接收短信。

### 5.3 修改手机号/邮箱绕过

```http
POST /api/reset/step1  -> {"account": "victim@target.com"}  // 第一步：填受害者账号
POST /api/reset/step2  -> {"account": "attacker@target.com", "code": "123456"}  // 第二步：改成自己邮箱接收验证码
```

服务端在第二步未校验 `account` 与第一步是否一致。

### 5.4 4 位验证码爆破

纯数字 4 位验证码共 10000 种可能，若无频率限制可在数分钟内爆破完成。

### 5.5 防御方案

1. **Token 随机性**：使用 `secrets.token_urlsafe(32)` 生成 32 字节随机 Token。
2. **验证码不回传**：短信/邮件验证码仅发送至用户终端，接口响应不包含验证码本身。
3. **账号绑定校验**：每一步请求校验 `account` 与初始步骤一致，使用服务端 Session 绑定。
4. **验证码长度**：至少 6 位，数字字母混合。
5. **爆破防护**：验证码错误 5 次后锁定该账号 15 分钟。

安全重置流程（Python）：

```python
import secrets

def initiate_reset(db, redis, account):
    token = secrets.token_urlsafe(32)
    redis.setex(f"reset_token:{token}", 600, account)  # 10分钟过期
    send_email(account, f"https://example.com/reset?token={token}")

def verify_reset(redis, token, new_password):
    account = redis.get(f"reset_token:{token}")
    if not account:
        return False, "Token无效或已过期"
    redis.delete(f"reset_token:{token}")  # 一次性使用
    update_password(account, new_password)
    return True, "密码重置成功"
```

## 6. 注册登录逻辑漏洞

### 6.1 用户名枚举（响应差异）

登录接口对不同错误返回不同提示：

```
用户不存在 -> "用户名不存在"
密码错误   -> "密码错误"
```

攻击者据此判断用户名是否存在，为后续撞库提供目标。

### 6.2 万能密码绕过

```php
// 漏洞：SQL拼接
$sql = "SELECT * FROM users WHERE username='{$_POST['user']}' AND password='{$_POST['pass']}'";
```

输入 `admin' -- ` 即可绕过密码校验。虽属 SQL 注入，但常在登录场景触发。

### 6.3 注册逻辑绕过

部分系统注册时服务端未校验用户角色字段：

```http
POST /register  -> {"username":"hacker","password":"123","role":"admin"}
```

后端直接将 `role` 写入数据库，导致任意用户可自注册管理员。

### 6.4 Session 固定攻击

攻击者预先获取一个 Session ID，诱使目标用户用该 ID 登录：

```
1. 攻击者访问站点获取 session_id=ABC123
2. 通过钓鱼链接让受害者使用 session_id=ABC123 登录
3. 受害者登录后，攻击者用 ABC123 即获得已认证会话
```

### 6.5 防御方案

1. **统一响应**：登录失败统一返回"用户名或密码错误"，不区分具体原因。
2. **参数化查询**：使用预编译语句彻底消除 SQL 注入。
3. **角色服务端控制**：注册接口不接受 `role` 等敏感字段，默认赋予普通用户角色。
4. **会话重生成**：登录成功后调用 `session_regenerate_id(true)` 销毁旧 Session。

```php
// 安全：登录后重生成Session
if (password_verify($input_pass, $user['password_hash'])) {
    session_regenerate_id(true);  // 防Session固定
    $_SESSION['user_id'] = $user['id'];
    $_SESSION['role'] = 'user';  // 角色 != 用户输入
}
// 统一错误
echo json_encode(['error' => '用户名或密码错误']);
```

## 7. 短信轰炸与接口滥用

### 7.1 短信轰炸原理

短信发送接口缺乏频率控制，攻击者编写脚本高频调用：

```python
while True:
    requests.post(url, json={"phone": target_phone})
```

目标用户手机号在短时间内收到大量验证码短信，造成骚扰和资费损失。

### 7.2 接口无频率限制

常见于以下接口：
- 短信验证码发送
- 邮件订阅
- 注册邀请码
- 投票/点赞接口

无频率限制还可能被用于刷接口消耗云服务额度。

### 7.3 防御方案

1. **滑动窗口限流**：基于 Redis ZSET 实现，60 秒内同一手机号限 1 次，10 分钟内同一 IP 限 5 次。
2. **行为验证前置**：发送短信前要求完成图形验证码或滑块验证。
3. **黑名单机制**：高频请求 IP 加入临时黑名单，24 小时后释放。
4. **云服务熔断**：单日发送量达阈值自动熔断告警。

滑动窗口限流代码（Python/Redis）：

```python
import time

class RateLimiter:
    """基于Redis ZSET的滑动窗口限流"""
    def __init__(self, redis_client):
        self.redis = redis_client

    def allow(self, key, max_count, window_seconds):
        now = time.time()
        pipe = self.redis.pipeline()
        pipe.zremrangebyscore(key, 0, now - window_seconds)  # 清除窗口外记录
        pipe.zadd(key, {str(now): now})
        pipe.zcard(key)                                       # 当前窗口内计数
        pipe.expire(key, window_seconds)
        results = pipe.execute()
        current_count = results[2]
        return current_count <= max_count

# 使用：手机号60秒内只能发1次短信
limiter = RateLimiter(redis_client)
if not limiter.allow(f"sms:{phone}", 1, 60):
    return "操作过于频繁，请稍后再试"
```

  [可篡改]      [抓包改]    [校验?]    [校验?]    [校验?]   [约束?]

- 库存扣减
- 投票计数
- 抽奖参与

### 8.5 业务逻辑漏洞检查清单

- [ ] 所有接口是否做了对象归属校验（防 IDOR）
- [ ] 支付金额是否由服务端计算（防金额篡改）

- [ ] 关键操作是否审计日志（防抵赖）

### 9.1 模拟越权测试框架

```python
import requests
from abc import ABC, abstractmethod

class BusinessLogicTest(ABC):
    """业务逻辑测试基类"""
    def __init__(self, target_url, auth_cookie):
        self.target = target_url.rstrip('/')
        self.session = requests.Session()
        self.session.headers.update({'Cookie': auth_cookie})

    @abstractmethod
    def run(self):
        """子类实现具体测试逻辑"""
        pass

class HorizontalIDORTest(BusinessLogicTest):
    """水平越权测试"""
    def run(self):
        findings = []
        # 用A账户获取自己的资源ID
        my_data = self.session.get(f"{self.target}/api/profile").json()
        my_id = my_data['user_id']
        # 尝试遍历其他ID
        for target_id in range(my_id - 5, my_id + 5):
            if target_id == my_id:
                continue
            resp = self.session.get(f"{self.target}/api/profile?uid={target_id}")
            if resp.status_code == 200 and 'phone' in str(resp.json()):
                findings.append(f"IDOR: uid={target_id} 可越权访问")
        return findings

class VerticalPrivilegeTest(BusinessLogicTest):
    """垂直越权测试"""
    ADMIN_ENDPOINTS = [
        '/admin/users/list', '/admin/system/config',
        '/admin/users/delete', '/admin/logs/view'
    ]
    def run(self):
        findings = []
        for ep in self.ADMIN_ENDPOINTS:
            resp = self.session.get(f"{self.target}{ep}")
            if resp.status_code == 200:
                findings.append(f"垂直越权: {ep} 可被普通用户访问")
        return findings
```

### 9.2 并发条件竞争测试脚本

```python
import threading
import requests
import time

class RaceConditionTester:
    """并发条件竞争测试器"""
    def __init__(self, target_url, cookie, threads=50):
        self.url = target_url
        self.headers = {'Cookie': cookie}
        self.threads = threads
        self.results = []
        self.barrier = threading.Barrier(threads)

    def execute_concurrent(self, payload_builder):
        """并发执行同一请求"""
        def worker():
            payload = payload_builder()
            self.barrier.wait()  # 确保所有线程同时发请求
            resp = requests.post(self.url, headers=self.headers, json=payload, timeout=10)
            self.results.append({'status': resp.status_code, 'body': resp.text[:200]})

        workers = [threading.Thread(target=worker) for _ in range(self.threads)]
        for w in workers: w.start()
        for w in workers: w.join()

        success = sum(1 for r in self.results if r['status'] == 200)
        if success > 1:
            print(f"[!] 条件竞争: {success}/{self.threads} 次操作成功（应仅1次）")
        else:
            print(f"[+] 无条件竞争: {success}/1 次成功")
        return self.results

# 使用示例
tester = RaceConditionTester('https://shop.target/api/coupon/redeem', 'session=hacker', 30)
tester.execute_concurrent(lambda: {'coupon_code': 'NEWUSER50'})
```

## 总结

业务逻辑漏洞的核心特征是"请求合法但语义违规"。防御要点不在于 WAF 规则或黑名单，而在于：

1. **服务端信任边界**：前端传来的任何参数都不可信任，金额、数量、角色、状态等关键字段必须服务端重新校验。
2. **原子性与幂等性**：涉及资金、积分、库存的操作必须保证原子性和幂等性，防止并发竞争和重复执行。
3. **最小权限默认**：接口默认拒绝，授权才放行；角色字段由服务端控制。
4. **业务感知测试**：将安全测试融入业务流程，用攻击者视角审视每一个状态转换和数据流向。

掌握业务逻辑漏洞的关键在于理解业务本身——唯有知道"正确的行为应该是什么"，才能识别"行为在哪里偏离了正确"。
