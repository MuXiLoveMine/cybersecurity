# HMAC 消息认证码

### 6.1 MAC 概述

**MAC（Message Authentication Code）** 消息认证码，是带有密钥的哈希函数，用于验证消息的完整性和真实性。

```
消息 M + 密钥 K ───MAC 算法───▶ 认证标签 T

只有持有相同密钥的人才能生成和验证标签
```

**MAC 与哈希的区别：**
- 哈希：不需要密钥，任何人都可以计算
- MAC：需要密钥，只有密钥持有者才能计算

**MAC 的性质：**
- 确定性：相同密钥 + 相同消息 → 相同标签
- 高效计算
- 抗伪造：没有密钥的人无法生成有效的标签

### 6.2 MAC 的用途

1. **完整性验证**：消息在传输中没有被篡改
2. **身份认证**：消息确实来自声称的发送者
3. **防重放**：结合序列号或时间戳

**注意：MAC 不提供不可否认性**
- 因为发送方和接收方共享密钥
- 接收方也能生成 MAC，所以不能向第三方证明是发送方发的
- 不可否认性需要数字签名

### 6.3 HMAC 原理

**HMAC（Hash-based MAC）** 是基于哈希函数的 MAC 构造方法。

**设计者**：Mihir Bellare、Ran Canetti、Hugo Krawczyk（1996 年）

**HMAC 的公式：**
```
HMAC(K, m) = H( (K' ⊕ opad) || H( (K' ⊕ ipad) || m ) )

其中：
- H：底层哈希函数（如 SHA-256）
- K：密钥
- K'：密钥填充到块大小（如果密钥比块大，先哈希）
- ipad：内部填充，0x36 重复
- opad：外部填充，0x5c 重复
```

**图示：**
```
密钥 K
  │
  ├─ 如果 K 比块大 → H(K) → K'
  └─ 否则 → K' = K（后面补 0 到块大小）
  │
  ├─────────────────────────────┐
  │                             │
  ▼                             ▼
K' ⊕ ipad (0x36...)         K' ⊕ opad (0x5c...)
  │                             │
  │  ┌───┐                      │
  └─▶│   │                      │
     │ H │◀── 消息 m             │
  ┌──┤   │                      │
  │  └───┘                      │
  │  内层哈希                     │
  │                             │
  └─────────────||──────────────▶
                │
                ▼
              ┌───┐
              │ H │
              └───┘
                │
                ▼
             HMAC 值
```

**ipad 和 opad：**
- ipad = 0x36 重复（块大小次）
- opad = 0x5c 重复（块大小次）
- 选择这两个值是因为它们的位模式差异大（汉明距离大）

### 6.4 HMAC 的安全性

**HMAC 的安全证明：**
- 如果底层哈希函数 H 是安全的（具有抗碰撞性等），则 HMAC 是安全的
- HMAC 的安全性不直接依赖于哈希函数的抗碰撞性
- 即使 MD5 已经被碰撞攻击破解，HMAC-MD5 仍然相对安全（但仍不推荐）

**常见 HMAC 变体：**

| HMAC 变体 | 底层哈希 | 输出长度 | 安全状态 |
|-----------|---------|---------|---------|
| HMAC-MD5 | MD5 | 128 位 | 不推荐 |
| HMAC-SHA1 | SHA-1 | 160 位 | 不推荐 |
| HMAC-SHA256 | SHA-256 | 256 位 | 推荐 |
| HMAC-SHA512 | SHA-512 | 512 位 | 推荐 |
| HMAC-SM3 | SM3 | 256 位 | 国密推荐 |

### 6.5 HMAC 的应用

| 应用 | 说明 |
|------|------|
| TLS/SSL | 记录层认证（早期版本） |
| IPSec | AH 和 ESP 协议 |
| SSH | 消息认证 |
| JWT | JSON Web Token 签名（HS256 等） |
| API 认证 | 接口签名验证 |
| 密码存储 | HMAC + Salt（但推荐 bcrypt 等慢哈希） |
| HOTP/TOTP | 一次性口令算法 |

### 6.6 密钥长度

- **密钥太短**：容易被暴力破解
- **密钥太长**：如果密钥比哈希函数的块大小还长，会先被哈希一次，实际有效长度变为哈希输出长度

**建议：**
- 密钥长度至少等于哈希输出长度
- HMAC-SHA256 使用至少 256 位（32 字节）密钥
- 使用密码学安全的随机数生成密钥
