# 密码工程概述

### 5.1 从理论到工程的挑战

密码学理论建立在严格的数学证明上，但工程实现经常引入安全漏洞。理论和实现之间的差距是密码工程的核心挑战。

```
密码工程转化链路：

理论证明                    工程实现
┌──────────┐              ┌──────────┐
│数学正确性  │    转化     │编程实现    │
│安全证明    │──────────→│系统架构    │
│算法设计    │            │部署运维    │
└──────────┘              └──────────┘
     │                         │
     │ 安全属性                  │ 风险点
     │ - IND-CPA                │ - 时序泄露
     │ - IND-CCA2               │ - 填充泄露
     │ - EUF-CMA                │ - 随机数缺陷
     │                          │ - 侧信道
     ↓                          ↓
  理论安全 ≠ 实现安全

经典案例：
  论：AES在只考虑CPA模型下安全
  实现：缓存时序攻击恢复AES密钥（Osvik 2006）

  理论：PKCS#7填充的CBC模式在CPA下安全
  实现：Padding Oracle攻击在CCA下可解密（Vaudenay 2002）

  理论：RSA-OAEP在随机预言模型下CCA安全
  实现：Bleichenbacher攻击利用错误信息恢复明文
```

### 5.2 密码工程的六条原则

```
密码工程安全原则：

1. 不要自己实现密码算法
   └── 使用经过审计的标准库（OpenSSL、libsodium）
   └── 自实现几乎必然有安全缺陷

2. 不要设计自己的密码协议
   └── 使用经过学术审查的标准协议
   └── "密码家不要自己发明密码"

3. 使用经过验证的参数
   └── 密钥长度、IV长度、迭代次数等遵循NIST推荐
   └── 不要使用弱参数（RSA-1024、SHA-1）

4. 正确处理错误信息
   └── 错误信息不应泄露密码学状态
   └── 统一错误消息防止Oracle攻击

5. 使用密码学安全随机数
   └── 密钥/IV/nonce必须用CSPRNG生成
   └── 不要用rand()、random()等非安全PRNG

6. 持续更新和审计
   └── 密码库版本及时更新
   └── 定期安全审计和渗透测试
```
