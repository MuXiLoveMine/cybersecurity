# 密码实现安全常见问题

### 6.1 时序攻击与常量时间实现

**时序攻击原理：**

```
时序攻击（Timing Attack）：
  通过测量操作执行时间来推断秘密信息

攻击原理：
  密码学操作的时间取决于操作的数据
  ├── 字符串比较：第一个不匹配字符处停止 → 时间泄露匹配长度
  ├── 模幂运算：按位扫描，1的位需要额外乘法 → 时间泄露密钥汉明重量
  └── 查表操作：不同缓存行命中时间不同 → 泄露密钥相关数据

经典案例：RSA密钥恢复
  ┌──────────────────────────────────────┐
  │ OpenSSL RSA签名验证时序攻击           │
  │                                      │
  │ 签名验证：m = sig^e mod n             │
  │   e为公钥指数（已知），n为模数（已知）  │
  │   sig为签名（攻击者控制）              │
  │                                      │
  │ 模幂运算使用"窗口法"（sliding window）  │
  │   按密钥位扫描，1→平方+乘法            │
  │   0→仅平方                            │
  │                                      │
  │ 攻击者构造特殊sig值                    │
  │   测量验证时间 → 推断密钥位             │
  │   数百万次测量 → 逐位恢复密钥           │
  └──────────────────────────────────────┘
```

**字符串比较的时序漏洞：**

```python
# 错误实现：非常量时间比较（存在时序泄露）
def insecure_compare(a, b):
    """安全令牌验证 - 错误实现"""
    if len(a) != len(b):
        return False
    for i in range(len(a)):
        if a[i] != b[i]:
            return False  # 第一个不匹配处立即返回
    return True
    # 问题：比较时间与匹配长度成正比
    # 攻击者可逐字节猜测正确值


# 正确实现：常量时间比较
def secure_compare(a, b):
    """安全令牌验证 - 常量时间实现"""
    if len(a) != len(b):
        return False
    
    result = 0
    for i in range(len(a)):
        # XOR累积差异，不提前退出
        result |= ord(a[i]) ^ ord(b[i])
    
    # 所有位比较完毕后才返回
    return result == 0

# 更好的方案：使用标准库
import hmac
def best_compare(a, b):
    """使用hmac.compare_digest（标准库常量时间比较）"""
    return hmac.compare_digest(a, b)
```

**模幂运算的常量时间实现：**

```python
# 错误：滑动窗口法（时间依赖密钥位）
def insecure_modexp(base, exponent, modulus):
    result = 1
    base = base % modulus
    while exponent > 0:
        if exponent % 2 == 1:  # 密钥位为1
            result = (result * base) % modulus  # 额外乘法
        exponent >>= 1
        base = (base * base) % modulus
    return result
    # 问题：1的位多一次乘法 → 时间泄露


# 正确：固定窗口法（常量时间）
def constant_time_modexp(base, exponent, modulus, window_size=4):
    """Montgomery阶梯法 - 常量时间模幂"""
    R0 = 1
    R1 = base % modulus
    
    for bit in bin(exponent)[2:]:  # 从高到低
        if bit == '0':
            R1 = (R0 * R1) % modulus
            R0 = (R0 * R0) % modulus
        else:
            R0 = (R0 * R1) % modulus
            R1 = (R1 * R1) % modulus
        # 无论bit是0还是1，都执行相同次数的乘法
    
    return R0
```

### 6.2 填充预言攻击与 PKCS#7 验证

**Padding Oracle 攻击原理：**

```
Vaudenay Padding Oracle Attack (2002)

攻击条件：
  - 使用CBC模式 + PKCS#7填充
  - 解密时填充验证的错误信息可区分
    （"填充错误" vs "MAC错误"）

攻击流程：
  假设密文块：C1 || C2（各16字节AES块）
  解密：P2 = Decrypt(C2) XOR C1
  
  攻击者修改C1最后1字节为不同值
    → P2最后1字节变化
    → 构造使P2最后1字节=0x01的C1值
    → 服务器返回"填充正确" → 得知Decrypt(C2)最后1字节
    → 逐字节恢复整个P2

  16字节块 → 最多256×16=4096次请求恢复明文
```

**Padding Oracle 攻击的代码示例：**

```python
# 漏洞代码：填充验证泄露信息
class VulnerableDecryptor:
    def decrypt(self, ciphertext, key):
        iv = ciphertext[:16]
        ct_blocks = [ciphertext[i:i+16] for i in range(16, len(ciphertext), 16)]
        
        plaintext = b''
        prev_block = iv
        
        for block in ct_blocks:
            decrypted = AES_decrypt(block, key)  # 原始解密
            
            # CBC XOR
            plain_block = bytes(a ^ b for a, b in zip(decrypted, prev_block))
            
            # PKCS#7填充验证 - 泄露点！
            padding_len = plain_block[-1]
            if padding_len > 16 or padding_len == 0:
                raise PaddingError("Invalid padding")  # ← 泄露1
            
            # 检查填充字节
            for i in range(padding_len):
                if plain_block[-(i+1)] != padding_len:
                    raise PaddingError("Invalid padding bytes")  # ← 泄露2
            
            plaintext += plain_block[:-padding_len]
            prev_block = block
        
        return plaintext  # 无错误 → 泄露3（填充正确）


# 正确方案：先验证MAC再解密（Encrypt-then-MAC）
class SecureDecryptor:
    def decrypt(self, ciphertext, key, mac_key):
        # 1. 先验证MAC
        ct_data = ciphertext[:-32]
        received_mac = ciphertext[-32:]
        expected_mac = HMAC(mac_key, ct_data)
        
        if not constant_time_compare(received_mac, expected_mac):
            raise AuthenticationError("MAC verification failed")
            # 统一错误，不区分填充错误
        
        # 2. MAC验证通过后才解密
        iv = ct_data[:16]
        ct_blocks = [ct_data[i:i+16] for i in range(16, len(ct_data), 16)]
        
        plaintext = b''
        prev_block = iv
        
        for block in ct_blocks:
            decrypted = AES_decrypt(block, key)
            plain_block = bytes(a ^ b for a, b in zip(decrypted, prev_block))
            
            # 去除填充（此时MAC已验证，填充Oracle攻击不可行）
            padding_len = plain_block[-1]
            plaintext += plain_block[:-padding_len]
            prev_block = block
        
        return plaintext
```

**认证加密模式（AEAD）推荐：**

```
安全的加密模式选择：

推荐（AEAD - 自带认证）：
  ├── AES-GCM (Galois/Counter Mode)
  │   └── AES-256-GCM（量子安全）
  │   └── 注意：IV不可重复！
  ├── ChaCha20-Poly1305
  │   └── 移动端性能好，抗侧信道
  └── AES-CCM
      └── 适合受限环境

不推荐：
  ✗ AES-CBC（需额外MAC，易出错）
  ✗ AES-ECB（确定性加密，泄露模式）
  ✗ RC4（已破）
  ✗ 3DES（已过时，64位块生日攻击）
```

### 6.3 随机数生成器安全

```
随机数生成器分级：

┌──────────────────────────────────────────────────────┐
│                  随机数生成器层级                       │
├──────────────┬───────────────┬───────────────────────┤
│  TRNG (真随机) │ CSPRNG (密码安全) │ PRNG (伪随机)     │
│  物理噪声源    │ 密码学种子+扩展  │ 普通随机数         │
├──────────────┼───────────────┼───────────────────────┤
│ /dev/hwrng   │ /dev/urandom  │ rand()              │
│ 硬件RNG       │ OpenSSL RAND  │ Math.random()       │
│ RdRand指令    │ /dev/random   │ random模块          │
├──────────────┼───────────────┼───────────────────────┤
│ 物理不可预测  │ 密码学不可区分 │ 不可用于密码学         │
│ 最安全        │ 安全           │ 可预测，危险         │
└──────────────┴───────────────┴───────────────────────┘

Linux随机数源：
  /dev/random    ← 阻塞式，熵不足时等待（密码学安全）
  /dev/urandom   ← 非阻塞，使用CSPRNG扩展（密码学安全）
  getrandom()    ← 系统调用，推荐方式（Linux 3.17+）

  注意：现代Linux中/dev/urandom同样安全
  /dev/random的阻塞行为在Linux 4.8+已改进
```

**随机数安全最佳实践：**

```python
import os
import secrets
from cryptography.hazmat.backends import default_backend
from cryptography.hazmat.primitives.asymmetric import ec

# 错误：使用不安全的随机数
def insecure_keygen():
    import random
    key = random.randint(1, 2**256)  # 危险！random非CSPRNG
    return key

# 正确：使用secrets模块（Python 3.6+）
def secure_keygen():
    key = secrets.token_bytes(32)  # 256位密钥
    return key

# 正确：使用os.urandom
def secure_random_bytes(n):
    return os.urandom(n)  # 使用系统CSPRNG

# 正确：生成ECDSA密钥对（库内部使用CSPRNG）
def generate_ec_keypair():
    private_key = ec.generate_private_key(
        ec.SECP256R1(),
        backend=default_backend()
    )
    # cryptography库内部使用OpenSSL CSPRNG
    return private_key

# CSPRNG种子收集事件示例
class EntropyCollector:
    """收集系统熵源（简化版）"""
    
    def __init__(self):
        self.entropy_pool = bytearray()
    
    def add_entropy(self, source):
        """从各种来源收集熵"""
        # 硬件随机（如果有）
        # 进程ID、时间戳、内存地址等
        import time, os, threading
        self.entropy_pool.extend(
            str(os.getpid()).encode() +
            str(time.time_ns()).encode() +
            str(id(object())).encode() +
            str(threading.get_ident()).encode()
        )
    
    def get_random_bytes(self, n):
        """使用系统CSPRNG生成随机数"""
        # 实际应用中直接使用os.urandom
        # 这里仅展示熵收集概念
        return os.urandom(n)
```

**NSA后门风险案例（Dual_EC_DRBG）：**

```
Dual_EC_DRBG事件：
  - NIST SP 800-90A标准中的伪随机数生成器
  - 基于椭圆曲线（含NSA推荐的曲线参数）
  - 2013年斯诺登文档揭示NSA植入了后门
  
后门原理：
  ┌──────────────────────────────────────┐
  │ Dual_EC_DRBG算法结构                  │
  │   state → P(state) → output           │
  │   output → Q(output) → next_state     │
  │                                      │
  │ P和Q为椭圆曲线上的点                   │
  │ NSA知道P和Q之间的离散对数关系           │
  │   即知道e使得 Q = e·P                 │
  │                                      │
  │ 攻击：                                │
  │   观察output → 计算Q(output)          │
  │   若知道e，可反推state                 │
  │   → 预测后续所有随机数                  │
  │                                      │
  │ 后门关键：NSA选择了特定的Q值            │
  │   外界无法验证P和Q的关系               │
  └──────────────────────────────────────┘

教训：
  - 不使用参数来源不明的密码标准
  - 优先使用可审计的开放实现
  - Dual_EC_DRBG已于2014年从NIST标准中移除
```

### 6.4 侧信道攻击

```
侧信道攻击分类：

┌──────────────────────────────────────────────┐
│              侧信道攻击类型                     │
├──────────────┬────────────────────────────────┤
│ 功耗分析      │ 测量芯片功耗推断密钥            │
│ (Power)      │ SPA（简单功耗分析）             │
│              │ DPA（差分功耗分析）             │
├──────────────┼────────────────────────────────┤
│ 电磁泄漏      │ 测量电磁辐射                    │
│ (EM)         │ 与功耗分析类似                   │
├──────────────┼────────────────────────────────┤
│ 时序分析      │ 测量执行时间                    │
│ (Timing)     │ 见6.1节                        │
├──────────────┼────────────────────────────────┤
│ 缓存时序      │ 利用CPU缓存行为                │
│ (Cache)      │ Flush+Reload、Prime+Probe     │
├──────────────┼────────────────────────────────┤
│ 声学分析      │ 分析CPU高频噪声                │
│ (Acoustic)   │ 可区分不同密钥位                │
├──────────────┼────────────────────────────────┤
│ 故障注入      │ 诱导计算错误获取信息            │
│ (Fault)      │ 电压/时钟/激光/glitch          │
└──────────────┴────────────────────────────────┘

DPA攻击示例（AES）：
  1. 测量大量加密操作的功耗轨迹
  2. 对每个密钥假设，计算中间值（如S盒输出）
  3. 按中间值比特将轨迹分组
  4. 计算分组均值差异
  5. 正确密钥假设 → 差异显著峰值
  
  防护：掩码（masking）、隐藏（hiding）、盲化（blinding）
```

### 6.5 错误实现的安全协议

**Heartbleed 漏洞分析：**

```
CVE-2014-0160: OpenSSL Heartbleed

漏洞代码（简化）：
  ┌──────────────────────────────────────┐
  │ TLS Heartbeat扩展                    │
  │                                      │
  │ 客户端发送：                          │
  │   "hello" + length=5                 │
  │                                      │
  │ 服务器回复（echo回同样的payload）：     │
  │   读取5字节 → 返回5字节               │
  │                                      │
  │ 恶意客户端发送：                      │
  │   "hello" + length=65535              │
  │   （声明payload有65535字节，实际只5字节）│
  │                                      │
  │ 漏洞代码：                            │
  │   memcpy(response, request, length); │
  │   ← 没有验证length <= 实际payload长度 │
  │   ← 越界读取堆内存65535-5=65530字节    │
  │                                      │
  │ 泄露内容：                            │
  │   - 其他连接的TLS私钥                │
  │   - 会话cookie                      │
  │   - 用户密码                         │
  │   - 其他堆数据                       │
  └──────────────────────────────────────┘

漏洞根因：
  - 信任用户提供的长度参数
  - 缺少边界检查
  - memcpy不检查越界

修复：
  if (length > payload_actual_length) {
      return error;
  }
  memcpy(response, request, length);

教训：
  - 永远不信任用户输入的长度
  - 边界检查必须在数据使用前
  - 密码库需要严格的代码审计
```

**Lucky 13 攻击分析：**

```
CVE-2013-0169: TLS CBC MAC timing attack

攻击背景：
  TLS 1.0/1.1使用 CBC模式 + MAC-then-Encrypt
  
  流程：
  1. 明文 → 附加MAC → PKCS#7填充 → CBC加密
  
  解密：
  1. CBC解密 → 去除填充 → 验证MAC → 返回明文
  
  问题：填充验证和MAC验证分开执行
  - 填充错误 → 立即返回错误
  - MAC错误 → 验证完MAC后返回错误
  - 两者时间差异 → Oracle

Lucky13改进：
  即使实现做了"常量时间"处理（填充错误也继续验证MAC）
  仍可通过微妙的时间差（HMAC计算依赖去除的填充长度）
  来区分填充正确与否

防护：
  - 使用AEAD模式（GCM/ChaCha20-Poly1305）
  - 禁用CBC模式
  - TLS 1.3已移除CBC模式支持
```
