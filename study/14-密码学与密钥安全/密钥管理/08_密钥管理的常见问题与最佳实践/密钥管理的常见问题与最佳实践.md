# 密钥管理的常见问题与最佳实践

### 8.1 常见错误

#### 错误 1：硬编码密钥

```python
# 错误！密钥硬编码在代码中
API_KEY = "sk-1234567890abcdef"
ENCRYPTION_KEY = b"my_secret_key_12345"
```

**风险：**
- 反编译即可获取
- 代码泄露（如 GitHub）= 密钥泄露
- 所有环境使用相同密钥

**正确做法：**
- 从环境变量读取
- 从配置中心/KMS 读取
- 不同环境使用不同密钥

#### 错误 2：密钥提交到版本控制

**案例：**
- 开发者不小心把包含密钥的配置文件提交到 GitHub
- 被爬虫扫描到，密钥被盗
- 造成经济损失（如云服务被挖矿）

**防护：**
- 使用 `.gitignore` 排除配置文件
- 使用 Git 钩子检查敏感信息
- 密钥泄露检测工具（如 git-secrets、truffleHog）
- 一旦泄露立即轮换密钥

#### 错误 3：密钥明文存储

```
# 错误！配置文件中明文存储密钥
database.password = my_secret_password
api.key = abc123def456
```

**正确做法：**
- 加密配置文件
- 使用 KMS 加密密钥
- 使用 Secret 管理工具（HashiCorp Vault 等）

#### 错误 4：密钥复用

- 一个密钥用于多个系统
- 一个密钥既用于加密又用于签名
- 测试环境和生产环境使用相同密钥

**风险：** 一个地方泄露，所有地方都不安全

**原则：** 一用一密，一系统一密

#### 错误 5：从不轮换密钥

- 密钥一旦生成就永远不变
- 员工离职了密钥还在使用
- 系统上线几年了密钥从没换过

**风险：** 密钥泄露了也不知道，长期暴露

#### 错误 6：没有备份

- 密钥丢失 = 数据永久丢失
- 只有一份密钥，损坏了就完了

**正确做法：**
- 密钥要有备份
- 备份要加密存储
- 定期测试恢复
- 密钥分割多人保管（Shamir 秘密共享）

### 8.2 最佳实践总结

**1. 密钥生成**
- 使用密码学安全的随机数生成器
- 密钥长度满足安全要求
- 在可信环境中生成

**2. 密钥存储**
- 永远不要明文存储密钥
- 使用 KMS 或 HSM 存储
- 访问控制最小化
- 内存中的密钥及时清除

**3. 密钥分发**
- 使用安全的密钥分发协议
- 验证对方身份
- 传输过程加密保护

**4. 密钥使用**
- 一用一密（不同用途不同密钥）
- 最小权限原则
- 审计所有密钥使用
- 监控异常使用模式

**5. 密钥轮换**
- 定期轮换（按策略执行）
- 事件驱动轮换（怀疑泄露立即轮换）
- 无缝轮换（不影响业务）
- 轮换后验证

**6. 密钥销毁**
- 不再使用的密钥及时销毁
- 确保所有副本都被销毁
- 销毁后验证不可恢复
- 保留销毁记录

**7. 备份与恢复**
- 密钥要有备份
- 备份要安全存储
- 定期测试恢复流程
- 多人共管（关键密钥）

**8. 审计与监控**
- 记录所有密钥操作
- 定期审计密钥使用
- 监控异常行为
- 告警机制

### 8.3 关键指标（KPI）

| 指标 | 说明 | 目标 |
|------|------|------|
| 密钥轮换及时率 | 按时轮换的密钥比例 | 100% |
| 密钥泄露事件数 | 密钥泄露的次数 | 0 |
| 密钥管理合规率 | 符合政策的密钥比例 | 100% |
| 密钥恢复时间 | 密钥丢失后恢复所需时间 | < 4小时 |
| 密钥使用审计覆盖率 | 有审计记录的密钥使用比例 | 100% |
