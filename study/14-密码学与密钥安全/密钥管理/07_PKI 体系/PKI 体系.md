# PKI 体系

### 7.1 PKI 概述

**PKI（Public Key Infrastructure）** 公钥基础设施，是管理公钥和数字证书的一套完整体系。

**PKI 的核心作用：**
- 证明公钥属于谁（身份绑定）
- 建立信任关系
- 管理数字证书的生命周期

**为什么需要 PKI？**

公钥密码学有一个根本问题：
```
你怎么知道这个公钥真的属于你以为的那个人？
```

PKI 通过可信第三方（CA）来解决这个问题。

### 7.2 PKI 组成

```
PKI 体系
├── CA（Certification Authority）
│   ├── 根 CA
│   └── 中间 CA
├── RA（Registration Authority）
├── 证书库 / 目录服务
├── 终端实体（用户/设备）
├── 证书撤销机制
│   ├── CRL（证书撤销列表）
│   └── OCSP（在线证书状态协议）
└── 密钥管理系统
```

#### （1）CA（证书颁发机构）

**CA（Certificate Authority）** 是 PKI 的核心，负责颁发和管理数字证书。

**CA 的职责：**
- 颁发数字证书
- 续期证书
- 撤销证书
- 发布 CRL/OCSP
- 维护证书状态

**CA 的层级：**

```
        根 CA (Root CA)
       /    |    \
  中间CA1  中间CA2  中间CA3
    / \      |      / \
 用户  用户  用户   用户 用户
```

- **根 CA**：最顶层，自签名证书，信任的根
- **中间 CA**：由根 CA 签发，用于签发终端实体证书
- **终端实体证书**：用户/服务器证书，由中间 CA 签发

**为什么需要多层 CA？**
- 根 CA 尽量离线，减少暴露
- 中间 CA 可以有多个，分工不同
- 一个中间 CA 出问题可以吊销，不影响根 CA
- 便于管理和扩展

#### （2）RA（注册机构）

**RA（Registration Authority）** 负责审核用户的身份信息，验证证书申请。

**RA 的职责：**
- 接收证书申请
- 验证申请人身份
- 审核证书申请信息
- 向 CA 提交签发请求
- 分发证书

RA 不签发证书（签发是 CA 的事），只负责身份验证。

#### （3）证书库

存储和分发证书的系统：
- LDAP 目录
- HTTP 下载
- 证书透明日志（Certificate Transparency）

#### （4）终端实体

拥有证书的用户或设备：
- 个人用户证书
- 服务器证书（TLS 证书）
- 设备证书
- 代码签名证书
- 邮件加密证书

### 7.3 数字证书

#### 什么是数字证书

**数字证书** 是由 CA 签发的电子文档，证明某个公钥属于某个实体。

**类比：**
数字证书就像身份证：
- 身份证证明你的名字和照片对应
- 数字证书证明你的公钥和你的身份对应
- 身份证由政府签发
- 数字证书由 CA 签发

#### X.509 证书格式

X.509 是最常用的数字证书标准。

**证书结构：**

```
X.509 证书
├── 证书版本（Version）
├── 序列号（Serial Number）
├── 签名算法（Signature Algorithm）
├── 颁发者（Issuer）
├── 有效期（Validity）
│   ├── 生效时间（Not Before）
│   └── 失效时间（Not After）
├── 主体（Subject）
├── 主体公钥信息（Subject Public Key Info）
│   ├── 公钥算法
│   └── 公钥值
├── 扩展（Extensions）
│   ├── 密钥用法
│   ├── 扩展密钥用法
│   ├── 基本约束（是否是CA）
│   ├── 主题备用名称（SAN）
│   ├── CRL 分发点
│   ├── 授权信息访问（OCSP地址）
│   └── ...
└── 签名（Signature）
```

**证书编码格式：**
- **PEM**：Base64 编码，以 `-----BEGIN CERTIFICATE-----` 开头
- **DER**：二进制格式
- **PKCS#7**：证书链格式
- **PKCS#12**：证书 + 私钥（通常有密码保护）

#### 证书验证过程

```
验证服务器证书的过程：

1. 检查证书格式是否正确
2. 检查证书是否在有效期内
3. 检查证书是否被吊销（CRL/OCSP）
4. 验证证书的签名
   - 用颁发者的公钥验证证书上的签名
   - 签名有效 → 证书确实是该 CA 签发的
5. 验证颁发者证书
   - 递归验证上一级证书
   - 直到根 CA
6. 检查根证书是否在信任列表中
7. 检查证书用途（是否用于服务器认证）
8. 检查域名是否匹配（SAN / CN）

所有检查都通过 → 证书可信
```

**信任链（Chain of Trust）：**
```
服务器证书 → 中间 CA 证书 → 根 CA 证书
  (用户验证)    (CA签发)     (自签名，操作系统信任)

信任根：根 CA 证书（预装在操作系统/浏览器中）
```

### 7.4 证书生命周期

```
申请 → 审核 → 签发 → 使用 → 续期 → 撤销 → 过期
```

#### （1）证书申请

**CSR（Certificate Signing Request）**：
- 申请者生成密钥对
- 构造 CSR（包含公钥、身份信息等）
- 用私钥签名 CSR
- 发送 CSR 给 CA

#### （2）身份审核

CA 在签发证书前需要验证申请人的身份：

| 验证级别 | 说明 | 适用场景 |
|---------|------|---------|
| DV（Domain Validation） | 验证域名控制权 | 普通网站 |
| OV（Organization Validation） | 验证组织身份 | 企业网站 |
| EV（Extended Validation） | 严格验证组织身份 | 银行、电商等 |

#### （3）证书签发

CA 验证通过后，签发证书：
- 用 CA 私钥对证书签名
- 返回证书给申请人
- 发布到证书库

#### （4）证书使用

证书的使用场景：
- TLS/SSL 服务器认证
- 客户端认证
- 代码签名
- 邮件加密（S/MIME）
- 文档签名
- VPN 认证

#### （5）证书续期

证书有效期满前需要续期：
- 生成新的密钥对（推荐）
- 申请新证书
- 替换旧证书
- 旧证书过期失效

**证书有效期趋势：**
- 早期：5-10 年
- 2018 年：最长 2 年
- 2020 年：最长 1 年
- 未来可能更短（90 天）

#### （6）证书撤销

证书在有效期内可能需要提前撤销：

**撤销原因：**
- 私钥泄露
- 身份信息变更
- 组织关系终止
- 证书信息错误
- 安全事件

**撤销机制：**

| 机制 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| CRL | 证书撤销列表 | 简单、批量 | 文件大、更新不及时 |
| OCSP | 在线证书状态协议 | 实时查询、响应小 | 隐私问题、性能压力 |
| OCSP Stapling | OCSP 装订 | 实时、保护隐私 | 服务器实现复杂 |

**CRL（Certificate Revocation List）：**
```
CA 定期发布撤销列表
包含所有被撤销证书的序列号和撤销时间
用户下载 CRL 并检查证书是否在列表中

问题：
- CRL 文件可能很大
- 更新有延迟（不是实时的）
- 用户需要定期下载
```

**OCSP（Online Certificate Status Protocol）：**
```
用户向 OCSP 服务器查询特定证书的状态
OCSP 服务器返回：有效 / 已撤销 / 未知

优点：
- 实时
- 响应小（只查一个证书）

问题：
- 隐私泄露（OCSP 服务器知道你访问了哪个网站）
- 性能压力（每个证书都要查询）
- OCSP 服务器可能不可用
```

**OCSP Stapling（OCSP 装订）：**
```
服务器自己去 OCSP 查询证书状态
然后将 OCSP 响应"装订"在 TLS 握手中发给客户端

优点：
- 保护用户隐私（OCSP 服务器不知道用户）
- 减少 OCSP 服务器压力
- 客户端不需要额外连接

Must-Staple 扩展：
- 证书要求必须装订 OCSP
- 否则浏览器拒绝连接
```

### 7.5 根证书信任

**信任根从哪里来？**
- 操作系统预装（Windows、macOS、iOS、Android）
- 浏览器自带（Firefox 有自己的根证书库）
- 企业内部部署（企业根 CA）

**根证书的重要性：**
- 信任根 CA = 信任它签发的所有证书
- 根 CA 私钥泄露 = 整个 PKI 体系崩塌
- 根 CA 必须最高级别保护

**根 CA 保护措施：**
- 离线存储（Air-gapped）
- HSM 硬件保护
- 多人控制（M of N 密钥分割）
- 严格的物理安全
- 极少使用（只签发中间 CA）

### 7.6 证书透明性（Certificate Transparency）

**问题：**
- CA 可能错误地或恶意地签发不属于你的证书
- 你可能不知道有人冒用你的域名申请了证书

**解决方案：Certificate Transparency（CT）**

**原理：**
- 所有 CA 签发的证书都必须记录在公开的日志中
- 日志是只追加的（Append-only）
- 任何人都可以查询日志
- 浏览器要求证书有 CT 证明

**CT 日志：**
- 全球有多个 CT 日志服务器
- 证书必须至少有 2 个以上的 CT 证明
- 可以监控你的域名有哪些证书被签发
