# 密钥管理

> 密码学的安全不仅取决于算法的强度，更取决于密钥的安全管理。再强的算法，如果密钥管理不当，也会变得不堪一击。本文详细讲解密钥生命周期、密钥分级、密钥存储、密钥分发、密钥轮换以及 PKI 体系。

---

## 一、密钥管理概述

### 1.1 什么是密钥管理

**密钥管理（Key Management）** 是指对密钥的整个生命周期进行安全管理的过程和技术。

```
密钥生命周期：
  生成 → 分发 → 存储 → 使用 → 轮换 → 归档 → 销毁
```

**密钥管理的重要性：**
- 密码算法的安全依赖于密钥的保密
- 大多数安全事件不是因为算法被破解，而是密钥管理出了问题
- 密钥是密码系统中最敏感的资产

**格言：**
> "密码学的关键不在算法，而在密钥。"
> —— 密码学界共识

### 1.2 密钥管理的目标

| 目标 | 说明 |
|------|------|
| 保密性 | 密钥只能被授权方访问 |
| 完整性 | 密钥不能被未授权修改 |
| 可用性 | 授权方在需要时能获取密钥 |
| 可审计 | 密钥的使用可以追溯和审计 |
| 可恢复 | 密钥丢失或损坏时可以恢复 |
| 合规性 | 满足相关法规和标准要求 |

### 1.3 密钥管理原则

**原则 1：最小权限原则（Least Privilege）**
- 只给需要的人最少的密钥访问权限
- 不同系统、不同用途使用不同的密钥
- 定期审查和回收权限

**原则 2：职责分离原则（Separation of Duties）**
- 密钥管理的不同职责由不同人负责
- 例如：密钥生成、密钥审批、密钥使用由不同人操作
- 防止单人可以完成敏感操作

**原则 3：密钥分层原则（Key Hierarchy）**
- 用高级密钥保护低级密钥
- 减少顶级密钥的使用频率
- 降低密钥泄露的影响

**原则 4：定期轮换原则（Key Rotation）**
- 定期更换密钥
- 减少密钥泄露的时间窗口
- 符合合规要求

**原则 5：安全存储原则（Secure Storage）**
- 密钥不能明文存储
- 使用专用硬件或加密系统存储
- 访问控制严格

**原则 6：审计监控原则（Audit & Monitoring）**
- 记录所有密钥操作
- 监控密钥使用情况
- 异常行为及时告警

### 1.4 密钥管理标准和法规

| 标准/法规 | 发布机构 | 说明 |
|----------|---------|------|
| NIST SP 800-57 | NIST | 密钥管理指南（3部分） |
| NIST SP 800-130 | NIST | 密钥管理系统框架 |
| ISO/IEC 11770 | ISO/IEC | IT 安全技术-密钥管理 |
| PKCS #11 | RSA 实验室 | 加密设备接口标准 |
| FIPS 140-2/140-3 | NIST | 加密模块安全要求 |
| 等保 2.0 | 中国 | 网络安全等级保护 |
| 商用密码管理条例 | 中国 | 商用密码管理法规 |
| GDPR | 欧盟 | 数据保护条例（涉及加密密钥） |
| PCI DSS | PCI SSC | 支付卡行业数据安全标准 |

## 二、密钥生命周期

### 2.1 生命周期总览

密钥的完整生命周期包括以下阶段：

```
┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐
│  生成  │→│  分发  │→│  存储  │→│  使用  │
└────────┘  └────────┘  └────────┘  └────────┘
                                         │
                                         ▼
┌────────┐  ┌────────┐  ┌────────┐
│  销毁  │←│  归档  │←│  轮换  │
└────────┘  └────────┘  └────────┘
```

**各阶段说明：**

| 阶段 | 说明 | 关键安全点 |
|------|------|-----------|
| 生成 | 创建新的密钥 | 随机性、密钥强度 |
| 分发 | 将密钥安全送达使用方 | 传输安全、身份验证 |
| 存储 | 安全保存密钥 | 加密存储、访问控制 |
| 使用 | 用密钥进行加密/解密/签名 | 使用审计、最小权限 |
| 轮换 | 定期更换新密钥 | 无缝切换、旧密钥处理 |
| 归档 | 不再使用但需要保留的密钥 | 安全存储、访问限制 |
| 销毁 | 彻底删除不再需要的密钥 | 不可恢复、销毁证明 |

### 2.2 密钥生成

**密钥生成的要求：**
1. **足够的熵**：密钥必须从密码学安全的随机源生成
2. **正确的长度**：密钥长度要满足安全要求
3. **合规的算法**：使用经过验证的算法生成
4. **可验证性**：生成的密钥符合规范要求

**随机数来源：**

| 随机源类型 | 说明 | 安全性 |
|-----------|------|--------|
| 硬件随机数生成器（HRNG） | 基于物理现象（热噪声、量子效应等） | 高 |
| 操作系统 CSPRNG | /dev/urandom、CryptGenRandom 等 | 较高 |
| 用户输入熵 | 鼠标移动、键盘输入等 | 中等（需要处理） |
| 伪随机数生成器（PRNG） | 软件算法生成 | 低（不能用于密钥） |

**密钥生成最佳实践：**
- 使用操作系统提供的 CSPRNG（如 /dev/urandom）
- 重要密钥使用硬件随机数生成器（HRNG）
- 密钥生成过程要审计
- 生成后立即验证密钥的有效性

**常见错误：**
- 使用 `rand()`、`Math.random()` 等非密码学随机数
- 使用时间戳、进程 ID 等可预测的种子
- 硬编码密钥（"固定密钥"）
- 密钥长度不够

### 2.3 密钥分发

**密钥分发的挑战：**
- 如何在不安全的信道上安全地传输密钥？
- 如何确认对方的身份？
- 如何防止密钥在传输中被窃取？

**密钥分发方式：**

| 方式 | 说明 | 适用场景 |
|------|------|---------|
| 人工分发 | 专人面对面交接 | 最高安全级别、少量密钥 |
| 加密传输 | 用另一个密钥加密传输 | 有密钥加密密钥的场景 |
| 公钥加密 | 用接收方公钥加密密钥 | 有 PKI 体系的场景 |
| 密钥交换协议 | DH、ECDH 等 | 实时通信场景 |
| 密钥分发中心（KDC） | 中心化的密钥分发 | Kerberos 等体系 |
| 密钥协商 | 双方协商生成会话密钥 | TLS 等协议 |

**密钥分发协议（以 Kerberos 为例）：**
```
Kerberos 密钥分发：
1. 用户向认证服务器（AS）请求票据许可票据（TGT）
2. AS 用 TGS 密钥加密 TGT，发给用户
3. 用户向票据许可服务器（TGS）请求服务票据
4. TGS 用服务密钥加密服务票据，发给用户
5. 用户向应用服务器出示服务票据
6. 双方获得会话密钥
```

### 2.4 密钥存储

**密钥存储的原则：**
1. **不落地**：敏感密钥尽量只在内存中使用
2. **加密存储**：存储的密钥必须加密保护
3. **访问控制**：严格限制密钥的访问权限
4. **审计记录**：所有访问密钥的操作都要记录

**密钥存储方式对比：**

| 存储方式 | 安全性 | 成本 | 说明 |
|---------|--------|------|------|
| 硬编码在代码中 | 极低 | 低 | 绝对禁止 |
| 明文文件 | 低 | 低 | 绝对禁止 |
| 加密文件 | 中 | 低 | 适合非敏感场景 |
| 数据库加密存储 | 中 | 中 | 一般应用场景 |
| 操作系统密钥链 | 中高 | 低 | macOS Keychain、Windows DPAPI |
| KMS（密钥管理服务） | 高 | 中高 | 云环境、企业级应用 |
| HSM（硬件安全模块） | 极高 | 高 | 金融、政府等高安全场景 |
| 智能卡 / USB Key | 高 | 中 | 用户身份认证、数字签名 |

**密钥存储的常见错误：**
- 密钥硬编码在源代码中（通过反编译即可获取）
- 密钥提交到版本控制系统（GitHub 等）
- 密钥明文存储在配置文件中
- 密钥存储在日志文件中
- 备份中包含明文密钥

### 2.5 密钥使用

**密钥使用的安全要点：**
1. **用途分离**：不同用途使用不同密钥（加密密钥不用于签名）
2. **最小权限**：只给需要的进程/用户访问密钥的权限
3. **使用审计**：记录每次密钥使用的时间、操作、使用者
4. **内存安全**：使用后及时清除内存中的密钥
5. **异常监控**：监控密钥的异常使用模式

**密钥使用的常见错误：**
- 一个密钥用于多个系统/多个用途
- 密钥在内存中长期存在
- 密钥被交换到磁盘（swap/pagefile）
- 核心转储（core dump）中包含密钥
- 错误日志中泄露密钥

### 2.6 密钥轮换

**什么是密钥轮换？**
定期或在特定条件下更换新的密钥，旧密钥停止使用。

**为什么需要轮换？**
1. **限制泄露影响**：如果密钥泄露，只影响一段时间
2. **降低破解概率**：减少攻击者的时间窗口
3. **合规要求**：很多法规要求定期轮换密钥
4. **最佳实践**：纵深防御的一部分

**轮换策略：**

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| 定期轮换 | 按固定时间周期轮换 | 常规密钥管理 |
| 事件驱动轮换 | 发生安全事件时立即轮换 | 应急响应 |
| 按需轮换 | 根据使用量或特定条件轮换 | 高频率使用的密钥 |
| 分级轮换 | 不同级别密钥轮换周期不同 | 密钥分层体系 |

**常见密钥轮换周期建议：**

| 密钥类型 | 建议轮换周期 |
|----------|-------------|
| 会话密钥 | 每次会话 |
| 数据加密密钥（DEK） | 30-90 天 |
| 密钥加密密钥（KEK） | 6-12 个月 |
| 主密钥（Master Key） | 1-2 年 |
| 根 CA 私钥 | 5-10 年（或到期更换） |
| TLS 证书私钥 | 1 年（或更短） |

**无缝轮换（零停机）：**
- 新旧密钥并行使用一段时间
- 先添加新密钥，再逐步淘汰旧密钥
- 对应用透明，不影响业务

### 2.7 密钥归档

**什么是密钥归档？**
密钥不再用于生产环境，但需要长期保存以便将来解密历史数据。

**归档的要求：**
1. **安全存储**：归档密钥的安全性不低于在用密钥
2. **访问控制**：更严格的访问控制
3. **可恢复性**：确保需要时能够恢复
4. **生命周期管理**：归档也有生命周期，到期后销毁

**归档的场景：**
- 轮换后的旧密钥（可能需要解密旧数据）
- 已停用系统的密钥
- 合规要求长期保存的密钥

### 2.8 密钥销毁

**什么是密钥销毁？**
当密钥不再需要时，彻底删除，使其不可恢复。

**销毁要求：**
1. **不可恢复**：销毁后无法通过任何手段恢复
2. **所有副本**：销毁所有存储位置的密钥副本
3. **销毁证明**：记录销毁过程，提供证明
4. **合规审计**：销毁操作需要审计记录

**销毁方法：**

| 介质类型 | 销毁方法 |
|---------|---------|
| 内存 | 覆写（用 0 或随机数据覆盖） |
| 普通磁盘 | 多次覆写（DoD 5220.22-M 标准） |
| SSD | 加密擦除（Crypto Erase）或物理销毁 |
| 硬件安全模块 | 调用销毁命令 |
| 纸质/物理介质 | 粉碎、焚烧、消磁 |
| 云存储 | 删除所有副本 + 验证 |

**销毁的注意事项：**
- 确保所有副本都被销毁（备份、缓存、日志等）
- 销毁后要验证确实无法恢复
- 保留销毁记录以备审计

## 三、密钥分级

### 3.1 为什么需要密钥分级

**问题：** 如果所有密钥都用相同的保护级别：
- 高安全级别的密钥保护不足
- 低安全级别的密钥保护过度（成本高）
- 一个密钥泄露可能影响整个系统

**解决方案：密钥分层架构**
```
用高级密钥保护低级密钥
高级密钥数量少、保护强、使用少
低级密钥数量多、保护相对弱、使用多
```

### 3.2 密钥分层模型

典型的三层密钥分层架构：

```
┌─────────────────────────────────────┐
│  主密钥 (Master Key / Root Key)      │  ← 第 0 层：最高级
│  数量最少，安全级别最高              │
│  用于保护密钥加密密钥                │
└─────────────────────────────────────┘
                   │ 加密保护
                   ▼
┌─────────────────────────────────────┐
│  密钥加密密钥 (KEK)                  │  ← 第 1 层：中间层
│  用于加密保护数据加密密钥            │
│  也叫密钥加密密钥、密钥包装密钥      │
└─────────────────────────────────────┘
                   │ 加密保护
                   ▼
┌─────────────────────────────────────┐
│  数据加密密钥 (DEK)                  │  ← 第 2 层：工作层
│  直接用于加密用户数据                │
│  数量最多，轮换最频繁                │
└─────────────────────────────────────┘
```

### 3.3 各层密钥详解

#### （1）主密钥（Master Key / Root Key）

**特点：**
- 整个密钥体系的根基
- 数量最少（通常每个系统只有 1 个或几个）
- 安全级别最高
- 不直接用于加密数据，只用于加密其他密钥
- 轮换周期最长（1-2 年或更长）

**存储要求：**
- 必须存储在 HSM 或同等安全级别的设备中
- 多重身份认证才能访问
- 物理安全保护

**风险：**
- 主密钥泄露 = 所有密钥泄露
- 主密钥丢失 = 所有加密数据丢失
- 必须有备份和恢复机制

#### （2）密钥加密密钥（KEK / Key Encryption Key）

**特点：**
- 用于加密/解密数据加密密钥（密钥包装）
- 也叫 Key Wrapping Key
- 不直接加密用户数据
- 轮换周期中等（6-12 个月）

**密钥包装（Key Wrapping）：**
```
包装（加密密钥）：
  包装后的密钥 = E(KEK, 原始DEK)

解包（解密密钥）：
  原始DEK = D(KEK, 包装后的密钥)
```

**优势：**
- DEK 可以安全地存储在普通存储中（因为被 KEK 加密了）
- KEK 不需要频繁更换（更换 KEK 只需要重新包装所有 DEK）
- DEK 可以方便地传输和备份

#### （3）数据加密密钥（DEK / Data Encryption Key）

**特点：**
- 直接用于加密用户数据
- 数量最多（每个用户/每个文件/每个会话可能一个）
- 轮换周期最短（30-90 天）
- 安全级别相对较低（因为有上层密钥保护）

**存储方式：**
- 被 KEK 加密后存储
- 可以和加密数据存储在一起
- 使用时解密到内存

#### （4）会话密钥（Session Key）

**特点：**
- 单次会话使用的临时密钥
- 会话结束后立即销毁
- 安全性要求：前向保密
- 数量非常多

**用途：**
- TLS 会话密钥
- VPN 会话密钥
- 即时通信会话密钥

### 3.4 密钥分层的优势

1. **降低风险**：高级密钥使用频率低，泄露概率小
2. **便于管理**：大量 DEK 的管理通过少数 KEK 实现
3. **灵活轮换**：更换 DEK 不需要更换主密钥
4. **职责分离**：不同层级的密钥由不同角色管理
5. **成本优化**：只对少量高级密钥使用高成本保护
6. **影响限制**：一个 DEK 泄露只影响对应的数据

## 四、密钥存储技术

### 4.1 硬件安全模块（HSM）

**HSM（Hardware Security Module）** 是专门用于密钥管理和密码运算的硬件设备。

**HSM 的核心功能：**
- 安全生成密钥
- 安全存储密钥（密钥永不离开 HSM）
- 执行密码运算（加密、解密、签名等）
- 密钥管理（生成、轮换、销毁）
- 访问控制和审计

**HSM 的安全特性：**

| 特性 | 说明 |
|------|------|
| 物理防篡改 | 检测到物理攻击时自动销毁密钥 |
| 密钥不导出 | 私钥永不出 HSM，只在内部使用 |
| 安全认证 | FIPS 140-2/3 Level 3/4 认证 |
| 多因素认证 | 密码 + 智能卡 + 指纹等 |
| 审计日志 | 记录所有操作，不可篡改 |
| 高可用性 | 支持集群、冗余、热备 |

**HSM 的部署形式：**
- 独立设备（PCIe 卡、网络设备）
- 云服务（AWS CloudHSM、Azure Key Vault HSM）
- 智能卡、USB Key（简化版 HSM）

**HSM 的适用场景：**
- 金融机构（银行、支付）
- 政府和军队
- 大型企业的核心密钥管理
- CA 机构的根密钥保护
- 密码服务平台

**FIPS 140 安全等级：**

| 等级 | 说明 | 典型应用 |
|------|------|---------|
| Level 1 | 基本安全要求 | 普通加密软件 |
| Level 2 | 角色认证、物理防篡改证据 | 商业 HSM |
| Level 3 | 身份认证、防入侵 | 金融级 HSM |
| Level 4 | 最高级别，完全防篡改 | 军事、政府最高安全 |

### 4.2 密钥管理系统（KMS）

**KMS（Key Management Service）** 是专门用于管理密钥生命周期的系统。

**KMS 的核心功能：**
- 密钥生成
- 密钥存储（通常后端是 HSM）
- 密钥分发
- 密钥轮换
- 密钥版本管理
- 访问控制
- 审计日志
- 加密/解密 API

**云 KMS 服务：**

| 云厂商 | KMS 服务 | 特点 |
|--------|---------|------|
| AWS | AWS KMS | 集成 AWS 服务，支持 CloudHSM |
| Azure | Azure Key Vault | 密钥、证书、机密管理 |
| GCP | Cloud KMS | 集成 GCP 服务 |
| 阿里云 | 密钥管理服务 KMS | 国密支持 |
| 腾讯云 | 密钥管理系统 KMS | 国密支持 |

**KMS 的优势：**
- 集中管理密钥
- 自动化密钥轮换
- 细粒度访问控制
- 完整的审计日志
- 高可用、高可靠
- 按使用量付费

** envelope encryption（信封加密）：**
KMS 的典型使用模式：
```
1. 生成数据密钥 DEK（由 KMS 生成）
2. 用 DEK 加密数据（本地加密，速度快）
3. 用 KMS 主密钥加密 DEK（信封）
4. 存储：加密的数据 + 加密的 DEK
5. 解密时：先调用 KMS 解密 DEK，再用 DEK 解密数据
```

### 4.3 可信平台模块（TPM）

**TPM（Trusted Platform Module）** 是集成在计算机主板上的安全芯片。

**TPM 的功能：**
- 安全存储密钥（绑定到硬件）
- 平台完整性度量（Secure Boot）
- 磁盘加密密钥保护（BitLocker、LUKS）
- 硬件随机数生成
- 密码运算加速

**TPM 的特点：**
- 绑定到特定设备，密钥不能迁移
- 防物理篡改
- 成本低（集成在主板上）
- 适合设备级密钥保护

### 4.4 智能卡 / USB Key

**智能卡（Smart Card）**：
- 内含微处理器和安全芯片
- 可以存储密钥和执行密码运算
- 密钥永不离开卡片
- 需要 PIN 码认证

**USB Key / U 盾：**
- 智能卡 + USB 接口
- 常见于网银、数字证书
- 双因素认证（持有设备 + 知道 PIN）

**特点：**
- 便携
- 成本适中
- 适合用户级密钥存储
- 物理持有 = 身份认证

### 4.5 软件密钥存储

#### 操作系统密钥存储

| 系统 | 存储方式 | 说明 |
|------|---------|------|
| Windows | DPAPI、证书存储 | 基于用户密码加密 |
| macOS | Keychain | 钥匙串，支持 iCloud 同步 |
| Linux | gnome-keyring、KWallet | 桌面环境密钥管理 |

#### 应用级密钥存储

- **Java KeyStore（JKS）**：Java 的密钥库文件
- **PKCS#12**：跨平台的密钥/证书存储格式（.p12, .pfx）
- **SSH agent**：SSH 密钥代理

#### 软件存储的问题：
- 依赖操作系统的安全性
- 可能被恶意软件窃取
- 物理安全依赖设备安全
- 需要额外的保护措施（主密码等）

## 五、密钥分发协议

### 5.1 密钥分发的需求

**核心问题：** 如何在不安全的信道上安全地共享密钥？

**解决方案分类：**

```
密钥分发方案
├── 人工分发（带外传输）
├── 对称密钥分发
│   ├── 密钥分发中心（KDC）
│   └── 预共享密钥（PSK）
├── 非对称密钥分发
│   ├── 公钥加密密钥
│   └── 证书 + PKI
└── 密钥协商
    ├── DH / ECDH
    └── 认证密钥交换（如 TLS）
```

### 5.2 密钥分发中心（KDC）

**KDC（Key Distribution Center）** 是一个可信的第三方，负责分发密钥。

**典型代表：Kerberos**

```
Kerberos 协议流程：

  Alice (用户)          KDC                  Bob (服务器)
     │                    │                     │
     │── AS 请求 ────────→│                     │
     │←── TGT ────────────│                     │
     │   (用 TGS 密钥加密)  │                     │
     │                    │                     │
     │── TGS 请求 ───────→│                     │
     │   (包含 TGT)        │                     │
     │←── 服务票据 ────────│                     │
     │   (用 Bob 密钥加密)  │                     │
     │                    │                     │
     │────────────── 服务票据 ─────────────────→│
     │                    │                     │
     │←──────────── 认证响应 ───────────────────│
     │                    │                     │
     │     双方获得会话密钥                      │
```

**Kerberos 的特点：**
- 中心化的密钥管理
- 支持单点登录（SSO）
- 使用对称加密
- 依赖 KDC 的可用性和安全性
- 有时间同步要求（防止重放攻击）

### 5.3 公钥加密分发

**原理：** 用接收方的公钥加密对称密钥，发送给接收方。

```
Alice 想给 Bob 发送密钥 K：

1. Alice 获取 Bob 的公钥（通过证书等方式）
2. Alice 生成随机对称密钥 K
3. Alice 用 Bob 的公钥加密 K：C = E(PK_Bob, K)
4. Alice 将 C 发送给 Bob
5. Bob 用私钥解密：K = D(SK_Bob, C)
6. 双方共享密钥 K
```

**特点：**
- 不需要第三方在线服务
- 需要公钥基础设施（PKI）来认证公钥
- 适合密钥交换，但不适合大量数据加密

### 5.4 Diffie-Hellman 密钥交换

（详细原理见「非对称密码学详解」第六章）

**DH 的问题：** 不提供身份认证，容易遭受中间人攻击。

**解决方案：认证 DH**

```
静态 DH（Static DH）：
- 双方使用固定的公钥（经过证书认证）
- 每次会话使用相同的私钥
- 不提供前向保密

临时 DH（Ephemeral DH, DHE）：
- 每次会话生成临时密钥对
- 用长期私钥签名临时公钥
- 提供前向保密
- 需要身份认证（签名）
```

**实际应用中的认证密钥交换：**

| 协议 | 说明 |
|------|------|
| TLS-DHE-RSA | DH 密钥交换 + RSA 认证 |
| TLS-ECDHE-RSA | ECDH 密钥交换 + RSA 认证 |
| TLS-ECDHE-ECDSA | ECDH 密钥交换 + ECDSA 认证 |
| IKE | IPsec 的密钥交换协议 |
| SSH | SSH 协议的密钥交换 |

### 5.5 预共享密钥（PSK）

**PSK（Pre-Shared Key）**：双方事先通过安全渠道共享密钥，直接使用。

**特点：**
- 简单直接
- 不需要复杂的协议
- 适合小规模、固定的场景
- 扩展性差（n 个用户需要 n(n-1)/2 个密钥）

**应用场景：**
- WiFi（WPA-PSK）
- VPN（预共享密钥模式）
- 小型设备之间的通信

## 六、密钥轮换策略

### 6.1 轮换策略设计

**设计轮换策略需要考虑的因素：**

| 因素 | 说明 |
|------|------|
| 密钥级别 | 越高级的密钥轮换周期越长 |
| 安全要求 | 安全要求越高，轮换越频繁 |
| 合规要求 | 法规标准的具体要求 |
| 业务影响 | 轮换对业务的影响程度 |
| 实施成本 | 轮换的技术复杂度和成本 |
| 风险容忍度 | 可接受的密钥泄露风险 |

### 6.2 轮换方式

#### （1）定期轮换（Scheduled Rotation）

**定义：** 按照固定的时间周期轮换密钥。

**优点：**
- 可预测，便于计划
- 符合合规要求
- 实现简单

**缺点：**
- 不够灵活
- 可能在密钥泄露后仍要等到轮换周期

**实现方式：**
```
方案 A：手动轮换
- 运维人员按计划执行
- 适合少量、低频率的密钥

方案 B：自动化轮换
- KMS 自动轮换
- 应用程序自动获取新密钥
- 适合大量密钥
```

#### （2）事件驱动轮换（Event-driven Rotation）

**定义：** 发生特定事件时立即轮换密钥。

**触发事件：**
- 怀疑密钥泄露
- 安全事件发生
- 员工离职（特别是有密钥访问权限的）
- 系统被入侵
- 安全审计发现问题
- 密钥使用异常

**原则：**
- 一旦怀疑密钥泄露，立即轮换
- 不要等确认，宁可信其有

#### （3）按需轮换（On-demand Rotation）

**定义：** 根据密钥的使用量或其他条件触发轮换。

**触发条件：**
- 密钥使用次数达到阈值
- 加密数据量达到阈值
- 特定操作完成后（如每次批量加密后）

### 6.3 无缝轮换实现

**目标：** 密钥轮换过程中不影响业务，对应用透明。

**实现方式：双密钥并行**

```
时间线：
  T0: 只有 Key A 在使用
  T1: 生成 Key B，添加到系统
       新数据用 Key B 加密
       旧数据仍用 Key A 解密
  T2: 所有旧数据都重新加密（或自然过期）
       废弃 Key A
  T3: 只有 Key B 在使用

应用程序：
  - 加密时始终使用最新版本的密钥
  - 解密时根据密钥版本选择对应的密钥
```

**密钥版本化：**
- 每个密钥有版本号
- 加密数据中包含密钥版本标识
- 解密时根据版本号选择正确的密钥

**示例（信封加密）：**
```
加密数据格式：
  [密钥版本号] + [加密的 DEK] + [加密的数据]

解密流程：
  1. 读取密钥版本号
  2. 用对应版本的 KEK 解密 DEK
  3. 用 DEK 解密数据
```

### 6.4 轮换后的旧密钥处理

**旧密钥的处理方式：**

| 方式 | 适用场景 | 说明 |
|------|---------|------|
| 立即销毁 | 会话密钥、临时密钥 | 不需要保留 |
| 归档保留 | 数据加密密钥 | 可能需要解密历史数据 |
| 逐步淘汰 | 所有密钥 | 给迁移留出时间 |

**旧密钥保留时间：**
- 取决于数据保留策略
- 取决于合规要求
- 数据解密完了就可以销毁旧密钥

### 6.5 轮换的审计与验证

**轮换后需要验证：**
1. 新密钥正常工作
2. 旧数据仍可解密（如果需要）
3. 旧密钥已正确处理
4. 所有系统都已更新到新密钥
5. 轮换过程有完整的审计记录

## 七、PKI 体系

### 7.1 PKI 概述

**PKI（Public Key Infrastructure）** 公钥基础设施，是管理公钥和数字证书的一套完整体系。

**PKI 的核心作用：**
- 证明公钥属于谁（身份绑定）
- 建立信任关系
- 管理数字证书的生命周期

**为什么需要 PKI？**

公钥密码学有一个根本问题：
```
你怎么知道这个公钥真的属于你以为的那个人？
```

PKI 通过可信第三方（CA）来解决这个问题。

### 7.2 PKI 组成

```
PKI 体系
├── CA（Certification Authority）
│   ├── 根 CA
│   └── 中间 CA
├── RA（Registration Authority）
├── 证书库 / 目录服务
├── 终端实体（用户/设备）
├── 证书撤销机制
│   ├── CRL（证书撤销列表）
│   └── OCSP（在线证书状态协议）
└── 密钥管理系统
```

#### （1）CA（证书颁发机构）

**CA（Certificate Authority）** 是 PKI 的核心，负责颁发和管理数字证书。

**CA 的职责：**
- 颁发数字证书
- 续期证书
- 撤销证书
- 发布 CRL/OCSP
- 维护证书状态

**CA 的层级：**

```
        根 CA (Root CA)
       /    |    \
  中间CA1  中间CA2  中间CA3
    / \      |      / \
 用户  用户  用户   用户 用户
```

- **根 CA**：最顶层，自签名证书，信任的根
- **中间 CA**：由根 CA 签发，用于签发终端实体证书
- **终端实体证书**：用户/服务器证书，由中间 CA 签发

**为什么需要多层 CA？**
- 根 CA 尽量离线，减少暴露
- 中间 CA 可以有多个，分工不同
- 一个中间 CA 出问题可以吊销，不影响根 CA
- 便于管理和扩展

#### （2）RA（注册机构）

**RA（Registration Authority）** 负责审核用户的身份信息，验证证书申请。

**RA 的职责：**
- 接收证书申请
- 验证申请人身份
- 审核证书申请信息
- 向 CA 提交签发请求
- 分发证书

RA 不签发证书（签发是 CA 的事），只负责身份验证。

#### （3）证书库

存储和分发证书的系统：
- LDAP 目录
- HTTP 下载
- 证书透明日志（Certificate Transparency）

#### （4）终端实体

拥有证书的用户或设备：
- 个人用户证书
- 服务器证书（TLS 证书）
- 设备证书
- 代码签名证书
- 邮件加密证书

### 7.3 数字证书

#### 什么是数字证书

**数字证书** 是由 CA 签发的电子文档，证明某个公钥属于某个实体。

**类比：**
数字证书就像身份证：
- 身份证证明你的名字和照片对应
- 数字证书证明你的公钥和你的身份对应
- 身份证由政府签发
- 数字证书由 CA 签发

#### X.509 证书格式

X.509 是最常用的数字证书标准。

**证书结构：**

```
X.509 证书
├── 证书版本（Version）
├── 序列号（Serial Number）
├── 签名算法（Signature Algorithm）
├── 颁发者（Issuer）
├── 有效期（Validity）
│   ├── 生效时间（Not Before）
│   └── 失效时间（Not After）
├── 主体（Subject）
├── 主体公钥信息（Subject Public Key Info）
│   ├── 公钥算法
│   └── 公钥值
├── 扩展（Extensions）
│   ├── 密钥用法
│   ├── 扩展密钥用法
│   ├── 基本约束（是否是CA）
│   ├── 主题备用名称（SAN）
│   ├── CRL 分发点
│   ├── 授权信息访问（OCSP地址）
│   └── ...
└── 签名（Signature）
```

**证书编码格式：**
- **PEM**：Base64 编码，以 `-----BEGIN CERTIFICATE-----` 开头
- **DER**：二进制格式
- **PKCS#7**：证书链格式
- **PKCS#12**：证书 + 私钥（通常有密码保护）

#### 证书验证过程

```
验证服务器证书的过程：

1. 检查证书格式是否正确
2. 检查证书是否在有效期内
3. 检查证书是否被吊销（CRL/OCSP）
4. 验证证书的签名
   - 用颁发者的公钥验证证书上的签名
   - 签名有效 → 证书确实是该 CA 签发的
5. 验证颁发者证书
   - 递归验证上一级证书
   - 直到根 CA
6. 检查根证书是否在信任列表中
7. 检查证书用途（是否用于服务器认证）
8. 检查域名是否匹配（SAN / CN）

所有检查都通过 → 证书可信
```

**信任链（Chain of Trust）：**
```
服务器证书 → 中间 CA 证书 → 根 CA 证书
  (用户验证)    (CA签发)     (自签名，操作系统信任)

信任根：根 CA 证书（预装在操作系统/浏览器中）
```

### 7.4 证书生命周期

```
申请 → 审核 → 签发 → 使用 → 续期 → 撤销 → 过期
```

#### （1）证书申请

**CSR（Certificate Signing Request）**：
- 申请者生成密钥对
- 构造 CSR（包含公钥、身份信息等）
- 用私钥签名 CSR
- 发送 CSR 给 CA

#### （2）身份审核

CA 在签发证书前需要验证申请人的身份：

| 验证级别 | 说明 | 适用场景 |
|---------|------|---------|
| DV（Domain Validation） | 验证域名控制权 | 普通网站 |
| OV（Organization Validation） | 验证组织身份 | 企业网站 |
| EV（Extended Validation） | 严格验证组织身份 | 银行、电商等 |

#### （3）证书签发

CA 验证通过后，签发证书：
- 用 CA 私钥对证书签名
- 返回证书给申请人
- 发布到证书库

#### （4）证书使用

证书的使用场景：
- TLS/SSL 服务器认证
- 客户端认证
- 代码签名
- 邮件加密（S/MIME）
- 文档签名
- VPN 认证

#### （5）证书续期

证书有效期满前需要续期：
- 生成新的密钥对（推荐）
- 申请新证书
- 替换旧证书
- 旧证书过期失效

**证书有效期趋势：**
- 早期：5-10 年
- 2018 年：最长 2 年
- 2020 年：最长 1 年
- 未来可能更短（90 天）

#### （6）证书撤销

证书在有效期内可能需要提前撤销：

**撤销原因：**
- 私钥泄露
- 身份信息变更
- 组织关系终止
- 证书信息错误
- 安全事件

**撤销机制：**

| 机制 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| CRL | 证书撤销列表 | 简单、批量 | 文件大、更新不及时 |
| OCSP | 在线证书状态协议 | 实时查询、响应小 | 隐私问题、性能压力 |
| OCSP Stapling | OCSP 装订 | 实时、保护隐私 | 服务器实现复杂 |

**CRL（Certificate Revocation List）：**
```
CA 定期发布撤销列表
包含所有被撤销证书的序列号和撤销时间
用户下载 CRL 并检查证书是否在列表中

问题：
- CRL 文件可能很大
- 更新有延迟（不是实时的）
- 用户需要定期下载
```

**OCSP（Online Certificate Status Protocol）：**
```
用户向 OCSP 服务器查询特定证书的状态
OCSP 服务器返回：有效 / 已撤销 / 未知

优点：
- 实时
- 响应小（只查一个证书）

问题：
- 隐私泄露（OCSP 服务器知道你访问了哪个网站）
- 性能压力（每个证书都要查询）
- OCSP 服务器可能不可用
```

**OCSP Stapling（OCSP 装订）：**
```
服务器自己去 OCSP 查询证书状态
然后将 OCSP 响应"装订"在 TLS 握手中发给客户端

优点：
- 保护用户隐私（OCSP 服务器不知道用户）
- 减少 OCSP 服务器压力
- 客户端不需要额外连接

Must-Staple 扩展：
- 证书要求必须装订 OCSP
- 否则浏览器拒绝连接
```

### 7.5 根证书信任

**信任根从哪里来？**
- 操作系统预装（Windows、macOS、iOS、Android）
- 浏览器自带（Firefox 有自己的根证书库）
- 企业内部部署（企业根 CA）

**根证书的重要性：**
- 信任根 CA = 信任它签发的所有证书
- 根 CA 私钥泄露 = 整个 PKI 体系崩塌
- 根 CA 必须最高级别保护

**根 CA 保护措施：**
- 离线存储（Air-gapped）
- HSM 硬件保护
- 多人控制（M of N 密钥分割）
- 严格的物理安全
- 极少使用（只签发中间 CA）

### 7.6 证书透明性（Certificate Transparency）

**问题：**
- CA 可能错误地或恶意地签发不属于你的证书
- 你可能不知道有人冒用你的域名申请了证书

**解决方案：Certificate Transparency（CT）**

**原理：**
- 所有 CA 签发的证书都必须记录在公开的日志中
- 日志是只追加的（Append-only）
- 任何人都可以查询日志
- 浏览器要求证书有 CT 证明

**CT 日志：**
- 全球有多个 CT 日志服务器
- 证书必须至少有 2 个以上的 CT 证明
- 可以监控你的域名有哪些证书被签发

## 八、密钥管理的常见问题与最佳实践

### 8.1 常见错误

#### 错误 1：硬编码密钥

```python
# 错误！密钥硬编码在代码中
API_KEY = "sk-1234567890abcdef"
ENCRYPTION_KEY = b"my_secret_key_12345"
```

**风险：**
- 反编译即可获取
- 代码泄露（如 GitHub）= 密钥泄露
- 所有环境使用相同密钥

**正确做法：**
- 从环境变量读取
- 从配置中心/KMS 读取
- 不同环境使用不同密钥

#### 错误 2：密钥提交到版本控制

**案例：**
- 开发者不小心把包含密钥的配置文件提交到 GitHub
- 被爬虫扫描到，密钥被盗
- 造成经济损失（如云服务被挖矿）

**防护：**
- 使用 `.gitignore` 排除配置文件
- 使用 Git 钩子检查敏感信息
- 密钥泄露检测工具（如 git-secrets、truffleHog）
- 一旦泄露立即轮换密钥

#### 错误 3：密钥明文存储

```
# 错误！配置文件中明文存储密钥
database.password = my_secret_password
api.key = abc123def456
```

**正确做法：**
- 加密配置文件
- 使用 KMS 加密密钥
- 使用 Secret 管理工具（HashiCorp Vault 等）

#### 错误 4：密钥复用

- 一个密钥用于多个系统
- 一个密钥既用于加密又用于签名
- 测试环境和生产环境使用相同密钥

**风险：** 一个地方泄露，所有地方都不安全

**原则：** 一用一密，一系统一密

#### 错误 5：从不轮换密钥

- 密钥一旦生成就永远不变
- 员工离职了密钥还在使用
- 系统上线几年了密钥从没换过

**风险：** 密钥泄露了也不知道，长期暴露

#### 错误 6：没有备份

- 密钥丢失 = 数据永久丢失
- 只有一份密钥，损坏了就完了

**正确做法：**
- 密钥要有备份
- 备份要加密存储
- 定期测试恢复
- 密钥分割多人保管（Shamir 秘密共享）

### 8.2 最佳实践总结

**1. 密钥生成**
- 使用密码学安全的随机数生成器
- 密钥长度满足安全要求
- 在可信环境中生成

**2. 密钥存储**
- 永远不要明文存储密钥
- 使用 KMS 或 HSM 存储
- 访问控制最小化
- 内存中的密钥及时清除

**3. 密钥分发**
- 使用安全的密钥分发协议
- 验证对方身份
- 传输过程加密保护

**4. 密钥使用**
- 一用一密（不同用途不同密钥）
- 最小权限原则
- 审计所有密钥使用
- 监控异常使用模式

**5. 密钥轮换**
- 定期轮换（按策略执行）
- 事件驱动轮换（怀疑泄露立即轮换）
- 无缝轮换（不影响业务）
- 轮换后验证

**6. 密钥销毁**
- 不再使用的密钥及时销毁
- 确保所有副本都被销毁
- 销毁后验证不可恢复
- 保留销毁记录

**7. 备份与恢复**
- 密钥要有备份
- 备份要安全存储
- 定期测试恢复流程
- 多人共管（关键密钥）

**8. 审计与监控**
- 记录所有密钥操作
- 定期审计密钥使用
- 监控异常行为
- 告警机制

### 8.3 关键指标（KPI）

| 指标 | 说明 | 目标 |
|------|------|------|
| 密钥轮换及时率 | 按时轮换的密钥比例 | 100% |
| 密钥泄露事件数 | 密钥泄露的次数 | 0 |
| 密钥管理合规率 | 符合政策的密钥比例 | 100% |
| 密钥恢复时间 | 密钥丢失后恢复所需时间 | < 4小时 |
| 密钥使用审计覆盖率 | 有审计记录的密钥使用比例 | 100% |

## 九、实际案例

### 案例 1：Code Spaces 被黑客删除所有数据

**背景：**
- Code Spaces 是一家代码托管服务
- 使用 AWS 云服务

**事件经过：**
1. 黑客获取了 Code Spaces 的 AWS 访问密钥
2. 黑客登录 AWS 控制台
3. 黑客先是勒索，要求支付赎金
4. Code Spaces 试图恢复访问权限
5. 黑客发现后，删除了所有数据（EC2、S3、EBS 等）
6. Code Spaces 因此倒闭

**原因分析：**
- AWS 访问密钥管理不当
- 可能是硬编码在代码中或配置文件泄露
- 没有启用 MFA 保护
- 权限过大（一个密钥可以访问所有资源）

**教训：**
- 密钥权限要最小化
- 启用多因素认证
- 定期轮换密钥
- 监控异常访问
- 数据备份要隔离（不能用同一个账号）

### 案例 2：Uber 数据泄露（2016）

**背景：**
- Uber 5700 万用户数据泄露
- 包括司机和乘客的个人信息

**事件经过：**
1. 黑客在 GitHub 上发现了 Uber 工程师提交的 AWS 密钥
2. 黑客用这个密钥访问了 Uber 的 AWS 账户
3. 下载了 5700 万用户的数据
4. 黑客向 Uber 勒索 10 万美元
5. Uber 支付了赎金，并试图掩盖事件

**后果：**
- Uber 被罚款 1.48 亿美元
- CEO 被迫辞职
- 声誉严重受损

**教训：**
- 绝对不能把密钥提交到版本控制
- 密钥扫描和检测很重要
- 密钥权限要最小化
- 安全事件不能隐瞒

### 案例 3：DigiNotar CA 被黑

**背景：**
- DigiNotar 是荷兰的一家 CA 机构
- 2011 年被黑客入侵

**事件经过：**
1. 黑客入侵了 DigiNotar 的系统
2. 黑客签发了数百张伪造的证书
3. 包括 Google、Yahoo、Mozilla 等知名网站的证书
4. 这些伪造证书被用于伊朗的中间人攻击
5. 浏览器厂商紧急撤销 DigiNotar 的根证书
6. DigiNotar 破产

**影响：**
- 整个 PKI 体系的信任受到质疑
- 数百万用户面临安全风险
- CA 的安全标准被提高

**教训：**
- CA 是 PKI 的信任根基，必须最高级别保护
- CA 被攻破 = 整个信任体系崩塌
- 证书透明性（CT）很重要
- 根 CA 应该离线保护
