# 密钥轮换策略

### 6.1 轮换策略设计

**设计轮换策略需要考虑的因素：**

| 因素 | 说明 |
|------|------|
| 密钥级别 | 越高级的密钥轮换周期越长 |
| 安全要求 | 安全要求越高，轮换越频繁 |
| 合规要求 | 法规标准的具体要求 |
| 业务影响 | 轮换对业务的影响程度 |
| 实施成本 | 轮换的技术复杂度和成本 |
| 风险容忍度 | 可接受的密钥泄露风险 |

### 6.2 轮换方式

#### （1）定期轮换（Scheduled Rotation）

**定义：** 按照固定的时间周期轮换密钥。

**优点：**
- 可预测，便于计划
- 符合合规要求
- 实现简单

**缺点：**
- 不够灵活
- 可能在密钥泄露后仍要等到轮换周期

**实现方式：**
```
方案 A：手动轮换
- 运维人员按计划执行
- 适合少量、低频率的密钥

方案 B：自动化轮换
- KMS 自动轮换
- 应用程序自动获取新密钥
- 适合大量密钥
```

#### （2）事件驱动轮换（Event-driven Rotation）

**定义：** 发生特定事件时立即轮换密钥。

**触发事件：**
- 怀疑密钥泄露
- 安全事件发生
- 员工离职（特别是有密钥访问权限的）
- 系统被入侵
- 安全审计发现问题
- 密钥使用异常

**原则：**
- 一旦怀疑密钥泄露，立即轮换
- 不要等确认，宁可信其有

#### （3）按需轮换（On-demand Rotation）

**定义：** 根据密钥的使用量或其他条件触发轮换。

**触发条件：**
- 密钥使用次数达到阈值
- 加密数据量达到阈值
- 特定操作完成后（如每次批量加密后）

### 6.3 无缝轮换实现

**目标：** 密钥轮换过程中不影响业务，对应用透明。

**实现方式：双密钥并行**

```
时间线：
  T0: 只有 Key A 在使用
  T1: 生成 Key B，添加到系统
       新数据用 Key B 加密
       旧数据仍用 Key A 解密
  T2: 所有旧数据都重新加密（或自然过期）
       废弃 Key A
  T3: 只有 Key B 在使用

应用程序：
  - 加密时始终使用最新版本的密钥
  - 解密时根据密钥版本选择对应的密钥
```

**密钥版本化：**
- 每个密钥有版本号
- 加密数据中包含密钥版本标识
- 解密时根据版本号选择正确的密钥

**示例（信封加密）：**
```
加密数据格式：
  [密钥版本号] + [加密的 DEK] + [加密的数据]

解密流程：
  1. 读取密钥版本号
  2. 用对应版本的 KEK 解密 DEK
  3. 用 DEK 解密数据
```

### 6.4 轮换后的旧密钥处理

**旧密钥的处理方式：**

| 方式 | 适用场景 | 说明 |
|------|---------|------|
| 立即销毁 | 会话密钥、临时密钥 | 不需要保留 |
| 归档保留 | 数据加密密钥 | 可能需要解密历史数据 |
| 逐步淘汰 | 所有密钥 | 给迁移留出时间 |

**旧密钥保留时间：**
- 取决于数据保留策略
- 取决于合规要求
- 数据解密完了就可以销毁旧密钥

### 6.5 轮换的审计与验证

**轮换后需要验证：**
1. 新密钥正常工作
2. 旧数据仍可解密（如果需要）
3. 旧密钥已正确处理
4. 所有系统都已更新到新密钥
5. 轮换过程有完整的审计记录
