# 数据泄露应急响应

### 7.1 数据泄露事件分级

根据《国家网络安全事件应急预案》和行业实践，数据泄露事件可分为以下级别：

| 级别 | 定义 | 判定标准（参考） |
|------|------|------------------|
| **特别重大（I 级）** | 特别严重的数据泄露 | 1000 万人以上个人信息泄露，或核心数据泄露 |
| **重大（II 级）** | 严重的数据泄露 | 100 万-1000 万人个人信息泄露，或重要数据泄露 |
| **较大（III 级）** | 较严重的数据泄露 | 10 万-100 万人个人信息泄露 |
| **一般（IV 级）** | 一般的数据泄露 | 1 万-10 万人个人信息泄露 |
| **轻微** | 轻微的数据泄露 | 1 万人以下，影响有限 |

### 7.2 应急响应组织

**应急响应小组组成**：

| 角色 | 职责 |
|------|------|
| **总指挥** | 总体决策、资源协调 |
| **技术组** | 技术分析、事件处置、漏洞修复 |
| **业务组** | 业务影响评估、业务恢复 |
| **法务组** | 法律风险评估、合规上报 |
| **公关组** | 对外沟通、媒体应对 |
| **人力资源组** | 内部人员相关事宜 |

### 7.3 应急响应流程

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  发现报告  │ →  │  研判启动  │ →  │  应急处置  │ →  │  恢复重建  │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
                                                                 ↓
                                                           ┌──────────┐
                                                           │  总结改进  │
                                                           └──────────┘
```

#### 7.3.1 发现与报告

**发现途径**：
- DLP 系统告警
- IDS/IPS 告警
- 安全设备告警
- 员工举报
- 用户投诉
- 监管通报
- 媒体曝光
- 暗网监测

**报告要求**：
- 第一时间上报
- 报告内容：时间、地点、事件描述、影响范围、已采取措施
- 逐级上报，紧急情况可越级

#### 7.3.2 研判与启动

**研判内容**：
- 事件真实性确认
- 事件类型判定
- 事件级别评估
- 影响范围评估
- 是否启动应急预案

**启动条件**：
- 确认发生数据泄露
- 达到一定级别以上
- 由总指挥或授权人宣布启动

#### 7.3.3 应急处置

**核心处置措施**：

1. **遏制（Containment）**
   - 隔离受影响的系统和网络
   - 封禁攻击 IP
   - 禁用被盗账号
   - 关闭可疑端口和服务
   - 切断数据泄露通道

2. **取证（Evidence Preservation）**
   - 保存系统日志
   - 保存网络流量
   - 磁盘镜像
   - 内存镜像
   - 记录操作过程
   - 注意：取证不能破坏原始证据

3. **评估（Assessment）**
   - 泄露了什么数据？
   - 泄露了多少数据？
   - 数据敏感级别？
   - 影响哪些用户/业务？
   - 造成了什么损失？
   - 泄露途径是什么？
   - 攻击者是谁？（如可确定）

4. **根除（Eradication）**
   - 修复漏洞
   - 清除后门/木马
   - 重置密码/密钥
   - 加固系统配置
   - 清除恶意账号

5. **通知（Notification）**
   - 通知受影响的用户
   - 上报监管部门
   - 必要时向公众披露
   - 通知合作方

#### 7.3.4 恢复与重建

**恢复步骤**：
1. 验证系统安全性
2. 逐步恢复业务
3. 监控系统状态
4. 确认恢复正常

**重建工作**：
- 完善安全防护体系
- 补充安全设备
- 优化安全策略
- 加强安全管理

#### 7.3.5 总结与改进

**事后总结**：
- 事件时间线还原
- 根本原因分析
- 处置过程评估
- 经验教训总结

**改进措施**：
- 技术改进（补充防护手段）
- 管理改进（完善制度流程）
- 人员改进（加强培训教育）
- 预案改进（优化应急预案）

### 7.4 数据泄露通知

#### 7.4.1 通知对象

1. **受影响的个人**
   - 告知其个人信息被泄露
   - 告知可能的影响
   - 提供保护建议

2. **监管部门**
   - 根据法律法规要求上报
   - 《个人信息保护法》要求及时上报
   - 《网络安全法》要求及时上报

3. **合作方**
   - 如果涉及合作方数据
   - 如果合作方也受到影响

4. **公众/媒体**
   - 大规模数据泄露时
   - 需要公开透明

#### 7.4.2 通知时限

| 法规 | 通知时限 |
|------|----------|
| 《个人信息保护法》 | 及时通知（未明确具体时限，一般理解为 72 小时内） |
| 《网络安全法》 | 及时上报 |
| GDPR | 72 小时内通知监管机构 |
| 等保 2.0 | 及时上报，重大事件 1 小时内 |

#### 7.4.3 通知内容

**对个人的通知内容**：
- 泄露事件概况
- 泄露的信息类型
- 可能造成的影响
- 已采取的措施
- 个人可采取的保护措施
- 联系方式

**对监管部门的报告内容**：
- 事件基本情况
- 影响范围和程度
- 已采取的措施
- 下一步工作计划
- 联系人及方式

### 7.5 典型案例分析

#### 案例：某酒店数据泄露事件

**事件经过**：
- 某连锁酒店集团 5 亿条客户信息在暗网售卖
- 包括姓名、身份证号、手机号、住址、入住记录等
- 数据来源：酒店开房记录系统漏洞

**应急响应过程**：

1. **发现（T+0）**
   - 安全公司监测到暗网售卖信息
   - 通知酒店集团
   - 酒店集团内部核实

2. **启动（T+1 天）**
   - 成立应急小组
   - 确认数据真实性
   - 评估影响范围
   - 启动应急预案

3. **处置（T+1~7 天）**
   - 修复相关系统漏洞
   - 封禁可疑访问 IP
   - 加强数据库访问控制
   - 开展全面安全排查
   - 向监管部门报告

4. **恢复（T+7~30 天）**
   - 系统恢复正常运行
   - 安全加固完成
   - 持续监控异常

5. **改进（持续）**
   - 全面安全整改
   - 部署数据库安全产品
   - 完善数据安全治理
   - 加强人员安全培训

**事件影响**：
- 股价下跌 10%+
- 用户集体诉讼
- 监管部门罚款
- 品牌声誉严重受损

**经验教训**：
- 数据库安全防护不足
- 缺乏数据访问审计
- 应急响应能力不足
- 数据安全意识薄弱
