# 数据备份容灾与安全

> 本文档系统介绍数据备份策略与 3-2-1 原则、备份安全威胁与防护措施、容灾技术与双活数据中心架构、灾难恢复计划（DRP）制定、RPO/RTO 指标与业务影响分析（BIA），以及云备份安全和恢复演练实践。

## 一、数据备份策略

### 1.1 备份类型详解

| 备份类型 | 原理 | 优点 | 缺点 | 适用场景 |
|----------|------|------|------|----------|
| 全量备份 | 完整复制所有数据 | 恢复简单快速 | 耗时长、存储大 | 基础备份、周期性执行 |
| 增量备份 | 只备份上次备份后变化的数据 | 速度快、存储小 | 恢复需全量+所有增量 | 日常备份 |
| 差异备份 | 备份自上次全量后所有变化数据 | 恢复只需全量+最近差异 | 随时间增大 | 中等规模环境 |

```
备份策略时间线示例:

周日 周一 周二 周三 周四 周五 周六
 ↓    ↓    ↓    ↓    ↓    ↓    ↓
全量  增量 增量 增量 增量 增量 全量

恢复场景（周五故障）:
1. 恢复周日全量备份
2. 依次恢复周一至周五增量备份
→ 需要6个备份文件

优化策略（差异备份）:
周日 周一 周二 周三 周四 周五 周六
 ↓    ↓    ↓    ↓    ↓    ↓    ↓
全量  差异 差异 差异 差异 差异 全量

恢复场景（周五故障）:
1. 恢复周日全量备份
2. 恢复周五差异备份
→ 只需2个备份文件
```

### 1.2 3-2-1 备份原则

```
3-2-1 备份黄金法则:

3 - 至少保留 3 份数据副本
│   ├── 1份生产数据（原始数据）
│   ├── 1份主备份（本地/近线）
│   └── 1份备份的备份（异地/离线）

2 - 使用 2 种不同存储介质
│   ├── 介质1: 磁盘/NAS/SAN
│   └── 介质2: 磁带/对象存储/云存储

1 - 至少 1 份备份存放在异地
    ├── 异地机房
    ├── 云存储（不同区域）
    └── 离线保险箱（磁带/移动硬盘）

扩展: 3-2-1-1-0 原则
├── +1 份不可变备份（Immutable Backup）
└── 0 错误验证（每次备份都需验证恢复）
```

### 1.3 备份窗口与备份计划

```
企业备份时间窗口设计:

每日备份计划:
00:00 ──────────────────────────────── 24:00
  │                                       │
  ├── 02:00-04:00  数据库全量备份         │ ← 业务低谷期
  ├── 04:00-05:00  文件增量备份           │
  ├── 05:00-06:00  日志归档               │
  ├── 06:00-07:00  备份验证               │
  ├── 12:00-12:30  数据库增量备份（午间）  │ ← 业务午休
  └── 18:00-19:00  数据库增量备份（晚间）  │ ← 业务结束前

每周备份计划:
  ├── 周日: 全量备份 + 异地复制
  ├── 周一~周六: 增量备份
  └── 周三: 差异备份（额外验证点）

每月备份计划:
  ├── 月初: 全量备份归档（长期保存）
  ├── 月中: 备份恢复演练
  └── 月末: 备份数据完整性校验

保留策略:
  ├── 日备份保留: 30天
  ├── 周备份保留: 12周
  ├── 月备份保留: 36个月
  └── 年备份保留: 7年（合规要求）
```

## 二、备份安全威胁

### 2.1 勒索软件对备份的威胁

勒索软件是数据备份面临的最大威胁。现代勒索软件（如 LockBit、BlackCat、Akira）在加密生产数据前，会先尝试破坏或加密备份数据。

```
勒索软件攻击备份的典型路径:

攻击阶段1: 侦察
├── 发现备份系统（vssadmin list shadows）
├── 识别备份软件和存储位置
├── 探测网络共享和映射驱动器
└── 获取备份管理凭据

攻击阶段2: 备份破坏
├── 删除卷影副本 (vssadmin delete shadows /all /quiet)
├── 篡改备份软件配置
├── 加密备份存储目录
├── 停止备份服务 (net stop BackupExecAgent)
└── 删除备份历史记录

攻击阶段3: 生产数据加密
├── 加密业务数据库
├── 加密文件服务器
├── 加密应用数据
└── 留下勒索说明

攻击阶段4: 勒索谈判
├── 威胁公开敏感数据
├── 要求加密货币支付
└── 提供解密密钥（不可靠）
```

```powershell
# 攻击者常用的备份破坏命令（防御者需监控这些操作）

# 删除 Windows 卷影副本
vssadmin delete shadows /all /quiet
wmic shadowcopy delete

# 停止备份相关服务
net stop VSS
net stop swprv
net stop BackupExecAgentAccelerator
net stop BackupExecRPCService
net stop BackupExecAgentBrowser

# 禁用 Windows 备份
wbadmin delete catalog -quiet
bcdedit /set {default} recoveryenabled No

# 破坏 Veeam 备份（如已获取管理权限）
# 停止 Veeam 服务
net stop "Veeam Backup Service"
net stop "Veeam Backup Catalog Data Service"

# 删除备份文件
del /f /q "D:\Backups\*.vbk"
del /f /q "\\backup-server\share\*.vib"
```

```
备份篡改风险场景:

场景1: 内部威胁
├── 恶意管理员修改备份数据
├── 篡改财务数据进行欺诈
└── 修改日志备份消除痕迹

场景2: 供应链攻击
├── 备份软件本身被植入后门
├── 备份存储设备固件被篡改
└── 备份传输通道被劫持

场景3: 权限滥用
├── 备份管理员账号被盗
├── 过度授权导致误操作或恶意操作
└── 共享备份凭据泄露

场景4: 数据投毒
├── 攻击者提前植入恶意数据
├── 等待数据进入备份后触发
└── 恢复时连带恢复恶意载荷
```

### 2.3 备份泄露威胁

```
备份泄露场景:

场景1: 备份存储未加密

├── 备份文件未经加密上传云存储
└── 网络传输中备份数据被截获

场景3: 云备份配置错误
├── S3 存储桶公开访问
├── 快照共享给了错误账号
└── 跨区域复制配置暴露
```

## 三、备份安全措施

### 3.1 备份加密

```
备份加密分层方案:

存储层加密:
├── 硬件级: 自加密磁盘（SED）
├── 存储阵列加密（如 EMC KMIP）
└── 对象存储 SSE-S3/SSE-KMS

文件层加密:
├── 备份软件内置加密（AES-256）
├── 传输层 TLS 1.2+ 加密
└── 独立加密工具（GnuPG）

密钥管理:
├── 密钥分离存储（KMS/HSM）
├── 密钥轮换（每季度）
├── 密钥备份和恢复
└── 多人控制（M-of-N 分片）
```

```bash
# 备份加密示例

# 1. 数据库备份 + GPG 加密
mysqldump -u root -p --all-databases --single-transaction | \
  gpg --cipher-algo AES256 --symmetric --batch --passphrase-file key.txt | \
  gzip > backup_$(date +%Y%m%d).sql.gz.gpg

# 2. 文件备份 + openssl 加密
tar czf - /data | openssl enc -aes-256-cbc -salt \
  -pass file:password.txt -out backup_$(date +%Y%m%d).tar.enc

# 3. 验证备份完整性
sha256sum backup_*.tar.enc > backup_hashes.txt

# 4. 恢复时解密
openssl enc -d -aes-256-cbc -in backup_20260911.tar.enc \
  -pass file:password.txt | tar xzf -
```

### 3.2 离线备份（Air-Gap Backup）

```
离线备份实现方式:

1. 物理离线 - 磁带备份
   ├── 备份完成后磁带物理移出磁带库
   ├── 存储在异地保险库
   └── 恢复时需人工取回并加载

2. 逻辑离线 - 不可变存储
   ├── AWS S3 Object Lock（WORM）
   ├── Azure Immutable Blob Storage
   └── 对象存储版本锁定

3. 网络隔离 - 网络离线
   ├── 备份存储位于独立网络/VLAN
   ├── 仅在备份窗口开放网络连接
   └── 备份完成后立即断开网络

4. 云离线 - 冷存储归档
   ├── 备份数据归档到云冷存储
   ├── 设置最短保留期（不可提前删除）
   └── 恢复需提前发起（数小时延迟）
```

```python
# 不可变备份配置示例 (AWS S3 Object Lock)

import boto3

s3 = boto3.client('s3')

# 创建启用了对象锁的存储桶
bucket_name = 'immutable-backup-bucket'
s3.create_bucket(
    Bucket=bucket_name,
    ObjectLockEnabledForBucket=True,
    CreateBucketConfiguration={
        'LocationConstraint': 'ap-northeast-1'
    }
)

# 上传备份文件并设置保留期
import datetime

retention_date = datetime.datetime.now() + datetime.timedelta(days=90)

s3.put_object(
    Bucket=bucket_name,
    Key='backup/database_20260911.dump',
    Body=open('database.dump', 'rb').read(),
    ContentType='application/octet-stream'
)

# 设置对象锁定（90天内不可删除/覆盖）
s3.put_object_retention(
    Bucket=bucket_name,
    Key='backup/database_20260911.dump',
    Retention={
        'Mode': 'COMPLIANCE',  # 合规模式 - 任何人都无法绕过
        'RetainUntilDate': retention_date
    }
)

# 设置法律持有（Legal Hold - 完全锁定）
s3.put_object_legal_hold(
    Bucket=bucket_name,
    Key='backup/database_20260911.dump',
    LegalHold={'Status': 'ON'}
)

# 尝试删除会被拒绝（在保留期内）
# s3.delete_object(...) -> AccessDenied
```

### 3.3 不可变备份（Immutable Backup）

```
不可变备份核心原则:

WORM (Write Once Read Many) - 一写多读
├── 备份数据写入后不可修改
├── 在保留期内不可删除
├── 即使管理员也无法篡改
└── 勒索软件无法加密或删除

实现级别:
├── Level 1: 软件级锁定（备份软件配置）
│   └── 可被管理员绕过，安全性低
├── Level 2: 存储级锁定（对象存储WORM）
│   └── 存储引擎强制执行，安全性中
├── Level 3: 硬件级锁定（磁带物理离线）
│   └── 物理隔离，安全性最高
└── Level 4: 多层组合（存储级 + 硬件级 + 加密）
    └── 纵深防御，安全性最高
```

### 3.4 备份验证

```bash
#!/bin/bash
# 备份完整性验证脚本

BACKUP_FILE="$1"
EXPECTED_HASH="$2"
LOG_FILE="/var/log/backup_verify.log"

log() {
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] $1" | tee -a "$LOG_FILE"
}

# 1. 文件完整性校验
log "开始验证备份文件: $BACKUP_FILE"
ACTUAL_HASH=$(sha256sum "$BACKUP_FILE" | awk '{print $1}')

if [ "$ACTUAL_HASH" = "$EXPECTED_HASH" ]; then
    log "[通过] 哈希校验通过"
else
    log "[失败] 哈希不匹配！期望: $EXPECTED_HASH 实际: $ACTUAL_HASH"
    exit 1
fi

# 2. 备份内容验证（解压检查）
TEMP_DIR=$(mktemp -d)
log "解压备份到临时目录: $TEMP_DIR"

# 解密+解压
openssl enc -d -aes-256-cbc -in "$BACKUP_FILE" -pass file:/etc/backup.key | \
    tar xzf - -C "$TEMP_DIR"

# 3. 验证关键文件存在
REQUIRED_FILES=("database.sql" "config.json" "users.csv")
for file in "${REQUIRED_FILES[@]}"; do
    if [ -f "$TEMP_DIR/$file" ]; then
        log "[通过] 文件存在: $file"
    else
        log "[失败] 文件缺失: $file"
        exit 1
    fi
done

# 4. 验证数据完整性（抽样检查）
RECORD_COUNT=$(wc -l < "$TEMP_DIR/database.sql")
log "数据库备份记录数: $RECORD_COUNT"
if [ "$RECORD_COUNT" -lt 100 ]; then
    log "[警告] 记录数异常少，可能备份不完整"
fi

# 5. 清理
rm -rf "$TEMP_DIR"
log "备份验证完成，所有检查通过"
exit 0
```

## 四、容灾技术

### 4.1 容灾模式对比

| 模式 | 原理 | RTO | RPO | 成本 | 适用场景 |
|------|------|-----|-----|------|----------|
| 热备 | 主备同时运行，备机实时同步 | 秒级 | 秒级 | 高 | 关键业务系统 |
| 温备 | 备机就绪但不处理业务，定期同步 | 分钟级 | 小时级 | 中 | 重要业务系统 |
| 冷备 | 备机离线，需手动启动恢复 | 小时~天 | 天级 | 低 | 非关键系统 |
| 双活 | 双中心同时运行，互为备份 | 零 | 零 | 最高 | 核心业务系统 |

### 4.2 双活数据中心

```
双活数据中心架构:

              ┌─────────────────┐
              │   全局负载均衡    │
              │  (GSLB / DNS)   │
              └────────┬────────┘
                       │
           ┌───────────┴───────────┐
           │                       │
    ┌──────▼──────┐          ┌──────▼──────┐
    │  数据中心 A  │◄────────►│  数据中心 B  │
    │  (北京)     │  专线    │  (上海)     │
    │             │  DWDM    │             │
    │ ┌─────────┐ │  10G/    │ ┌─────────┐ │
    │ │ 应用集群  │ │ 100G    │ │ 应用集群  │ │
    │ ├─────────┤ │          │ ├─────────┤ │
    │ │ 数据库   │◄┼─────────┼►│ 数据库   │ │
    │ │ (主/备)   │ │ Data    │ │(备/主)   │ │
    │ └─────────┘ │ Guard    │ └─────────┘ │
    └─────────────┘          └─────────────┘

双活核心要求:
├── 网络层: 低延迟专线（<2ms RTT）
├── 存储层: 存储虚拟化/双活存储
├── 数据库层: 数据同步（Oracle Data Guard/MySQL Group Replication）
├── 应用层: 无状态设计/会话共享
└── 流量层: 全局DNS负载均衡 + 健康检查
```

### 4.3 两地三中心架构

```
两地三中心架构:

         ┌─────────────────────────────┐
         │      同城双活中心          │
         │  ┌─────────┐  ┌─────────┐  │
         │  │ 中心A    │  │ 中心B    │  │
         │  │ (生产)  │◄─►│ (同城备)│  │
         │  │         │同│         │  │
         │  │         │城│         │  │
         │  │         │专│         │  │
         │  │         │线│         │  │
         │  └─────────┘  └────┬────┘  │
         └────────────────────┼──────┘
                              │
                      异地专线 (≥1000km)
                              │
         ┌────────────────────┼──────┐
         │              ┌─────▼────┐│
         │              │  中心C   ││
         │              │ (异地灾) ││
         │              │  备中心  ││
         │              └─────────┘│
         └────────────────────────┘

设计要点:
├── 中心A: 主生产中心
├── 中心B: 同城备份（RPO≈0，RTO≈分钟级）
├── 中心C: 异地灾备（RPO<小时级，RTO<小时级）
├── A→B: 同步复制（数据零丢失）
├── A/B→C: 异步复制（允许少量数据丢失）
└── 故障切换: A故障切B，A+B同时故障切C
```

## 五、灾难恢复计划（DRP）

### 5.1 DRP 核心要素

```
灾难恢复计划框架:

1. 组织与职责
   ├── DRP 负责人（CIO/CISO）
   ├── 应急响应团队
   ├── 技术恢复团队
   ├── 业务恢复团队
   └── 通讯协调团队

2. 风险评估
   ├── 识别可能灾难场景
   │   ├── 自然灾害（地震/洪水/火灾）
   │   ├── 技术故障（硬件/软件/网络）
   │   ├── 人为因素（误操作/恶意攻击）
   │   └── 供应链中断
   ├── 评估影响程度
   └── 确定优先恢复系统

3. 恢复策略
   ├── 按系统优先级分级
   │   ├── P0: 核心系统（立即恢复）
   │   ├── P1: 关键系统（4小时内恢复）
   │   ├── P2: 重要系统（24小时内恢复）
   │   └── P3: 一般系统（72小时内恢复）
   ├── 恢复方式选择
   └── 备用方案（降级运行）

4. 应急流程
   ├── 灾难判定标准
   ├── 启动 DRP 的决策流程
   ├── 恢复操作步骤
   └── 恢复后验证流程

5. 通讯计划
   ├── 内部通讯模板
   ├── 外部通报（监管/客户/媒体）
   └── 通讯录与备用联系方式

6. 演练与维护
   ├── 定期演练计划
   ├── DRP 文档更新机制
   └── 演练结果改进
```

### 5.2 DRP 文档模板

```markdown

## 1. 文档信息
- 版本: v2.0
- 生效日期: 2026-09-01
- 下次审查: 2027-03-01
- 批准人: CIO

## 2. 系统优先级与恢复目标
```

## 六、RPO/RTO 指标与 BIA

### 6.1 核心指标定义

```
RPO (Recovery Point Objective) - 恢复点目标
├── 定义: 灾难发生后可容忍的数据丢失量
├── RPO=0: 不允许任何数据丢失（同步复制）
├── RPO=15min: 可容忍15分钟数据丢失
└── 衡量维度: 时间

RTO (Recovery Time Objective) - 恢复时间目标
├── 定义: 灾难发生后系统恢复运行的最大时间
├── RTO=0: 零停机（双活/HA集群）
├── RTO=4h: 4小时内恢复
└── 衡量维度: 时间

      数据丢失量(RPO)    恢复时间(RTO)
      ←──────────→    ←──────────────────→
      
  灾难发生        数据恢复点         业务恢复
  ─────●─────────────│──────────────────●──────
       │     丢失的数据    │     恢复过程时间     │
       │                 │                      │
       └─── RPO ─────────┘                      │
                         └──── RTO ─────────────┘

其他指标:
├── MTD (Maximum Tolerable Downtime): 最大容忍停机时间
│   └── 通常 MTD > RTO（RTO后还需验证才能恢复业务）
├── WRT (Work Recovery Time): 工作恢复时间
│   └── 系统恢复后验证和配置的时间
└── MTBF (Mean Time Between Failures): 平均故障间隔时间
```

```python
# 云备份安全配置示例 (AWS)

import boto3
from botocore.exceptions import ClientError

s3 = boto3.client('s3')
kms = boto3.client('kms')
bucket = 'enterprise-backup-prod'

# 1. 创建专用 KMS 密钥（备份加密）
kms_key = kms.create_key(
    Description='Backup encryption key',
    KeyUsage='ENCRYPT_DECRYPT',
    Origin='AWS_KMS',
    Tags=[{'TagKey': 'Purpose', 'TagValue': 'Backup'}]
)
kms_key_id = kms_key['KeyMetadata']['KeyId']

# 2. 配置存储桶默认加密
s3.put_bucket_encryption(
    Bucket=bucket,
    ServerSideEncryptionConfiguration={
        'Rules': [{
            'ApplyServerSideEncryptionByDefault': {
                'SSEAlgorithm': 'aws:kms',
                'KMSMasterKeyID': kms_key_id
            },
            'BucketKeyEnabled': True  # 使用存储桶密钥降低KMS成本
        }]
    }
)

# 3. 启用版本控制（防覆盖删除）
s3.put_bucket_versioning(
    Bucket=bucket,
    VersioningConfiguration={'Status': 'Enabled'}
)

# 4. 启用 MFA 删除保护
s3.put_bucket_versioning(
    Bucket=bucket,
    VersioningConfiguration={
        'Status': 'Enabled',
        'MFADelete': 'Enabled'  # 删除需MFA认证
    }
)

# 5. 配置对象锁定策略
s3.put_object_lock_configuration(
    Bucket=bucket,
    ObjectLockConfiguration={
        'ObjectLockEnabled': 'Enabled',
        'Rule': {
            'DefaultRetention': {
                'Mode': 'COMPLIANCE',
                'Days': 365  # 默认保留365天
            }
        }
    }
)

# 6. 限制公共访问
s3.put_public_access_block(
    Bucket=bucket,
    PublicAccessBlockConfiguration={
        'BlockPublicAcls': True,
        'BlockPublicPolicy': True,
        'IgnorePublicAcls': True,
        'RestrictPublicBuckets': True
    }
)

# 7. 配置跨区域复制（异地容灾）
repl_bucket = 'enterprise-backup-dr'
s3.put_bucket_replication(
    Bucket=bucket,
    ReplicationConfiguration={
        'Role': 'arn:aws:iam::123456789:role/replication-role',
        'Rules': [{
            'Status': 'Enabled',
            'Priority': 100,
            'Filter': {'Prefix': ''},
            'Destination': {
                'Bucket': f'arn:aws:s3:::{repl_bucket}',
                'StorageClass': 'STANDARD_IA'
            }
        }]
    }
)

# 8. 配置生命周期策略（自动降级和归档）
s3.put_bucket_lifecycle_configuration(
    Bucket=bucket,
    LifecycleConfiguration={
        'Rules': [{
            'Status': 'Enabled',
            'Transitions': [
                {'Days': 30, 'StorageClass': 'STANDARD_IA'},   # 30天后转低频
                {'Days': 90, 'StorageClass': 'GLACIER_IR'},   # 90天后转冰川
                {'Days': 365, 'StorageClass': 'DEEP_ARCHIVE'} # 1年后转深度归档
            ],
            'NoncurrentVersionTransitions': [  # 非当前版本
                {'NoncurrentDays': 30, 'StorageClass': 'STANDARD_IA'},
                {'NoncurrentDays': 90, 'StorageClass': 'GLACIER'}
            ],
            'NoncurrentVersionExpiration': {
                'NoncurrentDays': 180  # 旧版本180天后自动删除
            }
        }]
    }
)
```

### 8.2 恢复演练脚本

```bash
#!/bin/bash
# 备份恢复演练脚本

set -e  # 任何错误立即退出

# ===== 演练配置 =====
BACKUP_FILE="/backups/prod_20260911_full.dump"
BACKUP_HASH="/backups/prod_20260911_full.dump.sha256"
RESTORE_HOST="dr-test-db.internal"
RESTORE_DB="restore_test"
LOG_FILE="/var/log/restore_drill_$(date +%Y%m%d_%H%M%S).log"

# ===== 日志函数 =====
log() {
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] $1" | tee -a "$LOG_FILE"
}

START_TIME=$(date +%s)
log "======== 备份恢复演练开始 ========"
log "备份文件: $BACKUP_FILE"
log "恢复目标: $RESTORE_HOST:$RESTORE_DB"

# ===== 步骤1: 备份文件完整性验证 =====
log "[步骤1] 验证备份文件完整性"
if [ ! -f "$BACKUP_FILE" ]; then
    log "[失败] 备份文件不存在"
    exit 1
fi

EXPECTED_HASH=$(cat "$BACKUP_HASH" | awk '{print $1}')
ACTUAL_HASH=$(sha256sum "$BACKUP_FILE" | awk '{print $1}')

if [ "$EXPECTED_HASH" = "$ACTUAL_HASH" ]; then
    log "[通过] 哈希校验一致"
else
    log "[失败] 哈希不匹配，备份文件可能被篡改"
    exit 1
fi

# ===== 步骤2: 解密备份 =====
log "[步骤2] 解密备份文件"
DECRYPT_TIME_START=$(date +%s%N)
openssl enc -d -aes-256-cbc -in "$BACKUP_FILE" \
    -pass file:/etc/backup/key \
    -out /tmp/restore_temp.sql
DECRYPT_TIME_END=$(date +%s%N)
DECRYPT_DURATION=$(( (DECRYPT_TIME_END - DECRYPT_TIME_START) / 1000000 ))
log "解密完成，耗时: ${DECRYPT_DURATION}ms"

# ===== 步骤3: 数据库恢复 =====
log "[步骤3] 恢复数据库到测试环境"

# 创建测试数据库
PGPASSWORD=dr_test_pass psql -h "$RESTORE_HOST" -U dr_admin \
    -c "DROP DATABASE IF EXISTS $RESTORE_DB;" 2>/dev/null
PGPASSWORD=dr_test_pass psql -h "$RESTORE_HOST" -U dr_admin \
    -c "CREATE DATABASE $RESTORE_DB;" 2>/dev/null

# 恢复数据
RESTORE_TIME_START=$(date +%s)
PGPASSWORD=dr_test_pass psql -h "$RESTORE_HOST" -U dr_admin \
    -d "$RESTORE_DB" -f /tmp/restore_temp.sql >> "$LOG_FILE" 2>&1
RESTORE_TIME_END=$(date +%s)
RESTORE_DURATION=$(( RESTORE_TIME_END - RESTORE_TIME_START ))
log "数据库恢复完成，耗时: ${RESTORE_DURATION}s"

# ===== 步骤4: 数据验证 =====
log "[步骤4] 验证恢复数据完整性"

# 检查表数量
TABLE_COUNT=$(PGPASSWORD=dr_test_pass psql -h "$RESTORE_HOST" -U dr_admin \
    -d "$RESTORE_DB" -t -c \
    "SELECT count(*) FROM information_schema.tables WHERE table_schema='public';")
log "恢复表数量: $TABLE_COUNT"

# 检查关键表记录数
for table in users orders products; do
    COUNT=$(PGPASSWORD=dr_test_pass psql -h "$RESTORE_HOST" -U dr_admin \
        -d "$RESTORE_DB" -t -c "SELECT count(*) FROM $table;")
    log "  表 $table: $COUNT 条记录"
    
    # 与生产数据对比（通过API获取生产计数）
    PROD_COUNT=$(curl -s -H "Authorization: Bearer $API_TOKEN" \
        "https://api.prod.internal/stats/$table/count")
    
    if [ "$COUNT" = "$PROD_COUNT" ]; then
        log "  [通过] 记录数一致"
    else
        log "  [警告] 记录数不一致！生产: $PROD_COUNT 恢复: $COUNT"
    fi
done

# ===== 步骤5: 应用功能验证 =====
log "[步骤5] 应用功能验证"

# 启动测试应用连接恢复的数据库
export DATABASE_URL="postgresql://dr_admin:dr_test_pass@$RESTORE_HOST/$RESTORE_DB"

# 基本功能测试
log "测试用户登录..."
LOGIN_TEST=$(curl -s -X POST http://test-app:8080/api/auth/login \
    -H "Content-Type: application/json" \
    -d '{"username":"test_user","password":"test_pass"}' | \
    jq -r '.status // "failed"')

if [ "$LOGIN_TEST" = "success" ]; then
    log "  [通过] 登录测试成功"
else
    log "  [失败] 登录测试失败"
fi

# ===== 步骤6: 清理 =====
log "[步骤6] 清理测试环境"
rm -f /tmp/restore_temp.sql
PGPASSWORD=dr_test_pass psql -h "$RESTORE_HOST" -U dr_admin \
    -c "DROP DATABASE $RESTORE_DB;" 2>/dev/null
log "清理完成"

# ===== 演练总结 =====
END_TIME=$(date +%s)
TOTAL_DURATION=$(( END_TIME - START_TIME ))
log "======== 演练总结 ========"
log "总耗时: ${TOTAL_DURATION}s"
log "恢复RTO实测: ${RESTORE_DURATION}s"
log "目标RTO: 900s (15分钟)"
if [ "$RESTORE_DURATION" -le 900 ]; then
    log "RTO达标: [通过]"
else
    log "RTO超标: [未达标] 需优化恢复方案"
fi
log "演练结果: 成功完成"
```
