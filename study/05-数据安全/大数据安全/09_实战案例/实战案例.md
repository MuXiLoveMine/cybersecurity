# 实战案例

### 案例1：Hadoop 集群安全加固实战

**背景：** 某公司 Hadoop 集群长期"裸奔"（simple 模式），300+ 节点，存储 PB 级业务数据。审计要求一年内完成安全加固。

**加固过程：**

1. **资产盘点：** 用脚本扫描集群所有组件版本，识别 CVE。发现 Hadoop 2.7（多个高危 CVE）、Hive 未启用授权。

```bash
# 全集群组件版本扫描
for node in $(cat nodes.txt); do
  ssh $node "hadoop version; hive --version; hbase version" 
done > versions.txt
```

2. **升级组件：** Hadoop 2.7 → 3.3，修复已知 CVE。灰度升级（先边缘节点，再核心）。

3. **启用 Kerberos：** 部署 KDC，为每个服务生成 principal 与 keytab。难点是数百节点的 `_HOST` 必须正确——逐台检查 `hostname -f` 返回 FQDN，修正 DNS。

4. **配置 Hadoop 安全：** 推送 core-site.xml/hdfs-site.xml，重启 NameNode/DataNode。第一次启动失败——发现部分 DataNode 时间差超 5 分钟，强制 NTP 同步后恢复。

5. **部署 Ranger：** 集中管理授权策略。把原有 HDFS POSIX 权限梳理成 Ranger 策略，按业务线分库分目录授权，敏感目录加列级脱敏。

6. **启用加密：** 敏感数据目录建加密区，KMS 用独立密钥管理服务。审计发现 KMS 密钥原本存在 NameNode 内存，改为独立 KMS + HSM 根密钥。

7. **审计与监控：** 把 HDFS/Hive/Ranger/KDC 日志汇入 ELK，建异常查询告警规则。

**成果：** 通过等保三级测评，"内网默认信任"风险消除。沉淀了 Kerberos 部署 SOP、Ranger 策略模板、加固检查清单。

### 案例2：Kerberos 部署排错全过程

**背景：** 新上线 Hadoop 启用 Kerberos 后，用户 `kinit` 成功但执行 `hadoop fs -ls /` 报错 `GSSException: No valid credentials provided`。

**排错过程：**

1. **初步定位：** `klist` 看到 TGT 正常，但 NameNode 日志报 `Key version number for principal hdfs/namenode in keytab incorrect`。

2. **比对 KVNO：**

```bash
klist -kt /etc/security/keytabs/hdfs.keytab
# keytab: hdfs/namenode.hadoop.com@BIGDATA.COM KVNO=3

kadmin.local -q "getprinc hdfs/namenode.hadoop.com"
# principal: hdfs/namenode.hadoop.com@BIGDATA.COM
# Key: vno 4, aes256...
# KVNO不一致! keytab是3, KDC是4
```

原因：曾用 `ktadd` 重新生成过 keytab，但旧 keytab 没及时分发。解决：重新 `ktadd -k` 并分发。

3. **二次报错：** 修完 KVNO 后，又报 `Server not found in Kerberos database (7)`。客户端 principal 是 `hdfs/namenode.hadoop.com`，但实际 DNS 解析的 hostname 不一致。

```bash
hostname -f   # 返回 namenode (短名, 不带域)
# 而principal是 hdfs/namenode.hadoop.com
```

解决：设置 `/etc/hosts` 把 FQDN 与 IP 对应，并设置 hostname 为 FQDN：

```bash
hostnamectl set-hostname namenode.hadoop.com
# /etc/hosts:
# 10.0.0.1 namenode.hadoop.com namenode
```

4. **三次报错：** 修完 hostname 后，DataNode 起不来，报 `Clock skew too great`。

```bash
date   # 对比namenode和datanode时间, 差6分钟
# Kerberos默认允许5分钟时差
```

解决：所有节点装 chrony 并强制同步。

```bash
systemctl enable chronyd
chronyc makestep
```

5. **最终验证：** `kinit alice && hadoop fs -ls /` 成功。把排错经验沉淀为检查清单：FQDN 一致性、KVNO 一致性、时钟同步、keytab 权限、DNS 反向解析。

### 案例3：大数据平台数据泄露事件响应

**背景：** 审计发现某分析团队离职员工疑似在离职前批量拉取了客户敏感数据。

**响应过程：**

1. **遏制：** 立即用 kadmin 冻结该账号 TGT（`cpw -randkey` 使旧票据失效），同时撤销其 Ranger 权限策略。

2. **取证 - 审计关联：** 拉取该用户最后 30 天的所有审计日志（HDFS audit、Hive audit、Ranger audit）。

```bash
# 从ELK导出该用户的操作记录
# Elasticsearch查询: user.keyword: "li.ming"
# 时间: 离职前30天
# 结果: 发现离职前3天大量SELECT customers WHERE region=...
```

3. **分析 - 链路还原：** 审计日志显示该用户离职前 3 天通过 Hive 执行了 23 次 SELECT 查询，每次查不同 region 的客户表，合计拉取约 50 万条客户记录（含手机号、身份证）。每次查询后都伴随 `hadoop fs -getmerge` 把结果导出为本地文件。

4. **量化定损：** 根据查询记录统计：
   - 涉及表：customers（敏感）
   - 字段：手机号、身份证号、地址（PII）
   - 记录数：约 50 万条
   - 被拉取数据的客户分布：东、南、西三个大区
   - 是否外传：审计显示文件被写到本地，需结合该工作站 EDR 进一步看是否上传到外部存储

5. **处置：**
   - 联系该员工配合调查，要求删除已导出数据
   - 评估是否构成"重要数据/个人信息泄露"，按数据安全法评估是否需上报监管
   - 修复控制缺陷：敏感表查询加 Ranger 行级过滤（限定只能查自己负责 region）、批量导出操作增加审批流、离职流程增加数据访问审查节点

6. **改进：** 增设"敏感数据批量查询告警"规则——单用户单日 SELECT 敏感表记录数超阈值即告警 SOC。

**结论：** 该事件暴露了"权限虽在但无行为监控"的盲区。光有 Ranger 授权不够，必须配合行为审计才能发现异常批量访问。
