## 一、大数据安全概述

### 1.1 大数据 5V 特征

大数据的"5V"模型定义了其与传统数据处理的本质差异，这些差异也直接决定了安全防护的难点。

| 特征 | 含义 | 安全影响 |
|------|------|----------|
| Volume（体量大） | PB 至 EB 级数据 | 全量加密/扫描成本极高；备份恢复窗口长 |
| Velocity（速度快） | 流式实时处理，毫秒级 | 安全策略需在高速流中实时生效，延迟敏感 |
| Variety（种类多） | 结构化、半结构化、非结构化混杂 | 分类分级困难；不同数据类型需不同保护 |
| Veracity（真实性） | 数据质量参差，有噪声 | 脏数据可能触发错误决策，需数据完整性校验 |
| Value（价值密度低） | 海量数据中价值集中 | 单条数据价值低易被忽视，但聚合后价值巨大且敏感 |

体量大意味着传统"加密整个数据库"的思路在大数据上性能不可接受；速度快意味着安全检查不能成为流处理瓶颈；种类多意味着无法用统一策略覆盖所有数据。这正是大数据安全的根本挑战。

### 1.2 大数据安全挑战与威胁模型

**核心挑战：**

1. **分布式攻击面扩大：** Hadoop/Spark 集群动辄数百节点，每个节点都是潜在入口。一个节点被攻破就可能横向扩散到整个集群。
2. **多租户隔离困难：** 同一集群承载多个业务/部门的数据，租户间隔离既是性能问题也是安全问题。
3. **明文协议默认：** Hadoop 早期设计假设内网可信，RPC、Web UI、数据传输默认明文，未启用安全时裸奔。
4. **权限粒度粗放：** 原生 HDFS 权限只有类 UNIX 的 rwx，无法做列级、行级、单元格级控制，难以满足最小权限。
5. **审计能力薄弱：** 原生日志分散在各节点，缺乏统一审计视图，事后追溯困难。

**威胁模型（STRIDE 映射）：**

```
Spoofing(仿冒):    伪造身份直连 HDFS/数据库窃取数据
Tampering(篡改):   篡改 MR/Spark 任务结果, 篡改数据文件
Repudiation(抵赖):  操作无审计, 无法追责
Info Disclosure:   明文传输被嗅探, 未授权读取敏感数据
DoS(拒绝服务):     提交恶意任务耗尽集群资源
Elevation(提权):   普通用户利用漏洞获取管理员权限
```

典型攻击场景：攻击者拿到一台边缘节点（如离线分析跳板）的 shell，由于 Hadoop 未启用 Kerberos，可直接用 `hadoop fs` 命令以任意用户身份访问 HDFS，进而遍历整个数据湖窃取数据。这就是"内网默认信任"的代价。

### 1.3 大数据安全框架与标准

**分层防护框架：**

```
┌─────────────────────────────────────────────┐
│ 应用层: 数据分类分级、脱敏API、访问审计       │
├─────────────────────────────────────────────┤
│ 平台层: Ranger统一授权、Kerberos认证、SSL传输 │
├─────────────────────────────────────────────┤
│ 存储层: HDFS权限、透明加密、审计日志          │
├─────────────────────────────────────────────┤
│ 网络层: 网络隔离、防火墙、东西向加密          │
├─────────────────────────────────────────────┤
│ 物理层: 机房、硬件HSM、可信计算              │
└─────────────────────────────────────────────┘
```

**相关标准：**
- NIST SP 800-122：个人身份信息（PII）保护指南
- GB/T 35273：个人信息安全规范（国内）
- 数据安全法、个人信息保护法（PIPL）：国内法律红线
- GDPR：欧盟数据保护，跨境业务适用

大数据安全的核心原则：**认证到人、授权到列、传输加密、存储加密、操作留痕、数据分级**。

## 二、Hadoop 安全

### 2.1 Hadoop 安全架构

Hadoop 安全体系围绕"Kerberos 认证 + ACL 授权 + 审计"三要素构建。未启用安全前，Hadoop 处于"simple"模式，客户端声称自己是任何用户都能被接受，极度危险。

**认证：Kerberos**

用户访问 Hadoop 任何服务前，必须先获取 Kerberos 票据。Kerberos 为每个用户/服务颁发 TGT，服务间通信也通过票据互验，确保"你说的就是你"。

```
Hadoop Kerberos 认证流程:

  用户 → KDC: AS-REQ (用户身份)
  KDC → 用户: TGT (用用户密钥加密)
  用户 → HDFS NameNode: TGT + Service Ticket
  NameNode 验证票据 → 授权访问
```

**授权：ACL**

HDFS 有原生 POSIX-like 权限（owner/group/other 的 rwx），HBase 有 ACL 表。但更细粒度的列级/行级控制需要 Ranger。

**传输加密：**

Hadoop RPC 与数据传输支持 SASL + 加密（AES/3DES），Web UI 支持 SSL。

### 2.2 HDFS 安全

**1. 权限控制：**

```bash
# HDFS POSIX权限
hadoop fs -chmod 750 /user/finance/sensitive
hadoop fs -chown finance:finance /user/finance/sensitive

# 启用ACL（更细粒度）
hadoop fs -setfacl -m user:analyst:rw- /user/finance/reports
hadoop fs -getfacl /user/finance/reports

# 设置sticky位防删除
hadoop fs -chmod 1777 /tmp
```

HDFS ACL 扩展了 POSIX 模型，允许给特定用户/组单独授权，但仍无法做"列级"控制，需 Ranger。

**2. 透明加密（TDE）：**

HDFS 透明加密区（Encryption Zone）在数据写入时自动加密、读取时自动解密，对应用透明。

```bash
# 创建密钥（需KMS服务）
hadoop key create myKey

# 创建加密区
hadoop fs -mkdir /user/secure
hdfs crypto -createZone -keyName myKey -path /user/secure

# 之后写入的数据自动加密
hadoop fs -put sensitive.csv /user/secure/
```

加密区原理：每个加密区有独立的 Data Encryption Key（DEK），DEK 用 Key Encryption Key（KEK）加密后存于 KMS。文件块加密用 EDEK，密钥不在 NameNode 明文存储。

**3. 审计日志：**

```xml
<!-- hdfs-site.xml 启用审计 -->
<property>
  <name>dfs.namenode.audit.log.enabled</name>
  <value>true</value>
</property>
<property>
  <name>dfs.namenode.audit.log.location</name>
  <value>/var/log/hadoop/audit/hdfs-audit.log</value>
</property>
```

审计日志记录每次文件操作（谁、何时、做了什么、成功/失败），是事后追溯的关键。

### 2.3 Hadoop Ranger 统一授权管理

Ranger 提供集中化的策略管理，支持 HDFS/Hive/HBase/Kafka 等组件，可做列级、行级（Hive 行级过滤器）控制。

```json
// Ranger HDFS 策略示例
{
  "policyName": "finance_data_access",
  "resourceName": "/user/finance/*",
  "permissions": [
    {"principal": "finance_group", "access": ["read","execute"], "allow": true},
    {"principal": "auditor", "access": ["read"], "allow": true}
  ]
}
```

Ranger 还提供审计中心，把各组件审计日志汇总，形成"谁访问了什么"的统一视图。

### 2.4 Hadoop 安全配置最佳实践

```xml
<!-- core-site.xml -->
<property>
  <name>hadoop.security.authentication</name>
  <value>kerberos</value>
</property>
<property>
  <name>hadoop.security.authorization</name>
  <value>true</value>
</property>

<!-- hdfs-site.xml -->
<property>
  <name>dfs.encrypt.data.transfer</name>
  <value>true</value>
</property>
<property>
  <name>dfs.data.transfer.protection</name>
  <value>authentication,integrity,privacy</value>
</property>
<property>
  <name>dfs.namenode.audit.log.enabled</name>
  <value>true</value>
</property>
```

```bash
# 关键加固清单
1. 启用 Kerberos (hadoop.security.authentication=kerberos)
2. 启用授权 (hadoop.security.authorization=true)
3. 启用 RPC 加密 (dfs.encrypt.data.transfer=true)
4. 启用审计日志
5. 部署 Ranger 做细粒度授权
6. Web UI 启用 SSL + 认证
7. 敏感数据目录设加密区
8. 禁用匿名访问、默认账户改密
9. 节点间防火墙限制 RPC 端口
10. 定期巡检审计日志
```

## 三、Spark 安全

### 3.1 Spark 安全架构

Spark 安全包含认证、授权、加密三部分。认证确保用户/服务身份；授权控制谁能否提交/查看任务；加密保护 RPC 与数据传输。

```
Spark 安全组件:

认证层: Spark 认证(SASL/Kerberos) + UI认证
授权层: Spark ACL (查看/修改权限)
加密层: RPC加密(SASL) + 数据传输SSL
存储层: 与HDFS/HBase加密联动
```

### 3.2 Spark RPC 安全配置

Spark 内部 RPC（driver-executor、executor-executor）默认明文。启用 SASL 加密。

```bash
# spark-defaults.conf
spark.authenticate true
spark.authenticate.secret MySecretKey        # 共享密钥(非Kerberos模式)

# 或使用Kerberos
spark.kerberos.principal spark/_HOST@REALM
spark.kerberos.keytab /etc/security/keytabs/spark.keytab
spark.kerberos.access.hadoopFileSystems hdfs://namenode:8020
```

`spark.authenticate=true` 启用后，所有 RPC 通信需验证，防止恶意节点加入集群。

### 3.3 Spark 数据加密（SSL/TLS）

```bash
# spark-defaults.conf
spark.ssl.enabled true
spark.ssl.keyStore /etc/spark/keystore.jks
spark.ssl.keyStorePassword changeit
spark.ssl.keyPassword changeit
spark.ssl.trustStore /etc/spark/truststore.jks
spark.ssl.trustStorePassword changeit

# 启用后, UI和文件服务器都走HTTPS
spark.ui.https.enabled true
```

生成密钥库：

```bash
keytool -genkeypair -alias spark -keyalg RSA -keysize 2048 \
  -keystore /etc/spark/keystore.jks -validity 3650 \
  -dname "CN=spark-host, OU=bigdata, O=company, C=CN"
```

### 3.4 Spark on Kubernetes 安全

Spark on K8s 是现代趋势。安全要点：

```yaml
# Spark-submit 参数示例
spark.kubernetes.namespace = analytics           # 隔离命名空间
spark.kubernetes.authenticate.driverServiceAccountName = spark-sa  # SA
spark.kubernetes.driver.secrets=spark-secret    # 挂载密钥(Kerberos keytab)
spark.kubernetes.executor.secrets=spark-secret
spark.kubernetes.driver.podTemplateFile=/path/template.yaml
```

关键安全措施：
1. **RBAC：** Spark ServiceAccount 只授予最小权限，禁止 list/create pods 全集群权限。
2. **NetworkPolicy：** 限制 driver/executor 只能访问指定数据源。
3. **镜像安全：** 用私有镜像仓库 + 镜像签名校验，禁止拉取任意镜像。
4. **Secret 管理：** Kerberos keytab、数据库密码用 K8s Secret 或 Vault 注入，不硬编码。
5. **Pod Security：** 启用 PodSecurityPolicy/PodSecurity admission，禁止 privileged 容器。

## 四、Kafka 安全

### 4.1 Kafka 安全机制

Kafka 安全三件套：**SASL 认证 + SSL 加密 + ACL 授权**。

```
Kafka 安全栈:

客户端
  ├── SASL认证 (PLAIN/SCRAM/GSSAPI(Kerberos)/OAUTHBEARER)
  ├── SSL加密 (mTLS双向认证 或 单向+SASL)
  └── ACL授权 (topic/group/cluster级权限)
Broker
  ├── 监听器隔离 (INTERNAL/EXTERNAL分端口)
  ├── SSL/TLS
  └── 审计日志
```

**认证机制对比：**

| 机制 | 说明 | 适用 |
|------|------|------|
| SASL/PLAIN | 用户名密码（明文传输，需配SSL） | 内网简单场景 |
| SASL/SCRAM | 用户名密码+挑战（密码不在broker存明文） | 推荐，无Kerberos |
| SASL/GSSAPI | Kerberos | 大企业、与Hadoop统一 |
| SSL mTLS | 双向证书认证 | 高安全要求 |
| OAUTHBEARER | OAuth2令牌 | 云原生、多租户 |

### 4.2 Kafka 安全配置实战

**1. 启用 SSL + SASL/SCRAM：**

```bash
# 创建SCRAM用户
kafka-configs.sh --zookeeper zoo1:2181 --alter \
  --add-config 'SCRAM-SHA-256=[password=mysecret]' \
  --entity-type users --entity-name alice

# broker配置 server.properties
listeners=INTERNAL://broker1:9092,EXTERNAL://broker1:9094
advertised.listeners=EXTERNAL://broker1:9094
listener.security.protocol.map=INTERNAL:SASL_SSL,EXTERNAL:SASL_SSL
sasl.enabled.mechanisms=SCRAM-SHA-256
sasl.mechanism.inter.broker.protocol=SCRAM-SHA-256

# SSL配置
ssl.keystore.location=/etc/kafka/keystore.jks
ssl.keystore.password=changeit
ssl.truststore.location=/etc/kafka/truststore.jks
ssl.truststore.password=changeit
ssl.client.auth=required                    # 强制客户端证书
```

**2. 客户端 JAAS 配置：**

```bash
# 客inaaas.conf
KafkaClient {
  org.apache.kafka.common.security.scram.ScramLoginModule required
  username="alice"
  password="mysecret";
};

# client配置
security.protocol=SASL_SSL
sasl.mechanism=SCRAM-SHA-256
ssl.truststore.location=/etc/kafka/client.truststore.jks
ssl.truststore.password=changeit
```

**3. ACL 授权：**

```bash
# 授权alice对topic 'transactions'的读写
kafka-acls.sh --authorizer-properties \
  zookeeper.connect=zoo1:2181 \
  --add --allow-principal User:alice \
  --operation Read --operation Write \
  --topic transactions

# 授权消费组
kafka-acls.sh --add --allow-principal User:alice \
  --operation Read --group analytics-consumer

# 拒绝某用户(显式Deny优先)
kafka-acls.sh --add --deny-principal User:bob \
  --operation Write --topic sensitive
```

### 4.3 Kafka 安全监控与审计

```bash
# 启用审计日志(authorizer logger)
# log4j.properties
log4j.logger.kafka.authorizer.logger=INFO, authorizerAppender

# 审计日志会记录每次ACL判定: 允许/拒绝、用户、操作、资源
# 查看权限
kafka-acls.sh --list --principal User:alice

# 监控未授权访问告警(日志中Deny)
grep "DENIED" /var/log/kafka/authorizer.log
```

监控指标：
- 认证失败次数突增 → 暴力破解或证书过期
- DENIED 频繁 → 可能有越权尝试
- TLS 握手失败率 → 客户端配置错误或攻击

## 五、大数据平台权限管理

### 5.1 Apache Ranger 架构与部署

Ranger 是 Hadoop 生态最主流的统一权限管理平台。

```
Ranger 架构:

┌────────────────────────────────────────┐
│  Ranger Admin (Web UI + 策略中心)      │
│  ┌──────────┐ ┌──────────┐            │
│  │ 策略存储  │ │ 审计存储  │ (DB)       │
│  └──────────┘ └──────────┘            │
└──────────────┬─────────────────────────┘
               │ 策略下发
   ┌───────────┼───────────┐
   ↓           ↓           ↓
┌──────┐  ┌──────┐    ┌──────┐
│HDFS  │  │ Hive │    │Kafka │  (各组件的Plugin)
│Plugin│  │Plugin│    │Plugin│
└──────┘  └──────┘    └──────┘
   ↓           ↓           ↓
  HDFS       Hive       Kafka (各组件实际执行鉴权)
```

部署步骤：

```bash
# 1. 准备DB
mysql -e "CREATE DATABASE ranger; CREATE USER 'ranger'@'%' IDENTIFIED BY 'pass'; GRANT ALL ON ranger.* TO 'ranger'@'%';"

# 2. 解压并配置
cd ranger-admin
# 修改 install.properties
db_root_password=pass
db_host=localhost
rangerAdmin_password=Ranger123

# 3. 安装
./setup.sh

# 4. 启动
./ranger-admin start

# 5. 安装各组件Plugin (以HDFS为例)
cd hdfs-plugin
# 修改 install.properties 指向Admin
./enable-hdfs-plugin.sh
# 重启NameNode生效
```

### 5.2 Ranger 策略管理

**1. HDFS 策略：** 路径级别权限，可指定用户/组/IP 范围。

**2. Hive 策略：** 库/表/列级别，支持行级过滤（Row Filter）和列脱敏（Masking）。

```json
// Hive 策略示例: 列级授权 + 行级过滤
{
  "policyName": "customer_pii_access",
  "resource": {"database": "sales", "table": "customers", "columns": ["phone","idcard"]},
  "permissions": [
    {"principal": "analyst", "access": ["select"], "masking": "MASK_SHOW_LAST_4"},
    {"principal": "finance_admin", "access": ["select"], "rowFilter": "region='east'"}
  ]
}
```

**3. Kafka 策略：** Topic/Group/Cluster 级，控制 Produce/Consume/Describe。

**4. Spark 策略：** 通过 Ranger Spark Plugin 控制 SQL 查询权限（SparkSQL 接入 Ranger）。

Ranger 的审计中心统一展示所有组件的访问记录，是事后追溯与合规审计的核心。

### 5.3 Apache Sentry（历史参考）

Sentry 是 Cloudera 推出的基于角色的授权（RBAC），曾是 Hadoop 授权主流之一。优势是"基于角色"简化授权管理，劣势是只支持 Hive/Impala，组件覆盖少，社区已不活跃，被 Ranger 取代。了解原理即可，新部署不建议选 Sentry。

### 5.4 统一审计日志管理

大数据平台日志分散（HDFS audit、Hive audit、Kafka authorizer、Ranger audit）。统一审计方案：

```
各组件审计日志 → Filebeat/Flume → Kafka → Logstash → Elasticsearch → Kibana
```

关键能力：
- 统一时间线：把多组件日志按时间关联，还原一次操作的完整链路。
- 实体关联：用"谁访问了哪张表的哪列"做关联分析。
- 异常检测：某用户突然大量查询敏感表 → 告警。

## 六、Kerberos 认证体系

### 6.1 Kerberos 原理详解

Kerberos 是对称密钥网络认证协议，核心是 KDC（Key Distribution Center）。用户和服务都向 KDC 注册，通过票据（Ticket）机制实现"无需在网络上明文传密码"的认证。

```
Kerberos 三次握手:

1. AS-REQ/AS-REP (获取TGT)
   用户 → KDC的AS: "我是alice, 我要TGT"
   KDC: 用alice的密钥验证身份, 颁发TGT(用TGS密钥加密)

2. TGS-REQ/TGS-REP (获取服务票据)
   用户 → KDC的TGS: 出示TGT, 请求访问hdfs服务
   KDC: 验证TGT, 颁发Service Ticket(用hdfs服务密钥加密)

3. AP-REQ/AP-REP (访问服务)
   用户 → hdfs: 出示Service Ticket
   hdfs: 用自己的密钥解密票据, 验证用户身份, 授权
```

**关键概念：**

| 概念 | 全称/含义 |
|------|----------|
| KDC | Key Distribution Center，认证中心 |
| AS | Authentication Server，认证服务（颁TGT） |
| TGS | Ticket Granting Server，票据授予服务（颁服务票据） |
| TGT | Ticket Granting Ticket，票据授予票据（"入场券"） |
| Service Ticket | 访问具体服务的票据 |
| Principal | Kerberos身份标识，如 alice@REALM 或 hdfs/_HOST@REALM |
| Keytab | 存principal密钥的文件，供服务免密登录 |

Principal 命名规范：`主成分/实例@REALM`。如 `hdfs/namenode.hadoop.com@BIGDATA.COM`，`_HOST` 是占位符，会替换为实际主机名。

### 6.2 Hadoop Kerberos 配置实战

**1. 安装配置 KDC：**

```bash
# 安装Kerberos server (MIT KDC)
yum install -y krb5-server krb5-workstation

# /var/kerberos/krb5kdc/kdc.conf
[realms]
  BIGDATA.COM = {
    kdc_ports = 88
    admin_keytab = /var/kerberos/krb5kdc/kadm5.keytab
    database_name = /var/kerberos/krb5kdc/principal
    max_life = 10h 0m 0s
    max_renewable_life = 7d 0h 0m 0s
  }

# /etc/krb5.conf
[libdefaults]
  default_realm = BIGDATA.COM
  dns_lookup_realm = false
  dns_lookup_kdc = false
  ticket_lifetime = 24h
  renew_lifetime = 7d
  forwardable = true

# 创建数据库
kdb5_util create -s
# 启动KDC和admin
systemctl start krb5kdc kadmin
```

**2. 创建 principals：**

```bash
# 管理员
kadmin.local -q "addprinc admin/admin"
# 用户
kadmin.local -q "addprinc alice"
# 服务(hdfs的namenode)
kadmin.local -q "addprinc -randkey hdfs/namenode.hadoop.com"
# 导出keytab
kadmin.local -q "ktadd -k /etc/security/keytabs/hdfs.keytab hdfs/namenode.hadoop.com"
# 所有节点复用_HOST, 需对每个节点生成对应principal
```

**3. Hadoop 配置启用 Kerberos：**

```xml
<!-- hdfs-site.xml -->
<property>
  <name>dfs.block.access.token.enabled</name><value>true</value>
</property>
<property>
  <name>dfs.namenode.kerberos.principal</name>
  <value>hdfs/_HOST@BIGDATA.COM</value>
</property>
<property>
  <name>dfs.namenode.keytab.file</name>
  <value>/etc/security/keytabs/hdfs.keytab</value>
</property>
<property>
  <name>dfs.datanode.kerberos.principal</name>
  <value>hdfs/_HOST@BIGDATA.COM</value>
</property>
<property>
  <name>dfs.datanode.keytab.file</name>
  <value>/etc/security/keytabs/hdfs.keytab</value>
</property>

<!-- core-site.xml -->
<property>
  <name>hadoop.security.authentication</name><value>kerberos</value>
</property>
<property>
  <name>hadoop.security.authorization</name><value>true</value>
</property>
```

**4. 用户使用：**

```bash
# 申请票据
kinit alice
# 之后即可访问hadoop
hadoop fs -ls /
# 查看票据
klist
# 注销
kdestroy
# keytab免密登录(用于服务)
kinit -kt /etc/security/keytabs/alice.keytab alice
```

### 6.3 Kerberos 运维与故障排查

**常见故障与排查：**

```bash
# 1. "Server not found in Kerberos database"
# 原因: DNS解析与principal不匹配
# 排查:
hostname -f   # 检查主机名是否完整FQDN
nslookup namenode.hadoop.com   # 反向解析是否一致
# 解决: 确保所有节点hostname -f返回FQDN, /etc/hosts配置正确, 反向解析存在

# 2. "Clock skew too great"
# 原因: 节点时间差超5分钟
# 解决: 所有节点装ntp/chrony, 强制同步
chronyc makestep

# 3. "Key version number for principal incorrect"
# 原因: keytab过期或被重新生成, 旧票据失效
# 解决: kdestroy后kinit, 或重新ktadd

# 4. kinit成功但hadoop命令报错GSSException
# 原因: 服务principal没注册或keytab权限错
# 排查:
klist -kt /etc/security/keytabs/hdfs.keytab   # 查看keytab内容
kadmin.local -q "getprinc hdfs/namenode.hadoop.com"  # 比对KVNO
# 解决: KVNO不一致需重新ktadd, keytab权限设为600属主hdfs:hdfs

# 5. TGT过期导致长任务失败
# 解决: 用renewable ticket + 自动renew
kinit -r 7d alice
# 或在yarn-site.xml配置自动renew
```

运维清单：
- KDC 高可用（主备 KDC + 同步）
- keytab 文件权限严格（600，属主对应服务用户）
- 票据自动续期机制（长跑任务必备）
- 监控 KDC 可用性（挂了整个集群登录瘫痪）
- 定期备份 principal 数据库

### 6.4 Kerberos 与其他认证方式对比

| 方式 | 优势 | 劣势 | 适用 |
|------|------|------|------|
| Kerberos | 强身份、双向认证、企业成熟 | 部署复杂、需KDC高可用、时钟敏感 | 大数据集群内部 |
| OAuth2 | 灵活、易集成云原生 | 依赖IdP、令牌管理复杂 | 应用层、API |
| mTLS | 极强、无需KDC | 证书管理复杂、撤销难 | 服务网格、零信任 |
| LDAP/AD | 集中用户管理 | 仅认证不授权、明文需配SSL | 用户目录集成 |

Hadoop 生态主流是 Kerberos + Ranger（认证+授权），KDC 常与 AD/LDAP 集成做用户统一管理。

## 七、大数据加密与隐私保护

### 7.1 透明数据加密（TDE）

TDE 在存储层自动加解密，应用无感。HDFS 透明加密区、HBase Cell 加密、Kafka 消息加密都属于此类。

```bash
# HDFS透明加密区(见2.2节)
# 关键: KEK存在KMS, 数据用EDEK加密, 密钥与数据分离

# HBase Cell级加密
# hbase-site.xml
<property>
  <name>hbase.crypto.keyprovider</name>
  <value>org.apache.hadoop.hbase.io.crypto.KeyProviderForTesting</value>
</property>
<property>
  <name>hbase.crypto.masterkey.alg</name>
  <value>AES</value>
</property>
```

TDE 防护的是"存储介质失窃"（硬盘被偷、备份磁带丢失），不防"已认证用户访问"——用户有权限读就能解密。所以 TDE 必须配合权限控制。

### 7.2 列级加密与行级加密

**列级加密：** 在应用层对敏感列做加密后存储，查询时解密。

```sql
-- Hive列级加密示例(UDF)
INSERT INTO customers_encrypted
SELECT id, encrypt_aes(name, '${KEY}'), phone, encrypt_aes(idcard, '${KEY}')
FROM customers_raw;

-- 查询时解密
SELECT id, decrypt_aes(name_enc, '${KEY}') FROM customers_encrypted WHERE id=100;

-- 缺点: 加密列无法用索引/谓词下推优化, 性能差
-- 替代: 确定性加密(可等值查询但泄露频次)
```

**行级控制：** Ranger 行级过滤在 SQL 执行时自动加 WHERE 条件，不同用户看到不同行。

### 7.3 差分隐私在大数据中的应用

差分隐私（Differential Privacy）通过添加噪声，保证"加入或移除任一条记录，统计结果几乎不变"，从而保护个体隐私。

```
差分隐私原理:

原始统计: COUNT(*) = 1000
加噪后:   COUNT(*) + Laplace(0, 1/ε) = 1000 ± 噪声

ε(epsilon)越小隐私越强, 但结果越不准
特性: 即使攻击者知道其他999条记录, 也无法推断第1000条
```

应用场景：
- 数据统计发布（如发布用户画像聚合数据）
- 跨部门数据共享前的脱敏
- 机器学习训练数据保护（DP-SGD）

局限：差分隐私适合"聚合统计"，不适合"精确查询"——总不能给用户查自己订单还加噪声。大数据平台中通常用于对外发布的统计报表。

### 7.4 数据脱敏与匿名化

**静态脱敏：** 把生产数据复制到测试库时，对敏感字段做不可逆变换。

```python
# Python脱敏示例
import hashlib
import random

def mask_idcard(idcard):
    # 保留前6后4, 中间打码
    return idcard[:6] + "********" + idcard[-4:]

def hash_phone(phone, salt="s3cr3t"):
    return hashlib.sha256((phone + salt).encode()).hexdigest()[:16]

def generalize_age(age):
    # 泛化为区间
    return f"{age//10*10}-{age//10*10+9}"

# k-匿名: 保证每条记录至少与k-1条在准标识符上不可区分
# 实现方式: 泛化(如年龄→区间, 邮编→前3位) + 抑制(删除标识列)
```

**动态脱敏：** 在查询时实时掩码，原始数据不动。Ranger 的 Masking 策略支持。

```
Ranger脱敏策略类型:
  MASK: 全部掩码 ****
  MASK_SHOW_LAST_4: 末4位可见 ****1234
  MASK_SHOW_FIRST_4: 首4位可见 1234****
  MASK_HASH: 哈希值
  MASK_DATE: 日期精度降到年
  MASK_NULL: 返回NULL
```

**匿名化标准：**
- k-匿名：每条记录至少与 k-1 条在准标识符上不可区分
- l-多样性：每个等价类中敏感属性至少有 l 个不同值
- t-贴近：敏感属性分布接近整体分布

## 八、大数据安全运营

### 8.1 大数据平台安全监控

监控对象覆盖"用户行为、平台组件、网络、数据访问"四维度。

**用户行为监控：**
- 异常登录（新 IP、非工作时间、频繁失败）
- 异常查询（大批量拉取敏感表、跨业务线查询）
- 权限变更（敏感授权操作）

**组件健康监控：**
- KDC 可用性、票据续期成功率
- Ranger Admin 可用性、策略下发延迟
- 各组件审计日志是否正常输出

**数据访问监控：**
- 敏感表访问 TOP 用户
- 全表扫描告警（少量用例才需全表）
- 数据导出操作（hive 导出文件、kafka 消费者拉取量）

```bash
# 监控Kerberos认证失败率
grep "PREAUTH_FAILED" /var/log/kadmind.log | wc -l

# 监控Ranger策略变更
grep "POLICY_UPDATE" /var/log/ranger/audit.log

# 监控全表扫描(Hive审计)
grep "SELECT \*" /var/log/hive/hive-audit.log | awk '{print $user}' | sort | uniq -c
```

### 8.2 安全事件响应流程

大数据平台安全事件响应典型流程：

```
1. 发现: 监控告警/审计异常/外部通报
   ↓
2. 遏制: 冻结账号(kadmin)、阻断IP(防火墙)、隔离节点
   ↓
3. 取证: 拉取审计日志、Ranger审计、KDC日志、网络流量
   ↓
4. 分析: 还原操作链路、定损(影响范围、泄露数据量)
   ↓
5. 处置: 撤销非法授权、修复漏洞、加固配置
   ↓
6. 报告: 形成事件报告, 按合规要求上报(72小时GDPR)
   ↓
7. 改进: 复盘、补充监控规则、更新SOP
```

关键能力：能快速冻结账号是遏制扩散的第一招，Kerberos 一注销 TGT 失效，比改密码更彻底。

### 8.3 大数据合规要求

**数据安全法（国内）：**
- 建立数据分类分级保护制度
- 重要数据出境需安全评估
- 数据处理者需定期风险评估

**个人信息保护法（PIPL）：**
- 处理个人信息需告知并取得同意
- 敏感个人信息（生物识别、医疗、金融等）需单独同意
- 数据可携带权、删除权

**GDPR（欧盟，跨境适用）：**
- 数据处理需合法性基础
- 数据主体权利：访问、更正、删除、可携带
- 数据泄露 72 小时内上报监管

**合规落地要点：**
1. 数据资产盘点与分类分级（核心、重要、一般）
2. 敏感数据加密与脱敏
3. 访问授权与审计留痕（满足"可追溯"要求）
4. 数据出境评估（跨境传输前必做）
5. 数据生命周期管理（不再需要时安全删除）

### 8.4 大数据安全评估与加固

**评估维度：**

## 九、实战案例

### 案例1：Hadoop 集群安全加固实战

**背景：** 某公司 Hadoop 集群长期"裸奔"（simple 模式），300+ 节点，存储 PB 级业务数据。审计要求一年内完成安全加固。

**加固过程：**

1. **资产盘点：** 用脚本扫描集群所有组件版本，识别 CVE。发现 Hadoop 2.7（多个高危 CVE）、Hive 未启用授权。

```bash
# 全集群组件版本扫描
for node in $(cat nodes.txt); do
  ssh $node "hadoop version; hive --version; hbase version" 
done > versions.txt
```

2. **升级组件：** Hadoop 2.7 → 3.3，修复已知 CVE。灰度升级（先边缘节点，再核心）。

3. **启用 Kerberos：** 部署 KDC，为每个服务生成 principal 与 keytab。难点是数百节点的 `_HOST` 必须正确——逐台检查 `hostname -f` 返回 FQDN，修正 DNS。

4. **配置 Hadoop 安全：** 推送 core-site.xml/hdfs-site.xml，重启 NameNode/DataNode。第一次启动失败——发现部分 DataNode 时间差超 5 分钟，强制 NTP 同步后恢复。

5. **部署 Ranger：** 集中管理授权策略。把原有 HDFS POSIX 权限梳理成 Ranger 策略，按业务线分库分目录授权，敏感目录加列级脱敏。

6. **启用加密：** 敏感数据目录建加密区，KMS 用独立密钥管理服务。审计发现 KMS 密钥原本存在 NameNode 内存，改为独立 KMS + HSM 根密钥。

7. **审计与监控：** 把 HDFS/Hive/Ranger/KDC 日志汇入 ELK，建异常查询告警规则。

**成果：** 通过等保三级测评，"内网默认信任"风险消除。沉淀了 Kerberos 部署 SOP、Ranger 策略模板、加固检查清单。

### 案例2：Kerberos 部署排错全过程

**背景：** 新上线 Hadoop 启用 Kerberos 后，用户 `kinit` 成功但执行 `hadoop fs -ls /` 报错 `GSSException: No valid credentials provided`。

**排错过程：**

1. **初步定位：** `klist` 看到 TGT 正常，但 NameNode 日志报 `Key version number for principal hdfs/namenode in keytab incorrect`。

2. **比对 KVNO：**

```bash
klist -kt /etc/security/keytabs/hdfs.keytab
# keytab: hdfs/namenode.hadoop.com@BIGDATA.COM KVNO=3

kadmin.local -q "getprinc hdfs/namenode.hadoop.com"
# principal: hdfs/namenode.hadoop.com@BIGDATA.COM
# Key: vno 4, aes256...
# KVNO不一致! keytab是3, KDC是4
```

原因：曾用 `ktadd` 重新生成过 keytab，但旧 keytab 没及时分发。解决：重新 `ktadd -k` 并分发。

3. **二次报错：** 修完 KVNO 后，又报 `Server not found in Kerberos database (7)`。客户端 principal 是 `hdfs/namenode.hadoop.com`，但实际 DNS 解析的 hostname 不一致。

```bash
hostname -f   # 返回 namenode (短名, 不带域)
# 而principal是 hdfs/namenode.hadoop.com
```

解决：设置 `/etc/hosts` 把 FQDN 与 IP 对应，并设置 hostname 为 FQDN：

```bash
hostnamectl set-hostname namenode.hadoop.com
# /etc/hosts:
# 10.0.0.1 namenode.hadoop.com namenode
```

4. **三次报错：** 修完 hostname 后，DataNode 起不来，报 `Clock skew too great`。

```bash
date   # 对比namenode和datanode时间, 差6分钟
# Kerberos默认允许5分钟时差
```

解决：所有节点装 chrony 并强制同步。

```bash
systemctl enable chronyd
chronyc makestep
```

5. **最终验证：** `kinit alice && hadoop fs -ls /` 成功。把排错经验沉淀为检查清单：FQDN 一致性、KVNO 一致性、时钟同步、keytab 权限、DNS 反向解析。

### 案例3：大数据平台数据泄露事件响应

**背景：** 审计发现某分析团队离职员工疑似在离职前批量拉取了客户敏感数据。

**响应过程：**

1. **遏制：** 立即用 kadmin 冻结该账号 TGT（`cpw -randkey` 使旧票据失效），同时撤销其 Ranger 权限策略。

2. **取证 - 审计关联：** 拉取该用户最后 30 天的所有审计日志（HDFS audit、Hive audit、Ranger audit）。

```bash
# 从ELK导出该用户的操作记录
# Elasticsearch查询: user.keyword: "li.ming"
# 时间: 离职前30天
# 结果: 发现离职前3天大量SELECT customers WHERE region=...
```

3. **分析 - 链路还原：** 审计日志显示该用户离职前 3 天通过 Hive 执行了 23 次 SELECT 查询，每次查不同 region 的客户表，合计拉取约 50 万条客户记录（含手机号、身份证）。每次查询后都伴随 `hadoop fs -getmerge` 把结果导出为本地文件。

4. **量化定损：** 根据查询记录统计：
   - 涉及表：customers（敏感）
   - 字段：手机号、身份证号、地址（PII）
   - 记录数：约 50 万条
   - 被拉取数据的客户分布：东、南、西三个大区
   - 是否外传：审计显示文件被写到本地，需结合该工作站 EDR 进一步看是否上传到外部存储

5. **处置：**
   - 联系该员工配合调查，要求删除已导出数据
   - 评估是否构成"重要数据/个人信息泄露"，按数据安全法评估是否需上报监管
   - 修复控制缺陷：敏感表查询加 Ranger 行级过滤（限定只能查自己负责 region）、批量导出操作增加审批流、离职流程增加数据访问审查节点

6. **改进：** 增设"敏感数据批量查询告警"规则——单用户单日 SELECT 敏感表记录数超阈值即告警 SOC。

**结论：** 该事件暴露了"权限虽在但无行为监控"的盲区。光有 Ranger 授权不够，必须配合行为审计才能发现异常批量访问。

## 总结

大数据安全是"分布式系统 + 海量敏感数据"双重挑战下的安全工程。掌握要点：

1. **认证是地基：** Kerberos 是 Hadoop 生态的认证基石，部署虽复杂但不可绕过。关键运维：KDC 高可用、keytab 严管、时钟同步。
2. **授权到列：** 原生 HDFS 权限粒度粗，Ranger 实现库/表/列级 + 行级过滤 + 动态脱敏，是合规审计的核心。
3. **加密分层：** 传输加密（SASL/SSL）防嗅探，存储加密（TDE）防介质失窃，应用层加密（列级）防越权，各防一面。
4. **审计贯通：** 各组件审计汇入统一平台，能按"谁、何时、访问了什么数据"还原完整链路，是事后追溯与合规证据的关键。
5. **行为监控补授权盲区：** 光有权限控制不够，必须监控"权限内的异常使用"——批量拉取、敏感字段高频查询、跨业务线访问。

持续学习路径：先理解 Kerberos 原理与排错 → 上手 Hadoop/Kafka 安全配置 → 部署 Ranger 统一授权 → 实施加密与脱敏 → 搭建统一审计与行为监控 → 在实战加固与事件响应中沉淀经验。大数据安全没有银弹，是认证、授权、加密、审计、监控五位一体的系统工程。
