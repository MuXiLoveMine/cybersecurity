## 一、数据安全事件概述

### 1.1 事件定义与分类

数据安全事件是指由于人为原因、软硬件缺陷或故障、自然灾害等因素，导致信息系统中的数据遭到未经授权的获取、损坏或修改，对数据机密性、完整性或可用性造成影响的事件。

**事件分类**

| 类别 | 定义 | 典型场景 |
|------|------|----------|
| 数据泄露 | 数据被未经授权地获取或暴露 | 数据库拖库、API数据泄露 |
| 数据篡改 | 数据被未经授权地修改 | 篡改交易数据、网页挂马 |
| 数据损毁 | 数据被破坏或不可用 | 勒索软件加密、误删除 |
| 数据丢失 | 数据永久性消失 | 存储设备损坏、备份失败 |
| 未授权访问 | 数据被不应当访问的人访问 | 越权访问、权限滥用 |

### 1.2 事件分级标准

**特别重大事件（一级）**

- 影响范围：涉及1000万以上个人信息
- 数据类型：敏感个人信息（生物识别、医疗健康、金融账户）
- 社会影响：国家安全、社会秩序受到严重影响
- 业务影响：核心业务系统中断

**重大事件（二级）**

- 影响范围：涉及100万至1000万个人信息
- 数据类型：重要数据或敏感个人信息
- 社会影响：较大范围社会影响
- 业务影响：重要业务系统中断

**较大事件（三级）**

- 影响范围：涉及10万至100万个人信息
- 数据类型：一般个人信息
- 社会影响：一定范围社会影响
- 业务影响：部分业务系统中断

**一般事件（四级）**

- 影响范围：涉及10万以下个人信息
- 数据类型：非敏感数据
- 社会影响：影响有限
- 业务影响：个别系统短暂中断

### 1.3 常见数据安全事件类型

**数据泄露事件**

```
攻击链：
  1. 初始入侵 (漏洞利用/钓鱼/供应链攻击)
  2. 内网横向移动 (凭证窃取/漏洞利用)
  3. 数据库访问 (SQL注入/凭证复用)
  4. 数据外传 (加密通道/压缩打包/DNS隧道)
  5. 数据公开或出售
```

常见泄露途径：

| 途径 | 说明 | 案例 |
|------|------|------|
| SQL注入 | 数据库直接被拖 | 某电商网站5000万用户数据泄露 |
| API泄露 | 接口未鉴权或越权 | 某社交平台API暴露用户好友列表 |
| 云存储泄露 | S3 Bucket/Object公开 | 某公司S3存储桶公开暴露6亿用户数据 |
| 内部人员泄露 | 员工恶意或疏忽 | 某银行员工离职前导出客户数据 |
| 供应链攻击 | 第三方服务商被入侵 | 某SDK收集并泄露宿主APP用户数据 |
| 勒索泄露 | 勒索软件双重勒索 | 某企业被勒索后数据被公开 |

**数据篡改事件**

```
攻击类型：
  - 网页篡改：修改网站页面内容
  - 交易篡改：修改交易金额或记录
  - 配置篡改：修改系统或应用配置
  - 日志篡改：删除或修改安全日志
  - DNS劫持：修改DNS解析指向
```

**勒索软件事件**

```
勒索软件攻击链：
  1. 初始入侵 (钓鱼邮件/RDP暴力破解/漏洞利用)
  2. 权限提升 (漏洞利用/凭证窃取)
  3. 横向移动 (PsExec/WMI/RDP)
  4. 数据窃取 (双重勒索筹码)
  5. 数据加密 (全盘/数据库/文件服务器)
  6. 勒索通知 (加密货币赎金)
```

### 2.1 响应组织架构

```
                    +------------------+
                    |   应急指挥中心   |
                    | (Incident Command)|
                    +--------+---------+
                             |
            +----------------+----------------+
            |                |                |
  +---------v------+  +------v-------+  +----v--------+
  | 技术处置组     |  | 法律合规组   |  | 对外联络组  |
  | - 安全工程师   |  | - 法务       |  | - 公关     |

  | - 取证分析师   |  | - 隐私官     |  | - 媒体     |
  +----------------+  +--------------+  +-------------+
            |
  +---------v------+

  | - 人力资源     |
  | - 财务保障     |
  | - 后勤支持     |
  +----------------+
```

### 2.2 PICERL六阶段模型

PICERL（Preparation, Identification, Containment, Eradication, Recovery, Lessons Learned）是NIST SP 800-61定义的事件响应标准流程：

```
  准备阶段 (Preparation)
       |
       v
  识别阶段 (Identification) -----> 不是安全事件? ---> 回到准备阶段
       |
       v
  遏制阶段 (Containment)
       |
       v
  根除阶段 (Eradication)
       |
       v
  恢复阶段 (Recovery)
       |
       v
  经验总结 (Lessons Learned) ---> 更新预案/改进措施 ---> 回到准备阶段
```

### 3.4 预案与演练

```

触发条件：IDS告警/异常数据查询/数据外传检测

响应步骤：
  1. 识别确认
     - 确认告警真实性
     - 初步评估影响范围
     - 启动二级响应

  2. 紧急遏制
     - 隔离数据库服务器
     - 封锁攻击源IP
     - 禁用相关账号
     - 保留系统快照

  3. 取证分析
     - 采集内存镜像
     - 采集磁盘镜像
     - 提取数据库访问日志
     - 提取网络流量

  4. 影响评估
     - 确定泄露数据类型和数量
     - 识别受影响用户
     - 评估法律合规影响

  5. 根除与恢复
     - 修复漏洞
     - 清除后门
     - 重置所有凭证
     - 从备份恢复数据

  6. 通知报告
     - 监管机构报告（72小时内）
     - 用户通知
     - 内部总结报告
```

## 四、识别阶段

### 4.1 事件发现渠道

| 渠道 | 描述 | 响应时间 |
|------|------|----------|
| SIEM告警 | 安全设备和日志聚合分析触发告警 | 最快，自动化 |
| EDR告警 | 端点检测与响应系统告警 | 快，自动化 |
| 用户报告 | 内部员工或外部用户发现异常 | 中等，被动 |
| 第三方通报 | 合作伙伴/安全厂商/监管机构通报 | 慢，被动 |
| 威胁情报 | 对比IOC发现已知威胁 | 快，自动化 |
| 数据泄露监控 | 暗网/公开渠道监控发现数据泄露 | 慢，被动 |
| 安全扫描 | 定期安全扫描发现异常 | 预防性 |

### 4.2 初步评估

**评估检查清单**

```
1. 确认事件真实性
   - 验证告警来源和可信度
   - 排除误报可能性
   - 收集初始证据

2. 确定事件类型
   - 数据泄露 / 数据篡改 / 勒索软件 / 未授权访问
   - 识别攻击手法（TTPs）

3. 评估影响范围
   - 受影响的系统和服务
   - 受影响的数据类型和数量
   - 受影响的用户数量

4. 确定事件级别
   - 参照分级标准
   - 决定响应级别

5. 通知启动
   - 通知事件指挥官
   - 启动响应团队
   - 建立通信渠道
```

### 4.3 事件分级启动

```
一级事件（特别重大）:
  - 立即启动最高级响应
  - CEO/董事会通报
  - 国家网信部门报告
  - 外部安全专家支援

二级事件（重大）:
  - 启动高级响应
  - CISO/CTO通报
  - 省级网信部门报告
  - 考虑外部支援

三级事件（较大）:
  - 启动标准响应
  - 安全总监通报
  - 地市级网信部门报告

四级事件（一般）:
  - 启动基础响应
  - 安全团队处置
  - 内部记录报告
```

## 五、遏制阶段

### 5.1 短期遏制

**立即遏制措施**

```
网络隔离:
  - 在防火墙封锁攻击源IP
  - 在交换机关闭攻击端口
  - 将受感染主机移到隔离VLAN
  - 禁用远程访问通道

账号控制:
  - 禁用被入侵的账号
  - 强制重置相关用户密码
  - 撤销活跃会话令牌
  - 禁用VPN/远程桌面访问

服务控制:
  - 停止可疑进程
  - 停止相关服务
  - 关闭受影响的端口
  - 暂停数据同步/外传
```

**遏制操作记录**

```
记录每项遏制操作的：
  - 操作时间（精确到秒）
  - 操作人员
  - 操作内容
  - 操作前后状态
  - 使用工具和命令
  - 操作结果
```

### 5.2 长期遏制

```
长期遏制措施：
  - 修补已知漏洞
  - 部署临时规则（WAF/IPS）
  - 增加监控覆盖
  - 隔离非必要服务
  - 加强访问控制
  - 部署蜜罐/诱饵
```

### 5.3 证据保全

**取证顺序（按易失性排序）**

```
1. 寄存器和缓存        (极快丢失)
2. 内存(RAM)          (断电即丢失)
3. 网络状态           (连接会超时)
4. 运行进程           (可被终止)
5. 临时文件           (可被覆盖)
6. 磁盘数据           (持久)
7. 远程日志           (持久)
8. 物理存储           (持久)
```

**内存取证**

```bash
# Windows
# 使用Magnet RAM Capture或winpmem
winpmem_mini_x64.exe output.mem

# 使用Magnet RAM Capture (GUI工具)
# 或使用NIST的WindowsSCOPE

# Linux
# 使用LiME (Linux Memory Extractor)
insmod lime.ko "path=/tmp/memory.lime format=lime"

# 使用AVML (Azure Virtual Machine Linux)
avml output.lime

# 内存分析 (Volatility 3)
vol -f memory.dmp windows.pslist
vol -f memory.dmp windows.netscan
vol -f memory.dmp windows.malfind
vol -f memory.dmp windows.cmdline
```

**磁盘取证**

```bash
# 使用写保护器防止数据被修改

# Linux使用dd或dc3dd
dc3dd if=/dev/sda of=disk_image.dd hash=sha256 log=acquisition.log
# dc3dd会同时计算哈希，确保完整性

# 使用dc3dd带校验
dc3dd if=/dev/sda of=disk_image.dd \
    hash=sha256 hash=md5 \
    log=acquisition.log \
    mlog=multi.log \
    ofs=0

# 验证镜像
sha256sum disk_image.dd
md5sum disk_image.dd

# 比对源盘和镜像哈希是否一致

# Windows使用FTK Imager
# 1. 启动FTK Imager
# 2. 选择"Create Disk Image"
# 3. 选择物理设备
# 4. 选择镜像格式（E01/DD/RAW）
# 5. 设置哈希算法（MD5+SHA256）
# 6. 采集并验证
```

## 六、根除阶段

### 6.1 威胁清除

**恶意软件清除**

```bash
# 1. 识别恶意进程
# Windows
wmic process list full | findstr "suspicious"
tasklist /svc

# Linux
ps auxf
lsof -i

# 2. 终止恶意进程
taskkill /PID <pid> /F      # Windows
kill -9 <pid>               # Linux

# 3. 删除恶意文件
del /f <path>               # Windows
rm -f <path>                 # Linux

# 4. 清除持久化机制
# Windows
```

### 6.2 漏洞修复

```
修复优先级排序：

P0 - 紧急修复 (24小时内)
  - 被利用的远程代码执行漏洞
  - 被利用的认证绕过漏洞
  - 被利用的权限提升漏洞

P1 - 高优先级 (72小时内)
  - 未被利用但影响严重
  - 公开PoC的漏洞
  - 暴露在公面的服务漏洞

P2 - 中优先级 (1周内)
  - 内部服务漏洞
  - 需要认证才能利用的漏洞

P3 - 低优先级 (1月内)
  - 信息泄露
  - 非关键系统漏洞
```

### 6.3 加固措施

```
访问控制加固：
  - 重置所有可能泄露的凭证
  - 启用多因素认证(MFA)
  - 实施最小权限原则
  - 审查并清理用户权限
  - 加强特权账户管理

网络加固：
  - 更新防火墙规则
  - 实施网络分段
  - 部署IDS/IPS规则
  - 加强出口流量监控
  - 启用DNS过滤

监控加固：
  - 部署EDR
  - 增加日志覆盖范围
  - 配置新检测规则
  - 加强告警阈值
```

## 七、恢复阶段

### 7.1 数据恢复

```
数据恢复策略：

1. 评估备份可用性
   - 确认备份未被感染
   - 验证备份完整性
   - 确认备份时间点

2. 从备份恢复
   - 选择感染前的备份
   - 在隔离环境验证
   - 分批次恢复

3. 数据完整性验证
   - 比对数据哈希
   - 验证业务逻辑
   - 检查数据一致性

4. 被加密数据恢复
   - 评估是否有解密工具
   - 检查是否有影子副本
   - 评估支付赎金的利弊
```

### 7.2 系统恢复

```
恢复步骤：

1. 从干净镜像重建系统
   - 使用经过验证的OS镜像
   - 安装最新补丁
   - 配置安全基线

2. 应用恢复
   - 从可信源恢复应用
   - 验证应用完整性
   - 配置安全参数

3. 网络恢复
   - 逐步开放网络访问
   - 验证防火墙规则
   - 确认隔离已解除

4. 服务恢复
   - 按优先级恢复服务
   - 监控恢复后状态
   - 确认业务正常
```

### 7.3 验证与监控

```
恢复后验证清单：

[ ] 所有系统补丁已更新到最新
[ ] 所有用户密码已重置
[ ] 所有API密钥已轮换
[ ] MFA已强制启用
[ ] 网络隔离已精确解除
[ ] 监控系统正常运行
[ ] 备份系统正常运行
[ ] 日志系统正常运行
[ ] 告警规则已更新
[ ] 安全设备已配置最新规则
[ ] 业务功能全部正常
[ ] 性能指标恢复正常
```

## 九、数字取证方法

### 9.1 取证原则

```
1. 不改变原始证据
   - 使用写保护器
   - 操作副本而非原件
   - 记录所有操作

2. 证据完整性
   - 采集时计算哈希
   - 传输后验证哈希
   - 存储后定期验证

3. 证据链
   - 从采集到呈堂的完整记录
   - 每个环节有签名
   - 时间戳精确

4. 合法性
   - 取证授权明确
   - 遵循法律法规
   - 保护隐私权利
```

### 9.4 网络取证

```bash
# 全流量捕获
tcpdump -i eth0 -w full_traffic.pcap -G 3600 -W 24

# 过滤特定流量
tcpdump -i eth0 -w suspicious.pcap \
    'port 4444 or port 8080 or host 192.168.1.100'

# 使用Zeek(Bro)进行流量分析
zeek -r traffic.pcap local

# 分析HTTP流量
tshark -r traffic.pcap -Y http -T fields \
    -e http.request.uri -e http.host

# 分析DNS查询
tshark -r traffic.pcap -Y dns -T fields \
    -e dns.qry.name -e dns.resp.addr

# 检测数据外传
tshark -r traffic.pcap -Y 'tcp.dstport != 80 and tcp.dstport != 443' \
    -T fields -e ip.src -e ip.dst -e tcp.dstport -e frame.len
```

### 10.2 通知流程

```
数据泄露通知决策流程：

1. 确认泄露
   |
2. 评估是否需要通知
   - 是否涉及个人信息？
   - 是否对个人权益造成影响？
   - 是否触发法定通知义务？
   |
   +-- 是 --> 启动通知流程
   |
   +-- 否 --> 记录但不通知

3. 确定通知对象
   - 监管机构 (网信/公安/通信管理)
   - 受影响个人 (用户)
   - 业务合作伙伴
   - 内部管理层

4. 准备通知内容
   - 泄露事件描述
   - 涉及的数据类型
   - 可能的影响
   - 已采取的措施
   - 建议的防护措施
   - 联系方式和咨询渠道

5. 执行通知
   - 监管机构：书面报告
   - 用户：邮件/短信/公告
   - 合作伙伴：协议约定方式
   - 内部：内部通报

6. 后续跟进
   - 回应咨询
   - 补充报告
   - 整改报告
```
