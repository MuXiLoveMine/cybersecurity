# 工控渗透测试指南

> 本文档介绍工控系统渗透测试的特点、流程、方法和工具。工控渗透测试与传统 IT 渗透测试有显著区别，必须在严格授权和安全保障的前提下进行。

---

## 一、工控渗透测试特点与注意事项

### 1.1 工控渗透测试的特殊性

工控渗透测试（OT Pentest）与传统 IT 渗透测试相比，具有以下显著差异：

| 对比维度 | IT 渗透测试 | 工控渗透测试 |
|----------|------------|-------------|
| **首要目标** | 发现漏洞、获取权限 | 评估安全风险、验证防护能力 |
| **风险控制** | 相对可控，系统可重启 | 风险极高，可能影响生产安全 |
| **测试环境** | 通常在线测试 | 优先离线/测试环境测试 |
| **测试深度** | 尽可能深入 | 严格控制深度，避免影响生产 |
| **协议栈** | TCP/IP、HTTP 等通用协议 | Modbus、S7、Profinet 等专用协议 |
| **目标系统** | 服务器、网站、应用 | PLC、HMI、SCADA、控制器 |
| **法律要求** | 一般授权即可 | 需要更严格的审批和应急预案 |
| **报告重点** | 漏洞详情和利用方式 | 风险评估和防护建议 |

### 1.2 工控渗透测试的核心原则

#### 原则一：安全第一，生产优先

- 绝对不能影响正常生产
- 遇到异常立即停止测试并上报
- 生产系统稳定运行高于一切
- 宁可测试不充分，也不能出事故

#### 原则二：充分授权，书面确认

- 必须获得明确的书面授权
- 授权范围要详细明确
- 测试方案需甲方审核确认
- 关键操作需甲方现场确认

#### 原则三：最小影响原则

- 尽可能减少对系统的影响
- 优先使用被动侦察手段
- 主动探测控制强度和范围
- 写入操作要极其谨慎

#### 原则四：应急预案完备

- 测试前制定应急预案
- 明确回滚和恢复方案
- 安排运维人员待命
- 准备好应急联系方式

#### 原则五：专业人员操作

- 测试人员需具备工控专业知识
- 了解测试对象的工艺和设备
- 熟悉工控协议和系统特点
- 有工控安全测试经验

### 1.3 法律与合规要求

**相关法律法规：**
- 《中华人民共和国网络安全法》
- 《中华人民共和国刑法》第 285/286 条
- 《关键信息基础设施安全保护条例》
- 《工业控制系统信息安全防护指南》

**法律风险：**
- 非法侵入计算机信息系统罪
- 破坏计算机信息系统罪
- 提供侵入、非法控制计算机信息系统程序、工具罪
- 危害公共安全罪（如造成严重后果）

> ⚠️ **特别提醒**：工控系统属于关键信息基础设施，攻击工控系统的法律后果远比攻击普通 IT 系统严重。可能涉及危害公共安全罪，最高可判死刑。

### 1.4 渗透测试分类

按测试环境分类：

| 类型 | 说明 | 风险等级 | 适用场景 |
|------|------|---------|---------|
| **实验室测试** | 在自建实验环境中测试 | 低 | 漏洞验证、工具开发、技术研究 |
| **测试环境测试** | 在甲方提供的测试环境中测试 | 中 | 正式测试前的验证、方案确认 |
| **生产环境测试** | 在真实生产环境中测试 | 高 | 真实安全评估、合规检测 |

按测试深度分类：

| 类型 | 测试内容 | 风险 |
|------|---------|------|
| **信息收集型** | 被动侦察、端口扫描、设备识别 | 低 |
| **漏洞扫描型** | 漏洞扫描、配置核查、协议分析 | 中低 |
| **漏洞验证型** | PoC 验证、影响评估 | 中 |
| **深度渗透型** | 漏洞利用、横向移动、权限提升 | 高 |
| **红队演练型** | 模拟真实攻击，全面检验防护能力 | 很高 |

### 2.2 资产发现

#### 2.2.1 主机发现

**注意事项：**
- 工控网络中谨慎使用扫描
- 控制扫描速率，避免影响生产
- 优先使用 ARP 扫描（二层），对设备影响小
- 大规模扫描前需甲方确认

**常用工具：**

**Nmap 主机发现（轻量级）：**
```bash
# ARP 扫描（最安全，仅二层，不影响设备）
nmap -sn -PR 192.168.1.0/24

# ICMP 扫描（轻量）
nmap -sn -PE 192.168.1.0/24

# 慢速扫描（降低影响）
nmap -sn -T2 192.168.1.0/24
```

**Masscan（高速扫描，谨慎使用）：**
```bash
# 快速扫描指定端口
masscan 192.168.1.0/24 -p502,102,2404 --rate=100
```

## 三、工控漏洞利用

### 3.1 PLC 漏洞

#### 3.1.1 PLC 漏洞类型

| 漏洞类型 | 说明 | 危害 |
|----------|------|------|
| **认证绕过** | 可绕过 PLC 的认证机制 | 未授权读写程序和数据 |
| **命令注入** | 通过协议注入系统命令 | 完全控制 PLC |
| **缓冲区溢出** | 协议解析溢出 | 远程代码执行 / 拒绝服务 |
| **拒绝服务** | 畸形报文导致 PLC 崩溃 | 生产中断 |
| **固件篡改** | 可修改 PLC 固件 | 植入后门，长期控制 |
| **程序下载** | 未授权下载 PLC 程序 | 窃取工艺逻辑 |
| **程序上传** | 未授权上传恶意程序 | 修改控制逻辑 |
| **硬编码密码** | 固件中存在后门密码 | 直接登录设备 |

#### 3.1.2 常见 PLC 漏洞示例

**西门子 S7 系列：**
- CVE-2019-13944：S7-1200/1500 认证绕过漏洞，攻击者可以绕过认证读写 PLC 数据
- CVE-2020-15782：S7-1200/1500 内存损坏漏洞，可能导致拒绝服务
- CVE-2022-38465：S7-1200/1500 拒绝服务漏洞

**罗克韦尔 ControlLogix：**
- CVE-2017-6030：EtherNet/IP 模块漏洞，可导致拒绝服务
- CVE-2021-22681：Studio 5000 Logix Designer 漏洞

**施耐德 Modicon：**
- CVE-2018-7839：Modicon M340 信息泄露漏洞
- CVE-2019-6815：Modicon M580 拒绝服务漏洞

**三菱 Q 系列：**
- CVE-2019-10935：三菱 Q 系列 PLC 缓冲区溢出
- CVE-2020-5580：三菱 MELSEC iQ-R 系列漏洞

#### 3.1.3 PLC 攻击方式

**方式一：直接协议攻击**
```
攻击者 → 连接 PLC 通信端口 → 发送恶意协议报文 → 
利用漏洞 → 控制 PLC / 造成拒绝服务
```

**方式二：工程师站攻击**
```
攻击者 → 攻破工程师站 → 获取编程软件权限 → 
通过编程软件下载恶意程序到 PLC → 控制生产过程
```

**方式三：固件攻击**
```
攻击者 → 获取固件 → 修改固件植入后门 → 
通过各种方式刷入 PLC → 长期控制
```

### 3.2 HMI 漏洞

#### 3.2.1 HMI 安全问题

HMI（人机界面）是工控系统中最常被攻击的目标之一：

**常见问题：**
- 操作系统老旧（Windows XP/2000/7）
- 常年不打补丁
- 弱口令或默认口令
- 开启了不必要的服务
- 安装了多个工控软件，组件复杂
- 作为连接上层网络和控制层的跳板

#### 3.2.2 HMI 攻击路径

```
1. 发现 HMI 主机（端口扫描、网络侦察）
2. 攻击 HMI 操作系统
   - 利用 Windows 漏洞
   - 弱口令爆破（RDP/VNC）
   - 社会工程学
3. 获取 HMI 权限后
   - 查看生产画面和数据
   - 通过 HMI 操作控制设备
   - 利用 HMI 上的组态软件攻击 PLC
   - 作为跳板横向移动
```

### 3.3 工程师站漏洞

#### 3.3.1 工程师站的重要性

工程师站（Engineering Workstation）是工控系统的"大脑"：
- 用于 PLC 程序的编写和下载
- 存储有完整的源程序
- 拥有对 PLC 的完全控制权限
- 通常装有各种组态和编程软件

#### 3.3.2 攻击工程师站的价值

- 获取 PLC 源程序（商业秘密）
- 修改控制逻辑（物理破坏）
- 植入后门程序
- 控制整个生产线
- 作为深入渗透的跳板

## 四、工控协议攻击

### 4.1 Modbus 攻击

#### 4.1.1 Modbus 攻击面

| 攻击类型 | 功能码 | 说明 | 风险等级 |
|----------|--------|------|---------|
| 信息收集 | 0x03/0x04/0x01/0x02 | 读取寄存器和线圈数据 | 中 |
| 设备探测 | 0x08/0x11/0x2B | 读取设备信息 | 低 |
| 写入控制 | 0x05/0x06 | 写入单个线圈/寄存器 | 高 |
| 批量写入 | 0x0F/0x10 | 写入多个线圈/寄存器 | 很高 |
| 拒绝服务 | 畸形报文 | 导致设备崩溃 | 高 |
| 中间人 | 所有 | 篡改通信数据 | 很高 |

#### 4.1.2 Modbus 攻击示例

**示例 1：读取生产数据（信息收集）**

攻击者通过 Modbus 读取保持寄存器，获取生产工艺参数：
```python
# 读取温度、压力、流量等工艺参数
# 功能码 0x03 - 读保持寄存器
# 可用于商业间谍活动或为后续攻击做准备
```

**示例 2：写入线圈控制设备（主动控制）**

攻击者向 Modbus 设备写入线圈，控制输出状态：
```python
# 功能码 0x0F - 写多个线圈
# 将所有输出线圈置为 OFF
# 可导致生产线停机
# 详细实现见 modbus_tool.py
```

**示例 3：篡改工艺参数（隐蔽破坏）**

攻击者修改保持寄存器中的控制参数，导致产品不合格或设备损坏：
```python
# 功能码 0x10 - 写多个保持寄存器
# 修改温度设定值，导致过热损坏
# 修改速度参数，导致机械故障
# 这种攻击隐蔽性强，难以及时发现
```

**示例 4：伪造传感器数据（欺骗攻击）**

如果攻击者能控制输入寄存器（某些设备支持写入），可以伪造传感器数据：
```python
# 修改传感器读数
# 使监控系统显示虚假的正常数据
# 实际设备可能已经异常
# 类似 Stuxnet 的欺骗手段
```

### 4.2 S7 攻击

#### 4.2.1 S7 攻击面

| 攻击类型 | 功能码 | 说明 | 风险等级 |
|----------|--------|------|---------|
| 信息收集 | 0x04 (Read) | 读取数据块、输入输出、存储器 | 中 |
| 设备探测 | 0x1A (Read SZL) | 读取系统状态列表和设备信息 | 低 |
| 写入控制 | 0x05 (Write) | 写入数据块和输出 | 高 |
| PLC 控制 | 0x29 | 启动/停止 PLC | 很高 |
| 程序下载 | 0x28 | 上传/下载程序块 | 很高 |
| 认证绕过 | - | 绕过 S7 认证机制 | 很高 |

#### 4.2.2 S7 攻击示例

**示例 1：停止 PLC**

通过 S7 协议将 PLC 切换到 STOP 模式：
```python
# 发送 PLC 停止命令
# 功能码 0x29 (PLC 控制)
# 子功能：停止 CPU
```

## 五、横向移动与持久化

### 5.1 工控网络横向移动路径

#### 5.1.1 典型路径

```
互联网暴露面
    ↓
办公网络（IT 区）
    ↓ （利用 IT/OT 边界漏洞）
生产管理区（MES / 历史数据库）
    ↓ （利用监控系统漏洞）
过程监控区（SCADA / HMI / 工程师站）
    ↓ （利用工控协议或编程软件）
现场控制区（PLC / 控制器）
    ↓ （直接控制）
现场设备（传感器 / 执行器）
```

#### 5.1.2 横向移动技术

**从 IT 到 OT：**
- 利用 IT/OT 边界设备漏洞（防火墙、网闸）
- 通过 VPN/远程维护通道进入
- 利用跨区数据交换服务器
- 钓鱼攻击工控人员的办公电脑
- U 盘摆渡攻击

**在 OT 内部横向移动：**
- 利用 HMI 作为跳板
- 利用工程师站的编程软件
- 通过 SCADA 服务器
- 利用 OPC 服务器
- 利用工业交换机漏洞
- 利用共享凭据（工控网络常用弱口令/默认口令）

### 5.2 持久化技术

#### 5.2.1 网络层持久化

- 在工业交换机/路由器上配置后门
- 建立隐蔽的 VPN 通道
- 利用工控协议隧道
- 在边界防火墙上开后门

#### 5.2.2 主机层持久化

- HMI/工程师站安装后门
- 修改系统服务和启动项
- 替换正常的工控软件组件
- 利用计划任务
- WMI 事件订阅
- 利用工控软件的自动启动功能

#### 5.2.3 控制层持久化

- 向 PLC 下载恶意逻辑（最隐蔽）
- 修改 PLC 固件（最深层持久化）
- 在 RTU 中植入后门
- 利用控制器的维护功能

**PLC 持久化的特点：**
- 极其隐蔽，常规安全检测发现不了
- 重装系统也无法清除（恶意代码在 PLC 中）
- 可以长期潜伏
- 可在需要时激活攻击
- Stuxnet 就是典型案例

### 5.3 痕迹清除

工控系统的日志和审计通常比较薄弱，但仍需注意：

- HMI 操作日志
- SCADA 系统报警记录
- 历史数据库中的异常数据
- 网络设备日志
- 防火墙日志
- 工控审计系统记录

## 六、渗透测试报告撰写

### 6.1 报告结构

工控渗透测试报告应包含以下部分：

```
1. 项目概述
   - 测试背景和目标
   - 测试范围和边界
   - 测试时间和人员
   - 授权说明

2. 测试依据
   - 相关标准（等保2.0、IEC 62443等）
   - 测试方案
   - 甲方提供的资料

3. 测试方法
   - 测试流程
   - 使用的工具
   - 测试环境说明

4. 资产识别
   - 网络拓扑
   - 设备清单
   - 系统和软件清单

5. 安全风险分析
   - 总体风险评估
   - 风险等级分布
   - 攻击路径分析

6. 漏洞详情
   - 每个漏洞的详细描述
   - 漏洞位置和影响范围
   - 风险等级
   - 验证过程和证据
   - 修复建议

7. 横向移动路径分析
   - 攻击路径图
   - 关键薄弱点
   - 最大可能的攻击场景

8. 安全加固建议
   - 网络架构优化
   - 安全设备部署
   - 主机加固建议
   - 管理改进建议

9. 附录
   - 工具列表
   - 漏洞参考链接
   - 测试日志（脱敏）
```

### 6.2 漏洞描述规范

每个漏洞应包含：

```
【漏洞名称】 简洁明确的漏洞名称
【风险等级】 严重/高危/中危/低危
【影响范围】 受影响的设备、系统、区域
【漏洞描述】 漏洞的详细说明
【技术原理】 漏洞产生的原因和利用原理
【验证过程】 如何验证该漏洞（步骤）
【实际影响】 对生产和安全的实际影响
【修复建议】 具体的修复或缓解措施
【参考信息】 CVE编号、厂商公告等
```

### 6.3 风险等级评估

工控系统风险评估需要特别考虑生产影响：

| 风险等级 | 判定标准 | 示例 |
|----------|---------|------|
| **严重** | 可直接导致生产中断或物理破坏 | PLC 未授权控制、SIS 漏洞 |
| **高危** | 可严重影响生产或造成重大损失 | HMI 完全可控、关键数据泄露 |
| **中危** | 可能影响生产或有一定影响 | 信息泄露、弱口令 |
| **低危** | 影响较小，需结合其他漏洞 | 版本信息泄露、banner 信息 |

**风险评估因素：**
- 资产重要性（该设备/系统在生产中的作用）
- 攻击难度（利用该漏洞的技术门槛）
- 影响范围（影响单个设备还是整个生产线）
- 生产影响（是否导致停机、次品、安全事故）
- 修复难度（是否容易修复）

### 6.4 报告注意事项

1. **实事求是**：不夸大也不隐瞒
2. **证据充分**：每个漏洞都要有验证证据
3. **保护敏感信息**：对敏感生产信息进行脱敏
4. **突出重点**：高风险问题重点说明
5. **建议可行**：加固建议要考虑工控实际情况
6. **保密要求**：报告内容严格保密

## 八、实践建议与注意事项

### 8.1 学习建议

1. **先学习工控基础知识**：了解 PLC、SCADA、工业协议
2. **从协议分析入手**：掌握 Wireshark 抓包和协议分析
3. **搭建实验环境**：使用模拟器和虚拟环境练习
4. **学习编程**：Python + Scapy，自己写测试脚本
5. **关注漏洞情报**：跟踪 ICS-CERT、CNVD 等漏洞公告

### 8.2 实验环境搭建

**低成本方案：**
- 虚拟机 + 各种模拟器
- Modbus 模拟器（Modbus Slave）
- OPC UA 模拟器
- 树莓派 + 开源 PLC 软件

**中等成本方案：**
- 二手入门级 PLC（S7-200 SMART、FX3U 等）
- 工业交换机
- 真实 HMI 软件

### 8.3 道德与法律红线

**绝对不能做的事：**
- 未经授权扫描任何工控系统
- 未经授权访问任何工控设备
- 对生产系统进行任何测试
- 发布或传播工控漏洞利用代码
- 利用工控漏洞进行非法活动

**正确的做法：**
- 在授权范围内进行测试
- 及时向厂商报告漏洞
- 遵守负责任披露原则
- 只用于防护目的
