# IoT 渗透测试指南

> 本文档系统介绍物联网渗透测试的方法论、技术和工具，涵盖硬件攻击、固件分析、协议攻击、Web/API 攻击、移动 APP 分析和云平台攻击面。

---

## 一、IoT 渗透测试方法论

### 1.1 IoT 渗透测试的特殊性

物联网渗透测试与传统 Web 渗透测试有显著区别：

| 维度 | 传统 Web 渗透 | IoT 渗透测试 |
|------|-------------|-------------|
| **测试对象** | Web 应用/服务器 | 设备+固件+协议+云+APP |
| **技术栈** | Web 技术为主 | 硬件+嵌入式+网络+Web |
| **物理接触** | 通常不需要 | 通常需要物理接触设备 |
| **工具集** | Burp、sqlmap 等 | 硬件工具+逆向工具+协议工具 |
| **架构** | B/S 或 C/S | 端-网-云三层架构 |
| **漏洞类型** | Web 漏洞为主 | 固件漏洞+协议漏洞+Web 漏洞+硬件漏洞 |
| **修复难度** | 相对容易 | 困难（固件更新周期长） |

### 1.2 IoT 安全测试模型

OWASP IoT Security Testing Guide 提出的测试模型：

```
┌──────────────────────────────────────────────────────────┐
│                    IoT 攻击面总览                         │

│ 硬件层 │ 软件层 │ 协议层 │ 服务层 │ 客户端 │ 平台层     │
└────────┴────────┴────────┴────────┴────────┴────────────┘
```

### 1.4 渗透测试前的准备

#### 1.4.1 法律授权

**必须获得的授权**：
- 书面授权文件
- 明确的测试范围（哪些设备、哪些IP、哪些功能）
- 明确的时间范围
- 应急联系方式

**注意事项**：
- 严禁测试未授权的设备和网络
- 测试过程中避免影响正常业务
- 发现严重漏洞及时通报

#### 1.4.2 工具准备

**硬件工具**：
- USB 转 TTL 串口适配器
- J-Link / ST-Link 调试器
- CH341A 编程器 + 测试夹
- 万用表
- 烙铁/热风枪
- 逻辑分析仪
- Ubertooth One（BLE 抓包）
- 树莓派（测试平台）

**软件工具**：
- binwalk、firmware-mod-kit
- IDA Pro / Ghidra
- QEMU
- Wireshark
- Burp Suite
- Metasploit
- Nmap
- 串口终端（SecureCRT、minicom、screen）

#### 1.4.3 设备准备

- 至少 2 台同款设备（一台拆毁分析，一台保持完整）
- 设备说明书和技术文档（如有）
- 配套的移动 APP
- 云平台账号

## 二、硬件攻击

### 2.1 硬件攻击概述

硬件攻击是 IoT 渗透测试的特色，通过物理接触设备获取固件、提取密钥或绕过安全机制。

**硬件攻击的层次**：
```
┌─────────────────────────────────────┐
│  软件攻击（难度低，破坏性小）         │
│  通过网络/接口利用软件漏洞           │
├─────────────────────────────────────┤
│  接口攻击（难度中，破坏性小）         │
│  UART / JTAG / SWD / USB            │
├─────────────────────────────────────┤
│  芯片攻击（难度高，破坏性中）         │
│  Flash 读取 / 侧信道 / 故障注入      │
├─────────────────────────────────────┤
│  硅级攻击（难度极高，破坏性大）       │
│  芯片逆向 / 物理攻击                 │
└─────────────────────────────────────┘
```

### 2.2 UART 串口攻击

#### 2.2.1 UART 简介

UART（Universal Asynchronous Receiver/Transmitter）是通用异步收发传输器，是嵌入式设备最常见的调试接口。

**信号线**：
- **TX**：发送（Transmit）
- **RX**：接收（Receive）
- **GND**：地线（Ground）
- **VCC**：电源（可选，通常不接）

**常见参数**：
- 波特率：9600、19200、38400、57600、115200（最常见）
- 数据位：8
- 停止位：1
- 校验位：无

#### 2.2.2 寻找串口

**方法 1：目视查找**
- 寻找板上的排针或测试点
- 通常标有 TX、RX、GND、VCC 字样
- 常见位置：主板边缘、芯片附近

**方法 2：万用表测量**
1. 找 GND：用通断档测量，与屏蔽罩/USB 外壳导通的就是 GND
2. 找 VCC：上电后测量电压，3.3V 或 5V 的是 VCC
3. 找 TX：上电瞬间有电压波动的通常是 TX
4. 找 RX：电压稳定的通常是 RX

**方法 3：逻辑分析仪**
- 使用逻辑分析仪同时测量多个测试点
- 分析串口信号确定 TX/RX 和波特率

#### 2.2.3 串口连接步骤

```
设备端                    USB 转 TTL 适配器
┌───────┐                 ┌──────────────┐
│ GND   │─────────────────│ GND          │
│ TX    │─────────────────│ RX           │  ← 注意交叉连接
│ RX    │─────────────────│ TX           │
│ VCC   │     (不接)      │ 3.3V/5V      │
└───────┘                 └──────────────┘
```

**重要提醒**：
- TX 和 RX 要交叉连接（设备 TX → 适配器 RX，设备 RX → 适配器 TX）
- GND 必须连接（共地）
- VCC 通常不接（设备自身供电）
- 确认电压（3.3V 还是 5V），避免烧坏设备

#### 2.2.4 串口终端软件

| 系统 | 软件 | 说明 |
|------|------|------|
| Linux | minicom / screen / picocom | 命令行工具 |
| Windows | SecureCRT / Putty / TeraTerm | 图形化工具 |
| 跨平台 | minicom / PuTTY | |

**minicom 使用示例**：
```bash
# 安装
sudo apt install minicom

# 配置（设置串口、波特率、硬件流控关闭）
sudo minicom -s

# 直接连接
sudo minicom -D /dev/ttyUSB0 -b 115200
```

**screen 使用示例**：
```bash
sudo screen /dev/ttyUSB0 115200
# 退出：Ctrl+A, 然后按 K
```

#### 2.2.5 波特率识别

如果不知道波特率，可以尝试常见值或使用工具识别。

**常见波特率**（从高到低尝试）：
115200 → 57600 → 38400 → 19200 → 9600

**识别工具**：
- **baudrate.py**：自动识别串口波特率
- **sigrok/PulseView**：逻辑分析仪软件
- 手动观察乱码程度判断

#### 2.2.6 串口攻击面

**1. 启动日志信息泄露**

设备启动时会输出大量调试信息：
- 系统版本
- 内存布局
- Flash 分区信息
- 启动参数
- 硬件信息
- 调试信息

**分析价值**：
- 了解设备架构和系统
- 获取内存地址用于漏洞利用
- 发现调试功能和后门

**2. bootloader 命令行**

很多设备的 bootloader（如 U-Boot）可以通过串口中断启动，进入命令行。

**U-Boot 命令行能力**：
- 查看和修改环境变量
- 读取/写入 Flash
- 加载/执行代码
- 修改启动参数
- 绕过固件验证

**常见中断方式**：
- 按任意键（最常见）
- 按特定键（空格键、回车键、ESC）
- 发送特定字符序列

**典型场景**：
```
U-Boot 2013.07 (Sep 15 2020 - 14:38:26)

DRAM:  64 MiB
Flash: 16 MiB
Net:   ag7240_enet_initialize...
Hit any key to stop autoboot:  3  ← 倒计时期间按任意键中断

ar7240>
ar7240> help        ← 查看命令列表
ar7240> printenv    ← 查看环境变量
ar7240> sf probe    ← 探测 SPI Flash
ar7240> sf read 0x80000000 0x0 0x100000  ← 读取 Flash 到内存
```

**3. 登录 Shell**

启动完成后可能提供 shell 登录：
- 尝试默认用户名密码
- 利用漏洞绕过认证
- 通过 bootloader 修改密码

**4. 命令注入**

某些管理功能的命令行界面可能存在命令注入漏洞。

### 2.3 JTAG/SWD 攻击

#### 2.3.1 JTAG 简介

JTAG（Joint Test Action Group）是一种标准的硬件调试接口，主要用于芯片测试和调试。

**JTAG 引脚**：
| 引脚 | 名称 | 方向 | 说明 |
|------|------|------|------|
| TCK | Test Clock | 输入 | 测试时钟 |
| TMS | Test Mode Select | 输入 | 测试模式选择 |
| TDI | Test Data In | 输入 | 测试数据输入 |
| TDO | Test Data Out | 输出 | 测试数据输出 |
| TRST | Test Reset | 输入 | 测试复位（可选） |
| GND | Ground | - | 地 |
| VCC | Power | - | 电源（可选） |

#### 2.3.2 SWD 简介

SWD（Serial Wire Debug）是 ARM 推出的调试接口，使用更少的引脚。

**SWD 引脚**：
| 引脚 | 名称 | 说明 |
|------|------|------|
| SWCLK | Serial Wire Clock | 时钟信号 |
| SWDIO | Serial Wire Data I/O | 数据输入输出 |
| GND | Ground | 地 |
| VCC | Power | 电源（可选） |

#### 2.3.3 寻找 JTAG/SWD 接口

**方法**：
1. 目视查找：找标有 JTAG、SWD、TCK、TMS 等字样的排针或测试点
2. 查找芯片 datasheet：根据芯片型号确定 JTAG 引脚位置
3. JTAGulator：专用 JTAG 引脚识别工具

#### 2.3.4 JTAG 调试工具

| 工具 | 价格 | 说明 |
|------|------|------|
| J-Link | 较贵 | 功能最强大，支持多种芯片 |
| ST-Link | 便宜 | 主要支持 STM32 等 ARM 芯片 |
| FT2232H | 中等 | 通用 USB 转 JTAG 方案 |
| Bus Blaster | 中等 | 开源 JTAG 调试器 |
| Raspberry Pi | 便宜 | 可用树莓派模拟 JTAG |

#### 2.3.5 OpenOCD 使用

OpenOCD（Open On-Chip Debugger）是开源的片上调试器。

**安装**：
```bash
sudo apt install openocd
```

**配置文件示例**（STM32 + ST-Link）：
```tcl
# stm32.cfg
source [find interface/stlink.cfg]
source [find target/stm32f4x.cfg]
```

**启动 OpenOCD**：
```bash
sudo openocd -f stm32.cfg
```

**连接并读取 Flash**：
```bash
# 在另一个终端连接
telnet localhost 4444

> halt                    # 暂停 CPU
> flash banks             # 查看 Flash 信息
> flash read_bank 0 firmware.bin 0 0x100000  # 读取 Flash
> resume                  # 恢复运行
> exit
```

**GDB 调试**：
```bash
arm-none-eabi-gdb
(gdb) target remote :3333
(gdb) file firmware.elf
(gdb) break main
(gdb) continue
```

#### 2.3.6 JTAG 锁定与解锁

很多设备会锁定 JTAG 接口：
- STM32：读保护（RDP Level 1/2）
- NXP：CRP 级别
- ESP32：Secure Boot + Flash Encryption

**绕过方法**（因芯片而异）：
- 故障注入（电压毛刺、时钟毛刺）
- 利用特定芯片的漏洞
- 物理攻击（拆除芯片读取）
- 某些情况下可以通过 UART 解锁

### 2.4 SPI Flash 读取

#### 2.4.1 SPI Flash 简介

SPI Flash 是 IoT 设备中最常见的固件存储芯片，通过 SPI 接口通信。

**常见封装**：
- SOIC-8：8 引脚小外形封装（最常见）
- SOP-8：同上
- WSON-8：8 引脚无引脚封装

**引脚定义（SOIC-8）**：
```
   ┌──────────┐
CS │1     8│ VCC
 SO │2     7│ HOLD
 WP │3     6│ SCK
GND │4     5│ SI
   └──────────┘

CS: Chip Select（片选）
SO: Serial Output（串行输出，也叫 MISO）
WP: Write Protect（写保护）
GND: Ground（地）
SI: Serial Input（串行输入，也叫 MOSI）
SCK: Serial Clock（串行时钟）
HOLD: 挂起
VCC: 电源（通常 3.3V）
```

#### 2.4.2 读取方法

**方法 1：拆芯片 + 编程器（最可靠）**
1. 使用热风枪吹下 Flash 芯片
2. 将芯片放入编程器插座
3. 使用编程器软件读取

**方法 2：在线读取（测试夹）**
1. 使用测试夹夹在芯片上（不用拆）
2. 连接到编程器
3. 读取 Flash 内容
4. 注意：需要断开设备电源或确保芯片不被主控干扰

**方法 3：通过其他接口**
- U-boot 命令行读取
- JTAG 读取
- 固件漏洞读取

#### 2.4.3 CH341A 编程器使用

CH341A 是最廉价的 SPI Flash 编程器。

**软件工具**：
- **Windows**：CH341A Programmer、NeoProgrammer
- **Linux**：flashrom、ch341prog

**Linux 下使用 flashrom**：
```bash
# 安装
sudo apt install flashrom

# 检测芯片
sudo flashrom -p ch341a_spi

# 读取固件
sudo flashrom -p ch341a_spi -r firmware.bin

# 写入固件
sudo flashrom -p ch341a_spi -w firmware_modified.bin

# 验证
sudo flashrom -p ch341a_spi -v firmware.bin
```

### 2.5 其他硬件攻击技术

#### 2.5.1 侧信道攻击 (Side-Channel Attack)

通过分析设备的物理特性（功耗、电磁辐射、运行时间等）来获取密钥等敏感信息。

**常见类型**：
- **功耗分析 (Power Analysis)**：分析设备运行时的电流变化
  - 简单功耗分析 (SPA)
  - 差分功耗分析 (DPA)
- **电磁分析 (EM Analysis)**：分析设备的电磁辐射
- **时间分析 (Timing Analysis)**：分析操作的执行时间

**所需设备**：
- 示波器（高采样率）
- 电流探头/电磁探头
- 低噪声放大器
- 稳定的电源

#### 2.5.2 故障注入攻击 (Fault Injection)

通过向设备注入故障（电压毛刺、时钟毛刺、激光等），使芯片产生错误行为，从而绕过安全机制。

**常见类型**：
- **电压毛刺 (Voltage Glitching)**：在电源上产生短暂的电压脉冲
- **时钟毛刺 (Clock Glitching)**：在时钟上产生异常脉冲
- **激光故障注入**：用激光照射芯片特定区域
- **电磁故障注入**：用电磁脉冲干扰芯片

**攻击效果**：
- 跳过安全检查（如密码验证）
- 泄露敏感数据
- 绕过安全启动
- 解锁调试接口

#### 2.5.3 PCB 逆向

通过分析电路板的走线和元件，理解硬件设计和连接关系。

**方法**：
- 目视观察（放大镜、显微镜）
- 万用表通断测试
- 拍照后用软件追踪走线
- 去层分析（多层板，破坏性）

## 三、固件分析

固件分析是 IoT 渗透测试的核心环节，详细内容请参考《IoT固件安全.md》。

### 3.1 固件获取（渗透测试视角）

在渗透测试中，获取固件的优先级顺序：

1. **官方下载**：最简单，优先尝试
2. **OTA 抓包**：通过监听设备更新获取
3. **UART 读取**：通过串口从 bootloader 读取
4. **JTAG/SWD 读取**：通过调试接口读取
5. **拆芯片读取**：最可靠但有破坏性

### 3.2 固件分析流程（渗透测试）

```
固件获取
    │
    ▼
固件解包（binwalk / FMK）
    │
    ▼
信息收集 ────────────────────────┐
    │                            │
    ├─> 用户/密码/密钥           │
    ├─> 服务和端口               │
    ├─> Web 界面源码             │
    └─> 配置文件                 │
                                 │
    ▼                            │
二进制分析  <────────────────────┘
    │
    ├─> 危险函数查找
    ├─> 认证逻辑分析
    ├─> 命令注入查找
    └─> 缓冲区溢出查找
    │
    ▼
漏洞验证（QEMU / 真实设备）
    │
    ▼
漏洞利用
```

### 3.3 重点关注的漏洞类型

1. **硬编码凭证**：最快的突破口
2. **命令注入**：Web 接口和管理功能中常见
3. **认证绕过**：直接获取设备控制权
4. **缓冲区溢出**：可能实现代码执行
5. **后门账户**：厂商预留的调试账户

## 四、网络协议攻击

### 4.1 网络服务发现

#### 4.1.1 端口扫描

使用 Nmap 扫描设备开放的端口和服务。

```bash
# 全端口扫描
nmap -p- 192.168.1.100

# 服务识别和版本探测
nmap -sV -p- 192.168.1.100

# 脚本扫描（安全相关）
nmap -sV --script=safe 192.168.1.100

# 常见 IoT 端口扫描
nmap -p 21,22,23,80,443,1883,5683,8080,8443,9090 192.168.1.100
```

#### 4.1.2 常见 IoT 端口和服务

| 端口 | 协议/服务 | 说明 |
|------|----------|------|
| 21 | FTP | 文件传输 |
| 22 | SSH | 安全登录 |
| 23 | Telnet | 远程登录（不安全，常见弱口令） |
| 80 | HTTP | Web 管理界面 |
| 443 | HTTPS | 加密 Web 管理 |
| 1883 | MQTT | 消息队列遥测传输 |
| 5683 | CoAP | 受限应用协议 |
| 502 | Modbus | 工业控制协议 |

## 五、Web/API 攻击

### 5.1 IoT 设备 Web 界面

很多 IoT 设备提供 Web 管理界面，是重要的攻击面。

#### 5.1.1 常见 Web 漏洞

| 漏洞类型 | IoT 场景示例 |
|---------|-------------|
| **弱口令** | 管理后台使用默认密码（admin/admin） |
| **命令注入** | Ping/Traceoute 功能将用户输入拼接到系统命令 |
| **身份认证绕过** | 直接访问管理页面，无需登录 |
| **CSRF** | 没有 CSRF 防护，可诱导管理员执行操作 |
| **XSS** | 设备名称等字段未过滤，可注入脚本 |
| **信息泄露** | 错误页面泄露敏感信息 |
| **未授权 API 访问** | API 接口不需要认证即可调用 |
| **固件上传漏洞** | 固件上传功能可上传恶意固件 |

#### 5.1.2 命令注入测试

IoT 设备的 Web 界面经常有命令注入漏洞，因为很多功能通过调用系统命令实现。

**常见注入点**：
- Ping / Traceroute 功能（IP 地址参数）
- 系统诊断功能
- 文件上传（文件名注入）
- 设备名称/位置等配置项
- NTP 服务器配置
- DDNS 配置

**测试方法**：
```
# 测试命令分隔符
127.0.0.1; id
127.0.0.1| id
127.0.0.1&& id
127.0.0.1 || id

# 测试反引号
`id`
$(id)

# 测试重定向（验证命令执行）
127.0.0.1; cat /etc/passwd > /www/passwd.txt
# 然后访问 http://device/passwd.txt
```

**真实案例**：某品牌路由器的 ping 功能存在命令注入漏洞，通过在 IP 地址中注入 `;命令` 可以执行任意系统命令，获取 root 权限。

### 5.2 云 API 攻击

IoT 设备通常连接到云平台，云 API 是重要的攻击面。

#### 5.2.1 API 发现

**发现 API 的方法**：
1. 抓包分析：在设备和 APP 通信时抓包
2. APP 逆向：反编译移动 APP，查找 API 地址和密钥
3. 固件分析：从固件中提取 API 相关信息
4. 文档泄露：查找公开的 API 文档

#### 5.2.2 常见 API 安全问题

| 问题类型 | 说明 | 风险 |
|---------|------|------|
| **硬编码 API Key** | API 密钥硬编码在 APP/固件中 | 密钥泄露，可冒充设备 |
| **弱认证** | API 认证机制不完善 | 未授权访问 |
| **越权访问** | 可访问其他用户的设备和数据 | 数据泄露、设备控制 |
| **注入攻击** | API 参数存在注入漏洞 | 数据泄露、代码执行 |
| **无速率限制** | API 没有调用频率限制 | 暴力破解、枚举 |
| **敏感数据泄露** | API 返回过多敏感信息 | 信息泄露 |

#### 5.2.3 越权访问测试

**水平越权**：访问同级别其他用户的资源
```
正常：/api/device?device_id=12345（自己的设备）
测试：/api/device?device_id=12346（别人的设备）
```

**垂直越权**：访问高级别权限的功能
```
普通用户：/api/user/info
测试：/api/admin/users
```

**IDOR（不安全的直接对象引用）**：
- 修改请求中的设备 ID
- 修改用户 ID
- 修改资源 ID

### 5.3 移动 APP 关联分析

IoT 设备通常配有移动 APP，通过分析 APP 可以发现大量安全问题。

#### 5.3.1 APP 分析内容

1. **API 接口发现**：反编译 APP，提取 API 地址和参数
2. **硬编码凭证**：查找硬编码的 API Key、密钥、密码
3. **认证机制分析**：分析 APP 的认证流程
4. **本地数据存储**：检查本地存储的敏感数据
5. **通信安全**：检查是否使用 HTTPS、证书验证
6. **组件安全**：检查 Activity、Service 等组件是否可导出

#### 5.3.2 分析工具

| 工具 | 用途 |
|------|------|
| apktool | APK 反编译 |
| jadx | DEX 反编译为 Java |
| Frida | 动态插桩、Hook |
| MobSF | 移动 APP 安全分析框架 |
| Burp Suite | 抓包分析 API 通信 |
| drozer | Android 安全测试框架 |

#### 5.3.3 分析步骤

```
1. APK 反编译
   ├─> 提取资源文件
   ├─> 反编译 smali/dex
   └─> 查找硬编码字符串

2. API 分析
   ├─> 配置 Burp 抓包
   ├─> 分析 API 接口
   ├─> 测试认证和授权
   └─> 测试越权访问

3. 动态分析
   ├─> Frida Hook 关键函数
   ├─> 绕过证书固定
   └─> 分析运行时行为
```

### 6.2 漏洞详情模板

每个漏洞应包含以下信息：

```
【漏洞名称】硬编码管理员密码

【漏洞编号】VULN-2024-001

【严重程度】高危
  严重程度分级：
  - 高危：可直接获取设备控制权，造成严重影响
  - 中危：可获取敏感信息或部分控制权限
  - 低危：信息泄露或配置不当，影响较小
  - 信息：一般性信息，不构成直接威胁

【漏洞描述】
设备固件中硬编码了管理员账户的密码，攻击者可通过分析固件或利用
其他漏洞获取该密码，从而获得设备的完全控制权。

【影响范围】
设备型号：XXX 智能路由器
固件版本：V1.2.3 及之前版本

【复现步骤】
1. 从厂商官网下载固件文件 firmware_v1.2.3.bin
2. 使用 binwalk 提取文件系统：binwalk -e firmware_v1.2.3.bin
3. 查看 /etc/shadow 文件：cat _firmware.bin.extracted/squashfs-root/etc/shadow
4. 发现 admin 用户的密码哈希
5. 使用 hashcat 破解，得到密码为 "admin12345"
6. 使用该密码登录设备管理后台，验证成功

【PoC 代码/截图】
（此处附上关键截图或代码）

【风险评估】
- 技术影响：完全控制设备
- 业务影响：设备被劫持，用户隐私泄露，可作为僵尸网络节点
- 可利用性：容易，只需获取固件即可

【修复建议】
1. 移除硬编码密码，使用随机生成的唯一密码
2. 首次启动时强制用户修改密码
3. 使用强密码策略
4. 限制登录失败次数，防止暴力破解

【参考资料】
- CWE-798: Use of Hard-coded Credentials
- OWASP IoT Top 10 I1: Weak, Guessable, or Hardcoded Passwords
```

### 6.3 修复建议优先级

| 优先级 | 修复时间要求 | 适用漏洞 |
|-------|------------|---------|
| **紧急 (P0)** | 立即修复（72 小时内） | 可被远程利用的高危漏洞 |
| **高 (P1)** | 1 周内修复 | 有一定利用条件的高危漏洞 |
| **中 (P2)** | 1 个月内修复 | 中危漏洞 |
| **低 (P3)** | 下一个版本修复 | 低危漏洞和优化建议 |
