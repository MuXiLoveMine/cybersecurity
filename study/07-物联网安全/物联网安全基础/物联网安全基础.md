# 物联网安全基础

> 本文档系统介绍物联网安全的基础知识，包括架构、设备类型、安全威胁、安全标准和著名安全事件。

---

## 一、IoT 概述与架构

### 1.1 物联网定义

物联网（Internet of Things，IoT）是通过各种信息传感器、射频识别技术、全球定位系统、红外感应器、激光扫描器等装置与技术，实时采集任何需要监控、连接、互动的物体或过程，采集其声、光、热、电、力学、化学、生物、位置等各种需要的信息，通过各类可能的网络接入，实现物与物、物与人的泛在连接，实现对物品和过程的智能化感知、识别和管理。

**核心特征**：
- **全面感知**：利用 RFID、传感器、二维码等随时随地获取物体信息
- **可靠传输**：通过各种网络融合，实时准确地传递信息
- **智能处理**：利用云计算、大数据等技术对海量数据进行分析处理
- **智能决策**：基于分析结果实现智能控制和决策

### 1.2 物联网四层架构

物联网通常采用四层架构模型，各层功能和安全挑战各不相同。

```
┌─────────────────────────────────────────────────┐
│                   应用层 (Application)          │
│  智能家居 / 智慧城市 / 工业物联网 / 智慧医疗等  │
├─────────────────────────────────────────────────┤
│                   平台层 (Platform)             │
│  设备管理 / 数据处理 / 应用支撑 / API服务      │
├─────────────────────────────────────────────────┤
│                   网络层 (Network)              │
│  互联网 / 移动通信 / LoRa / NB-IoT / WiFi等    │
├─────────────────────────────────────────────────┤
│                   感知层 (Perception)           │
│  传感器 / 执行器 / RFID / 智能终端 / 摄像头    │
└─────────────────────────────────────────────────┘
```

#### 1.2.1 感知层

**功能**：负责信息采集和物体识别，是物联网的底层基础。

**主要组成**：
- **传感器**：温度、湿度、光照、压力、加速度、气体等各类传感器
- **执行器**：继电器、电机、阀门、灯光控制等
- **RFID 设备**：RFID 标签和读写器
- **智能终端**：智能门锁、智能灯泡、智能摄像头等
- **可穿戴设备**：智能手表、手环、健康监测设备
- **工业设备**：PLC、RTU、传感器节点等

**安全挑战**：
| 挑战类型 | 具体描述 |
|---------|---------|
| 资源受限 | CPU 算力低、内存小、存储空间有限，难以部署复杂安全机制 |
| 低功耗 | 电池供电，安全算法不能消耗过多电量 |
| 物理暴露 | 设备部署在开放环境中，易被物理接触和篡改 |
| 数量庞大 | 设备数量巨大，难以逐一管理和更新 |
| 默认配置 | 大量设备使用默认口令，出厂配置不安全 |

**案例**：某品牌智能门锁存在物理攻击面，攻击者可通过拆解设备读取 Flash 芯片中的固件，获取加密密钥。

#### 1.2.2 网络层

**功能**：负责感知层数据的传输和通信，连接感知层和平台层。

**主要技术**：
- **短距离无线通信**：WiFi、蓝牙/BLE、ZigBee、Z-Wave、NFC
- **低功耗广域网 (LPWAN)**：LoRaWAN、NB-IoT、Sigfox、eMTC
- **有线通信**：以太网、电力线通信 (PLC)
- **移动通信**：4G/5G、Cat-M1
- **边缘网络**：边缘计算网关、雾计算节点

**安全挑战**：
| 挑战类型 | 具体描述 |
|---------|---------|
| 协议多样性 | 多种通信协议并存，安全机制不统一 |
| 异构网络融合 | 不同网络之间的边界安全和协议转换安全 |
| 传输安全 | 数据在传输过程中被窃听、篡改的风险 |
| 身份认证 | 设备身份认证和接入控制困难 |
| 网络拓扑动态 | 设备移动、休眠导致网络拓扑频繁变化 |

**案例**：BLE 设备在配对过程中可能遭受中间人攻击，攻击者通过嗅探配对过程中的密钥交换信息，可解密后续通信内容。

#### 1.2.3 平台层

**功能**：提供设备接入、数据存储、数据分析、应用开发等核心服务能力。

**主要功能模块**：
- **设备管理**：设备注册、认证、配置、监控、升级
- **数据管理**：数据采集、存储、清洗、分析
- **规则引擎**：基于规则的设备联动和告警
- **API 服务**：RESTful API、MQTT API 等对外接口
- **用户管理**：用户认证、权限管理、租户管理
- **消息服务**：消息路由、消息队列、通知推送

**安全挑战**：
| 挑战类型 | 具体描述 |
|---------|---------|
| 身份认证 | 海量设备的身份认证和管理 |
| 访问控制 | 细粒度的访问控制和权限管理 |
| API 安全 | API 接口的认证、授权、防滥用 |
| 数据安全 | 海量数据的存储安全和隐私保护 |
| 租户隔离 | 多租户环境下的数据和资源隔离 |
| 固件安全 | 固件存储、分发和升级的安全 |

**案例**：某物联网云平台存在 API 越权访问漏洞，攻击者通过修改请求中的设备 ID 参数，可以控制其他用户的设备。

#### 1.2.4 应用层

**功能**：面向最终用户提供各类物联网应用服务。

**典型应用领域**：
- **智能家居**：智能音箱、智能照明、智能安防、智能家电
- **智慧城市**：智能交通、智能路灯、环境监测、智慧停车
- **工业物联网**：智能制造、设备监控、预测性维护
- **智慧医疗**：远程监护、健康管理、医疗设备联网
- **智慧农业**：精准农业、温室控制、畜牧追踪
- **智能物流**：货物追踪、仓储管理、冷链监控

**安全挑战**：
| 挑战类型 | 具体描述 |
|---------|---------|
| 业务逻辑安全 | 业务流程中的安全漏洞和逻辑缺陷 |
| 用户隐私 | 个人敏感信息和位置信息的保护 |
| 数据安全 | 用户数据的存储、传输和使用安全 |
| 应用漏洞 | Web/APP 端的安全漏洞 |
| 身份冒充 | 设备身份伪造和用户身份冒充 |

**案例**：某智能摄像头 APP 存在未授权访问漏洞，攻击者可以查看任意摄像头的实时画面。

## 二、常见 IoT 设备类型

### 2.1 消费级物联网设备

#### 2.1.1 智能家居设备

| 设备类型 | 典型产品 | 通信方式 | 常见安全问题 |
|---------|---------|---------|-------------|
| 智能音箱 | Amazon Echo、Google Home、小爱同学 | WiFi、蓝牙 | 语音指令窃听、隐私泄露、未授权访问 |
| 智能摄像头 | 海康威视、小米摄像头、Ring | WiFi、有线 | 弱口令、未授权访问、视频泄露 |
| 智能门锁 | 凯迪仕、德施曼、August | 蓝牙、WiFi、ZigBee | 物理攻击、蓝牙嗅探、默认密码 |
| 智能灯泡 | Philips Hue、Yeelight | ZigBee、WiFi、蓝牙 | 协议漏洞、未授权控制 |
| 智能插座 | 小米智能插座、TP-Link | WiFi、ZigBee | 弱口令、命令注入 |
| 智能路由器 | 小米路由器、TP-Link | WiFi、有线 | 固件漏洞、弱口令、后门 |
| 智能电视 | 小米电视、三星智能电视 | WiFi、蓝牙 | 恶意应用、隐私窃听 |
| 智能冰箱/洗衣机 | 各品牌智能家电 | WiFi | 弱口令、未授权访问 |

**典型安全案例**：2021 年，某品牌智能摄像头存在严重安全漏洞，超过 15 万台设备可被未授权访问，攻击者可实时查看监控画面并控制摄像头转向。

#### 2.1.2 可穿戴设备

| 设备类型 | 典型产品 | 通信方式 | 常见安全问题 |
|---------|---------|---------|-------------|
| 智能手表 | Apple Watch、小米手表、华为手表 | 蓝牙、WiFi | 数据泄露、配对攻击 |
| 智能手环 | 小米手环、Fitbit | 蓝牙 | 健康数据泄露、欺骗攻击 |
| 健康监测设备 | 智能血压计、血糖仪 | 蓝牙 | 医疗数据泄露、数据篡改 |
| 智能眼镜 | Google Glass、Meta 眼镜 | 蓝牙、WiFi | 隐私窃听、未授权访问 |

**典型安全案例**：研究人员发现多款智能手环在同步健康数据时未加密，攻击者可通过蓝牙嗅探获取用户的心率、睡眠、运动轨迹等敏感信息。

### 2.2 工业物联网设备

#### 2.2.1 工业控制设备

| 设备类型 | 说明 | 通信协议 | 安全风险 |
|---------|------|---------|---------|
| PLC（可编程逻辑控制器） | 工业自动化核心控制设备 | Modbus、S7、Profinet | 未授权访问、协议漏洞 |
| RTU（远程终端单元） | 远程数据采集和控制 | Modbus、DNP3 | 弱口令、未授权访问 |
| 工业传感器 | 温度、压力、流量等传感器 | Modbus、HART | 数据篡改、欺骗攻击 |
| 工业网关 | 协议转换和数据转发 | 多种协议 | 协议转换漏洞、认证绕过 |
| SCADA 系统 | 监控与数据采集系统 | 多种工业协议 | 系统漏洞、未授权访问 |
| 工业机器人 | 智能制造机器人 | 专用协议 | 未授权控制、安全模式绕过 |

**典型安全案例**：2010 年震网病毒（Stuxnet）攻击伊朗核设施，通过感染 PLC 控制离心机转速，造成约 1000 台离心机损坏。这是首个针对工业控制系统的网络武器。

| 智能水表/电表/气表 | 用户家中 | LoRa、NB-IoT | 计量篡改、数据泄露 |

**典型安全案例**：2020 年，美国某城市的智能停车系统被黑客攻击，导致停车计费系统瘫痪，攻击者勒索比特币。

## 三、IoT 安全威胁与挑战

### 3.1 IoT 安全威胁分类

#### 3.1.1 按攻击对象分类

```
                    IoT 安全威胁
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   设备层威胁        网络层威胁        数据层威胁
        │               │               │
   ┌────┴────┐     ┌────┴────┐     ┌────┴────┐
   │         │     │         │     │         │
 硬件攻击  固件攻击 协议攻击  中间人攻击 数据泄露 隐私侵犯
```

#### 3.1.2 按攻击方式分类

| 攻击类别 | 具体攻击方式 | 典型场景 |
|---------|-------------|---------|
| **物理攻击** | 设备拆解、芯片读取、侧信道攻击、故障注入 | 获取固件、提取密钥、绕过安全启动 |
| **固件攻击** | 固件逆向、漏洞利用、固件篡改、恶意固件 | 挖掘漏洞、植入后门、绕过认证 |
| **网络攻击** | 中间人攻击、拒绝服务、重放攻击、欺骗攻击 | 窃听通信、DDoS、身份冒充 |
| **协议攻击** | 协议漏洞利用、模糊测试、恶意数据包 | 协议栈溢出、认证绕过 |
| **应用攻击** | Web 漏洞、API 漏洞、APP 漏洞 | 越权访问、数据泄露、设备控制 |
| **供应链攻击** | 恶意固件植入、硬件木马、组件漏洞 | 出厂后门、供应链投毒 |

### 3.2 主要安全挑战

#### 3.2.1 设备资源受限

**问题描述**：物联网设备通常使用低成本微控制器，计算能力、存储空间和内存都非常有限。

**具体影响**：
- 无法运行复杂的加密算法（如 RSA-2048、AES-256 可能都难以承担）
- 无法安装杀毒软件、防火墙等安全软件
- 无法实现完整的安全协议栈
- 安全更新难以部署（存储空间不足）

**典型数据**：
- 低端 IoT 设备：8 位 MCU，几 KB RAM，几十 KB Flash
- 中端 IoT 设备：32 位 MCU，几十 KB~几 MB RAM，几百 KB~几十 MB Flash
- 高端 IoT 设备：应用处理器，几百 MB RAM，几 GB 存储

#### 3.2.2 设备数量庞大且分布广泛

**问题描述**：物联网设备数量巨大（预计 2025 年全球联网设备超过 300 亿台），分布范围极广。

**具体影响**：
- 设备管理困难，难以逐一进行安全配置
- 漏洞影响范围广，攻击面巨大
- 安全更新难以全面覆盖
- 僵尸网络规模可以极其庞大

**案例**：Mirai 僵尸网络在高峰期控制了超过 60 万台 IoT 设备，发起的 DDoS 攻击流量达到 1.2 Tbps。

#### 3.2.3 设备生命周期长且更新困难

**问题描述**：物联网设备的生命周期通常很长（5~15 年甚至更长），但安全更新机制不完善。

**具体影响**：
- 大量设备存在已知漏洞但无法修复
- 设备厂商可能停止维护（倒闭或产品迭代）
- 用户缺乏安全更新意识
- OTA 升级机制本身可能存在安全问题

**案例**：某品牌路由器 2013 年发布的固件中存在命令注入漏洞，直到 2020 年仍有大量设备未更新，成为 Mirai 僵尸网络的感染目标。

#### 3.2.4 安全标准不统一

**问题描述**：物联网行业缺乏统一的安全标准和规范，各厂商安全水平参差不齐。

**具体影响**：
- 安全设计缺乏指导
- 设备之间互操作时安全难以保证
- 安全评估缺乏统一依据
- 监管困难

#### 3.2.5 物理安全挑战

**问题描述**：物联网设备部署在开放环境中，攻击者可以物理接触设备。

**具体影响**：
- 设备可以被拆解分析
- 固件可以被直接读取
- 调试接口可以被利用
- 侧信道攻击可以实施
- 设备可以被替换或篡改

#### 3.2.6 隐私保护挑战

**问题描述**：物联网设备收集大量个人敏感数据，隐私保护难度大。

**涉及数据**：
- 位置信息（智能手表、车载设备）
- 健康数据（智能手环、医疗设备）
- 家庭活动（智能摄像头、智能音箱）
- 生活习惯（智能家电、智能照明）
- 语音数据（智能音箱）

### 3.3 OWASP IoT Top 10

OWASP（开放式 Web 应用程序安全项目）发布了物联网安全 Top 10，列出了物联网设备最严重的十大安全风险：

| 编号 | 风险名称 | 风险描述 | 严重程度 |
|------|---------|---------|---------|
| **I1** | 弱口令、可猜测的密码 | 使用默认密码、硬编码密码或弱密码 | 极高 |
| **I2** | 不安全的网络服务 | 开放不必要的端口、服务存在漏洞 | 高 |
| **I3** | 不安全的生态系统接口 | 云 API、移动 APP、后端接口不安全 | 高 |
| **I4** | 缺乏安全的更新机制 | 无法更新、更新无签名验证、更新不及时 | 高 |
| **I5** | 使用不安全或过时的组件 | 使用有漏洞的开源组件、旧版固件 | 高 |
| **I6** | 隐私保护不足 | 个人数据未加密、数据过度收集 | 中高 |
| **I7** | 数据传输和保护不足 | 数据传输未加密、数据存储不安全 | 中高 |
| **I8** | 缺乏安全的设备管理 | 无设备身份管理、无远程安全管理 | 中 |
| **I9** | 不安全的默认设置 | 出厂配置不安全、用户难以修改 | 高 |
| **I10** | 缺乏物理加固 | 调试接口暴露、设备易被拆解 | 中 |

## 五、著名 IoT 安全事件

### 5.1 Mirai 僵尸网络

#### 5.1.1 事件概述

**时间**：2016 年首次被发现

**发现者**：安全研究人员 MalwareMustDie

**作者**：Anna-senpai（真实身份：Paras Jha，美国大学生）

**影响规模**：峰值时控制超过 60 万台 IoT 设备

#### 5.1.2 工作原理

**感染流程**：
```
                    ┌─────────────┐
                    │   C&C 服务器 │
                    └──────┬──────┘
                           │ 指令
                    ┌──────▼──────┐
                    │  Mirai 僵尸  │
                    │  （感染设备） │
                    └──────┬──────┘
                           │ 扫描
              ┌────────────┼────────────┐
              ▼            ▼            ▼
          目标设备1     目标设备2     目标设备N
         （Telnet弱口令）
              │
              ▼ 感染成功
         加入僵尸网络
```

**传播机制**：
1. 已感染设备随机扫描公网 IP
2. 尝试使用预设的 60+ 组默认用户名密码组合登录 Telnet 服务
3. 登录成功后，下载并执行 Mirai 恶意代码
4. 新感染设备加入僵尸网络，继续扫描传播

**默认口令示例**：
```
admin / admin
root / root
admin / 12345
root / 123456
user / user
guest / guest
admin / (空密码)
...
```

#### 5.1.3 攻击能力

Mirai 支持多种 DDoS 攻击方式：

| 攻击类型 | 说明 |
|---------|------|
| SYN Flood | TCP SYN 洪水攻击 |
| UDP Flood | UDP 洪水攻击 |
| ACK Flood | TCP ACK 洪水攻击 |
| DNS Flood | DNS 请求洪水攻击 |
| HTTP Flood | HTTP 请求洪水攻击 |
| GRE Flood | GRE 封装洪水攻击 |
| STOMP Flood | STOMP 协议洪水攻击 |

#### 5.1.4 著名攻击事件

**Dyn DNS 攻击（2016 年 10 月 21 日）**：
- 攻击目标：美国 DNS 服务提供商 Dyn
- 攻击流量：峰值 1.2 Tbps
- 影响：Twitter、Netflix、Spotify、Reddit、CNN 等大量网站无法访问
- 持续时间：约一天，分两波攻击
- 攻击来源：Mirai 僵尸网络的数千台 IoT 设备

**攻击流程**：
1. 第一波攻击：上午 7:10 开始，针对 Dyn 的东海岸数据中心
2. 第二波攻击：中午 11:50 再次发起攻击，规模更大
3. 影响范围：美国东海岸首先受影响，随后扩散至全美和欧洲

#### 5.1.5 代码开源与变种

2016 年 10 月，Mirai 源代码被发布在黑客论坛上，导致大量变种出现：

| 变种名称 | 特点 |
|---------|------|
| Mirai | 原始版本，60+ 组口令 |
| Mirai Okiru | 针对 ARC 处理器 |
| Mirai Satori | 增加漏洞利用（如华为 HG532 漏洞） |
| Mirai JenX | 增加新的漏洞利用方式 |
| Gafgyt/BASHLITE | 类似的 IoT 僵尸网络 |
| Mozi | 基于 DHT 网络的 Mirai 变种 |
| Hajime | 类似 Mirai 但带有"善意"目的的蠕虫 |

#### 5.1.6 影响与启示

**安全影响**：
- 首次让公众意识到物联网安全的严重性
- 暴露了大量 IoT 设备使用弱口令的问题
- 推动了行业对 IoT 安全的重视
- 促使厂商加强设备安全配置

**防护措施**：
- 修改默认密码，使用强密码
- 关闭不必要的服务和端口
- 及时更新固件
- 网络边界部署防火墙和入侵检测
- 部署 IoT 安全管理平台

### 5.2 BASHLITE (Gafgyt) 僵尸网络

#### 5.2.1 事件概述

**时间**：2014 年首次被发现

**命名由来**：利用 Bash Shellshock 漏洞（CVE-2014-6271）传播，因此得名 BASHLITE

**影响规模**：峰值感染超过 100 万台设备

#### 5.2.2 传播方式

**初始传播**：利用 Shellshock 漏洞
- 向存在漏洞的设备发送包含恶意命令的 HTTP 请求
- 漏洞触发后下载并执行恶意代码

**后续传播**：Telnet/SSH 弱口令扫描
- 与 Mirai 类似，通过弱口令暴力破解传播
- 使用的默认口令列表略有不同

#### 5.2.3 与 Mirai 的对比

| 特性 | BASHLITE | Mirai |
|------|----------|-------|
| 出现时间 | 2014 年 | 2016 年 |
| 初始传播方式 | Shellshock 漏洞 | Telnet 弱口令 |
| 代码状态 | 未完全开源 | 已开源 |
| 架构支持 | 较少 | 多种架构（ARM、MIPS、x86 等） |
| 攻击方式 | 主要是 DDoS | 多种 DDoS 攻击方式 |
| 隐蔽性 | 相对较高 | 相对较低 |

### 5.3 Reaper (IoT Trojan) 僵尸网络

#### 5.3.1 事件概述

**时间**：2017 年被发现

**发现者**：Check Point 研究人员

**命名**：Reaper（收割者），又称 IoT Trojan

**影响规模**：截至 2017 年 10 月，感染约 200 万台设备

#### 5.3.2 特点与创新

**与 Mirai 的主要区别**：
1. **漏洞利用传播**：不仅使用弱口令，还主动利用已知漏洞传播
2. **更强大的传播能力**：利用漏洞可以快速感染大量设备
3. **模块化设计**：采用模块化架构，功能可扩展
4. **更隐蔽**：隐藏技术更先进

#### 5.3.3 利用的漏洞

Reaper 利用了多个 IoT 设备的已知漏洞：

| 漏洞标识 | 影响设备 | 漏洞类型 |
|---------|---------|---------|
| CVE-2017-17215 | 华为 HG532 路由器 | 远程命令注入 |
| CVE-2014-8361 | 多种路由器 | 命令注入 |
| CVE-2016-6277 | Netgear 路由器 | 命令注入 |
| CVE-2015-2051 | D-Link 路由器 | 命令注入 |
| GoAhead 漏洞 | 多种嵌入式设备 | 远程代码执行 |

#### 5.3.4 攻击能力

Reaper 被认为是 Mirai 的进化版：
- 支持多种 DDoS 攻击方式
- 可能具有更高级的功能（如代理、挖矿等）
- 具备自我更新能力
- C&C 通信更隐蔽

### 5.4 其他著名 IoT 安全事件

#### 5.4.1 智能摄像头大规模入侵（2016）

**事件**：某网站公开了 10 万+ 台网络摄像头的实时画面
- 涉及 250 多个国家和地区的设备
- 包括家庭、商店、办公室、医院等场所
- 原因：弱口令和默认配置不安全

**涉及品牌**：多个品牌的网络摄像头

#### 5.4.2 BrickerBot 僵尸网络（2017）

**特点**：不进行 DDoS 攻击，而是直接破坏设备
- 感染设备后破坏存储、禁用网络接口
- 导致设备变砖（无法使用）
- 被认为是" vigilante "（义警）性质的恶意软件
- 目的可能是减少可用的 IoT 僵尸网络设备

#### 5.4.3 VPNFilter 恶意软件（2018）

**发现者**：Cisco Talos

**影响**：全球至少 50 万台路由器和 NAS 设备被感染

**特点**：
- 模块化设计，功能强大
- 支持数据窃取、流量监听、设备控制
- 具有持久化能力，即使重启也不会清除
- 被认为与国家级黑客组织有关

#### 5.4.4 智能门铃安全漏洞（2019）

**事件**：Ring 智能门铃被曝存在多个安全漏洞
- 攻击者可通过漏洞获取用户 WiFi 密码
- 可未授权查看摄像头画面
- 可与设备进行语音交互
- 涉及数百万用户

#### 5.4.5 特斯拉自动驾驶漏洞（2021）

**事件**：安全研究人员发现特斯拉 Autopilot 存在安全漏洞
- 攻击者可通过特定方式欺骗 Autopilot
- 可导致车辆做出错误决策
- 暴露了自动驾驶系统的安全风险

## 六、IoT 安全防护体系

### 6.1 纵深防御架构

```
┌──────────────────────────────────────────────────────────┐
│                     应用层防护                           │
│  用户认证 / 权限控制 / 数据加密 / 安全审计              │
├──────────────────────────────────────────────────────────┤
│                     平台层防护                           │
│  设备认证 / API 安全 / 数据保护 / 租户隔离              │
├──────────────────────────────────────────────────────────┤
│                     网络层防护                           │
│  加密传输 / 防火墙 / 入侵检测 / 访问控制                │
├──────────────────────────────────────────────────────────┤
│                     设备层防护                           │
│  安全启动 / 固件签名 / 硬件加密 / 安全调试              │
├──────────────────────────────────────────────────────────┤
│                     物理层防护                           │
│  设备加固 / 防拆解 / 调试接口禁用 / 侧信道防护          │
└──────────────────────────────────────────────────────────┘
```

### 6.2 设备安全设计原则

1. **安全默认原则**：设备出厂配置应为最安全状态
2. **最小权限原则**：设备和服务只授予必要的权限
3. **纵深防御原则**：多层安全防护，避免单点失效
4. **隐私保护原则**：数据最小化，保护用户隐私
5. **可更新原则**：设备应支持安全的固件更新
6. **可审计原则**：关键操作应有日志记录
