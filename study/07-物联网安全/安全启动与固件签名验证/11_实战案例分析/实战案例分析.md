# 实战案例分析

### 11.1 Nintendo Switch安全启动绕过

```
案例: Nintendo Switch (Fusee Gelee漏洞)

背景:
- Nintendo Switch使用Nvidia Tegra X1 SoC
- 安全启动基于eFuse存储公钥哈希
- USB恢复模式用于出厂前固件烧录

漏洞:
- USB恢复模式在Boot ROM中
- 恢复模式存在堆栈溢出
- 可以通过USB发送特殊构造的请求
- 覆盖返回地址, 执行任意代码

利用:
1. 通过USB触发恢复模式
2. 发送超长USB控制请求
3. 覆盖栈上的返回地址
4. 执行SMC (Secure Monitor Call) 绕过
5. 加载未签名固件

影响:
- 可运行自制固件(custom firmware)
- 可运行盗版游戏
- 可访问全部硬件功能

教训:
- Boot ROM代码必须经过严格审计
- USB恢复模式应有额外保护
- 栈保护(Stack Canary)必须启用
- 地址空间随机化(ASLR)
```

### 11.2 Android Verified Boot分析

```
Android Verified Boot (AVB):

信任链:
Boot ROM → Bootloader → boot.img → system.img → vendor.img

验证流程:
1. Boot ROM验证Bootloader签名
2. Bootloader验证vbmeta (Verified Boot Metadata)
3. vbmeta包含各分区的哈希和签名
4. 逐个验证boot/system/vendor分区

AVB结构:
┌─────────────────────────────────┐
│  vbmeta分区                      │
│  ├── AvbHeader                  │
│  │   ├── 魔数 "AVB0"            │
│  │   ├── 签名算法                │
│  │   ├── 公钥                   │
│  │   ├── 签名                   │
│  │   └── 描述符列表              │
│  ├── Partition Descriptors      │
│  │   ├── boot分区描述符          │
│  │   │   ├── 分区名             │
│  │   │   ├── 哈希               │
│  │   │   └── 大小               │
│  │   ├── system分区描述符        │
│  │   └── vendor分区描述符        │
│  └── 签名数据                    │
└─────────────────────────────────┘

验证策略:
- enforce: 验证失败则拒绝启动
- logging: 记录失败但仍可启动(调试用)
- 防回滚: 通过eFuse/Trusty实现
```

### 11.3 固件签名密钥管理最佳实践

```
固件签名密钥管理:

1. 密钥生成
   - 使用HSM (硬件安全模块)生成
   - 在离线环境中操作
   - 足够的密钥长度(RSA-3072或ECDSA-P256+)
   - 使用高质量的随机数源

2. 密钥存储
   - 私钥存储在HSM中, 永不导出
   - 使用密钥轮换策略
   - 备份密钥用Shamir秘密共享分片存储
   - 定期审计密钥访问日志

3. 签名流程
   - 构建在隔离网络中进行
   - CI/CD管道通过API调用HSM签名
   - 签名操作需要双人授权
   - 签名记录不可篡改

4. 密钥轮换
   - 定期轮换签名密钥(如每年)
   - 设备支持多密钥验证
   - 旧密钥设置过渡期
   - 密钥撤销机制(dbx)

5. 应急预案
   - 密钥泄露的响应流程
   - OTA紧急更新能力
   - 密钥撤销和设备更新方案
   - 法律和合规通知流程
```
