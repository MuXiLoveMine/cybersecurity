# CoAP协议架构

### 2.1 协议分层

```
┌─────────────────────────────────────────┐
│              应用层 (Application)         │
│   传感器数据 / 设备控制 / 状态查询       │
├─────────────────────────────────────────┤
│          CoAP 请求/响应层                 │
│   GET / POST / PUT / DELETE             │
│   请求-响应 / 通知 / 批量操作            │
├─────────────────────────────────────────┤
│          CoAP 消息层                     │
│   CON / NON / ACK / RST                │
│   消息ID / Token / 重传                 │
├─────────────────────────────────────────┤
│          UDP (传输层)                    │
│   端口: 5683 (明文) / 5684 (DTLS)       │
├─────────────────────────────────────────┤
│          IPv6/IPv4                      │
│   6LoWPAN适配 / 压缩                    │
├─────────────────────────────────────────┤
│          IEEE 802.15.4 / WiFi           │
│          物理层和MAC层                   │
└─────────────────────────────────────────┘
```

### 2.2 消息类型

CoAP定义了四种消息类型：

```
1. CON (Confirmable, 需确认)
   发送方 → 消息 → 接收方
   发送方 ← ACK ← 接收方
   
   特点: 可靠传输，需要接收方确认
   
2. NON (Non-confirmable, 无需确认)
   发送方 → 消息 → 接收方
   （无ACK）
   
   特点: 不可靠传输，适合频繁的传感器数据

3. ACK (Acknowledgement, 确认)
   接收方 → ACK → 发送方
   
   特点: 确认收到CON消息

4. RST (Reset, 重置)
   接收方 → RST → 发送方
   
   特点: 拒绝消息（如未识别的Message ID）
```

### 2.3 请求-响应模型

```
CoAP支持两种响应模式:

模式1: 请求-响应（携带在ACK中）
  Client                Server
    │─── GET /temp ──→│  (CON)
    │←── 2.05 23.5 ───│  (ACK + 响应)
    │                  │

模式2: 分离响应（ACK不携带数据）
  Client                Server
    │─── GET /temp ──→│  (CON)
    │←── (空ACK) ─────│  (ACK)
    │                  │  (处理中...)
    │←── 2.05 23.5 ───│  (CON, 单独响应)
    │─── (ACK) ──────→│  (ACK)

模式2适用于:
- 传感器需要时间采集数据
- 设备从休眠中唤醒
- 数据处理耗时较长
```
