## 一、动态调试概述

### 1.1 静态分析 vs 动态分析

逆向分析通常分为静态分析和动态分析两条路径，两者互补使用才能高效完成逆向任务。

| 维度 | 静态分析 | 动态分析 |
|------|----------|----------|
| 执行状态 | 不运行目标程序 | 实际运行目标程序 |
| 信息来源 | 反汇编/反编译代码 | 运行时寄存器、内存、I/O |
| 优势 | 全局视野、控制流完整 | 真实值、执行路径、解密数据 |
| 劣势 | 难以应对混淆/加密/自修改代码 | 只能看到执行到的路径 |
| 典型工具 | IDA Pro、Ghidra、radare2 | x64dbg、WinDbg、GDB |
| 适用场景 | 理解程序结构、定位关键函数 | 验证推测、提取解密数据、跟踪算法 |

实践中的典型流程：先用静态分析定位关键函数和数据结构，再切换到动态调试验证运行时行为，两者交替迭代。

### 1.2 动态调试在逆向中的角色

动态调试在逆向工程中承担以下核心角色：

- **验证推测**：静态分析推断出的算法逻辑，通过运行时寄存器和内存值加以确认。
- **数据解密**：对运行时解密的字符串、配置或代码，在解密完成后从内存中提取。
- **算法追踪**：跟踪加密/校验算法的每一步运算，还原算法细节。
- **行为分析**：观察程序的外部行为（文件、注册表、网络、进程操作），用于恶意代码分析。
- **漏洞验证**：在漏洞利用开发中，调试 payload 的执行过程，定位偏移和覆盖效果。

### 1.3 调试器分类

调试器按所处的运行级别可分为两类：

**用户态调试器**：运行在 Ring 3，通过操作系统提供的调试接口（Windows 的 Debug API、Linux 的 ptrace）调试目标进程。典型代表：x64dbg、OllyDbg、GDB。

**内核态调试器**：运行在 Ring 0，直接控制 CPU 和物理内存，可调试操作系统内核和驱动程序。典型代表：WinDbg（内核模式）、SoftICE（已淘汰）、windbgkd。

```
Ring 0  ┌─────────────────────────────────┐
        │  内核调试器 WinDbg (kernel mode) │  可调试OS内核、驱动
Ring 3  ├─────────────────────────────────┤
        │  用户态调试器 x64dbg / GDB       │  调试普通应用程序
        └─────────────────────────────────┘
```

用户态调试器依赖操作系统的调试接口：

```c
// Windows 调试API核心
DebugActiveProcess()    // 附加到进程
WaitForDebugEvent()     // 等待调试事件
ContinueDebugEvent()    // 继续执行
ReadProcessMemory()     // 读内存
WriteProcessMemory()    // 写内存
```

```c
// Linux ptrace 接口
ptrace(PTRACE_ATTACH, pid, 0, 0);       // 附加
ptrace(PTRACE_CONT, pid, 0, 0);         // 继续
ptrace(PTRACE_SINGLESTEP, pid, 0, 0);   // 单步
ptrace(PTRACE_PEEKDATA, pid, addr, 0);   // 读内存
```

## 二、Windows动态调试

### 2.1 x64dbg/WinDbg使用

**x64dbg** 是当前最流行的开源 Windows 用户态调试器，是 OllyDbg 的现代继任者，支持 x86/x64。它集成反汇编、内存查看、堆栈跟踪、脚本引擎等功能。

x64dbg 的基本操作流程：

```
1. File → Open / Attach       打开或附加目标程序
2. F9      运行               程序全速执行
3. F8      Step Over          单步步过（不进入函数）
4. F7      Step Into           单步步入（进入函数）
5. F2      Toggle Breakpoint  在当前指令设置/取消断点
6. Ctrl+F9 Execute till Return 运行到函数返回
```

**WinDbg** 既支持用户态也支持内核态调试，是调试 Windows 内核和驱动的首选工具。常用命令：

```
!process 0 0              // 列出所有进程（内核模式）
!devnode 0 1              // 设备树
bp nt!NtCreateFile        // 在内核函数设断点
!process 0 7 /m image.exe // 查看指定进程详细信息
.reload /f                // 强制重新加载符号
!analyze -v               // 自动分析崩溃
dt nt!_EPROCESS           // 显示结构体
```

### 2.2 断点类型

断点是动态调试的核心机制，不同类型的断点适用于不同场景。

**软件断点（INT3 Breakpoint）**：将目标指令首字节替换为 `0xCC`（INT3），CPU 执行到此处触发异常，调试器捕获。

```
原始指令:  55              push ebp
断点设置后:CC              int 3   ← 首字节被替换为0xCC
```

- 优点：数量不限、设置简单。
- 缺点：修改内存，容易被反调试检测（CRC 自校验）。

**硬件断点（Hardware Breakpoint）**：使用 CPU 的调试寄存器（DR0-DR3）设置断点，不修改内存。

```
DR0-DR3: 断点地址（最多4个硬件断点）
DR7:     控制寄存器（断点类型/长度/启用）
```

x64dbg 设置硬件断点：
```
bphws 0x00401000        // 硬件执行断点
bphws 0x00405000,r,1    // 硬件读取断点，长度1字节
bphws 0x00405000,w,4    // 硬件写入断点，长度4字节
```

- 优点：不修改内存、速度快、可设内存访问断点。
- 缺点：最多4个。

**内存断点（Memory Breakpoint）**：设置页面保护属性，访问触发异常。

```
bpm 0x00401000,1,a      // 内存访问断点
bpm 0x00401000,1,w      // 内存写入断点
```

**条件断点**：满足条件才中断，避免频繁断下。

```
bp 0x00401000
bpcnd 0x00401000,"[eax]==0x1234"     // 条件断点：内存[eax]等于0x1234时断下
bp 0x00402000,"eax>0x100 && ecx==0"  // 多条件组合
bp 0x00403000,"[esp+4]=="password""  // 检查参数
```

### 2.3 调试事件

Windows 调试器通过调试事件循环接收目标进程的状态通知。主要事件类型：

| 事件 | 触发时机 | 调试用途 |
|------|----------|----------|
| CREATE_PROCESS_DEBUG_EVENT | 进程创建 | 初始化断点、读取PE头 |
| LOAD_DLL_DEBUG_EVENT | DLL加载 | 在特定DLL加载后设断点 |
| EXCEPTION_DEBUG_EVENT | 异常发生 | 断点命中、访问违例、除零 |
| EXIT_PROCESS_DEBUG_EVENT | 进程退出 | 清理、分析结束 |
| RIP_EVENT | 调试器内部错误 | 诊断 |

```
调试事件循环（伪代码）：
while (WaitForDebugEvent(&de, INFINITE)) {
    switch (de.dwDebugEventCode) {
        case EXCEPTION_DEBUG_EVENT:
            if (de.Exception.ExceptionRecord.ExceptionCode == EXCEPTION_BREAKPOINT)
                // INT3断点命中
            else if (de.Exception.ExceptionRecord.ExceptionCode == EXCEPTION_SINGLE_STEP)
                // 单步或硬件断点命中
            else if (de.Exception.ExceptionRecord.ExceptionCode == EXCEPTION_ACCESS_VIOLATION)
                // 内存访问违例
            break;
        case LOAD_DLL_DEBUG_EVENT:
            if ( strstr(de.LoadDll.lpImageName, "user32.dll") )
                // user32.dll加载完成
            break;
    }
    ContinueDebugEvent(...);
}
```

### 2.4 跟踪操作

```
Step Into (F7)        步入：进入CALL调用的函数内部
Step Over (F8)        步过：执行CALL但不进入函数
Step Out  (Ctrl+F9)  步出：运行到当前函数返回
Run to Cursor         运行到光标位置
Trace Into            跟踪步入：自动单步并记录每条指令
Trace Over            跟踪步过：自动单步步过并记录
```

运行跟踪（Run Trace）会记录每一步执行的寄存器状态和内存变化，用于事后分析复杂算法：

```
x64dbg 跟踪命令：
TraceIntoConditional 0x00401000     // 跟踪到条件满足
TraceIntoConditional "eax==0x1234"  // 跟踪到eax为指定值
TraceCount 1000                      // 跟踪指定步数
```

### 2.5 调试窗口与运行跟踪

x64dbg 提供多种调试窗口用于观察程序状态：

- **反汇编窗口**：显示当前位置的反汇编代码，可滚动查看。
- **寄存器窗口**：实时显示通用寄存器、标志位、段寄存器值，变化时高亮。
- **内存窗口**：以十六进制+ASCII 形式显示指定地址的内存内容，可同时打开多个。
- **堆栈窗口**：显示当前 ESP/RSP 指向的栈内容，自动标注返回地址和参数。
- **日志窗口**：输出调试器脚本和插件的日志信息。
- **引用窗口**：查找指令、字符串、常量的引用。

运行跟踪日志：开启后，每条执行指令的寄存器状态都会记录到日志文件，便于事后分析。配置在 `Options → Preferences → Events`。

### 2.6 脚本调试

x64dbg 内置脚本引擎，支持变量、条件、循环，用于自动化调试任务。

**x64dbg 脚本示例 - 在 API 设断点并打印参数：**

```
// 设置API断点
bp VirtualAlloc
// 运行到断点
run
// 循环打印每次调用的参数
loop:
    log "VirtualAlloc: lpAddress={?,[esp+4]}, size={?,[esp+8]}, allocType={?,[esp+12]}, protect={?,[esp+16]}"
    run
    cmp eip, VirtualAlloc
    jne done
    jmp loop
done:
    msg "跟踪结束"
```

**WinDbg 脚本示例 - 命令脚本块：**

```
$$ 遍历所有堆块并检查
.foreach (chunk {!heap -h 0 -all}) {
    .printf "Chunk: %p\n", chunk
}
```

### 2.7 插件开发

x64dbg 提供完整的插件 SDK（C++），开发者可以编写插件扩展功能。核心 API：

```cpp
// 插件回调：菜单点击
PLUG_CB_MENUENTRY {
    int hEntry = callbackInfo->hEntry;
    if (hEntry == MENU_TEST) {
        // 读取当前EIP
        duint eip = 0;
        RegGetValue(EIP, &eip);
        _plugin_logprintf("Current EIP: 0x%p\n", eip);

        // 在EIP处设断点
        DbgCmdExec("bp eip");
    }
}

// 注册插件
extern "C" __declspec(dllexport) bool pluginit(PLUG_INITSTRUCT* initStruct) {
    initStruct->pluginVersion = 1;
    initStruct->sdkVersion = 1;
    strcpy_s(initStruct->pluginName, "MyPlugin");
    return true;
}
```

常用插件功能接口：
```
DbgCmdExec()           执行调试器命令
DbgMemRead()           读取目标进程内存
DbgMemWrite()          写入目标进程内存
DbgSetBreakpoint()     设置断点
PluginMenuAddEntry     添加菜单项
```

## 三、Linux动态调试

### 3.1 GDB基础与进阶

GDB 是 Linux 平台最强大的调试器，既可调试用户态程序也可调试内核。下面从基础到进阶列出核心命令。

**基础命令：**

```
gdb ./target                    启动调试
gdb -pid 1234                   附加到运行中的进程
break main                      在main函数设断点
break *0x401234                 在地址处设断点
watch *0x601040                 写监视点（内存被修改时断下）
rwatch *0x601040                读监视点
awatch *0x601040                读写监视点
run arg1 arg2                   带参数运行
continue / c                    继续执行
next / n                        步过
step / s                        步入
finish                          步出（运行到函数返回
info registers                  显示所有寄存器
info breakpoints                显示断点列表
backtrace / bt                  显示调用栈
```

**进阶命令：**

```
set disassembly-flavor intel    设置Intel语法（默认AT&T）
disas main                      反汇编函数
x/20x 0x601040                  以十六进制查看20字节内存
x/10i $eip                      以指令形式查看10条指令
x/s 0x401234                    以字符串形式查看内存
print/x $eax                    十六进制打印寄存器
set $eax = 0x1234               修改寄存器
set {int}0x601040 = 0xDEAD     修改内存
set follow-fork-mode child      跟踪子进程
catch syscall open              捕获open系统调用
```

**条件断点与命令序列：**

```
break 42 if i==100              条件断点
commands 1                      断点1命中时执行的命令序列
silent
  printf "i=%d, buf=%s\n", i, buf
  continue
end
```

### 3.2 GDB脚本与插件

**.gdbinit 配置文件**：GDB 启动时自动加载 `~/.gdbinit`，常用于设置默认参数。

```
# ~/.gdbinit
set disassembly-flavor intel
set follow-fork-mode child
set print pretty on
set disassemble-next-line on
```

**GDB Python 脚本**：GDB 内置 Python 解释器，可以编写强大的调试脚本。

```python
# trace_decrypt.py - 跟踪解密函数并提取解密结果
import gdb

class TraceDecrypt(gdb.Breakpoint):
    def __init__(self, addr):
        super().__init__("*" + addr, internal=True)
        self.count = 0

    def stop(self):
        self.count += 1
        rdi = int(gdb.parse_and_eval("$rdi"))  # 第一个参数：密文地址
        rsi = int(gdb.parse_and_eval("$rsi"))  # 第二个参数：长度
        inf = gdb.selected_inferior()
        data = bytes(inf.read_memory(rdi, rsi))
        print(f"[Decrypt #{self.count}] len={rsi}, data={data.hex()}")
        gdb.execute("continue")

# 设置断点
TraceDecrypt("0x401234")
print("解密跟踪断点已设置")
```

在 GDB 中加载：
```
(gdb) source trace_decrypt.py
(gdb) run
```

**主流增强插件：**

| 插件 | 特点 | 安装 |
|------|------|------|
| pwndbg | 专注pwn，增强内存/堆显示 | `git clone github.com/pwndbg/pwndbg && ./setup.sh` |
| GEF | 多架构支持、丰富的实用命令 | `echo 'source ~/.gdbinit-gef.py' >> ~/.gdbinit` |
| peda | 经典插件，含pattern等工具 | `echo 'source ~/peda/peda.py' >> ~/.gdbinit` |

pwndbg 常用增强命令：
```
pwndbg> context         显示完整上下文（寄存器/反汇编/栈）
pwndbg> heap            查看堆块
pwndbg> bins            查看fastbin/unsorted bin
pwndbg> cyclic 100      生成De Bruijn pattern
pwndbg> cyclic_offset   查找偏移
pwndbg> ropgadget       查找ROP gadget
pwndbg> vmmap           显示内存映射
pwndbg> search -t string "flag"  搜索内存中的字符串
```

### 3.3 strace/ltrace系统调用跟踪

**strace** 跟踪进程的系统调用，用于分析程序与内核的交互；**ltrace** 跟踪库函数调用。

```bash
# 跟踪所有系统调用
strace ./program arg1

# 只跟踪文件相关
strace -e trace=open,read,write,close ./program

# 跟踪网络相关
strace -e trace=network ./program

# 统计系统调用次数
strace -c ./program

# 跟踪子进程
strace -f ./program

# 附加到运行中的进程
strace -p 1234

# 输出时间戳
strace -t -T ./program

# ltrace 跟踪库函数
ltrace -e malloc+free+strcpy ./program
```

strace 输出示例分析：
```
open("/etc/config", O_RDONLY)          = 3     // 打开文件成功，fd=3
read(3, "secret_data", 11)             = 11   // 读取成功
write(1, "result", 6)                  = 6    // 写入stdout
connect(3, {sa_family=AF_INET, sin_addr=inet_addr("192.168.1.1"), sin_port=htons(80)}, 16) = 0
```

### 3.4 动态链接库调试与核心转储

**LD_PRELOAD 注入**：在目标程序加载前注入自定义库，用于 Hook 函数。

```c
// hook.c - Hook libc的rand函数
#define _GNU_SOURCE
#include <dlfcn.h>
#include <stdio.h>

int rand(void) {
    static int (*real_rand)(void) = NULL;
    if (!real_rand)
        real_rand = dlsym(RTLD_NEXT, "rand");

    int result = real_rand();
    fprintf(stderr, "[Hook] rand() = %d\n", result);
    return result;
}
```

```bash
gcc -shared -fPIC -o hook.so hook.c -ldl
LD_PRELOAD=./hook.so ./target_program
```

**核心转储分析**：

```bash
# 启用核心转储
ulimit -c unlimited

# 运行崩溃程序
./crash_program
# 输出: Segmentation fault (core dumped)

# 使用GDB分析core文件
gdb ./crash_program core
(gdb) bt                 # 查看崩溃时的调用栈
(gdb) info registers     # 查看崩溃时的寄存器
(gdb) x/i $pc            # 查看崩溃时的指令
```

在 `/proc/sys/kernel/core_pattern` 设置 core 文件的存储路径和命名规则。

## 四、IDA Pro动态调试

IDA Pro 不仅支持静态分析，还内置了强大的动态调试器，支持多平台调试。

**调试器配置**：

```
1. Debugger → Select debugger
2. 选择目标平台：
   - Local Windows debugger     本地Windows调试
   - Local Linux debugger       本地Linux调试
   - Remote GDB debugger        远程GDB调试
   - Remote Win32 user-mode    IDA win32_server远程调试
3. Debugger → Process options  设置可执行文件路径和参数
4. F9 启动调试
```

**远程调试**：IDA 提供 `win32_server.exe`（Windows）和 `linux_server`（Linux）作为远程调试服务端。

```
# 目标机器上启动调试服务端
linux_server                  # 默认端口23946
win32_server.exe -Ppassword   # 带密码保护

# IDA端配置：
# Debugger → Select debugger → Remote GDB debugger
# Debugger → Process options → Hostname: 目标IP, Port: 23946
```

**Android/iOS 调试**：

```
Android:
  1. adb push android_server /data/local/tmp/
  2. adb shell "chmod +x /data/local/tmp/android_server"
  3. adb forward tcp:23946 tcp:23946
  4. /data/local/tmp/android_server
  5. IDA: Remote GDB debugger → localhost:23946
```

## 五、高级调试技术

### 5.1 反调试检测与绕过

恶意软件和保护壳常使用反调试技术检测调试器存在，检测到后改变行为或退出。

**IsDebuggerPresent / PEB 检测**：

```c
// 方法1：直接调用API
if (IsDebuggerPresent()) ExitProcess(0);

// 方法2：直接读取PEB的BeingDebugged标志
BOOL detected = FALSE;
__asm {
    mov eax, fs:[0x30]       // TEB->ProcessEnvironmentBlock
    movzx eax, byte ptr [eax+2] // PEB->BeingDebugged
    mov detected, eax
}
if (detected) ExitProcess(0);

// 方法3：检查NtGlobalFlag（x86偏移0x68, x64偏移0xBC）
DWORD NtGlobalFlag = *(DWORD*)(__readgsqword(0x60) + 0xBC);
if (NtGlobalFlag & 0x70) ExitProcess(0); // FLG_HEAP_ENABLE_TAIL_CHECK|FREE_CHECK|VALIDATE
```

绕过方法：在 x64dbg 中使用 ScyllaHide 插件，自动 patch PEB 标志位；或手动修改：

```
// x64dbg中手动清除BeingDebugged
1. 命令行: SetPEBBeingDebugged 0
2. 或在内存窗口跳转到PEB地址，将偏移2处改为0
3. 同样清除NtGlobalFlag的相关标志位
```

**硬件断点检测**：检查 DR0-DR7 寄存器是否被设置。

```c
CONTEXT ctx;
ctx.ContextFlags = CONTEXT_DEBUG_REGISTERS;
GetThreadContext(GetCurrentThread(), &ctx);
if (ctx.Dr0 || ctx.Dr1 || ctx.Dr2 || ctx.Dr3)
    ExitProcess(0); // 检测到硬件断点
```

绕过：在 x64dbg 中用 ScyllaHide 清除 DR 寄存器，或改用内存断点。

**时间检测**：利用 `RDTSC` 指令测量代码执行时间，调试时单步会导致时间异常。

```c
DWORD64 t1, t2;
t1 = __rdtsc();
// ... 关键代码 ...
t2 = __rdtsc();
if (t2 - t1 > 0x10000) // 阈值
    ExitProcess(0); // 检测到调试
```

绕过：在 x64dbg 中对 `RDTSC` 设断点，修改返回的时间值；或使用 ScyllaHide 的时间检测绕过选项。

### 6.1 Crackme分析流程

一个典型 Crackme 的逆向流程：

```
1. 初步运行：观察程序行为（输入→输出）

   - 在输入函数（GetDlgItemText/scanf）设断点
   - 输入测试数据后断下
   - 跟踪数据流向（Step Into/Over）
   - 在比较指令（cmp/test/strcmp）处断下
   - 观察比较的两个值
4. 算法分析：跟踪校验算法，理解正确值的生成方式

```

## 七、动态调试自动化

### 7.1 GDB Python脚本自动化

```python
#!/usr/bin/env python3
# auto_trace.py - 自动化跟踪函数调用并记录参数
import gdb
import struct

class AutoTrace(gdb.Command):
    """自动跟踪指定函数的所有调用"""
    def __init__(self):
        super().__init__("auto-trace", gdb.COMMAND_USER)

    def invoke(self, arg, from_tty):
        addr = int(arg, 16) if arg.startswith("0x") else int(arg)
        bp = gdb.Breakpoint(f"*{addr:#x}")

        results = []
        def stop_handler(event):
            if isinstance(event, gdb.StopEvent):
                rdi = int(gdb.parse_and_eval("$rdi"))
                rsi = int(gdb.parse_and_eval("$rsi"))
                rdx = int(gdb.parse_and_eval("$rdx"))
                inf = gdb.selected_inferior()
                try:
                    buf = bytes(inf.read_memory(rdi, min(rsi, 64)))
                except:
                    buf = b"<unreadable>"
                results.append({
                    "rdi": rdi, "rsi": rsi, "rdx": rdx, "buf": buf
                })
                print(f"[Trace] rdi={rdi:#x} rsi={rsi} rdx={rdx} buf={buf[:32]}")
                gdb.execute("continue")

        gdb.events.stop.connect(stop_handler)
        print(f"自动跟踪已启动，断点地址: {addr:#x}")
        gdb.execute("run")

        # 汇总结果
        print(f"\n=== 跟踪完成，共记录 {len(results)} 次调用 ===")
        gdb.events.stop.disconnect(stop_handler)

AutoTrace()
```

使用：
```bash

(gdb) auto-trace 0x401234
```

### 7.3 自动化断点与日志收集

```python
#!/usr/bin/env python3
# auto_bp.py - 批量设断点并收集日志
import gdb

# 批量断点配置
BREAKPOINTS = {
    0x401000: "decryption_func",
    0x401200: "validation_func",
    0x401400: "network_send",
}

LOG_FILE = open("debug_log.txt", "w")

def setup_auto_log():
    for addr, name in BREAKPOINTS.items():
        gdb.execute(f"break *{addr}")
        # 设置断点命令序列：打印信息后继续
        cmds = f"""
commands {addr}
silent
  printf "[{name}] rdi=%#x rsi=%#x rdx=%#x\\n", $rdi, $rsi, $rdx
  x/16bx $rdi
end
"""
        gdb.execute(cmds)

setup_auto_log()
print(f"已设置 {len(BREAKPOINTS)} 个自动化断点，日志输出到 debug_log.txt")
gdb.execute("run")
```

## 小结

动态调试是逆向工程不可或缺的能力。掌握不同平台调试器（x64dbg/WinDbg/GDB/IDA）的使用、理解断点机制和调试事件循环、熟悉反调试技术及其绕过方法，是成为一名合格逆向工程师的基础。实践中应将静态分析与动态调试结合，利用脚本和自动化工具提高分析效率。在实际分析中，建议始终在隔离的虚拟机环境中操作，并遵守相关法律法规。
