# 第7章 防御与加固建议

前面的章节介绍了如何发现和利用IoT设备的安全漏洞，本章从防御的角度，为IoT设备厂商和用户提供安全加固建议。安全是一个持续的过程，需要从设计、开发、部署到运维的全生命周期考虑。

### 7.1 固件安全开发规范

安全应该从产品设计阶段就开始考虑，而不是事后补救。以下是固件安全开发的基本规范。

#### 7.1.1 安全开发生命周期（SDL）

**1. 需求分析阶段**
- 明确安全需求和合规要求
- 进行威胁建模（STRIDE、DREAD等方法）
- 识别敏感数据和关键资产
- 定义安全验收标准

**2. 设计阶段**
- 遵循最小权限原则
- 采用纵深防御策略
- 设计安全的认证和授权机制
- 规划安全更新机制
- 进行安全设计评审

**3. 开发阶段**
- 使用安全的编码规范
- 避免使用危险函数
- 输入验证和输出编码
- 使用静态代码分析工具
- 定期进行代码安全审计

**4. 测试阶段**
- 进行渗透测试
- Fuzzing测试
- 漏洞扫描
- 安全功能验证
- 第三方组件安全检查

**5. 发布与运维阶段**
- 安全的固件分发机制
- 漏洞响应流程
- 定期安全更新
- 安全事件响应机制

#### 7.1.2 安全编码规范

**内存安全：**
- 禁止使用 `gets()`、`strcpy()`、`strcat()`、`sprintf()` 等危险函数
- 使用 `strncpy()`、`snprintf()` 等带长度限制的函数
- 仔细检查边界条件
- 启用编译器安全选项

```c
// 错误示例
char buf[64];
strcpy(buf, user_input);

// 正确示例
char buf[64];
strncpy(buf, user_input, sizeof(buf) - 1);
buf[sizeof(buf) - 1] = '\0';
```

**输入验证：**
- 所有外部输入都必须验证
- 使用白名单验证（只允许已知合法的输入）
- 验证输入的长度、格式、范围
- 多层验证（客户端和服务端都要验证）

```c
// 命令注入防护：验证IP地址格式
int is_valid_ip(const char *ip) {
    struct sockaddr_in sa;
    return inet_pton(AF_INET, ip, &(sa.sin_addr)) != 0;
}

// 使用exec系列函数代替system
// 避免shell解析
pid_t pid = fork();
if (pid == 0) {
    execl("/bin/ping", "ping", "-c", "4", ip, NULL);
    _exit(1);
}
```

**密码安全：**
- 禁止硬编码密码和密钥
- 使用安全的密码哈希算法（bcrypt、scrypt、Argon2）
- 加盐哈希
- 强制用户修改默认密码

```c
// 错误：明文比较密码
if (strcmp(password, stored_password) == 0) {
    // 认证成功
}

// 正确：使用加盐哈希
if (bcrypt_verify(password, stored_hash)) {
    // 认证成功
}
```

#### 7.1.3 编译器安全选项

**GCC安全编译选项：**
```makefile
# 栈保护
CFLAGS += -fstack-protector-strong

# 不可执行栈
LDFLAGS += -z noexecstack

# 不可执行内存页（DEP/NX）
LDFLAGS += -z relro -z now

# 地址无关代码（支持ASLR）
CFLAGS += -fPIC
LDFLAGS += -pie

# 控制流完整性（较新GCC支持）
CFLAGS += -fcf-protection

# Fortify源（检测缓冲区溢出）
CFLAGS += -D_FORTIFY_SOURCE=2 -O2

# 警告即错误
CFLAGS += -Wall -Wextra -Werror
```

**推荐的完整编译选项：**
```bash
arm-linux-gnueabi-gcc \
    -O2 -D_FORTIFY_SOURCE=2 \
    -fstack-protector-strong \
    -fPIE -pie \
    -fno-strict-aliasing \
    -Wall -Wextra -Wformat -Wformat-security \
    -z relro -z now -z noexecstack \
    -o output source.c
```

### 7.2 固件安全加固

#### 7.2.1 固件加密与签名

**固件签名验证：**
设备在升级固件时，应该验证固件的数字签名，确保固件来自可信来源且未被篡改。

**工作原理：**
1. 厂商使用私钥对固件进行签名
2. 设备中内置公钥
3. 升级时设备使用公钥验证签名
4. 签名验证通过才允许升级

**实现要点：**
- 使用非对称加密算法（RSA-2048、ECC-256）
- 签名应覆盖整个固件镜像
- 公钥应安全存储在设备中（OTP、安全元件）
- 防止回滚攻击（版本号检查）
- 引导加载程序也要验证内核签名

**固件加密：**
- 固件可以加密存储，防止逆向分析
- 解密密钥应安全存储
- 注意：加密不能替代签名，只能增加逆向难度

#### 7.2.2 安全启动（Secure Boot）

安全启动是指从硬件层面确保设备只运行经过验证的可信代码。

**启动链信任：**
```
ROM Bootloader (可信根) 
    → 验证第二阶段Bootloader签名
        → 验证内核签名
            → 验证内核模块签名
                → 验证应用程序
```

**ARM TrustZone：**
ARM TrustZone技术提供硬件级别的安全隔离：
- 安全世界（Secure World）：运行安全操作系统、密钥管理等
- 普通世界（Normal World）：运行普通操作系统和应用
- 安全监控器（Monitor）：负责世界切换

**实现建议：**
- 使用芯片厂商提供的安全启动方案
- 启用eFuse/OTP烧录公钥哈希
- 禁用调试接口（JTAG/SWD）
- 锁定Flash的安全区域

#### 7.2.3 服务与接口安全

**关闭不必要的服务：**
- 禁用Telnet，使用SSH代替
- 禁用不必要的网络服务
- 关闭调试接口（出厂前）
- 移除或禁用厂商后门

**服务安全配置：**
- 使用强密码策略
- 启用登录失败锁定
- 使用证书认证代替密码
- 限制服务监听的网络接口
- 使用防火墙规则限制访问

**Web服务安全：**
- 使用HTTPS加密通信
- 实现安全的Session管理
- 输入验证和输出编码
- 防范CSRF、XSS、SQL注入
- 安全的文件上传处理
- 启用安全响应头

#### 7.2.4 账户与认证安全

**默认凭据处理：**
- 设备出厂时无默认密码
- 首次使用强制设置密码
- 密码强度要求（长度、复杂度）
- 唯一的默认凭据（每台设备不同）

**认证机制：**
- 使用多因素认证
- 实现安全的密码找回机制
- Session超时自动登出
- 登录失败次数限制
- 异常登录检测与告警

**权限管理：**
- 最小权限原则
- 角色权限分离
- 敏感操作二次验证
- 操作审计日志

### 7.3 运行时安全防护

#### 7.3.1 地址空间布局随机化（ASLR）

ASLR通过随机化进程地址空间的布局，增加漏洞利用的难度。

**启用ASLR：**
```bash
# 启用内核ASLR
echo 2 > /proc/sys/kernel/randomize_va_space

# 编译时启用PIE
gcc -fPIE -pie -o program program.c
```

**ASLR级别：**
- 0：禁用
- 1：随机化栈、共享库、mmap
- 2：随机化栈、共享库、mmap、堆

#### 7.3.2 栈保护（Stack Canary）

栈保护通过在栈上放置一个"金丝雀"值，检测栈溢出的发生。

**工作原理：**
1. 函数入口时，将一个随机值（Canary）放在栈上
2. 函数返回前，检查这个值是否被修改
3. 如果被修改，说明发生了栈溢出，程序终止

**注意事项：**
- 不是所有函数都会插入Canary
- Canary值需要随机且保密
- 可以与其他保护机制结合使用

#### 7.3.3 数据执行保护（DEP/NX）

数据执行保护将内存页标记为不可执行，防止在栈和堆上执行代码。

**实现方式：**
- ARM架构使用XN（Execute Never）位
- 栈、堆、数据段标记为不可执行
- 只有代码段是可执行的

**绕过技术：**
- Return-to-libc
- ROP（Return-Oriented Programming）
- 信息泄露+内存改写

#### 7.3.4 其他防护机制

**控制流完整性（CFI）：**
- 确保程序的控制流在预期范围内
- 防止ROP等代码重用攻击
- 细粒度CFI性能开销大

**栈随机化：**
- 每次函数调用的栈帧位置随机
- 增加预测栈地址的难度

**堆安全：**
- 堆元数据保护
- Double-free检测
- Use-after-free检测

### 7.4 设备使用安全建议

#### 7.4.1 用户侧安全措施

**初始配置：**
1. 修改默认管理员密码
2. 修改WiFi默认密码
3. 禁用不必要的服务
4. 更新到最新固件
5. 配置正确的时间和时区

**网络安全：**
- 将IoT设备放在单独的网络（访客网络/VLAN）
- 不要将管理端口暴露在公网
- 使用防火墙限制设备的网络访问
- 监控设备的网络流量
- 定期检查设备的活跃连接

**日常维护：**
- 定期检查固件更新
- 关注厂商的安全公告
- 定期更换密码
- 备份配置文件
- 不使用时断电

#### 7.4.2 漏洞响应

**发现漏洞后：**
1. 验证漏洞的真实性和影响范围
2. 评估风险等级
3. 查找缓解措施（临时方案）
4. 联系厂商报告漏洞
5. 等待官方补丁
6. 安装补丁并验证

**负责任的漏洞披露：**
- 给予厂商合理的修复时间（通常90天）
- 不公开详细利用代码（至少在补丁发布前）
- 协调披露时间
- 遵守相关法律法规

#### 7.5.2 渗透测试流程

1. **侦察阶段**
   - 设备识别（型号、版本）
   - 端口扫描和服务识别
   - 固件获取和分析

2. **漏洞扫描**
   - 已知漏洞扫描
   - 默认凭据测试
   - 配置问题检查

3. **漏洞挖掘**
   - Web漏洞挖掘
   - 网络服务Fuzzing
   - 二进制漏洞挖掘

4. **漏洞利用**
   - 验证漏洞的可利用性
   - 评估影响范围
   - 获取访问权限

5. **后渗透**
   - 权限提升
   - 内网横向移动
   - 数据窃取

6. **报告撰写**
   - 漏洞详情
   - 复现步骤
   - 风险评估
   - 修复建议
