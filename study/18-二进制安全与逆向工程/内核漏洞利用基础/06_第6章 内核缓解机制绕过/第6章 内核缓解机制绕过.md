# 第6章 内核缓解机制绕过

现代操作系统在内核中部署了层层安全防护机制，攻击者需要逐一绕过才能完成利用。本章详细讲解各类缓解机制的原理及绕过技术。

### 6.1 KASLR绕过技术

#### 6.1.1 KASLR原理

内核地址空间布局随机化（Kernel Address Space Layout Randomization）在系统启动时随机化内核的基地址，使得攻击者无法预测内核代码和数据的位置。

**随机化范围**：
- 内核代码段（.text）基址
- 内核数据段（.data / .bss）基址
- 内核栈位置
- 模块加载基址
- 堆（slab）的随机化（粒度较粗）

**随机化熵**：
- 32位系统：约8-12位熵（几百到几千种可能）
- 64位系统：约20-30位熵（百万到十亿种可能）

#### 6.1.2 信息泄露绕过

最直接、最常用的KASLR绕过方法是利用信息泄露漏洞获取一个内核地址，然后通过偏移计算出所有需要的内核符号地址。

**常见泄露源**：
- **未初始化内存**：内核栈或堆上的局部变量未初始化，返回给用户态时包含旧数据
- **越界读**：数组越界读取到相邻的内核指针
- **/proc/kallsyms**：在未加固的系统中可直接读取内核符号地址
- **dmesg / 内核日志**：某些内核Oops信息会泄露地址
- **网络协议栈**：某些协议实现可能泄露内核地址
- **调试接口**：如`/sys/kernel/debug`下的文件

**泄露后计算偏移**：
```c
// 已知：泄露的地址 leak_addr
// 已知：该符号在内核中的偏移（从vmlinux中提取）symbol_offset
// 求：内核基址 kernel_base

unsigned long kernel_base = leak_addr - symbol_offset;

// 然后计算其他符号地址
unsigned long commit_creds = kernel_base + COMMIT_CREDS_OFFSET;
```

#### 6.1.3 暴力破解

在32位系统中，KASLR的熵较低（通常只有8-10位），可以通过暴力破解绕过。但在64位系统中，暴力破解几乎不可行。

**方法**：
- 利用一个不会导致系统永久崩溃的漏洞（如某些可以重试的用户态触发路径）
- 反复尝试不同的地址，直到猜中
- 每次失败后进程崩溃但系统不崩溃，重新fork进程继续尝试

**适用场景**：
- 32位系统
- 某些特定漏洞（如fork后子进程崩溃，父进程继续）
- 内核重启不影响攻击者的场景

#### 6.1.4 侧信道攻击

利用CPU缓存、TLB等微架构侧信道泄露内核地址信息。

**TLB侧信道**：
- TLB（Translation Lookaside Buffer）是页表缓存
- 访问已映射的地址和未映射的地址在TLB命中率上有差异
- 通过精确测量访问时间，可以推断哪些地址是有效的内核地址

**缓存侧信道**：
- 利用CPU缓存的timing差异
- Flush+Reload、Prime+Probe等技术

**注意**：侧信道攻击通常需要非常精确的计时，且受系统噪声影响较大，实际利用难度较高。

### 6.2 SMEP/SMAP绕过

#### 6.2.1 SMEP原理

SMEP（Supervisor Mode Execution Protection）由CR4寄存器的第20位（SMEP位）控制。当SMEP启用时，如果CPU处于内核态（CPL=0），尝试执行用户态页（U/S位为1）中的代码会触发页错误（#PF）。

**检测SMEP是否启用**：
```c
unsigned long cr4;
asm volatile ("mov %%cr4, %0" : "=r"(cr4));
if (cr4 & (1 << 20)) {
    // SMEP已启用
}
```

#### 6.2.2 SMAP原理

SMAP（Supervisor Mode Access Prevention）由CR4寄存器的第21位（SMAP位）控制。当SMAP启用时，内核态访问用户态数据也会触发页错误。内核必须使用`copy_from_user`/`copy_to_user`等专用函数，这些函数会临时清除AC标志（EFLAGS的第18位）以允许访问。

#### 6.2.3 SMEP绕过方法

**方法1：修改CR4寄存器**

最直接的方法是在内核ROP链中关闭CR4的SMEP位：

```
# ROP链
pop rcx; ret
<cr4_value_without_smep>   # cr4 & ~(1<<20)
mov cr4, rcx; ret
<user_shellcode_addr>       # 现在可以跳转到用户态shellcode了
```

**注意事项**：
- 需要找到包含`mov cr4, rcx; ret`的gadget
- 某些较新的内核会验证CR4的值，不允许随意修改
- Windows的PatchGuard会检测CR4的异常修改

**方法2：使用内核ROP完成所有操作**

如果无法关闭SMEP，就完全在内核态通过ROP完成提权，不依赖用户态代码执行：

```
# ROP链（Linux示例）
pop rdi; ret
0
prepare_kernel_cred_addr    # 调用prepare_kernel_cred(0)
<gadget to move rax to rdi> # 将返回值移到rdi
commit_creds_addr           # 调用commit_creds(new_cred)
swapgs_iretq_gadget         # 返回用户态
```

**方法3：ret2dir（Return-to-Direct Map）**

利用物理内存的直接映射区域（direct map / linear map）。在Linux中，所有物理内存都被映射到内核虚拟地址空间的某个固定偏移（如`PAGE_OFFSET`或`__va()`对应的区域）。

如果攻击者：
1. 可以将shellcode放置到物理内存中（如通过用户态分配的页面，这些页面在物理内存中）
2. 知道物理地址到内核虚拟地址的映射关系
3. 可以跳转到直接映射区域的对应地址

那么即使SMEP启用，由于直接映射区域的页面是内核态页面（U/S位为0），执行其中的代码不会触发SMEP。

**方法4：覆盖函数指针到内核代码**

如果漏洞提供了任意写原语，可以修改某个内核函数指针（如文件操作的`release`回调）为ROP链的起点或特定内核函数。当该函数指针被调用时，控制流转移到攻击者控制的路径，整个过程都在内核态执行。

#### 6.2.4 SMAP绕过方法

SMAP阻止内核态访问用户态数据，绕过方法包括：

**方法1：清除CR4的SMAP位**

与SMEP类似，通过ROP清除CR4的第21位。

**方法2：使用内核栈中转**

将需要的数据先复制到内核栈上（利用漏洞的溢出数据本身就在内核栈上），然后在内核栈上操作。

**方法3：利用内核数据**

所有操作都在内核数据上完成，不访问用户态内存。例如，直接在内核堆上构造伪造对象。

### 6.3 KPTI绕过

#### 6.3.1 KPTI原理

KPTI（Kernel Page Table Isolation，内核页表隔离）是为了缓解Meltdown漏洞而引入的保护机制。它将内核页表和用户态页表完全分离：

- **用户态页表**：只包含用户态地址空间的映射，以及进入内核所需的最小内核映射（如系统调用入口、中断描述符表等）
- **内核态页表**：包含完整的内核地址空间映射

进入内核时（系统调用、中断等）切换到内核页表，返回用户态时切换回用户页表。

**对漏洞利用的影响**：
- KPTI使得从用户态直接读取内核数据（Meltdown类漏洞）变得困难
- 但对于已经获得内核代码执行的情况，KPTI影响不大（因为内核态运行时使用完整的内核页表）

#### 6.3.2 KPTI对利用的影响

**正面影响（对防御者）**：
- 阻止了纯信息泄露类的侧信道攻击（如Meltdown）
- 用户态无法直接访问内核页表映射的大部分内容

**对传统内存破坏漏洞利用的影响有限**：
- 如果漏洞已经允许控制内核态的指令指针，KPTI不影响ROP链的执行
- 内核态执行时拥有完整的内核页表
- 提权操作（修改cred、替换Token等）仍然可行

#### 6.3.3 绕过思路

KPTI本身不是为了阻止内存破坏漏洞利用，而是阻止侧信道信息泄露。对于内存破坏漏洞：

1. **正常执行ROP**：进入内核态后使用完整内核页表，KPTI不构成障碍
2. **利用KPTI trampoline**：KPTI保留的入口trampoline中可能有可利用的gadget
3. **Meltdown + KASLR绕过**：如果系统有Meltdown漏洞但启用了KPTI，需要寻找KPTI的"缝隙"

### 6.4 CET影子栈绕过

#### 6.4.1 CET原理

CET（Control-flow Enforcement Technology）是Intel推出的硬件级控制流完整性保护，包含两个主要部分：

**影子栈（Shadow Stack）**：
- 为每个栈维护一个影子栈，存储返回地址的副本
- `call`指令将返回地址同时压入正常栈和影子栈
- `ret`指令从两个栈弹出返回地址并比较，如果不一致则触发异常
- 影子栈受硬件保护，普通指令无法修改

**间接分支跟踪（IBT）**：
- 要求间接跳转的目标必须是`endbr`指令
- 防止跳转到函数中间（如某些gadget的中间部分）

#### 6.4.2 影子栈对ROP的影响

影子栈直接针对ROP攻击——ROP的核心就是通过控制栈上的返回地址来控制程序流，而影子栈使得修改返回地址会被检测到。

**CET对内核漏洞利用的影响**：
- 传统的基于ret的ROP链被有效阻止
- 基于jmp/call的技巧（如JOP、COP）可能仍然有效
- 需要寻找新的控制流劫持方法

#### 6.4.3 绕过思路

**方法1：寻找影子栈的漏洞**

影子栈本身也存储在内存中，如果有任意写原语，理论上可以同时修改正常栈和影子栈上的返回地址。但影子栈的地址通常是随机化且受保护的。

**方法2：JOP/COP（Jump-Oriented Programming / Call-Oriented Programming）**

不依赖`ret`指令，而是使用间接跳转（jmp）或间接调用（call）来串联gadget：
- 寻找以`jmp rax`、`call rbx`等结尾的gadget
- 通过控制寄存器的值来控制跳转目标
- 这种方式不修改返回地址，不受影子栈保护

**方法3：异常/中断处理路径**

利用异常或中断处理的控制流转移，这些路径可能不完全受CET保护。

**方法4：数据导向编程（DOP）**

不劫持控制流，而是通过修改数据来达到目的。例如：
- 直接修改cred结构体实现提权（需要任意写原语）
- 修改安全相关的变量
- 操纵内核数据结构实现逻辑绕过

**注意**：CET是较新的保护机制，相关的绕过研究仍在快速发展中。实际绕过方法取决于具体的实现细节和漏洞场景。

### 6.5 其他缓解机制

#### 6.5.1 Stack Canary

**原理**：在函数栈帧中返回地址之前放置一个随机的"金丝雀"值，函数返回前检查该值是否被修改。如果被修改，说明发生了栈溢出，触发内核崩溃。

**绕过方法**：
- **泄露Canary值**：通过信息泄露漏洞获取当前栈帧的canary值，然后在溢出数据中包含正确的canary
- **绕过检查**：覆盖异常处理结构，在canary检查触发异常前就劫持控制流
- **逐字节爆破**：利用某些情况下canary可以逐字节猜测的特点（较少适用于内核）

#### 6.5.2 CFG（Control Flow Guard）

**原理**：微软的控制流保护技术，在编译时为所有间接调用目标建立合法目标列表，运行时检查间接调用的目标是否在列表中。

**内核CFG（kCFG）**：Windows 10 1709及以上版本支持内核级CFG。

**绕过方法**：
- 寻找合法的间接调用目标作为"跳板"
- 利用未被CFG保护的函数
- 数据导向攻击（不修改控制流，只修改数据）

#### 6.5.3 Windows PatchGuard

**原理**：PatchGuard（内核补丁保护）定期检查内核关键数据结构的完整性，包括：
- 系统调用表（SSDT）
- 中断描述符表（IDT）
- 全局描述符表（GDT）
- 内核驱动的代码完整性
- 某些关键内核函数

如果检测到修改，系统会触发BSOD（蓝屏死机）。

**对漏洞利用的影响**：
- 不能直接修改SSDT、IDT等关键结构
- 不能直接patch内核代码
- 提权后如果修改了受保护的结构，可能在几分钟内触发蓝屏

**绕过思路**：
- 利用代码执行完成提权后立即恢复（"打一枪换一个地方"）
- 修改不受PatchGuard保护的数据结构
- 利用合法的内核API完成目标，不直接patch内核
