# 第4章 内核漏洞类型

内核漏洞类型与用户态有很多相似之处，但由于内核运行环境的特殊性，其利用方式和影响程度有显著差异。本章详细介绍各类内核漏洞的原理和特点。

### 4.1 栈溢出

#### 4.1.1 内核栈溢出原理

内核栈溢出与用户态栈溢出原理相同——向栈上缓冲区写入超出其大小的数据，覆盖栈上的返回地址或其他关键数据。但内核栈溢出有以下特点：

**内核栈的特点**：
- **大小有限**：Windows内核栈通常为12KB或24KB，Linux内核栈通常为8KB或16KB（4KB页面的2或4倍），远小于用户态栈
- **不可扩展**：内核栈溢出后不会有用户态那样的guard page提示，直接导致内核崩溃（BSOD/OOPS）
- **共享性**：中断处理、异常处理可能借用当前进程的内核栈
- **结构复杂**：栈上不仅有函数调用帧，还有中断上下文、异常帧等

**触发场景**：
- 驱动程序的IOCTL处理中，将用户态数据复制到栈上缓冲区但未验证长度
- 内核函数中使用`strcpy`、`sprintf`等不安全字符串操作
- 递归调用深度过大导致栈耗尽（Stack Overflow）

#### 4.1.2 利用差异

与用户态栈溢出相比，内核栈溢出的利用有以下不同：

1. **目标不同**：用户态是获取代码执行，内核态是获取权限提升（通常是提权到root/SYSTEM）
2. **返回目标不同**：传统的ret2usr（返回用户态shellcode）已被SMEP阻止
3. **栈布局不同**：内核栈上有更多敏感数据（如`_KEXCEPTION_REGISTRATION_RECORD`、`_KTRAP_FRAME`等）
4. **崩溃后果不同**：用户态崩溃只影响当前进程，内核崩溃导致整个系统蓝屏/宕机

**经典利用路径（无SMEP时）**：
1. 溢出覆盖返回地址
2. 返回地址指向用户态的shellcode
3. Shellcode执行提权操作（如修改cred结构体）
4. 修复内核栈并返回用户态

**有SMEP时的利用路径**：
1. 溢出覆盖返回地址
2. 构造ROP链，在内核态完成提权
3. 通过`iret`/`sysret`返回用户态

### 4.2 堆溢出

#### 4.2.1 内核堆分配器

内核堆是漏洞利用的重要战场，不同操作系统有不同的堆分配器。

**Linux内核 - SLUB分配器**：

SLUB是当前Linux内核默认的分配器，核心概念：
- **slab**：一个或多个连续物理页组成的内存块
- **cache**：同一种大小对象的缓存（如`kmalloc-64`、`kmalloc-128`等）
- **object**：具体分配的对象

SLUB的关键特性：
- 每个CPU有per-cpu缓存（kmem_cache_cpu），快速分配释放
- slab有三种状态：full（全部分配）、partial（部分分配）、empty（全部空闲）
- 空闲对象通过freelist链表串联（指针存储在对象内部）

**Windows内核 - 堆管理器**：

Windows内核堆（Kernel Pool）的特点：
- 分为分页池（PagedPool）和非分页池（NonPagedPool）
- 池块有Pool Header（池头），记录大小、类型、标签等信息
- Windows 8引入了池随机化、池Cookie等保护
- Windows 10引入了更严格的池完整性检查（如Pool Integrity、Segment Heap）

#### 4.2.2 堆溢出利用原理

**Linux内核堆溢出**：

经典的堆溢出利用方法是覆盖相邻对象的数据：
1. 选择合适大小的slab缓存
2. 喷射大量目标对象，控制内存布局
3. 分配"受害者"对象和"溢出源"对象（使其在内存中相邻）
4. 利用溢出漏洞覆盖受害者对象的关键成员
5. 后续对受害者对象的操作触发任意读写或代码执行

常见的利用原语：
- **覆盖对象的虚函数表指针（vtable）**：后续调用虚函数时劫持控制流
- **覆盖链表节点指针**：通过链表操作实现任意地址写
- **覆盖函数指针**：直接修改回调函数指针

**Windows内核堆溢出**：

Windows堆溢出利用的演进：
- 早期：覆盖Pool Header的Next/Previous指针 → 任意地址写
- Vista/Win7：覆盖Pool Cookie导致保护增强 → 转向覆盖对象数据
- Win8+：利用类型混淆或UAF替代直接堆溢出

#### 4.2.3 堆喷射（Heap Spraying）

堆喷射是内核漏洞利用的关键技术，用于控制内存布局：

**目的**：
- 在特定地址放置可控数据
- 提高漏洞利用的可靠性
- 为后续利用步骤准备内存布局

**方法**：
- 反复分配大量内核对象（如通过创建大量文件句柄、套接字等）
- 利用特定大小的对象填充对应slab/池
- 精确控制"空洞"的位置和大小

**Linux内核堆喷射技巧**：
- 使用`msgsnd`/`msgrcv`操作消息队列（可精确控制分配大小和内容）
- 使用`setxattr`/`getxattr`扩展属性
- 使用`sendmsg`的消息控制数据（CMSG）
- 使用文件描述符表（fdtable）喷射
- 使用`timerfd`、`eventfd`、`signalfd`等特殊文件描述符

### 4.3 空指针引用（NULL Pointer Dereference）

#### 4.3.1 漏洞原理

空指针引用发生在内核代码对NULL指针进行解引用时。如果攻击者能够将NULL页（地址0）映射到用户态并填充可控数据，那么内核访问NULL指针偏移处的数据时，实际上会读取攻击者可控的数据。

**典型触发场景**：
```c
struct object *obj = get_object(); // 可能返回NULL
// 缺少NULL检查
obj->callback(obj->data); // 空指针解引用
```

#### 4.3.2 利用方法

**经典利用（无SMAP时）**：
1. 使用`mmap`将地址0映射到用户态（需要关闭`mmap_min_addr`保护）
2. 在地址0处伪造内核对象
3. 触发空指针引用，内核访问地址0处的数据
4. 如果被访问的是函数指针，则直接劫持控制流

**缓解机制**：
- `mmap_min_addr`：限制用户态可以映射的最低地址（通常为65536）
- SMAP：阻止内核态直接访问用户态内存
- 现代内核中，空指针引用漏洞的利用难度大大增加

### 4.4 释放后重用（Use-After-Free, UAF）

#### 4.4.1 漏洞原理

UAF是指内存块被释放后，仍然被引用（读或写）。这是内核漏洞中最常见、也是最危险的类型之一。

**典型场景**：
```c
struct object *obj = kmalloc(sizeof(*obj), GFP_KERNEL);
// ... 使用obj ...
kfree(obj);
// ... 中间逻辑 ...
obj->callback(); // Use-After-Free！
```

#### 4.4.2 为什么UAF在内核中更危险

1. **内核堆对象通常包含函数指针**：如文件操作结构体（file_operations）、设备操作结构体等，UAF可以轻易劫持控制流
2. **对象生命周期复杂**：引用计数、RCU、异步回调等机制使对象生命周期难以正确管理
3. **堆重用可控性高**：通过堆喷射可以精确控制释放的内存被什么数据覆盖

#### 4.4.3 利用步骤

标准UAF利用流程：

1. **分配对象**：创建并使用内核对象（如打开设备、创建文件等）
2. **释放对象**：通过某种方式释放对象（如关闭句柄），但保留"悬空指针"
3. **重新占用（Reallocation）**：分配与原对象相同大小的其他对象，填充可控数据，占据原对象的内存位置
4. **触发重用**：通过悬空指针再次访问对象，此时对象内容已被攻击者控制
5. **实现利用**：通过伪造的虚函数表、函数指针等劫持控制流

**关键技术点**：
- 选择与目标对象相同大小的"占位"对象类型
- 占位对象的内容必须可控
- 确保释放的内存块确实被新分配的对象占用（slab freelist的LIFO特性通常能保证这一点）

### 4.5 竞态条件（Race Condition）

#### 4.5.1 TOCTOU漏洞

TOCTOU（Time Of Check To Time Of Use）是最常见的竞态条件类型：检查时和使用时的状态不一致。

**内核中的典型场景**：
- 用户态传递的数据在内核检查和使用之间被修改
- 共享数据结构在加锁间隙被修改
- 信号处理中断了临界区代码

**用户态数据竞争**：
```c
// 内核代码示例（有漏洞）
if (user_buf->length < MAX_SIZE) {  // Check
    // 此时用户态线程可能修改user_buf->length
    copy_from_user(kernel_buf, user_buf->data, user_buf->length);  // Use
}
```

利用方法：攻击者用一个线程不断修改`user_buf->length`，另一个线程触发系统调用，利用时间差实现越界读写。

#### 4.5.2 双取（Double Fetch）

双取是TOCTOU的一种特殊形式，内核从用户态内存读取同一数据两次，且两次读取之间数据可能被修改。

**示例**：
```c
// 第一次读取（检查）
copy_from_user(&hdr, user_ptr, sizeof(hdr));
if (hdr.length > MAX) return -EINVAL;

// 第二次读取（使用）
copy_from_user(buf, user_ptr + sizeof(hdr), hdr.length);
// 此时user_ptr处的数据可能已被修改，hdr.length可能变大
```

**利用技巧**：
- 使用多线程，一个线程修改用户态数据，一个线程触发系统调用
- 利用CPU调度的不确定性增加竞态窗口
- 可通过CPU亲和力、优先级等手段提高竞态成功率

#### 4.5.3 RCU相关竞态

RCU机制虽然高效，但如果使用不当也会引入漏洞：
- 写者在宽限期结束前就释放了数据
- 读者端未使用`rcu_dereference`正确获取指针
- `rcu_assign_pointer`和`rcu_dereference`不配对使用

### 4.6 整数溢出与符号错误

#### 4.6.1 整数溢出

整数溢出本身通常不直接导致代码执行，但常与其他漏洞结合，导致堆/栈溢出。

**典型模式**：
```c
// 分配计算溢出
size_t size = count * sizeof(struct entry);
buf = kmalloc(size, GFP_KERNEL);  // count过大时，size溢出为很小的值
copy_from_user(buf, user_buf, count * sizeof(struct entry));  // 实际复制更多数据 → 溢出
```

**常见类型**：
- 加法溢出
- 乘法溢出
- 无符号整数回绕（underflow）

#### 4.6.2 符号错误

有符号整数和无符号整数混用导致的问题：

```c
int len = -1;  // 有符号，值为-1
if (len > 1024)  // 比较时被转换为无符号，-1变成很大的正数
    return -EINVAL;
copy_from_user(buf, user_buf, len);  // len被当作size_t（无符号），复制大量数据 → 溢出
```

### 4.7 类型混淆（Type Confusion）

#### 4.7.1 漏洞原理

类型混淆是指程序将一种类型的对象当作另一种类型来使用。在C语言中，由于缺乏运行时类型信息（RTTI），类型混淆在内核中非常常见。

**典型场景**：
- 多态对象的向下转型（downcast）未验证实际类型
- 通过魔术字（magic number）标识类型但魔术字可被伪造
- 联合体（union）的成员访问与实际设置的类型不匹配
- 不同类型的对象在同一个slab缓存中分配，通过UAF实现类型混淆

#### 4.7.2 利用方法

类型混淆的利用依赖于两种类型的内存布局差异：

1. **找到两种类型A和B，大小相同或相近（可在同一slab中分配）**
2. **类型A有攻击者可控的数据字段**
3. **类型B有敏感的指针或函数指针**
4. **通过UAF或其他方式，让内核将类型A的对象当作类型B使用**
5. **攻击者通过控制类型A中的字段，实现对类型B中敏感字段的控制**

**示例**：如果一个对象有虚函数表指针，而另一个对象的对应偏移是攻击者可控的数据字段，那么类型混淆后就可以劫持虚函数表，实现任意代码执行。

#### 4.7.3 CVE示例

许多著名的内核漏洞都是类型混淆漏洞：
- **CVE-2016-5195（Dirty COW）**：虽然本质是竞态条件，但涉及到对页对象的类型混淆使用
- **CVE-2017-1000112**：Linux内核UDP UFO功能中的类型混淆漏洞
- **CVE-2019-2215**：Android内核的binder驱动类型混淆漏洞
