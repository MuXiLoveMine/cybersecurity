# 缓解机制组合分析

```
checksec输出解读:

$ checksec --file=./binary
RELRO:    Full RELRO        <- GOT表保护
Stack:    Canary found       <- 栈溢出保护
NX:       NX enabled         <- 数据执行保护
PIE:      PIE enabled        <- 地址随机化

各机制的交互作用:

场景1: 栈溢出 + 无所有保护
  -> 简单覆盖返回地址 + 跳转到shellcode
  -> 难度: 低

场景2: 栈溢出 + DEP
  -> 不能跳到栈上shellcode
  -> 使用ret2libc或ROP
  -> 难度: 中

场景3: 栈溢出 + DEP + ASLR
  -> 需要信息泄露地址
  -> 或使用非随机化模块
  -> 难度: 中高

场景4: 栈溢出 + DEP + ASLR + Canary
  -> 需要泄露Canary
  -> 需要泄露地址
  -> 需要ROP
  -> 难度: 高

场景5: 栈溢出 + 全部保护(含CFI)
  -> 需要泄露多个值
  -> 需要绕过CFI
  -> 数据导向攻击
  -> 难度: 极高

当前攻击者能力:
  - 信息泄露是关键第一步
  - 一旦泄露足够信息，大多数机制可被绕过
  - CFI是当前最难绕过的机制
  - 内核缓解(SMEP/SMAP/KPTI)进一步增加难度
```

```
缓解机制的分层防御:

应用层:
  | - ASLR: 地址不可预测
  | - PIE: 代码地址随机
  | - DEP: 不可在数据区执行
  | - Canary: 栈溢出检测
  | - RELRO: GOT表保护
  | - CFI: 控制流合法

内核层:
  | - KASLR: 内核地址随机
  | - SMEP: 管理模式下不可执行用户代码
  | - SMAP: 管理模式下不可访问用户数据
  | - KPTI: 内核页表隔离
  | - KCFI: 内核控制流完整性
```

```bash
# 完整安全检查
checksec --file=./binary

# 查看GCC编译选项
gcc -Q --help=common | grep -i "stack-protector\|pie\|cf-protection\|relro"

# 编译时启用所有保护
gcc -o secure_binary source.c \
    -fstack-protector-strong \     # Stack Canary
    -D_FORTIFY_SOURCE=2 \          # 源码级保护
    -Wl,-z,relro \                 # RELRO
    -Wl,-z,now \                   # Full RELRO
    -fPIE -pie \                   # PIE
    -fcf-protection=full \         # CFI
    -fstack-clash-protection        # 栈冲突保护
```
