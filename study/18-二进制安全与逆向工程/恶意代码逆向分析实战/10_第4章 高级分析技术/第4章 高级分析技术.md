# 第4章 高级分析技术

当基础的静态分析和动态分析无法满足需求时，就需要运用更高级的分析技术，包括对抗反调试反虚拟机、代码解密与脱壳、注入技术分析、Rootkit分析等。

### 4.1 反调试技术与绕过

反调试是恶意代码保护自身不被逆向分析的重要手段。分析者需要了解常见的反调试技术及其绕过方法。

#### 4.1.1 常见反调试技术

**1. IsDebuggerPresent**

最简单的反调试方式，调用Windows API `IsDebuggerPresent` 检查是否存在调试器。

```asm
call IsDebuggerPresent
test eax, eax
jnz debug_detected
```

**绕过方法：**
- 在调试器中修改返回值（EAX置0）
- Hook `IsDebuggerPresent` 函数使其始终返回0
- 使用ScyllaHide等反反调试插件

**2. PEB反调试**

通过直接读取PEB（进程环境块）中的BeingDebugged标志位来检测调试器。

```asm
mov eax, fs:[30h]   ; 获取PEB地址
mov al, [eax+2]     ; 读取BeingDebugged字段
test al, al
jnz debug_detected
```

PEB中与反调试相关的字段：
- `BeingDebugged`（偏移0x2）：是否被调试
- `NtGlobalFlag`（偏移0x68）：全局标志，被调试时会设置某些标志位
- `ProcessHeap`（偏移0x18）：堆结构，堆头中也有调试相关的标志

**绕过方法：**
- 手动修改PEB中的BeingDebugged标志为0
- 修改NtGlobalFlag的值（正常为0x70，被调试时为0x7070）
- 使用调试器插件自动隐藏

**3. 时间检测**

通过测量代码执行时间来判断是否被调试（单步执行会导致执行时间显著增加）。

常见实现方式：
- 使用 `GetTickCount` 获取系统时间戳
- 使用 `QueryPerformanceCounter` 获取高精度计数器
- 使用 `rdtsc` 指令读取CPU时间戳计数器

```asm
rdtsc               ; 读取时间戳计数器
mov ebx, eax        ; 保存低32位
; ... 执行一段代码 ...
rdtsc               ; 再次读取
sub eax, ebx        ; 计算差值
cmp eax, 0x1000     ; 比较阈值
ja debug_detected   ; 差值过大则认为被调试
```

**绕过方法：**
- 在时间检测的比较指令处设置断点，修改比较结果
- 使用 `rdtsc` 虚拟化插件
- 设置条件断点，自动修改返回值

**4. 硬件断点检测**

检测调试寄存器（DR0-DR7）是否被设置了硬件断点。

```asm
pushad
mov eax, [esp+0x20] ; 获取CONTEXT结构指针
cmp dword [eax+0x04], 0  ; 检查DR0
jnz debug_detected
cmp dword [eax+0x08], 0  ; 检查DR1
jnz debug_detected
; ... 检查DR2, DR3, DR6, DR7 ...
popad
```

**绕过方法：**
- 避免使用硬件断点，改用软件断点（INT 3）或内存断点
- 使用插件修改调试寄存器的值

**5. 软件断点检测**

扫描代码段中是否存在 `0xCC`（INT 3指令，软件断点）。

```asm
mov edi, offset function_to_check
mov ecx, function_size
mov al, 0CCh        ; INT 3 指令码
repne scasb
jz debug_detected
```

**绕过方法：**
- 使用硬件断点代替软件断点
- 使用内存断点
- 修改检测代码

**6. NtQueryInformationProcess**

使用Native API `NtQueryInformationProcess` 查询进程信息，包括调试端口等。

```asm
push 0
push 4
push offset info
push ProcessDebugPort  ; 7
push -1                ; 当前进程
call NtQueryInformationProcess
cmp dword [info], 0
jnz debug_detected
```

可用于反调试的信息类：
- `ProcessDebugPort`（7）：调试端口
- `ProcessDebugFlags`（0x1F）：调试标志
- `ProcessDebugObjectHandle`（0x1E）：调试对象句柄

**7. 异常处理反调试**

故意触发异常，利用异常处理机制检测是否被调试。正常情况下异常会被程序自己的异常处理函数处理，被调试时异常会先交给调试器。

**8. 窗口类检测**

检测是否存在常见调试器的窗口类名（如OllyDbg的 "OLLYDBG"、IDA的 "ida"）。

#### 4.1.2 反反调试工具与插件

**ScyllaHide：**
- x64dbg和IDA的反反调试插件
- 能够隐藏多种反调试检测
- 支持PEB伪装、Hook反调试API、隐藏调试器窗口等
- 开源且持续更新

**StrongOD：**
- OllyDbg的反反调试插件
- 功能强大，支持多种反调试绕过
- 包含驱动级别的隐藏功能

**Phantom：**
- OllyDbg的插件，用于绕过各种反调试和反虚拟机检测

**手动绕过技巧：**
1. 定位反调试代码（通过搜索特征API或常量）
2. 在检测点设置断点
3. 修改检测结果或跳过检测代码
4. 使用NOP填充或修改跳转指令

### 4.2 反虚拟机检测与绕过

恶意代码经常检测运行环境是否为虚拟机，如果是虚拟机则不执行恶意行为或直接退出。

#### 4.2.1 常见虚拟机检测方法

**1. VMware/VirtualBox特定文件和服务检测**

检测虚拟机的特征文件、驱动和服务：

- VMware相关：`vm3dservice`、`vmtoolsd`、`vmmouse.sys`、`vmhgfs.sys`
- VirtualBox相关：`VBoxService`、`VBoxTray`、`VBoxGuest.sys`
- 检测 `C:\Windows\System32\drivers\` 下的VM相关驱动文件
- 检测运行中的VM相关进程

**2. 注册表检测**

检查注册表中是否存在虚拟机相关的键值：

- VMware：`HKLM\SOFTWARE\VMware, Inc.\VMware Tools`
- VirtualBox：`HKLM\SOFTWARE\Oracle\VirtualBox Guest Additions`
- 硬件信息中的VM相关字符串（如 "VMware"、"VirtualBox"）

**3. SIDT方法（Red Pill）**

通过执行 `sidt` 指令读取中断描述符表寄存器（IDTR）的内容。在虚拟机中，IDT的地址通常与物理机不同（VMware的IDT基址通常在 `0xFFXXXXXX` 范围）。

```asm
sidt [esp-2]
mov eax, [esp+2]     ; 获取IDT基址
cmp ah, 0xFF         ; 检查高字节是否为0xFF
je vm_detected
```

类似的还有 `sgdt`（读GDT）和 `sldt`（读LDT）指令。

**4. CPUID指令检测**

通过 `cpuid` 指令检测CPU信息中的虚拟化特征。

```asm
mov eax, 1
cpuid
test ecx, 0x80000000 ; 检查ECX的第31位（hypervisor位）
jnz vm_detected
```

还可以通过CPUID的leaf 0x40000000获取Hypervisor的品牌字符串：
- VMware："VMwareVMware"
- VirtualBox："VBoxVBoxVBox"
- KVM："KVMKVMKVM"
- Hyper-V："Microsoft Hv"

**5. 特定端口I/O检测**

VMware使用特定的I/O端口（0x5658/X86）进行宿主机和虚拟机之间的通信。

```asm
mov eax, 'VMXh'      ; VMware魔法值
mov ebx, 0           ; 返回值测试
mov ecx, 10          ; 获取VMware版本
mov edx, 'VX'        ; 端口号0x5658
in eax, dx           ; 从端口读取
cmp ebx, 'VMXh'      ; 检查ebx是否被修改为VMXh
je vm_detected
```

**6. MAC地址检测**

虚拟机的网卡MAC地址通常有特定的前缀：
- VMware：`00:0C:29`、`00:50:56`、`00:1C:14`
- VirtualBox：`08:00:27`
- Hyper-V：`00:15:5D`

#### 4.2.2 绕过方法

**1. 修改虚拟机配置文件**

**VMware绕过：**

在 `.vmx` 配置文件中添加以下设置：

```

isolation.tools.setPtrLocation.disable = "TRUE"
isolation.tools.setVersion.disable = "TRUE"
isolation.tools.getVersion.disable = "TRUE"
monitor_control.disable_directexec = "TRUE"
monitor_control.disable_chksimd = "TRUE"
monitor_control.disable_ntreloc = "TRUE"
monitor_control.disable_selfmod = "TRUE"
monitor_control.disable_reloc = "TRUE"
monitor_control.disable_btinout = "TRUE"
monitor_control.disable_btmemspace = "TRUE"
monitor_control.disable_btpriv = "TRUE"
monitor_control.disable_btseg = "TRUE"
```

**2. 修改MAC地址**

将虚拟机的网卡MAC地址修改为非虚拟机厂商的前缀。

**3. 安装反虚拟机工具**

- **VMware Hardened**：VMware虚拟机加固配置工具
- **VBoxHardened**：VirtualBox虚拟机加固配置工具
- **AntiVmDetect**：综合反检测工具

**4. 调试器中手动绕过**

- 在虚拟机检测代码处设置断点
- 修改检测结果或跳过检测代码
- 利用条件断点自动修改返回值

**5. 使用物理机分析**

对于检测特别严格的恶意代码，可以使用专用的物理分析机（配置独立硬盘、支持快速还原）。

### 4.3 代码解密与脱壳

#### 4.3.1 常见加密算法识别

**对称加密算法：**

**AES（Advanced Encryption Standard）：**
- 数据块大小：128位（16字节）
- 密钥长度：128、192、256位
- 识别特征：
  - 存在S盒（256字节的查找表，值为 `63 7C 77 7B F2 6B 6F...`）
  - 有明显的轮密钥扩展过程
  - 轮常数Rcon数组：`01 02 04 08 10 20 40 80 1B 36...`
  - 通常处理16字节对齐的数据块

**DES / 3DES：**
- 数据块大小：64位（8字节）
- 密钥长度：56位（DES）、112/168位（3DES）
- 识别特征：
  - 初始置换表（IP）和逆初始置换表（IP-1）
  - 8个S盒（每个4x16的查找表）
  - 16轮Feistel结构

**RC4：**
- 流加密算法，无固定数据块大小
- 识别特征：
  - 256字节的S盒初始化过程（0-255依次赋值）
  - 密钥调度算法（KSA）：使用密钥打乱S盒
  - 伪随机生成算法（PRGA）：生成密钥流并与明文异或
  - 代码中通常有对256字节数组的初始化循环

**XOR：**
- 最简单的加密方式
- 识别特征：
  - 循环中包含XOR指令
  - 密钥长度固定（单字节或多字节）
  - 加密和解密使用相同的操作

**非对称加密算法：**

**RSA：**
- 识别特征：
  - 大整数运算（模幂运算）
  - 使用Windows CryptoAPI（`CryptEncrypt`、`CryptImportKey`等）
  - 公钥特征：以 `MIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQ...` 开头的Base64编码
  - 私钥特征：以 `MIIEvgIBADANBgkqhkiG9w0BAQEFAASCBKgwggSkAgEAAoIBAQ...` 开头

#### 4.3.2 OEP查找技术

**1. ESP定律（堆栈平衡法）**

适用于大多数压缩壳，原理是：壳代码在解压原始代码前会 `pushad` 保存所有寄存器，解压完成后 `popad` 恢复寄存器，此时ESP的值与刚进入壳时相同。

操作步骤：
1. 载入程序到调试器，在入口点停下
2. 观察ESP的值（如 `0x0012FFA4`）
3. 对ESP指向的栈地址设置硬件写入断点：`hr esp`
4. 按F9运行程序
5. 程序会在 `popad` 指令处中断（因为popad会修改栈上的数据）
6. 单步执行几步，通常很快就能到达OEP

**2. 最后一次异常法**

部分壳利用异常处理来混淆控制流，可以通过忽略异常直到最后一次异常来接近OEP。

操作步骤：
1. 载入程序，忽略所有异常（Shift+F9）
2. 记录每次异常的位置
3. 当异常不再出现时，程序可能已经到达或接近OEP
4. 此时可配合内存断点精确定位OEP

**3. 内存断点法**

原理是原始代码被解压到代码段后才会被执行，在代码段上设置内存执行断点。

操作步骤：
1. 查看PE文件的 `.text` 节区的虚拟地址和大小
2. 在内存映射中找到对应的内存区域
3. 对该区域设置内存访问/执行断点
4. 运行程序，当EIP进入该区域时中断
5. 此时通常就在OEP或OEP附近

**4. 单步跟踪法**

对于简单的壳，可以使用单步执行（F8步过、F7步入）配合跟踪，逐步找到跳转到原始代码的位置。这种方法比较耗时，但最直观。

#### 4.3.3 Import表重建

找到OEP并Dump内存后，通常还需要重建导入表（Import Table），因为壳通常会破坏或加密原始的导入表。

**Scylla工具使用：**

Scylla是x64dbg的插件，也是独立工具，用于PE转储和导入表重建。

操作步骤：
1. 在调试器中到达OEP
2. 启动Scylla（在x64dbg中是菜单 Plugins → Scylla）
3. 确认目标进程和OEP地址正确
4. 点击 "IAT AutoSearch" 自动搜索IAT
5. 点击 "Get Imports" 获取导入函数列表
6. 检查导入函数是否有效（无效的会标红）
7. 点击 "Fix Dump" 选择之前Dump的文件进行修复
8. 如果有无效的导入函数，可能需要手动调整IAT地址和大小

**Import REConstructor：**

另一款经典的导入表重建工具，通常与OllyDbg配合使用。

### 4.4 注入技术分析

进程注入是恶意代码最常用的技术之一，用于隐藏自身执行、提升权限、绕过防护等。

#### 4.4.1 经典进程注入

**流程：**
1. `OpenProcess`：以足够的权限打开目标进程
2. `VirtualAllocEx`：在目标进程中分配一块内存
3. `WriteProcessMemory`：将Shellcode或DLL路径写入目标进程内存
4. `CreateRemoteThread`：在目标进程中创建远程线程执行注入的代码

**识别特征：**
- 导入表中存在 `OpenProcess`、`VirtualAllocEx`、`WriteProcessMemory`、`CreateRemoteThread` 等API
- 动态获取这些API地址
- Shellcode特征（如以 `55 8B EC` 或 `FC E8 89...` 开头）

**分析技巧：**
- 在 `WriteProcessMemory` 处设置断点
- 查看缓冲区内容（要注入的Shellcode或数据）
- 在 `CreateRemoteThread` 处设置断点
- 查看起始地址（lpStartAddress）参数
- 可以将Shellcode Dump出来单独分析

#### 4.4.2 DLL注入

**原理：** 通过在目标进程中加载恶意DLL来执行代码。

**实现方式：**
1. 调用 `CreateRemoteThread`，传入 `LoadLibraryA` 作为线程函数，传入DLL路径作为参数
2. 目标进程加载DLL并执行DllMain中的代码

**识别特征：**
- 恶意代码释放一个DLL文件
- 调用 `CreateRemoteThread` 时，lpStartAddress是 `LoadLibraryA` 的地址
- lpParameter是DLL路径字符串的地址

#### 4.4.3 APC注入

**APC（Asynchronous Procedure Call）注入**是一种更隐蔽的注入方式，利用异步过程调用机制。

**原理：**
- 每个线程都有一个APC队列
- 当线程处于可报警等待状态（alertable wait）时，会执行APC队列中的函数
- 调用 `QueueUserAPC` 可以向指定线程的APC队列中插入一个APC对象

**优势：**
- 比 `CreateRemoteThread` 更隐蔽，不容易被监控工具检测到
- 不需要创建新线程，直接利用现有线程执行

**识别特征：**
- 使用 `QueueUserAPC` 或 `NtQueueApcThread` API
- 配合 `OpenThread`、`SuspendThread`、`ResumeThread` 等使用
- 通常会遍历进程中的所有线程，向每个线程插入APC

#### 4.4.4 反射式DLL注入（Reflective DLL Injection）

反射式DLL注入是一种高级注入技术，不需要将DLL写入磁盘，也不需要依赖 `LoadLibrary`。

**原理：**
- 将DLL的完整镜像注入到目标进程内存中
- 执行一个称为"反射式加载器"的代码，手动完成DLL的加载过程：
  - 解析PE头，分配合适的内存
  - 处理基址重定位
  - 解析导入表，加载依赖的DLL
  - 调用DllMain
- 整个过程不依赖系统的加载器，也不会在模块列表中出现

**特点：**
- 无文件落地，难以检测
- 进程的模块列表中看不到被注入的DLL
- 可绕过基于模块枚举的安全检测

**分析要点：**
- 注意内存中可疑的可执行区域
- 使用内存扫描工具检测未被模块列表记录的代码
- 分析Shellcode中的PE解析和重定位逻辑

### 4.5 Rootkit分析

Rootkit是一种能够隐藏自身及其他恶意程序存在的工具集，通常工作在内核层，分析难度较高。

#### 4.5.1 Rootkit分类

**按运行层级分类：**

1. **用户态Rootkit**：
   - 运行在Ring 3
   - 通过Hook用户态API实现隐藏
   - 相对容易检测和分析
   - 典型技术：IAT Hook、Inline Hook、EAT Hook

2. **内核态Rootkit**：
   - 运行在Ring 0
   - 通过修改内核数据结构或Hook内核函数实现隐藏
   - 分析难度大，需要内核调试能力
   - 典型技术：SSDT Hook、Inline Hook、DKOM

3. **Bootkit**：
   - 感染MBR或VBR，在操作系统启动前获得控制权
   - 可以在操作系统加载前就注入恶意代码
   - 极难检测和清除

4. **固件Rootkit**：
   - 植入BIOS、UEFI、网卡固件、硬盘固件等
   - 即使重装系统也无法清除
   - 极为罕见但危害极大

#### 4.5.2 常见Rootkit技术

**1. SSDT Hook**

SSDT（System Service Descriptor Table）是系统服务描述符表，包含了所有系统调用服务例程的地址。Rootkit通过修改SSDT中的函数地址来Hook系统调用。

**检测方法：**
- 对比SSDT中函数地址与 `ntoskrnl.exe` 中的原始地址
- 如果函数地址不在 `ntoskrnl.exe` 的模块范围内，说明被Hook了
- 工具：Sreng、IceSword、PCHunter

**2. DKOM（Direct Kernel Object Manipulation）**

直接修改内核对象来实现隐藏。例如，从活动进程链表（EPROCESS的ActiveProcessLinks）中摘除进程对象，使系统无法枚举到该进程。

**检测方法：**
- 多渠道交叉对比进程列表
- 对比CSRSS中的进程列表与通过系统调用获取的进程列表
- 扫描EPROCESS池查找未链接的进程对象

**3. IRP Hook**

Hook驱动对象的IRP（I/O Request Packet）处理函数，拦截和修改I/O请求。常用于隐藏文件、注册表项等。

**检测方法：**
- 检查驱动对象的MajorFunction表
- 对比各IRP处理函数的地址是否在驱动模块范围内

**4. System Call Table Hook / syscall Hook**

x64系统上SSDT的保护更强，Rootkit可能使用其他方式Hook系统调用，如修改MSR寄存器的LSTAR来Hook `syscall` 指令。

#### 4.5.3 Rootkit分析方法

**静态分析：**
- 分析恶意驱动文件（.sys）
- 查看驱动的导入表（导入了哪些内核函数）
- 反汇编驱动的入口点和派遣函数
- 识别内核Hook模式和隐藏技术

**动态分析：**
- 使用内核调试器（WinDbg）进行双机调试
- 在虚拟机中加载驱动并观察行为
- 使用ARK工具（如PCHunter、PowerTool）检测系统中的Rootkit痕迹

**常用ARK工具：**
- **PCHunter**：功能强大的ARK工具，支持进程、驱动、网络、注册表等多方面检测
- **PowerTool**：集进程管理、文件管理、注册表管理、驱动管理于一体
- **IceSword**：经典的ARK工具（更新较慢）
- **GMER**：专门的Rootkit检测工具

#### 4.5.4 驱动分析基础

**驱动入口点：**

驱动的入口点是 `DriverEntry` 函数，类似于用户态程序的 `main` 函数。

```c
NTSTATUS DriverEntry(
    _In_ PDRIVER_OBJECT  DriverObject,
    _In_ PUNICODE_STRING RegistryPath
);
```

DriverEntry的主要工作：
1. 初始化驱动对象
2. 设置各个IRP的派遣函数（MajorFunction数组）
3. 设置卸载函数（DriverUnload）
4. 创建设备对象和符号链接
5. 执行其他初始化工作

**IRP派遣函数：**

驱动通过IRP（I/O Request Packet）与上层应用和下层硬件通信。每个驱动对象有一个 `MajorFunction` 数组，包含了各种IRP主功能号对应的处理函数。

常见的IRP主功能号：
- `IRP_MJ_CREATE`：创建/打开设备
- `IRP_MJ_CLOSE`：关闭设备
- `IRP_MJ_READ`：读操作
- `IRP_MJ_WRITE`：写操作
- `IRP_MJ_DEVICE_CONTROL`：设备控制（最常用的通信方式）

**应用层与驱动通信：**

应用层通过 `CreateFile` 打开设备，然后通过 `DeviceIoControl` 发送控制码与驱动通信。
