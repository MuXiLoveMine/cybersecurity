# 云平台安全配置

> 本文档详细介绍主流云平台的安全配置实践，涵盖身份与访问管理、网络安全、数据安全、日志审计等核心领域，结合 AWS 和阿里云两大平台提供实际配置案例。

---

## 一、AWS 安全配置

### 1.1 IAM（身份与访问管理）

#### 1.1.1 IAM 核心概念

| 概念 | 说明 |
|------|------|
| 用户（User） | 具有长期凭证的身份实体，代表人或应用 |
| 组（Group） | 用户的集合，便于批量授权 |
| 角色（Role） | 临时凭证的身份，可被用户/服务/账户扮演 |
| 策略（Policy） | JSON 格式的权限定义文档 |
| 访问密钥（Access Key） | 用于 API/CLI 访问的密钥对（Access Key ID + Secret Access Key） |

#### 1.1.2 IAM 策略结构

IAM 策略是 JSON 格式的文档，定义了允许或拒绝的操作。

**策略基本结构**：

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowS3ReadAccess",
            "Effect": "Allow",
            "Action": [
                "s3:GetObject",
                "s3:ListBucket"
            ],
            "Resource": [
                "arn:aws:s3:::my-bucket",
                "arn:aws:s3:::my-bucket/*"
            ],
            "Condition": {
                "IpAddress": {
                    "aws:SourceIp": "192.168.1.0/24"
                }
            }
        }
    ]
}
```

**字段说明**：
- **Version**：策略语言版本，固定为 "2012-10-17"
- **Statement**：策略语句数组，可以有多条
- **Sid**：语句标识符（可选），用于描述策略目的
- **Effect**：效果，"Allow"（允许）或 "Deny"（拒绝）
- **Action**：操作列表，格式为 `服务:操作`，如 `s3:GetObject`
- **Resource**：资源列表，ARN 格式
- **Condition**：条件（可选），满足条件时策略才生效

#### 1.1.3 IAM 安全最佳实践

| 最佳实践 | 说明 | 配置方式 |
|----------|------|----------|
| 启用 MFA | 根账号和所有用户启用多因素认证 | IAM 控制台 → 用户 → 安全凭证 → 分配 MFA 设备 |
| 最小权限原则 | 只授予必要的最小权限 | 使用 AWS 托管策略或自定义精细策略 |
| 使用角色而非长期密钥 | 应用通过角色获取临时凭证 | EC2 实例配置文件、Lambda 执行角色 |
| 定期轮换密钥 | 访问密钥定期更换 | IAM 控制台或 API 轮换 |
| 密码策略 | 设置强密码策略 | IAM 账户设置 → 密码策略 |
| 最小化根账号使用 | 日常操作不使用根账号 | 创建管理员用户进行日常管理 |
| 权限边界 | 限制用户/角色的最大权限 | Permissions Boundary |
| 定期审计权限 | 检查是否有权限过大 | IAM Access Analyzer、Access Advisor |

#### 1.1.4 危险的 IAM 策略示例

**危险策略 1：完全管理员权限（绝对禁止给普通用户）**
```json
{
    "Effect": "Allow",
    "Action": "*",
    "Resource": "*"
}
```
**风险**：拥有所有 AWS 服务的完全访问权限，一旦泄露可造成毁灭性损失。

**危险策略 2：资源通配符 + 敏感操作**
```json
{
    "Effect": "Allow",
    "Action": "s3:*",
    "Resource": "*"
}
```
**风险**：可访问所有 S3 存储桶，包括其他账户的公开桶，可能导致数据泄露。

**危险策略 3：过宽的角色信任策略**
```json
{
    "Effect": "Allow",
    "Principal": {
        "AWS": "*"
    },
    "Action": "sts:AssumeRole"
}
```
**风险**：任何 AWS 账户都可以扮演该角色，严重的权限泄露风险。

### 1.2 S3（简单存储服务）安全配置

#### 1.2.1 S3 安全配置清单

| 配置项 | 安全要求 | 风险等级 |
|--------|----------|----------|
| 阻止公开访问 | 启用（Block all public access） | 高危 |
| 存储桶策略 | 最小权限，禁止 Principal: "*" | 高危 |
| ACL | 私有（Private） | 高危 |
| 服务端加密 | 启用（SSE-KMS 或 SSE-S3） | 中危 |
| 版本控制 | 启用 | 中危 |
| 访问日志 | 启用 | 中危 |
| MFA 删除 | 启用（可选） | 中危 |
| 对象锁定 | 按需启用（WORM） | 低危 |
| 传输加密 | 强制 HTTPS | 中危 |

#### 1.2.2 安全的存储桶策略示例

**示例 1：仅允许特定 VPC 访问**
```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowOnlyFromVPC",
            "Effect": "Allow",
            "Principal": "*",
            "Action": "s3:GetObject",
            "Resource": "arn:aws:s3:::my-secure-bucket/*",
            "Condition": {
                "StringEquals": {
                    "aws:SourceVpc": "vpc-12345678"
                }
            }
        }
    ]
}
```

**示例 2：强制 HTTPS 传输**
```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "ForceSSLOnly",
            "Effect": "Deny",
            "Principal": "*",
            "Action": "s3:*",
            "Resource": [
                "arn:aws:s3:::my-secure-bucket",
                "arn:aws:s3:::my-secure-bucket/*"
            ],
            "Condition": {
                "Bool": {
                    "aws:SecureTransport": "false"
                }
            }
        }
    ]
}
```

**示例 3：限制特定 IP 访问**
```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowSpecificIP",
            "Effect": "Allow",
            "Principal": "*",
            "Action": "s3:GetObject",
            "Resource": "arn:aws:s3:::my-secure-bucket/*",
            "Condition": {
                "IpAddress": {
                    "aws:SourceIp": "10.0.0.0/8"
                }
            }
        }
    ]
}
```

#### 1.2.3 S3 公开访问检测与修复

**检测公开存储桶的方法**：
1. AWS 控制台：S3 → 权限 → 阻止公开访问
2. AWS CLI：`aws s3api get-bucket-policy-status --bucket my-bucket`
3. 使用 S3 Access Analyzer
4. 使用 Prowler、Scout Suite 等审计工具

**修复步骤**：
1. 启用"阻止全部公开访问"（Block all public access）
2. 审查存储桶策略，移除公开访问权限
3. 审查 ACL，设置为私有
4. 启用访问日志，审计历史访问记录

### 1.3 EC2（弹性计算云）安全配置

#### 1.3.1 EC2 安全基线

| 配置项 | 安全要求 |
|--------|----------|
| 实例元数据服务 | 使用 IMDSv2（需要会话令牌） |
| 密钥对 | 使用强密钥，禁止共享 |
| IAM 角色 | 为实例分配角色，而非使用访问密钥 |
| 安全组 | 最小权限原则，限制入站访问 |
| 操作系统 | 及时安装安全补丁 |
| 安全软件 | 安装主机安全/HIDS |
| 远程访问 | 限制 SSH/RDP 来源 IP |
| 存储加密 | EBS 卷启用加密 |

#### 1.3.2 实例元数据服务（IMDS）安全

**IMDSv1 vs IMDSv2**：
- **IMDSv1**：直接 GET 请求即可获取元数据，存在 SSRF 利用风险
- **IMDSv2**：需要先 PUT 请求获取会话令牌，再使用令牌访问元数据

**启用 IMDSv2**：
```bash
# 修改实例为仅 IMDSv2
aws ec2 modify-instance-metadata-options \
    --instance-id i-1234567890abcdef0 \
    --http-tokens required \
    --http-endpoint enabled
```

**元数据服务可获取的敏感信息**：
- 实例角色的临时凭证（`/latest/meta-data/iam/security-credentials/role-name`）
- 实例 ID、IP、AMI ID
- 用户数据（User Data）
- 公有密钥

#### 1.3.3 EC2 安全加固清单

**操作系统加固**：
- 禁用 root 用户 SSH 登录
- 使用密钥认证，禁用密码登录
- 修改 SSH 默认端口（可选）
- 配置 fail2ban 防暴力破解
- 启用防火墙（iptables/ufw）
- 定期更新系统补丁

**应用加固**：
- Web 服务器配置 WAF
- 数据库禁止公网访问
- 敏感配置文件加密存储
- 日志集中收集

### 1.4 VPC（虚拟私有云）与安全组

#### 1.4.1 VPC 网络架构设计

```
                    Internet
                        │
                   Internet Gateway
                        │
          ┌─────────────┴─────────────┐
          │                           │
     公有子网 1a                  公有子网 1b
     (Bastion/NAT GW)            (Bastion/NAT GW)
          │                           │
    路由表（公有）              路由表（公有）
          │                           │
          └─────────────┬─────────────┘
                        │
          ┌─────────────┴─────────────┐
          │                           │
     私有子网 1a                  私有子网 1b
     (Web/应用服务器)            (Web/应用服务器)
          │                           │
    路由表（私有）              路由表（私有）
          │                           │
          └─────────────┬─────────────┘
                        │
          ┌─────────────┴─────────────┐
          │                           │
    数据子网 1a                  数据子网 1b
     (数据库)                     (数据库)
```

**设计原则**：
1. **多可用区部署**：提高可用性
2. **分层网络**：公有子网放对外服务，私有子网放内部服务，数据子网放数据库
3. **最小暴露原则**：尽量减少公网暴露的资源
4. **安全分层**：安全组 + NACL 多层防护

#### 1.4.2 安全组（Security Group）配置

**安全组特点**：
- 有状态（Stateful）：入站允许则出站自动允许响应
- 实例级别的防火墙
- 只支持 Allow 规则，不支持 Deny 规则
- 可配置多个安全组

**安全组最佳实践**：

| 最佳实践 | 说明 |
|----------|------|
| 最小权限 | 只开放必要的端口和来源 |
| 命名清晰 | 用有意义的名称，如 web-sg、db-sg |
| 按角色分组 | 同类角色的实例使用相同安全组 |
| 限制来源 | 尽量指定安全组或具体 IP，不用 0.0.0.0/0 |
| 禁止全开放 | 禁止 0.0.0.0/0 到所有端口 |
| 定期审计 | 定期审查安全组规则 |

**危险的安全组配置示例**：

| 危险配置 | 风险 | 正确做法 |
|----------|------|----------|
| 入站规则：0.0.0.0/0 到 22 端口 | SSH 暴露给全网，易被暴力破解 | 限制为公司 IP 或堡垒机 IP |
| 入站规则：0.0.0.0/0 到 3306 端口 | MySQL 数据库公网暴露 | 数据库放私有子网，来源设为应用安全组 |
| 入站规则：0.0.0.0/0 到所有端口 | 等于没有防火墙 | 按需开放必要端口 |
| 出站规则：全部允许 0.0.0.0/0 | 被入侵后可对外发起任意连接 | 根据需要限制出站 |

**安全的安全组配置示例**：

Web 服务器安全组（web-sg）：
| 方向 | 协议 | 端口 | 来源 | 说明 |
|------|------|------|------|------|
| 入站 | TCP | 80 | 0.0.0.0/0 | HTTP 访问 |
| 入站 | TCP | 443 | 0.0.0.0/0 | HTTPS 访问 |
| 入站 | TCP | 22 | 10.0.1.0/24 | 仅允许堡垒机网段 SSH |
| 出站 | 全部 | 全部 | 0.0.0.0/0 | 出站按需限制 |

数据库安全组（db-sg）：
| 方向 | 协议 | 端口 | 来源 | 说明 |
|------|------|------|------|------|
| 入站 | TCP | 3306 | web-sg | 仅允许 Web 安全组访问 |
| 出站 | 全部 | 全部 | 0.0.0.0/0 | 出站按需限制 |

#### 1.4.3 网络 ACL（NACL）

**NACL 特点**：
- 无状态（Stateless）：入站和出站规则独立
- 子网级别的防火墙
- 支持 Allow 和 Deny 规则
- 规则按编号顺序匹配

**安全组 vs NACL**：

| 对比项 | 安全组 | 网络 ACL |
|--------|--------|----------|
| 作用层级 | 实例级别 | 子网级别 |
| 状态 | 有状态 | 无状态 |
| 规则类型 | 仅 Allow | Allow + Deny |
| 规则顺序 | 不按顺序 | 按编号顺序 |
| 默认配置 | 全部拒绝入站，全部允许出站 | 全部允许 |

### 1.5 CloudTrail（日志审计）

#### 1.5.1 CloudTrail 概述

AWS CloudTrail 记录 AWS 账户的 API 调用活动，包括：
- 谁发起了调用（身份）
- 调用了什么 API
- 何时调用（时间）
- 从哪里调用（IP 地址）
- 调用结果（成功/失败）

#### 1.5.2 CloudTrail 安全配置

| 配置项 | 安全要求 | 说明 |
|--------|----------|------|
| 启用全局跟踪 | 启用所有区域 | 覆盖所有 AWS 区域的 API 调用 |
| 日志文件验证 | 启用 | 防止日志被篡改 |
| 多区域跟踪 | 启用 | 记录所有区域的活动 |
| 管理事件 | 启用 | 记录管理操作 |
| 数据事件 | 按需启用 | 记录 S3、Lambda 等数据操作 |
| S3 存储桶加密 | 启用 | 日志文件加密存储 |
| 日志完整性 | 启用 S3 对象锁定 | 防止日志被删除 |
| 集中式日志 | 集中到安全账户 | 统一管理和分析 |

#### 1.5.3 关键监控事件

需要重点监控的 CloudTrail 事件：

| 事件名 | 说明 | 风险等级 |
|--------|------|----------|
| ConsoleLogin | 控制台登录 | 高危（失败登录） |
| CreateUser / DeleteUser | IAM 用户变更 | 高危 |
| CreateAccessKey | 创建访问密钥 | 高危 |
| AssumeRole | 扮演角色 | 中危 |
| PutBucketPolicy | 修改存储桶策略 | 高危 |
| AuthorizeSecurityGroupIngress | 安全组添加入站规则 | 高危 |
| RunInstances | 启动实例 | 中危 |
| StopInstances / TerminateInstances | 停止/终止实例 | 高危 |
| CreateTrail / UpdateTrail / DeleteTrail | CloudTrail 配置变更 | 高危 |

## 二、阿里云安全配置

### 2.1 RAM（资源访问管理）

#### 2.1.1 RAM 核心概念

| 概念 | 对应 AWS | 说明 |
|------|----------|------|
| RAM 用户 | IAM User | 具有长期凭证的身份 |
| RAM 用户组 | IAM Group | 用户的集合 |
| RAM 角色 | IAM Role | 临时凭证身份 |
| 权限策略 | IAM Policy | JSON 格式权限定义 |
| AccessKey | Access Key | API 访问密钥 |
| 身份提供商 | Identity Provider | SSO/SAML 联合身份 |

#### 2.1.2 RAM 策略结构

阿里云 RAM 策略与 AWS IAM 策略类似，也是 JSON 格式。

```json
{
    "Version": "1",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "oss:GetObject",
                "oss:ListObjects"
            ],
            "Resource": [
                "acs:oss:*:*:my-bucket",
                "acs:oss:*:*:my-bucket/*"
            ],
            "Condition": {
                "IpAddress": {
                    "acs:SourceIp": "192.168.1.0/24"
                }
            }
        }
    ]
}
```

**与 AWS 的主要区别**：
- Version 为 "1"（AWS 为 "2012-10-17"）
- 资源 ARN 前缀为 `acs:`（阿里云），AWS 为 `arn:aws:`
- 条件前缀为 `acs:`，AWS 为 `aws:`

#### 2.1.3 RAM 安全最佳实践

| 最佳实践 | 配置路径 |
|----------|----------|
| 启用 MFA | RAM 控制台 → 用户 → 安全信息 → 虚拟 MFA |
| 密码策略 | RAM 控制台 → 设置 → 密码策略 |
| 最小权限原则 | 使用自定义策略，避免使用 AliyunFullAccess |
| 定期轮换 AccessKey | RAM 控制台 → 用户 → AccessKey 管理 |
| 使用 RAM 角色 | ECS 实例 RAM 角色、函数计算执行角色 |
| 审计登录事件 | 操作审计（ActionTrail） |
| 限制登录 IP | RAM 策略中添加 IP 条件 |

### 2.2 OSS（对象存储服务）安全配置

#### 2.2.1 OSS 安全配置清单

| 配置项 | 安全要求 | 风险等级 |
|--------|----------|----------|
| 访问权限 | 私有（Private） | 高危 |
| Bucket 策略 | 最小权限原则 | 高危 |
| 服务端加密 | 启用（SSE-KMS 或 SSE-OSS） | 中危 |
| 版本控制 | 启用 | 中危 |
| 访问日志 | 启用 | 中危 |
| 防盗链 | 按需配置 Referer 白名单 | 中危 |
| HTTPS 传输 | 强制 HTTPS | 中危 |
| 跨域配置 | 最小化允许的来源 | 低危 |

#### 2.2.2 OSS Bucket 策略示例

**示例 1：仅允许 VPC 内访问**
```json
{
    "Version": "1",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": "*",
            "Action": [
                "oss:GetObject"
            ],
            "Resource": [
                "acs:oss:*:*:my-secure-bucket/*"
            ],
            "Condition": {
                "StringEquals": {
                    "oss:SourceVpc": "vpc-bp1234567890abcdef"
                }
            }
        }
    ]
}
```

**示例 2：仅允许特定 IP 段访问**
```json
{
    "Version": "1",
    "Statement": [
        {
            "Effect": "Deny",
            "Principal": "*",
            "Action": [
                "oss:*"
            ],
            "Resource": [
                "acs:oss:*:*:my-secure-bucket",
                "acs:oss:*:*:my-secure-bucket/*"
            ],
            "Condition": {
                "NotIpAddress": {
                    "acs:SourceIp": "10.0.0.0/8"
                }
            }
        }
    ]
}
```

#### 2.2.3 常见 OSS 安全问题与修复

**问题 1：Bucket 设置为公共读**
- **风险**：任何人都可以读取 Bucket 中的文件
- **检测**：控制台查看访问权限为"公共读"或"公共读写"
- **修复**：将访问权限改为"私有"

**问题 2：Bucket Policy 配置过宽**
- **风险**：策略中允许 `Principal: "*"` 且 Effect 为 Allow
- **检测**：检查 Bucket 策略中的 Principal 和 Action
- **修复**：限制 Principal 为特定 RAM 用户/角色，或添加条件限制

**问题 3：服务端加密未启用**
- **风险**：数据明文存储在磁盘上
- **检测**：查看 Bucket 加密配置
- **修复**：启用 SSE-OSS 或 SSE-KMS 加密

### 2.3 ECS（云服务器）安全配置

#### 2.3.1 ECS 安全基线

| 配置项 | 安全要求 |
|--------|----------|
| 远程访问 | 限制安全组来源 IP |
| 密钥对 | 使用 SSH 密钥对，禁用密码登录 |
| RAM 角色 | 为 ECS 实例绑定 RAM 角色 |
| 安全组 | 最小权限原则 |
| 系统加固 | 禁用 root 远程登录、修改 SSH 端口 |
| 补丁管理 | 定期更新系统补丁 |
| 安全软件 | 安装云安全中心 Agent |
| 磁盘加密 | 系统盘和数据盘启用加密 |

#### 2.3.2 ECS 实例元数据服务

阿里云 ECS 也提供元数据服务，地址为 `100.100.100.200`。

**可获取的敏感信息**：
- 实例 ID、IP、hostname
- RAM 角色的临时凭证
- 用户数据（user-data）

**防护措施**：
- 使用 IMDSv2（需要令牌）
- 为 ECS 实例角色授予最小权限
- 防御 SSRF 漏洞

### 2.4 安全组配置

阿里云安全组与 AWS 安全组功能类似，都是实例级别的有状态防火墙。

#### 2.4.1 安全组最佳实践

| 最佳实践 | 说明 |
|----------|------|
| 最小化入站规则 | 只开放必要的端口 |
| 限制授权对象 | 使用安全组 ID 或具体 IP，避免 0.0.0.0/0 |
| 按用途分组 | Web、数据库、应用分别使用不同安全组 |
| 禁止公网开放高危端口 | 22、3389、3306、6379 等不应对公网开放 |
| 定期审计 | 定期检查安全组规则的合理性 |

#### 2.4.2 常见高危端口清单

| 端口 | 服务 | 风险 | 建议 |
|------|------|------|------|
| 22 | SSH | 暴力破解 | 限制来源 IP，使用密钥登录 |
| 3389 | RDP | 暴力破解 | 限制来源 IP，使用强密码 |
| 3306 | MySQL | 数据泄露 | 禁止公网访问，放私有子网 |
| 6379 | Redis | 未授权访问 | 禁止公网访问，设置密码 |
| 27017 | MongoDB | 未授权访问 | 禁止公网访问，设置认证 |
| 11211 | Memcached | 未授权访问 | 禁止公网访问 |
| 2375 | Docker API | 远程代码执行 | 禁止公网访问 |

## 三、身份与访问管理（IAM/RAM）深度解析

### 3.1 权限模型对比

| 概念 | AWS IAM | 阿里云 RAM | 说明 |
|------|---------|------------|------|
| 策略评估逻辑 | 显式拒绝 > 显式允许 > 默认拒绝 | 相同 | 所有策略聚合评估 |
| 策略类型 | 托管策略、内联策略 | 系统策略、自定义策略 | 策略复用方式 |
| 权限边界 | Permissions Boundary | 权限边界（部分支持） | 限制最大权限 |
| 资源级权限 | 大多数服务支持 | 多数服务支持 | 精细到资源的权限 |
| 条件策略 | 丰富的条件键 | 丰富的条件键 | 基于条件的授权 |

### 3.2 常见权限错误

#### 错误 1：权限过大的管理员策略
```json
// 错误示例：给普通用户完全管理员权限
{
    "Effect": "Allow",
    "Action": "*",
    "Resource": "*"
}
```
**正确做法**：只授予需要的具体服务权限。

#### 错误 2：资源通配符
```json
// 错误示例：允许操作所有存储桶
{
    "Effect": "Allow",
    "Action": "s3:*",
    "Resource": "*"
}
```
**正确做法**：指定具体的资源 ARN。

#### 错误 3：角色信任策略过宽
```json
// 错误示例：允许所有人扮演角色
{
    "Effect": "Allow",
    "Principal": {
        "AWS": "*"
    },
    "Action": "sts:AssumeRole"
}
```
**正确做法**：只允许信任的账户或服务扮演角色。

### 3.3 最小权限原则实践

**实施步骤**：
1. **列出所需操作**：明确用户/角色需要执行的具体操作
2. **映射到 API**：将操作映射到具体的云服务 API
3. **确定资源范围**：明确操作涉及的具体资源
4. **添加条件限制**：如 IP 限制、时间限制、MFA 要求
5. **定期审计**：使用 Access Advisor 等工具检查权限使用情况
6. **及时回收**：移除不再使用的权限

**示例：S3 只读权限策略**
```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "S3ReadOnlySpecificBucket",
            "Effect": "Allow",
            "Action": [
                "s3:GetObject",
                "s3:ListBucket",
                "s3:GetBucketLocation"
            ],
            "Resource": [
                "arn:aws:s3:::my-app-data",
                "arn:aws:s3:::my-app-data/*"
            ],
            "Condition": {
                "IpAddress": {
                    "aws:SourceIp": "10.0.0.0/8"
                },
                "Bool": {
                    "aws:MultiFactorAuthPresent": "true"
                }
            }
        }
    ]
}
```

## 四、网络安全

### 4.1 VPC 安全架构

#### 4.1.1 网络分段设计

**三层架构模式**：
```
┌─────────────────────────────────────────────────────┐
│                    公有子网层                        │
│  (对外服务：负载均衡、堡垒机、NAT 网关)            │
├─────────────────────────────────────────────────────┤
│                    应用子网层                        │
│  (内部服务：Web 服务器、应用服务器)                │
├─────────────────────────────────────────────────────┤
│                    数据子网层                        │
│  (数据服务：数据库、缓存、消息队列)                │
└─────────────────────────────────────────────────────┘
```

**安全控制**：
- 公有子网 → 互联网：通过 Internet Gateway
- 应用子网 → 互联网：通过 NAT 网关（出站）
- 数据子网：不允许直接访问互联网
- 各层之间通过安全组控制访问

#### 4.1.2 网络访问路径

**入站访问**：
```
用户 → 负载均衡（公有子网） → Web 服务器（应用子网） → 数据库（数据子网）
```

**出站访问**：
```
应用服务器 → NAT 网关（公有子网） → 互联网
```

**管理访问**：
```
管理员 → 堡垒机（公有子网） → 应用服务器（应用子网）
```

### 4.2 安全组 vs NACL 深度对比

| 特性 | 安全组（Security Group） | 网络 ACL（NACL） |
|------|--------------------------|------------------|
| 操作级别 | 实例级别 | 子网级别 |
| 状态类型 | 有状态 | 无状态 |
| 支持的规则 | 仅 Allow | Allow + Deny |
| 规则顺序 | 不按顺序，全部评估 | 按编号顺序，匹配即停止 |
| 默认行为 | 入站拒绝，出站允许 | 全部允许 |
| 应用范围 | 关联的实例 | 子网内所有实例 |
| 配置复杂度 | 简单 | 较复杂 |
| 使用场景 | 实例级精细控制 | 子网级粗粒度控制 |

### 4.3 负载均衡安全

#### 4.3.1 负载均衡安全配置

| 配置项 | 安全要求 |
|--------|----------|
| 监听器协议 | 使用 HTTPS，禁用 HTTP 或配置重定向 |
| SSL/TLS 证书 | 使用强加密套件，禁用弱加密 |
| 安全组 | 限制后端服务只能被负载均衡访问 |
| 访问控制 | 配置黑白名单（按需） |
| WAF 集成 | 开启 WAF 防护 |
| DDoS 防护 | 开启 DDoS 防护 |
| 健康检查 | 配置合理的健康检查 |

#### 4.3.2 HTTPS 配置最佳实践
- 使用 TLS 1.2 及以上版本
- 禁用 SSLv3、TLS 1.0、TLS 1.1
- 使用强加密套件（如 ECDHE-RSA-AES256-GCM-SHA384）
- 证书有效期管理，自动续期
- 启用 HTTP Strict Transport Security (HSTS)

## 五、数据安全

### 5.1 存储加密

#### 5.1.1 加密类型

| 加密类型 | 说明 | 场景 |
|----------|------|------|
| 服务端加密（SSE） | 数据写入磁盘时由服务端加密 | 存储加密，对用户透明 |
| 客户端加密（CSE） | 数据上传前由客户端加密 | 极高安全要求，密钥自己掌控 |
| 传输加密 | SSL/TLS 加密传输过程 | 防止数据在传输中被窃取 |

#### 5.1.2 S3/OSS 服务端加密选项

| 选项 | 密钥管理 | 适用场景 |
|------|----------|----------|
| SSE-S3 / SSE-OSS | 云厂商管理密钥 | 简单加密需求 |
| SSE-KMS | KMS 管理密钥，可审计 | 需要密钥使用审计 |
| SSE-C / BYOK | 客户自己提供密钥 | 完全掌控密钥 |

### 5.2 数据库安全

#### 5.2.1 云数据库安全配置清单

| 配置项 | 安全要求 |
|--------|----------|
| 网络隔离 | 部署在私有子网，不分配公网 IP |
| 访问控制 | 白名单限制访问来源 |
| 强密码 | 设置强密码策略，定期更换 |
| 最小权限 | 数据库账号只授予必要权限 |
| 存储加密 | 启用 TDE（透明数据加密） |
| 传输加密 | 启用 SSL 连接 |
| 审计日志 | 开启数据库审计 |
| 备份 | 定期备份，测试恢复 |
| 补丁 | 及时应用数据库补丁 |

#### 5.2.2 常见数据库安全问题

**问题 1：数据库公网暴露**
- **风险**：直接面临互联网攻击，暴力破解、漏洞利用
- **修复**：将数据库迁移到私有子网，通过内网访问

**问题 2：弱口令/默认口令**
- **风险**：易被暴力破解
- **修复**：设置强密码（12 位以上，包含大小写、数字、特殊字符）

**问题 3：未启用 SSL**
- **风险**：数据传输过程中可能被窃听
- **修复**：启用 SSL/TLS 加密连接

### 5.3 密钥管理（KMS）

#### 5.3.1 KMS 核心功能
- 密钥创建与管理
- 密钥轮换
- 密钥使用审计
- 数据加密/解密 API
- 与云服务深度集成

#### 5.3.2 密钥管理最佳实践
1. **密钥分类**：按数据类型和业务使用不同密钥
2. **定期轮换**：启用自动密钥轮换（建议每年至少一次）
3. **权限控制**：严格控制谁可以使用和管理密钥
4. **密钥审计**：监控密钥使用情况
5. **多区域备份**：关键密钥多区域备份

### 6.2 关键审计日志类型

| 日志类型 | AWS | 阿里云 | 用途 |
|----------|-----|--------|------|
| API 操作日志 | CloudTrail | 操作审计 | 记录所有云资源操作 |

### 6.3 审计最佳实践

1. **开启全量审计**：所有 API 操作、关键服务访问日志全部开启
2. **集中化管理**：日志集中存储到独立的安全账户
3. **防篡改保护**：日志存储启用版本控制和对象锁定
4. **定期审计**：定期分析日志，发现异常行为
5. **实时告警**：配置关键事件的实时告警
6. **长期保存**：根据合规要求保存足够长时间（等保要求 6 个月以上）

## 七、安全配置实际案例

### 案例一：初创公司云安全配置

**场景**：某 20 人初创公司，业务全部在 AWS 上运行。

**安全配置方案**：

| 领域 | 配置措施 |
|------|----------|
| IAM | 所有用户启用 MFA；开发人员使用 IAM 用户，不使用根账号；EC2 使用角色而非密钥 |
| 网络 | VPC 分为公有和私有子网；Web 服务器放私有子网，通过 ALB 对外提供服务 |
| 存储 | S3 全部私有，启用加密和版本控制；敏感数据使用 KMS 加密 |
| 数据库 | RDS 放私有子网，不分配公网 IP；启用加密和自动备份 |
| 审计 | 开启 CloudTrail 全区域跟踪；关键操作配置告警 |
| 服务器 | 使用 Amazon Linux 2，启用自动更新；安装 SSM Agent 统一管理 |

### 案例二：金融企业云安全合规配置

**场景**：某金融机构，需要满足等保三级和行业监管要求。

**安全配置方案**：

| 领域 | 配置措施 |
|------|----------|
| 身份认证 | 强密码策略 + MFA + IP 白名单 + 登录审计 |
| 网络安全 | 网络分层架构 + 安全组严格控制 + WAF + DDoS 防护 |
| 数据安全 | 全链路加密（传输+存储）+ 数据分类分级 + 密钥分级管理 |
| 审计日志 | 操作审计 + 数据库审计 + 应用日志 + 日志保存 1 年以上 |
| 访问控制 | 最小权限 + 权限定期审计 + 特权操作审批 |
| 安全运营 | 7×24 安全监控 + 漏洞管理 + 渗透测试 + 应急响应 |

---

> **小结**：云平台安全配置的核心是遵循最小权限原则，从身份、网络、数据、审计四个维度构建纵深防御体系。配置错误是云安全最大的风险，必须建立持续的配置审计和合规检查机制。
