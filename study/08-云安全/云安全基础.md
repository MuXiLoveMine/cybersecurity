# 云安全基础

> 本文档系统介绍云计算安全的基础知识，包括云计算概念、责任共担模型、安全威胁、安全标准以及著名云安全事件。

---

## 一、云计算概述

### 1.1 云计算定义

云计算（Cloud Computing）是一种通过网络按需提供可弹性扩展的计算资源的服务模式。用户无需购买和维护物理硬件，而是通过互联网访问计算、存储、数据库、网络等资源，按使用量付费。

**云计算的五大核心特征**（NIST 定义）：

| 特征 | 说明 |
|------|------|
| 按需自助服务 | 用户可自动按需获取计算能力，无需与服务提供商人工交互 |
| 广泛的网络接入 | 通过网络访问，支持各种客户端（手机、平板、笔记本） |
| 资源池化 | 提供商的计算资源池化，以多租户模式服务多个用户 |
| 快速弹性 | 可快速弹性地提供和释放资源，按需增减 |
| 可计量的服务 | 按使用量计费，资源使用可监控、控制和报告 |

### 1.2 云服务模式（IaaS / PaaS / SaaS）

#### 1.2.1 IaaS（基础设施即服务）

**定义**：提供虚拟化的计算基础设施，包括虚拟机、存储、网络等基础资源。

**典型服务**：
- 云服务器（AWS EC2、阿里云 ECS、Azure VM）
- 对象存储（AWS S3、阿里云 OSS、Azure Blob）
- 虚拟网络（AWS VPC、阿里云 VPC、Azure VNet）
- 块存储、文件存储

**用户责任**：
- 操作系统安装与维护
- 中间件、运行时配置
- 应用程序部署
- 数据安全
- 身份认证与访问控制
- 网络安全配置（安全组等）

**适用场景**：
- 需要完全控制基础设施的企业
- 有特殊操作系统/软件需求
- 传统应用迁移上云

**案例**：某创业公司使用 AWS EC2 部署 Web 应用，自行管理 Linux 系统、Nginx、应用代码和数据库。

---

#### 1.2.2 PaaS（平台即服务）

**定义**：提供应用开发、运行和管理的平台环境，用户无需管理底层基础设施。

**典型服务**：
- 云数据库（AWS RDS、阿里云 RDS、Azure SQL）
- 容器服务（AWS ECS/EKS、阿里云 ACK、Azure AKS）
- 无服务器计算（AWS Lambda、阿里云函数计算、Azure Functions）
- 消息队列、缓存服务
- 开发平台（Heroku、Google App Engine）

**用户责任**：
- 应用程序开发与部署
- 数据安全
- 身份认证与访问控制
- 应用层安全配置

**适用场景**：
- 快速应用开发与部署
- 微服务架构
- 无需关心底层运维

**案例**：某电商平台使用阿里云 RDS（MySQL）作为数据库，云厂商负责数据库安装、补丁、备份、高可用，客户只负责表结构设计、数据操作和访问控制。

---

#### 1.2.3 SaaS（软件即服务）

**定义**：通过互联网提供完整的软件应用，用户直接使用，无需管理任何基础设施。

**典型服务**：
- 企业邮箱（腾讯企业邮、Gmail）
- CRM 系统（Salesforce、纷享销客）
- 协作工具（飞书、钉钉、Slack）
- 在线办公（Office 365、Google Workspace）
- ERP、HR 系统

**用户责任**：
- 数据输入与管理
- 用户账号管理
- 基本的配置安全
- 数据导出与备份

**适用场景**：
- 通用办公软件
- 标准化业务应用
- 快速上线、降低成本

**案例**：某公司使用 Salesforce CRM 管理客户关系，Salesforce 负责所有基础设施、平台、应用的安全，客户只负责账号配置、数据录入和权限管理。

---

#### 1.2.4 三种模式对比

| 对比项 | IaaS | PaaS | SaaS |
|--------|------|------|------|
| 用户管理 | 操作系统及以上 | 应用及数据 | 数据和配置 |
| 厂商管理 | 物理设施、虚拟化 | 基础设施、平台 | 全部基础设施和应用 |
| 灵活性 | 最高 | 中等 | 最低 |
| 运维成本 | 最高 | 中等 | 最低 |
| 用户技术要求 | 高 | 中 | 低 |
| 安全责任（客户） | 最大 | 中等 | 最小 |
| 典型代表 | AWS EC2 | AWS RDS | Salesforce |

### 1.3 云部署模式

#### 1.3.1 公有云（Public Cloud）
- 由第三方云服务提供商运营，向公众开放
- 多租户共享资源
- 成本低、弹性好、无需维护
- 代表：阿里云、AWS、Azure

#### 1.3.2 私有云（Private Cloud）
- 为单个组织单独构建
- 可部署在企业内部或由第三方托管
- 安全性高、可控性强
- 成本高、弹性相对较弱
- 代表：VMware、OpenStack

#### 1.3.3 混合云（Hybrid Cloud）
- 公有云 + 私有云的组合
- 敏感数据放私有云，非敏感业务放公有云
- 兼顾安全与灵活性
- 挑战：数据同步、统一管理、网络连接

#### 1.3.4 多云（Multi-Cloud）
- 同时使用多个公有云服务商
- 避免厂商锁定
- 可选择各厂商优势服务
- 挑战：管理复杂度、安全策略统一

## 二、云安全责任共担模型

### 2.1 核心概念

**责任共担模型（Shared Responsibility Model）** 是云安全的基石。云厂商负责云基础设施的安全，客户负责自己在云上的数据和应用的安全。

> **关键理解**：云安全 OF 云 vs 云安全 IN 云
> - 云厂商负责 "Security OF the Cloud"（云本身的安全）
> - 客户负责 "Security IN the Cloud"（云上内容的安全）

| 安全领域 | IaaS（客户负责） | PaaS（客户负责） | SaaS（客户负责） |
|----------|------------------|------------------|------------------|
| 数据安全 | 全部 | 全部 | 自有数据 |
| 应用安全 | 全部 | 客户开发的应用 | 无 |
| 身份与访问管理 | 全部 | 大部分 | 账号配置 |
| 操作系统安全 | 全部 | 无 | 无 |
| 网络安全 | 安全组等配置 | 部分配置 | 无 |
| 虚拟化安全 | 无 | 无 | 无 |
| 物理安全 | 无 | 无 | 无 |
| 数据库安全 | 全部 | 权限、数据 | 无 |
| 补丁管理 | OS 及以上 | 平台级由厂商 | 全部由厂商 |

### 2.4 实际案例：责任边界的混淆

**案例场景**：
某公司使用 AWS EC2 部署 Web 应用，服务器被入侵后数据泄露。AWS 表示基础设施运行正常，责任在客户。客户认为云厂商应该负责安全。

**分析**：
- EC2 属于 IaaS 服务
- AWS 负责物理设施、虚拟化层、EC2 服务本身的安全
- 客户负责操作系统加固、补丁更新、应用安全、访问控制配置
- 如果是因为客户未及时打补丁导致入侵，责任在客户
- 如果是因为 AWS 虚拟化层漏洞导致宿主机被攻破，责任在 AWS

**教训**：
明确责任边界是云安全的第一步，不能简单地认为"上云就安全了"或"安全都是云厂商的事"。

## 三、云安全威胁与挑战

### 3.1 云安全顶级威胁（CSA Top Threats）

根据云安全联盟（CSA）发布的《云计算顶级威胁报告》，主要威胁包括：

#### 3.1.1 数据泄露（Data Breaches）
**威胁描述**：敏感数据被未授权访问、窃取或泄露。

**常见原因**：
- 存储桶配置错误（公开访问）
- 弱口令或凭证泄露
- API 安全漏洞
- 内部人员恶意泄露
- 供应链攻击

**实际案例**：
2019 年，Capital One 数据泄露事件中，攻击者利用 AWS WAF 配置错误，通过 SSRF 漏洞访问元数据服务获取角色凭证，进而访问 S3 存储桶，泄露超过 1 亿客户的个人信息。

#### 3.1.2 配置错误、变更管理不足
**威胁描述**：云资源配置错误导致安全漏洞。

**常见错误类型**：
- 存储桶公开访问
- 安全组端口全开放（0.0.0.0/0）
- IAM 权限过大
- 数据库公网暴露
- 未启用加密
- 未启用日志审计

**统计数据**：
- 据 Gartner 预测，到 2025 年，99% 的云安全失败将由客户自身配置错误导致
- 错误配置是云数据泄露的首要原因

#### 3.1.3 身份与访问管理薄弱
**威胁描述**：身份认证和访问控制存在缺陷，导致未授权访问。

**常见问题**：
- 权限过大（过度授权）
- 长期密钥未轮换
- 未启用多因素认证（MFA）
- 角色信任策略过宽
- 废弃账号未清理
- 根账号日常使用

#### 3.1.4 不安全的接口与 API
**威胁描述**：云服务 API 设计或实现存在安全漏洞。

**常见问题**：
- API 未授权访问
- 弱认证机制
- 缺乏速率限制
- 敏感信息明文传输
- API 密钥泄露

#### 3.1.5 账户劫持
**威胁描述**：攻击者窃取用户凭证，控制云账户。

**攻击方式**：
- 钓鱼攻击获取凭证
- 凭证泄露（代码仓库、日志文件）
- 社会工程学攻击
- 暴力破解弱口令

#### 3.1.6 内部威胁
**威胁描述**：企业内部人员恶意或误操作导致安全事件。

**类型**：
- 恶意内部人员：窃取数据、破坏系统
- 疏忽大意：误删数据、配置错误
- 第三方人员：供应商、合作伙伴

#### 3.1.7 共享技术漏洞
**威胁描述**：云基础设施共享导致的安全风险。

**风险点**：
- 虚拟化漏洞（如 VMware 逃逸）
- 容器逃逸
- 多租户隔离缺陷
- 宿主机漏洞影响客户虚拟机

### 3.2 云安全的独特挑战

| 挑战 | 说明 | 传统环境 vs 云环境 |
|------|------|-------------------|
| 边界模糊 | 云环境没有明确的物理边界，网络边界动态变化 | 传统：固定物理边界 → 云：软件定义边界 |
| 资产动态性 | 云资源弹性伸缩，IP、实例随时变化 | 传统：固定资产 → 云：动态资产 |
| 多租户共享 | 多用户共享基础设施，隔离依赖软件 | 传统：物理隔离 → 云：逻辑隔离 |
| 责任共担 | 安全责任由厂商和客户共同承担 | 传统：全部自己负责 → 云：分工负责 |
| API 驱动 | 一切操作通过 API 完成，API 安全至关重要 | 传统：物理/控制台操作 → 云：API 驱动 |
| 可见性不足 | 对底层基础设施缺乏可见性 | 传统：完全可见 → 云：黑盒底层 |
| 合规复杂性 | 不同地区、行业合规要求不同 | 传统：自主合规 → 云：共同合规 |

## 四、云安全标准

### 4.1 CSA CCM（云控制矩阵）

#### 4.1.1 概述
CSA（Cloud Security Alliance，云安全联盟）是全球领先的云安全组织，CCM（Cloud Controls Matrix，云控制矩阵）是其发布的云安全控制框架。

**最新版本**：CCM v4.0

#### 4.1.2 CCM 控制域

CCM 包含 17 个控制域，覆盖云安全的各个方面：

| 控制域 | 代码 | 说明 |
|--------|------|------|
| 审计与保证 | CCM-AAR | 审计日志、合规验证 |
| 应用安全 | CCM-APP | 应用开发安全、API 安全 |
| 密码学 | CCM-CEK | 加密、密钥管理 |
| 数据中心安全 | CCM-DCS | 物理安全、环境安全 |
| 数据安全与生命周期管理 | CCM-DSL | 数据分类、加密、销毁 |
| 治理、风险管理与合规 | CCM-GRC | 安全治理、风险管理 |
| 人力资源安全 | CCM-HRS | 人员背景调查、安全培训 |
| 身份与访问管理 | CCM-IAM | 身份认证、访问控制 |
| 基础设施与虚拟化安全 | CCM-IVS | 虚拟化安全、基础设施安全 |
| 互操作性与可移植性 | CCM-IPY | 数据和应用可移植性 |
| 运维安全 | CCM-OPS | 变更管理、漏洞管理 |
| 人员安全 | CCM-PES | 人员安全管理 |
| 物理安全 | CCM-PHY | 物理访问控制 |
| 风险管理 | CCM-RSK | 风险评估、风险处理 |
| 安全架构 | CCM-SEC | 安全架构设计 |
| 供应链管理、透明度与问责 | CCM-STA | 第三方管理、供应链安全 |
| 威胁与脆弱性管理 | CCM-TVM | 威胁检测、漏洞管理 |

#### 4.1.3 CCM 的价值
- 提供统一的云安全评估标准
- 帮助云厂商建立安全体系
- 帮助客户评估云服务商安全能力
- 可映射到多个合规标准（ISO 27001、SOC 2、PCI DSS 等）

### 4.2 等保 2.0 云计算安全扩展要求

#### 4.2.1 概述
《网络安全等级保护基本要求》（GB/T 22239-2019）简称"等保 2.0"，其中包含云计算安全扩展要求。

**适用范围**：
- 等级保护对象采用云计算技术构建时，除满足通用要求外，还应满足云计算安全扩展要求
- 适用于云服务商和云服务客户

#### 4.2.2 云计算安全扩展要求主要内容

**1. 安全物理环境**
- 机房位置选择：云服务商机房应满足相应等级要求
- 物理访问控制：云服务商数据中心物理安全
- 防盗窃和防破坏

**2. 安全通信网络**
- 网络架构：云平台网络架构安全
- 通信传输：数据传输加密
- 可信验证：网络设备可信验证

**3. 安全区域边界**
- 边界防护：云平台与外部边界防护
- 访问控制：不同租户之间的访问控制
- 入侵防范：边界入侵检测/防御
- 安全审计：边界访问审计

**4. 安全计算环境**
- 身份鉴别：云租户身份认证
- 访问控制：云资源访问控制
- 安全审计：云操作审计
- 入侵防范：云环境入侵检测
- 数据完整性：数据完整性保护
- 数据保密性：数据加密保护
- 数据备份恢复：数据备份与恢复
- 剩余信息保护：数据销毁
- 个人信息保护：个人信息安全

**5. 安全管理中心**
- 系统管理：云平台系统管理
- 审计管理：安全审计管理
- 安全管理：安全策略管理
- 集中管控：安全集中管控

#### 4.2.3 云服务商与客户责任
等保 2.0 明确了云计算环境下的责任划分：
- **云服务商**：负责云平台基础设施的安全，提供安全能力
- **云服务客户**：负责自身业务系统和数据的安全
- 客户租用的云资源应纳入自身等级保护对象范围

### 4.3 ISO 27001 与云安全

#### 4.3.1 ISO 27001 概述
ISO 27001 是国际公认的信息安全管理体系（ISMS）标准，规定了建立、实施、维护和持续改进信息安全管理体系的要求。

**标准编号**：ISO/IEC 27001:2022

#### 4.3.2 云安全相关 ISO 标准

| 标准 | 名称 | 说明 |
|------|------|------|
| ISO 27001 | 信息安全管理体系要求 | 基础标准，适用于所有组织 |

| ISO 27018 | 公有云个人信息保护实践指南 | 针对公有云中个人数据保护 |

#### 4.3.3 ISO 27017 云安全控制要点
- 云服务中的职责划分

- 虚拟环境安全

## 六、著名云安全事件

### 6.1 Capital One 数据泄露事件（2019）

#### 事件概述
- **时间**：2019 年 7 月披露
- **涉及公司**：Capital One（美国第一资本金融公司）
- **影响**：超过 1.06 亿客户的个人信息泄露
- **数据类型**：姓名、地址、邮编、电话号码、邮箱、出生日期、收入信息、信用评分等

#### 攻击过程

```
攻击者（前 AWS 员工）
    │
    ├─ 发现 Capital One 的 WAF 配置存在 SSRF 漏洞
    │
    ├─ 利用 SSRF 访问 EC2 元数据服务（169.254.169.254）
    │   获取 EC2 实例角色的临时凭证
    │
    ├─ 使用获取的临时凭证调用 AWS API
    │
    └─ 访问 S3 存储桶，下载 1.06 亿客户数据
```

#### 根本原因

1. **WAF 配置错误**：Web 应用防火墙配置不当，存在 SSRF 漏洞
2. **EC2 角色权限过大**：关联的 IAM 角色拥有过多 S3 权限，违反最小权限原则
3. **元数据服务版本过低**：使用了 IMDSv1（无需令牌即可访问）
4. **缺乏异常检测**：大量数据下载未触发告警

#### 安全启示
- 严格遵循最小权限原则配置 IAM 角色
- 启用 IMDSv2，提升元数据服务安全性
- 部署 WAF 规则防御 SSRF 攻击
- 监控异常 API 调用和数据访问行为
- 定期进行渗透测试和安全审计

### 6.2 Uber 数据泄露事件（2016/2017）

#### 事件概述
- **时间**：2016 年发生，2017 年披露
- **涉及公司**：Uber（优步）
- **影响**：5700 万用户和司机数据泄露
- **数据类型**：姓名、邮箱、手机号、驾照号

#### 攻击过程
1. 攻击者在 GitHub 代码仓库中发现了 Uber 工程师提交的 AWS 访问密钥
2. 使用该密钥登录 Uber 的 AWS 账户
3. 访问 S3 存储桶，下载 5700 万用户数据
4. Uber 向攻击者支付 10 万美元"漏洞赏金"要求保密（隐瞒事件）

#### 根本原因
- **密钥管理混乱**：开发人员将生产环境密钥提交到公开代码仓库
- **权限过大**：该密钥拥有过高的 AWS 权限
- **密钥轮换缺失**：密钥长期未轮换
- **事件隐瞒**：未按规定披露数据泄露事件

#### 安全启示
- 禁止在代码中硬编码密钥，使用密钥管理服务
- 使用 Git 预提交钩子检查密钥泄露
- 实施密钥定期轮换策略
- 严格遵循最小权限原则
- 建立完善的事件响应和披露机制

### 6.3 无数 S3 存储桶泄露事件

#### 事件概述
多年来，因 AWS S3 存储桶配置错误（公开访问）导致的数据泄露事件层出不穷，涉及政府、企业、医疗等各个领域。

#### 典型案例
| 时间 | 机构 | 泄露数据 | 原因 |
|------|------|----------|------|
| 2017 | 美国国防部 | 18 亿条社交媒体数据 | S3 桶公开 |
| 2017 | Verizon | 1400 万客户数据 | 第三方配置错误 |
| 2018 | 美国空军 | 军官个人信息 | S3 桶公开可写 |
| 2019 | 多家医疗公司 | 数百万患者记录 | 存储桶无认证 |
| 2020 | 多家公司 | 数十亿条数据记录 | 配置错误 |

#### 常见配置错误
1. **存储桶策略允许公开访问**：`Principal: "*"` 且 `Effect: Allow`
2. **ACL 设置为公开读取**：Everyone 可读
3. **访问控制列表过宽**：未限制来源
4. **静态网站托管配置不当**
5. **跨账户访问配置错误**

#### 防护措施
- 默认拒绝公开访问（Block Public Access）
- 启用存储桶策略强制私有
- 定期审计存储桶权限
- 使用 S3 Access Analyzer 检测公开访问
- 启用 CloudTrail 监控存储桶操作

### 6.4 SolarWinds 供应链攻击（2020）

#### 事件概述
- **时间**：2020 年 12 月披露
- **影响范围**：全球约 1.8 万客户受影响，包括美国政府多个部门
- **攻击方式**：软件供应链攻击

#### 攻击过程

```
攻击者入侵 SolarWinds 公司
    │
    ├─ 植入后门到 Orion 平台软件更新包
    │
    ├─ SolarWinds 客户正常下载并安装更新
    │
    ├─ 后门程序在客户环境中激活
    │
    └─ 横向移动，窃取敏感数据
        │
        ├─ 美国国土安全部
        ├─ 美国国务院
        ├─ 美国财政部
        └─ 多家财富 500 强公司
```

#### 与云安全的关系
- 许多受影响客户将 SolarWinds 部署在云环境中
- 攻击者利用云环境的身份系统（如 Azure AD）进行横向移动
- 云环境的弹性和自动化特性放大了攻击影响范围
- 云供应链安全成为新的关注点

#### 安全启示
- 加强软件供应链安全管理
- 对第三方软件进行安全审查
- 实施零信任架构
- 加强云环境中的横向移动防护
- 监控异常的身份认证行为

### 6.5 国内云安全事件

#### 案例一：某电商平台 OSS 配置泄露
**事件**：某电商平台将用户头像存储在阿里云 OSS 中，由于 Bucket 策略配置错误，允许匿名列举和读取，导致数百万用户头像和手机号泄露。

**原因**：
- OSS Bucket 设置了公共读权限
- 服务端未做鉴权校验
- 文件名可预测（用户 ID 直接作为文件名）

#### 案例二：云服务器挖矿事件
**事件**：某公司云服务器被入侵，植入挖矿木马，CPU 使用率持续 100%，产生高额云费用。

**常见入侵途径**：
- Redis 未授权访问
- SSH 弱口令
- 应用漏洞（如 ThinkPHP、Struts2）
- Docker API 公开访问
