> 本文档系统介绍云原生安全的核心知识，包括容器安全、Kubernetes 安全、DevSecOps、镜像安全和微服务安全，配合实际配置示例和工具使用指南。

## 一、容器安全基础

### 1.1 容器与虚拟机的区别

| 特性 | 容器（Container） | 虚拟机（VM） |
|------|-------------------|--------------|
| 虚拟化层级 | 操作系统级虚拟化 | 硬件级虚拟化 |
| 内核共享 | 共享宿主机内核 | 每个 VM 有独立内核 |
| 隔离级别 | 进程级隔离（较弱） | 系统级隔离（较强） |
| 资源占用 | 轻量（MB 级） | 重量（GB 级） |
| 启动速度 | 秒级 | 分钟级 |
| 性能损耗 | 极小 | 较大 |
| 安全边界 | cgroup + namespace | Hypervisor |

**容器安全的核心挑战**：
- 共享内核带来的逃逸风险
- 镜像供应链安全
- 容器间隔离与横向移动
- 运行时安全监控
- 密钥与敏感信息管理

### 1.2 容器安全风险矩阵

| 风险类别 | 具体风险 | 严重程度 | 常见场景 |
|----------|----------|----------|----------|
| 镜像安全 | 基础镜像漏洞 | 高危 | 使用过时的基础镜像 |
| 镜像安全 | 恶意镜像 | 高危 | 从不可信来源拉取镜像 |
| 镜像安全 | 敏感信息泄露 | 高危 | Dockerfile 中硬编码密钥 |
| 运行时安全 | 容器逃逸 | 高危 | 特权容器 + 内核漏洞 |
| 运行时安全 | 权限提升 | 高危 | root 用户运行容器 |
| 运行时安全 | 资源滥用 | 中危 | 未设置资源限制 |
| 配置安全 | 特权容器 | 高危 | --privileged 参数 |
| 配置安全 | 挂载敏感目录 | 高危 | 挂载 /var/run/docker.sock |
| 网络安全 | 容器间未隔离 | 中危 | 默认网络模式 |
| 网络安全 | 端口暴露过多 | 中危 | -P 参数暴露所有端口 |

## 二、Docker 安全配置

### 2.1 Docker 安全基线

#### 2.1.1 Docker 守护进程安全

**1. 限制 Docker 守护进程网络访问**

默认情况下，Docker 守护进程监听 Unix socket（/var/run/docker.sock），不应暴露 TCP 端口。

```bash
# 危险配置：暴露 Docker API 到公网（绝对禁止）
dockerd -H tcp://0.0.0.0:2375

# 安全配置：仅监听 Unix socket（默认）
dockerd -H unix:///var/run/docker.sock

# 如需远程访问，使用 TLS 加密
dockerd --tlsverify --tlscacert=ca.pem --tlscert=server-cert.pem --tlskey=server-key.pem -H tcp://0.0.0.0:2376
```

**2. 启用 Docker 内容信任（Content Trust）**

Docker Content Trust (DCT) 用于验证镜像的签名和完整性，防止镜像被篡改。

```bash
# 启用内容信任
export DOCKER_CONTENT_TRUST=1

# 拉取镜像时会自动验证签名
docker pull nginx:latest
```

**3. 启用用户命名空间（User Namespaces）**

用户命名空间可将容器内的 root 用户映射到宿主机的非特权用户，降低容器逃逸后的影响。

```bash
# 修改 /etc/docker/daemon.json
{
    "userns-remap": "default"
}

# 重启 Docker 服务
systemctl restart docker
```

#### 2.1.2 Dockerfile 安全最佳实践

**不安全的 Dockerfile 示例**：
```dockerfile
# 危险 1：使用 latest 标签，不可控
FROM ubuntu:latest

# 危险 2：以 root 用户运行
USER root

# 危险 3：硬编码敏感信息
ENV DB_PASSWORD=supersecret
ENV API_KEY=AKIAIOSFODNN7EXAMPLE

# 危险 4：安装不必要的软件包，增加攻击面
RUN apt-get update && apt-get install -y \
    vim \
    netcat \
    curl \
    wget \
    && rm -rf /var/lib/apt/lists/*

# 危险 5：复制整个目录，可能包含敏感文件
COPY . /app

# 危险 6：暴露过多端口
EXPOSE 22 80 443 3306 6379

# 危险 7：使用 root 运行应用
CMD ["python", "app.py"]
```

**安全的 Dockerfile 示例**：
```dockerfile
# 安全 1：使用具体版本的基础镜像，最好是官方镜像
FROM python:3.11-slim-bookworm

# 安全 2：设置非 root 用户
RUN groupadd -r appuser && useradd -r -g appuser appuser

# 安全 3：只安装必要的依赖
RUN apt-get update && apt-get install -y --no-install-recommends \
    ca-certificates \
    && rm -rf /var/lib/apt/lists/*

# 安全 4：设置工作目录
WORKDIR /app

# 安全 5：先复制依赖文件，利用缓存
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 安全 6：只复制必要的代码文件
COPY src/ ./src/

# 安全 7：切换到非 root 用户
USER appuser

# 安全 8：只暴露必要的端口
EXPOSE 8080

# 安全 9：使用健康检查
HEALTHCHECK --interval=30s --timeout=3s \
    CMD curl -f http://localhost:8080/health || exit 1

# 安全 10：使用 exec 形式运行，确保信号正确传递
CMD ["python", "src/app.py"]
```

**Dockerfile 安全要点总结**：

| 要点 | 说明 | 实现方式 |
|------|------|----------|
| 使用官方基础镜像 | 减少恶意代码风险 | 从 Docker Hub 官方仓库拉取 |
| 指定具体版本标签 | 可重现构建 | 避免使用 latest |
| 最小化镜像 | 减少攻击面 | 使用 slim/alpine 变体，多阶段构建 |
| 非 root 用户运行 | 降低权限 | USER 指令 |
| 敏感信息不入镜像 | 防止密钥泄露 | 使用环境变量/Secret/构建参数 |
| 最小化复制内容 | 防止意外泄露 | .dockerignore，精确复制 |
| 健康检查 | 运行状态监控 | HEALTHCHECK 指令 |
| 多阶段构建 | 减小最终镜像大小 | FROM ... AS builder + FROM ... |

### 2.2 容器运行时安全配置

#### 2.2.1 危险的运行参数

**绝对禁止的参数**：

| 参数 | 风险 | 说明 |
|------|------|------|
| `--privileged` | 容器逃逸 | 授予容器几乎所有宿主机权限 |
| `--net=host` | 网络监听 | 共享宿主机网络命名空间 |
| `--pid=host` | 进程可见 | 共享宿主机 PID 命名空间 |
| `-v /var/run/docker.sock:/var/run/docker.sock` | 权限提升 | 可控制宿主机 Docker |
| `-v /proc:/proc` | 内核攻击 | 可访问宿主机 proc 文件系统 |
| `-v /sys:/sys` | 系统配置 | 可修改宿主机系统参数 |
| `-v /root:/root` | 数据窃取 | 可访问宿主机 root 目录 |
| `--cap-add=ALL` | 权限过大 | 授予所有 Linux capabilities |

#### 2.2.2 安全的容器启动参数

**推荐的安全启动命令**：

```bash
docker run -d \
    --name my-app \
    --read-only \                    # 只读根文件系统
    --tmpfs /tmp \                    # /tmp 使用 tmpfs
    --tmpfs /run \                    # /run 使用 tmpfs
    --memory=512m \                   # 内存限制
    --cpus=1 \                        # CPU 限制
    --pids-limit=100 \                # 进程数限制
    --user 1000:1000 \                # 非 root 用户
    --cap-drop=ALL \                  # 丢弃所有 capabilities
    --cap-add=NET_BIND_SERVICE \      # 只添加必要的 capability
    --security-opt=no-new-privileges \ # 禁止获取新权限
    --security-opt seccomp=default \  # seccomp 过滤
    --restart=on-failure:5 \          # 重启策略
    --network=my-network \            # 自定义网络
    -p 8080:8080 \                    # 只映射必要端口
    my-app:latest
```

#### 2.2.3 Linux Capabilities 详解

Capabilities 是 Linux 内核提供的权限细分机制，将 root 权限分解为多个独立的权限。

**常用 Capabilities**：

| Capability | 权限 | 是否通常需要 |
|------------|------|-------------|
| NET_BIND_SERVICE | 绑定小于 1024 的端口 | Web 服务可能需要 |
| NET_RAW | 使用 RAW 和 PACKET 套接字 | 通常不需要 |
| SYS_ADMIN | 系统管理权限（非常强大） | 几乎不需要 |
| SYS_PTRACE | 跟踪进程（ptrace） | 通常不需要 |
| DAC_OVERRIDE | 绕过文件读写权限检查 | 通常不需要 |

**最佳实践**：
- 默认使用 `--cap-drop=ALL` 丢弃所有 capabilities
- 只添加应用实际需要的 capability
- 优先使用非 root 用户替代 capabilities

### 2.3 Docker 网络安全

#### 2.3.1 Docker 网络模式

| 网络模式 | 说明 | 安全性 |

```bash
docker run -d --network my-app-network --name db mysql
```

2. **避免使用 host 网络模式**

3. **使用网络别名而非 --link**

4. **限制容器间通信**：

```bash
# 创建禁用 ICC（容器间通信）的网络
```

### 3.2 RBAC（基于角色的访问控制）

#### 3.2.1 RBAC 核心概念

| 资源 | 说明 |
|------|------|
| Role | 命名空间内的角色，定义权限规则 |
| ClusterRole | 集群级别的角色 |
| RoleBinding | 将 Role 绑定到用户/组/ServiceAccount |
| ClusterRoleBinding | 将 ClusterRole 绑定到用户/组/ServiceAccount |
| ServiceAccount | Pod 使用的身份 |

#### 3.2.2 RBAC 策略示例

**示例 1：命名空间只读权限（Role）**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: production
  name: pod-reader
rules:
- apiGroups: [""]  # "" 表示核心 API 组
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: production
subjects:
- kind: User
  name: alice
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**示例 2：集群管理员（ClusterRole，危险）**
```yaml
# 警告：这是集群完全管理员权限，应谨慎授予
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: cluster-admin-binding
subjects:
- kind: User
  name: admin-user
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: cluster-admin
  apiGroup: rbac.authorization.k8s.io
```

**示例 3：ServiceAccount 权限**
```yaml
# 创建 ServiceAccount
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-app-sa
  namespace: production
---
# 创建 Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: production
  name: configmap-reader
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list"]
---
# 绑定 Role 到 ServiceAccount
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: my-app-read-configmap
  namespace: production
subjects:
- kind: ServiceAccount
  name: my-app-sa
  namespace: production
roleRef:
  kind: Role
  name: configmap-reader
  apiGroup: rbac.authorization.k8s.io
```

#### 3.2.3 RBAC 安全最佳实践

| 最佳实践 | 说明 |
|----------|------|
| 最小权限原则 | 只授予必要的最小权限 |
| 避免使用 cluster-admin | 集群管理员权限应极少授予 |
| 使用命名空间隔离 | 不同环境/团队使用不同命名空间 |
| 定期审计 RBAC | 检查是否有权限过大的情况 |
| 谨慎使用通配符 | 避免在 resources 和 verbs 中使用 "*" |
| ServiceAccount 最小化 | 每个应用使用独立的 SA，权限最小化 |
| 禁用默认 SA 自动挂载 | 不需要时关闭 automountServiceAccountToken |

#### 3.2.4 危险的 RBAC 配置

**危险配置 1：通配符权限**
```yaml
# 危险：拥有所有资源的所有操作权限
rules:
- apiGroups: ["*"]
  resources: ["*"]
  verbs: ["*"]
```

**危险配置 2：可以创建 Pod 的权限 + 特权容器 = 逃逸**
```yaml
# 如果可以创建特权 Pod，基本等于获得节点 root 权限
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["create", "update"]
```

**危险配置 3：可以修改 ClusterRoleBinding**
```yaml
# 可以修改 ClusterRoleBinding = 可以提升自己的权限
rules:
- apiGroups: ["rbac.authorization.k8s.io"]
  resources: ["clusterrolebindings"]
  verbs: ["create", "update", "patch"]
```

### 3.3 Pod 安全上下文（Security Context）

#### 3.3.1 安全上下文配置

Pod 安全上下文定义了 Pod 和容器的安全设置。

**完整的安全配置示例**：
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  # Pod 级别的安全上下文
  securityContext:
    runAsNonRoot: true           # 禁止以 root 用户运行
    runAsUser: 1000              # 指定运行用户 ID
    runAsGroup: 3000             # 指定运行组 ID
    fsGroup: 2000                # 文件系统组 ID
    seccompProfile:
      type: RuntimeDefault       # 使用默认 seccomp 配置
  containers:
  - name: app
    image: my-app:latest
    # 容器级别的安全上下文
    securityContext:
      allowPrivilegeEscalation: false  # 禁止权限提升
      readOnlyRootFilesystem: true     # 只读根文件系统
      capabilities:
        drop:
        - ALL                          # 丢弃所有 capabilities
        add:
        - NET_BIND_SERVICE             # 只添加必要的
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "128Mi"
        cpu: "500m"
```

#### 3.3.2 Pod 安全策略（PSP）与 Pod 安全标准（PSS）

PodSecurityPolicy 已在 Kubernetes 1.25 中被移除，替代方案是 Pod Security Admission（PSA）和 Pod Security Standards（PSS）。

**Pod 安全标准（PSS）三个级别**：

| 级别 | 说明 | 适用场景 |
|------|------|----------|
| Privileged | 无限制，完全开放 | 系统级组件、需要特权的工作负载 |
| Baseline | 基本安全限制，防止常见的提权手段 | 默认策略，大多数应用 |
| Restricted | 严格限制，遵循当前 Pod 加固最佳实践 | 高安全要求环境、不可信代码 |

**启用 Pod 安全准入（PSA）**：
```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    # 强制实施 restricted 策略
    pod-security.kubernetes.io/enforce: restricted
    # 审计模式（记录但不阻止）
    pod-security.kubernetes.io/audit: restricted
    # 警告模式（给出警告但不阻止）
    pod-security.kubernetes.io/warn: restricted
```

### 3.4 网络策略（Network Policy）

#### 3.4.1 网络策略概述

默认情况下，Kubernetes 中所有 Pod 之间可以互相通信。网络策略用于限制 Pod 之间的网络流量。

**前提条件**：需要使用支持 NetworkPolicy 的网络插件，如 Calico、Cilium 等。

#### 3.4.2 网络策略示例

**示例 1：默认拒绝所有入站流量**
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: production
spec:
  podSelector: {}    # 空选择器匹配所有 Pod
  policyTypes:
  - Ingress
  # 没有 ingress 规则 = 拒绝所有入站
```

**示例 2：允许特定命名空间访问数据库**
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-app-to-db
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: database    # 匹配数据库 Pod
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: web     # 只允许 web Pod 访问
    ports:
    - protocol: TCP
      port: 5432       # 只允许 PostgreSQL 端口
```

**示例 3：限制出站流量**
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: restrict-egress
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes:
  - Egress
  egress:
  # 允许 DNS 查询
  - to:
    - namespaceSelector: {}
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
  # 允许访问数据库
  - to:
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: 5432
```

#### 3.4.3 网络策略最佳实践

1. **默认拒绝**：每个命名空间设置默认拒绝所有入站和出站流量
2. **白名单模式**：只显式允许必要的流量
3. **按应用分层**：Web → App → DB 逐层限制
4. **限制出站**：不仅限制入站，也要限制出站（防止横向移动和数据外发）
5. **命名空间隔离**：不同环境（dev/staging/prod）使用不同命名空间并设置网络策略

### 3.5 Secret 管理

#### 3.5.1 Secret 基础

Kubernetes Secret 用于存储敏感信息，如密码、令牌、密钥等。

**Secret 类型**：
- Opaque：通用 Secret，base64 编码
- kubernetes.io/service-account-token：ServiceAccount 令牌
- kubernetes.io/dockerconfigjson：Docker 镜像仓库凭证
- kubernetes.io/tls：TLS 证书

**Secret 使用示例**：
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  username: YWRtaW4=      # base64 编码的 "admin"
  password: cGFzc3dvcmQ=  # base64 编码的 "password"
---
# 在 Pod 中使用 Secret（环境变量方式）
apiVersion: v1
kind: Pod
metadata:
  name: app-pod
spec:
  containers:
  - name: app
    image: my-app
    env:
    - name: DB_USERNAME
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: username
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: password
---
# 在 Pod 中使用 Secret（挂载文件方式）
apiVersion: v1
kind: Pod
metadata:
  name: app-pod
spec:
  containers:
  - name: app
    image: my-app
    volumeMounts:
    - name: secret-volume
      mountPath: /etc/secrets
      readOnly: true
  volumes:
  - name: secret-volume
    secret:
      secretName: db-secret
```

#### 3.5.2 Secret 的安全问题

| 问题 | 说明 | 解决方案 |
|------|------|----------|
| base64 不是加密 | 只是编码，可直接解码 | 启用 etcd 加密 |
| etcd 中明文存储 | 默认情况下 Secret 在 etcd 中是明文 | 启用 etcd 静态加密 |
| 访问权限控制 | 能 list secret 的用户能看到所有 secret | RBAC 严格控制 Secret 访问 |
| 镜像中泄露 | 应用日志可能打印 Secret | 日志脱敏处理 |
| YAML 文件泄露 | Secret YAML 提交到代码仓库 | 使用 SealedSecret 或外部密钥管理 |

#### 3.5.3 Secret 安全最佳实践

1. **启用 etcd 加密**：
```yaml
# 在 kube-apiserver 配置中启用加密
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
    - secrets
    providers:
    - aescbc:
        keys:
        - name: key1
          secret: <base64-encoded-32-byte-key>
    - identity: {}
```

2. **使用外部密钥管理服务**：
   - HashiCorp Vault
   - AWS Secrets Manager
   - 阿里云密钥管理服务（KMS）
   - 通过 External Secrets Operator 同步到 K8s

3. **RBAC 严格控制 Secret 访问**

4. **不要在代码或配置文件中硬编码 Secret**

5. **定期轮换 Secret**

## 四、DevSecOps 与 CI/CD 安全

### 4.1 DevSecOps 概述

DevSecOps 是将安全融入 DevOps 流程的理念，在软件开发生命周期（SDLC）的每个阶段都考虑安全。

**安全左移（Shift Left）**：将安全工作从后期（生产环境）提前到早期（设计、开发、测试阶段），更早发现和修复安全问题，降低修复成本。

#### 4.1.1 DevSecOps 工具链

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│    代码提交    │  │   构建阶段    │  │   测试阶段    │  │   部署阶段    │
│  (Commit)    │  │   (Build)    │  │   (Test)     │  │  (Deploy)    │
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘
       │                │                │                │
       ▼                ▼                ▼                ▼
┌─────────────┐  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  SAST 扫描   │  │  镜像构建    │  │  DAST 测试   │  │  IaC 扫描    │
│  代码静态分析 │  │  镜像扫描    │  │  动态安全测试 │  │  配置合规检查 │
│  密钥检测    │  │  SCA 依赖检查│  │  模糊测试    │  │  准入控制    │
│  依赖检查    │  │  镜像签名    │  │  渗透测试    │  │  运行时监控  │
└─────────────┘  └─────────────┘  └─────────────┘  └─────────────┘
```

### 4.2 CI/CD 流水线安全

#### 4.2.1 CI/CD 流水线安全风险

| 风险 | 说明 |
|------|------|
| 凭证泄露 | CI/CD 配置中的密钥被泄露 |
| 代码投毒 | 攻击者通过 PR 注入恶意代码 |
| 供应链攻击 | 依赖包被篡改 |
| 镜像篡改 | 构建的镜像被篡改 |
| 权限过大 | CI/CD 系统拥有过多部署权限 |
| 流水线注入 | 构建脚本被篡改 |

#### 4.2.2 CI/CD 安全最佳实践

1. **凭证管理**：
   - 使用 CI/CD 系统的 Secrets 管理功能
   - 禁止在代码中硬编码密钥
   - 定期轮换 CI/CD 凭证

2. **代码安全**：
   - 代码审查（Code Review）
   - 静态代码分析（SAST）
   - 依赖漏洞扫描（SCA）
   - 密钥检测（Secret Scanning）

3. **构建安全**：
   - 使用可信的基础镜像
   - 镜像漏洞扫描
   - 镜像签名与验证
   - 最小化镜像（减少攻击面）

4. **部署安全**：
   - 基础设施即代码（IaC）安全扫描
   - 部署前安全门禁
   - 金丝雀发布/蓝绿部署
   - 最小权限的部署账号

#### 4.2.3 GitHub Actions 安全示例

```yaml
name: CI/CD Pipeline

on: [push, pull_request]

jobs:
  security-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 1. 代码静态分析（SAST）
      - name: Run SAST with SonarQube
        uses: sonarsource/sonarqube-scan-action@master
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}

      # 2. 依赖漏洞扫描（SCA）
      - name: Run SCA with Snyk
        uses: snyk/actions/node@master
        env:
          SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}
        with:
          args: test --severity-threshold=high

      # 3. 密钥检测
      - name: Secret Scanning
        uses: trufflesecurity/trufflehog@main
        with:
          path: .
          extra_args: --only-verified

      # 4. IaC 扫描
      - name: IaC Scan with Checkov
        uses: bridgecrewio/checkov-action@master
        with:
          directory: terraform/
          framework: terraform

  build-and-scan-image:
    runs-on: ubuntu-latest
    needs: security-scan
    steps:
      - uses: actions/checkout@v4

      # 5. 构建镜像
      - name: Build Docker image
        run: docker build -t my-app:${{ github.sha }} .

      # 6. 镜像漏洞扫描
      - name: Scan image with Trivy
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: my-app:${{ github.sha }}
          format: 'table'
          exit-code: '1'
          ignore-unfixed: true
          severity: 'CRITICAL,HIGH'

      # 7. 镜像签名
      - name: Sign image with Cosign
        run: |
          cosign sign --key ${{ secrets.COSIGN_PRIVATE_KEY }} \
            my-app:${{ github.sha }}
```

### 4.3 安全测试类型

| 测试类型 | 全称 | 阶段 | 说明 |
|----------|------|------|------|

## 五、镜像安全与镜像扫描

### 5.1 镜像安全风险

#### 5.1.1 镜像安全威胁

| 威胁类型 | 说明 | 示例 |
|----------|------|------|
| 漏洞镜像 | 基础镜像或应用包含已知漏洞 | Log4j、OpenSSL 漏洞 |
| 恶意镜像 | 镜像中植入恶意代码 | 挖矿木马、后门 |
| 敏感信息泄露 | 镜像中包含密钥、密码等 | Dockerfile 中的 ENV 密码 |
| 镜像篡改 | 镜像在传输或存储中被篡改 | 中间人攻击替换镜像 |
| 供应链攻击 | 基础镜像或依赖被投毒 | npm 包投毒、Docker Hub 恶意镜像 |
| 配置不当 | 镜像配置存在安全缺陷 | root 用户运行、开放过多端口 |

### 5.2 镜像安全防护措施

#### 5.2.1 镜像构建安全

1. **使用可信的基础镜像**：
   - 优先使用官方镜像
   - 验证镜像签名
   - 固定镜像版本（digest 而非 tag）

2. **最小化镜像**：
   - 使用 distroless 镜像
   - 使用 alpine/slim 变体
   - 多阶段构建
   - 删除不必要的工具和文件

3. **敏感信息保护**：
   - 使用 BuildKit 的 secret 挂载
   - 使用 multi-stage build 清除中间层敏感信息
   - 配置 .dockerignore 排除敏感文件

4. **非 root 用户**：
   - Dockerfile 中使用 USER 指令
   - 指定具体的 UID/GID

#### 5.2.2 多阶段构建示例

```dockerfile
# 构建阶段
FROM golang:1.21-alpine AS builder

WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -a -installsuffix cgo -o app .

# 最终阶段（使用最小镜像）
FROM gcr.io/distroless/static:nonroot

WORKDIR /app
# 只复制编译后的二进制文件
COPY --from=builder /app/app .

# 使用非 root 用户
USER nonroot:nonroot

EXPOSE 8080

CMD ["./app"]
```

### 5.3 镜像签名与验证

#### 5.3.1 Cosign 工具

Cosign 是 Sigstore 项目的一部分，用于容器镜像的签名和验证。

**使用示例**：
```bash
# 生成密钥对
cosign generate-key-pair

# 签名镜像
cosign sign --key cosign.key myregistry/myimage:tag

# 验证镜像签名
cosign verify --key cosign.pub myregistry/myimage:tag

# 在 Kubernetes 中通过准入控制器验证
# 使用 policy-controller 或 Kyverno
```

### 5.4 镜像扫描实践

#### 5.4.1 Trivy 详细使用

```bash
# 扫描镜像漏洞
trivy image nginx:1.24

# 指定严重级别
```

### 6.3 服务网格（Service Mesh）安全

#### 6.3.1 服务网格概述

服务网格是微服务架构中的基础设施层，负责处理服务间通信，提供流量管理、可观测性和安全功能。

**主流服务网格**：
- Istio：最流行，功能全面
- Linkerd：轻量级，简单易用
- Cilium Service Mesh：基于 eBPF，高性能

#### 6.3.2 Istio 安全功能

| 功能 | 说明 |
|------|------|
| mTLS | 服务间双向 TLS 认证，自动加密通信 |
| 身份认证 | 基于 SPIFFE 的服务身份 |
| 授权策略 | 细粒度的服务访问控制 |
| 对等认证 | 服务到服务的认证 |
| 请求认证 | 用户到服务的认证（JWT） |

#### 6.3.3 Istio mTLS 配置

**启用全局 mTLS（STRICT 模式）**：
```yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system
spec:
  mtls:
    mode: STRICT  # 强制 mTLS
```

**服务级授权策略**：
```yaml
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: httpbin-require-jwt
  namespace: default
spec:
  selector:
    matchLabels:
      app: httpbin
  action: ALLOW
  rules:
  - from:
    - source:
        requestPrincipals: ["*"]   # 需要有效的 JWT
    when:
    - key: request.auth.claims[role]
      values: ["admin", "user"]   # JWT 中需要有 role 声明
```

#### 6.3.4 零信任与服务网格

服务网格是实现零信任架构的重要技术基础：

- **身份认证**：每个服务都有唯一身份（SPIFFE ID）
- **mTLS**：所有服务间通信自动加密
- **细粒度授权**：基于身份的访问控制策略
- **可观测性**：完整的流量日志和追踪

## 七、云原生安全实际案例

### 案例一：Tesla 云账号被入侵（2018）

**事件**：攻击者发现 Tesla 的 Kubernetes 管理控制台暴露在公网上，其中一个 Pod 包含 AWS 访问密钥，攻击者利用密钥访问了 Tesla 的 AWS 资源。

**攻击路径**：
```
Kubernetes Dashboard 公网暴露
    │
    ▼
未授权访问 Dashboard
    │
    ▼
查看 Pod 中的环境变量
    │
    ▼
获取 AWS Access Key
    │
    ▼
访问 AWS 资源（数据窃取、挖矿）
```

**安全教训**：
- Kubernetes Dashboard 不应暴露在公网
- 不应在环境变量中存储敏感信息
- RBAC 应严格配置，禁止匿名访问
- 定期审计云凭证权限

### 案例二：容器挖矿事件

**场景**：某公司 Kubernetes 集群中出现异常 CPU 占用，排查发现被植入挖矿木马。

**入侵途径**：
1. 攻击者扫描公网，发现暴露的 Docker API（2375 端口）
2. 通过 Docker API 启动挖矿容器
3. 利用容器逃逸或横向移动感染更多节点

**防护措施**：
1. 禁止 Docker API 公网暴露
2. 启用 TLS 认证
3. 部署运行时安全监控（Falco）
4. 设置资源限制防止影响业务
5. 镜像仓库准入控制

### 案例三：CI/CD 流水线供应链攻击

**场景**：攻击者通过提交 PR（Pull Request）注入恶意代码到 CI/CD 流水线，窃取构建凭证。

**攻击方式**：
1. 在开源项目中提交看似正常的 PR
2. PR 中的代码修改了 CI/CD 配置
3. CI/CD 运行时执行了恶意代码
4. 恶意代码读取并外传了 CI Secrets

**防护措施**：
1. 对外部贡献者的 PR 进行人工审核
2. CI 流水线中敏感操作需要审批
3. Secrets 最小权限原则
4. 构建环境隔离
5. 监控 CI 运行异常

---

> **小结**：云原生安全是云安全的进阶方向，涵盖容器安全、Kubernetes 安全、DevSecOps 和微服务安全。核心思想是"安全左移"和"纵深防御"，通过自动化工具将安全融入开发流程的每个环节，同时在运行时持续监控和防护。
