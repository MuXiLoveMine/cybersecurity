## 一、网络流量分析概述

### 1.1 流量分析的重要性与应用场景

网络流量是网络行为的"指纹"。每一个数据包都携带源/目的地址、协议、载荷与时间戳，这些元数据组合起来能够还原网络中发生的一切。流量分析的核心价值在于"看见"——看见谁在和谁通信、传了什么数据、行为是否正常。

**主要应用场景：**

| 场景 | 说明 | 关键能力 |
|------|------|----------|
| 安全事件调查 | 排查入侵、定位失陷主机、还原攻击链 | 全流量回放、协议解码 |
| 威胁狩猎 | 主动发现潜伏的 APT、C2 通信 | 行为基线、异常检测 |
| DDoS 攻击防护 | 实时识别攻击流量并清洗 | 流量峰值检测、溯源 |
| 合规审计 | 满足等保、PCI-DSS 等审计要求 | 流量留存、日志归档 |
| 网络运维 | 排查延迟、丢包、环路等故障 | 协议分析、IO 图表 |
| 数据泄露取证 | 追踪外泄通道与外发数据量 | 流量回溯、会话重组 |

一个典型场景：某企业终端 EDR 报警某主机有可疑外联，但 EDR 只能看到进程行为，无法回答"它到底传了什么数据出去、和谁通信、通信频率如何"。这时必须依赖网络流量分析——调取该时段全流量 pcap，用 Wireshark 过滤出该主机的外联会话，发现每隔 60 秒向一个境外 IP 发送一个 128 字节的固定长度包，典型的心跳 Beaconing 行为，据此确认 C2 通信。

### 1.2 流量分析方法论：实时分析 vs 离线分析

**实时分析** 关注"正在发生"的流量，强调低延迟告警。典型工具是 IDS/IPS（Snort、Suricata）和流采样分析器（ElastiFlow、Nfsen）。实时分析适合 DDoS 清洗、即时阻断已知攻击，但由于只能处理当前流速，无法回溯历史，且在高带宽环境下受处理能力限制可能丢包。

**离线分析** 关注"已经发生"的流量，把全流量存成 pcap 后再慢慢分析。典型工具是 Wireshark、Moloch/Arkime、Zeek。离线分析的优势是"可回溯"——发现告警后可以回到任意时间点重放流量，适合深度取证与威胁狩猎。代价是存储成本高（1Gbps 链路满载一天约 10.8TB）。

```
实时分析链路:
  镜像/分流 ──→ IDS引擎(Snort/Suricata) ──→ 告警 ──→ SIEM
  特点: 毫秒级响应, 可联动阻断, 但无法回溯

离线分析链路:
  镜像/分流 ──→ 全流量采集(Moloch/n2disk) ──→ 存储池 ──→ Wireshark/Zeek 回溯分析
  特点: 可回溯任意时刻, 深度取证, 但存储成本高

最佳实践: 实时 + 离线并行部署
  实时链路: 快速告警与阻断
  离线链路: 深度取证与狩猎
```

### 1.3 流量数据来源

**1. 镜像端口（SPAN/RSPAN/Port Mirroring）**

交换机将一个或多个端口的流量复制到镜像端口，分析设备接在镜像端口上被动监听。这是最常用的流量获取方式，零侵入、不影响业务。

```
# Cisco 交换机配置 SPAN
monitor session 1 source interface Gi0/1 - 4 both
monitor session 1 destination interface Gi0/24

#华为交换机配置镜像
observe-port 1 interface GigabitEthernet0/0/24
interface GigabitEthernet0/0/1
  port-mirroring to observe-port 1 inbound
```

镜像端口的局限：交换机背板带宽不足时镜像流量会丢包；RSPAN 跨交换机时受中间链路带宽限制。

**2. 网络分流器（Network TAP）**

TAP 是一种硬件设备，串接在链路物理层，把光/电信号复制一份输出给分析设备。相比 SPAN，TAP 不消耗交换机资源、不丢包、支持全双工复制，适合核心链路的全流量采集。缺点是需要物理改接线，成本高。

**3. NetFlow/sFlow**

NetFlow/sFlow 不是全流量，而是流记录（元数据）。路由器/交换机按流聚合后只输出"五元组+字节数+包数+时间"等统计信息，数据量极小（约全流量的 0.1%~1%）。适合大范围、跨地域的流量趋势监控和异常流量初筛，但无法看到应用层载荷。

```
三种来源对比:

┌─────────────┬──────────┬──────────┬──────────┬──────────┐
│   来源      │ 数据量   │ 载荷可见 │ 部署侵入 │ 适用场景 │
├─────────────┼──────────┼──────────┼──────────┼──────────┤
│ SPAN镜像    │ 全流量   │ 是       │ 低       │ 单点深度分析 │
│ 网络TAP     │ 全流量   │ 是       │ 中(物理) │ 核心链路全流量 │
│ NetFlow     │ ~1%      │ 否       │ 低       │ 大范围趋势/异常初筛 │
│ sFlow       │ ~0.1%    │ 否       │ 低       │ 超大带宽采样监控 │
└─────────────┴──────────┴──────────┴──────────┴──────────┘
```

实战建议：关键互联网出口用 TAP + 全流量采集做深度分析，内网核心用 SPAN + IDS 做实时告警，全网用 NetFlow 做趋势基线。三层互补。

## 二、Wireshark 深入使用

### 2.1 高级过滤技巧

Wireshark 有两套过滤器：捕获过滤器（BPF 语法，抓包时生效）和显示过滤器（Wireshark 专有语法，抓包后过滤）。

**捕获过滤器（BPF 语法）：**

```
# 只抓某主机的80端口流量
host 192.168.1.100 and port 80

# 抓某网段的所有流量
net 192.168.1.0/24

# 排除 ARP 和广播，减少噪音
not arp and not (broadcast or multicast)

# 只抓 TCP SYN 包（扫描检测）
tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0

# 只抓 DNS 查询
udp port 53 or tcp port 53
```

**显示过滤器（实战常用）：**

```
# 基础字段过滤
ip.addr == 192.168.1.100          # 源或目的为该IP
ip.src == 10.0.0.1 && ip.dst == 8.8.8.8
tcp.port == 443
http.request.method == "POST"

# 协议组合与逻辑
http or dns or tls                 # 只看应用层握手
tcp.flags.syn == 1 && tcp.flags.ack == 0   # SYN扫描
!(ip.src == 192.168.1.0/24)       # 外联流量

# 字符串与内容匹配
http contains "password"           # HTTP中包含password
http.request.uri contains "admin"   # URL含admin
frame contains "SELECT"            # 任意层含SELECT（SQL注入痕迹）

# TLS 证书与 SNI
tls.handshake.type == 1            # ClientHello
tls.handshake.extensions_server_name contains "evil"
ssl.handshake.type == 11 && ssl.handshake.certificate contains "CN="

# 时间间隔（检测Beaconing）
# 用 Statistics -> I/O Graphs 配合更直观

# TCP 异常
tcp.analysis.retransmission        # 重传
tcp.analysis.fast_retransmission   # 快速重传
tcp.analysis.zero_window          # 零窗口
tcp.flags.reset == 1              # RST包

# 过滤特定HTTP状态码
http.response.code == 404
http.response.code >= 500
```

**复杂表达式实战：**

```
# 检测可疑的TLS外联（非标准端口、非常见SNI）
tls.handshake.type == 1 && not tls.handshake.extensions_server_name matches "google|facebook|microsoft|apple"

# 检测HTTP上传大文件（POST且Content-Length大）
http.request.method == "POST" && http.content_length > 1000000

# 检测DNS隧道（超长子域）
dns.qry.name.len > 50
dns.qry.type == 16  # TXT记录查询（常用于DNS隧道数据外泄）

# 检测ICMP隧道（大载荷）
icmp and data.len > 64
```

### 2.2 协议分析与解密

Wireshark 能解码上千种协议，但加密协议（TLS/IPSec/WLAN）默认看不到明文。掌握解密技术是深度分析的关键。

**TLS 解密：**

原理是用会话密钥（Session Key）把加密的 ApplicationData 解密成明文。获取密钥有三种途径：

```
方法1: 浏览器导出预主密钥（最常用）
# 设置环境变量，让浏览器把密钥写到文件
# Windows (PowerShell):
$env:SSLKEYLOGFILE = "C:\temp\sslkeys.log"
# 然后启动 Chrome/Firefox，所有TLS会话密钥写入该文件

# Wireshark 配置:
# Edit -> Preferences -> Protocols -> TLS
# (Pre)-Master-Secret log filename = C:\temp\sslkeys.log
```

配置后，Wireshark 会自动用密钥解密 TLS 流量，在包详情中新增 "Decrypted TLS" 层，可见明文 HTTP 请求/响应。

```
方法2: 服务端私钥解密（适用于RSA密钥交换，不适用DHE/ECDHE）
# Edit -> Preferences -> Protocols -> TLS -> RSA keys list
# 添加服务端私钥文件、密码、IP、端口
# 注意: 现代TLS 1.3与前向保密机制下此方法无效

方法3: 中间人代理（mitmproxy）
mitmproxy --mode transparent --listen-port 8080
# 抓包设备指向mitmproxy，Wireshark抓代理与目标间的流量
```

**WLAN 解密：**

抓 802.11 无线帧时，数据帧是加密的（WPA2/WPA3）。解密需要 EAPOL 4 次握手包。

```
# Wireshark配置:
# Edit -> Preferences -> Protocols -> IEEE 802.11
# Enable decryption: 勾选
# Decryption keys: 添加 wpa-pwd:你的WiFi密码
# 抓包时必须包含关联和4次握手，否则无法派生PTK
```

### 2.3 统计分析工具

Wireshark 的 Statistics 菜单是流量分析的"瑞士军刀"。

**1. 捕获文件属性（Capture File Properties）**

显示包数、流量大小、捕获时长、平均速率、是否有丢包等概览。

**2. 协议分层统计（Protocol Hierarchy）**

```
# 典型输出:
Frame 100000 100%
  Ethernet 100000 100%
    IPv4 98000 98%
      TCP 85000 85%
        HTTP 5000 5%
        TLS 30000 30%
      UDP 12000 12%
        DNS 3000 3%
    ARP 1500 1.5%
```

价值：一眼看出协议占比异常。正常内网 ARP 应很少，如果 ARP 占比 >10% 可能是 ARP 扫描或中毒；如果大量未知 UDP，可能是 P2P 或隧道。

**3. 会话统计**

按五元组聚合，显示每条会话的包数、字节数、持续时间。可按字节数排序，快速发现"大户"——可能是数据外泄或大文件下载。

**4. I/O 图表（I/O Graphs）**

```
# 实战配置示例:
# Filter: ip.addr==192.168.1.100
# Graph Type: Bytes/tick
# 看某主机的流量时序曲线，发现规律性脉冲=Beaconing
```

I/O 图表对检测周期性通信（C2 心跳）极为有效。把 Y 轴设为"packets/tick"，X 轴 1 秒一格，如果出现每隔 60 秒的固定峰值，就是典型 Beaconing。

### 2.4 专家信息系统与异常提示

Wireshark 内置专家系统，自动给包打标签提示异常：

| 标签 | 含义 | 可能原因 |
|------|------|----------|
| Retransmission | TCP重传 | 网络丢包、拥塞 |
| Fast Retransmission | 快速重传 | 收到3个重复ACK |
| Zero Window | 零窗口 | 接收方处理不过来 |
| Window Update | 窗口更新 | 接收方恢复 |
| Out-of-Order | 乱序 | 路径多径、丢包重排 |
| Keep-Alive | 保活 | TCP保活机制 |
| Connection RST | 连接重置 | 服务拒绝、防火墙、扫描 |
| Previous segment lost | 前序段丢失 | 丢包 |

实战：在专家信息中看到大量"Connection RST (TCP)"且来自同一源 IP，配合 SYN 多、ACK 少，基本可判定为 SYN 扫描。

### 2.5 Wireshark 自定义配置与插件

**1. 自定义协议解析器表：** Wireshark 允许把某个端口强制按某协议解析。

```
# Analyze -> Decode As
# 例: 把 8443 端口强制按 TLS 解析（默认可能是HTTP）
```

**2. Profile 管理：** 不同场景用不同配置（字体、列布局、过滤器）。Edit → Configuration Profiles，建议建三个 Profile：通用、安全分析、网络排障。

**3. 自定义列：** 在包列表右键列标题可添加自定义列，如 `http.request.uri`、`tls.handshake.extensions_server_name`，便于在列表里直接看到 URL 和 SNI。

**4. Lua 插件：** Wireshark 支持 Lua 编写自定义 dissector。

```lua
-- 示例: 简单自定义协议解析器
local my_proto = Proto("myproto", "My Custom Protocol")
local f_cmd = ProtoField.uint8("myproto.cmd", "Command", base.DEC)
my_proto.fields = { f_cmd }

function my_proto.dissector(buffer, pinfo, tree)
    if buffer:len() < 1 then return end
    pinfo.cols.protocol = "MYPROTO"
    local subtree = tree:add(my_proto, buffer())
    subtree:add(f_cmd, buffer(0,1))
end
-- 注册到UDP 9999端口
DissectorTable.get("udp.port"):add(9999, my_proto)
```

## 三、网络流量异常检测方法

### 3.1 基线方法

基线方法的思路：先建立"正常"的画像，凡偏离基线的即视为异常。

**建立正常流量基线：** 连续采集 7-30 天的流量统计（源/目的 IP TOP、端口分布、协议占比、每秒包数/字节数、外联目的国家等），计算均值和标准差，得到"正常区间"。

```
# 用 Zeek 的 conn.log 建立基线示例（Python）
import pandas as pd
df = pd.read_csv("conn.log", sep="\t")
# 每小时外联字节数统计
df['hour'] = pd.to_datetime(df['ts'].astype(float), unit='s').dt.hour
baseline = df.groupby('hour')['bytes'].agg(['mean','std'])
# 阈值: mean + 3*std
threshold = baseline['mean'] + 3 * baseline['std']
```

**偏差检测：** 实时流量与基线对比，超出阈值即告警。常见偏差维度：单 IP 流量突增、新出现的目的 IP、新端口、非工作时段大量外联。

局限：基线方法对渐变型异常敏感，但对"低慢"攻击（如每天只传几个 KB 的数据外泄）不敏感，需配合行为分析。

### 3.2 阈值检测

最简单直接的方法：设定固定阈值，超过即告警。

```
典型阈值规则:

DDoS类:
  - 单IP入向SYN速率 > 5000 pkt/s  → SYN Flood告警
  - 单IP UDP速率 > 100Mbps        → UDP Flood告警
  - 目的IP ICMP速率 > 1000 pkt/s  → ICMP Flood告警

扫描类:
  - 单源IP在10秒内连接不同目的端口数 > 20  → 端口扫描
  - 单源IP在1分钟内访问不同目的IP数 > 50   → 主机扫描

外联类:
  - 内网IP连接境外IP数(非白名单) > 10/小时  → 可疑外联
  - 单IP DNS查询子域长度>50次数 > 5/分钟    → DNS隧道嫌疑

隧道类:
  - 单IP ICMP大包(>1000B)频率 > 10/分钟    → ICMP隧道嫌疑
  - TLS连接无SNI或SNI非常见域名 > 20/小时  → 可疑TLS
```

阈值检测优点是简单可解释，缺点是误报多（正常业务高峰也可能触发），需结合业务白名单调优。

### 3.3 行为分析方法

**1. 端口扫描检测：** 一个源 IP 短时间内对多个端口发起连接。检测维度是"源 IP 在时间窗口内访问的不同目的端口数"。

```
# Zeek 脚本: 检测端口扫描
event connection_established(c: connection)
{
    # 用一个全局表累计每个源IP的端口集合
    # 超过阈值则告警
}
# 等价SQL (基于conn.log):
SELECT id.orig_h, COUNT(DISTINCT id.resp_p) AS ports
FROM conn
WHERE ts > now() - INTERVAL 10 SECOND
GROUP BY id.orig_h
HAVING ports > 20;
```

**2. DGA（域名生成算法）检测：** 僵尸网络用 DGA 每天生成大量随机域名尝试连接 C2。检测特征：域名熵值高、辅音/元音比例异常、NXDOMAIN 响应率高。

```python
# 简化版 DGA 检测
import math
def shannon_entropy(s):
    if not s: return 0
    freq = {}
    for c in s:
        freq[c] = freq.get(c, 0) + 1
    ent = 0.0
    for cnt in freq.values():
        p = cnt / len(s)
        ent -= p * math.log2(p)
    return ent

# 域名熵>3.0且长度>10且NXDOMAIN率高 → DGA嫌疑
# 结合已知DGA家族特征库做机器学习分类更准
```

**3. C2 通信检测（Beaconing）：** C2 客户端周期性回连，表现为固定/准固定间隔的小流量通信。

```
Beaconing检测算法:
1. 提取某源IP的所有外联会话，按时间排序
2. 计算相邻会话的时间间隔序列 [d1, d2, d3...]
3. 计算间隔的"抖动比" = std(intervals) / mean(intervals)
   - 抖动比 < 0.3 且会话数 > 20 → 高度疑似Beaconing
4. 进一步过滤: 包大小恒定、目的IP新出现、目的端口非常用
```

### 3.4 签名检测

签名检测基于规则匹配，准确率高、可解释，但只能检测"已知"攻击。

**Snort/Suricata 规则：** 规则由头部 + 选项组成。

```
# Snort/Suricata 规则语法
# 头部: 动作 协议 源IP 源端口 -> 目的IP 目的端口
# 选项: (option:value; option:value;)

# 示例1: 检测SQL注入 (HTTP中含UNION SELECT)
alert http any any -> $HOME_NET any (msg:"SQL Injection Attempt - UNION SELECT"; content:"UNION"; nocase; content:"SELECT"; nocase; distance:0; within:50; sid:1000001; rev:1;)

# 示例2: 检测特定C2域名
alert dns any any -> any any (msg:"Suspicious C2 Domain"; dns.query; content:"badc2.example.com"; sid:1000002; rev:1;)

# 示例3: 检测TLS SNI匹配已知恶意
alert tls any any -> any any (msg:"Malicious TLS SNI"; tls.sni; content:"c2.malware"; sid:1000003; rev:1;)

# 示例4: 检测非标准端口的SSH
alert tcp any any -> $HOME_NET ![22] (msg:"SSH on non-standard port"; flow:to_server; content:"SSH-"; sid:1000004; rev:1;)
```

**YARA 网络规则：** YARA 主要用于文件/内存扫描，但对从流量中提取的载荷同样适用。

```yara
rule Malware_C2_Beacon
{
    meta:
        description = "Detect C2 beacon marker"
        author = "soc-team"

        $magic = { 4D 5A 90 00 }              // MZ头
        $url = "http://c2.evil/update?id=" nocase

        $url or ($config and $magic)
}
```

### 3.5 机器学习检测方法

**1. 聚类异常检测（无监督）：** 对流量特征做聚类，离群点即异常。

```python
from sklearn.cluster import KMeans
import numpy as np

# 特征: [包速率, 字节速率, 流持续时间, 目的端口熵, 源端口数]
X = np.array([[120, 50000, 30, 0.2, 1],
              [130, 52000, 32, 0.2, 1],
              [5000, 9000000, 1, 3.8, 200]])  # 异常点

kmeans = KMeans(n_clusters=2).fit(X)
# 距离质心远的样本 = 异常
distances = kmeans.transform(X).min(axis=1)
anomaly = distances > np.percentile(distances, 95)
```

**2. 分类器（有监督）：** 用标注数据训练分类器。常用算法：随机森林、XGBoost。

```python
from sklearn.ensemble import RandomForestClassifier
# 特征工程: 流的五元组统计、时序、包长分布、TCP标志分布
# 标签: 正常/恶意 (来自威胁情报或人工标注)
clf = RandomForestClassifier(n_estimators=100).fit(X_train, y_train)
# 注意: 需要充足的正样本，否则模型偏向多数类
```

**3. 深度学习：** 用于序列模式识别，如 LSTM 检测时序异常流量、CNN 识别包长序列模式。代表项目: Kitsune（自编码器异常检测）、DeepNet。

局限：机器学习方法解释性差，误报需人工复核，模型漂移需定期重训。实战中通常作为"辅助发现"，不替代签名检测。

## 四、NetFlow 与 sFlow 分析

### 4.1 NetFlow 原理与版本

NetFlow 是 Cisco 提出的流记录技术。一条"流"由七元组唯一定义：源/目的 IP、源/目的端口、协议、TOS、入接口。设备把同一流的所有包聚合，流结束时输出一条记录，包含字节数、包数、起止时间等。

```
流记录字段(NetFlow v5):
  srcaddr  dstaddr  srcport  dstport  prot  dPkts  dOctets  first  last
  10.1.1.5 8.8.8.8  54321    53       17    10     780      1000   1005
```

**版本演进：**

| 版本 | 特点 | 现状 |
|------|------|------|
| v1 | 早期版本，字段少 | 已淘汰 |
| v5 | 最经典版本，固定字段32个 | 仍广泛使用 |
| v9 | 模板化，字段可扩展 | 现代 Cisco 默认 |
| IPFIX | IETF 标准（基于 v9） | 行业标准，未来主流 |

```
# Cisco 路由器配置 NetFlow v9
flow exporter EXPORTER1
 destination 192.168.10.50
 source Loopback0
 transport udp 2055
 template data timeout 60
!
flow monitor MONITOR1
 record netflow ipv4 original-input
 exporter EXPORTER1
 cache timeout active 60
 cache timeout inactive 15
!
interface GigabitEthernet0/0/1
 ip flow monitor MONITOR1 input
```

### 4.2 sFlow 原理与采样

sFlow 是基于采样的流技术（Sampled Flow）。设备按 1/N 比例随机采样数据包，只输出采样包的前 N 字节（含头部+部分载荷）给采集器。sFlow 优势是硬件实现、转发性能不降，适合超高速链路（40G/100G）。劣势是采样的，不能精确计费，不适合小流量精确分析。

```
# 华为交换机配置 sFlow
sflow agent ip 192.168.1.1
sflow collector 1 ip 192.168.10.50 port 6343
interface 10GE1/0/1
 sflow sampling rate 1000      # 每1000包采样1个
 sflow counter interval 30     # 每30秒上报计数器
```

### 4.3 流量采集工具

**nfdump/nfcapd：** 经典的 NetFlow 采集与查询工具。

### 4.4 流量分析工具

**ElastiFlow：** 基于 ELK 的 NetFlow/IPFIX 分析平台，开箱即用的 Kibana 仪表盘，可视化 TOP 源/目的、协议分布、国家地图。

**VeloCloud/商业方案：** SD-WAN 厂商自带 NetFlow 分析能力，适合分支机构广域网。

### 4.5 NetFlow 与 sFlow 在安全分析中的应用

1. **DDoS 检测：** NetFlow 实时统计目的 IP 的入向包速/字节速，超阈值告警；可快速定位攻击源 IP 集合。
2. **横向移动发现：** 内网某主机突然对大量其他内网 IP 发起新端口连接，NetFlow 上表现为源 IP 的目的 IP 熵值突增。
3. **数据外泄量化：** 用 NetFlow 统计某主机对某外部 IP 的总出向字节数，量化外泄规模——这是全流量取证前的快速初判。
4. **影子资产发现：** 出现从未见过的目的 IP/端口，可能是影子 IT 或后门。

## 五、常见攻击流量特征

### 5.1 DDoS 攻击流量特征

**1. SYN Flood：** 攻击者发送海量 TCP SYN，但不完成三次握手，耗尽服务器半连接队列。

```
特征:
  - 大量 SYN 包 (flags=0x02), 极少 SYN-ACK 完成
  - 源IP多为伪造(随机)
  - 同一目的端口(如80/443)被狂轰
  - Wireshark: tcp.flags.syn==1 && tcp.flags.ack==0
  - 服务器侧: 大量SYN-ACK未收到ACK, 半连接堆积

检测: 单目的IP的SYN速率 > 阈值, 且 SYN/ACK 比值 >> 正常
```

**2. UDP Flood：** 向目标随机端口发大 UDP 包。

```
特征:
  - 大量UDP包, 源端口随机, 目的端口随机或固定
  - 包载荷可填充随机数据
  - 目标ICMP端口不可达回应(若无服务)
```

**3. HTTP Flood（应用层DDoS）：** 完成三次握手后发大量 HTTP 请求，消耗应用层资源。

```
特征:
  - 连接正常建立(有完整握手), 但请求量大
  - 常见: GET /大URL 反复请求, 或 POST 大body
  - User-Agent异常(相同/伪造/爬虫特征)
  - 单IP的HTTP请求速率异常
```

**4. 放大攻击（DNS/NTP/Memcached Amplification）：** 利用 UDP 无连接特性，伪造源 IP 为受害者 IP，向开放服务发小请求，放大成大响应打向受害者。

```
DNS放大: 查ANY记录, 响应可达请求的50-100倍
NTP放大: monlist命令, 放大700倍
Memcached: stats命令, 放大5万倍

特征:
  - 大量源端口为53/123/11211的UDP包涌入受害者
  - 单包大小异常(>1000B)
  - 源IP众多但都是开放服务器(可被识别)
```

### 5.2 端口扫描流量特征

| 扫描类型 | 原理 | 流量特征 |
|----------|------|----------|
| SYN扫描 | 发SYN等SYN-ACK，不完成握手 | 大量SYN无后续ACK；SYN-ACK=开放，RST=关闭 |
| UDP扫描 | 发UDP包看是否ICMP不可达 | UDP包+ICMP type3 code3响应 |
| FIN/Xmas/Null扫描 | 发异常标志组合绕过防火墙 | flags=0x01/0x29/0x00，无响应=开放 |
| Connect扫描 | 完整三次握手 | 大量短连接，RST快速关闭 |

SYN 扫描是最常见的，nmap 默认 -sS。检测：单源 IP 在短时间内访问大量不同目的端口，且 SYN 多、完整握手少。

### 5.3 横向移动流量特征

攻击者拿到内网一个 foothold 后，在内网横向扩散。

**1. SMB 枚举（445 端口）：** 列举共享、用户、域信息。

```
特征:
  - 某内网IP向大量其他内网IP的445端口发起连接
  - SMB2 Negotiate / Session Setup 包密集
  - 大量树连接(TCON)和共享枚举
  - 可能有NTLM认证(被攻击者Pass-the-Hash)
```

**2. RDP 爆破（3389）：** 暴力破解远程桌面。

```
特征:
  - 对单主机3389端口的大量短连接
  - 大量RDP Negotiate + 连接快速RST
  - 失败登录(可在事件日志交叉验证)
```

**3. PSExec / WMI 远程执行：** 横向执行命令。

```
特征:
  - 目标主机突然出现 ADMIN$ 共享访问
  - SMB连接后立即出现新进程(svcexec类的服务安装)
  - 445端口通信后伴随135端口(DCOM/WMI)活动
```

### 5.4 数据外泄流量特征

**1. DNS 隧道：** 把数据切分成子域，编码进 DNS 查询名外发，恶意 DNS 服务器返回响应（可含回传指令）。

```
特征:
  - 超长子域名 (>50字符), 高熵
  - 大量TXT记录查询
  - 查询的域根不是常见CDN/服务商
  - 单IP对特定域查询频率异常高
  - 查询长度分布异常(正常DNS查询多<30字符)
```

**2. ICMP 隧道：** 把数据塞进 ICMP 载荷。

```
特征:
  - ICMP包载荷大(>64B)，正常ping很小
  - ICMP Type8/0 包速率异常
  - 单IP对单目的IP的ICMP频率异常
  - 载荷内容可解码出明文
```

**3. HTTPS 外泄：** 数据藏在加密通道里，最难检测。

```
检测思路:
  - 出向流量峰值异常(基线对比)
  - 目的IP/SNI不在业务白名单
  - 上行字节远大于下行(正常浏览是下行大)
  - 连接持续时间长但数据量大(慢传)
  - 配合EDR看进程行为交叉验证
```

### 5.5 C2 通信流量特征

```
Beaconing(信标):
  - 固定/准固定间隔的小流量回连
  - 抖动比(std/mean)低
  - 包大小恒定

心跳包:
  - 周期性单包, 极小载荷
  - 典型间隔: 30s/60s/300s

自定义协议:
  - 非标准端口的二进制流量
  - 协议指纹不匹配(端口声称某服务但握手异常)
  - 流量模式异常(对称上下行, 而非请求-响应)

协议伪装:
  - 看起来像HTTP但请求路径规律
  - 看起来像TLS但证书/SNI异常
  - JA3/JA3S指纹匹配已知恶意客户端
```

JA3 指纹是对 TLS ClientHello 各字段做 MD5，得到客户端"指纹"。APT 用固定工具，JA3 常常固定，可与威胁情报匹配识别。

### 6.1 Snort 安装与配置

Snort 是经典的开源 IDS/IPS。安装以 Linux 为例：

```bash

# 安装snort

mkdir -p /etc/snort/rules
cp etc/snort.conf /etc/snort/
cp etc/so_preprocessor.conf /etc/snort/

# 下载社区规则
wget https://www.snort.org/downloads/community/community-rules.tar.gz
tar xvf community-rules.tar.gz -C /etc/snort/rules

关键配置 `/etc/snort/snort.conf`：

```
# 网络定义
var HOME_NET 192.168.1.0/24
var EXTERNAL_NET !$HOME_NET

# 规则路径
var RULE_PATH /etc/snort/rules

# 启用动态加载规则

### 6.4 告警管理与误报处理

告警多了会淹没真实威胁。管理流程：

1. **告警聚合：** 同一规则短时间内多次触发合并成一条事件。
2. **白名单：** 已知正常业务（备份、扫描器）加入白名单抑制。
3. **优先级：** 按规则 severity、资产价值、是否成功三维度评分，高优处理。
4. **关闭低价值规则：** 永远不会响应的探测规则关掉。
5. **联动威胁情报：** 告警中的 IP/域名与威胁情报库交叉，自动升级置信度。

```
# 用jq过滤高优先级告警
cat eve.json | jq 'select(.event_type=="alert" and .alert.severity==1)'

# 统计各规则告警数, 找到噪音规则
cat eve.json | jq -r 'select(.event_type=="alert") | .alert.signature' | sort | uniq -c | sort -rn | head
```

### 6.5 IDS/IPS 部署模式

```
旁路部署(IDS):
  镜像口 ──→ IDS引擎
  优点: 不影响业务, 不成为瓶颈
  缺点: 只能告警不能阻断

串行部署(IPS):
  业务流量 ──→ IPS引擎 ──→ 目标网络
  优点: 可实时阻断
  缺点: 故障会断业务, 需Bypass机制, 性能要求高

混合部署:
  出口串行IPS(阻断已知攻击) + 内网旁路IDS(深度检测)
```

### 7.1 Zeek（Bro）日志分析框架

Zeek 不是签名 IDS，而是"流量日志生成器"。它把流量解析成结构化日志，让你用 SQL/Python 分析。

**核心日志：**

| 日志 | 内容 |
|------|------|
| conn.log | 所有连接的五元组、字节数、持续时间 |
| dns.log | DNS查询/响应 |
| http.log | HTTP请求/响应摘要 |
| ssl.log | TLS连接、SNI、证书 |
| files.log | 文件提取记录 |
| weird.log | 协议异常 |
| notice.log | Zeek脚本产生的告警 |

```bash
# 安装Zeek
apt install zeek
# 或源码安装(更灵活)
./configure --with-libpcap && make && make install

# 配置监听 /opt/zeek/etc/zeek.conf
[zeek]
host=localhost
interface=eth1

# 启动
zeekctl deploy
zeekctl start

# 查看日志
ls /opt/zeek/logs/current/
# conn.log dns.log http.log ssl.log ...

# 简单分析: 找外联TOP10
cat conn.log | zeek-cut id.orig_h id.resp_h bytes | \
  sort | uniq -c | sort -rn | head
```

**Zeek 脚本示例（检测 DNS 隧道）：**

```zeek
# detect_dns_tunnel.zeek
module DNS_TUNNEL;

export {
    redef enum Notice::Type += { DNS_Tunnel_Suspect };
    global threshold: double = 50 &redef;
}

event dns_request(c: connection, msg: dns_msg, query: string, qtype: count)
{
    if (|query| > threshold)
        NOTICE([$note=DNS_Tunnel_Suspect,
                $msg=fmt("Long DNS query %s from %s", query, c$id$orig_h),
                $conn=c]);
}
```

### 7.2 Moloch / Arkime 全流量捕获与索引

Arkime（原 Moloch）是大规模全流量捕获与搜索系统。它把 pcap 存储到磁盘，同时把元数据索引到 Elasticsearch，支持 PB 级流量的秒级搜索。

## 八、实战案例

### 案例1：通过流量分析发现 APT C2 通信

**背景：** 某企业 EDR 报告财务部一台主机行为异常，但无法确认是否真失陷。

**分析过程：**

1. **初筛：** 调取该主机近 7 天的 Zeek conn.log，统计外联目的 IP。

```bash
zeek-cut id.orig_h id.resp_h id.resp_p < conn.log | \
  awk '$1=="10.20.30.40"' | sort | uniq -c | sort -rn
# 发现: 10.20.30.40 185.234.219.10 443 出现 4820次
```

2. **行为分析：** 该 IP 出现次数异常高，但每次流量极小（几百字节）。

```bash
zeek-cut id.orig_h id.resp_h duration bytes < conn.log | \
  awk '$1=="10.20.30.40" && $2=="185.234.219.10"'
# 看到持续时间≈0, 字节≈300, 极简短
```

3. **周期性检测：** 用 Python 算时间间隔。

```python
import pandas as pd
df = pd.read_csv("beacon.csv")
intervals = df['ts'].diff().dropna()
print(f"间隔均值={intervals.mean():.0f} 抖动比={intervals.std()/intervals.mean():.2f}")
# 输出: 间隔均值=60 抖动比=0.08 → 高度疑似Beaconing
```

4. **威胁情报比对：** 查询 185.234.219.10，命中某 APT 组织已知 C2。

5. **载荷确认：** 从 Arkime 下载对应 pcap，用 Wireshark 配合 TLS ClientHello 看到 JA3 指纹匹配已知恶意框架 Cobalt Strike。

**结论：** 该主机已失陷，C2 为 185.234.219.10，每 60 秒一次心跳，使用 Cobalt Strike。处置：隔离主机、阻断 C2 IP、全网回溯该 C2 的所有通信主机。

### 案例2：DDoS 攻击流量分析与溯源

**背景：** 公司官网突然访问极慢，监控显示入向流量从 100Mbps 飙到 8Gbps。

**分析过程：**

1. **类型初判：** 用 NetFlow 实时统计，发现大量源端口随机的 UDP 包涌向 Web 服务器 53 端口——初步判定 DNS 放大攻击。

```bash
nfdump -r current -s srcip -n 20 'dst port 53 and proto udp'
# TOP源IP多为开放DNS服务器(53端口)
```

2. **放大倍数计算：** 用 Wireshark 看具体流量，发现查询的是 `.` 的 ANY 记录，请求 60 字节，响应 3000+ 字节，放大 50 倍。

3. **受害者与反射器识别：** 受害者是 Web 服务器 IP，反射器是全网开放递归 DNS（源端口 53）。

4. **溯源：** 攻击源 IP 分布在多个国家，无明显单一源，属于租用反射器的 DDoS 即服务。

**处置：** 上游 ISP 清洗（丢弃 53 端口入向大包），同时向反射器管理员报告开放递归问题。

### 案例3：数据泄露事件流量取证

**背景：** 审计发现某离职员工在职期间疑似外传客户数据，需要取证。

**分析过程：**

1. **时间定位：** 确认该员工使用的工作站 IP 和疑似外泄时间窗（最后两周）。

2. **外发流量统计：** 用 Arkime 按该 IP 过滤出向流量，按字节数排序会话。

```
Arkime搜索: ip.src == 10.10.5.20 && ip.dst != 10.0.0.0/8
按字节排序TOP10:
  10.10.5.20 → 45.77.123.9:443   2.3GB   持续5天
  10.10.5.20 → 103.21.55.7:80    800MB
  ...
```

3. **通道识别：** 2.3GB 通过 443 出向到境外 IP，SNI 是某个人网盘域名，行为高度可疑。

4. **内容取证：** 下载该会话 pcap。由于是 TLS 加密，尝试用工作站提取的浏览器密钥（SSLKEYLOGFILE）解密，成功看到 POST 上传的 Excel 文件，文件名包含"客户名单"。

5. **量化与定损：** 统计上传文件数、总字节数、上传时间段，形成取证报告。

**结论：** 该员工在两周内将约 2.3GB 客户数据通过个人网盘外泄，证据链完整（流量元数据 + 解密内容 + 文件名）。

## 总结

网络流量分析是安全运营与应急响应的核心能力。掌握要点：

1. **方法论分层：** 实时告警（IDS）+ 离线取证（全流量）+ 趋势基线（NetFlow）三层互补。
2. **工具链打通：** Wireshark 深度解包、Suricata/Zeek 自动化、Arkime 大规模检索、ELK 可视化告警。
3. **异常检测多维度：** 阈值（快速）+ 行为（Beaconing/扫描）+ 签名（已知）+ 机器学习（未知），不可单靠一种。
4. **攻击特征熟悉：** DDoS/扫描/横向/外泄/C2 各有典型流量指纹，熟悉才能快速判定。
5. **实战思维：** 先用元数据/NetFlow 快速定位可疑会话，再用全流量 Wireshark 深挖确认，形成"定位—深挖—取证"工作流。

持续学习路径：先精通 Wireshark 过滤与解密 → 上手 Suricata 规则编写 → 部署 Zeek 日志分析 → 搭建 Arkime+ELK 平台 → 在实战案例中沉淀经验。
