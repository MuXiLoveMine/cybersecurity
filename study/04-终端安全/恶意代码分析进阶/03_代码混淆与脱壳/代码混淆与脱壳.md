# 代码混淆与脱壳

### 3.1 常见壳类型

```
壳（Packer/Protector）用于压缩或保护可执行文件：

压缩壳：
- UPX：开源压缩壳，最常见，易于脱壳
- ASPack：商业压缩壳
- PECompact：压缩壳
- MPRESS：压缩壳+反调试

加密保护壳：
- Themida/WinLicense：强保护，虚拟化+反调试
  - 代码虚拟化（VM）
  - 反调试/反dump/反patch
  - 许可证管理
- VMProtect（VMP）：代码虚拟化保护
  - 将x86指令转换为虚拟指令
  - 每次保护的VM结构不同
  - 分析难度极高
- Enigma Protector：加密+反调试+许可证

.NET保护：
- ConfuserEx：.NET混淆器
- dotfuscator：.NET混淆
- .NET Reactor：.NET加密保护

壳的识别工具：
- Detect It Easy (DIE)：特征签名+熵值分析
- PEiD：经典查壳工具（已较旧）
- Exeinfo PE：查壳+查编译器
```

### 3.2 通用脱壳方法

**ESP定律寻OEP**

```
ESP定律（堆栈平衡法）原理：
- 壳代码执行前会保存原始堆栈状态
- 壳代码执行完毕后恢复堆栈并跳转到OEP
- 通过监控堆栈指针变化找到跳转点

操作步骤（以x64dbg为例）：
1. 在入口点暂停程序
2. 记下当前ESP值（如ESP=0x0019FFA0）
3. 在ESP指向的地址下硬件访问断点（DWORD）
4. 按F9运行程序
5. 程序在壳代码恢复堆栈时断下
6. 单步执行直到看到远跳转（JMP/CALL到原代码段）
7. 跳转目标即为OEP

适用范围：
- UPX、ASPack等压缩壳
- 简单的加密壳
- 不适用于虚拟化壳（VMP/Themida）
```

**内存断点法**

```
通过在内存区域设置断点找到OEP：

操作步骤：
1. 运行程序到入口点
2. 查看内存映射（Alt+M）
3. 找到程序的代码段（.text或第一个可执行段）
4. 在该段设置"内存访问断点"（或内存写入断点）
5. 按F9运行
6. 程序执行到代码段时断下
7. 此时可能已接近OEP，单步执行确认

原理：
- 壳代码在解压/解密完毕后会跳转到原始代码段执行
- 设置代码段的访问断点可以捕获这个跳转
```

**内存对齐法（Direct Memory Dump）**

```
无论壳如何复杂，最终代码必须在内存中解密后才能执行：

步骤：
1. 让程序运行足够长时间（确保壳完全解密）
2. 暂停程序
3. 使用Scylla或PE Dumper工具
4. 选择目标进程
5. 找到OEP（可通过上述方法或特征定位）
6. Dump完整PE镜像到文件
7. 修复IAT（Import Address Table）

工具：
- Scylla：最流行的dump+IAT修复工具
- PE Dumper：命令行dump工具
- Process Hacker：进程内存查看/dump
- x64dbg内置dump功能
```

### 3.3 VMP/Themida分析思路

```
虚拟化壳的核心原理：
- 将原始x86/x64指令转换为自定义虚拟指令
- 使用自定义虚拟机解释执行
- 每次保护的VM指令集不同（多态）
- 无法直接还原原始代码

VMP分析思路：

1. 定位VM入口
   - VMP通常通过VMDispatcher跳转
   - 找到虚拟指令分发逻辑

2. 分析VM结构
   - 虚拟寄存器（vR0-vR7等）
   - 虚拟栈
   - Handler表（每个虚拟操作码对应一个Handler）

3. 逆向Handler
   - 提取每个Handler的语义
   - 映射虚拟操作码到x86指令
   - 构建虚拟指令到真实指令的映射表

4. 还原代码
   - 遍历虚拟指令流
   - 逐条翻译为x86指令
   - 重建原始代码逻辑

辅助工具：
- VMP分析插件（如VMAttack）
- 符号执行（Triton/angr）
- 模式匹配自动化Handler识别

实际建议：
- VMP/Themida全量逆向耗时巨大
- 实际分析中通常只关注关键功能点
- 结合动态分析在VM执行后获取行为
```

### 3.4 花指令去除

```
花指令（Junk Code）是插入在真实代码中的无意义指令，用于干扰反汇编：

常见花指令模式：

模式1：永假跳转
  jmp label1
  db 0E8h          ; 假call（干扰线性反汇编）
label1:
  ...真实代码...

模式2：x86/x64互斥跳转
  jz  label2
  jnz label2       ; jz+jnz = 无条件跳转
  db 0E8h          ; 垃圾字节
label2:
  ...真实代码...

模式3：SEH花指令
  push label_handler
  push dword [fs:0]
  mov fs:0, esp    ; 注册SEH
  int 3            ; 触发异常跳到handler
  ...垃圾代码...
label_handler:
  ...真实代码...

去除方法：

1. 手动NOP
   - 在反汇编器中识别花指令
   - 将垃圾字节替换为NOP（0x90）
   - 适用于少量花指令

2. 脚本自动化
   - IDA Python脚本批量识别模式
   - Ghidra脚本自动化处理
   - 基于模式匹配自动NOP花指令

3. 动态Trace
   - 运行程序并记录实际执行路径
   - 仅保留被执行的指令
   - 未执行的就是花指令

示例IDAPython去花指令脚本思路：
  扫描所有 jmp + 垃圾字节 + label 模式
  将垃圾字节patch为NOP
  重新分析代码
```

### 3.5 控制流平坦化还原

```
控制流平坦化（Control Flow Flattening, CFF）：
- 将函数的控制流打乱
- 使用一个dispatcher分发基本块
- 增加静态分析难度

原始控制流：
  if (cond) { block_A } else { block_B }
  block_C

平坦化后：
  while (true) {
    switch (state) {
      case 0: block_A; state = 2; break;
      case 1: block_B; state = 2; break;
      case 2: block_C; state = EXIT; break;
    }
  }

还原方法：

1. 符号执行
   - 使用angr/Triton符号执行
   - 枚举从dispatcher到各基本块的路径
   - 恢复原始控制流图

2. 动态Trace + 静态分析
   - 多次运行记录执行路径
   - 根据实际执行顺序重建CFG
   - 合并多个执行trace

3. 模式匹配
   - 识别dispatcher模式（switch-case结构）
   - 分析state变量的转移关系
   - 重建基本块的前驱/后继关系

工具：
- angr（Python符号执行框架）
- Triton（动态二进制分析框架）
- D810（IDA插件，反混淆）
- Unflattener（专用CFF还原工具）
```
