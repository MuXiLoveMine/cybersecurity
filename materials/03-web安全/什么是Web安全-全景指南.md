## 一、Web 安全概述

### 1.1 什么是 Web 安全

**Web 安全（Web Security）** 是指保护 Web 应用、Web 服务、用户数据和底层系统免遭未经授权的访问、使用、泄露、篡改或破坏的行为与技术体系。

| 维度 | 说明 |
|------|------|
| **保护对象** | Web 应用、API 接口、用户数据、业务系统、底层基础设施 |
| **数据范围** | 公司内部数据、用户个人数据、合作伙伴数据、交易数据 |
| **核心目标** | 保护敏感信息不被窃取或滥用，保障业务正常运行 |
| **涉及层面** | 前端/客户端、后端服务、API、数据库、网络、基础设施 |

### 1.2 Web 安全与隐私的关系

很多人把安全和隐私混为一谈，两者紧密相关但侧重点不同：

| 维度 | Web 安全（Security） | Web 隐私（Privacy） |
|------|---------------------|-------------------|
| **核心问题** | "如何保护数据免遭未授权访问？" | "用户如何控制自己的数据？" |
| **关注焦点** | 防攻击、防泄露、防篡改、防破坏 | 数据的收集目的、范围、使用方式、用户控制权 |
| **典型威胁** | 黑客攻击、SQL 注入、XSS、数据泄露 | 过度收集、滥用数据、未经同意共享、跟踪用户 |
| **典型手段** | 加密、防火墙、访问控制、漏洞修复 | 用户授权、隐私政策、数据最小化、匿名化 |
| **法规代表** | 《网络安全法》《数据安全法》 | 《个人信息保护法》《GDPR》 |

> **关系**：安全是隐私的基础——没有安全，隐私无从谈起；但安全了不等于尊重隐私。一个系统可以很安全（没人能攻破），但仍然可能不尊重用户隐私（过度收集、滥用数据）。

### 1.3 Web 安全的核心目标

Web 安全围绕保护以下资产展开：

| 资产类型 | 具体内容 | 被破坏的后果 |
|---------|---------|-------------|
| **用户认证信息** | 用户名、密码、Session、Token | 账号被盗、身份冒用 |
| **敏感业务数据** | 银行信息、支付记录、订单数据 | 经济损失、欺诈 |
| **个人信息** | 手机号、邮箱、身份证、地址 | 隐私泄露、诈骗风险 |
| **内部算法与代码** | 业务逻辑、核心算法、源代码 | 商业机密泄露 |
| **系统可用性** | 网站、服务、API 的正常访问 | 业务中断、经济损失 |
| **用户信任** | 用户对平台的信任和品牌声誉 | 用户流失、品牌受损 |

### 1.4 Web 安全的多层防护范围

```
用户层（人的安全）
    │ 社会工程学、钓鱼、账号安全
    ▼
客户端/前端层（浏览器安全）
    │ XSS、CSRF、前端逻辑漏洞、CSP、同源策略
    ▼
传输层（网络安全）
    │ HTTPS、TLS、中间人攻击、流量劫持
    ▼
应用层（Web 应用安全）
    │ SQL 注入、文件上传、命令注入、业务逻辑漏洞
    ▼
API 层（接口安全）
    │ 未授权访问、越权、API 注入、速率限制
    ▼
基础设施层（服务器/云）
    │ 配置错误、未授权访问、容器安全、云安全
    ▼
供应链层（第三方依赖）
    │ 依赖漏洞、恶意包、CDN 劫持、开源组件风险
```

Web 安全不是单一层面的事情，而是一个多层次的体系。每一层都可能成为攻击的入口，也都需要相应的防护措施——这就是纵深防御（Defense in Depth）在 Web 安全中的体现。

> **攻击者的视角**：他们只需要找到一个层面的一个漏洞。
> **防守者的视角**：需要在每个层面都做好防护，层层设防。
> 这就是安全领域著名的"攻防不对称"。

## 二、Web 安全模型与浏览器安全机制

### 2.1 Web 平台的安全模型

Web 平台的核心特点是：**浏览器会执行来自不可信网站的代码**。你访问一个网站，它的 HTML、JavaScript、WebAssembly 就会在你的浏览器里运行——这是 Web 最强大的地方，也是最危险的地方。

| 内容类型 | 举例 | 行为 | 安全风险 |
|---------|------|------|---------|
| **被动内容** | 图片、字体、CSS、视频、音频 | 被解码和渲染，不执行代码 | 较低，主要是资源替换/欺骗 |
| **主动内容** | HTML、JavaScript、WebAssembly、SVG | 以来源的权限执行代码 | 高，是 Web 的主要攻击面 |

> **核心挑战**：
> 浏览器既要让来自不同网站的代码正常运行（功能），
> 又要防止它们互相干扰、窃取数据（安全）。
> 这就需要一系列的安全机制来隔离和限制。

### 2.2 同源策略（Same-Origin Policy, SOP）

**同源策略**是 Web 安全的基石。它限制从一个源（Origin）加载的文档或脚本如何与另一个源的资源交互，目的是隔离潜在的恶意文档，减少攻击载体。

#### 什么是"源"（Origin）

两个 URL 属于**同源**，必须满足三个相同：

```
  https://www.example.com:443/path/page.html
  └─┬──┘ └──────┬──────────┘ └┬┘
  协议          主机           端口

  同源 = 协议相同 + 主机相同 + 端口相同
```

| URL | 是否同源 | 原因 |
|-----|---------|------|
| `https://www.example.com/a.html` | ✅ 同源 | 协议、主机、端口都相同 |
| `https://www.example.com/b/c.html` | ✅ 同源 | 路径不影响 |
| `http://www.example.com/a.html` | ❌ 不同源 | 协议不同（https vs http） |
| `https://api.example.com/a.html` | ❌ 不同源 | 主机不同（子域名不同） |
| `https://www.example.com:8080/a.html` | ❌ 不同源 | 端口不同 |
| `https://www.example.com:443/a.html` | ✅ 同源 | 默认端口可以省略 |

#### 同源策略限制了什么

| 资源类型 | 限制情况 | 说明 |
|---------|---------|------|
| **Cookie / LocalStorage / IndexedDB** | ❌ 严格限制 | 不同源的网站不能读取对方的存储 |
| **DOM 访问** | ❌ 严格限制 | 不能通过 JS 访问不同源页面的 DOM |
| **AJAX / Fetch 请求** | ❌ 默认限制 | 跨域请求默认被拦截（可通过 CORS 放宽） |
| **图片 / CSS / JS 文件加载** | ✅ 允许加载 | 可以嵌入跨域资源（但有安全限制） |
| **iframe 嵌套** | ⚠️ 有限制 | 可以嵌入，但 JS 不能互相访问 DOM |

> **为什么同源策略这么重要？**
> 如果没有同源策略，恶意网站 A 就可以：
> - 读取你登录的银行网站 B 的页面内容
> - 以你的名义在银行网站 B 上执行操作
> - 窃取你在网站 B 上的所有 Cookie 和数据
> 这将使 Web 完全不可信。

### 2.3 CORS（跨域资源共享）

**CORS（Cross-Origin Resource Sharing，跨域资源共享）** 是一种在受控情况下放宽同源策略限制的机制。它允许服务器明确指定哪些源可以访问它的资源。

```
浏览器                                   服务器
  │                                        │
  │  1. 发起跨域请求                         │
  │     Origin: https://a.example.com       │
  │───────────────────────────────────────►│
  │                                        │
  │  2. 服务器返回 CORS 头                   │
  │     Access-Control-Allow-Origin: ...    │
  │◄───────────────────────────────────────│
  │                                        │
  │  3. 浏览器检查 CORS 头                   │
  │     允许 → 把响应给 JS                   │
  │     拒绝 → 拦截响应（报错）              │
```

#### 简单请求 vs 预检请求

| 类型 | 触发条件 | 过程 |
|------|---------|------|
| **简单请求** | GET/HEAD/POST + 简单 Content-Type | 直接发请求，看响应头 |
| **预检请求（Preflight）** | PUT/DELETE、自定义 Header、JSON Content-Type 等 | 先发 OPTIONS 请求问服务器允不允许，再发真实请求 |

#### 常见 CORS 响应头

| 响应头 | 作用 |
|--------|------|
| `Access-Control-Allow-Origin` | 允许哪些源（`*` 表示所有源，或具体源） |
| `Access-Control-Allow-Methods` | 允许的 HTTP 方法 |
| `Access-Control-Allow-Headers` | 允许的请求头 |
| `Access-Control-Allow-Credentials` | 是否允许携带 Cookie（`true` 时不能用 `*`） |
| `Access-Control-Max-Age` | 预检请求的缓存时间 |

> **安全提醒**：
> - `Access-Control-Allow-Origin: *` + `Access-Control-Allow-Credentials: true` 是不允许的（浏览器会拒绝）
> - 不要为了方便就设置 `Access-Control-Allow-Origin: *`，应精确指定允许的源
> - CORS 配置错误本身也是一种安全漏洞（可能导致数据泄露）

### 2.4 浏览器安全特性

#### 内容安全策略（Content Security Policy, CSP）

**CSP** 是浏览器的一层安全防护，可以限制页面能加载哪些资源、能执行哪些脚本，有效防止和缓解 XSS 攻击。

| 作用 | 说明 |
|------|------|
| **限制脚本来源** | 只允许加载指定域名的 JS，内联脚本默认不执行 |
| **限制资源加载** | 图片、样式、字体、frame 等都可以限制来源 |
| **禁止 eval** | 可以禁止 `eval()` 和动态代码执行 |
| **违规报告** | 违反策略时发送报告，便于发现问题 |

**示例 CSP 配置**：
```http
Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' https://cdn.example.com; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; report-uri /csp-violation-report
```

#### Trusted Types

**Trusted Types** 是 CSP 的增强版，它要求所有注入 DOM 的内容（HTML、脚本、样式 URL 等）必须经过"可信类型"的处理，从源头上防止 DOM XSS。

```
开启 Trusted Types 后：
  ❌ element.innerHTML = userInput;  // 直接赋值会被阻止
  ✅ element.innerHTML = sanitizer.sanitize(userInput);  // 必须经过处理
```

#### 其他浏览器安全特性

| 特性 | 作用 |
|------|------|
| **HttpOnly Cookie** | 防止 JavaScript 读取 Cookie，缓解 XSS 窃取 Cookie |
| **Secure Cookie** | Cookie 只在 HTTPS 连接中发送 |
| **SameSite Cookie** | 限制跨站请求携带 Cookie，缓解 CSRF |
| **HSTS** | 强制浏览器使用 HTTPS 访问，防止降级攻击 |
| **X-Frame-Options** | 控制页面是否可以被 iframe 嵌入，防止点击劫持 |
| **X-Content-Type-Options** | 禁止浏览器猜测文件类型，防止 MIME 嗅探攻击 |
| **Referrer-Policy** | 控制 Referer 头的信息泄露 |
| **沙箱（Sandbox）** | iframe 的沙箱模式，限制 iframe 的权限 |
| **隔离（Isolation）** | 站点隔离、进程隔离，防止侧信道攻击 |

## 三、OWASP Top 10:2025

### 3.1 什么是 OWASP Top 10

| 项目 | 内容 |
|------|------|
| **全称** | Open Web Application Security Project Top 10 |
| **发布机构** | OWASP（开放式 Web 应用程序安全项目） |
| **性质** | Web 应用最关键安全风险的行业共识标准 |
| **数据来源** | 基于数十万个应用的安全测试数据 + 行业调查 |
| **更新频率** | 大约 3-4 年更新一次 |
| **地位** | Web 安全领域最权威、最广泛认可的风险清单 |

> **OWASP Top 10 的意义**：
> - 是 Web 安全的"入门必学清单"
> - 是企业安全建设的重要参考
> - 是很多安全标准和合规要求的基础
> - 代表了当前 Web 应用最普遍、最危险的安全风险

### 3.2 OWASP Top 10:2025 概述

**OWASP Top 10:2025** 于 **2025 年 11 月发布，2026 年 1 月定稿**，是当前的最新标准。下一次修订预计在 2028-2029 年。

> **⚠️ 2026 年时效性标注**：本文引用的是 **OWASP Top 10:2025** 版本，该版本于 2026 年 1 月正式定稿，是 2026 年的现行标准。请注意区分旧版本（2021/2017/2013）。

### 3.3 2025 版 vs 2021 版的主要变化

| 变化类型 | 具体变化 | 说明 |
|---------|---------|------|
| **新增类别** | A03 软件供应链失效 | 新增类别，反映供应链安全日益重要 |
| **新增类别** | A10 特殊情况处理不当 | 新增类别，关注异常处理中的安全问题 |
| **排名上升** | A02 安全配置错误：第 5 位 → 第 2 位 | 最大上升者，云环境配置问题是主因 |
| **排名下降** | A05 注入：第 3 位 → 第 5 位 | 有所下降但仍是高频风险 |
| **类别合并** | SSRF 并入 A01 访问控制失效 | SSRF 不再是独立类别 |
| **类别更名** | A04 加密机制失效（原 A02 密码学失效） | 名称微调 |

| **8** | A08:2025 | 软件或数据完整性失效 | Software or Data Integrity Failures | ⬇ 从第 8 位微调 |
| **9** | A09:2025 | 安全日志与告警失效 | Security Logging & Alerting Failures | ⬇ 从第 9 位微调 |

### 3.5 十大风险详解

#### A01:2025 访问控制失效（Broken Access Control）

| 项目 | 内容 |
|------|------|
| **排名** | 第 1 位（连续四届榜首） |
| **说明** | 用户可以访问其权限之外的功能或数据 |
| **包含** | 越权访问（水平/垂直）、未授权访问、IDOR、SSRF |
| **常见场景** | 改一下 ID 就能看别人的数据、普通用户能访问管理员功能 |
| **根本原因** | 服务端没有正确验证用户权限，依赖前端控制 |
| **防御** | 服务端统一权限校验、最小权限原则、默认拒绝 |

#### A02:2025 安全配置错误（Security Misconfiguration）

| 项目 | 内容 |
|------|------|
| **排名** | 第 2 位（从第 5 跃升，最大上升者） |
| **说明** | 安全配置不正确或缺失，导致系统暴露在风险中 |
| **上升原因** | 云环境普及，配置复杂，错误配置成为主要风险来源 |
| **常见场景** | 默认密码、未禁用调试功能、目录遍历、不必要的服务开启、云存储桶公开 |
| **防御** | 安全基线配置、自动化配置检查、最小化部署、定期审计 |

#### A03:2025 软件供应链失效（Software Supply Chain Failures）⭐ 新增

| 项目 | 内容 |
|------|------|
| **排名** | 第 3 位（新增类别） |
| **说明** | 第三方组件、依赖库、CI/CD 管道等供应链环节的安全问题 |
| **发生率** | 平均发生率最高（5.72%） |
| **常见场景** | 依赖库有漏洞、恶意开源包、CI/CD 管道被入侵、CDN 劫持 |
| **防御** | SCA（软件成分分析）、依赖审计、SBOM、最小化依赖、供应链安全评估 |

#### A04:2025 加密机制失效（Cryptographic Failures）

| 项目 | 内容 |
|------|------|
| **排名** | 第 4 位 |
| **说明** | 加密算法使用不当或缺失，导致数据泄露 |
| **常见场景** | 明文存储密码、使用弱算法（MD5/SHA1）、HTTP 明文传输、硬编码密钥 |
| **防御** | 使用强加密算法、HTTPS 全站、安全的密码哈希（Argon2/bcrypt）、密钥管理 |

#### A05:2025 注入（Injection）

| 项目 | 内容 |
|------|------|
| **排名** | 第 5 位（从第 3 下降，含 XSS） |
| **说明** | 恶意数据被注入到命令或查询中，被解释器执行 |
| **包含** | SQL 注入、命令注入、LDAP 注入、XSS 等 |
| **常见场景** | 用户输入直接拼接到 SQL 语句、直接传给系统命令 |
| **防御** | 参数化查询（预编译）、输入验证、输出编码、最小权限 |

#### A06:2025 不安全设计（Insecure Design）

| 项目 | 内容 |
|------|------|
| **排名** | 第 6 位 |
| **说明** | 设计层面的缺陷，不是实现层面的 bug |
| **与注入的区别** | 注入是"代码写错了"，不安全设计是"从设计上就有问题" |
| **常见场景** | 业务逻辑漏洞、支付安全问题、没有风控、没有限流 |
| **防御** | 安全左移、威胁建模、安全设计评审、业务安全测试 |

#### A07:2025 认证失效（Authentication Failures）

| 项目 | 内容 |
|------|------|
| **排名** | 第 7 位 |
| **说明** | 认证机制存在缺陷，攻击者可以冒充其他用户 |
| **常见场景** | 弱密码、无暴力破解防护、会话固定、Cookie 不安全、凭证泄露 |
| **防御** | 强密码策略、MFA 多因素认证、安全的会话管理、登录限流、密码哈希 |

#### A08:2025 软件或数据完整性失效（Software or Data Integrity Failures）

| 项目 | 内容 |
|------|------|
| **排名** | 第 8 位 |
| **说明** | 软件或数据在传输/存储过程中被篡改，而没有被检测到 |
| **常见场景** | 自动更新被劫持、CI/CD 管道被篡改、数据传输无完整性校验 |
| **防御** | 数字签名、哈希校验、CI/CD 安全、完整性验证 |

#### A09:2025 安全日志与告警失效（Security Logging & Alerting Failures）

| 项目 | 内容 |
|------|------|
| **排名** | 第 9 位 |
| **说明** | 没有足够的日志记录和告警，导致攻击无法被及时发现 |
| **常见场景** | 关键操作无日志、日志不完整、没有告警机制、没人看日志 |
| **防御** | 全面审计日志、集中日志管理、告警规则、定期审计分析、SIEM |

#### A10:2025 特殊情况处理不当（Mishandling of Exceptional Conditions）⭐ 新增

| 项目 | 内容 |
|------|------|
| **排名** | 第 10 位（新增类别） |
| **说明** | 异常情况和边界条件处理不当，导致安全问题 |
| **常见场景** | 错误信息泄露（栈轨迹、调试信息）、异常时绕过安全检查、空值/边界值导致逻辑错误 |
| **防御** | 统一的错误处理、用户友好的错误页面、异常情况的安全测试、输入验证 |

## 四、Web 安全核心攻击类型与原理

### 4.1 注入类（Injection）

#### SQL 注入（SQL Injection）

| 项目 | 内容 |
|------|------|
| **原理** | 用户输入被直接拼接到 SQL 语句中，改变了 SQL 的语义 |
| **影响** | 数据泄露、数据篡改、权限绕过、甚至服务器被控 |
| **类型** | 联合注入、报错注入、布尔盲注、时间盲注、堆叠查询 |
| **根本原因** | 代码和数据没有分离，用户输入被当作代码执行 |

**攻击示例（仅原理演示）**：
```
正常查询：
  SELECT * FROM users WHERE username = 'admin' AND password = 'xxx'

注入后（输入密码为 ' OR '1'='1）：
  SELECT * FROM users WHERE username = 'admin' AND password = '' OR '1'='1'
  结果：查询出所有用户，绕过密码验证
```

**防御措施（按优先级）**：
1. **参数化查询（预编译语句）**——最核心的防御
2. **输入验证（白名单）**——辅助手段
3. **最小权限原则**——数据库账号只给必要的权限
4. **WAF**——补充防线（不能作为主要防御）
5. **安全编码规范**——从源头避免

> **重要**：SQL 注入是"老而弥坚"的漏洞，虽然排名下降，但仍然非常普遍。参数化查询是根本解决方法。

#### 命令注入（Command Injection）

| 项目 | 内容 |
|------|------|
| **原理** | 用户输入被拼接到系统命令中执行 |
| **影响** | 服务器被控、任意命令执行 |
| **常见场景** | 调用系统命令的功能（ping、文件操作等） |
| **防御** | 尽量不调用系统命令、使用安全的 API、严格的输入白名单、最小权限运行 |

#### LDAP 注入、XPATH 注入等

原理类似——只要是"把用户输入拼接到某种查询/命令语言中"，都可能产生注入漏洞。防御思路也一致：使用安全的 API（参数化），而不是字符串拼接。

---

### 4.2 脚本类（XSS / CSRF）

#### XSS（跨站脚本攻击，Cross-Site Scripting）

| 项目 | 内容 |
|------|------|
| **原理** | 恶意脚本被注入到网页中，在其他用户的浏览器中执行 |
| **影响** | Cookie 窃取、会话劫持、钓鱼、篡改页面、键盘记录 |

**三种主要类型**：

| 类型 | 英文 | 原理 | 触发方式 |
|------|------|------|---------|
| **反射型 XSS** | Reflected XSS | 恶意脚本在 URL 参数中，后端直接输出到页面 | 用户点击恶意链接 |
| **存储型 XSS** | Stored XSS | 恶意脚本被存储到数据库，所有访问的用户都会执行 | 用户访问包含恶意脚本的页面 |
| **DOM 型 XSS** | DOM-based XSS | 前端 JS 直接把用户输入写到 DOM 中，不经过后端 | 用户操作触发前端 JS |

**防御措施（多层防御）**：
1. **输出编码**——根据输出位置（HTML/JS/CSS/URL）进行相应的编码
2. **输入验证**——白名单校验，过滤危险字符（辅助）
3. **CSP（内容安全策略）**——浏览器层面限制脚本执行
4. **HttpOnly Cookie**——防止 JS 读取 Cookie（减轻危害）
5. **Trusted Types**——从源头防止 DOM XSS

#### CSRF（跨站请求伪造，Cross-Site Request Forgery）

| 项目 | 内容 |
|------|------|
| **原理** | 利用用户已登录的身份，诱导用户访问恶意页面，自动发起伪造请求 |
| **影响** | 以用户的名义执行操作（改密码、转账、发邮件等） |
| **前提** | 用户已登录目标网站；目标网站仅凭 Cookie 认证 |

**防御措施**：
1. **CSRF Token**——请求中携带随机 Token，服务端验证
2. **SameSite Cookie**——限制跨站请求携带 Cookie
3. **验证 Referer / Origin**——检查请求来源（不够可靠）
4. **关键操作二次验证**——如短信验证码、支付密码

---

### 4.3 文件类

#### 文件上传漏洞

| 项目 | 内容 |
|------|------|
| **原理** | 上传功能没有正确校验文件类型和内容，攻击者上传恶意文件（如 WebShell） |
| **影响** | 服务器被控、WebShell 上传、任意代码执行 |
| **常见绕过** | 改后缀名、双后缀、Content-Type 伪造、图片马、解析漏洞 |

**防御措施（多层校验）**：
1. **文件扩展名白名单校验**（不是黑名单）
2. **文件内容校验**（检查文件头、魔数、内容）
3. **文件重命名**（随机文件名，防止预测路径）
4. **上传目录权限限制**（不可执行、禁止脚本解析）
5. **独立域名/独立服务器存储**
6. **文件大小限制**

#### 文件包含漏洞（LFI / RFI）

| 类型 | 全称 | 原理 | 影响 |
|------|------|------|------|
| **LFI** | 本地文件包含（Local File Inclusion） | 包含本地服务器上的文件 | 读取敏感文件、配合文件上传 Getshell |
| **RFI** | 远程文件包含（Remote File Inclusion） | 包含远程服务器上的文件 | 直接执行任意代码 |

**防御**：
- 尽量不要动态包含文件
- 白名单限制包含的文件
- 关闭 allow_url_include 等危险配置
- 严格的输入验证

### 4.4 逻辑类（业务逻辑漏洞）

#### 越权访问

| 类型 | 说明 | 示例 |
|------|------|------|
| **水平越权** | 同级别用户之间的越权 | 用户 A 查看/修改用户 B 的数据 |
| **垂直越权** | 低权限用户越权访问高权限功能 | 普通用户访问管理员功能 |
| **未授权访问** | 完全不需要认证就能访问 | 后台页面直接可以访问 |

**根本原因**：服务端没有对每个请求做权限校验，误以为前端控制了就安全。

**防御**：
- 服务端统一的权限校验中间件/过滤器
- 每个接口都验证用户身份和权限
- 最小权限原则
- 默认拒绝，显式允许

#### 其他业务逻辑漏洞

| 漏洞类型 | 说明 | 典型场景 |
|---------|------|---------|
| **支付漏洞** | 支付逻辑有缺陷 | 修改价格、修改数量为负数、重放支付成功 |
| **验证码绕过** | 验证码机制有问题 | 验证码不过期、可重复使用、可预测 |
| **密码找回漏洞** | 密码重置逻辑缺陷 | 重置链接可预测、验证码可爆破 |
| **条件竞争** | 并发请求导致逻辑错误 | 重复领取优惠、重复提现、重复下单 |
| **接口遍历** | 接口没有鉴权，遍历 ID 获取数据 | 用户 ID 自增，遍历获取所有用户信息 |

> **业务逻辑漏洞的特点**：
> - 没有通用的"工具"能扫出来，需要理解业务逻辑
> - 往往是高价值漏洞（直接影响钱和核心业务）
> - 也是 SRC 漏洞的重要来源
> - 防御需要安全人员深入理解业务

---

### 4.5 其他重要攻击类型

#### SSRF（服务器端请求伪造，Server-Side Request Forgery）

| 项目 | 内容 |
|------|------|
| **原理** | 服务器端发起的请求可以被用户控制，攻击者诱导服务器访问内部资源 |
| **影响** | 探测内网、访问内网服务、云环境元数据泄露、内网漏洞利用 |
| **为何并入 A01** | 本质上是访问控制问题——服务器能访问它不该访问的资源 |
| **常见场景** | 图片加载、URL 预览、远程文件读取、Webhook |

**防御**：
- 禁用不需要的协议（只允许 http/https）
- 内网地址黑名单（10.x、172.16-31.x、192.168.x、127.x 等）
- 不返回响应内容（防止读取数据）
- 专用出口网络隔离
- DNS 重绑定防护

#### XXE（XML 外部实体注入）

| 项目 | 内容 |
|------|------|
| **原理** | XML 解析器解析了包含外部实体引用的恶意 XML |
| **影响** | 任意文件读取、SSRF、DOS |
| **为什么减少了** | 很多现代 XML 解析器默认禁用外部实体了 |
| **防御** | 禁用 DTD（文档类型定义）、禁用外部实体、使用 JSON 替代 XML |

#### 反序列化漏洞

| 项目 | 内容 |
|------|------|
| **原理** | 反序列化不可信的数据，导致执行恶意代码 |
| **影响** | 远程代码执行（RCE） |
| **典型语言/框架** | Java（最多）、PHP、Python（pickle）、.NET |
| **防御** | 尽量不要反序列化不可信数据、白名单类限制、安全的反序列化库 |

#### API 安全缺陷

| 常见问题 | 说明 |
|---------|------|
| **未授权访问** | API 接口没有认证校验 |
| **越权访问** | BOLA（对象级授权破坏），OWASP API Top 10 第一名 |
| **速率限制缺失** | 没有限流，可暴力破解、数据爬取 |
| **数据过度暴露** | 返回了过多的字段（前端需要的没那么多） |
| **API 版本管理混乱** | 旧版本 API 有漏洞但没下线 |
| **影子 API** | 未记录、未管理的 API 接口 |

> **API 安全是当前 Web 安全的热点方向**。随着前后端分离和微服务架构的普及，API 越来越多，API 安全问题也越来越突出。OWASP 有专门的 **API Security Top 10**。

## 五、Web 安全防御体系

### 5.1 安全设计原则

| 原则 | 英文 | 在 Web 安全中的体现 |
|------|------|-------------------|
| **纵深防御** | Defense in Depth | 前端验证 + 服务端验证 + WAF + 数据库权限控制 |
| **最小权限** | Least Privilege | 数据库账号只给 SELECT/INSERT，不给 DROP/ALTER |
| **安全默认配置** | Secure by Default | 默认关闭调试功能、默认启用安全选项 |
| **失败安全** | Fail Secure | 认证失败默认拒绝，错误时不泄露敏感信息 |
| **职责分离** | Separation of Duties | 普通用户和管理员分离，操作和审计分离 |
| **不要信任客户端** | Never Trust the Client | 所有校验必须在服务端再做一遍，前端校验只是体验优化 |
| **安全左移** | Shift Left | 在设计和编码阶段就考虑安全，而不是上线后才补 |

### 5.2 输入验证与输出编码

#### 输入验证（Input Validation）

| 验证方式 | 说明 | 优先级 |
|---------|------|--------|
| **白名单验证** | 只允许符合预期格式的输入通过 | 推荐（首选） |
| **黑名单验证** | 过滤掉已知的危险字符 | 不推荐（容易被绕过） |
| **长度限制** | 限制输入的最大/最小长度 | 基础防线 |
| **类型验证** | 验证输入的类型（数字、邮箱、手机号等） | 基础防线 |

> **重要原则**：所有客户端验证都只能作为用户体验优化，**服务端必须重新验证一遍**。

#### 输出编码（Output Encoding）

根据输出位置的不同，使用不同的编码方式：

| 输出位置 | 编码方式 | 目的 |
|---------|---------|------|
| **HTML 内容** | HTML 实体编码（&lt; &gt; &amp; 等） | 防止 XSS |
| **JavaScript** | JavaScript 编码 | 防止 XSS |
| **CSS** | CSS 编码 | 防止 XSS |
| **URL 参数** | URL 编码 | 防止参数污染 |
| **SQL 查询** | 参数化查询（不是编码） | 防止 SQL 注入 |

### 5.3 安全配置与安全头

#### 重要的 HTTP 安全响应头

| 安全头 | 作用 | 推荐配置示例 |
|--------|------|-------------|
| **Strict-Transport-Security (HSTS)** | 强制使用 HTTPS，防止降级 | `max-age=63072000; includeSubDomains; preload` |
| **Content-Security-Policy (CSP)** | 限制资源加载，防 XSS | 按实际情况配置，默认 `default-src 'self'` |
| **X-Frame-Options** | 防止点击劫持 | `DENY` 或 `SAMEORIGIN` |
| **X-Content-Type-Options** | 禁止 MIME 嗅探 | `nosniff` |
| **Referrer-Policy** | 控制 Referer 泄露 | `strict-origin-when-cross-origin` |
| **X-XSS-Protection** | 浏览器 XSS 过滤（已过时） | 不建议依赖，用 CSP 替代 |
| **Permissions-Policy** | 控制浏览器功能权限 | `geolocation=(), camera=(), microphone=()` |

### 5.4 认证与会话管理安全

| 方面 | 最佳实践 |
|------|---------|
| **密码存储** | 使用 Argon2 / bcrypt / scrypt 等慢哈希算法，加盐 |
| **密码强度** | 强密码策略，长度优先于复杂度 |
| **多因素认证（MFA）** | 关键账号强制启用 MFA |
| **登录防护** | 登录失败次数限制、验证码、IP 限流 |
| **会话管理** | 会话 ID 足够随机、登录后重新生成会话 ID |
| **Cookie 属性** | HttpOnly + Secure + SameSite + 合理的过期时间 |
| **Token 管理** | JWT 使用短有效期 + 刷新机制，密钥足够强 |
| **注销功能** | 服务端使会话/Token 失效，不是只清前端 |
| **密码找回** | 安全的重置链接（随机、一次性、限时），不能直接返回密码 |

### 5.5 供应链安全

| 措施 | 说明 |
|------|------|
| **软件成分分析（SCA）** | 扫描项目依赖，发现已知漏洞 |
| **依赖项审计** | 定期审计依赖的安全性和活跃度 |
| **最小化依赖** | 减少不必要的依赖，攻击面越小越好 |
| **SBOM（软件物料清单）** | 记录软件使用了哪些组件和版本 |
| **依赖锁定** | 锁定依赖版本，防止意外升级引入问题 |
| **包签名验证** | 验证包的完整性和来源 |
| **CI/CD 安全** | 保护构建管道，防止供应链投毒 |

### 5.6 监控与日志

| 方面 | 最佳实践 |
|------|---------|
| **记录什么** | 登录事件、关键操作、异常请求、错误、权限变更 |
| **日志内容** | 时间、用户、IP、操作、结果、请求参数（敏感信息脱敏） |
| **日志存储** | 集中存储、防篡改、保留足够时间 |
| **告警规则** | 基于规则和异常检测的告警机制 |
| **定期审计** | 定期分析日志，发现异常行为 |
| **监控覆盖** | 应用层、API 层、基础设施层都要监控 |

> - sqlmap 是功能强大的 SQL 注入工具，仅限在**授权测试环境**中使用
> - 未经授权对他人系统使用 sqlmap 是违法行为
> - 自动化工具可能对目标系统造成压力和破坏
> - 用于学习时请使用本地靶场（DVWA、SQLi-Labs 等）

### 6.3 浏览器开发者工具

浏览器自带的开发者工具（F12）是 Web 安全测试的基础工具。

| 面板 | 安全用途 |
|------|---------|
| **Network（网络）** | 查看请求和响应、分析接口、查看 Cookie/Header |
| **Elements（元素）** | 查看和修改 DOM、分析前端逻辑、测试 XSS |
| **Console（控制台）** | 执行 JavaScript、调试前端代码 |
| **Application（应用）** | 查看 Cookie、LocalStorage、SessionStorage、缓存 |
| **Sources（源文件）** | 查看前端 JS 源码、设置断点调试 |
| **Security（安全）** | 查看证书、安全头、混合内容问题 |

### 6.4 SAST / DAST / SCA

| 类型 | 全称 | 说明 | 代表工具 |
|------|------|------|---------|
| **SAST** | 静态应用安全测试 | 不运行代码，直接分析源代码找漏洞 | Semgrep、SonarQube、Coverity、CodeQL |
| **DAST** | 动态应用安全测试 | 运行中的应用，从外部扫描找漏洞 | Burp Scanner、OWASP ZAP、Invicti、AppScan |
| **SCA** | 软件成分分析 | 分析第三方组件和依赖的漏洞 | OWASP Dependency-Check、Snyk、Dependabot、NPM Audit |

#### 各类工具对比

| 维度 | SAST | DAST | SCA |
|------|------|------|-----|
| **测试时机** | 编码阶段 | 测试/上线后 | 依赖管理阶段 |
| **是否需要运行** | 否 | 是 | 否 |
| **发现的问题** | 代码层面的漏洞 | 运行时的漏洞 | 第三方依赖漏洞 |
| **误报率** | 较高 | 中等 | 较低 |
| **修复成本** | 低（早发现） | 高（快上线了才发现） | 中等 |
| **适合谁用** | 开发人员、代码审计 | 安全测试人员 | 开发、安全运维 |

> **最佳实践**：不是三选一，而是都用——SAST 在开发阶段发现代码问题，SCA 发现依赖问题，DAST 做最终验证。三者互补，组成完整的应用安全测试体系。

| **子域名枚举** | subfinder、amass、Sublist3r | 发现子域名，扩大测试范围 |
| **指纹识别** | whatweb、Wappalyzer、EHole | 识别网站使用的技术栈和 CMS |

| **API 测试** | Postman、Insomnia、k6 | API 接口测试和性能测试 |
| **密码破解** | Hydra、Medusa、Burp Intruder | 暴力破解测试（仅授权环境） |

|---------|---------|
| **《网络安全法》** | 网络运行安全、网络信息安全、法律责任 |
| **《数据安全法》** | 数据安全保护、数据分类分级、数据出境 |
| **《个人信息保护法》** | 个人信息处理规则、个人权利、法律责任 |
| **《刑法》** | 非法侵入计算机信息系统罪、破坏计算机信息系统罪、提供侵入/非法控制计算机信息系统程序/工具罪 |
| **《关键信息基础设施安全保护条例》** | CII 安全保护 |

> **重要提醒**：
> - 技术本身没有对错，但使用技术的行为有合法与非法之分
> - "我只是学习/测试"不是免责理由
> - 未经授权的测试，即使没有造成损害，也可能违法
> - 安全从业者要对自己的行为负责，守住法律底线

### 10.3 安全工具使用原则

1. **授权原则**：只用在有书面授权的目标上
2. **最小影响原则**：测试时尽量减少对目标系统的影响（尤其是自动化扫描）
3. **保密原则**：对测试中接触到的数据保密
4. **报告原则**：发现漏洞及时报告，协助修复
5. **不滥用原则**：不利用漏洞获取超出测试范围的利益

### 10.4 学习建议

1. **先学防御，再学攻击**：理解了防御才能更好地理解攻击，也更安全
2. **以防御的视角学习攻击**：学习攻击是为了更好地防御，不是为了搞破坏
3. **在合法环境中练习**：靶场、CTF、授权的 SRC
4. **关注合规**：安全和合规是分不开的，懂安全也要懂合规
5. **坚守底线**：技术越强，责任越大，不要用技术做违法的事

> 它既需要扎实的基础（网络、系统、编程），
> 也需要持续的学习（新漏洞、新技术、新趋势层出不穷）。
>
> 但只要找对方法、持续练习、合法实践，
> 每个人都可以在这个领域找到自己的位置。
>
> 这条路没有捷径，但每一步都算数。
