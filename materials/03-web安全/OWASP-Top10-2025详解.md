## 一、OWASP Top 10 概述

### 1.1 什么是 OWASP Top 10

| 项目 | 内容 |
|------|------|
| **全称** | OWASP Top 10（开放式 Web 应用程序安全项目十大风险） |
| **发布机构** | OWASP（Open Web Application Security Project） |
| **性质** | Web 应用最关键安全风险的**行业共识标准** |
| **数据来源** | 基于数十万个应用的安全测试数据 + 广泛的行业调查 |
| **地位** | 安全开发生命周期的**事实基线**，影响合规检查、供应商问卷和安全培训 |

> **一句话理解**：OWASP Top 10 就是"当前 Web 应用最危险、最常见的 10 类安全风险"的排行榜，由全球安全行业共同评选和更新。

### 1.2 OWASP Top 10 的定位与价值

| 维度 | 说明 |
|------|------|
| **对企业** | Web 安全建设的基线参考、安全培训的标准教材、合规检查的对标清单 |
| **对开发人员** | 需要了解和避免的 10 类最常见安全错误 |
| **对安全人员** | Web 安全知识体系的核心框架、渗透测试的重点方向 |
| **对产品** | 供应商安全评估的重要参考、安全功能规划的依据 |
| **对教育** | Web 安全入门的标准课程大纲 |

> OWASP Top 10 不是"全部"，而是"最重要的 10 类"。
> 它是最低标准（baseline），不是终点——做好 Top 10 不代表绝对安全，但没做好 Top 10 肯定不安全。

### 1.3 修订历史与节奏

| 版本 | 发布年份 | 说明 |
|------|---------|------|
| **Top 10 2003** | 2003 | 最早的版本 |
| **Top 10 2004** | 2004 | |
| **Top 10 2007** | 2007 | |
| **Top 10 2010** | 2010 | |
| **Top 10 2013** | 2013 | 经典版本之一 |
| **Top 10 2017** | 2017 | 引入了"不安全的反序列化"等 |
| **Top 10 2021** | 2021 | 新增"不安全设计"，"注入"排名下降 |
| **Top 10 2025** | **2025.11 发布，2026.1 定稿** | 当前标准，新增供应链和异常处理 |
| **下一版** | 预计 2028-2029 | 大约每 3-4 年更新一次 |

> **⚠️ 2026 年时效性标注**：本文引用的是 **OWASP Top 10:2025** 版本，该版本于 2025 年 11 月发布、2026 年 1 月正式定稿，是 2026 年的现行标准。请在使用时注意版本，避免引用旧版本的分类和排名。

### 1.4 2025 版数据概览

| 指标 | 数据 | 说明 |
|------|------|------|
| **分析的应用数** | 数十万个 | 来自多家安全厂商的贡献数据 |
| **CVE 分析数** | 175,000+ | 用于供应链等类别的分析 |
| **CWE 检查数** | 589 个 | 2021 年约 400 个，覆盖面大幅扩大 |
| **映射到十类的 CWE** | 248 个 | 最终 589 个 CWE 中有 248 个映射到 Top 10 |
| **新增类别** | 2 个 | 软件供应链失效、特殊情况处理不当 |
| **合并类别** | 1 个 | SSRF 并入访问控制失效 |

### 1.5 研究方法简介

OWASP Top 10 不是拍脑袋排的，它有严谨的方法论：

```
数据收集
  ├── 可测量数据（Quantitative）：安全测试工具的数据
  │     └── 来自多家厂商的真实应用扫描数据
  └── 行业调查（Qualitative）：行业从业者的主观排序
        └── 数千名安全从业者的投票和反馈

      ↓ 综合分析

类别归纳
  ├── 将数百个 CWE 归纳为 10 大类别
  ├── 每个类别有代表性的 CWE 映射
  └── 考虑行业趋势和新兴风险

      ↓

Top 10 排名
  ├── 基于发生率、影响范围、可利用性等综合排序
  └── 发布候选版 → 收集反馈 → 正式定稿
```

## 二、2021 → 2025 主要变化分析

### 2.1 排名对比总表

| 2025 排名 | 编号 | 风险名称 | 2021 排名 | 变化 |
|---------|------|---------|----------|------|
| **1** | A01:2025 | 访问控制失效 | 1 | ➡️ 持平（连续四届榜首） |
| **2** | A02:2025 | 安全配置错误 | 5 | ⬆️⬆️ 上升 3 位（最大上升者） |
| **3** | A03:2025 | 软件供应链失效 | — | 🆕 新增 |
| **4** | A04:2025 | 加密机制失效 | 2 | ⬇️ 下降 2 位 |
| **5** | A05:2025 | 注入 | 3 | ⬇️ 下降 2 位（含 XSS） |
| **6** | A06:2025 | 不安全设计 | 4 | ⬇️ 下降 2 位 |
| **7** | A07:2025 | 认证失效 | 7 | ➡️ 持平（微调） |
| **8** | A08:2025 | 软件或数据完整性失效 | 8 | ➡️ 持平（微调） |
| **9** | A09:2025 | 安全日志与告警失效 | 10 | ⬆️ 上升 1 位（更名：监控→告警） |
| **10** | A10:2025 | 特殊情况处理不当 | — | 🆕 新增 |

> **从榜单中退出的 2021 版类别**：
> - **A05:2021 安全配置错误** → 上升到了第 2 位（不是退出，是上升了）
> - **A10:2021 服务端请求伪造（SSRF）** → 被并入 A01 访问控制失效

### 2.2 关键变化解读

#### 🆕 新增 A03：软件供应链失效

**为什么新增？**
- 过去几年供应链攻击频发（SolarWinds、Log4j、npm 恶意包等事件）
- 现代应用 80%+ 的代码来自第三方依赖
- 平均发生率达到 5.72%，是所有类别中最高的之一
- 虽然映射的 CWE 只有 11 个，但影响面极大

**反映的行业趋势**：
- 软件供应链安全从"小众话题"变成"主流风险"
- 企业越来越依赖开源组件和第三方服务
- 一个依赖出问题，影响成千上万的应用

---

#### 🆕 新增 A10：特殊情况处理不当

**为什么新增？**
- 错误处理和边界条件的安全问题长期被忽视
- AI 驱动的系统让这个问题更突出（异常输入可能导致 AI 产生不安全输出）
- 很多业务逻辑漏洞本质上是"异常情况没处理好"
- 涵盖了错误信息泄露、空值处理不当、边界条件绕过等

**反映的行业趋势**：
- 安全关注点从"已知漏洞类型"扩展到"设计和逻辑层面的缺陷"
- AI 时代，异常和边界情况的处理变得更加重要

---

#### ⬆️⬆️ A02 安全配置错误：从第 5 跃升至第 2

**为什么大幅上升？**
- **云环境普及**：云的配置复杂度远高于传统环境，配置错误成为主要风险来源
- **默认配置不安全**：很多云服务、容器、框架的默认配置不够安全
- **环境多样性**：多环境（开发/测试/生产）、多云、混合云增加了配置管理的难度
- **基础设施即代码（IaC）**：虽然提高了效率，但配置错误也更容易批量传播

**启示**：
- 云安全已经从"加分项"变成"必选项"
- 安全配置管理和基线检查的重要性大幅提升
- CSPM（云安全态势管理）类工具的需求增长

---

#### ⬇️ 注入：从第 3 降至第 5

**为什么下降？**
- **不是因为注入变少了**，而是其他风险（供应链、配置错误）上升更快
- ORM 和参数化查询的普及降低了 SQL 注入的发生率
- 框架层面的改进（如很多框架默认防 XSS）
- 安全开发意识提高，注入类漏洞相对更容易被检测和修复

**注意**：
- 排名下降 ≠ 风险降低，注入仍然是非常高频的漏洞
- XSS 被并入注入类别，使这个类别更全面
- 在实际测试中，注入类漏洞仍然很常见

---

#### 🔀 SSRF 被并入 A01 访问控制失效

**为什么合并？**
- SSRF 的本质是"服务器能访问它不该访问的资源"——这本质上就是访问控制问题
- 从"访问控制失效"的角度理解和防御 SSRF 更准确
- 避免把 SSRF 当作一个独立的、孤立的漏洞类型

**影响**：
- SSRF 不再是独立的 Top 10 类别
- 但它仍然是重要的安全风险，只是归类方式变了
- 访问控制失效的涵盖面进一步扩大

---

#### 📊 分析范围大幅扩大

| 指标 | 2021 版 | 2025 版 | 变化 |
|------|---------|---------|------|
| CWE 检查数 | ~400 个 | 589 个 | +47% |
| 映射到 Top 10 的 CWE | 约 180 个 | 248 个 | +38% |
| CVE 分析数 | 较少 | 175,000+ | 大幅增加 |

> 这说明 OWASP Top 10 的数据基础越来越扎实，覆盖面越来越广。
> 同时也说明：随着研究深入，我们发现的安全风险种类也越来越多。

## 三、A01:2025 访问控制失效（Broken Access Control）

### 3.1 基本信息

| 项目 | 内容 |
|------|------|
| **排名** | 第 1 位（连续四届榜首） |
| **英文原名** | Broken Access Control |
| **核心问题** | 用户可以访问或操作其权限范围之外的资源或功能 |
| **2025 变化** | 新增包含 SSRF（服务端请求伪造） |
| **CWE 映射数** | 30+ 个 CWE |
| **典型 CWE** | CWE-285（不当授权）、CWE-639（IDOR）、CWE-918（SSRF）等 |

### 3.2 典型攻击场景

#### 场景 1：水平越权（IDOR）

```
用户 A 的订单页面：
  https://example.com/order?id=123  （id=123 是用户 A 的订单）

攻击者把 id 改成 124：
  https://example.com/order?id=124

如果系统只验证了"用户是否登录"，没验证"这个订单是不是该用户的"，
攻击者就能看到用户 B 的订单信息——这就是水平越权。
```

水平越权的特点：同级用户之间越权，都是普通用户，但能访问别人的数据。

#### 场景 2：垂直越权

```
普通用户访问管理员后台：
  https://example.com/admin

如果系统只是在前端隐藏了"管理后台"的入口，
但后端没有验证用户的角色，
普通用户直接输入 URL 就能访问管理后台——这就是垂直越权。
```

垂直越权的特点：低权限用户越权访问高权限功能。

#### 场景 3：未授权访问

```
某个 API 接口完全不需要认证就能访问：
  GET /api/users/all → 返回所有用户列表

只要知道接口地址，任何人都能调用——这是最严重的访问控制失效。
```

#### 场景 4：SSRF（服务器端请求伪造）

```
网站有一个"图片加载"功能，用户可以输入图片 URL：
  https://example.com/load-image?url=https://test.com/a.jpg

攻击者把 url 改成内网地址：
  https://example.com/load-image?url=http://192.168.1.1/admin

服务器端发起请求，访问了内网资源——这就是 SSRF。
本质上是"服务器能访问它不该访问的资源"，属于访问控制问题。
```

### 3.3 常见成因

| 成因 | 说明 |
|------|------|
| **只做前端控制** | 前端隐藏按钮/菜单，但后端没有校验 |
| **依赖 obscurity** | 以为"用户不知道 URL 就不会访问" |
| **ID 可预测** | 使用自增 ID，容易遍历（1, 2, 3...） |
| **统一权限校验缺失** | 每个接口各自校验，有的忘写了 |
| **权限粒度太粗** | 只验证"是不是登录用户"，不验证"有没有权限访问这个数据" |
| **服务端内网访问无限制** | 服务器可以自由访问内网，没有限制 |

### 3.4 影响评估

| 影响维度 | 严重程度 | 说明 |
|---------|---------|------|
| **机密性** | 🔴 高 | 可能泄露所有用户的敏感数据 |
| **完整性** | 🔴 高 | 可能篡改他人数据或系统配置 |
| **可用性** | 🟡 中 | 可能删除数据导致服务不可用 |
| **普遍程度** | 🔴 很高 | 排名第一，说明非常普遍 |
| **可利用性** | 🟢 容易 | 很多时候改个参数就行，工具就能扫 |

### 3.5 防御措施

#### 核心防御原则

1. **服务端统一权限校验**——所有请求在服务端验证权限，不依赖前端

2. **默认拒绝（Deny by Default）**——默认没有权限，显式授权的才能访问

3. **最小权限原则**——只给用户完成任务需要的最小权限

#### 具体措施

| 防御层面 | 措施 |
|---------|------|
| **架构层** | 统一的权限校验中间件/过滤器，避免每个接口自己写（容易漏） |
| **数据层** | 查询时带上用户身份条件（如 `WHERE user_id = 当前用户`） |
| **API 层** | 使用基于属性的访问控制（ABAC）或基于角色的访问控制（RBAC） |
| **ID 设计** | 使用不可预测的 ID（UUID），降低遍历风险（但这不是主要防御） |
| **SSRF 防御** | 内网地址黑名单、协议限制、独立出口网络、DNS 重绑定防护 |
| **测试验证** | 越权测试：用 A 用户的 Token 访问 B 用户的数据，应该被拒绝 |

#### 防御代码示例（伪代码）

```
❌ 错误示范（只验证是否登录，不验证数据归属）：
  function getOrder(orderId) {
    if (!isLoggedIn()) return 401;       // 只检查登录状态
    return db.query("SELECT * FROM orders WHERE id = ?", orderId);
  }

✅ 正确示范（验证数据归属）：
  function getOrder(orderId) {
    const userId = getCurrentUserId();
    if (!userId) return 401;
    const order = db.query(
      "SELECT * FROM orders WHERE id = ? AND user_id = ?",  // 查询时带上用户 ID
      orderId, userId
    );
    if (!order) return 403;  // 找不到或不属于当前用户，返回 403
    return order;
  }
```

> **关键**：访问控制必须在**服务端**做，而且要**统一**做。不要依赖前端隐藏，也不要每个接口各自为政。

## 四、A02:2025 安全配置错误（Security Misconfiguration）

### 4.1 基本信息

| 项目 | 内容 |
|------|------|
| **排名** | 第 2 位（从第 5 位跃升，最大上升者） |
| **英文原名** | Security Misconfiguration |
| **核心问题** | 安全配置不当、缺失或不正确，导致系统暴露在风险中 |
| **2025 变化** | 上升 3 位，主要受云环境配置问题推动 |
| **CWE 映射数** | 20+ 个 CWE |
| **典型 CWE** | CWE-16（配置错误）、CWE-522（凭证保护不足）、CWE-209（错误信息泄露）等 |

### 4.2 典型场景

#### 场景 1：默认配置问题

| 问题 | 示例 |
|------|------|
| **默认密码** | 应用/设备使用默认密码（admin/admin） |
| **默认开启调试** | 生产环境开启调试模式，暴露栈轨迹和敏感信息 |
| **默认账户** | 没有禁用默认账户（如 test/guest/admin） |
| **默认权限** | 文件/目录权限过宽，任何人都能读写 |

#### 场景 2：云环境配置错误

| 问题 | 示例 |
|------|------|
| **存储桶公开** | S3/OSS 存储桶设置为公开可读，数据泄露 |
| **安全组过宽** | 安全组允许 0.0.0.0/0 访问敏感端口 |
| **IAM 权限过大** | IAM 角色权限超出实际需要（过度权限） |
| **未加密** | 存储、数据库没有启用加密 |
| **日志未启用** | 云平台的访问日志、操作日志没有开启 |

#### 场景 3：不必要的功能和服务

| 问题 | 示例 |
|------|------|
| **开启不必要的端口** | 服务器开了很多不需要的服务和端口 |
| **启用危险方法** | WebDAV、PUT/DELETE 等不需要的 HTTP 方法开启 |
| **示例页面保留** | 生产环境保留了示例页面、测试页面 |
| **管理接口暴露** | 管理后台、监控面板暴露在公网 |

#### 场景 4：错误信息泄露

| 问题 | 示例 |
|------|------|
| **详细错误页** | 生产环境返回完整的栈轨迹、SQL 错误信息 |
| **版本信息泄露** | 响应头泄露服务器、框架、中间件的版本号 |
| **目录列表** | 开启目录列表，可浏览文件结构 |

### 4.3 为什么在云时代排名大幅上升

```
传统时代                    云时代
  ├── 几台服务器              ├── 成百上千台虚拟机/容器
  ├── 手动配置                 ├── 自动化配置（IaC）
  ├── 网络边界清晰             ├── 边界模糊，微服务众多
  ├── 配置项较少               ├── 配置项爆炸式增长
  └── 错误影响有限             └── 一个配置错误可能影响全局
```

**云环境下配置错误的特点**：
- 配置数量多：云服务有大量配置项，每个都可能出错
- 影响范围大：一个配置错误可能影响整个云环境
- 传播速度快：IaC 模板的错误会批量复制到所有环境
- 动态变化快：云环境变化快，配置容易过时或漂移
- 权限复杂：IAM 权限模型复杂，容易配置过度权限

### 4.4 防御措施

| 防御层面 | 措施 |
|---------|------|
| **安全基线** | 建立和维护安全配置基线，所有环境按基线配置 |
| **自动化检查** | 使用配置核查工具定期扫描，发现偏差及时修复 |
| **CSPM** | 云安全态势管理工具，持续监控云配置安全 |
| **IaC 安全** | 基础设施即代码的静态扫描，在部署前发现配置问题 |
| **最小化部署** | 关闭不需要的服务、端口、功能，减少攻击面 |
| **环境隔离** | 开发/测试/生产环境严格隔离，配置分别管理 |
| **生产环境加固** | 禁用调试、自定义错误页、移除版本信息、禁用目录列表 |
| **定期审计** | 定期审计配置，确保没有漂移（配置漂移） |
| **变更管理** | 配置变更走流程，有审批、有记录、可回滚 |

#### 常见安全加固清单（节选）

- [ ] 所有默认密码已修改或默认账户已禁用
- [ ] 生产环境关闭调试模式和详细错误输出
- [ ] 不必要的服务和端口已关闭
- [ ] 目录列表已禁用
- [ ] 服务器版本信息已隐藏
- [ ] 安全组/防火墙策略遵循最小权限原则
- [ ] 云存储桶默认私有，公开需审批
- [ ] IAM 角色遵循最小权限原则
- [ ] 敏感数据存储已加密
- [ ] 日志和监控已启用

## 五、A03:2025 软件供应链失效（Software Supply Chain Failures）⭐ 新增

### 5.1 基本信息

| 项目 | 内容 |
|------|------|
| **排名** | 第 3 位（新增类别） |
| **英文原名** | Software Supply Chain Failures |
| **核心问题** | 软件供应链中的组件、依赖、管道存在安全缺陷或被篡改 |
| **2025 变化** | 新增类别，反映供应链安全日益重要 |
| **平均发生率** | 5.72%（所有类别中最高之一） |
| **CWE 映射数** | 11 个 CWE（数量少但影响大） |
| **典型 CWE** | CWE-1104（使用未经维护的第三方组件）、CWE-829（包含来自不可信控制域的功能）等 |

> **为什么是新增类别但排名这么高？**
> 虽然映射的 CWE 只有 11 个（是十类中最少的之一），但发生率很高，且影响面极大。
> 一个流行的开源组件有漏洞，会影响数十万甚至上百万个应用——这就是供应链风险的可怕之处。

### 5.2 典型场景

#### 场景 1：依赖库漏洞

```
你的应用
  └── 依赖了框架 A
        └── 依赖了工具库 B
              └── 依赖了日志库 C
                    └── 日志库 C 有漏洞（比如 Log4j）

你甚至不知道 C 的存在，但它有漏洞，你的应用就有风险。
```

**典型事件**：Log4j（Log4Shell）漏洞——一个小小的日志库，影响了全球几乎所有 Java 应用。

#### 场景 2：恶意开源包

```
攻击者在 npm/PyPI/maven 上发布一个包：
  名字和流行包很像（typosquatting，拼写劫持）
  或者投毒到一个流行包（账号被盗、维护者被收买）

开发者安装了这个包 → 包中的恶意代码在构建或运行时执行
→ 窃取密钥、植入后门、破坏构建产物
```

**典型事件**：npm 包投毒事件、PyPI 恶意包、SolarWinds 供应链攻击。

#### 场景 3：CI/CD 管道被入侵

```
攻击者入侵了 CI/CD 管道 → 修改了构建脚本
→ 构建出来的软件带后门 → 分发给所有客户
→ 所有客户都中招了（供应链攻击的最高境界）
```

**典型事件**：SolarWinds 攻击——攻击者在软件更新中植入后门，影响了数千个客户，包括美国政府机构。

#### 场景 4：不受维护的依赖

```
某个依赖库已经 3 年没更新了
  → 有漏洞没人修
  → 甚至项目已经被废弃
  → 但你的应用还在使用它

这就是"供应链中的定时炸弹"——现在没事，不代表将来没事。
```

### 5.3 为什么供应链安全越来越受重视

| 趋势 | 说明 |
|------|------|
| **开源普及** | 现代应用 80%+ 的代码来自第三方开源组件 |
| **依赖链复杂** | 一个应用可能依赖上千个间接依赖，根本数不清 |
| **攻击效率高** | 攻击一个上游组件，下游几千几万个应用全部中招 |
| **事件频发** | 近年重大安全事件很多和供应链有关 |
| **监管关注** | 各国开始出台供应链安全相关的法规和标准 |

### 5.4 防御措施

| 防御层面 | 措施 |
|---------|------|
| **依赖管理** | 建立依赖清单，知道用了哪些组件和版本 |
| **软件成分分析（SCA）** | 自动扫描依赖，发现已知漏洞和许可证风险 |
| **SBOM** | 软件物料清单（Software Bill of Materials），记录所有组件 |
| **最小化依赖** | 减少不必要的依赖，攻击面越小越好 |
| **依赖锁定** | 锁定依赖版本，使用 lockfile，防止意外升级 |
| **来源验证** | 验证包的签名和校验和，确保来源可信 |
| **CI/CD 安全** | 保护构建管道：最小权限、访问控制、 Secrets 管理 |
| **更新策略** | 建立依赖更新流程，及时修复安全漏洞 |
| **风险评估** | 对关键依赖进行风险评估（活跃度、维护情况、历史安全记录） |
| **供应链安全评估** | 对供应商和关键组件进行安全评估 |

#### 实践建议：从哪里开始

1. **先盘点**：用 SCA 工具扫一遍你的项目，看看用了哪些依赖，有哪些已知漏洞
2. **再排序**：按严重程度和可利用性排序，优先修高危的
3. **建流程**：建立依赖更新和漏洞修复的流程
4. **左移**：把 SCA 集成到 CI/CD 中，提交代码就检查
5. **长期治理**：SBOM、供应链安全策略、供应商管理

## 六、A04:2025 加密机制失效（Cryptographic Failures）

### 6.1 基本信息

| 项目 | 内容 |
|------|------|
| **排名** | 第 4 位（从第 2 位下降） |
| **英文原名** | Cryptographic Failures |
| **原名称** | Sensitive Data Exposure（敏感数据泄露，2017/2021 版叫这个） |
| **核心问题** | 加密机制缺失或使用不当，导致敏感数据泄露 |
| **CWE 映射数** | 30+ 个 CWE |
| **典型 CWE** | CWE-327（使用破损的加密算法）、CWE-311（缺少敏感数据加密）、CWE-798（硬编码凭证）等 |

> **排名下降说明什么？**
> 排名下降不一定是因为风险降低了，也可能是其他风险上升更快。
> 加密问题仍然非常重要，只是供应链、配置错误等问题更加突出。

### 6.2 典型场景

| 场景 | 说明 |
|------|------|
| **明文存储密码** | 密码用明文或弱哈希（MD5）存储，数据库泄露就是灾难 |
| **明文传输** | 使用 HTTP 而不是 HTTPS，数据在传输中可被窃听和篡改 |
| **弱加密算法** | 使用已被破解的算法：MD5、SHA-1、DES、RC4 等 |
| **硬编码密钥** | 密钥、密码写死在代码里或配置文件中，容易泄露 |
| **密码学误用** | 自己实现加密算法、错误使用加密模式（如 ECB 模式） |
| **随机数不安全** | 使用不安全的随机数生成器（如 Math.random() 做安全用途） |
| **证书问题** | 过期证书、自签名证书、证书验证关闭 |
| **敏感数据暴露** | 日志、错误页面、备份中包含明文敏感数据 |

### 6.3 防御措施

#### 数据分类

先做数据分类分级，知道哪些数据是敏感的：
- 密码、密钥、Token → 最高级
- 个人信息、支付信息、健康数据 → 高级
- 业务数据 → 中级
- 公开数据 → 低级

#### 分类保护

| 数据状态 | 保护措施 |
|---------|---------|
| **传输中** | 强制 HTTPS（TLS 1.2+）、禁用弱密码套件、HSTS |
| **存储中** | 敏感字段加密、整库加密（TDE）、磁盘加密 |
| **使用中** | 内存中尽量少存留敏感数据、使用后及时清理 |

#### 密码存储

| 算法 | 安全性 | 推荐程度 |
|------|--------|---------|
| **Argon2** | 高（抗 GPU 破解） | ⭐⭐⭐⭐⭐ 首选 |
| **bcrypt** | 高 | ⭐⭐⭐⭐ 推荐 |
| **scrypt** | 高 | ⭐⭐⭐⭐ 推荐 |
| **PBKDF2** | 中高（迭代次数足够时） | ⭐⭐⭐ 可用 |
| **SHA-256 + Salt** | 低（容易被 GPU 破解） | ❌ 不推荐用于密码 |
| **MD5 / SHA-1** | 极低（完全不安全） | ❌ 绝对不要用 |

> 密码哈希的关键：**慢**——计算越慢，暴力破解越难。
> 普通哈希（SHA-256）太快了，GPU 每秒可以算几十亿次。

#### 密钥管理

- 不要硬编码密钥（用环境变量、配置中心、KMS 等管理）
- 密钥定期轮换
- 密钥和数据分开存储
- 使用专业的密钥管理系统（KMS / HSM）

## 七、A05:2025 注入（Injection）

### 7.1 基本信息

| 项目 | 内容 |
|------|------|
| **排名** | 第 5 位（从第 3 位下降） |
| **英文原名** | Injection |
| **核心问题** | 不可信数据被注入到命令或查询中，改变了执行逻辑 |
| **2025 变化** | 排名下降，但仍是高频风险；XSS 被并入此类别 |
| **CWE 映射数** | 30+ 个 CWE |
| **典型 CWE** | CWE-89（SQL 注入）、CWE-79（XSS）、CWE-78（命令注入）、CWE-90（LDAP 注入）等 |

> **XSS 被并入注入类别**：
> 从本质上讲，XSS 就是把脚本注入到 HTML/JS 中，也是一种注入攻击。
> 2025 版把 XSS 从独立类别合并到注入类别，使分类更加准确。

### 7.2 注入类型总览

| 注入类型 | 注入对象 | 典型场景 | 风险等级 |
|---------|---------|---------|---------|
| **SQL 注入** | SQL 查询语句 | 登录框、搜索框、查询参数 | 🔴 高 |
| **命令注入** | 系统命令 | 调用系统命令的功能（ping、文件操作等） | 🔴 高 |
| **XSS（跨站脚本）** | HTML/JS | 留言板、评论、用户资料、搜索结果 | 🔴 高 |
| **LDAP 注入** | LDAP 查询 | 目录服务查询、用户认证 | 🟡 中 |
| **XPath 注入** | XPath 查询 | XML 数据查询 | 🟡 中 |
| **OS 命令注入** | 操作系统命令 | 调用系统命令的接口 | 🔴 高 |
| **表达式注入** | 表达式引擎 | OGNL、SpEL、EL 表达式 | 🟡 中高 |
| **模板注入** | 模板引擎 | Jinja2、Freemarker、Velocity 等 | 🟡 中高 |

### 7.3 SQL 注入

**原理**：用户输入被直接拼接到 SQL 语句中，改变了 SQL 的语义。

**根本原因**：代码和数据没有分离。

**防御（按优先级）**：
1. **参数化查询（预编译语句）**——根本解决方法
2. **输入白名单验证**——辅助手段
3. **最小权限原则**——数据库账号只给必要的权限（兜底）
4. **WAF**——补充防线（不能作为主要防御）

> **核心思想**：永远不要把用户输入和 SQL 语句拼接在一起。

### 7.4 XSS（跨站脚本）

**原理**：恶意脚本被注入到网页中，在其他用户的浏览器中执行。

**三种类型**：
- **反射型**：脚本在 URL 中，后端直接输出
- **存储型**：脚本存在数据库里，所有访问用户都中招
- **DOM 型**：前端 JS 直接把用户输入写到 DOM 中

**防御（多层防御）**：
1. **输出编码**——根据输出位置做相应编码（HTML/JS/CSS/URL）
2. **输入验证（白名单）**——辅助
3. **CSP（内容安全策略）**——浏览器层面限制脚本执行
4. **HttpOnly Cookie**——减轻 Cookie 被窃取的危害
5. **Trusted Types**——从源头防 DOM XSS

### 7.5 注入的通用防御原则

| 原则 | 说明 |
|------|------|
| **不要拼接** | 永远不要把不可信输入拼接到命令/查询/代码中 |
| **使用安全的 API** | 参数化查询、安全的模板引擎、安全的命令执行方式 |
| **白名单验证** | 只允许符合预期格式的输入通过 |
| **输出编码** | 输出到不同上下文用不同的编码方式 |
| **最小权限** | 运行环境的权限越小越好（即使被注入也影响有限） |
| **默认安全** | 框架和库默认开启安全选项 |

## 八、A06:2025 不安全设计（Insecure Design）

### 8.1 基本信息

| 项目 | 内容 |
|------|------|
| **排名** | 第 6 位（从第 4 位下降） |
| **英文原名** | Insecure Design |
| **核心问题** | 设计层面的缺陷，不是代码写错了，而是从设计上就有问题 |
| **与注入的区别** | 注入是"实现错误"，不安全设计是"设计错误" |
| **CWE 映射数** | 40+ 个 CWE（十类中最多） |
| **典型 CWE** | CWE-209（错误信息泄露）、CWE-444（HTTP 请求走私）、CWE-284（访问控制不当）等 |

### 8.2 什么是"不安全设计"

"不安全设计"关注的是**设计和架构层面**的缺陷，而不是代码实现层面的 bug。

```
安全漏洞的两个层面：

  实现缺陷（Implementation Bug）        设计缺陷（Design Flaw）
  ├── 代码写错了                        ├── 从设计上就有问题
  ├── 修复：改代码                      ├── 修复：重新设计
  ├── 例子：SQL 注入（拼接了字符串）     ├── 例子：没有权限校验的设计
  └── SAST 工具比较容易发现              └── 工具很难发现，需要人来分析
```

### 8.3 典型场景

| 场景 | 说明 |
|------|------|
| **业务逻辑漏洞** | 支付流程设计有缺陷，可以绕过支付 |
| **缺少风控** | 没有限流、没有防刷、没有异常检测 |
| **信任边界错误** | 信任了不该信任的数据或接口 |
| **错误的安全假设** | 假设"用户不会发现这个接口"、假设"前端会校验" |
| **职责不分离** | 一个角色能完成所有高风险操作，没有制衡 |
| **缺少状态管理** | 关键步骤没有状态校验，可以跳步执行 |
| **默认配置不安全** | 默认开启危险功能、默认权限过大 |

### 8.4 为什么"不安全设计"很重要

- **工具扫不出来**：自动化扫描器很难发现设计缺陷
- **影响往往更大**：设计缺陷通常影响整个业务逻辑，而不只是某个点
- **修复成本更高**：设计问题发现越晚，修复成本越高（可能要重构）
- **数量在增加**：随着安全编码的普及，低级漏洞减少，设计层面的问题占比上升

### 8.5 防御措施

| 措施 | 说明 |
|------|------|
| **安全左移** | 在设计阶段就引入安全，而不是等写完代码才测 |
| **威胁建模** | 系统设计时进行威胁分析，识别风险 |
| **安全设计评审** | 架构和设计方案要经过安全评审 |
| **安全设计原则** | 遵循安全设计原则（最小权限、纵深防御、失败安全等） |
| **业务安全测试** | 不只是测技术漏洞，还要测业务逻辑 |
| **安全设计模式** | 总结和复用安全的设计模式 |
| **安全需求** | 在需求阶段就明确安全需求 |

> **核心思想**：问题发现得越早，修复成本越低。
> 设计阶段发现并修复一个问题，成本可能是上线后发现的 1/100。

## 九、A07:2025 认证失效（Authentication Failures）

### 9.1 基本信息

| 项目 | 内容 |
|------|------|
| **排名** | 第 7 位（基本持平） |
| **英文原名** | Authentication Failures |
| **曾用名** | Broken Authentication（失效身份认证） |
| **核心问题** | 身份认证机制存在缺陷，攻击者可以冒充其他用户 |
| **CWE 映射数** | 20+ 个 CWE |
| **典型 CWE** | CWE-287（不当认证）、CWE-384（会话固定）、CWE-307（过度认证尝试）等 |

### 9.2 典型场景

| 场景 | 说明 |
|------|------|
| **弱密码** | 用户可以设置简单密码，如 123456、admin 等 |
| **暴力破解无防护** | 登录接口没有限流和锁定，攻击者可以无限试密码 |
| **会话固定** | 登录前后会话 ID 不变，攻击者可以固定受害者的会话 ID |
| **不安全的 Cookie** | Cookie 没有设置 HttpOnly、Secure、SameSite 属性 |
| **会话泄露** | 会话 ID 出现在 URL 中、日志中，容易泄露 |
| **密码明文存储** | 密码用明文或弱哈希存储 |
| **凭证填充** | 攻击者用其他网站泄露的账号密码来试（撞库） |
| **找回密码漏洞** | 密码重置链接可预测、验证码可爆破、重置逻辑有缺陷 |
| **缺少 MFA** | 没有多因素认证，账号被盗风险高 |
| **JWT 安全问题** | JWT 密钥太弱、算法可被篡改、没有过期机制 |

### 9.3 防御措施

| 方面 | 最佳实践 |
|------|---------|
| **密码策略** | 强密码策略（长度优先于复杂度）、禁止常见弱密码 |
| **密码存储** | 使用 Argon2 / bcrypt / scrypt 等慢哈希算法，加盐 |
| **登录防护** | 登录失败次数限制、验证码、IP 限流、防暴力破解 |
| **会话管理** | 会话 ID 足够随机（密码学安全）、登录后重新生成会话 ID |
| **Cookie 安全** | HttpOnly + Secure + SameSite（Lax/Strict）+ 合理过期时间 |
| **多因素认证（MFA）** | 关键账号强制启用 MFA（短信/邮件/TOTP/硬件密钥） |
| **注销机制** | 服务端使会话失效，不能只清前端 Cookie |
| **密码找回** | 安全的重置链接（随机、一次性、限时），不返回原始密码 |
| **防凭证填充** | 检测异常登录、新设备登录提醒、风险认证 |
| **JWT 安全** | 强密钥、合理的过期时间、验证算法、刷新机制 |

## 十、A08:2025 软件或数据完整性失效（Software or Data Integrity Failures）

### 10.1 基本信息

| 项目 | 内容 |
|------|------|
| **排名** | 第 8 位（基本持平） |
| **英文原名** | Software or Data Integrity Failures |
| **核心问题** | 软件或数据在传输/存储/更新过程中被篡改，而没有被检测到 |
| **2025 变化** | 基本持平，和供应链安全（A03）有联系但不同 |
| **CWE 映射数** | 10+ 个 CWE |
| **典型 CWE** | CWE-494（下载代码未经完整性校验）、CWE-502（反序列化不受信任的数据）、CWE-345（数据源验证不足）等 |

> **和 A03（供应链失效）的区别**：
> - A03 关注的是供应链本身的安全（依赖漏洞、恶意包、CI/CD 管道安全）
> - A08 关注的是完整性验证的缺失（更新时不校验签名、数据传输不校验完整性）
> 两者相关但角度不同——A03 是"供应链有问题"，A08 是"没有验证完整性"。

### 10.2 典型场景

#### 场景 1：自动更新无校验

```
软件自动更新功能：
  1. 下载更新包
  2. 直接安装

问题：如果下载过程中被篡改，或者下载源被劫持，
     用户安装的就是带后门的更新包。
     因为没有验证更新包的签名或哈希。
```

#### 场景 2：不安全的反序列化

```
应用接收序列化的数据（如 Java 对象流、Python pickle）
→ 直接反序列化
→ 恶意构造的序列化数据可以执行任意代码

这就是反序列化漏洞——本质上也是完整性问题：
你不知道收到的数据是不是原来的样子。
```

#### 场景 3：CI/CD 管道完整性问题

```
代码提交 → 构建 → 测试 → 部署
  ↓
如果中间某个环节被篡改（构建脚本被改、依赖被投毒）
最终部署到生产环境的就是有问题的版本
```

#### 场景 4：数据传输无完整性保护

```
数据在传输过程中没有完整性校验
→ 中间人可以篡改数据
→ 接收方收到的是被篡改的数据，但不知道
```

### 10.3 防御措施

| 措施 | 说明 |
|------|------|
| **数字签名** | 软件更新、重要数据使用数字签名验证来源和完整性 |
| **哈希校验** | 下载文件后验证哈希值（SHA-256 等） |
| **安全反序列化** | 尽量不要反序列化不可信数据；白名单类限制；使用安全的格式（JSON） |
| **CI/CD 安全** | 保护构建管道、代码签名、构建产物签名 |
| **完整性校验** | 关键数据传输和存储都要有完整性保护 |
| **供应链完整性** | 验证第三方组件的完整性和来源 |
| **不可篡改日志** | 安全日志使用只追加、防篡改的存储 |

## 十一、A09:2025 安全日志与告警失效（Security Logging & Alerting Failures）

### 11.1 基本信息

| 项目 | 内容 |
|------|------|
| **排名** | 第 9 位（从第 10 位上升 1 位） |
| **英文原名** | Security Logging and Alerting Failures |
| **曾用名** | Insufficient Logging & Monitoring（2021 及之前） |
| **更名说明** | 从"监控不足"改为"告警失效"，更强调主动检测和告警 |
| **核心问题** | 没有足够的日志记录和告警机制，攻击无法被及时发现 |
| **CWE 映射数** | 10+ 个 CWE |
| **典型 CWE** | CWE-778（日志记录不足）、CWE-223（信息泄露）、CWE-532（日志中敏感信息）等 |

### 11.2 典型场景

| 场景 | 说明 |
|------|------|
| **关键操作无日志** | 登录、密码修改、权限变更等关键操作没有记录日志 |
| **日志不完整** | 日志缺少关键信息（谁、什么时候、做了什么、结果） |
| **没有告警** | 有日志但没有告警规则，异常行为不会触发提醒 |
| **日志只存不看** | 日志收集了但没人分析，出了事才去查 |
| **日志留存时间不够** | 日志保留时间太短，等发现问题时日志已经没了 |
| **日志容易被篡改** | 攻击者入侵后可以删掉或修改日志，销毁证据 |
| **敏感信息明文日志** | 密码、Token 等敏感数据被明文记录在日志里 |
| **缺少集中管理** | 日志分散在各个地方，难以关联分析 |

### 11.3 为什么"告警"比"监控"更重要

- 收集日志 ≠ 监控
- 监控 ≠ 告警
- 告警 ≠ 响应

```
日志收集 → 监控分析 → 告警触发 → 响应处置
  ↑         ↑          ↑          ↑
  │         │          │          └── 出了事能不能及时处理
  │         │          └──────────── 异常能不能被发现
  │         └─────────────────────── 有没有人在看
  └───────────────────────────────── 有没有记录
```

> 很多企业的问题是：日志收集了一大堆，但告警没做或者告警不准，等于白收集。
> 2025 版把名字从"监控"改为"告警"，就是强调——**能被发现才是关键**。

### 11.4 防御措施

| 方面 | 最佳实践 |
|------|---------|
| **记录什么** | 登录/登出、关键操作、权限变更、异常请求、错误、安全事件 |
| **日志内容** | 时间戳（精确到毫秒）、用户 ID、IP、操作类型、对象、结果、请求参数（脱敏） |
| **日志存储** | 集中存储（SIEM / 日志平台）、防篡改（只追加）、足够的留存时间 |
| **告警规则** | 基于规则和异常检测的告警、分级告警、合理的阈值 |
| **告警质量** | 减少误报（告警疲劳是大问题）、持续优化规则 |
| **响应流程** | 告警有人处理、有 SLA、有升级机制 |
| **定期审计** | 定期分析日志和告警数据，发现趋势和盲区 |
| **敏感信息保护** | 日志中的敏感数据要脱敏，不能明文存密码/Token |
| **日志完整性** | 防篡改、定期备份、异地存储 |

## 十二、A10:2025 特殊情况处理不当（Mishandling of Exceptional Conditions）⭐ 新增

### 12.1 基本信息

| 项目 | 内容 |
|------|------|
| **排名** | 第 10 位（新增类别） |
| **英文原名** | Mishandling of Exceptional Conditions |
| **核心问题** | 异常情况、边界条件、错误处理不当，导致安全问题 |
| **2025 变化** | 新增类别，AI 驱动系统下风险上升 |
| **CWE 映射数** | 约 20 个 CWE |
| **典型 CWE** | CWE-252（未检查返回值）、CWE-703（异常条件不当处理）、CWE-476（空指针解引用）、CWE-193（越界）等 |

### 12.2 什么是"特殊情况处理不当"

这个类别涵盖的是"程序在处理异常情况、边界条件、错误情况时出的安全问题"。

```
正常情况：程序工作正常
异常情况：输入异常、状态异常、资源不足、并发冲突...
  ↓
处理不当 → 安全问题
  ├── 错误信息泄露（给攻击者提供信息）
  ├── 安全检查被绕过（异常时跳过了校验）
  ├── 状态不一致（异常时数据没回滚）
  ├── 拒绝服务（异常导致崩溃）
  └── 权限提升（异常导致权限判断错误）
```

### 12.3 典型场景

| 场景 | 说明 |
|------|------|
| **错误信息泄露** | 生产环境返回详细的错误栈、SQL 错误、调试信息 |
| **空值处理不当** | null/undefined 导致安全检查被绕过（如 null 等于任何权限） |
| **边界值问题** | 数字溢出、数组越界、长度为 0 或负数时的异常行为 |
| **异常时跳过校验** | try-catch 中把安全检查也跳过了，异常时直接放行 |
| **并发/竞态条件** | 并发请求导致逻辑错误（重复领取、重复下单） |
| **资源耗尽** | 异常导致资源泄露（内存、连接、文件句柄），最终 DoS |
| **AI 系统异常输入** | 恶意构造的异常输入导致 AI 产生不安全输出（提示注入等） |
| **默认值安全问题** | 异常时使用默认值，而默认值的权限或安全性有问题 |

### 12.4 为什么 AI 时代这个问题更重要

在 AI 驱动的系统中，"特殊情况处理不当"的风险被放大了：

- AI 系统面对的输入空间更大（自然语言、图像等），异常和边界情况更多
- 提示注入（Prompt Injection）本质上就是"异常输入处理不当"
- AI 模型的"幻觉"和意外输出，也是一种"特殊情况没处理好"
- AI 系统的可解释性差，异常情况更难预测和测试

> 这也是为什么 2025 版新增这个类别——随着 AI 应用越来越多，异常和边界情况的安全处理变得越来越重要。

### 12.5 防御措施

| 措施 | 说明 |
|------|------|
| **统一错误处理** | 全局异常处理器，返回用户友好的错误页面，不泄露内部信息 |
| **防御性编程** | 对所有输入做验证，对所有返回值做检查，假设"可能出错" |
| **边界值测试** | 充分测试边界情况：空值、零、负数、极大值、超长字符串等 |
| **异常时保持安全状态** | 异常发生时，系统应该进入安全状态（默认拒绝，而不是默认放行） |
| **失败安全** | 出错时"关闭"而不是"打开"（门禁坏了应该锁死，不是一直开着） |
| **并发安全** | 关键操作考虑并发场景，使用锁、事务、乐观并发控制等 |
| **AI 安全** | AI 系统的输入验证、输出校验、防护性过滤 |
| **日志和监控** | 异常情况要记录日志，便于分析和改进 |

### 13.1 攻击面与 Top 10 映射

| 攻击面 | 主要涉及的 Top 10 类别 |

| **后端 / 应用层** | A01 访问控制失效、A05 注入、A06 不安全设计、A07 认证失效、A08 完整性失效 |

| **运维 / 监控** | A02 安全配置错误、A09 日志与告警失效 |

### 13.2 安全开发生命周期（SDLC）中的 Top 10 集成

```
需求阶段 → 设计阶段 → 开发阶段 → 测试阶段 → 上线 → 运维
  │          │          │          │         │       │
  │          │          │          │         │       └── A09 监控告警
  │          │          │          │         └────── A02 配置审计
  │          │          │          └──────────────── A05 注入（DAST）
  │          │          └─────────────────────────── A03 供应链（SCA）
  │          │                                      A05 注入（SAST）
  │          └────────────────────────────────────── A06 不安全设计（威胁建模）
  └───────────────────────────────────────────────── A01 访问控制（安全需求）
```

**各阶段的安全活动**：

| SDLC 阶段 | 安全活动 | 对应 Top 10 类别 |
|----------|---------|----------------|
| **需求阶段** | 安全需求分析、隐私影响评估 | A01 访问控制、A07 认证、A04 加密 |
| **设计阶段** | 威胁建模、安全设计评审 | A06 不安全设计、A01 访问控制、A08 完整性 |
| **开发阶段** | 安全编码规范、代码评审、SAST、SCA | A05 注入、A03 供应链、A04 加密 |
| **测试阶段** | 安全测试、渗透测试、DAST | A01 访问控制、A05 注入、A07 认证 |
| **上线阶段** | 配置审计、安全基线检查 | A02 配置错误、A04 加密 |
| **运维阶段** | 监控、告警、漏洞管理、日志审计 | A09 日志告警、A02 配置错误 |

### 13.3 按角色的防御实践建议

#### 对开发人员

1. **输入验证**：所有外部输入都要验证，白名单优先
2. **参数化查询**：永远不要拼接 SQL，用参数化查询
3. **输出编码**：输出到不同上下文做相应编码（防 XSS）
4. **安全配置**：默认安全配置，生产环境关闭调试
5. **依赖管理**：定期更新依赖，用 SCA 工具扫描
6. **错误处理**：统一错误处理，不泄露敏感信息
7. **认证会话安全**：安全的密码存储、Cookie 属性、会话管理

#### 对安全工程师

1. **威胁建模**：在设计阶段就介入，识别风险
2. **安全评审**：代码评审、设计评审、配置评审
3. **安全测试**：渗透测试、漏洞验证、安全工具集成
4. **安全培训**：提升开发团队的安全意识和能力
5. **安全度量**：跟踪安全指标，衡量安全改进效果

#### 对运维人员

1. **安全基线**：建立和维护安全配置基线
2. **补丁管理**：及时修复安全漏洞
3. **日志监控**：完善的日志收集和告警机制
4. **访问控制**：严格的权限管理，最小权限原则
5. **备份与恢复**：安全的备份策略，定期验证恢复

### 14.2 重点项目介绍

#### OWASP ASVS（Application Security Verification Standard）

| 项目 | 内容 |
|------|------|

| **定位** | 更详细、更全面的应用安全验证清单 |
| **级别** | 三个级别：L1（基础）、L2（标准）、L3（高级） |
| **和 Top 10 的关系** | Top 10 是"最严重的 10 类风险"，ASVS 是"全面的验证清单" |
| **用途** | 应用安全评估、安全验收标准、供应商安全要求 |

> 简单说：Top 10 是"重点关注"，ASVS 是"全面检查清单"。
> 做 Top 10 是及格线，通过 ASVS L1/L2/L3 是更全面的安全验证。

```
入门：
  OWASP Top 10 → 了解最重要的 10 类风险
  OWASP Juice Shop → 动手实践，体验漏洞

进阶：
  OWASP Testing Guide → 学习怎么系统地测试
  OWASP Cheat Sheets → 各主题的详细参考
  OWASP ZAP → 学习使用安全扫描工具

深入：
  OWASP ASVS → 全面的应用安全验证标准
  OWASP SAMM → 组织级安全成熟度模型
  其他专项项目（按兴趣选择）
```

---

> **总结**：
> OWASP Top 10 是 Web 安全的"入门必读"和"基线标准"，但它不是全部。
> 它告诉我们"最危险的 10 类风险是什么"，
> 但真正的安全实践需要更全面的体系——
> 从设计到开发、从测试到运维、从个人到组织。
>
> Top 10 是起点，不是终点。
