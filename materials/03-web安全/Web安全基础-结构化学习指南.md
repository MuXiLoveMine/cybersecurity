## 2. 核心概念

### 2.1 HTTP 协议基础

#### 什么是 HTTP

**HTTP（HyperText Transfer Protocol，超文本传输协议）** 是 Web 的基础协议，定义了浏览器和服务器之间如何请求和响应数据。

```
客户端（浏览器）                          服务器
    │                                      │
    │  1. 发起 HTTP 请求                    │
    │     GET /index.html HTTP/1.1         │
    │     Host: example.com                │
    │─────────────────────────────────────►│
    │                                      │
    │  2. 返回 HTTP 响应                    │
    │     HTTP/1.1 200 OK                  │
    │     Content-Type: text/html          │
    │                                      │
    │     <html>...</html>                 │
    │◄─────────────────────────────────────│
```

#### HTTP 方法（动词）

| 方法 | 作用 | 安全性 | 幂等性 |
|------|------|--------|--------|
| **GET** | 获取资源 | ✅ 安全（不修改数据） | ✅ 幂等（多次调用结果一样） |
| **POST** | 创建资源 | ❌ 不安全 | ❌ 不幂等 |
| **PUT** | 更新资源（整体替换） | ❌ 不安全 | ✅ 幂等 |
| **PATCH** | 部分更新 | ❌ 不安全 | ❌ 不幂等 |
| **DELETE** | 删除资源 | ❌ 不安全 | ✅ 幂等 |
| **HEAD** | 获取响应头（无 body） | ✅ 安全 | ✅ 幂等 |
| **OPTIONS** | 查询支持的方法 | ✅ 安全 | ✅ 幂等 |

> **安全提示**：GET 请求不应该用来修改数据。很多安全漏洞（如 CSRF）和 GET 请求的误用有关。

#### HTTP 状态码

| 状态码 | 含义 | 安全相关 |
|--------|------|---------|
| **200 OK** | 请求成功 | - |
| **301/302** | 重定向 | 开放重定向漏洞 |
| **400 Bad Request** | 请求参数错误 | 错误信息泄露 |
| **401 Unauthorized** | 未认证 | 认证相关 |
| **403 Forbidden** | 已认证但无权限 | 越权访问 |
| **404 Not Found** | 资源不存在 | 信息收集 |
| **500 Internal Server Error** | 服务器内部错误 | 错误信息泄露（栈轨迹等） |

#### HTTP 请求结构

```
请求行：GET /path?query=value HTTP/1.1
请求头：
  Host: example.com
  User-Agent: Mozilla/5.0
  Cookie: sessionid=abc123
  Content-Type: application/json
  Authorization: Bearer tokenxxx
空行
请求体（可选）：
  {"username": "admin", "password": "xxx"}
```

#### HTTP 响应结构

```
状态行：HTTP/1.1 200 OK
响应头：
  Content-Type: text/html; charset=utf-8
  Set-Cookie: sessionid=xyz789; HttpOnly
  Content-Length: 1234
空行
响应体：
  <html>页面内容</html>
```

> **为什么要懂 HTTP？**  
> Web 安全的本质就是"HTTP 请求/响应中出了问题"。不懂 HTTP，就无法理解 Web 漏洞。

### 2.2 Cookie

#### 什么是 Cookie

**Cookie** 是服务器发送到浏览器并保存在本地的一小块数据，它会在浏览器下次向同一服务器发起请求时被携带。

**作用**：HTTP 是无状态的，Cookie 用来**维持状态**（如登录状态、用户偏好等）。

#### Cookie 的工作流程

```
1. 浏览器首次请求服务器
   └── 服务器响应时设置 Cookie：
       Set-Cookie: username=alice

2. 浏览器保存 Cookie

3. 浏览器后续请求时自动带上 Cookie：
   Cookie: username=alice

4. 服务器读取 Cookie，识别用户
```

#### Cookie 的重要属性

| 属性 | 作用 | 安全意义 |
|------|------|---------|
| **Name / Value** | Cookie 的名称和值 | 存储会话 ID 等 |
| **Domain** | Cookie 属于哪个域名 | 决定哪些域名能访问 |
| **Path** | Cookie 属于哪个路径 | 进一步限制范围 |
| **Expires / Max-Age** | 过期时间 | 会话 Cookie vs 持久 Cookie |
| **HttpOnly** | 禁止 JavaScript 读取 | ⭐ 防止 XSS 窃取 Cookie |
| **Secure** | 只在 HTTPS 连接中发送 | ⭐ 防止明文传输泄露 |
| **SameSite** | 控制跨站请求是否携带 Cookie | ⭐ 防止 CSRF |

**安全的 Cookie 配置示例**：
```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600
```

### 2.3 Session

#### 什么是 Session

**Session（会话）** 是服务器端维护的用户状态机制。服务器为每个用户创建一个 Session，存储用户信息，用一个唯一的 Session ID 标识。

#### Session 的工作流程

```
用户登录 → 服务器验证通过 → 创建 Session → 生成 Session ID
                                                ↓
                                         写入 Cookie 返回给浏览器
                                                ↓
浏览器保存 SessionID 的 Cookie
                                                ↓
后续请求 → 浏览器带上 Cookie → 服务器读取 SessionID → 找到对应 Session → 识别用户
```

#### Session vs Cookie 的区别

| 维度 | Cookie | Session |
|------|--------|---------|
| **存储位置** | 浏览器（客户端） | 服务器 |
| **安全性** | 较低（可被篡改/窃取） | 较高（数据在服务端） |
| **存储容量** | 小（约 4KB） | 大（服务器内存/数据库） |
| **生命周期** | 可设置过期时间 | 会话结束或超时失效 |
| **典型用途** | 记住用户名、偏好设置 | 登录状态、购物车、敏感信息 |

> **关系**：Session 依赖 Cookie 来传递 Session ID。如果禁用 Cookie，也可以通过 URL 参数传递（但不安全）。

#### Session 安全要点

1. **Session ID 要足够随机**（密码学安全的随机数）
2. **登录后重新生成 Session ID**（防止会话固定攻击）
3. **设置合理的过期时间**（超时自动失效）
4. **Cookie 设置 HttpOnly + Secure + SameSite**
5. **注销时服务端销毁 Session**（不是只清前端 Cookie）

### 2.4 Token

#### 什么是 Token

**Token（令牌）** 是一串代表用户身份的字符串，由服务器生成，客户端保存并在后续请求中携带。

最常见的是 **JWT（JSON Web Token）**。

#### JWT 的结构

JWT 由三部分组成，用 `.` 分隔：

```
xxxxx.yyyyy.zzzzz
  │     │      └── 签名（Signature）
  │     └────────── 载荷（Payload）
  └──────────────── 头部（Header）
```

| 部分 | 内容 | 说明 |
|------|------|------|
| **Header** | 算法、类型 | `{"alg": "HS256", "typ": "JWT"}`，Base64 编码 |
| **Payload** | 用户信息、过期时间等 | `{"sub": "123", "name": "alice", "exp": 1700000000}`，Base64 编码 |
| **Signature** | 签名 | 用密钥对前两部分签名，防止篡改 |

> **重要**：JWT 的 Header 和 Payload 只是 Base64 编码，**不是加密**！任何人都能解码看到内容。不要在 JWT 里放敏感信息。

#### Token vs Session 的区别

| 维度 | Session | Token（JWT） |
|------|---------|-------------|
| **存储位置** | 服务端 | 客户端 |
| **服务端状态** | 有状态（需查 Session） | 无状态（自包含） |
| **扩展性** | 较差（多服务器需共享 Session） | 好（分布式友好） |
| **注销难度** | 简单（服务端删除即可） | 复杂（需黑名单等机制） |
| **适用场景** | 传统 Web 应用 | SPA、API、微服务 |

#### Token 安全要点

1. **使用强密钥签名**（密钥足够长、足够随机）
2. **设置合理的过期时间**（Access Token 有效期短，配合 Refresh Token）
3. **验证算法**（确保用的是预期算法，防止算法混淆攻击）
4. **不要存敏感信息**（Payload 是 Base64 编码，不是加密）
5. **使用 HTTPS**（防止 Token 在传输中被窃取）

### 2.5 同源策略（SOP）

#### 什么是同源策略

**同源策略（Same-Origin Policy, SOP）** 是 Web 安全的基石。它限制从一个源加载的文档或脚本如何与另一个源的资源交互。

**目的**：隔离潜在的恶意文档，减少攻击载体。

#### 什么是"同源"

两个 URL 属于**同源**，必须同时满足三个相同：

```
  https://www.example.com:443/path/page.html
  └─┬──┘ └──────┬──────────┘ └┬┘
  协议          主机           端口

  同源 = 协议相同 + 主机相同 + 端口相同
```

| URL A | URL B | 是否同源 | 原因 |
|-------|-------|---------|------|
| `https://a.com/x.html` | `https://a.com/y.html` | ✅ 同源 | 协议、主机、端口都相同 |
| `https://a.com/x.html` | `http://a.com/x.html` | ❌ 不同源 | 协议不同 |
| `https://a.com/x.html` | `https://api.a.com/x.html` | ❌ 不同源 | 主机不同（子域名不同） |
| `https://a.com/x.html` | `https://a.com:8080/x.html` | ❌ 不同源 | 端口不同 |

#### 同源策略限制了什么

| 资源/操作 | 限制情况 | 说明 |
|-----------|---------|------|
| **Cookie / LocalStorage** | ❌ 严格限制 | 不同源不能读取对方存储 |
| **DOM 访问** | ❌ 严格限制 | JS 不能访问不同源页面的 DOM |
| **AJAX / Fetch** | ❌ 默认限制 | 跨域请求默认被拦截（可通过 CORS 放宽） |
| **图片 / CSS / JS 加载** | ✅ 允许嵌入 | 可以加载跨域资源（但有限制） |
| **iframe 嵌套** | ⚠️ 有限制 | 可以嵌入，但 JS 不能互相访问 DOM |

> **为什么同源策略这么重要？**  
> 如果没有同源策略，恶意网站 A 可以读取你登录的银行网站 B 的所有内容和 Cookie——Web 将完全不可信。

### 2.6 CORS（跨域资源共享）

#### 什么是 CORS

**CORS（Cross-Origin Resource Sharing，跨域资源共享）** 是一种在受控情况下放宽同源策略限制的机制。它允许服务器明确指定哪些源可以访问它的资源。

#### CORS 的工作流程

```
浏览器（源 A）                           服务器（源 B）
    │                                        │
    │  1. 发起跨域请求                         │
    │     Origin: https://a.example.com       │
    │───────────────────────────────────────►│
    │                                        │
    │  2. 服务器返回响应 + CORS 头             │
    │     Access-Control-Allow-Origin: ...    │
    │◄───────────────────────────────────────│
    │                                        │
    │  3. 浏览器检查 CORS 头                   │
    │     允许 → 把响应给 JS                   │
    │     拒绝 → 拦截响应（控制台报错）         │
```

#### 简单请求 vs 预检请求

| 类型 | 触发条件 | 过程 |
|------|---------|------|
| **简单请求** | GET/HEAD/POST + 简单 Content-Type | 直接发请求，看响应头判断是否允许 |
| **预检请求（Preflight）** | PUT/DELETE、自定义 Header、JSON 等 | 先发 **OPTIONS** 请求"问"服务器允不允许，再发真实请求 |

**预检请求的意义**：在发送可能有副作用的请求（如 PUT/DELETE）之前，先确认服务器是否允许，防止意外修改数据。

#### 常见 CORS 响应头

| 响应头 | 作用 |
|--------|------|
| `Access-Control-Allow-Origin` | 允许哪些源（`*` 表示所有源，或具体的源） |
| `Access-Control-Allow-Methods` | 允许的 HTTP 方法 |
| `Access-Control-Allow-Headers` | 允许的请求头 |
| `Access-Control-Allow-Credentials` | 是否允许携带 Cookie（设为 `true` 时不能用 `*`） |
| `Access-Control-Max-Age` | 预检请求的缓存时间（秒） |

#### CORS 安全注意事项

| ❌ 危险配置 | ✅ 安全配置 |
|------------|------------|
| `Access-Control-Allow-Origin: *` | 精确指定允许的源 |
| `Allow-Origin: *` + `Allow-Credentials: true` | 需要凭证时必须指定具体源 |
| 从请求的 Origin 头直接回显 | 白名单校验 Origin |

> **CORS 配置错误本身就是安全漏洞**，可能导致敏感数据泄露。

## 3. Web 安全边界

Web 安全不是单一层面的问题，而是一个多层次的体系。攻击者只需要找到一个层面的一个漏洞，而防守者需要在每个层面都做好防护。

```
用户层（人的安全）
    │ 社会工程学、钓鱼、账号安全
    ▼
浏览器 / 前端层
    │ XSS、CSRF、前端逻辑漏洞、CSP、同源策略
    ▼
网络 / 传输层
    │ HTTPS、TLS、中间人攻击、流量劫持
    ▼
应用 / 后端层
    │ SQL 注入、文件上传、命令注入、业务逻辑漏洞
    ▼
API 层
    │ 未授权访问、越权、速率限制缺失
    ▼
数据库层
    │ 注入、权限配置、数据加密
    ▼
基础设施层（服务器/云）
    │ 配置错误、未授权访问、容器安全
```

### 3.1 浏览器端

#### 攻击面

| 攻击类型 | 说明 |
|---------|------|
| **XSS** | 注入恶意脚本，窃取 Cookie、篡改页面 |
| **CSRF** | 利用用户登录态，伪造请求 |
| **点击劫持** | 用透明 iframe 覆盖，诱导用户点击 |
| **前端逻辑漏洞** | 前端校验被绕过、前端加密被破解 |
| **敏感信息泄露** | 注释、JS 源码中包含敏感信息 |

#### 浏览器自带的安全机制

| 机制 | 作用 |
|------|------|
| **同源策略** | 隔离不同源的资源和数据 |
| **CSP（内容安全策略）** | 限制脚本和资源加载，防 XSS |
| **HttpOnly Cookie** | 防止 JS 读取 Cookie |
| **SameSite Cookie** | 限制跨站请求携带 Cookie |
| **X-Frame-Options** | 防止点击劫持 |
| **HSTS** | 强制使用 HTTPS |

> **记住**：浏览器安全机制是重要的防线，但不能完全依赖。攻击者有各种绕过技巧。

---

### 3.2 服务器端

#### 攻击面

| 攻击类型 | 说明 |
|---------|------|
| **SQL 注入** | 注入 SQL 语句，窃取/篡改数据 |
| **命令注入** | 注入系统命令，控制服务器 |
| **文件上传漏洞** | 上传恶意文件，GetShell |
| **文件包含漏洞** | 包含恶意文件，执行代码 |
| **越权访问** | 访问权限外的功能和数据 |
| **业务逻辑漏洞** | 利用业务逻辑缺陷（如支付漏洞） |
| **反序列化漏洞** | 反序列化恶意数据，执行代码 |

#### 服务器端的防御原则

1. **不要信任客户端**：所有校验必须在服务端再做一遍
2. **输入验证**：所有外部输入都要验证（白名单优先）
3. **最小权限**：服务进程、数据库账号权限越小越好
4. **统一的安全中间件**：认证、授权、日志等统一处理
5. **错误处理**：统一错误页面，不泄露内部信息

---

### 3.3 数据库层

#### 攻击面

| 攻击类型 | 说明 |
|---------|------|
| **SQL 注入** | 最常见的数据库攻击 |
| **权限提升** | 利用数据库漏洞获取更高权限 |
| **数据泄露** | 数据库被拖库 |
| **配置错误** | 默认密码、弱口令、端口暴露 |

#### 数据库安全要点

| 方面 | 最佳实践 |
|------|---------|
| **访问控制** | 最小权限原则，应用账号只给必要的权限 |
| **注入防御** | 参数化查询（最核心） |
| **数据加密** | 敏感数据加密存储、传输加密 |
| **审计日志** | 记录数据库操作，便于溯源 |
| **备份安全** | 备份加密、定期验证恢复 |
| **补丁管理** | 及时安装数据库安全补丁 |
| **网络隔离** | 数据库不直接暴露在公网 |

| **VPN / 内网隔离** | 敏感系统不直接暴露在公网 |

## 5. 常见漏洞：原理、风险、防御要点

### 5.1 SQL 注入

#### 原理

**SQL 注入（SQL Injection）**：用户输入被直接拼接到 SQL 语句中，改变了 SQL 的语义，导致攻击者可以操纵数据库查询。

**根本原因**：代码和数据没有分离——用户输入被当作代码执行。

#### 攻击原理演示（仅学习用）

```
正常登录查询：
  SELECT * FROM users WHERE username = 'admin' AND password = '123456'

攻击者在密码框输入：' OR '1'='1

拼接后变成：
  SELECT * FROM users WHERE username = 'admin' AND password = '' OR '1'='1'
                                                              └──────┬──────┘
                                                              恒成立条件！

结果：查询出所有用户，直接绕过密码验证
```

#### 风险等级

| 维度 | 等级 | 说明 |
|------|------|------|
| **危害** | 🔴 严重 | 数据泄露、篡改、删除，甚至服务器被控 |
| **普遍性** | 🔴 高 | 非常常见，尤其是老旧系统 |
| **可利用性** | 🟢 容易 | 工具能自动化检测和利用 |

#### 常见类型

| 类型 | 说明 | 触发条件 |
|------|------|---------|
| **联合注入（UNION）** | 用 UNION 合并查询结果，直接获取数据 | 页面回显查询结果 |
| **报错注入** | 利用数据库报错信息获取数据 | 页面显示数据库错误 |
| **布尔盲注** | 根据页面真假（不同响应）判断 | 页面有真假差异但不回显数据 |
| **时间盲注** | 根据响应时间判断 | 页面完全无差异，只能靠时间 |

#### 防御措施（按优先级）

| 优先级 | 防御措施 | 说明 |
|--------|---------|------|
| ⭐⭐⭐⭐⭐ | **参数化查询（预编译语句）** | 最核心、最根本的防御。SQL 结构和数据分离，用户输入永远是数据 |
| ⭐⭐⭐ | **输入白名单验证** | 辅助手段。只允许符合预期格式的输入通过 |
| ⭐⭐⭐ | **最小权限原则** | 数据库账号只给必要的权限（如只有 SELECT/INSERT），即使注入也影响有限 |
| ⭐⭐ | **WAF** | 补充防线。有绕过可能，不能作为主要防御 |
| ⭐ | **安全编码规范** | 从源头避免，代码评审 |

#### 安全代码示例（伪代码）

```
❌ 错误示范（字符串拼接，存在注入）：
  function getUser(username, password) {
    sql = "SELECT * FROM users WHERE username = '" + username + "' AND password = '" + password + "'"
    return db.execute(sql)
  }

✅ 正确示范（参数化查询）：
  function getUser(username, password) {
    sql = "SELECT * FROM users WHERE username = ? AND password = ?"
    return db.execute(sql, [username, password])  // 参数化，数据和代码分离
  }
```

> **核心思想**：永远不要把用户输入拼接到 SQL 语句中。

### 5.2 XSS（跨站脚本）

#### 原理

**XSS（Cross-Site Scripting，跨站脚本攻击）**：恶意脚本被注入到网页中，当其他用户浏览网页时，这些脚本在他们的浏览器中执行。

**本质**：也是一种注入攻击——把脚本注入到 HTML/JS 中。

#### 三种主要类型

| 类型 | 英文 | 原理 | 触发方式 | 危害程度 |
|------|------|------|---------|---------|
| **反射型 XSS** | Reflected XSS | 恶意脚本在 URL 参数中，后端直接输出到页面 | 用户点击恶意链接 | 🟡 中（需诱导点击） |
| **存储型 XSS** | Stored XSS | 恶意脚本存储在数据库，所有访问用户都会执行 | 用户访问包含脚本的页面 | 🔴 高（影响所有访问者） |
| **DOM 型 XSS** | DOM-based XSS | 前端 JS 直接把用户输入写到 DOM 中，不经过后端 | 用户操作触发前端 JS | 🟡 中 |

#### 攻击能做什么

- 窃取 Cookie（会话劫持）
- 篡改页面内容（钓鱼、欺诈）
- 记录键盘输入
- 发起 CSRF 攻击
- 重定向到恶意网站

#### 防御措施（多层防御）

| 层级 | 措施 | 作用 |
|------|------|------|
| 第一层 | **输出编码** | 根据输出位置（HTML/JS/CSS/URL）进行相应的编码，让脚本不被执行 |
| 第二层 | **输入验证（白名单）** | 过滤不符合预期格式的输入（辅助手段） |
| 第三层 | **CSP（内容安全策略）** | 浏览器层面限制脚本执行，即使注入了也跑不起来 |
| 第四层 | **HttpOnly Cookie** | 防止 JS 读取 Cookie，减轻 Cookie 被窃取的危害 |
| 第五层 | **Trusted Types** | 从源头上防止 DOM XSS（现代浏览器支持） |

#### 安全代码示例（伪代码）

```
❌ 错误示范（直接输出用户输入，存在 XSS）：
  <div>搜索结果：<%= userInput %></div>

✅ 正确示范（HTML 实体编码后输出）：
  <div>搜索结果：<%= htmlEncode(userInput) %></div>
  // htmlEncode 会把 < 变成 &lt;，> 变成 &gt;，& 变成 &amp; 等
```

> **记住**：输出到不同的上下文，要用不同的编码方式。HTML 编码不能用在 JavaScript 里，反之亦然。

### 5.3 CSRF（跨站请求伪造）

#### 原理

**CSRF（Cross-Site Request Forgery，跨站请求伪造）**：攻击者利用用户已登录的身份，诱导用户访问恶意页面，自动发起伪造的请求，以用户的名义执行操作。

**核心**：利用 Cookie 会自动携带的特性，在用户不知情的情况下发起请求。

#### 攻击流程

```
1. 用户登录了银行网站 bank.com
   └── 浏览器保存了 bank.com 的登录 Cookie

2. 用户在同一个浏览器中访问了恶意网站 evil.com

3. evil.com 的页面中自动向 bank.com 发起请求（如转账）
   <img src="https://bank.com/transfer?to=hacker&amount=10000">

4. 浏览器自动带上 bank.com 的 Cookie 发送请求

5. 银行服务器收到请求，验证 Cookie 通过，执行转账
   └── 服务器以为是用户自己操作的
```

#### 攻击成立的前提

1. ✅ 用户已登录目标网站（有有效 Cookie）
2. ✅ 目标网站仅凭 Cookie 认证（没有其他验证）
3. ✅ 用户访问了恶意页面（诱导点击）
4. ✅ 请求可以被跨站发起（GET 请求或简单 POST）

#### 风险等级

| 维度 | 等级 | 说明 |
|------|------|------|
| **危害** | 🟡 中高 | 以用户名义执行操作（改密码、转账、发消息等） |
| **普遍性** | 🟡 中 | 很多网站防御不完善 |
| **可利用性** | 🟡 中 | 需要诱导用户访问恶意页面 |

#### 防御措施

| 优先级 | 防御措施 | 说明 |
|--------|---------|------|
| ⭐⭐⭐⭐⭐ | **CSRF Token** | 请求中携带随机 Token，服务端验证。Token 不可预测，且不在 Cookie 中 |
| ⭐⭐⭐⭐ | **SameSite Cookie** | 设置 `SameSite=Lax` 或 `Strict`，限制跨站请求携带 Cookie |
| ⭐⭐⭐ | **验证 Referer / Origin** | 检查请求来源（不够可靠，可被绕过） |
| ⭐⭐⭐ | **关键操作二次验证** | 如短信验证码、支付密码、重新登录 |
| ⭐⭐ | **只接受 POST** | GET 请求不修改数据（最低限度） |

#### 安全代码示例（伪代码）

```
✅ CSRF Token 防御流程：

1. 用户访问表单页面时，服务端生成随机 Token 并存入 Session
   <form action="/change-password" method="POST">
     <input type="hidden" name="csrf_token" value="随机字符串">
     <input type="password" name="new_password">
     <button type="submit">修改密码</button>
   </form>

2. 用户提交表单时，Token 一起提交

3. 服务端验证：
   function changePassword(newPassword, csrfToken) {
     if (!validateCsrfToken(csrfToken)) {  // 验证 Token
       return 403  // Token 不匹配，拒绝请求
     }
     // 执行修改密码
   }
```

> **SameSite Cookie 详解**：  
> - `Strict`：完全禁止跨站请求携带 Cookie（最严，但体验差）  
> - `Lax`：大多数情况禁止，用户主动跳转（点击链接）时允许（平衡）  
> - `None`：完全允许（需同时设置 Secure）

### 5.4 文件上传漏洞

#### 原理

**文件上传漏洞**：上传功能没有正确校验文件类型和内容，攻击者可以上传恶意文件（如 WebShell），从而控制服务器。

#### 常见绕过方式

| 绕过方式 | 说明 |
|---------|------|
| **改后缀名** | 把 `.php` 改成 `.jpg`（如果只检查 Content-Type） |
| **双后缀** | `shell.php.jpg`（某些解析规则下会被当作 PHP） |
| **Content-Type 伪造** | 修改请求头的 Content-Type |
| **图片马** | 把恶意代码插到图片里（文件头是图片，后面是代码） |
| **解析漏洞** | 利用中间件的解析缺陷（如 Apache 的 `%00` 截断） |
| **.htaccess** | 上传 .htaccess 文件改变解析规则 |

#### 风险等级

| 维度 | 等级 | 说明 |
|------|------|------|
| **危害** | 🔴 严重 | 可能直接上传 WebShell，控制整个服务器 |
| **普遍性** | 🟡 中 | 有上传功能的网站都可能有此问题 |
| **可利用性** | 🟡 中 | 取决于防护严格程度 |

#### 防御措施（多层校验）

| 层级 | 措施 | 说明 |
|------|------|------|
| 第一层 | **文件扩展名白名单校验** | 只允许指定的后缀（如 jpg/png/gif），用白名单不用黑名单 |
| 第二层 | **文件内容校验** | 检查文件头（魔数）、文件内容，不是图片就拒绝 |
| 第三层 | **文件重命名** | 随机文件名，防止预测路径，防止解析漏洞 |
| 第四层 | **上传目录权限限制** | 上传目录不可执行、禁止脚本解析 |
| 第五层 | **独立域名/独立服务器存储** | 和主站隔离，即使上传了恶意文件也影响有限 |
| 第六层 | **文件大小限制** | 防止大文件 DoS |

#### 安全代码示例（伪代码）

```
✅ 安全的文件上传处理：

  function uploadFile(file) {
    // 1. 白名单校验扩展名
    allowedExts = ['.jpg', '.jpeg', '.png', '.gif']
    ext = getFileExtension(file.name)
    if (!allowedExts.contains(ext.toLowerCase())) {
      return error("不允许的文件类型")
    }

    // 2. 校验文件内容（检查文件头）
    if (!isValidImage(file.content)) {
      return error("文件内容无效")
    }

    // 3. 生成随机文件名
    randomName = generateRandomString() + ext

    // 4. 保存到独立的上传目录（不可执行）
    savePath = "/uploads/" + randomName
    saveFile(file.content, savePath)

    return success(randomName)
  }
```

### 5.5 越权访问

#### 原理

**越权访问**：用户可以访问或操作其权限范围之外的资源或功能。

这是 OWASP Top 10:2025 的 **A01 访问控制失效**，连续四届排名第一。

#### 三种类型

| 类型 | 说明 | 示例 |
|------|------|------|
| **水平越权** | 同级别用户之间的越权 | 用户 A 查看/修改用户 B 的订单 |
| **垂直越权** | 低权限用户越权访问高权限功能 | 普通用户访问管理员后台 |
| **未授权访问** | 完全不需要认证就能访问 | 后台接口直接能调用 |

#### 水平越权示例（IDOR）

```
用户 A 的订单页面：
  https://example.com/order?id=1001  （id=1001 是用户 A 的订单）

攻击者把 id 改成 1002：
  https://example.com/order?id=1002

如果系统只验证了"用户是否登录"，
没验证"这个订单是不是该用户的"，
攻击者就能看到用户 B 的订单信息。
```

这种通过修改对象 ID 来越权的方式，有个专门的名字叫 **IDOR（Insecure Direct Object Reference，不安全的直接对象引用）**。

#### 根本原因

> 服务端没有对每个请求做权限校验，误以为前端控制了就安全。

#### 风险等级

| 维度 | 等级 | 说明 |
|------|------|------|
| **危害** | 🔴 严重 | 可能泄露所有用户的敏感数据 |
| **普遍性** | 🔴 极高 | 排名第一，说明非常普遍 |
| **可利用性** | 🟢 容易 | 很多时候改个参数就行 |

#### 防御措施

| 优先级 | 防御措施 | 说明 |
|--------|---------|------|
| ⭐⭐⭐⭐⭐ | **服务端统一权限校验** | 所有请求在服务端验证权限，不依赖前端 |
| ⭐⭐⭐⭐⭐ | **默认拒绝** | 默认没有权限，显式授权的才能访问 |
| ⭐⭐⭐⭐ | **最小权限原则** | 只给用户完成任务需要的最小权限 |
| ⭐⭐⭐ | **数据查询带用户条件** | 查询时带上用户 ID（如 `WHERE user_id = ?`） |
| ⭐⭐⭐ | **统一权限中间件** | 用中间件/过滤器统一处理，避免每个接口各自写 |
| ⭐⭐ | **不可预测的 ID** | 使用 UUID 而不是自增 ID（辅助，不是主要防御） |

#### 安全代码示例（伪代码）

```
❌ 错误示范（只验证登录，不验证数据归属）：
  function getOrder(orderId) {
    if (!isLoggedIn()) return 401  // 只检查是否登录
    return db.query("SELECT * FROM orders WHERE id = ?", orderId)
  }

✅ 正确示范（验证数据归属）：
  function getOrder(orderId) {
    const userId = getCurrentUserId()
    if (!userId) return 401
    const order = db.query(
      "SELECT * FROM orders WHERE id = ? AND user_id = ?",  // 查询时带上用户 ID
      [orderId, userId]
    )
    if (!order) return 403  // 找不到或不属于当前用户，返回 403
    return order
  }
```

> **关键**：访问控制必须在**服务端**做，而且要**统一**做。"前端隐藏了入口"不等于安全。

### 5.6 命令注入

#### 原理

**命令注入（Command Injection）**：用户输入被拼接到系统命令中执行，攻击者可以构造恶意输入来执行任意系统命令。

#### 攻击原理演示（仅学习用）

```
正常功能：网站提供 ping 测试，用户输入 IP 地址
  后端执行：ping -c 4 192.168.1.1

攻击者输入：192.168.1.1; ls /

拼接后变成：
  ping -c 4 192.168.1.1; ls /
                      └──┬──┘
                     命令分隔符！
  执行完 ping 后，还会执行 ls / 命令
```

#### 常见的命令连接符

| 符号 | 作用 |
|------|------|
| `;` | 顺序执行多个命令 |
| `&&` | 前一个成功才执行后一个 |
| `||` | 前一个失败才执行后一个 |
| `|` | 管道，前一个的输出作为后一个的输入 |
| `\n` | 换行，相当于回车执行 |
| `` ` `` | 反引号，先执行里面的命令（命令替换） |
| `$()` | 命令替换 |

#### 风险等级

| 维度 | 等级 | 说明 |
|------|------|------|
| **危害** | 🔴 严重 | 任意命令执行，服务器被控 |
| **普遍性** | 🟡 中 | 有调用系统命令功能的地方可能存在 |
| **可利用性** | 🟢 容易 | 找到注入点后利用相对简单 |

#### 防御措施

| 优先级 | 防御措施 | 说明 |
|--------|---------|------|
| ⭐⭐⭐⭐⭐ | **尽量不调用系统命令** | 用语言内置的 API 或库函数替代 |
| ⭐⭐⭐⭐ | **使用安全的执行方式** | 参数化执行，不是字符串拼接（如 Python 的 subprocess 列表参数） |
| ⭐⭐⭐ | **严格的输入白名单** | 只允许特定字符通过（如 IP 地址只允许数字和点） |
| ⭐⭐⭐ | **最小权限运行** | Web 进程以低权限用户运行，即使被注入也影响有限 |
| ⭐⭐ | **禁用危险函数** | 如 PHP 的 exec、system 等（不需要的话） |

#### 安全代码示例（伪代码）

```
❌ 错误示范（字符串拼接，存在命令注入）：
  function ping(ip) {
    return exec("ping -c 4 " + ip)  // 直接拼接
  }

✅ 正确示范 1（用安全的 API，不调用系统命令）：
  function ping(ip) {
    return pingLibrary.ping(ip)  // 使用编程语言的 ping 库
  }

✅ 正确示范 2（参数化执行 + 输入验证）：
  function ping(ip) {
    if (!isValidIp(ip)) {  // 严格验证输入格式
      return error("无效的 IP 地址")
    }
    return exec(["ping", "-c", "4", ip])  // 参数数组形式，不是字符串拼接
  }
```

> **核心思想**：和 SQL 注入一样——永远不要把用户输入拼接到命令字符串中。

## 6. 安全设计原则

安全设计原则是指导安全实践的高层准则，贯穿于所有安全工作中。

### 6.1 最小权限原则（Least Privilege）

**定义**：每个用户、每个程序、每个服务，只拥有完成其任务所必需的最小权限。

| 层面 | 示例 |
|------|------|
| **数据库** | Web 应用的数据库账号只有 SELECT/INSERT/UPDATE，没有 DROP/ALTER |
| **操作系统** | Web 服务以普通用户运行，不是 root/administrator |
| **API 接口** | 普通用户接口只能访问自己的数据，不能访问别人的 |
| **云服务** | IAM 角色只给必要的权限，不是 Administrator |

> **为什么重要？**：即使系统被攻破，攻击者能做的事情也有限——这是"兜底"的防线。

---

### 6.2 纵深防御（Defense in Depth）

**定义**：不是只靠一道防线，而是多层设防。即使一层被突破，还有下一层。

```
攻击者 → [防火墙] → [WAF] → [输入验证] → [参数化查询] → [数据库权限] → 数据
          第一层     第二层      第三层        第四层         第五层
```

| 漏洞 | 多层防御示例 |
|------|-------------|
| **XSS** | 输入验证 → 输出编码 → CSP → HttpOnly Cookie |
| **SQL 注入** | WAF → 输入验证 → 参数化查询 → 数据库最小权限 |
| **CSRF** | SameSite Cookie → CSRF Token → 关键操作二次验证 |

> **攻防不对称**：攻击者只需要找到一个漏洞，防守者需要防住所有可能的攻击面。纵深防御可以降低"一个漏洞就全盘皆输"的风险。

---

### 6.3 默认安全（Secure by Default）

**定义**：系统的默认配置应该是安全的，而不是需要用户自己去"打开安全"。

| 示例 | 默认不安全 ❌ | 默认安全 ✅ |
|------|-------------|-----------|
| **调试模式** | 默认开启 | 默认关闭 |
| **目录列表** | 默认开启 | 默认关闭 |
| **密码策略** | 无要求 | 要求强密码 |
| **HTTPS** | 默认 HTTP | 默认 HTTPS |
| **新用户权限** | 给很多权限 | 只给基础权限 |

> **现实**：大多数人用默认配置。默认不安全 = 大多数人不安全。

---

### 6.4 输入校验（Input Validation）

**定义**：对所有来自外部的输入进行验证，确保它们符合预期的格式和范围。

| 校验方式 | 说明 | 推荐程度 |
|---------|------|---------|
| **白名单验证** | 只允许符合预期格式的输入通过 | ⭐⭐⭐⭐⭐ 首选 |
| **黑名单验证** | 过滤掉已知的危险字符 | ⭐⭐ 不推荐（容易被绕过） |
| **长度限制** | 限制输入的最大/最小长度 | ⭐⭐⭐ 基础防线 |
| **类型验证** | 验证输入的类型（数字、邮箱、手机号等） | ⭐⭐⭐ 基础防线 |

> **黄金法则**：所有客户端验证都只能作为用户体验优化，**服务端必须重新验证一遍**。

---

### 6.5 输出编码（Output Encoding）

**定义**：在把数据输出到不同上下文（HTML、JavaScript、CSS、URL）时，进行相应的编码，防止数据被当作代码执行。

| 输出位置 | 编码方式 | 目的 |
|---------|---------|------|
| **HTML 内容** | HTML 实体编码（`&lt;` `&gt;` `&amp;`） | 防止 XSS |
| **JavaScript** | JavaScript 编码（Unicode 转义） | 防止 XSS |
| **CSS** | CSS 编码 | 防止 XSS |
| **URL 参数** | URL 编码（百分号编码） | 防止参数污染 |
| **SQL 查询** | 参数化查询（不是编码） | 防止 SQL 注入 |

> **记住**：输出到哪里，就用哪里的编码方式。一种编码不能通用所有场景。

---

### 6.6 失败安全（Fail Secure / Fail Safe）

**定义**：当系统出错或异常时，应该进入"安全状态"，而不是"不安全状态"。

| 场景 | 失败不安全 ❌ | 失败安全 ✅ |
|------|-------------|-----------|
| **门禁系统** | 断电后门一直开着 | 断电后门锁死 |
| **权限校验** | 异常时默认允许访问 | 异常时默认拒绝访问 |
| **防火墙** | 崩溃后所有流量通过 | 崩溃后阻断所有流量 |
| **错误处理** | 返回详细的错误栈信息 | 返回友好的错误提示 |

> **口诀**：出错时"关闭"，不要"打开"。

---

### 6.7 不要信任客户端（Never Trust the Client）

**定义**：所有来自客户端的数据、校验、逻辑，都只能作为参考，不能作为安全依据。

| 常见的错误认知 | 事实 |
|-------------|------|
| "前端做了校验就够了" | 前端校验可以被轻松绕过（改 JS、改请求） |
| "用户不知道这个 URL" | 接口可以被扫描和猜测 |
| "前端加密了就安全" | 前端加密的密钥和逻辑都在浏览器里 |
| "隐藏的表单字段用户改不了" | 可以用开发者工具或抓包修改 |

> **安全边界在服务端**——所有安全校验必须在服务端做。前端校验只是为了用户体验。

---

## 7. 常用防御措施

### 7.1 WAF（Web 应用防火墙）

| 项目 | 内容 |
|------|------|
| **全称** | Web Application Firewall |
| **作用** | 过滤 HTTP/HTTPS 流量，拦截常见的攻击（SQL 注入、XSS 等） |
| **部署位置** | 服务器之前，流量必经之路 |
| **类型** | 硬件 WAF、软件 WAF、云 WAF |
| **局限** | 有绕过可能，不能替代代码层面的防御 |

> **定位**：WAF 是补充防线，不是主要防御。有了 WAF 不代表就安全了，代码该怎么写还得怎么写。

---

### 7.2 参数化查询（Prepared Statement）

| 项目 | 内容 |
|------|------|
| **作用** | 防止 SQL 注入的最核心、最根本的方法 |
| **原理** | SQL 语句结构和数据分离，用户输入永远是数据，不会被当作代码执行 |
| **支持语言** | 几乎所有语言都支持（Java JDBC、Python DB-API、PHP PDO、Node.js 等） |
| **别名** | 预编译语句、Prepared Statement、Parameterized Query |

> **为什么有效？**：SQL 注入的本质是"用户输入改变了 SQL 的语义"。参数化查询保证了 SQL 结构在编译时就确定了，数据永远是数据。

---

### 7.3 CSP（内容安全策略）

| 项目 | 内容 |
|------|------|
| **全称** | Content Security Policy |
| **作用** | 限制页面能加载哪些资源、能执行哪些脚本，有效防止和缓解 XSS |
| **设置方式** | HTTP 响应头 `Content-Security-Policy` 或 `<meta>` 标签 |
| **效果** | 即使攻击者注入了脚本，也会被浏览器阻止 |

**示例配置**：
```http
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; object-src 'none'; base-uri 'self'; frame-ancestors 'none';
```

| 指令 | 作用 |
|------|------|
| `default-src 'self'` | 默认只允许加载同源资源 |
| `script-src 'self'` | 脚本只允许同源，内联脚本默认不执行 |
| `object-src 'none'` | 禁止插件（如 Flash） |
| `frame-ancestors 'none'` | 禁止被 iframe 嵌入（防点击劫持） |

---

### 7.4 HttpOnly Cookie

| 项目 | 内容 |
|------|------|
| **作用** | 禁止 JavaScript 读取 Cookie |
| **设置方式** | `Set-Cookie: name=value; HttpOnly` |
| **防御的攻击** | 缓解 XSS 窃取 Cookie 的危害 |
| **注意** | 不能防止 XSS 本身，只是减轻后果 |

> **为什么重要？**：XSS 最常见的危害就是窃取 Cookie 然后会话劫持。有了 HttpOnly，即使页面有 XSS，攻击者也拿不到 Cookie。

---

### 7.5 SameSite Cookie

| 项目 | 内容 |
|------|------|
| **作用** | 控制跨站请求是否携带 Cookie |
| **防御的攻击** | 主要防御 CSRF |
| **设置方式** | `Set-Cookie: name=value; SameSite=Lax` |

| 值 | 说明 | 安全性 |
|----|------|--------|
| `Strict` | 完全禁止跨站请求携带 Cookie | 🔒 最高（但体验可能受影响） |
| `Lax` | 大多数情况禁止，用户主动跳转时允许 | 🔒 高（推荐，平衡安全和体验） |
| `None` | 完全允许（需同时设置 Secure） | 🔒 低（需要时才用） |

---

### 7.6 CSRF Token

| 项目 | 内容 |
|------|------|
| **作用** | 验证请求是否来自本站，防止 CSRF 攻击 |
| **原理** | 每个请求携带一个随机 Token，服务端验证。Token 不在 Cookie 中，跨站请求拿不到 |
| **防御的攻击** | CSRF（跨站请求伪造） |
| **类型** | 表单隐藏字段、请求头、自定义 Cookie（配合双重提交） |

> **工作原理**：CSRF 攻击利用的是"Cookie 会自动携带"，但攻击者拿不到 Cookie 的内容，也拿不到页面上的 Token。所以如果请求必须携带一个 Cookie 之外的 Token，CSRF 就无法发动了。

---

### 7.7 防御措施对比总结

| 防御措施 | 主要防御的漏洞 | 防御层级 |
|---------|--------------|---------|
| **参数化查询** | SQL 注入 | 代码层（核心） |
| **输出编码** | XSS | 代码层（核心） |
| **CSP** | XSS、点击劫持 | 浏览器层 |
| **HttpOnly Cookie** | XSS（减轻危害） | 浏览器层 |
| **SameSite Cookie** | CSRF | 浏览器层 |
| **CSRF Token** | CSRF | 应用层 |
| **权限校验** | 越权访问 | 应用层（核心） |
| **WAF** | 多种注入类攻击 | 网络层（补充） |
| **HTTPS** | 中间人攻击、数据窃听 | 传输层 |

## 9. 自查清单

> 使用方法：对照以下清单，逐一检查你的 Web 应用/系统。打 ✅ 表示已完成，打 ❌ 表示需要改进。

### 9.1 认证与会话安全

- [ ] 密码使用强哈希算法存储（Argon2 / bcrypt / scrypt）
- [ ] 密码不是明文或弱哈希（MD5 / SHA-1）存储
- [ ] 登录失败有次数限制和锁定机制
- [ ] 登录后重新生成 Session ID
- [ ] Session ID 足够随机（密码学安全）
- [ ] Cookie 设置了 **HttpOnly** 属性
- [ ] Cookie 设置了 **Secure** 属性（HTTPS 环境）
- [ ] Cookie 设置了 **SameSite** 属性（Lax 或 Strict）
- [ ] 注销时服务端销毁 Session / Token
- [ ] 关键操作有二次验证（如修改密码、转账）
- [ ] 有密码强度策略（长度优先，禁止弱密码）

### 9.2 输入与输出安全

- [ ] 所有外部输入在服务端做验证
- [ ] 输入验证使用白名单（不是黑名单）
- [ ] SQL 查询使用参数化查询（不是字符串拼接）
- [ ] 输出到 HTML 时做 HTML 实体编码
- [ ] 输出到 JavaScript 时做 JS 编码
- [ ] 不调用系统命令；如果必须调用，使用参数化方式 + 输入验证
- [ ] 文件上传有多维校验（扩展名白名单 + 内容校验 + 重命名）
- [ ] 文件上传目录不可执行脚本

### 9.3 访问控制

- [ ] 每个接口在服务端验证用户权限
- [ ] 不依赖前端隐藏菜单/按钮来做权限控制
- [ ] 查询数据时带上用户身份条件（如 user_id）
- [ ] 默认拒绝访问，显式授权的才允许
- [ ] 普通用户不能访问管理员功能（垂直越权防护）
- [ ] 用户 A 不能访问用户 B 的数据（水平越权防护）
- [ ] 未登录用户不能访问需要登录的接口

### 9.4 安全配置

- [ ] 生产环境关闭调试模式
- [ ] 生产环境不返回详细错误信息（如栈轨迹、SQL 错误）
- [ ] 禁用了目录列表（目录浏览）
- [ ] 隐藏了服务器版本信息（Server 头、X-Powered-By）
- [ ] 默认密码已修改，默认账户已禁用
- [ ] 关闭了不必要的服务和端口
- [ ] 数据库账号使用最小权限
- [ ] Web 服务不以 root / 管理员权限运行

### 9.5 安全头

- [ ] 启用了 **HTTPS**（全站）
- [ ] 设置了 **HSTS** 头（Strict-Transport-Security）
- [ ] 设置了 **CSP** 头（Content-Security-Policy）
- [ ] 设置了 **X-Frame-Options** 头（或 CSP frame-ancestors）
- [ ] 设置了 **X-Content-Type-Options: nosniff**
- [ ] 设置了 **Referrer-Policy** 头

### 9.6 日志与监控

- [ ] 登录/登出有日志记录
- [ ] 关键操作有日志记录
- [ ] 权限变更有日志记录
- [ ] 日志包含时间、用户、IP、操作、结果
- [ ] 日志中的敏感信息已脱敏
- [ ] 日志集中存储，有备份
- [ ] 有告警机制（异常登录、大量失败请求等）
- [ ] 定期审计和分析日志

### 9.7 供应链安全

- [ ] 定期扫描依赖漏洞（SCA 工具）
- [ ] 及时更新有漏洞的依赖
- [ ] 尽量减少不必要的依赖
- [ ] 锁定依赖版本（lockfile）
- [ ] 不使用已废弃/不再维护的依赖

## 11. 常见误区

### ❌ 误区 1："有 WAF 就安全了"

**事实**：WAF 是补充防线，有很多绕过技巧。WAF 不能替代代码层面的安全防护。该用参数化查询还是得用，该做权限校验还是得做。

---

### ❌ 误区 2："前端做了校验就够了"

**事实**：前端校验可以被轻松绕过（修改 JS、抓包改请求、直接调用接口）。所有安全校验必须在**服务端**再做一遍。前端校验只是为了用户体验。

---

### ❌ 误区 3："会用工具就是会安全"

**事实**：工具只是手段，原理才是核心。会用 sqlmap 不等于会 SQL 注入，会用 Burp 不等于会渗透测试。理解原理、能思考、能变通，才是真正的能力。

---

### ❌ 误区 4："用了框架就不会有漏洞了"

**事实**：框架能减少很多低级错误，但用得不对仍然会有漏洞。比如 ORM 用原生查询、模板引擎关闭自动转义、权限框架配置错误等。框架是工具，安全还是得靠人。

---

### ❌ 误区 5："漏洞都是黑客挖出来的，和开发没关系"

**事实**：大多数漏洞是代码写出来的。安全不是安全团队一个团队的事，开发人员是安全的第一道防线。写安全的代码，比事后修漏洞成本低得多。

---

### ❌ 误区 6："安全是上线后才需要考虑的事"

**事实**：安全越晚介入，修复成本越高。设计阶段发现一个安全问题，修复成本可能是上线后的 1/100。这就是"安全左移"的意义——在设计和开发阶段就考虑安全。

---

### ❌ 误区 7："SQL 注入已经过时了"

**事实**：虽然 OWASP 排名有所下降，但 SQL 注入仍然非常常见。很多老系统、维护不善的系统、以及写得不好的新系统，都还有 SQL 注入。而且注入类漏洞（包括 XSS、命令注入等）的原理是相通的。

---

### ❌ 误区 8："HTTPS = 绝对安全"

**事实**：HTTPS 只保证了传输层的安全（防窃听、防篡改），但应用层的漏洞（SQL 注入、XSS、越权等）HTTPS 管不了。HTTPS 是必要条件，但不是充分条件。

---

### ❌ 误区 9："漏洞越复杂越厉害"

**事实**：现实中最常见、危害最大的往往是"简单"的漏洞——SQL 注入、XSS、越权访问。不是因为它们技术含量高，而是因为太多人犯这些低级错误。把基础漏洞防住，就能解决 80% 的安全问题。

---

### ❌ 误区 10："安全和我（开发/运维）没关系"

**事实**：安全是每个人的责任。开发写出安全的代码、运维做好安全配置、产品设计安全的功能——安全是整个团队的事，不是只有安全团队才需要关心。

---

## 12. 面试高频问答

### 基础概念类

**Q1：什么是同源策略？什么是同源？**

> 同源策略是 Web 安全的基石，限制不同源的文档和脚本之间的交互。两个 URL 属于同源需要同时满足三个条件：协议相同、主机相同、端口相同。

**Q2：Cookie、Session、Token 的区别？**

> - Cookie 是客户端存储机制，服务器通过 Set-Cookie 设置，浏览器后续请求自动携带。
> - Session 是服务端存储机制，用 Session ID 标识用户，Session ID 通常存在 Cookie 中。
> - Token（如 JWT）是无状态的认证方式，服务端不需要存储，Token 自包含用户信息，通过签名验证。

**Q3：CORS 是什么？简单请求和预检请求的区别？**

> CORS 是跨域资源共享，是一种放宽同源策略的机制，让服务器可以指定哪些源可以访问它的资源。
> - 简单请求：GET/HEAD/POST + 简单 Content-Type，直接发请求，看响应头。
> - 预检请求：PUT/DELETE、自定义 Header、JSON 等情况，先发 OPTIONS 请求"问"服务器允不允许，再发真实请求。

---

### 漏洞原理类

**Q4：SQL 注入的原理是什么？怎么防御？**

> 原理：用户输入被直接拼接到 SQL 语句中，改变了 SQL 的语义，用户输入被当作代码执行。
> 核心防御：参数化查询（预编译语句），让 SQL 结构和数据分离。
> 辅助防御：输入白名单验证、最小权限原则、WAF。

**Q5：XSS 有哪几种类型？区别是什么？怎么防御？**

> 三种类型：
> - 反射型：脚本在 URL 中，后端直接输出，需诱导点击。
> - 存储型：脚本存在数据库，所有访问用户都中招，危害最大。
> - DOM 型：前端 JS 直接把用户输入写到 DOM 中，不经过后端。
> 防御：输出编码（核心）、输入验证、CSP、HttpOnly Cookie。

**Q6：CSRF 的原理是什么？怎么防御？**

> 原理：利用用户已登录的身份，诱导用户访问恶意页面，自动发起伪造请求，以用户的名义执行操作。核心是利用 Cookie 自动携带的特性。
> 防御：CSRF Token（最有效）、SameSite Cookie、验证 Referer/Origin、关键操作二次验证。

**Q7：SQL 注入和 XSS 有什么共同点和不同点？**

> 共同点：都是注入类漏洞，本质都是"用户输入被当作代码执行"，根本原因都是代码和数据没有分离。
> 不同点：
> - SQL 注入注入的是 SQL 语句，发生在后端数据库层。
> - XSS 注入的是脚本代码，发生在浏览器端。
> - 防御方式不同：SQL 注入用参数化查询，XSS 用输出编码。

**Q8：越权访问有哪几种类型？怎么防御？**

> - 水平越权：同级用户之间越权（如 A 看 B 的订单）。
> - 垂直越权：低权限用户越权访问高权限功能（如普通用户访问管理员后台）。
> - 未授权访问：完全不需要认证就能访问。
> 防御：服务端统一权限校验、默认拒绝、最小权限原则、查询时带用户条件。

---

### 防御措施类

**Q9：参数化查询为什么能防 SQL 注入？**

> 参数化查询将 SQL 语句结构和数据分离。SQL 语句在编译时就确定了结构，参数位置用占位符表示。用户输入作为参数传入，永远是数据，不会改变 SQL 语句的结构，所以无法注入。

**Q10：CSP 是什么？有什么作用？**

> CSP（内容安全策略）是浏览器的安全机制，通过 HTTP 头或 meta 标签设置，限制页面能加载哪些资源、能执行哪些脚本。可以有效防止和缓解 XSS 攻击，即使攻击者注入了脚本，也会被浏览器阻止。

**Q11：HttpOnly 和 SameSite 的作用分别是什么？**

> - HttpOnly：禁止 JavaScript 读取 Cookie，防止 XSS 窃取 Cookie（减轻 XSS 的危害）。
> - SameSite：控制跨站请求是否携带 Cookie，主要用于防御 CSRF 攻击。

**Q12：CSRF Token 为什么能防 CSRF？**

> CSRF 攻击利用的是"Cookie 会自动携带，但攻击者拿不到 Cookie 的内容"。CSRF Token 不放在 Cookie 里，而是放在表单或请求头中，跨站请求拿不到这个 Token，所以无法伪造有效的请求。服务端验证 Token 是否匹配，不匹配就拒绝。

---

### 设计原则类

**Q13：什么是最小权限原则？举个例子。**

> 最小权限原则是指每个用户、程序、服务只拥有完成其任务所必需的最小权限。比如 Web 应用的数据库账号只给 SELECT/INSERT/UPDATE 权限，不给 DROP/ALTER 权限。这样即使应用被攻破，攻击者也不能删表或修改表结构。

**Q14：什么是纵深防御？举个例子。**

> 纵深防御是指多层设防，不是只靠一道防线。即使一层被突破，还有下一层。比如防 XSS：输入验证 → 输出编码 → CSP → HttpOnly Cookie，每一层都是一道防线，一层被突破还有下一层兜底。

**Q15：为什么不能信任客户端？**

> 因为客户端的所有东西都在用户手里——JS 代码可以改、请求可以抓包改、页面可以调试。前端校验、前端加密、前端隐藏的入口，都可以被绕过。安全边界在服务端，所有安全校验必须在服务端做。

---

### 综合类

**Q16：如果让你设计一个安全的登录系统，你会考虑哪些方面？**

> - 密码存储：使用 bcrypt/Argon2 等慢哈希算法，加盐
> - 密码强度：强密码策略，长度优先
> - 登录防护：失败次数限制、验证码、IP 限流
> - 会话安全：Session ID 足够随机、登录后重新生成、HttpOnly + Secure + SameSite
> - 多因素认证：关键账号支持 MFA
> - 日志审计：登录日志、异常登录告警
> - 密码找回：安全的重置链接（随机、一次性、限时）
> - HTTPS：全程加密传输

**Q17：OWASP Top 10 你知道哪些？挑一个详细说说。**

> （按 OWASP Top 10:2025 回答）
> 1. 访问控制失效 2. 安全配置错误 3. 软件供应链失效 4. 加密机制失效 5. 注入
> 6. 不安全设计 7. 认证失效 8. 软件或数据完整性失效 9. 安全日志与告警失效 10. 特殊情况处理不当
>
> （以访问控制失效为例详细说明）
> 访问控制失效排名第一，连续四届榜首。核心是用户能访问权限外的资源，包括水平越权、垂直越权、未授权访问、SSRF 等。根本原因是服务端没有正确验证权限，依赖前端控制。防御要点是服务端统一权限校验、默认拒绝、最小权限原则。

**Q18：HTTPS 的作用是什么？有了 HTTPS 就安全了吗？**

> HTTPS 的作用是加密传输，防止数据在传输过程中被窃听和篡改，同时验证服务器身份。
> 但有了 HTTPS 不代表就绝对安全。HTTPS 只解决了传输层的问题，应用层的漏洞（SQL 注入、XSS、越权等）HTTPS 管不了。HTTPS 是必要条件，但不是充分条件。

---

> **最后**：
> Web 安全是一个广阔且不断发展的领域。
> 掌握基础概念和核心漏洞原理是第一步，
> 更重要的是建立安全思维——
> 永远假设输入是恶意的，永远不相信客户端，
> 永远用最小权限和纵深防御来设计系统。
>
> 安全之路没有捷径，但每一步都算数。
