## 一、安全的核心目标

### 1.1 CIA 三元组

**CIA 三元组（CIA Triad）** 是信息安全的三大核心目标，是所有安全工作的出发点和衡量标准。

| 属性 | 英文 | 定义 | 实际含义 |
|------|------|------|---------|
| **机密性** | Confidentiality | 确保信息不被未授权的个人、实体或过程获取或泄露 | "不该看的人看不到" |
| **完整性** | Integrity | 确保信息准确、完整，未被未经授权地篡改 | "数据没有被改过，是真的" |
| **可用性** | Availability | 确保授权用户在需要时能够正常访问和使用信息系统 | "想用的时候能用" |

> **记忆口诀**：**CIA** — 每个字母对应一个核心目标。
> 这三个目标相互关联、有时互相矛盾（比如增加安全性可能降低可用性），需要根据业务场景权衡。

#### 机密性（Confidentiality）

| 维度 | 说明 |
|------|------|
| **典型破坏场景** | 数据泄露、SQL 注入拖库、内部人员窃取、未授权访问、明文传输被窃听 |
| **防护手段** | 加密（传输加密 + 存储加密）、访问控制、身份认证、数据脱敏、DLP（数据防泄漏）、最小权限原则 |
| **实际案例** | 某公司数据库被 SQL 注入，用户信息泄露；内部员工导出客户数据倒卖 |

#### 完整性（Integrity）

| 维度 | 说明 |
|------|------|
| **典型破坏场景** | 数据被篡改、文件被恶意修改、配置被更改、中间人攻击注入内容、越权修改 |
| **防护手段** | 哈希校验、数字签名、消息认证码（MAC）、访问控制、版本控制、审计日志、备份与校验 |
| **实际案例** | 黑客入侵网站篡改首页；中间人攻击在 HTTP 响应中注入恶意代码；内鬼改订单金额 |

#### 可用性（Availability）

| 维度 | 说明 |
|------|------|
| **典型破坏场景** | DDoS 攻击、勒索软件加密数据、服务器宕机、网络中断、硬件故障、配置错误 |
| **防护手段** | 高可用架构（集群/冗余）、DDoS 防护、备份与灾难恢复、负载均衡、补丁管理、容量规划 |
| **实际案例** | 大型 DDoS 导致网站无法访问；勒索软件加密医院系统，门诊停摆 |

### 1.2 扩展属性

CIA 三元组是最核心的三个目标，现代安全体系还扩展出以下重要属性：

| 属性 | 英文 | 定义 | 说明 |
|------|------|------|------|
| **不可否认性** | Non-repudiation | 确保发送方无法否认自己发送过信息或执行过操作 | 数字签名是主要实现方式 |
| **真实性** | Authenticity | 确保信息来源是真实的、身份是真实的 | 身份认证、证书验证 |
| **可审计性** | Accountability | 用户的行为可以被追溯和审计 | 审计日志、操作留痕 |
| **可控性** | Controllability | 对信息的传播和内容具有控制能力 | 访问控制、数据防泄漏 |

> **与 CIA 的关系**：
> - 机密性 + 完整性 → 不可否认性（数字签名同时提供认证和完整性）
> - 真实性 → 身份认证是访问控制的前提
> - 可审计性 → 是其他目标的保障，出了问题能追溯
>
> 有些模型用 **Parkerian Hexad（帕克六要素）** 扩展为：机密性、可用性、完整性、真实性、不可否认性、效用（Utility）。

## 二、安全模型与原则

### 2.1 纵深防御（Defense in Depth）

**纵深防御**，也叫**分层防御**，是指在多个层面部署安全控制措施，避免单点失效。即使某一层被攻破，还有下一层防线。

```
数据层 → 应用层 → 主机层 → 网络层 → 边界层 → 物理层 → 管理层
  ↑                                                              ↑
  └──────────── 每一层都有安全控制，层层设防 ────────────────────┘
```

#### 各层典型控制措施

| 层次 | 控制措施举例 |
|------|-------------|
| **数据层** | 加密、脱敏、数据防泄漏（DLP）、备份校验 |
| **应用层** | WAF、代码安全、输入验证、参数化查询、安全编码 |
| **主机层** | 主机防火墙、入侵检测（HIDS）、终端防护（EDR）、补丁管理 |
| **网络层** | 网络分段、VLAN、访问控制列表（ACL）、网络监控（NIDS） |
| **边界层** | 防火墙、VPN、DDoS 防护、IPS/IDS |
| **物理层** | 门禁、监控、机房安全、介质销毁 |
| **管理层** | 安全策略、培训、制度、审计、应急预案 |

> **核心思想**：
> - 没有任何单一控制是完美的
> - 攻击者需要突破多层防线才能到达目标
> - 即使某一层失效，其他层仍然提供保护
> - 增加攻击者的成本和难度，降低成功的概率

**现实比喻**：古代城池的防御——护城河、城墙、城门、瓮城、内城、禁卫军……一层又一层，攻破一道还有一道。

### 2.2 零信任（Zero Trust）

**零信任（Zero Trust）** 的核心原则是：**"永不信任，始终验证"（Never Trust, Always Verify）**。

传统安全模型默认"内部网络是可信的"，只要进了内网就可以横向移动。零信任彻底抛弃了这个假设。

#### 零信任三大原则（NIST SP 800-207）

| 原则 | 英文 | 说明 |
|------|------|------|
| **显式验证** | Verify Explicitly | 每次访问都要认证和授权，不因为"在内网"就信任 |
| **使用最低特权访问** | Use Least Privilege Access | 只给完成任务需要的最小权限，且只有必要的时间 |
| **假定违规** | Assume Breach | 假设已经被攻破，处处设防，最小化爆炸半径 |

#### 零信任的关键技术

| 技术 | 作用 |
|------|------|
| **身份认证与授权** | MFA、SSO、动态访问控制 |
| **微隔离（Micro-segmentation）** | 每个工作负载之间都有访问控制，防止横向移动 |
| **软件定义边界（SDP）** | 先认证后连接，网络资源默认不可见 |
| **持续验证** | 不只是登录时验证，而是持续评估风险、动态调整权限 |
| **最小权限** | 基于角色（RBAC）/ 属性（ABAC）的精细化权限管理 |

> **零信任 ≠ 一个产品**：
> 零信任是一种理念和架构，不是买一个"零信任设备"就能实现的。
> 它需要从网络、身份、应用、数据等多个层面整体设计和演进。

### 2.3 最小权限原则

**最小权限原则（Principle of Least Privilege, PoLP）**：每个用户、程序或进程只应该被授予完成其预定任务所必需的**最小权限**。

```
权限分配原则：
  ❌ "为了方便，先给所有权限再说"
  ✅ "只给刚好够用的权限，不够再加"
```

| 应用场景 | 错误做法 | 正确做法 |
|---------|---------|---------|
| **用户权限** | 所有人都是管理员 | 按角色分配最小权限，定期审计 |
| **应用数据库账号** | 应用用 root/sa 连接数据库 | 专用账号，只给 SELECT/INSERT/UPDATE |
| **服务账号** | 服务用 Local System / root 运行 | 专用低权限账号，只给需要的权限 |
| **API 权限** | 一个 Token 能访问所有接口 | 细粒度权限，按需要授权 |
| **容器权限** | 容器用 root 运行，挂载宿主目录 | 非 root 用户，只读文件系统，必要的挂载 |

**为什么重要？**
- 账号被攻破时，攻击者只能拿到该账号的权限（降低影响范围）
- 内部人员的误操作和恶意操作被限制
- 满足合规要求（等保、PCI-DSS 等都要求最小权限）

> **相关原则**：
> - **最小功能原则**：系统只启用需要的功能，关闭不需要的（减少攻击面）
> - **最小暴露原则**：对外暴露的接口、服务、端口越少越好

### 2.4 共享责任模型（Shared Responsibility Model）

在云计算时代，安全责任由云服务商和客户共同承担。不同云服务模式下，责任划分不同。

| 安全层面 | 本地部署 (On-premise) | IaaS | PaaS | SaaS |
|---------|---------------------|------|------|------|
| **数据** | 客户 | 客户 | 客户 | 客户 |
| **应用** | 客户 | 客户 | 客户 | 云厂商 |
| **操作系统** | 客户 | 客户 | 云厂商 | 云厂商 |
| **虚拟化层** | 客户 | 云厂商 | 云厂商 | 云厂商 |
| **物理服务器** | 客户 | 云厂商 | 云厂商 | 云厂商 |
| **物理网络** | 客户 | 云厂商 | 云厂商 | 云厂商 |
| **机房物理安全** | 客户 | 云厂商 | 云厂商 | 云厂商 |

```
客户责任越来越少 →
本地部署     IaaS      PaaS      SaaS
  │          │         │         │
  ├──────────┤         │         │
  │ 客户负责  │ 云厂商负责的部分  │
  └──────────┴─────────┴─────────┘
```

**各模式说明**：
- **本地部署（On-premise）**：什么都是你自己负责
- **IaaS（基础设施即服务）**：云厂商管物理设施和虚拟化，你管从 OS 到应用的一切（如 AWS EC2、阿里云 ECS）
- **PaaS（平台即服务）**：云厂商管基础设施和运行平台，你只管应用和数据（如 Heroku、阿里云 RDS）
- **SaaS（软件即服务）**：云厂商管几乎所有技术层面，你只管使用和配置（如 Office 365、钉钉、企业微信）

> **重要提醒**：
> 云不是更安全，也不是更不安全，而是**责任不同**。
> 很多人误以为"上云了安全就归云厂商管"，结果数据配置错误、权限没管好导致泄露——这些是客户自己的责任。
> **"云安全是共同的责任"——数据和配置永远是客户的责任。**

### 2.5 攻防不对称

**攻防不对称（Asymmetry of Offense and Defense）**：攻击者只需要找到一个漏洞就能成功，而防守者需要防御所有可能的攻击面。

| 维度 | 攻击者 | 防守者 |
|------|--------|--------|
| **成本** | 找到一个弱点 | 防御所有弱点 |
| **时间** | 可以慢慢研究、慢慢试 | 需要 7×24 小时防御 |
| **收益** | 攻破一个点就能获利 | 所有点都防住才算成功 |
| **选择** | 可以选最薄弱的环节攻击 | 每个环节都必须防 |
| **创新** | 随时可以用新的攻击方式 | 需要不断学习和更新防御 |

> **"攻击者只需要对一次，防守者需要每次都对。"**
>
> 这就是为什么安全难做——这是一场天然不公平的战争。
> 防守者的应对策略：纵深防御、威胁建模、安全左移（从源头减少漏洞）、假设被攻破后的检测与响应能力。

### 2.6 其他重要安全原则

| 原则 | 英文 | 说明 |
|------|------|------|
| **职责分离** | Separation of Duties (SoD) | 一个人不能完成高风险操作的所有步骤（如出纳和会计不能是同一个人） |
| **失败安全** | Fail Secure / Fail Closed | 系统故障时应该进入安全状态（如门禁断电应该锁闭，而不是打开） |
| **经济适用原则** | Economy of Mechanism | 安全设计要简单，越简单越不容易出错（KISS 原则） |
| **完全仲裁** | Complete Mediation | 对每一次访问都进行权限检查，不能缓存结果就不再验证 |
| **开放设计** | Open Design | 安全不依赖于设计的保密（Kerckhoffs 原则在系统设计中的体现） |
| **心理可接受性** | Psychological Acceptability | 安全措施不能太影响用户体验，否则用户会绕过它 |
| **安全左移** | Shift Left | 把安全工作前移到开发早期（设计、编码阶段），越往左成本越低 |
| **默认安全** | Secure by Default | 默认配置就是安全的，不需要用户手动加固 |

## 三、安全控制类型

### 3.1 按功能分类

| 类型 | 英文 | 定义 | 目的 | 举例 |
|------|------|------|------|------|
| **预防性控制** | Preventive | 阻止安全事件发生 | 防患于未然 | 防火墙、访问控制、加密、安全培训、门锁 |
| **检测性控制** | Detective | 发现已经发生的安全事件 | 及时发现 | 入侵检测系统（IDS）、日志监控、审计、安全警报 |
| **纠正性控制** | Corrective | 减轻安全事件的影响，恢复正常 | 止损修复 | 备份恢复、补丁、杀毒软件、灾难恢复计划 |
| **威慑性控制** | Deterrent | 阻止攻击者尝试攻击（心理威慑） | 不敢动手 | 监控摄像头、警告标语、审计公告、法律法规 |
| **补偿性控制** | Compensating | 替代或补充主要控制的不足 | 替补方案 | 当无法实施主要控制时的替代方案（如用监控补偿门禁不足） |

> **控制组合**：
> 一个好的安全体系应该同时包含多种类型的控制。
> 例如：防火墙（预防）+ IDS（检测）+ 备份恢复（纠正）+ 安全标语（威慑）+ 替代方案（补偿）。
>
> 只有预防性控制是不够的——没有什么预防措施是 100% 有效的。检测和纠正同样重要。

### 3.2 按形态分类

| 类型 | 英文 | 定义 | 举例 |
|------|------|------|------|
| **技术控制** | Technical / Logical | 使用技术手段实现的安全控制 | 防火墙、加密、身份认证、访问控制列表、入侵检测 |
| **管理控制** | Administrative / Managerial | 通过政策、流程、人员管理实现的控制 | 安全策略、安全培训、风险评估、审计、人员背景调查 |
| **物理控制** | Physical | 物理层面的安全控制 | 门禁、监控摄像头、保安、机房锁、灭火器、碎纸机 |

**三者关系**：

```
管理控制（策略、制度、流程）
    │ 指导和规范
    ▼
技术控制 + 物理控制（具体实施手段）
```

管理控制是方向，技术和物理控制是手段。没有管理控制的技术控制是混乱的，没有技术和物理控制的管理控制是空话。

### 3.3 控制选择原则

1. **成本效益原则**：控制措施的成本不能超过它所保护资产的价值
2. **风险驱动**：根据风险评估结果选择控制措施，优先处理高风险
3. **分层防御**：多种控制结合，避免单点依赖
4. **可验证性**：控制是否有效，应该能被测量和验证
5. **用户体验**：不能严重影响业务正常运行和用户体验（否则用户会绕过）

## 四、风险管理基础

### 4.1 基本概念

| 概念 | 英文 | 定义 | 举例 |
|------|------|------|------|
| **资产** | Asset | 对组织有价值的任何东西（数据、系统、设备、人员、声誉） | 客户数据库、Web 服务器、源代码、品牌声誉 |
| **威胁** | Threat | 可能对资产造成损害的潜在原因（人为或自然） | 黑客攻击、病毒、火灾、地震、内部人员、硬件故障 |
| **脆弱性** | Vulnerability | 资产中可以被威胁利用的弱点 | 未打补丁的系统、弱密码、配置错误、SQL 注入漏洞 |
| **风险** | Risk | 威胁利用脆弱性对资产造成损害的可能性和影响 | "黑客利用 SQL 注入漏洞窃取客户数据"的风险 |
| **影响** | Impact | 安全事件发生后造成的损失（财务、声誉、合规） | 数据泄露导致客户流失、罚款、股价下跌 |
| **可能性** | Likelihood | 安全事件发生的概率 | 高/中/低，或具体的数值 |

**关系图**：

```
威胁  →  利用  →  脆弱性  →  导致  →  风险（影响资产）

          风险 = 可能性 × 影响
         （更完整的公式：风险 = 威胁 × 脆弱性 × 资产价值）
```

### 4.2 风险公式

#### 简化公式
```
风险 = 可能性 × 影响
Risk = Likelihood × Impact
```

#### 更完整的公式
```
风险 = 资产价值 × 威胁可能性 × 脆弱性严重程度 × 影响
```

#### 定性评估（常用）

用"高、中、低"等定性级别评估：

| 影响 \ 可能性 | 低 | 中 | 高 |
|-------------|----|----|----|
| **高** | 中 | 高 | 极高 |
| **中** | 低 | 中 | 高 |
| **低** | 低 | 低 | 中 |

### 4.3 风险处置策略

| 策略 | 英文 | 说明 | 适用场景 | 举例 |
|------|------|------|---------|------|
| **风险规避** | Risk Avoidance | 消除风险来源，不做有风险的事 | 风险太高，得不偿失 | 不收集敏感数据就不会有数据泄露风险 |
| **风险转移** | Risk Transfer | 把风险转移给第三方 | 自己处理不划算/不专业 | 买保险、外包安全服务、上云（部分责任转移） |
| **风险减轻** | Risk Mitigation / Reduction | 采取措施降低风险 | 大部分风险都用这种方式 | 打补丁、装防火墙、加密、做备份 |
| **风险接受** | Risk Acceptance | 认识到风险但选择接受 | 风险很小，或者处理成本远大于损失 | 低风险的小系统，接受现状 |

> **选择原则**：
> - 高风险：优先考虑规避或减轻
> - 中风险：减轻或转移
> - 低风险：接受或少量减轻
> - 任何风险的处置决策都应该有文档记录和管理层批准

### 4.4 风险评估流程

```
1. 资产识别与估值
   ↓
2. 威胁识别（有哪些威胁？来自哪里？）
   ↓
3. 脆弱性识别（有哪些漏洞和弱点？）
   ↓
4. 风险分析（可能性多大？影响多大？）
   ↓
5. 风险评价（风险等级？是否可接受？）
   ↓
6. 风险处置（规避/转移/减轻/接受？）
   ↓
7. 监控与评审（持续监控，定期重评估）
```

**风险评估类型**：
- **定性评估**：用高/中/低等级别，速度快，主观性强
- **定量评估**：用具体数值（货币、概率），精确但复杂
- **半定量评估**：结合两者，给级别赋值

## 五、安全架构基础

### 5.1 安全域划分与边界防护

**安全域（Security Zone / Security Domain）**：具有相同安全级别和信任级别的资产组成的区域。

```
                边界防火墙
                    │
  ┌─────────────────┼─────────────────┐
  │          DMZ 区（非军事区）        │
  │   Web 服务器、邮件服务器、DNS      │
  │   （对外提供服务，最容易被攻击）     │
  └─────────────────┼─────────────────┘
                    │  内部防火墙
  ┌─────────────────┼─────────────────┐
  │          内部网络区                 │
  │   应用服务器、数据库、办公终端       │
  │   （信任度较高，但也要防内部威胁）   │
  └─────────────────┼─────────────────┘
                    │  严格访问控制
  ┌─────────────────┼─────────────────┐
  │          核心数据区                 │
  │   核心数据库、认证系统、管理平台     │
  │   （最高安全级别，严格限制访问）     │
  └───────────────────────────────────┘
```

**设计原则**：
1. **分级防护**：安全级别不同的资产放在不同的安全域
2. **边界防护**：安全域之间有明确的边界和访问控制
3. **最小化暴露**：高价值资产尽量少暴露，放在最内层
4. **纵深防御**：从外到内一层比一层严格

### 5.2 攻击面与攻击链

#### 攻击面（Attack Surface）

攻击面是系统中可以被攻击者利用的所有入口点的总和。

| 攻击面类型 | 举例 |
|-----------|------|
| **网络攻击面** | 开放的端口、运行的服务、网络协议 |
| **软件攻击面** | 应用接口、输入点、功能模块、第三方库 |
| **物理攻击面** | 机房、设备、USB 接口、门禁 |
| **人员攻击面** | 员工、供应商、客服（社会工程学攻击） |

**减少攻击面**：
- 关闭不需要的服务和端口
- 禁用不需要的功能
- 移除不必要的代码和组件
- 最小化权限
- 减少对外暴露的接口

> **安全设计的黄金法则之一：攻击面越小越好。**

#### 攻击链（Kill Chain）

**网络杀伤链（Cyber Kill Chain）** 是洛克希德·马丁公司提出的攻击模型，描述了攻击者从开始到完成攻击的七个阶段：

```
1. 侦察 (Reconnaissance)
      ↓ 收集目标信息（端口扫描、OSINT 等）
2. 武器化 (Weaponization)
      ↓ 制作攻击工具（带漏洞的文档、木马等）
3. 投递 (Delivery)
      ↓ 把武器送到目标（钓鱼邮件、水坑攻击等）
4. 利用 (Exploitation)
      ↓ 利用漏洞执行代码（漏洞利用、社会工程学）
5. 安装 (Installation)
      ↓ 安装后门/木马，持久化控制
6. 命令与控制 (Command & Control, C2)
      ↓ 建立 C2 通道，远程控制
7. 行动 (Actions on Objectives)
      ↓ 达到最终目的（窃取数据、破坏、勒索等）
```

**防守意义**：
- 每一个阶段都是防守的机会
- 在越前面的阶段拦截，损失越小
- 检测到第 1-2 阶段 = 还没出事，检测到第 7 阶段 = 已经出事了

### 5.3 信任边界与数据流

**信任边界（Trust Boundary）**：不同信任级别的区域之间的分界线。数据穿过信任边界时，需要进行验证和控制。

```
高信任区（内部网络）
    │
    │  ← 信任边界（防火墙、网关）
    │
低信任区（互联网）
```

**常见的信任边界**：
- 互联网 ↔ 企业内网
- 应用 ↔ 数据库
- 前端 ↔ 后端
- 用户输入 ↔ 系统内部
- 普通用户区 ↔ 管理员区

**数据流安全**：
- 数据穿过信任边界时必须验证（输入验证、身份认证）
- 高敏感数据在低信任区域传输需要加密
- 不要信任来自信任边界外的任何数据（"永远不要相信用户输入"）

### 5.4 安全设计原则

| 原则 | 英文 | 说明 | 示例 |
|------|------|------|------|
| **失败安全** | Fail Secure / Safe by Default | 系统故障或异常时进入安全状态 | 门禁断电应该锁闭（fail closed） |
| **职责分离** | Separation of Duties | 关键操作由多人分担，防止单点舞弊 | 财务审批和付款不能是同一个人 |
| **经济适用** | Economy of Mechanism | 设计尽量简单，简单=安全 | 安全机制越简单，越不容易出 bug |
| **完全仲裁** | Complete Mediation | 每次访问都检查权限，不要偷懒缓存 | 不能因为上次验证过就跳过这次 |
| **最小公共机制** | Least Common Mechanism | 减少共享资源，防止通过共享资源攻击 | 用户之间的数据隔离 |
| **心理可接受性** | Psychological Acceptability | 安全措施不能太反人类 | 密码规则太复杂用户会写在便利贴上 |
| **默认安全** | Secure by Default | 出厂/安装默认配置就是安全的 | 新系统默认强密码、关闭不必要的服务 |
| **纵深防御** | Defense in Depth | 多层防护，避免单点失效 | 网络层 + 应用层 + 数据层都有防护 |

## 六、密码学与安全概念的关系

### 6.1 密码学在安全体系中的位置

密码学是很多安全机制的**技术基础**，但不是全部。

```
安全体系
├── 机密性 ← 加密（对称/非对称）
├── 完整性 ← 哈希、消息认证码
├── 认证 ← 数字签名、证书
├── 不可否认性 ← 数字签名
├── 密钥管理
├── 安全协议（TLS、SSH、IPsec...）
└── 其他：访问控制、防火墙、审计、物理安全...
```

> 密码学提供了很多底层的安全原语（primitive），这些原语通过协议和系统组合起来，实现更高层的安全目标。
> 但密码学不是万能的——访问控制、安全管理、物理安全等同样重要。

### 6.2 数据的三种状态与加密

| 数据状态 | 英文 | 说明 | 主要防护手段 |
|---------|------|------|-------------|
| **静态数据** | Data at Rest | 存储在磁盘、数据库、备份中的数据 | 磁盘加密、数据库加密（TDE）、文件加密、列级加密 |
| **传输中数据** | Data in Transit / Data in Motion | 网络传输中的数据 | TLS/SSL、VPN、IPsec |
| **使用中数据** | Data in Use | 内存中正在处理的数据 | 同态加密（FHE，还在发展）、安全飞地（TEE/SEV/SGX）、内存加密 |

> **"使用中数据"的保护**是当前密码学和系统安全的前沿领域。
> 传统加密能保护静态和传输中的数据，但数据被使用时必须解密到内存中——这时候如果内存被攻破（冷启动攻击、内存泄露、恶意管理员），数据还是会泄露。
> 全同态加密、可信执行环境（TEE）等技术正在解决这个问题。

### 6.3 对称加密与非对称加密的角色

| 特性 | 对称加密 | 非对称加密 |
|------|---------|-----------|
| 密钥 | 同一个密钥 | 公钥 + 私钥 |
| 速度 | 快（100~1000x） | 慢 |
| 适合的数据量 | 大 | 小（通常只加密对称密钥） |
| 机密性 | ✅ | ✅（公钥加密，私钥解密） |
| 认证/不可否认 | ❌（需要配合 MAC） | ✅（数字签名） |
| 密钥分发 | ❌（困难） | ✅（公钥可以公开） |
| 主要用途 | 加密大量数据 | 密钥交换、数字签名、身份认证 |

**实际系统中两者配合使用（混合加密）**：
- 用非对称加密交换/加密对称密钥
- 用对称密钥加密实际的大量数据
- TLS、PGP、微信加密等几乎所有实际系统都是这样

### 6.4 数字签名与证书在安全体系中的位置

数字签名提供**认证 + 完整性 + 不可否认性**，是很多安全机制的基础：

| 应用 | 作用 |
|------|------|
| **TLS/HTTPS** | 验证网站身份，防止中间人攻击 |
| **代码签名** | 验证软件来源和完整性，防止被篡改植入恶意代码 |
| **文档签名** | 电子签名、电子合同、不可否认性 |
| **DNSSEC** | 验证 DNS 响应真实性，防止 DNS 欺骗 |
| **区块链** | 交易签名、身份验证 |
| **软件更新** | 验证更新包确实来自官方 |

**PKI（公钥基础设施）** 是让数字签名可信的体系——它解决的问题是："我怎么知道这个公钥真的是那个人的？"答案是：由可信的第三方（CA）用证书来证明。

## 七、安全治理概念

### 7.1 GRC：治理、风险与合规

**GRC（Governance, Risk Management, and Compliance）** 是三个相关但不同的概念的组合：

| 概念 | 英文 | 定义 | 说明 |
|------|------|------|------|
| **治理** | Governance | 确保组织目标被正确实现的顶层框架和机制 | "做正确的事"——方向和决策 |
| **风险管理** | Risk Management | 识别、评估、处置风险的流程 | "管理不确定性"——风险识别与控制 |
| **合规** | Compliance | 确保组织遵守法律法规、标准和内部政策 | "按规矩办事"——符合要求 |

**三者关系**：
```
治理（顶层设计）
  ├── 风险管理（核心手段）
  │     └── 合规（风险的一种：合规风险）
  └── 合规（治理要求的一部分）
```

治理是顶层，风险管理是核心方法，合规是其中的重要组成部分。

### 7.2 数据相关概念

| 概念 | 英文 | 定义 | 说明 |
|------|------|------|------|
| **数据驻留** | Data Residency | 数据存储在什么地理位置 | 很多国家要求本国数据存在境内 |
| **数据主权** | Data Sovereignty | 数据受所在国家法律管辖 | 数据在哪国，就受哪国法律约束 |
| **数据隐私** | Data Privacy | 个人数据的收集、使用、保护 | 保护个人信息不被滥用 |
| **数据保护** | Data Protection | 保护数据的安全措施 | 更广泛的概念，包括安全和隐私 |
| **数据安全** | Data Security | 保护数据的机密性、完整性、可用性 | 技术层面的保护 |

**相关法律法规（中国）**：
- 《数据安全法》：数据安全与数据主权
- 《个人信息保护法》：个人信息保护
- 《网络安全法》：网络安全与数据安全
- 《关键信息基础设施安全保护条例》：关键信息基础设施的数据保护

### 7.3 安全策略与标准的层次

```
顶层
  │
  ├── 安全愿景 / 安全方针 (Security Vision)
  │    一句话/一段话，最高层的方向指引
  │
  ├── 安全策略 (Security Policy)
  │    高层的原则和要求，管理层批准
  │
  ├── 安全标准 (Security Standard)
  │    具体的技术要求和基准（必须遵守）
  │
  ├── 安全基线 (Security Baseline)
  │    最低要求（如系统加固基线、配置基线）
  │
  ├── 操作规程 (Procedure)
  │    具体怎么做，一步步的操作指南
  │
  └── 指南 (Guideline)
       建议性的最佳实践（推荐但不强制）
底层
```

**越往上越抽象、越稳定；越往下越具体、更新越频繁。**
