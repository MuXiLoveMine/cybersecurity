## 一、风险管理

### 1.1 什么是风险管理

**信息安全风险管理**：系统地识别、分析、评估和处置信息安全风险，以实现组织的业务目标。

```
风险管理不是消除所有风险，而是：
  1. 知道有什么风险
  2. 知道风险有多大
  3. 决定怎么处理（接受/规避/转移/缓解）
  4. 把风险控制在可接受的范围内
```

### 1.2 风险管理流程

```
┌───────────────────────────────────────────────────┐
│                                                   │
│  1. 风险识别（Identify）                           │
│     → 找出可能发生什么坏事                         │
│                                                   │
│  2. 风险分析（Analyze）                            │
│     → 分析可能性和影响，确定风险水平                │
│                                                   │
│  3. 风险评价（Evaluate）                           │
│     → 与可接受风险比较，确定优先级                 │
│                                                   │
│  4. 风险处置（Treat）                              │
│     → 选择处置方式，制定措施并实施                 │
│                                                   │
│  5. 监控与评审（Monitor & Review）                 │
│     → 持续监控，定期评审，持续改进                 │
│                                                   │
└───────────────────────────────────────────────────┘
          ↓  循环往复，持续改进  ↑
          └─────────────────────┘
```

### 1.3 风险识别

**风险识别的方法**：

| 方法 | 说明 | 适用场景 |
|------|------|---------|
| **头脑风暴** | 团队一起想，发散思维 | 初步识别、集思广益 |
| **德尔菲法** | 专家匿名多轮调查 | 专家意见收集 |
| **检查表法** | 对照检查清单逐项检查 | 标准化、快速识别 |
| **情景分析** | 设想各种攻击场景 | 模拟真实情况 |
| **威胁建模** | STRIDE、DREAD 等模型 | 系统/应用设计阶段 |
| **漏洞评估** | 扫描系统发现漏洞 | 技术层面 |
| **历史数据分析** | 分析过去的安全事件 | 数据驱动 |
| **访谈/问卷** | 与各部门人员交流 | 业务和管理层面 |

**风险的三要素**：

| 要素 | 英文 | 说明 |
|------|------|------|
| **资产** | Asset | 有价值的东西（数据、系统、设备、声誉等） |
| **威胁** | Threat | 可能造成伤害的来源/事件（攻击、故障、灾害等） |
| **脆弱性** | Vulnerability | 资产的弱点，可能被威胁利用 |

```
风险 = 威胁 × 脆弱性 × 资产价值

没有威胁 → 即使脆弱也没风险
没有脆弱性 → 即使有威胁也没风险
没有资产 → 威胁和脆弱性都无所谓
```

### 1.4 风险分析

**风险分析方法**：

| 方法 | 说明 | 精度 | 工作量 |
|------|------|------|--------|
| **定性分析** | 用高/中/低等描述性等级 | 较低 | 少 |
| **定量分析** | 用具体数值（金额、概率） | 较高 | 大 |
| **半定量分析** | 等级打分，计算分值 | 中 | 中 |

#### 定性风险矩阵

最常用的定性分析方法——可能性 × 影响 = 风险等级：

| 可能性 ↓ / 影响 → | 轻微 | 一般 | 严重 | 重大 | 灾难 |
|:----------------:|:----:|:----:|:----:|:----:|:----:|
| **几乎确定** | 中 | 高 | 很高 | 极高 | 极高 |
| **很可能** | 中 | 高 | 很高 | 极高 | 极高 |
| **可能** | 低 | 中 | 高 | 很高 | 极高 |
| **不太可能** | 低 | 低 | 中 | 高 | 很高 |
| **罕见** | 很低 | 低 | 低 | 中 | 高 |

| 风险等级 | 对应措施 |
|---------|---------|
| **极高** | 立即处理，否则会造成灾难性后果 |
| **很高** | 优先处理，高层关注 |
| **高** | 限期处理 |
| **中** | 正常计划处理 |
| **低** | 接受或监控 |
| **很低** | 接受 |

#### 定量分析常用指标

| 指标 | 英文 | 说明 |
|------|------|------|
| **SLE** | Single Loss Expectancy | 单次事件预期损失 = 资产价值 × 暴露因子（EF） |
| **ARO** | Annualized Rate of Occurrence | 年发生频率（每年发生几次） |
| **ALE** | Annualized Loss Expectancy | 年预期损失 = SLE × ARO |

```
示例：
  数据库服务器价值 100 万
  如果被 ransomware 加密，暴露因子 70%（业务损失 + 恢复成本）
  SLE = 100 万 × 70% = 70 万
  
  行业统计这种事平均 2 年发生一次
  ARO = 0.5 次/年
  
  ALE = 70 万 × 0.5 = 35 万/年

  如果买一个解决方案成本 10 万/年，能把风险降低 80%，
  即 ALE 降低到 7 万，减少了 28 万损失
  成本 10 万 < 收益 28 万 → 划算，可以买
```

### 1.5 风险处置

四种风险处置方式：

| 处置方式 | 英文 | 说明 | 例子 |
|---------|------|------|------|
| **风险缓解** | Mitigate / Reduce | 采取措施降低风险 | 部署防火墙、打补丁、做备份 |
| **风险转移** | Transfer | 把风险转嫁给第三方 | 买保险、外包给云厂商 |
| **风险规避** | Avoid | 避免会带来风险的活动 | 不上线某个功能、不做某个业务 |
| **风险接受** | Accept | 承担风险（成本太高或风险太小） | 小概率小损失的风险，不处理 |

> **选择原则**：
> - 高风险 → 优先缓解或规避
> - 中风险 → 缓解或转移
> - 低风险 → 接受
> - 还要考虑成本效益：处置成本 < 风险减少的价值才划算
> - 所有接受的风险必须得到管理层批准

### 1.6 风险评估的常见标准/方法

| 标准/方法 | 发布方 | 说明 |
|----------|--------|------|
| **ISO 27005** | ISO | 信息安全风险管理指南 |
| **NIST SP 800-30** | NIST | 风险评估指南（美国联邦政府标准） |
| **OCTAVE** | CERT | 运营型关键威胁、资产与脆弱性评估 |
| **FAIR** | Factor Analysis of Information Risk | 信息风险因子分析，定量方法 |
| **GB/T 20984** | 中国国标 | 信息安全风险评估规范 |

## 二、安全治理体系

### 2.1 安全治理框架

**信息安全治理（Information Security Governance）**：一套指导和控制组织信息安全活动的体系，确保信息安全与业务目标对齐，并得到有效执行。

```
安全治理体系金字塔：

        安全方针（Policy）        ← 最高层，管理层承诺，方向性
            │
        安全标准（Standard）      ← 具体技术标准和规范
            │
        安全流程（Process）       ← 怎么做，步骤和责任人
            │
        操作指南（Guideline）     ← 具体操作说明
            │
        安全基线（Baseline）      ← 最低安全配置标准
```

### 2.2 安全策略体系

| 层级 | 名称 | 英文 | 说明 | 示例 |
|------|------|------|------|------|
| **第一层** | 安全方针 / 总策略 | Security Policy | 最高层级，管理层签发，阐述安全理念和总体要求 | 《信息安全管理总策略》 |
| **第二层** | 专项策略 | Topic-specific Policy | 各领域的策略文件 | 《密码策略》《访问控制策略》《备份策略》 |
| **第三层** | 标准 | Standard | 具体的技术标准和规范 | 《服务器安全配置标准》《密码算法标准》 |
| **第四层** | 流程 / 程序 | Process / Procedure | 具体怎么操作，步骤、角色、输入输出 | 《漏洞管理流程》《应急响应流程》 |
| **第五层** | 指南 / 基线 | Guideline / Baseline | 操作手册、配置模板、检查清单 | 《Linux 安全加固基线》《Windows 安全基线》 |

### 2.3 常见专项策略

| 策略 | 说明 | 核心内容 |
|------|------|---------|
| **访问控制策略** | 谁能访问什么资源 | 最小权限、职责分离、账号生命周期 |
| **密码策略** | 密码的安全要求 | 长度、复杂度、有效期、存储方式 |
| **备份策略** | 数据备份要求 | 备份内容、频率、保留期、恢复测试 |
| **加密策略** | 加密算法和使用要求 | 算法选择、密钥管理、数据分类加密 |
| **日志审计策略** | 日志记录和审计要求 | 审计范围、日志保留期、审计频率 |
| **物理安全策略** | 物理环境安全 | 机房安全、门禁、监控、设备管理 |
| **人员安全策略** | 员工和第三方的安全要求 | 背景调查、保密协议、安全培训、离职流程 |
| **第三方安全策略** | 供应商/合作伙伴安全 | 供应商评估、合同安全条款、审计 |
| **变更管理策略** | 系统变更的安全控制 | 变更申请、审批、测试、回滚 |
| **事件响应策略** | 安全事件的处理 | 事件分级、响应流程、上报机制 |
| **可接受使用策略** | 员工使用公司资源的规定 | AUP（Acceptable Use Policy），能做什么不能做什么 |

### 2.4 安全基线

**安全基线（Security Baseline）**：对一类系统/设备/应用的最低安全配置标准，确保系统达到基本的安全水位。

| 基线类型 | 说明 | 典型内容 |
|---------|------|---------|
| **操作系统基线** | Linux/Windows 系统加固标准 | 账号安全、服务最小化、补丁、审计配置、内核参数 |
| **数据库基线** | MySQL/Oracle/SQL Server 加固 | 账号权限、审计、加密、补丁、配置参数 |
| **中间件基线** | Nginx/Tomcat/JBoss 加固 | 版本、配置、权限、日志、隐藏信息 |
| **网络设备基线** | 交换机/路由器/防火墙加固 | 密码、SNMP、SSH、ACL、日志、禁用不必要服务 |
| **云服务基线** | 云平台安全配置 | 身份管理、网络安全、数据加密、日志监控 |
| **开发安全基线** | 开发环境和代码安全 | 代码规范、依赖检查、密钥管理、CI/CD 安全 |

> **基线的价值**：
> - 统一安全标准，避免各自为政
> - 自动化检查和合规验证
> - 新系统上线的安全准入标准
> - 持续监控和漂移检测

## 三、合规法规与标准

### 3.1 国内法律法规

#### （1）网络安全法

**《中华人民共和国网络安全法》**，2017 年 6 月 1 日施行，是我国网络安全领域的基础性法律。

| 核心内容 | 说明 |
|---------|------|
| **网络安全等级保护制度** | 国家实行网络安全等级保护制度（等保 2.0） |
| **关键信息基础设施** | 关键信息基础设施实行重点保护 |
| **网络运营者义务** | 安全保护义务、数据保护、实名登记、应急预案等 |
| **个人信息保护** | 收集使用个人信息的规则 |
| **监测预警与应急处置** | 建立网络安全监测预警和应急处置体系 |
| **法律责任** | 罚款、停业整顿、吊销执照、刑事责任 |

#### （2）数据安全法

**《中华人民共和国数据安全法》**，2021 年 9 月 1 日施行。

| 核心内容 | 说明 |
|---------|------|
| **数据分类分级** | 建立数据分类分级保护制度 |
| **重要数据** | 对关系国家安全等重要数据实行重点保护 |
| **数据安全制度** | 风险评估、应急响应、安全审查、出口管制 |
| **数据交易** | 规范数据交易行为 |
| **政务数据安全** | 政务数据安全与开放 |

#### （3）个人信息保护法

**《中华人民共和国个人信息保护法》**，2021 年 11 月 1 日施行。

| 核心内容 | 说明 |
|---------|------|
| **处理原则** | 合法、正当、必要、诚信 |
| **知情同意** | 个人信息处理需取得个人同意 |
| **敏感个人信息** | 生物识别、宗教信仰、医疗健康等需特别保护 |
| **个人权利** | 知情权、决定权、查阅权、更正权、删除权等 |
| **跨境传输** | 个人信息出境需满足条件 |
| **法律责任** | 最高 5000 万元或上一年度营业额 5% 罚款 |

#### （4）网络安全等级保护 2.0

**网络安全等级保护制度**（简称"等保"）是我国网络安全的基本制度，2.0 版本于 2019 年实施。

**等级划分**：

| 等级 | 名称 | 说明 | 受侵害对象 |
|------|------|------|-----------|
| **第一级** | 自主保护级 | 一般信息系统 | 公民、法人的合法权益 |
| **第二级** | 指导保护级 | 一定程度危害的信息系统 | 社会秩序、公共利益 |
| **第三级** | 监督保护级 | 造成严重危害 | 国家安全 |
| **第四级** | 强制保护级 | 造成特别严重危害 | 国家安全（严重） |
| **第五级** | 专控保护级 | 造成特别严重损害 | 国家安全（特别严重） |

> 绝大多数企业系统是二级或三级。一级很少（太简单不需要备案），四级以上是重要行业核心系统。

**等保 2.0 技术要求（简表）**：

| 层面 | 主要要求 |
|------|---------|
| **安全物理环境** | 机房位置、物理访问控制、防火、防水、电力供应 |
| **安全通信网络** | 网络架构、通信传输、可信验证 |
| **安全区域边界** | 边界防护、访问控制、入侵防范、恶意代码防范、安全审计 |
| **安全计算环境** | 身份鉴别、访问控制、安全审计、入侵防范、恶意代码防范、数据完整性/保密性 |
| **安全管理中心** | 系统管理、审计管理、安全管理、集中管控 |

**等保 2.0 管理要求（简表）**：

| 层面 | 主要要求 |
|------|---------|
| **安全管理制度** | 安全策略、制度、规范、流程 |
| **安全管理机构** | 岗位设置、人员配备、授权和审批、沟通与合作 |
| **安全管理人员** | 人员录用、离岗、考核、培训 |
| **安全建设管理** | 定级备案、方案设计、产品采购、工程实施、测试验收 |
| **安全运维管理** | 环境管理、资产管理、介质管理、设备管理、漏洞管理、应急管理 |

**等保工作流程**：

```
1. 定级  →  确定系统等级，专家评审，主管部门审批
2. 备案  →  到公安机关备案，拿到备案证明
3. 建设整改  →  按照等保要求建设和加固
4. 等级测评  →  第三方测评机构测评（合格/不合格）
5. 监督检查  →  公安机关定期检查
6. 持续改进  →  每年复测，持续维护
```

### 3.2 国际标准

#### （1）ISO/IEC 27001

**ISO/IEC 27001** 是国际上最权威的信息安全管理体系标准，规定了建立、实施、保持和持续改进信息安全管理体系（ISMS）的要求。

| 组成 | 说明 |
|------|------|
| **ISO 27000** | 概述和词汇 |
| **ISO 27001** | ISMS 要求（可认证的标准） |
| **ISO 27002** | 信息安全控制实践准则（控制措施指南） |
| **ISO 27005** | 信息安全风险管理 |
| **ISO 27017** | 云服务信息安全控制 |
| **ISO 27018** | 云中个人数据保护 |
| **ISO 27701** | 隐私信息管理体系（PIMS） |

**ISO 27001 结构（PDCA 循环 + Annex A 控制措施）**：

```
ISO 27001:2022 结构：

  第 4 章：组织环境
  第 5 章：领导作用
  第 6 章：规划（风险评估、风险处置、目标）
  第 7 章：支持（资源、能力、意识、沟通、文档化信息）
  第 8 章：运行（风险评估、风险处置、控制措施）
  第 9 章：绩效评价（监视测量、内部审核、管理评审）
  第 10 章：改进（不符合与纠正措施、持续改进）

  Annex A：93 项控制措施（参考 ISO 27002）
  分为 4 大类：
    A.5 组织控制（37 项）
    A.6 人员控制（8 项）
    A.7 物理控制（14 项）
    A.8 技术控制（34 项）
```

> ISO 27001 是可以第三方认证的标准——企业通过认证，证明其信息安全管理体系符合国际标准。

#### （2）NIST CSF

**NIST 网络安全框架（Cybersecurity Framework）**，由美国国家标准与技术研究院发布，是一个风险导向的网络安全框架。

```
NIST CSF 五大核心功能：

  1. 识别（Identify）→ 了解资产、风险、治理
       │
       ▼
  2. 保护（Protect）→ 部署防护措施
       │
       ▼
  3. 检测（Detect）→ 发现安全事件
       │
       ▼
  4. 响应（Respond）→ 响应和处置
       │
       ▼
  5. 恢复（Recover）→ 恢复和韧性
```

### 3.3 行业监管

|----------|------|--------|---------|
| **PCI DSS** | 支付卡行业 | PCI SSC | 支付卡数据安全标准，保护持卡人数据 |

| **等保 2.0** | 通用 | 中国 | 网络安全等级保护 |
| **关键信息基础设施安全保护条例** | 关键基础设施 | 中国 | 关基保护 |
| **金融行业网络安全等级保护** | 金融 | 中国人民银行 | 金融业等保实施指南 |
| **等保 2.0 云计算扩展要求** | 云 | 公安部 | 云计算安全扩展 |

#### PCI DSS 速览

**PCI DSS（Payment Card Industry Data Security Standard）**：支付卡行业数据安全标准，处理支付卡的机构必须遵守。

| 六大目标 | 12 项要求 |
|---------|----------|
| **建立并维护安全的网络和系统** | 1. 安装并维护防火墙配置<br>2. 不要使用供应商提供的默认密码和其他安全参数 |
| **保护持卡人数据** | 3. 保护存储的持卡人数据<br>4. 加密开放公用网络中持卡人数据的传输 |
| **维护漏洞管理计划** | 5. 使用并定期更新防病毒软件<br>6. 开发并维护安全的系统和应用 |
| **实施强访问控制措施** | 7. 按业务需要限制对持卡人数据的访问<br>8. 识别并验证对系统组件的访问<br>9. 限制对持卡人数据的物理访问 |
| **定期监控并测试网络** | 10. 跟踪并监控对网络资源和持卡人数据的所有访问<br>11. 定期测试安全系统和流程 |
| **维护信息安全政策** | 12. 维护一个解决信息安全的政策 |

#### GDPR 速览

**GDPR（General Data Protection Regulation）**：欧盟通用数据保护条例，是全球最严格的数据保护法规之一。

| 核心概念 | 说明 |
|---------|------|
| **数据主体** | 个人（被收集数据的人） |
| **数据控制者** | 决定数据处理目的和方式的组织 |
| **数据处理者** | 代表控制者处理数据的组织 |
| **数据主体权利** | 知情权、访问权、更正权、删除权（被遗忘权）、限制处理权、数据可携权、反对权 |
| **六大约法基础** | 同意、合同履行、法定义务、公共利益、合法利益、保护重大利益 |
| **问责制** | 控制者有责任证明合规 |
| **数据保护影响评估（DPIA）** | 高风险处理活动需做 DPIA |
| **数据泄露通知** | 72 小时内通知监管机构 |
| **罚款** | 最高 2000 万欧元或全球年营业额的 4%（取高者） |

## 四、审计与日志留存

### 4.1 安全审计

**安全审计（Security Audit）**：独立地检查和评估系统、流程和控制措施的有效性，确认是否符合政策、标准和法规要求。

| 审计类型 | 说明 |
|---------|------|
| **内部审计** | 组织内部审计部门进行 |
| **外部审计** | 第三方独立机构进行 |
| **合规审计** | 验证是否符合特定法规/标准（如等保、ISO 27001、PCI DSS） |
| **技术审计** | 技术层面的审计（系统配置、漏洞、渗透测试等） |
| **管理审计** | 管理层面的审计（制度、流程、人员） |

### 4.2 日志留存要求

日志留存是很多合规要求的重要组成部分。

| 法规/标准 | 日志留存要求 |
|----------|-------------|
| **网络安全法** | 网络日志留存不少于六个月 |
| **等保 2.0** | 三级系统：审计记录保存不少于 6 个月；二级：不少于 6 个月 |
| **关键信息基础设施** | 重要系统日志留存更长（按行业要求） |
| **PCI DSS** | 审计日志至少保留 1 年，其中至少 3 个月立即可用 |
| **ISO 27001** | 按业务和法规要求确定留存期 |
| **GDPR** | 个人数据不能超过必要时间保留 |

**应该记录哪些日志**：

| 类别 | 具体内容 |
|------|---------|
| **认证日志** | 登录成功/失败、登出、密码修改、账号锁定 |
| **访问日志** | 资源访问、文件操作、权限变更 |
| **系统日志** | 系统启动/关闭、服务启停、内核消息 |
| **安全设备日志** | 防火墙、IDS/IPS、WAF、VPN 的告警和流量 |
| **应用日志** | Web 服务器、应用系统、数据库的访问和错误 |
| **配置变更** | 配置修改、补丁安装、系统变更 |
| **管理员操作** | 特权账号的操作记录 |
| **数据操作** | 敏感数据的增删改查 |

### 4.3 审计日志的安全要求

```
日志安全要求：

1. 完整性
   □ 日志不能被篡改
   □ 重要日志做签名或哈希校验
   □ 日志服务器独立部署（与被审计系统分开）

2. 保密性
   □ 日志中可能包含敏感信息，需要保护
   □ 日志传输加密（TLS）
   □ 日志存储加密（涉及敏感数据时）

3. 可用性
   □ 日志服务高可用
   □ 日志定期备份
   □ 存储容量充足，防止日志溢出

4. 访问控制
   □ 日志访问权限严格控制
   □ 审计人员只有查看权限，不能修改
   □ 日志操作本身也要被审计

5. 留存管理
   □ 按法规要求的留存期保存
   □ 到期后安全删除
   □ 重要日志长期归档
```

### 4.4 审计跟踪与问责

**审计跟踪（Audit Trail）**：一系列按时间顺序排列的审计记录，能够重建事件的发生过程，用于调查和追责。

| 审计跟踪的作用 | 说明 |
|-------------|------|
| **事件调查** | 安全事件发生后，通过日志还原时间线 |
| **责任认定** | 谁在什么时候做了什么操作 |
| **合规证明** | 证明符合法规要求 |
| **问题定位** | 故障和问题的排查 |
| **威慑作用** | 知道操作会被记录，减少违规行为 |

## 五、业务连续性与灾难恢复

### 5.1 基本概念

| 概念 | 英文 | 说明 |
|------|------|------|
| **业务连续性管理** | BCM（Business Continuity Management） | 确保关键业务在中断后能持续运行的整体管理过程 |
| **业务连续性计划** | BCP（Business Continuity Plan） | 业务中断后的应急计划，保证业务持续 |
| **灾难恢复** | DR（Disaster Recovery） | 灾难后 IT 系统和数据的恢复 |
| **灾难恢复计划** | DRP（Disaster Recovery Plan） | IT 系统恢复的详细计划 |
| **高可用性** | HA（High Availability） | 系统尽量不停机（通过冗余等技术） |

```
关系：
  BCM 范围最大 → 包含 BCP → 包含 DRP → 包含技术恢复方案
  BCM 关注的是业务能不能持续
  DR 关注的是 IT 系统能不能恢复
```

### 5.2 核心指标

| 指标 | 英文 | 含义 | 说明 |
|------|------|------|------|
| **RPO** | Recovery Point Objective | 恢复点目标 | 最多能丢失多少数据（时间） |
| **RTO** | Recovery Time Objective | 恢复时间目标 | 最多能停机多久 |
| **RLO** | Recovery Level Objective | 恢复级别目标 | 恢复到什么功能级别 |
| **WRT** | Work Recovery Time | 工作恢复时间 | 技术恢复后到业务完全正常的时间 |
| **MTD** | Maximum Tolerable Downtime | 最大可容忍停机时间 | 超过这个时间业务就扛不住了 |

```
时间线：

  灾难发生              技术恢复完成      业务完全恢复
     │                      │                 │
     ├──────────────────────┼─────────────────┤
     │         RTO          │      WRT        │
     │                                        │
     └───────────────── MTD ──────────────────┘

  RTO + WRT ≤ MTD （必须满足，否则业务就扛不住了）
```

**RPO 和 RTO 的常见级别**：

| 级别 | RPO | RTO | 典型方案 | 成本 |
|------|-----|-----|---------|------|
| 低 | 24 小时 | 24~72 小时 | 磁带备份、异地冷备 | 低 |
| 中 | 4~8 小时 | 4~24 小时 | 磁盘备份、温备中心 | 中 |
| 高 | 1 小时以内 | 1 小时以内 | 实时复制、热备 | 高 |
| 很高 | 接近 0 | 分钟级 | 双活/多活数据中心 | 很高 |
| 极高 | 0（不丢数据） | 0（不中断） | 完全冗余的高可用集群 | 极高 |

### 5.3 BCM 流程

```
业务连续性管理生命周期：

  1. 项目启动与管理
     → 获得管理层支持，明确范围和目标

  2. 风险评估与业务影响分析（BIA）
     → 有什么风险？中断了损失多大？
     → 确定 RTO、RPO、MTD

  3. 业务连续性策略
     → 选择什么策略来保障业务连续性
     → （冗余、备份、替代方案、外包等）

  4. 制定和实施 BCP
     → 编写详细的业务连续性计划
     → 落实各项措施

  5. 培训与意识
     → 相关人员培训，全员意识

  6. 演练与测试
     → 定期演练，验证计划有效性

  7. 维护与持续改进
     → 定期评审，根据变化更新
```

### 5.4 灾难恢复策略

| 策略 | 说明 | RTO 级别 | 成本 |
|------|------|---------|------|
| **冷备（Cold Site）** | 有空机房和基础设施，设备要现运现装 | 几天~几周 | 低 |
| **温备（Warm Site）** | 有部分设备，数据定期备份，需要时恢复 | 几小时~几天 | 中 |
| **热备（Hot Site）** | 设备齐全，数据实时/准实时复制，可快速切换 | 几小时 | 高 |
| **双活（Active-Active）** | 两个/多个数据中心同时运行，负载分担 | 分钟级 | 很高 |
| **多云/多区域** | 在多个云区域/云厂商部署 | 分钟~小时 | 高 |

### 5.5 备份策略

**3-2-1 备份原则**：

```
3 份数据副本
2 种不同介质（如磁盘 + 磁带/云）
1 份异地备份（不在同一个地方）

再加 1 个离线/气隙（Air Gap）备份（防勒索软件）
```

| 备份类型 | 英文 | 说明 | 优点 | 缺点 |
|---------|------|------|------|------|
| **完全备份** | Full | 备份所有数据 | 恢复简单 | 慢、占空间大 |
| **增量备份** | Incremental | 只备份上次备份以来变化的 | 快、占空间小 | 恢复慢（要先全量再一条条恢复） |
| **差异备份** | Differential | 只备份上次全量备份以来变化的 | 恢复比增量快（全量+最后一次差异） | 介于全量和增量之间 |
| **快照** | Snapshot | 某一时刻的状态快照（指针） | 极快、占用空间小 | 依赖存储系统，不是独立备份 |

**备份验证**：备份了不等于能恢复，必须定期做恢复测试！

```
备份最佳实践：

1. 明确备份范围
   □ 哪些系统、哪些数据要备份
   □ 配置文件、数据库、文件数据

2. 选择备份策略
   □ 全量 + 增量/差异组合
   □ 备份频率（日备份/周备份/月备份）
   □ 保留期限（日备份保留 7 天、周备份保留 4 周、月备份保留 12 个月）

3. 异地备份
   □ 至少一份异地备份
   □ 传输加密
   □ 离线/气隙备份（防勒索软件）

4. 备份安全
   □ 备份数据加密
   □ 备份介质访问控制
   □ 备份服务器与生产隔离

5. 恢复测试
   □ 定期做恢复演练（至少每季度/每半年一次）
   □ 验证恢复数据的完整性
   □ 验证恢复时间满足 RTO/RPO
```

## 六、安全意识培训

### 6.1 为什么需要安全意识培训

> "人是安全最薄弱的环节。"——技术再强，人被骗了也没用。

| 数据 | 说明 |
|------|------|
| 社会工程/钓鱼 | 很多安全事件的初始入口是钓鱼邮件 |
| 弱密码 | 大量账号使用弱密码或重复密码 |
| 误操作 | 很多数据泄露是人为失误导致的 |
| 内部威胁 | 恶意或无意的内部人员风险 |

安全意识培训就是要让人成为安全的第一道防线，而不是最薄弱的环节。

### 6.2 培训内容

| 培训内容 | 针对人群 | 核心要点 |
|---------|---------|---------|
| **基础安全意识** | 全员 | 密码安全、钓鱼识别、数据保护、物理安全、社会工程 |
| **岗位专项培训** | 对应岗位 | 管理员：系统安全；开发：安全编码；财务：反诈骗 |
| **管理层培训** | 管理层 | 安全责任、风险管理、合规要求、决策支持 |
| **新员工入职培训** | 新员工 | 公司安全政策、基本安全规范、账号使用 |
| **定期复训** | 全员 | 每年至少一次，更新内容 |
| **钓鱼演练** | 全员 | 模拟钓鱼邮件，测试识别能力 |

**全员基础安全意识核心内容**：

```
安全意识 TOP 10：

1. 密码安全
   - 使用强密码，不用弱密码
   - 不同系统用不同密码
   - 使用密码管理器
   - 开启 MFA/双因素认证

2. 钓鱼识别
   - 警惕陌生邮件，特别是带链接和附件的
   - 检查发件人地址（注意拼写相似的域名）
   - 不随便点链接、不随便下附件
   - 可疑邮件及时上报

3. 数据保护
   - 敏感数据加密存储和传输
   - 不随便发敏感信息（邮件/微信/U盘）
   - 离开座位锁屏
   - 废弃文件/介质安全销毁

4. 设备安全
   - 不安装来源不明的软件
   - 及时打补丁和更新
   - 安装杀毒软件和防火墙
   - 不随便插别人的 U 盘

5. 网络安全
   - 不在公共 Wi-Fi 下处理敏感事务
   - 使用 VPN 访问公司内网
   - 注意 HTTPS 证书
   - 不随便连陌生 Wi-Fi

6. 物理安全
   - 门禁卡随身带，不转借
   - 不尾随（tailgating），也不让别人尾随
   - 桌面清理（clear desk）
   - 打印机/传真机及时取走文件

7. 社会工程
   - 不透露个人和公司信息
   - 核实对方身份
   - 不因为对方自称"IT 部"就给密码
   - 可疑情况及时报告

8. 社交媒体
   - 不在社交媒体上泄露过多个人信息
   - 不发布工作相关的敏感信息
   - 小心社交工程攻击

9. 事件报告
   - 发现可疑情况及时报告
   - 丢了设备立即报告
   - 点了可疑链接/输了密码也要及时报告
   - 报告得越早，损失越小

10. 合规意识
    - 遵守公司安全政策
    - 遵守法律法规
    - 保护客户和员工隐私
    - 知道违规的后果
```

### 6.3 培训方式与效果衡量

| 培训方式 | 说明 |
|---------|------|
| **线上课程** | E-learning 平台，自学为主 |
| **线下培训** | 讲师面对面授课，互动性好 |
| **钓鱼演练** | 模拟钓鱼邮件，实战检验 |
| **游戏化** | 安全知识游戏，提高趣味性 |
| **海报/宣传** | 日常宣传，持续提醒 |
| **案例分享** | 真实安全事件分析，印象深刻 |
| **考核测试** | 考试检验掌握程度 |

**衡量培训效果的指标**：

| 指标 | 说明 |
|------|------|
| **培训覆盖率** | 多少人参加了培训 |
| **考试通过率** | 安全知识考试的通过率 |
| **钓鱼点击率** | 钓鱼演练中点击的人数比例（越低越好） |
| **安全事件中人为因素占比** | 因为人出问题的事件比例（下降说明有效） |
| **报告率** | 员工主动报告可疑事件的数量（上升说明意识提高） |
| **合规违规率** | 安全政策违规的数量（下降说明有效） |

## 七、安全度量与报告

### 7.1 安全度量的目的

**安全度量（Security Metrics）**：用数据衡量安全状况和安全工作的效果，为决策提供依据。

```
为什么需要度量？
  - 不知道现在安全状况怎么样
  - 不知道安全投入有没有效果
  - 不知道哪里需要改进
  - 没法向管理层汇报
  - 没法和同行比较

"你无法管理你不能度量的东西。" —— 德鲁克
```

### 7.2 常见安全指标

#### （1）战略级指标（给管理层看）

| 指标 | 说明 |
|------|------|
| **安全风险等级** | 整体风险水平（高/中/低） |
| **重大安全事件数** | 造成严重影响的事件数量 |
| **合规符合率** | 通过合规审计/检查的比例 |
| **安全投资回报率** | 安全投入带来的风险降低 |
| **业务影响** | 安全事件造成的业务中断时间/损失 |

#### （2）运营级指标（给安全团队看）

| 类别 | 指标 | 说明 |
|------|------|------|
| **威胁检测** | MTTD（平均检测时间） | 从攻击发生到发现的时间 |
| | 告警量 | 每天/每周告警数量 |
| | 误报率 | 错误告警的比例 |
| | 威胁检测覆盖率 | 检测规则覆盖了多少攻击类型 |
| **事件响应** | MTTR（平均响应时间） | 从发现到响应的时间 |
| | MTTC（平均遏制时间） | 从发现到遏制的时间 |
| | 事件关闭率 | 按时关闭的事件比例 |
| | 事件复发率 | 同一事件再次发生的比例 |
| **漏洞管理** | 漏洞修复率 | 已修复漏洞 / 总漏洞数 |
| | 高危漏洞修复时间 | 高危漏洞平均修复时间 |
| | 漏洞存量 | 还有多少未修复的漏洞 |
| | 漏洞复发率 | 修复后又出现的比例 |
| **身份与访问** | 特权账号数量 | 管理员/root 账号数 |
| | 僵尸账号 | 长期未使用的账号 |
| | MFA 覆盖率 | 启用 MFA 的账号比例 |
| | 权限合规率 | 符合最小权限的比例 |
| **资产与配置** | 资产覆盖率 | 纳管的资产比例 |
| | 配置合规率 | 符合安全基线的比例 |
| | 补丁覆盖率 | 已安装安全补丁的比例 |
| **意识培训** | 培训覆盖率 | 参加培训的员工比例 |
| | 钓鱼点击率 | 钓鱼演练中点击的比例 |
| | 事件报告率 | 员工主动报告的数量 |

### 7.3 安全报告

**报告的受众与内容**：

| 受众 | 报告频率 | 报告重点 |
|------|---------|---------|
| **高层管理者** | 季度/年度 | 风险态势、重大事件、合规状态、资源需求 |
| **业务部门** | 月度/季度 | 本部门安全状况、需要配合的事项 |
| **安全团队** | 周/月 | 运营数据、趋势分析、工作进展、问题与计划 |
| **监管机构** | 按要求 | 合规情况、重大事件 |

**安全报告的原则**：

```
好的安全报告：

1. 数据说话
   □ 用数据和事实，不用"感觉""大概"
   □ 趋势比单点数据更有意义
   □ 用图表直观展示

2. 受众导向
   □ 给管理层看的：结论先行、业务影响、决策建议
   □ 给技术团队看的：详细数据、技术细节、改进方案

3. 持续可比
   □ 指标定义一致，可纵向对比（和过去比）
   □ 尽量可横向对比（和同行比）

4. 行动导向
   □ 不只展示问题，还要有改进建议
   □ 有优先级和资源需求
   □ 有跟踪和闭环
```

### 7.4 安全成熟度模型

**安全成熟度模型**：评估一个组织的安全能力处于什么水平，以及下一步该往哪个方向发展。

| 级别 | 名称 | 特征 |
|------|------|------|
| **Level 1** | 初始级 / 被动反应 | 没有体系，出事了才处理，靠人治 |
| **Level 2** | 可重复级 / 基本合规 | 有基本的制度和流程，能做基本的防护 |
| **Level 3** | 已定义级 / 体系化 | 建立了完整的安全管理体系，流程标准化 |
| **Level 4** | 已管理级 / 度量驱动 | 有量化的度量，数据驱动决策，持续改进 |
| **Level 5** | 优化级 / 自适应 | 持续优化，自适应进化，安全融入业务 |

> 大多数中小企业在 Level 1~2，大型企业在 Level 2~3，能到 Level 4~5 的很少。

---

> **总结**：技术只是安全的一部分，管理和治理才是让技术真正发挥作用的保障。风险管理是安全工作的方法论——识别风险、分析风险、处置风险，把有限的资源投入到最需要的地方。安全治理体系（策略/标准/流程/基线）让安全工作有章可循，而不是靠个人经验。合规（等保/ISO 27001/GDPR/PCI DSS 等）既是外部要求，也是驱动安全建设的抓手。审计与日志、业务连续性、安全意识培训、安全度量与报告，则构成了安全管理的闭环——有标准、有执行、有检查、有改进。记住：网络安全三分技术七分管理，没有管理体系支撑的技术投入，往往事倍功半。
