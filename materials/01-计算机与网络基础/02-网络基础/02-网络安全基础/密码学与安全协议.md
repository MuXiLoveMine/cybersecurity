## 一、密码学概述

### 1.1 什么是密码学

**密码学（Cryptography）**是研究如何隐秘地传递信息的学科，通过数学方法对信息进行加密、解密、认证和完整性保护。

| 分支 | 英文 | 说明 |
|------|------|------|
| **对称加密** | Symmetric Encryption | 加密解密用同一密钥 |
| **非对称加密** | Asymmetric Encryption | 用一对密钥（公钥+私钥） |
| **哈希算法** | Hash Algorithm | 单向散列，用于完整性 |
| **消息认证码** | MAC | 带密钥的哈希，认证+完整性 |
| **数字签名** | Digital Signature | 私钥签名，公钥验证，不可否认 |
| **密钥交换** | Key Exchange | 安全地协商共享密钥 |

### 1.2 密码学能解决什么问题

| 安全属性 | 密码学手段 |
|---------|-----------|
| **机密性** | 对称加密、非对称加密 |
| **完整性** | 哈希、消息认证码、数字签名 |
| **身份认证** | 消息认证码、数字签名、证书 |
| **不可否认性** | 数字签名 + PKI |
| **密钥协商** | DH 密钥交换、公钥加密 |

> 实际应用中，这些技术通常组合使用。例如 TLS = 非对称加密（密钥交换）+ 对称加密（数据加密）+ 哈希（完整性）+ 数字签名（认证）。

### 1.3 柯克霍夫原则

**柯克霍夫原则（Kerckhoffs's Principle）**：密码系统的安全性应该依赖于密钥，而不是算法本身的保密。即使算法被公开，只要密钥保密，系统仍然安全。

- ✅ **正确做法**：算法公开审查，密钥保密
- ❌ **错误做法**："加密算法是保密的，所以安全"（安全通过隐匿，Security by Obscurity）

> 为什么算法要公开？因为公开的算法经过全世界密码学家的审查，更可靠。保密的算法可能有很多漏洞，只是没人公开说而已。

## 二、对称加密

### 2.1 基本概念

**对称加密（Symmetric Encryption）**：加密和解密使用**同一个密钥**（共享密钥）。

```
加密：  明文 + 密钥 → 密文     C = E(K, P)
解密：  密文 + 密钥 → 明文     P = D(K, C)

  发送方                                  接收方
  明文 ──加密──► 密文 ────传输────► 密文 ──解密──► 明文
          ▲                                    ▲
          │                                    │
         密钥 ──────────怎么安全传递？───────── 密钥
```

| 优点 | 缺点 |
|------|------|
| 速度快（适合大数据量） | 密钥分发困难（怎么安全地把密钥给对方？） |
| 算法公开、安全性经过验证 | 密钥数量随通信方数量平方增长（n 个人需要 n(n-1)/2 个密钥） |
| 硬件加速支持好 | 不能提供不可否认性（双方都有密钥，谁都可以加密） |
| 密文长度 ≈ 明文长度 | |

### 2.2 常见对称加密算法

| 算法 | 密钥长度 | 块大小 | 安全性 | 现状 | 说明 |
|------|---------|--------|--------|------|------|
| **DES** | 56 位（实际 64 位，8 位校验） | 64 位 | 极低 | ❌ 已淘汰 | 1977 年标准，56 位太短，暴力可破 |
| **3DES / Triple DES** | 112/168 位 | 64 位 | 低~中 | ⚠️ 逐步淘汰 | DES 做三次，兼容老系统用 |
| **AES** | 128/192/256 位 | 128 位 | 高 | ✅ 推荐 | 目前主流标准，速度快、安全 |
| **Blowfish** | 32~448 位 | 64 位 | 中 | 较少用 | 免费开源，64 位块偏小 |
| **Twofish** | 128/192/256 位 | 128 位 | 高 | 较少用 | AES 最终候选之一 |
| **ChaCha20** | 256 位 | 流密码 | 高 | ✅ 推荐 | 流密码，移动/嵌入式性能好 |
| **SM4** | 128 位 | 128 位 | 高 | 中国国密 | 中国商用密码标准 |

> ⚠️ **安全警告**：DES 和 3DES 已经不安全，不应在新系统中使用。AES-256 和 ChaCha20 是目前推荐的选择。

### 2.3 AES 详解

**AES（Advanced Encryption Standard）** 是目前最主流的对称加密算法，由 NIST 于 2001 年发布，替代 DES。

| 版本 | 密钥长度 | 轮数 |
|------|---------|------|
| AES-128 | 128 位 | 10 轮 |
| AES-192 | 192 位 | 12 轮 |
| AES-256 | 256 位 | 14 轮 |

**AES 的特点**：
- ✅ 安全性高：目前没有有效的破解方法
- ✅ 速度快：软件硬件都有很好的性能
- ✅ 资源占用小：适合嵌入式设备
- ✅ 标准开放：全球通用，无专利问题

### 2.4 加密模式

**加密模式（Mode of Operation）**：决定了如何用块密码加密超过一个块大小的数据。

| 模式 | 英文 | 特点 | 安全性 | 推荐 |
|------|------|------|--------|------|
| **ECB** | Electronic Codebook | 每个块独立加密，相同明文产生相同密文 | ❌ 不安全 | 不推荐 |
| **CBC** | Cipher Block Chaining | 每个明文块与前一个密文块异或，需要 IV | 中（有 padding oracle 风险） | 谨慎使用 |
| **CFB** | Cipher Feedback | 把块密码变成流密码 | 中 | 较少用 |
| **OFB** | Output Feedback | 生成密钥流与明文异或 | 中 | 较少用 |
| **CTR** | Counter | 计数器模式，并行加密 | 高 | 推荐（配合 MAC 使用） |
| **GCM** | Galois/Counter Mode | CTR + GMAC（认证加密） | ✅ 很高 | 强烈推荐 |
| **CCM** | Counter with CBC-MAC | CTR + CBC-MAC（认证加密） | 高 | 推荐（IoT 常用） |

> **什么是认证加密（AEAD）？** 同时提供机密性和完整性/认证的加密模式。GCM 和 CCM 都是 AEAD 模式——加密的同时生成认证标签，解密时先验证标签，验证失败就不解密，防止篡改。

**ECB 模式为什么不安全？**

```
ECB 模式：每个块独立加密

  明文块1 ──加密──► 密文块1
  明文块2 ──加密──► 密文块2
  明文块3 ──加密──► 密文块3
  明文块1 ──加密──► 密文块1  ← 相同的明文产生相同的密文！

问题：
  - 相同明文块 → 相同密文块，泄露数据模式
  - 可以单独替换、删除、重排密文块
  - 经典例子：ECB 加密的 Tux 图片，加密后还能看出轮廓
```

> ✅ **最佳实践**：优先使用 **AES-256-GCM** 或 **ChaCha20-Poly1305**。它们都是认证加密（AEAD），同时提供机密性和完整性保护。

### 2.5 填充方式

块加密要求明文长度是块大小的整数倍，不够就要填充（Padding）。

| 填充方式 | 说明 |
|---------|------|
| **PKCS#7 / PKCS#5** | 缺 n 字节就填 n 个字节，每个字节值为 n |
| **Zero Padding** | 填 0（简单但不明确，明文以 0 结尾时有歧义） |
| **ISO 10126** | 最后一个字节是填充长度，其余随机 |

> **Padding Oracle 攻击**：CBC 模式下，如果系统会泄露"填充是否正确"的信息，攻击者可以逐字节解密数据。这也是为什么推荐用 GCM 等 AEAD 模式而不是 CBC。

## 三、非对称加密

### 3.1 基本概念

**非对称加密（Asymmetric Encryption）**，也叫**公钥加密（Public Key Encryption）**，使用一对密钥：**公钥（Public Key）**和**私钥（Private Key）**。

```
密钥对：
  公钥：可以公开给任何人
  私钥：只有自己知道，保密

加密场景（机密性）：
  发送方用接收方的公钥加密
  接收方用自己的私钥解密

  明文 ──用B的公钥加密──► 密文 ────► 密文 ──用B的私钥解密──► 明文
                              只有 B 的私钥能解开
```

| 优点 | 缺点 |
|------|------|
| 解决了密钥分发问题（公钥可以公开） | 速度慢（比对称加密慢 100~1000 倍） |
| 密钥数量少（n 个人只需 n 对密钥） | 密文比明文长（至少一个密钥长度） |
| 可以实现数字签名（不可否认性） | 密钥长度更长才能达到同等安全 |

### 3.2 常见非对称加密算法

| 算法 | 典型密钥长度 | 安全强度 | 速度 | 用途 | 现状 |
|------|-------------|---------|------|------|------|
| **RSA** | 2048/3072/4096 位 | 中~高 | 慢 | 加密、签名、密钥交换 | ✅ 主流 |
| **ECC（椭圆曲线）** | 256/384/521 位 | 很高 | 较快 | 加密、签名、密钥交换 | ✅ 推荐（新系统优先） |
| **DH** | 2048/3072 位 | 中~高 | 中 | 密钥交换 | 广泛使用 |
| **ECDH** | 256/384 位 | 很高 | 快 | 密钥交换（椭圆曲线版 DH） | ✅ 推荐 |
| **DSA** | 1024/2048 位 | 低~中 | 中 | 仅用于数字签名 | ⚠️ 逐步淘汰 |
| **ECDSA** | 256/384 位 | 很高 | 快 | 数字签名（ECC 版本） | ✅ 推荐 |
| **Ed25519** | 256 位 | 很高 | 很快 | 数字签名 | ✅ 推荐 |
| **SM2** | 256 位 | 高 | 较快 | 加密、签名（国密） | 中国标准 |

### 3.3 RSA 详解

**RSA** 是最经典的非对称加密算法，1977 年由 Rivest、Shamir、Adleman 三人发明，基于大整数分解的数学难题。

| 密钥长度 | 等效对称密钥强度 | 安全性 | 建议 |
|---------|----------------|--------|------|
| 1024 位 | ~80 位 | ❌ 不安全 | 不再使用 |
| 2048 位 | ~112 位 | ⚠️ 勉强安全 | 最低要求，新系统建议更长 |
| 3072 位 | ~128 位 | ✅ 安全 | 推荐 |
| 4096 位 | ~152 位 | ✅ 很安全 | 高安全要求 |

**RSA 的用途**：
1. **加密**：用公钥加密，私钥解密（但只能加密短数据，小于密钥长度）
2. **签名**：用私钥签名，公钥验证
3. **密钥交换**：用公钥加密对称密钥，发给对方

> RSA 加密为什么只能加密短数据？因为 RSA 加密的结果长度和密钥长度一样（2048 位密钥 → 256 字节密文），而且明文必须小于密钥长度（减去 padding 后更少）。所以 RSA 通常只用来加密对称密钥，而不是加密实际数据。

### 3.4 ECC（椭圆曲线加密）

**ECC（Elliptic Curve Cryptography）** 基于椭圆曲线离散对数难题，比 RSA 用更短的密钥达到同等安全强度。

| 对称密钥强度 | RSA 密钥长度 | ECC 密钥长度 |
|-------------|-------------|-------------|
| 80 位 | 1024 位 | 160 位 |
| 112 位 | 2048 位 | 224 位 |
| 128 位 | 3072 位 | 256 位 |
| 192 位 | 7680 位 | 384 位 |
| 256 位 | 15360 位 | 512 位 |

**ECC 的优势**：
- ✅ 密钥短，安全强度高（256 位 ECC ≈ 3072 位 RSA）
- ✅ 计算速度快
- ✅ 存储和带宽占用小
- ✅ 特别适合移动设备、物联网等资源受限环境

**常见 ECC 曲线**：

| 曲线 | 位数 | 说明 |
|------|------|------|
| **P-256** / secp256r1 | 256 位 | NIST 标准，最常用 |
| **P-384** / secp384r1 | 384 位 | 更高安全级 |
| **secp256k1** | 256 位 | 比特币使用 |
| **Curve25519** | 256 位 | 高性能，Ed25519/X25519 使用 |

> Ed25519（签名）和 X25519（密钥交换）是目前非常推荐的椭圆曲线算法，性能好、安全性高、实现简单。

### 3.5 DH 密钥交换

**DH（Diffie-Hellman）密钥交换**：双方在不安全的信道上安全地协商出一个共享密钥，而不需要事先交换任何秘密。

```
DH 密钥交换原理：

  Alice                                 Bob
    │                                   │
    │  1. 各自有私有参数（a, b）          │
    │                                   │
    │  2. 计算公开值 A = g^a mod p       │
    │     计算公开值 B = g^b mod p       │
    │                                   │
    │  3. 交换公开值                     │
    │──── A ──────────────────────────► │
    │◄────────────────────────── B ──── │
    │                                   │
    │  4. 计算共享密钥                   │
    │     s = B^a mod p                 │
    │     s = A^b mod p                 │
    │                                   │
    └──────► 两人算出的 s 是一样的 ◄─────┘

数学保证：B^a = (g^b)^a = g^(ab) = (g^a)^b = A^b
```

| 特性 | 说明 |
|------|------|
| **作用** | 安全地协商共享密钥 |
| **安全性基础** | 离散对数难题 |
| **注意** | DH 本身不提供身份认证，容易遭受中间人攻击 |
| **解决方法** | 配合数字签名使用（如 TLS 中的 DHE-RSA、ECDHE-ECDSA） |

**ECDHE**：椭圆曲线版本的 DH，密钥更短、速度更快，是 TLS 1.3 的默认密钥交换方式。

> **前向保密（Forward Secrecy / Perfect Forward Secrecy，PFS）**：即使长期私钥泄露，之前的会话密钥也不会被破解。DH/ECDH 密钥交换每次都生成新的临时密钥，所以有前向保密性。这是 TLS 推荐用 DHE/ECDHE 而不是 RSA 密钥交换的重要原因。

## 四、哈希算法

### 4.1 基本概念

**哈希算法（Hash Algorithm）**，也叫**散列算法**、**摘要算法**：把任意长度的输入通过数学变换变成固定长度的输出（哈希值/摘要）。

```
任意输入 ──► 哈希算法 ──► 固定长度输出（哈希值/摘要）

例：
  SHA-256("hello") = 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

**哈希算法的特性**：

| 特性 | 说明 |
|------|------|
| **单向性** | 从哈希值无法反推出原始输入 |
| **定长输出** | 无论输入多长，输出长度固定 |
| **雪崩效应** | 输入的微小变化导致输出完全不同 |
| **抗碰撞性** | 很难找到两个不同的输入有相同的哈希值 |
| **确定性** | 相同的输入永远得到相同的输出 |

### 4.2 常见哈希算法

| 算法 | 输出长度 | 安全强度 | 碰撞攻击 | 现状 |
|------|---------|---------|---------|------|
| **MD5** | 128 位 | 极低 | ✅ 已实现碰撞 | ❌ 已废弃，不用于安全场景 |
| **SHA-1** | 160 位 | 低 | ✅ 已实现碰撞 | ❌ 逐步淘汰中 |
| **SHA-256** | 256 位 | 高 | ❌ 未攻破 | ✅ 推荐 |
| **SHA-384** | 384 位 | 很高 | ❌ 未攻破 | ✅ 更高安全需求 |
| **SHA-512** | 512 位 | 很高 | ❌ 未攻破 | ✅ 最高安全需求 |
| **SHA-3** | 224/256/384/512 位 | 很高 | ❌ 未攻破 | ✅ 新一代标准 |
| **SM3** | 256 位 | 高 | ❌ 未攻破 | 中国国密标准 |

> ⚠️ **安全警告**：
> - **MD5**：碰撞攻击已完全实现，**绝对不能用于安全场景**（如数字签名、证书、密码哈希）。可用于非安全场景（如文件完整性校验的辅助）。
> - **SHA-1**：碰撞攻击已实现，**应尽快迁移到 SHA-256 及以上**。
> - 新系统应直接使用 **SHA-256** 或更高。

### 4.3 哈希的常见用途

| 用途 | 说明 |
|------|------|
| **数据完整性校验** | 下载文件后比对哈希值，确认文件没被篡改 |
| **数字签名** | 先对数据哈希，再对哈希值签名（提高效率） |
| **消息认证码（HMAC）** | 带密钥的哈希，认证+完整性 |
| **密码存储** | 密码哈希后存储（但不能直接用 SHA-256，需要加盐+慢哈希） |
| **区块链** | 区块哈希、Merkle Tree |
| **去重/索引** | 用哈希值作为唯一标识 |

### 4.4 密码哈希

> ⚠️ **重要**：普通哈希算法（MD5、SHA-1、SHA-256）**不适合直接用来存密码**！因为它们太快了，攻击者可以用 GPU 每秒计算几十亿次，暴力破解很容易。

**安全的密码哈希算法**（慢哈希、加盐、抗暴力破解）：

| 算法 | 说明 | 推荐度 |
|------|------|--------|
| **bcrypt** | 基于 Blowfish，可调计算成本 | ✅ 推荐 |
| **scrypt** | 内存难函数，抗 GPU/ASIC 攻击 | ✅ 推荐 |
| **Argon2** | 密码哈希竞赛冠军，可调时间/内存/并行度 | ✅ 首选推荐 |
| **PBKDF2** | 用 HMAC 迭代多次 | ✅ 可用（兼容性好） |
| **SHA-256 + 盐** | — | ❌ 不够安全（还是太快） |
| **MD5 / SHA-1** | — | ❌ 极不安全 |

**为什么加盐？**

如果直接用 SHA-256 存密码，相同密码的哈希值相同——攻击者可以用彩虹表（预先算好的哈希-密码对照表）快速反查。

加盐（Salt）就是在密码哈希前加一个随机字符串，这样即使密码相同，盐不同，哈希值也不同。

```
不安全：hash(password)                    ← 相同密码 = 相同哈希
安全：  hash(salt + password)             ← 每个人盐不同，哈希不同
更安全：bcrypt(password, cost_factor)    ← 自带盐 + 计算慢
```

## 五、消息认证码

### 5.1 什么是 MAC

**MAC（Message Authentication Code，消息认证码）**：带密钥的哈希，同时提供**完整性**和**身份认证**。

```
发送方：
  消息 + 共享密钥 ──► MAC 算法 ──► MAC 值
  把「消息 + MAC 值」一起发给接收方

接收方：
  收到的消息 + 共享密钥 ──► MAC 算法 ──► 计算出的 MAC 值
  比较计算值和收到的 MAC 值
  → 一致：消息完整，且来自正确的发送方
  → 不一致：消息被篡改或来源不可信
```

| 对比 | 哈希（Hash） | 消息认证码（MAC） |
|------|------------|-----------------|
| **密钥** | 不需要 | 需要共享密钥 |
| **完整性** | ✅ 提供 | ✅ 提供 |
| **身份认证** | ❌ 不提供 | ✅ 提供 |
| **抗抵赖** | ❌ | ❌（双方都有密钥，无法证明是谁发的） |

### 5.2 HMAC

**HMAC（Hash-based MAC，基于哈希的消息认证码）**：最常用的 MAC 算法，用哈希算法（如 SHA-256）构造。

```
HMAC(K, m) = H( (K' XOR opad) || H( (K' XOR ipad) || m ) )

其中：
  K  = 密钥
  K' = 填充后的密钥（块大小）
  H  = 哈希函数（SHA-256 等）
  ipad = 内层填充（0x36 重复）
  opad = 外层填充（0x5C 重复）
```

| 算法 | 说明 |
|------|------|
| HMAC-MD5 | 不推荐（MD5 不安全） |
| HMAC-SHA1 | 不推荐（SHA-1 不安全） |
| **HMAC-SHA256** | 推荐，最常用 |
| **HMAC-SHA512** | 更高安全需求 |

> HMAC 安全性高的原因：不是简单的"密钥+消息"哈希，而是用了双层哈希和异或填充，抵抗了长度扩展攻击等问题。

### 5.3 CMAC

**CMAC（Cipher-based MAC，基于密码的 MAC）**：用对称加密算法（如 AES）构造的 MAC。

| 对比 | HMAC | CMAC |
|------|------|------|
| **基础** | 哈希算法 | 对称加密算法 |
| **典型算法** | HMAC-SHA256 | AES-CMAC |
| **用途** | 通用 | 资源受限环境（如 IoT）、某些协议 |

### 5.4 MAC vs 数字签名

| 特性 | MAC | 数字签名 |
|------|-----|---------|
| **密钥** | 对称密钥（双方共享） | 非对称密钥对（私钥签名，公钥验证） |
| **完整性** | ✅ | ✅ |
| **身份认证** | ✅ | ✅ |
| **不可否认性** | ❌（双方都能生成） | ✅（只有私钥持有者能签名） |
| **速度** | 快 | 慢 |
| **密钥管理** | 需要共享密钥 | 需要公钥基础设施（PKI） |

## 六、数字签名与 PKI

### 6.1 数字签名原理

**数字签名（Digital Signature）**：用私钥对消息的哈希值进行加密（签名），任何人都可以用对应的公钥验证签名的有效性。

```
签名过程（发送方）：
  1. 计算消息的哈希值：H = Hash(message)
  2. 用发送方的私钥加密哈希值：Signature = Sign(private_key, H)
  3. 把「消息 + 签名」一起发送

验证过程（接收方）：
  1. 计算收到消息的哈希值：H' = Hash(received_message)
  2. 用发送方的公钥解密签名，得到原始哈希：H = Verify(public_key, Signature)
  3. 比较 H 和 H'
     → 相同：签名有效（消息完整 + 来自正确的私钥持有者）
     → 不同：签名无效（消息被篡改或不是正确的签名者）
```

**数字签名提供的安全属性**：

| 属性 | 说明 |
|------|------|
| **完整性** | 消息被篡改，签名就验证不通过 |
| **身份认证** | 只有私钥持有者能产生有效签名 |
| **不可否认性** | 签名者不能否认自己签过名（因为只有他有私钥） |

### 6.2 常见数字签名算法

| 算法 | 典型密钥长度 | 安全性 | 速度 | 现状 |
|------|-------------|--------|------|------|
| **RSA 签名** | 2048/3072/4096 位 | 中~高 | 慢 | 广泛使用 |
| **DSA** | 1024/2048 位 | 低~中 | 中 | 逐步淘汰 |
| **ECDSA** | 256/384 位 | 很高 | 快 | 推荐 |
| **Ed25519** | 256 位 | 很高 | 很快 | 推荐（高性能） |
| **SM2 签名** | 256 位 | 高 | 较快 | 中国国密 |

### 6.3 PKI 与数字证书

**问题**：怎么确认一个公钥真的属于某个人/某个网站？可能有人伪造公钥。

**答案**：**PKI（Public Key Infrastructure，公钥基础设施）**——通过可信的第三方（CA）来证明公钥的归属。

```
PKI 信任链：

  根 CA（最顶层，所有人信任）
    │  用根私钥签名颁发中级 CA 证书
    ▼
  中级 CA
    │  用中级私钥签名颁发终端实体证书
    ▼
  服务器证书（网站的公钥 + 域名 + CA 签名）

验证过程：
  浏览器收到网站证书 → 用中级 CA 公钥验证证书签名 → 
  用根 CA 公钥验证中级 CA 证书签名 → 根 CA 是内置信任的
  → 整链都有效 → 网站证书可信 → 公钥可信
```

#### （1）PKI 组成

| 组件 | 英文 | 作用 |
|------|------|------|
| **证书颁发机构** | CA（Certificate Authority） | 颁发和管理数字证书，是信任的根 |
| **注册机构** | RA（Registration Authority） | 验证申请者身份，代 CA 处理申请 |
| **数字证书** | Digital Certificate | 绑定公钥和身份，由 CA 签名 |
| **证书吊销列表** | CRL（Certificate Revocation List） | 列出被提前吊销的证书 |
| **在线证书状态协议** | OCSP（Online Certificate Status Protocol） | 在线查询单个证书的状态 |
| **证书策略** | CP / CPS | 证书颁发的策略和操作规程 |

#### （2）X.509 证书

**X.509** 是数字证书的标准格式，最常见的版本是 v3。

| 字段 | 说明 |
|------|------|
| **版本** | X.509 v1 / v2 / v3 |
| **序列号** | CA 分配的唯一编号 |
| **签名算法** | 证书签名用的算法（如 SHA256withRSA） |
| **颁发者** | 颁发证书的 CA 名称 |
| **有效期** | 生效时间 + 过期时间 |
| **主题** | 证书持有者的名称（域名/组织等） |
| **主题公钥信息** | 公钥 + 公钥算法 |
| **扩展** | v3 扩展（SAN、密钥用途、基本约束等） |
| **签名** | CA 对证书内容的签名 |

**证书常见格式**：

| 格式 | 扩展名 | 编码 | 说明 |
|------|--------|------|------|
| **PEM** | .pem / .crt / .cer | Base64 | 最常见，文本格式，`-----BEGIN...-----` |
| **DER** | .der / .cer | 二进制 | 二进制格式，Windows 常用 |
| **PKCS#7** | .p7b / .p7c | Base64/二进制 | 证书链，不含私钥 |
| **PKCS#12** | .pfx / .p12 | 二进制 | 包含证书 + 私钥，有密码保护 |

## 七、安全协议

### 7.1 TLS / SSL

**TLS（Transport Layer Security，传输层安全）** 和它的前身 **SSL（Secure Sockets Layer）** 是目前最重要的安全协议，用于在两个通信方之间提供加密的、认证的、完整的连接。

| 版本 | 年份 | 安全性 | 现状 |
|------|------|--------|------|
| SSL 1.0 | — | — | 未公开发布 |
| SSL 2.0 | 1995 | ❌ 不安全 | 已废弃 |
| SSL 3.0 | 1996 | ❌ 不安全 | 已废弃（POODLE 漏洞） |
| TLS 1.0 | 1999 | ⚠️ 弱 | 已废弃（PCI DSS 要求禁用） |
| TLS 1.1 | 2006 | ⚠️ 弱 | 已废弃 |
| TLS 1.2 | 2008 | ✅ 安全 | 目前主流，广泛支持 |
| TLS 1.3 | 2018 | ✅ 很安全 | 推荐，性能更好 |

> ⚠️ **安全警告**：SSL 3.0、TLS 1.0、TLS 1.1 都已经不安全了，新系统应只启用 TLS 1.2 和 TLS 1.3。

#### TLS 提供的安全保障

| 保障 | 实现方式 |
|------|---------|
| **机密性** | 对称加密（AES-GCM、ChaCha20 等） |
| **完整性** | MAC / AEAD 认证标签 |
| **身份认证** | 数字证书 + 数字签名（服务器端，可选客户端） |
| **前向保密** | DHE / ECDHE 密钥交换（可选，推荐开启） |

#### TLS 握手（简化）

```
TLS 1.2 完整握手（简化版）：

  Client                                    Server
    │                                        │
    │  1. Client Hello                        │
    │  （支持的密码套件、随机数、扩展）        │
    ├───────────────────────────────────────►│
    │                                        │
    │  2. Server Hello                        │
    │  （选定的密码套件、随机数）              │
    │  3. Certificate                         │
    │  （服务器证书链）                       │
    │  4. Server Key Exchange（可选）         │
    │  （DHE/ECDHE 的服务器参数）             │
    │  5. Server Hello Done                   │
    │◄───────────────────────────────────────┤
    │                                        │
    │  6. Client Key Exchange                 │
    │  （预主密钥 / 客户端 DH 参数）          │
    ├───────────────────────────────────────►│
    │                                        │
    │  双方各自计算出会话密钥                  │
    │                                        │
    │  7. Change Cipher Spec + Finished       │
    ├───────────────────────────────────────►│
    │  8. Change Cipher Spec + Finished       │
    │◄───────────────────────────────────────┤
    │                                        │
    │  之后用会话密钥加密应用数据              │
```

> TLS 1.3 做了很大优化：握手从 2-RTT 变成 1-RTT（甚至 0-RTT 恢复），删除了很多不安全的算法和扩展，更安全也更快。

### 7.2 HTTPS

**HTTPS（HTTP Secure）** = HTTP + TLS/SSL

```
  HTTP 明文   →  被 TLS 加密  →  在网络中传输的是密文

  应用层：HTTP
  安全层：TLS/SSL
  传输层：TCP
  网络层：IP
```

**HTTPS 的默认端口**：443（HTTP 默认 80）

**HTTPS 的工作流程**：
1. 客户端连接服务器 443 端口
2. 进行 TLS 握手（协商算法、验证证书、交换密钥）
3. 握手成功后，HTTP 请求和响应都通过 TLS 加密传输

### 7.3 SSH

**SSH（Secure Shell，安全外壳）**：用于安全远程登录和其他安全网络服务的协议，替代不安全的 Telnet、FTP 等。

| 版本 | 说明 |
|------|------|
| SSH 1 | 旧版本，有安全漏洞，已淘汰 |
| SSH 2 | 当前标准，更安全 |

**SSH 提供的功能**：
- 安全远程登录（替代 telnet）
- 安全文件传输（SFTP、SCP，替代 ftp）
- 端口转发 / 隧道（加密任意 TCP 连接）
- X11 转发（远程运行图形程序）

**SSH 认证方式**：

| 方式 | 说明 | 安全性 |
|------|------|--------|
| **密码认证** | 用户名+密码 | 中（易被暴力破解、钓鱼） |
| **公钥认证** | 客户端私钥签名，服务器用公钥验证 | 高（推荐） |
| **主机认证** | 验证服务器身份（第一次连接时确认指纹） | 中（TOFU 模型） |
| **基于主机** | 信任特定主机上的所有用户 | 低~中 |
| **多因素** | 密码 + 公钥 + 其他 | 很高 |

### 7.4 IPsec

**IPsec（IP Security）**：在 IP 层提供安全服务的协议套件，常用于 VPN。

| 协议 | 作用 | 提供 |
|------|------|------|
| **AH（Authentication Header）** | 认证头 | 完整性 + 数据源认证 + 防重放 |
| **ESP（Encapsulating Security Payload）** | 封装安全载荷 | 机密性 + 完整性 + 认证 + 防重放 |

> AH 不提供加密，所以现在基本都用 ESP。AH 在 NAT 环境下有问题（因为 AH 校验包括 IP 首部，NAT 会改 IP）。

**两种模式**：

| 模式 | 说明 | 典型应用 |
|------|------|---------|
| **传输模式（Transport）** | 只加密 IP 数据报的 payload，IP 首部不变 | 主机到主机 |
| **隧道模式（Tunnel）** | 整个 IP 数据报被加密，再加新的 IP 首部 | 站点到站点 VPN、远程访问 VPN |

**IKE（Internet Key Exchange）**：IPsec 的密钥交换协议，用来安全地协商 IPsec 使用的密钥和安全参数。

| 版本 | 说明 |
|------|------|
| IKEv1 | 旧版本，两个阶段（主模式/野蛮模式 + 快速模式） |
| IKEv2 | 新版本，更简单、更快、更安全（推荐） |

### 7.5 DNSSEC

**DNSSEC（DNS Security Extensions）**：给 DNS 响应加上数字签名，确保 DNS 响应是真实的、未被篡改的。

| 问题 | DNSSEC 解决方法 |
|------|---------------|
| DNS 响应被篡改 | 用数字签名验证响应完整性 |
| DNS 欺骗/缓存投毒 | 签名验证失败就拒绝 |

**DNSSEC 不解决的问题**：
- ❌ 不加密 DNS 查询内容（保密性由 DoH/DoT 解决）
- ❌ 不保证域名一定存在
- ❌ 不解决 DDoS 问题

**DNSSEC 的信任链**：

```
根 DNS 签名 → TLD 签名 → 二级域名签名 → ...

验证：从根开始，逐级验证签名
      根是信任锚（Trust Anchor）
```

### 7.6 安全协议对比

| 协议 | 层级 | 主要用途 | 机密性 | 认证 | 完整性 | 前向保密 |
|------|------|---------|--------|------|--------|---------|
| **TLS/SSL** | 传输层之上 | Web、邮件等通用加密 | ✅ | ✅ | ✅ | ✅（DHE/ECDHE） |
| **HTTPS** | 应用层 | HTTP 加密（=HTTP+TLS） | ✅ | ✅ | ✅ | ✅ |
| **SSH** | 应用层 | 远程登录、文件传输 | ✅ | ✅ | ✅ | ✅ |
| **IPsec** | 网络层 | VPN、网络层加密 | ✅ | ✅ | ✅ | ✅ |
| **DNSSEC** | 应用层 | DNS 数据完整性 | ❌ | ✅ | ✅ | — |
| **DoH / DoT** | 应用层 | DNS 查询加密 | ✅ | ✅ | ✅ | — |

## 八、Linux 实践

### 8.1 OpenSSL

**OpenSSL** 是最常用的开源密码学工具库，支持几乎所有加密算法和协议。

```bash
# ===== 查看版本 =====
openssl version
openssl version -a          # 详细信息（编译选项、支持的算法等）

# ===== 哈希计算 =====
openssl dgst -md5 file.txt
openssl dgst -sha1 file.txt
openssl dgst -sha256 file.txt
openssl dgst -sha512 file.txt
openssl dgst -sha3-256 file.txt

# 或用简写
openssl sha256 file.txt
openssl md5 file.txt

# ===== 对称加密 =====
# AES-256-CBC 加密文件
openssl enc -aes-256-cbc -salt -in file.txt -out file.enc
# 解密
openssl enc -aes-256-cbc -d -in file.enc -out file.txt

# AES-256-GCM（需要指定标签，较复杂，推荐用 3.0+ 版本）
# openssl enc -aes-256-gcm -in file.txt -out file.enc -K <key> -iv <iv>

# Base64 编码输出
openssl enc -aes-256-cbc -salt -a -in file.txt -out file.enc.b64

# ===== 非对称加密（RSA） =====
# 生成 RSA 私钥（2048 位）
openssl genrsa -out private.key 2048

# 从私钥提取公钥
openssl rsa -in private.key -pubout -out public.key

# 用公钥加密（只能加密短数据）
openssl rsautl -encrypt -inkey public.key -pubin -in msg.txt -out msg.enc

# 用私钥解密
openssl rsautl -decrypt -inkey private.key -in msg.enc -out msg.txt

# ===== 数字签名 =====
# 用私钥签名（先哈希再签名）
openssl dgst -sha256 -sign private.key -out file.sig file.txt

# 用公钥验证签名
openssl dgst -sha256 -verify public.key -signature file.sig file.txt
# 输出 Verified OK 或 Verification Failure

# ===== HMAC =====
openssl dgst -sha256 -hmac "secret_key" file.txt
openssl dgst -sha512 -hmac "mykey" file.txt

# ===== 证书操作 =====
# 查看证书信息
openssl x509 -in cert.pem -text -noout
openssl x509 -in cert.pem -subject -noout     # 主题
openssl x509 -in cert.pem -issuer -noout      # 颁发者
openssl x509 -in cert.pem -dates -noout       # 有效期
openssl x509 -in cert.pem -purpose -noout     # 用途
openssl x509 -in cert.pem -pubkey -noout      # 公钥

# 验证证书链
openssl verify -CAfile ca.pem cert.pem
openssl verify -CAfile ca-bundle.pem server.pem

# 生成自签名证书（测试用）
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes

# 生成 CSR（证书签名请求）
openssl req -new -newkey rsa:2048 -keyout private.key -out request.csr -nodes

# 查看 CSR
openssl req -in request.csr -text -noout

# 证书格式转换
# PEM → DER
openssl x509 -in cert.pem -outform DER -out cert.der
# DER → PEM
openssl x509 -in cert.der -inform DER -out cert.pem
# PFX → PEM（提取证书和私钥）
openssl pkcs12 -in cert.pfx -out cert_and_key.pem -nodes

# ===== 测试 TLS 连接 =====
openssl s_client -connect example.com:443
openssl s_client -connect example.com:443 -servername example.com   # SNI
openssl s_client -connect example.com:443 -tls1_2                   # 指定 TLS 1.2
openssl s_client -connect example.com:443 -tls1_3                   # 指定 TLS 1.3
openssl s_client -connect example.com:443 -CAfile ca-bundle.pem     # 指定 CA 证书
openssl s_client -connect example.com:443 -showcerts               # 显示完整证书链

# 查看支持的密码套件
openssl ciphers -v
openssl ciphers -v 'TLSv1.2'
```

> ⚠️ **安全警告**：
> - 不要使用 DES、3DES、RC4、MD5、SHA-1 等已不安全的算法
> - 生成密钥时使用足够的长度（RSA 至少 2048 位，推荐 3072 位；ECC 256 位起）
> - 私钥文件权限应该是 600（只有所有者能读写）
> - 自签名证书只用于测试环境，生产环境要用正规 CA 颁发的证书

### 8.2 SSH 密钥管理

```bash
# ===== 生成密钥对 =====
# 默认 RSA 2048 位（不推荐，太短了）
ssh-keygen

# 推荐：Ed25519（高性能、高安全）
ssh-keygen -t ed25519 -C "your_email@example.com"

# RSA 4096 位（兼容性好）
ssh-keygen -t rsa -b 4096 -C "your_email@example.com"

# ECDSA P-384
ssh-keygen -t ecdsa -b 384

# 指定文件名和密码
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_custom -N "passphrase"

# ===== 查看公钥指纹 =====
ssh-keygen -lf ~/.ssh/id_ed25519.pub
ssh-keygen -lf ~/.ssh/id_ed25519.pub -E sha256   # SHA-256 指纹
ssh-keygen -lf ~/.ssh/id_ed25519.pub -E md5      # MD5 指纹（旧格式）

# ===== 复制公钥到服务器 =====
ssh-copy-id user@server.example.com
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@server.example.com

# 手动方式
cat ~/.ssh/id_ed25519.pub | ssh user@server 'mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys'

# ===== 密钥格式转换 =====
# OpenSSH 格式 → PKCS#8 格式
ssh-keygen -e -m PKCS8 -f ~/.ssh/id_ed25519.pub

# PKCS#8 → OpenSSH
ssh-keygen -i -m PKCS8 -f pubkey.pem

# ===== known_hosts 管理 =====
# 查看服务器指纹
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

# 删除 known_hosts 中的某个主机
ssh-keygen -R server.example.com

# 搜索 known_hosts
ssh-keygen -F server.example.com

# ===== SSH 代理（避免重复输密码） =====
# 启动代理
eval $(ssh-agent)

# 添加密钥到代理
ssh-add ~/.ssh/id_ed25519
ssh-add -l                    # 列出已添加的密钥
ssh-add -D                    # 删除所有密钥
```

> **SSH 安全最佳实践**：
> - ✅ 使用公钥认证，禁用密码登录
> - ✅ 禁用 root 直接登录
> - ✅ 使用 Ed25519 或 RSA-4096 密钥
> - ✅ 密钥设置强密码（passphrase）
> - ✅ 使用 ssh-agent 管理密钥
> - ✅ 限制可登录的用户（AllowUsers / AllowGroups）
> - ✅ 更改默认端口（隐蔽性辅助，不是主要安全手段）
> - ✅ 配置失败次数限制（MaxAuthTries）
> - ✅ 配置空闲超时（ClientAliveInterval）
> - ⚠️ 第一次连接服务器时验证主机指纹，防止中间人

### 8.3 GPG（GNU Privacy Guard）

**GPG（GnuPG）**：OpenPGP 标准的开源实现，用于文件加密、数字签名、邮件加密等。

```bash
# 安装：apt install gnupg / yum install gnupg2

# ===== 密钥管理 =====
# 生成密钥对（交互式）
gpg --full-gen-key
gpg --gen-key                  # 快捷生成

# 列出密钥
gpg --list-keys
gpg --list-secret-keys
gpg --list-public-keys

# 查看密钥指纹
gpg --fingerprint user@example.com

# 导出公钥
gpg --export -a user@example.com > public.key   # ASCII 格式
gpg --export user@example.com > public.gpg      # 二进制格式

# 导出私钥（⚠️ 妥善保管！）
gpg --export-secret-keys -a user@example.com > private.key

# 导入公钥
gpg --import public.key
gpg --import received_pubkey.gpg

# 删除密钥
gpg --delete-key user@example.com               # 删除公钥
gpg --delete-secret-key user@example.com         # 删除私钥

# ===== 加密解密 =====
# 用公钥加密文件（只有对应私钥能解密）
gpg --encrypt --recipient user@example.com file.txt
gpg -e -r user@example.com file.txt              # 简写
# 输出 file.txt.gpg

# 用私钥解密
gpg --decrypt file.txt.gpg
gpg -d file.txt.gpg
gpg -d file.txt.gpg -o file_decrypted.txt        # 指定输出文件

# 对称加密（用密码加密，不需要密钥对）
gpg --symmetric file.txt
gpg -c file.txt

# ===== 数字签名 =====
# 签名（附签，签名在文件里）
gpg --sign file.txt
gpg -s file.txt

# 分离签名（单独的签名文件）
gpg --detach-sign file.txt
gpg -b file.txt
# 输出 file.txt.sig

# 明文签名（内容可读，签名附在后面）
gpg --clearsign file.txt

# 验证签名
gpg --verify file.txt.gpg
gpg --verify file.txt.sig file.txt

# ===== 信任模型 =====
# 签名他人密钥（表示你信任这个密钥属于这个人）
gpg --sign-key other@example.com

# 信任级别设置
gpg --edit-key other@example.com
# 然后输入 trust 设置信任级别

# ===== 密钥服务器 =====
# 上传公钥到密钥服务器
gpg --keyserver keyserver.ubuntu.com --send-keys KEYID

# 从密钥服务器下载公钥
gpg --keyserver keyserver.ubuntu.com --recv-keys KEYID

# 搜索密钥
gpg --keyserver keyserver.ubuntu.com --search-key "name"
```

> ⚠️ **安全警告**：
> - 私钥是最高机密，务必妥善保管（加密存储、离线备份）
> - 密钥密码（passphrase）要足够强
> - 密钥有有效期，定期轮换
> - 验证他人公钥的真实性（最好通过线下/电话等安全渠道验证指纹）
> - 不要信任来源不明的公钥
