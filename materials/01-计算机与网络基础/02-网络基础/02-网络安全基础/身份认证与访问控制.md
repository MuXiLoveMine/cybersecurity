## 一、身份认证基础

### 1.1 认证与授权的区别

| 概念 | 英文 | 含义 | 回答的问题 |
|------|------|------|-----------|
| **身份认证** | Authentication | 验证"你是谁" | "你真的是你声称的那个人吗？" |
| **授权** | Authorization | 决定"你能做什么" | "你有权限访问这个资源吗？" |
| **审计** | Accounting / Auditing | 记录"你做了什么" | "谁在什么时候做了什么操作？" |

> 三者合称 **AAA**（Authentication, Authorization, Accounting），是身份管理系统的三个核心环节。

```
用户访问资源的流程：

  1. 认证（Authentication）→ 确认身份
        ↓
  2. 授权（Authorization）→ 检查权限
        ↓
  3. 访问（Access）→ 允许/拒绝
        ↓
  4. 审计（Accounting）→ 记录操作
```

### 1.2 认证因素

**认证因素（Authentication Factor）**：用来验证身份的依据，分为几大类。

| 因素类型 | 英文 | 说明 | 典型例子 |
|---------|------|------|---------|
| **知识因素** | Something you know | 你知道的信息 | 密码、PIN、密保问题、图案 |
| **拥有因素** | Something you have | 你拥有的物品 | 手机、U 盾、智能卡、硬件令牌 |
| **生物特征** | Something you are | 你的生理特征 | 指纹、人脸、虹膜、声纹、掌纹 |
| **位置因素** | Somewhere you are | 你所在的位置 | IP 地址、GPS 位置、网络位置 |
| **行为特征** | Something you do | 你的行为模式 | 击键习惯、签名、步态 |

| 认证强度 | 因素数量 | 说明 |
|---------|---------|------|
| **单因素认证（SFA）** | 1 种 | 只用密码，最不安全 |
| **双因素认证（2FA）** | 2 种不同类型 | 密码 + 手机验证码，较安全 |
| **多因素认证（MFA）** | 2 种以上 | 密码 + U 盾 + 指纹，最安全 |

> ⚠️ **注意**：必须是**不同类型**的因素才算多因素。例如"密码 + 邮箱验证码"——邮箱也要用密码登录，严格来说可能都属于"知识因素"（你知道邮箱密码），所以不算真正的双因素。真正的 2FA 应该是跨类别的，如"密码（知识）+ 硬件令牌（拥有）"。

### 1.3 认证系统的安全原则

| 原则 | 说明 |
|------|------|
| **最小权限** | 认证通过后只授予必要的最小权限 |
| **强制身份验证** | 每次特权操作都应验证身份（sudo 就是例子） |
| **会话管理** | 会话超时、登出机制、防会话劫持 |
| **审计追踪** | 记录所有认证尝试（成功和失败） |
| **失败处理** | 登录失败次数限制、账号锁定、速率限制 |
| **密码安全** | 强密码策略、安全存储（加盐哈希）、定期更换 |
| **MFA** | 重要系统启用多因素认证 |

## 二、认证方式详解

### 2.1 密码认证

| 优点 | 缺点 |
|------|------|
| 简单、成本低 | 容易被遗忘/泄露/钓鱼/暴力破解 |
| 不需要额外硬件 | 用户倾向用弱密码、重复密码 |
| 易于部署和使用 | 数据库泄露风险 |

**密码安全策略（符合等保/合规要求）**：

| 策略项 | 等保三级建议 | 说明 |
|--------|-------------|------|
| **最小长度** | ≥ 8 位 | 越长越安全，建议 12 位以上 |
| **复杂度** | 包含大写、小写、数字、特殊字符中至少 3 种 | 增加熵值 |
| **有效期** | ≤ 90 天 | 定期更换（业界有争议，但合规要求） |
| **历史密码** | 不能重复使用最近 5 次密码 | 防止循环使用 |
| **失败锁定** | 连续 5 次失败后锁定 | 防暴力破解 |
| **锁定时间** | ≥ 30 分钟或管理员解锁 | |
| **首次登录改密** | 强制 | 初始密码必须修改 |
| **禁止明文存储** | 必须加盐哈希 | 绝对不能明文或可逆加密存密码 |

> **关于定期更换密码的争议**：NIST 等机构近年的指南不再强制要求定期更换密码，因为用户倾向于在旧密码基础上做微小修改（如 password1 → password2），实际安全性提升有限。但国内等保等合规要求仍然有定期更换的要求。

**密码存储安全**：

| 存储方式 | 安全性 | 说明 |
|---------|--------|------|
| 明文存储 | ❌ 极差 | 数据库泄露 = 所有密码泄露 |
| 对称加密 | ❌ 差 | 密钥泄露 = 全部泄露 |
| 普通哈希（MD5/SHA） | ❌ 差 | 彩虹表/暴力破解容易 |
| 加盐哈希（SHA-256 + salt） | ⚠️ 一般 | 还是太快，GPU 可暴力破解 |
| bcrypt / scrypt / Argon2 | ✅ 推荐 | 慢哈希，抗暴力破解 |

### 2.2 令牌 / 一次性密码

| 类型 | 英文 | 说明 | 例子 |
|------|------|------|------|
| **短信验证码** | SMS OTP | 短信发送一次性密码 | 银行、网站登录 |
| **邮件验证码** | Email OTP | 邮件发送一次性密码 | 账号验证 |
| **TOTP** | Time-based OTP | 基于时间的一次性密码（30/60 秒一变） | Google Authenticator、微软 Authenticator |
| **HOTP** | HMAC-based OTP | 基于事件计数器的一次性密码 | 某些硬件令牌 |
| **硬件令牌** | Hardware Token | 物理设备生成动态密码 | RSA SecurID、动态口令牌 |
| **推送通知** | Push Notification | 手机 App 推送确认 | 微信/钉钉/企业微信登录确认 |

**TOTP 工作原理**：
```
1. 服务器和客户端共享一个密钥（Secret Key）
2. 每 30 秒（默认）用当前时间 + 密钥通过 HMAC 计算出一个 6 位数字
3. 用户输入这个数字，服务器用同样方法计算后比对
4. 时间窗口内（通常 ±1 个窗口）都算有效
```

| 认证方式 | 安全性 | 便捷性 | 成本 | 抗钓鱼 |
|---------|--------|--------|------|--------|
| 短信验证码 | 中 | 高 | 低 | ❌ 差（SIM 劫持、钓鱼网站输入） |
| 邮件验证码 | 中低 | 高 | 低 | ❌ 差 |
| TOTP（App） | 高 | 中 | 低 | ❌ 差（钓鱼网站可转发） |
| 硬件令牌 | 很高 | 中 | 中高 | ❌ 差（钓鱼网站可转发） |
| 推送确认 | 高 | 高 | 中 | ✅ 较好（显示登录信息） |
| U2F / WebAuthn | 很高 | 中 | 中 | ✅ 很好（绑定域名，防钓鱼） |

### 2.3 数字证书认证

| 优点 | 缺点 |
|------|------|
| 安全性高（基于非对称加密） | 需要 PKI 基础设施，部署复杂 |
| 防钓鱼（证书绑定域名） | 证书管理成本高 |
| 可以做双向认证 | 用户需要安装/携带证书 |

**常见应用**：
- SSL/TLS 服务器证书（HTTPS）
- 客户端证书（双向认证 VPN、网银 U 盾）
- 代码签名证书
- 邮件签名证书（S/MIME）

### 2.4 生物特征认证

| 类型 | 准确性 | 易用性 | 安全性 | 问题 |
|------|--------|--------|--------|------|
| **指纹** | 中~高 | 很高 | 中 | 指纹可以被复制、无法更换 |
| **人脸** | 中~高 | 很高 | 中 | 照片/视频攻击、种族偏见 |
| **虹膜** | 很高 | 中 | 很高 | 设备贵、接触隐私顾虑 |
| **声纹** | 低~中 | 高 | 低 | 易被录音模仿、受环境影响 |
| **掌纹/掌静脉** | 高 | 中 | 高 | 设备较贵 |
| **签名** | 低 | 高 | 低 | 易模仿、每次不一样 |

> ⚠️ **生物特征的特殊风险**：密码丢了可以换，但指纹、人脸丢了换不了。而且生物特征数据一旦泄露就是永久泄露。所以生物识别更适合作为辅助认证手段，而不是唯一手段。

### 2.5 多因素认证（MFA）

**MFA（Multi-Factor Authentication）**：同时使用两种或以上不同类型的认证因素。

```
为什么 MFA 更安全？

  攻击者要攻破：
  只有密码 → 偷到密码就行（钓鱼、泄露）
  密码 + 手机令牌 → 既要偷密码，又要拿到手机/令牌
  密码 + U 盾 + 指纹 → 需要同时突破三层防御

  每增加一个因素，攻击难度指数级上升
```

**常见 MFA 组合**：
- 密码 + TOTP（最常见，成本低）
- 密码 + 短信验证码（用户体验好，但 SIM 劫持风险）
- 密码 + 硬件令牌/U 盾（安全性最高）
- 密码 + 生物识别（便捷，但注意生物特征泄露风险）
- 密码 + 推送通知（体验好，企业常用）

### 2.6 认证方式对比总结

| 方式 | 安全性 | 便捷性 | 成本 | 防钓鱼 | 适合场景 |
|------|--------|--------|------|--------|---------|
| 密码 | 低 | 高 | 低 | ❌ 差 | 普通账户、配合 MFA |
| 短信 OTP | 中 | 高 | 低 | ❌ 差 | 辅助验证、非高安全场景 |
| TOTP App | 高 | 中 | 低 | ❌ 差 | 通用 MFA |
| 硬件令牌 | 很高 | 中 | 高 | ❌ 差 | 高安全要求 |
| U2F / WebAuthn | 很高 | 中 | 中 | ✅ 好 | 防钓鱼要求高 |
| 数字证书 | 很高 | 低 | 高 | ✅ 好 | 双向认证、VPN、网银 |
| 生物识别 | 中~高 | 很高 | 中~高 | — | 辅助认证、解锁设备 |
| 推送通知 | 高 | 很高 | 中 | ✅ 较好 | 企业 SSO |

## 三、授权模型

### 3.1 自主访问控制（DAC）

**DAC（Discretionary Access Control，自主访问控制）**：资源的所有者（创建者）可以自主决定谁能访问该资源，以及有什么权限。

| 特点 | 说明 |
|------|------|
| **控制权** | 资源所有者决定权限 |
| **灵活性** | 高，所有者可以自由分配 |
| **安全性** | 较低（用户可能错误配置权限） |
| **典型例子** | Linux/Unix 文件权限、Windows NTFS 权限 |

```
DAC 示例（Linux 文件权限）：

  alice 创建了一个文件 report.txt
  alice 可以决定：
    - bob 可以读
    - charlie 可以读写
    - 其他人不能访问

  权限由所有者（alice）自主决定 ← 这就是"自主"的含义
```

**优点**：灵活、易于实现、用户体验好
**缺点**：
- 安全性较低（用户可能误操作给错权限）
- 权限分散，难以统一管理和审计
- 容易出现权限泄露（用户把敏感文件分享给不该看的人）

### 3.2 强制访问控制（MAC）

**MAC（Mandatory Access Control，强制访问控制）**：系统（而非用户）根据安全级别强制控制访问。每个用户和每个资源都有安全标签，只有级别匹配才能访问。

| 特点 | 说明 |
|------|------|
| **控制权** | 系统强制，用户无法更改 |
| **灵活性** | 低，规则由管理员制定 |
| **安全性** | 很高 |
| **典型例子** | SELinux、军用多级安全系统 |

```
MAC 示例（安全标签）：

  安全级别：公开 < 内部 < 秘密 < 机密 < 绝密

  用户 alice 安全级别 = 秘密
  文件 A 安全级别 = 公开     → alice 可以读（向下读）
  文件 B 安全级别 = 秘密     → alice 可以读写
  文件 C 安全级别 = 机密     → alice 不能读（级别不够）

  安全规则由系统强制，alice 自己改不了文件的安全级别
```

**两种经典模型**：

| 模型 | 规则 | 说明 |
|------|------|------|
| **BLP（Bell-LaPadula）** | 下读上写（No Read Down, No Write Up） | 机密性模型，防止低级别用户读高级别数据 |
| **Biba** | 上读下写（No Read Up, No Write Down） | 完整性模型，防止低完整性数据污染高完整性数据 |

**优点**：安全性极高，适合高安全要求环境
**缺点**：
- 配置复杂，管理成本高
- 灵活性差，用户体验不好
- 不适合普通商业环境

### 3.3 基于角色的访问控制（RBAC）

**RBAC（Role-Based Access Control，基于角色的访问控制）**：权限分配给角色，角色分配给用户。用户通过角色获得权限。

```
RBAC 模型：

  用户 ──► 角色 ──► 权限

  例如：
    用户 alice → 角色「财务经理」 → 权限：查看报表、审批报销
    用户 bob   → 角色「普通员工」 → 权限：提交报销、查看自己信息
    用户 charlie → 角色「系统管理员」 → 权限：系统配置、用户管理
```

| 核心概念 | 英文 | 说明 |
|---------|------|------|
| **用户** | User | 人或系统账号 |
| **角色** | Role | 一组权限的集合（如"管理员""财务""审计"） |
| **权限** | Permission | 对资源的操作许可（如"读文件""删记录"） |
| **会话** | Session | 用户登录后激活某些角色 |

**RBAC 的三个层次**：

| 层次 | 说明 |
|------|------|
| **RBAC0（基础模型）** | 用户-角色-权限，核心三要素 |
| **RBAC1（角色分层）** | 角色有继承关系（如"总经理"继承"部门经理"的所有权限） |
| **RBAC2（约束模型）** | 增加约束（如互斥角色：不能同时是"申请者"和"审批者"） |
| **RBAC3（统一模型）** | RBAC1 + RBAC2，完整模型 |

**优点**：
- ✅ 权限管理简单直观（按角色管理）
- ✅ 人员变动时只改角色分配，不用逐个改权限
- ✅ 符合企业组织结构
- ✅ 易于审计和合规

**缺点**：
- 角色数量可能爆炸（角色泛滥）
- 细粒度权限控制不够灵活
- 跨部门、动态场景下不够用

### 3.4 基于属性的访问控制（ABAC）

**ABAC（Attribute-Based Access Control，基于属性的访问控制）**：根据各种属性（用户属性、资源属性、环境属性）和策略规则动态决定是否授权。

```
ABAC 模型：

  if (用户.部门 == "财务" AND 
      资源.密级 == "内部" AND 
      环境.时间 == 工作时间 AND 
      环境.IP == 公司内网) 
  then allow("读")

  用策略规则来定义：当满足什么条件时，允许什么操作
```

| 属性类型 | 例子 |
|---------|------|
| **用户属性** | 部门、职位、级别、安全级别 |
| **资源属性** | 文件密级、所属部门、创建者 |
| **环境属性** | 时间、IP 地址、设备类型、地理位置 |
| **动作属性** | 读、写、删除、审批 |

**优点**：
- ✅ 非常灵活，能实现复杂的动态权限控制
- ✅ 不需要预先定义所有角色（自适应）
- ✅ 适合细粒度、动态场景
- ✅ 零信任架构的核心技术之一

**缺点**：
- 策略编写和管理复杂
- 性能开销较大（每次都要计算）
- 审计和排错困难（为什么被拒绝？）

### 3.5 四种授权模型对比

| 维度 | DAC | MAC | RBAC | ABAC |
|------|-----|-----|------|------|
| **控制权** | 资源所有者 | 系统强制 | 管理员 | 策略规则 |
| **灵活性** | 高 | 低 | 中 | 很高 |
| **安全性** | 中低 | 很高 | 中高 | 高 |
| **管理复杂度** | 低 | 高 | 中 | 高 |
| **细粒度** | 中 | 中 | 中 | 很高 |
| **适合场景** | 文件系统、小型系统 | 军事、高安全环境 | 企业管理系统（最常用） | 动态、复杂场景、零信任 |
| **典型实现** | Linux 权限、Windows | SELinux、多级安全 | 企业应用、AD | 零信任网关、云平台 |

## 四、访问控制列表与权限

### 4.1 ACL（访问控制列表）

**ACL（Access Control List，访问控制列表）**：一组规则的列表，每条规则规定"谁可以对什么资源做什么操作"。

```
ACL 示例（文件权限）：

  文件：report.txt

  主体    权限
  alice   rwx（读写执行）
  bob     r--（只读）
  财务组   rw-（读写）
  其他人   ---（无权限）

  每条记录 = 主体 + 权限
```

| 术语 | 英文 | 说明 |
|------|------|------|
| **主体（Subject）** | Subject | 谁在访问（用户、组、角色） |
| **客体（Object）** | Object | 被访问的资源（文件、目录、数据库、API） |
| **权限（Permission）** | Permission | 可以做什么操作（读、写、执行等） |
| **ACE** | Access Control Entry | ACL 中的一条规则 |

### 4.2 权限类型

| 权限类型 | 说明 | 常见示例 |
|---------|------|---------|
| **读（Read）** | 查看/读取内容 | r、view、list |
| **写（Write）** | 修改/创建/删除 | w、modify、create、delete |
| **执行（Execute）** | 运行/执行 | x、run、execute |
| **管理（Admin）** | 配置/授权 | admin、manage、grant |
| **删除（Delete）** | 删除资源 | d、delete |

**Linux 文件权限（经典 DAC）**：

```
-rwxr-xr--  alice  finance  report.txt
│││││││││
│││││││└── 其他人（Others）：r--  只读
││││││└─── 组（Group）：r-x  读+执行
│││││└──── 所有者（User）：rwx  读写执行
││││└───── 特殊权限位（通常显示为 -，见 s/S/t/T）
│││└────── 执行位
││└─────── 写位
│└──────── 读位
└───────── 文件类型（-普通文件/d目录/l链接等）
```

### 4.3 ACL vs 能力（Capability）

两种权限管理思路：

| 模型 | 说明 | 例子 |
|------|------|------|
| **ACL（访问控制列表）** | 资源上记录"谁可以访问" | 文件的权限位、Windows ACL |
| **能力（Capability）** | 用户/进程持有"能力令牌"，令牌决定能访问什么 | Unix 文件描述符、密钥、Ticket |

```
ACL 视角：在每个门上贴一个名单，名单上的人可以进
能力视角：每个人拿着一串钥匙，有哪个门的钥匙就能进哪个门
```

| 对比 | ACL | 能力（Capability） |
|------|-----|-------------------|
| **视角** | 以资源为中心 | 以主体为中心 |
| **存储位置** | 资源上 | 主体上 |
| **查询问题** | "谁能访问这个资源？"好回答 | "这个用户能访问哪些资源？"好回答 |
| **撤销权限** | 容易（直接从列表里删除） | 难（要收回所有已颁发的令牌） |
| **传递** | 不容易传递 | 容易传递（把钥匙给别人就行） |
| **典型实现** | 文件系统权限、数据库表权限 | Kerberos Ticket、API Token |

## 五、身份管理协议与技术

### 5.1 单点登录（SSO）

**SSO（Single Sign-On，单点登录）**：用户只需登录一次，就可以访问多个相互独立的应用系统，不需要每次都登录。

```
SSO 工作原理：

  用户登录一次 → 获得全局会话 / 票据
    ↓
  访问应用 A → 用票据换取应用 A 的会话 → 直接访问
  访问应用 B → 用票据换取应用 B 的会话 → 直接访问
  访问应用 C → 用票据换取应用 C 的会话 → 直接访问

  一次登录，处处通行
```

| SSO 类型 | 说明 | 典型协议 |
|---------|------|---------|
| **Web SSO** | Web 应用间的单点登录 | SAML、OAuth、OIDC、CAS |
| **企业级 SSO** | 企业内网统一认证 | Kerberos、AD、LDAP |
| **联邦 SSO** | 跨组织的单点登录 | SAML、OIDC |

**SSO 的好处**：
- ✅ 用户体验好（不用记一堆密码）
- ✅ 安全性提升（集中管理、减少密码泄露点）
- ✅ 管理成本低（统一账号生命周期管理）
- ✅ 便于审计和合规

**SSO 的风险**：
- ⚠️ 单点故障：SSO 挂了所有应用都登不了
- ⚠️ 单点突破：SSO 账号被盗 = 所有应用都被盗
- ⚠️ 所以一定要给 SSO 开 MFA

### 5.2 Kerberos

**Kerberos**：一种网络认证协议，使用票据（Ticket）进行身份认证，是 Windows AD 域环境的默认认证协议。

```
Kerberos 认证流程（简化）：

  1. 客户端向 KDC 认证（AS_REQ / AS_REP）
     → 获得 TGT（票据授予票据）

  2. 客户端要访问某个服务
     → 用 TGT 向 KDC 的 TGS 申请服务票据（TGS_REQ / TGS_REP）
     → 获得 ST（服务票据）

  3. 客户端用 ST 访问应用服务器（AP_REQ / AP_REP）
     → 服务器验证票据，允许访问

  KDC（密钥分发中心）= AS（认证服务）+ TGS（票据授予服务）
```

| 特性 | 说明 |
|------|------|
| **认证方式** | 基于对称加密的票据系统 |
| **安全性** | 高（不传输密码，有时间戳防重放） |
| **SSO 支持** | 支持（一次登录获得 TGT，后续用 TGT 换服务票据） |
| **互操作性** | Windows AD 默认支持，Linux 也有实现 |
| **复杂度** | 较高，配置和排错都不简单 |

**Kerberos 的几个关键概念**：

| 术语 | 说明 |
|------|------|
| **Realm** | Kerberos 域，类似域名，通常大写（如 EXAMPLE.COM） |
| **Principal** | 主体，格式：service/hostname@REALM |
| **KDC** | 密钥分发中心，Kerberos 的核心服务器 |
| **TGT** | 票据授予票据，用来申请服务票据 |
| **ST / TGS Ticket** | 服务票据，用来访问具体服务 |
| **Keytab** | 密钥表文件，存储服务账号的密钥 |

### 5.3 LDAP

**LDAP（Lightweight Directory Access Protocol，轻量目录访问协议）**：一种用于访问和维护分布式目录信息的协议，常用于存储用户、组、权限等信息。

```
LDAP 目录结构（树形）：

  dc=example, dc=com
      │
      ├── ou=people          ← 组织单元（人）
      │     ├── uid=alice
      │     ├── uid=bob
      │     └── uid=charlie
      │
      ├── ou=groups          ← 组织单元（组）
      │     ├── cn=admin
      │     ├── cn=finance
      │     └── cn=engineering
      │
      └── ou=servers         ← 组织单元（服务器）
            ├── cn=web01
            └── cn=db01
```

| 概念 | 说明 |
|------|------|
| **DN（Distinguished Name）** | 唯一标识，完整路径（如 uid=alice,ou=people,dc=example,dc=com） |
| **RDN（Relative DN）** | 相对路径（如 uid=alice） |
| **OU（Organizational Unit）** | 组织单元，树形结构的分支 |
| **DC（Domain Component）** | 域组件（如 dc=example,dc=com） |
| **Schema** | 目录结构的定义（什么对象有什么属性） |
| **Base DN** | 搜索的起始节点 |

**常见 LDAP 实现**：

| 实现 | 说明 |
|------|------|
| **OpenLDAP** | 开源 LDAP 服务器，最流行 |
| **Active Directory (AD)** | 微软的目录服务，集成了 LDAP + Kerberos + DNS |
| **389 Directory Server** | Red Hat 的 LDAP 实现 |
| **OpenDJ** | 开源 LDAP |
| **FreeIPA** | 集成了 LDAP + Kerberos + DNS + 证书的身份管理系统 |

### 5.4 OAuth 2.0

**OAuth 2.0**：一个授权框架，允许第三方应用在用户授权的情况下访问用户的资源，而不需要把密码告诉第三方应用。

```
OAuth 2.0 场景：
  "使用微信/QQ/GitHub 登录" 或 "允许应用访问你的相册"

  用户 → 第三方应用
  用户 → 服务提供商（微信/GitHub 等）
  第三方应用 → 服务提供商（在用户授权下获取资源）

  核心：用户把"有限的权限"授权给第三方应用，而不是把密码给它
```

**OAuth 2.0 四个角色**：

| 角色 | 说明 | 例子 |
|------|------|------|
| **资源所有者（Resource Owner）** | 用户 | 你 |
| **客户端（Client）** | 第三方应用 | 某个网站/APP |
| **授权服务器（Authorization Server）** | 颁发令牌的服务器 | 微信授权服务器 |
| **资源服务器（Resource Server）** | 托管用户资源的服务器 | 微信 API 服务器 |

**四种授权模式（Grant Type）**：

| 模式 | 英文 | 适用场景 | 安全性 |
|------|------|---------|--------|
| **授权码模式** | Authorization Code | 有后端的 Web 应用（最常用） | 高 |
| **隐式模式** | Implicit | 纯前端应用（SPA） | 低（不推荐，改用 PKCE） |
| **密码模式** | Resource Owner Password Credentials | 第一方应用、高信任 | 中（不推荐） |
| **客户端凭证模式** | Client Credentials | 服务端到服务端（无用户参与） | 高（适合服务间） |

> ⚠️ **重要**：OAuth 是**授权**框架，不是**认证**框架。它解决的是"授权第三方应用访问资源"的问题，而不是"用户是谁"的问题。但很多人用 OAuth 来做认证，这其实有问题。OIDC 就是在 OAuth 2.0 之上加了一层认证层。

### 5.5 OpenID Connect（OIDC）

**OIDC（OpenID Connect）**：在 OAuth 2.0 之上构建的身份认证层，解决 OAuth 本身不提供认证的问题。

| 协议 | 用途 | 获取的内容 |
|------|------|-----------|
| **OAuth 2.0** | 授权 | Access Token（访问令牌，用于访问资源） |
| **OIDC** | 认证 + 授权 | Access Token + **ID Token**（身份令牌，包含用户信息） |

**ID Token**：JWT 格式的令牌，包含用户的身份信息（sub、name、email 等）。

```
OIDC = OAuth 2.0 + 身份认证
  ├── Access Token → 授权（访问 API）
  └── ID Token     → 认证（用户是谁）
```

**OIDC vs SAML**：

| 对比 | OIDC | SAML 2.0 |
|------|------|----------|
| **年代** | 新（2014） | 旧（2005） |
| **格式** | JSON / JWT | XML |
| **适用场景** | 移动、Web、API | 企业级 SSO、政府 |
| **复杂度** | 较低 | 较高 |
| **安全性** | 高 | 很高 |
| **趋势** | 越来越流行 | 传统企业仍大量使用 |

### 5.6 身份协议对比

| 协议 | 层级 | 认证 | 授权 | 单点登录 | 典型应用 |
|------|------|------|------|---------|---------|
| **Kerberos** | 应用层 | ✅ | ✅ | ✅ | Windows AD、企业内网 |
| **LDAP** | 应用层 | ✅ | ✅（可用于） | 部分 | 目录服务、用户管理 |
| **SAML 2.0** | 应用层 | ✅ | ✅ | ✅ | 企业级 Web SSO |
| **OAuth 2.0** | 应用层 | ❌（本身） | ✅ | 间接 | API 授权、第三方登录 |
| **OIDC** | 应用层 | ✅ | ✅ | ✅ | 现代 Web/移动 SSO |
| **RADIUS** | 应用层 | ✅ | ✅ | ❌ | 网络接入认证（802.1X、VPN） |
| **TACACS+** | 应用层 | ✅ | ✅ | ❌ | 网络设备认证授权（Cisco） |

## 六、Linux 实践

### 6.1 PAM（可插拔认证模块）

**PAM（Pluggable Authentication Modules，可插拔认证模块）**：Linux 系统的统一认证框架，各种认证方式（密码、LDAP、指纹、令牌等）以模块的形式插入，应用程序通过 PAM 接口调用，不需要知道具体认证方式。

```
PAM 的作用：

  应用程序（login、sshd、su、sudo 等）
         │
         ├─────► PAM 接口
         │           │
         │           ├── pam_unix.so      （本地密码认证）
         │           ├── pam_ldap.so      （LDAP 认证）
         │           ├── pam_google_authenticator.so （TOTP）
         │           ├── pam_faillock.so  （失败锁定）
         │           ├── pam_cracklib.so  （密码复杂度检查）
         │           └── ... 各种认证模块
         │
         ▼
     认证成功 / 失败
```

#### PAM 配置

```bash
# ===== 配置文件位置 =====
# 主配置文件：/etc/pam.conf（较少用）
# 各服务配置：/etc/pam.d/<服务名>
ls /etc/pam.d/
# 常见服务：sshd、login、su、sudo、passwd、system-auth

# ===== PAM 配置语法 =====
# 格式：类型  控制标志  模块路径  模块参数

# 类型（Module Type）：
#   auth      认证（验证身份）
#   account   账号（检查账号是否允许登录、过期等）
#   password  密码（密码修改策略）
#   session   会话（登录/登出时的操作）

# 控制标志（Control Flag）：
#   required  必须通过，失败但继续执行后面的模块，最后一起返回失败
#   requisite 必须通过，失败立即返回失败
#   sufficient 如果成功就直接返回成功，不执行后面的
#   optional  可选，不影响结果（只用于日志等）
#   include   包含其他配置文件

# ===== 常见 PAM 模块 =====
pam_unix.so           # 标准 Unix 认证（/etc/shadow 密码）
pam_ldap.so           # LDAP 认证
pam_krb5.so           # Kerberos 认证
pam_sss.so            # SSSD（系统安全服务守护进程）
pam_faillock.so       # 登录失败锁定
pam_cracklib.so       # 密码复杂度检查（旧版）
pam_pwquality.so      # 密码质量检查（新版，替代 cracklib）
pam_tally2.so         # 登录失败计数（旧版）
pam_limits.so         # 资源限制（ulimit）
pam_motd.so           # 显示登录提示
pam_lastlog.so        # 记录上次登录时间
pam_env.so            # 设置环境变量
pam_rootok.so         # root 直接通过（su 不需要密码）

# ===== 示例：查看 /etc/pam.d/sshd =====
# 包含 system-auth 配置
cat /etc/pam.d/sshd
# %PAM-1.0
# auth       substack     password-auth
# auth       include      postlogin
# account    required     pam_nologin.so
# account    include      password-auth
# ...
```

#### 密码策略配置 🔑

```bash
# RHEL/CentOS：/etc/pam.d/system-auth 或 /etc/pam.d/password-auth
# Debian/Ubuntu：/etc/pam.d/common-password

# ===== 密码复杂度（pam_pwquality） =====
# 安装：yum install libpwquality / apt install libpam-pwquality

# 配置文件：/etc/security/pwquality.conf
# minlen = 12          最小长度
# dcredit = -1         至少 1 个数字
# ucredit = -1         至少 1 个大写字母
# lcredit = -1         至少 1 个小写字母
# ocredit = -1         至少 1 个特殊字符
# minclass = 3         至少包含 3 类字符
# maxrepeat = 3        同一字符最多连续 3 次
# gecoscheck = 1       检查是否包含用户信息

# 在 PAM 配置中启用：
# password requisite pam_pwquality.so retry=3

# ===== 登录失败锁定 =====
# RHEL 8+ 使用 pam_faillock
# 配置文件：/etc/security/faillock.conf
# deny = 5               失败 5 次锁定
# unlock_time = 300      锁定 300 秒（5 分钟）
# even_deny_root         root 也锁定
# root_unlock_time = 600 root 锁定时间更长

# 在 PAM 中配置：
# auth required pam_faillock.so preauth silent
# auth required pam_faillock.so authfail
# account required pam_faillock.so

# 查看失败记录
faillock --user alice
faillock --user alice --reset    # 解锁用户🔑

# ===== 密码历史 =====
# pam_pwhistory.so remember=5  不能重复最近 5 次密码
```

> ⚠️ **修改 PAM 配置警告**：PAM 配置错误可能导致所有用户都无法登录！
> - 修改前先备份配置文件
> - 保持一个已登录的 root 会话不关闭，测试通过后再关
> - 先在测试环境验证
> - 可以用 `pamtester` 工具测试 PAM 配置

### 6.2 sudo

**sudo**：允许普通用户以另一个用户（通常是 root）的身份执行命令。

```bash
# ===== 配置文件 =====
# 主配置：/etc/sudoers
# 推荐用 visudo 编辑（有语法检查）
visudo
visudo -f /etc/sudoers.d/custom      # 编辑子配置

# 也可以直接加文件到 /etc/sudoers.d/
echo "alice ALL=(ALL) ALL" > /etc/sudoers.d/alice

# ===== 基本语法 =====
# 用户/组    主机=(切换到的用户)  [NOPASSWD:]  命令
# 示例：

# 允许 alice 在任何主机上以任何用户身份执行任何命令（需要密码）
alice ALL=(ALL) ALL

# 允许 bob 不需要密码执行所有命令
bob ALL=(ALL) NOPASSWD: ALL

# 允许运维组执行 systemctl 和 yum
%ops ALL=(ALL) /usr/bin/systemctl, /usr/bin/yum

# 允许 charlie 以 root 身份重启 httpd
charlie ALL=(root) /usr/bin/systemctl restart httpd

# 允许 dave 不需要密码执行特定目录下的所有命令
dave ALL=(ALL) NOPASSWD: /opt/admin-scripts/

# 禁止某些命令（前面加 !）
alice ALL=(ALL) ALL, !/usr/bin/passwd root, !/bin/bash

# 命令参数也可以限定（精确匹配）
alice ALL=(ALL) /usr/bin/less /var/log/messages

# ===== 常用命令 =====
sudo -l              # 查看当前用户的 sudo 权限
sudo -u bob command  # 以 bob 用户身份执行
sudo -i              # 切换到 root（登录 shell）
sudo -s              # 切换到 root（非登录 shell）
sudo -k              # 清除 sudo 缓存（下次需要重新输密码）
sudo -v              # 延长 sudo 超时（验证密码）

# ===== 日志审计 =====
# sudo 的操作会记录到日志
# Debian: /var/log/auth.log
# RHEL: /var/log/secure
# 也可以配置到单独的日志文件

# ===== 安全配置建议 =====
# 1. 禁止 root 直接 SSH 登录，用 sudo 提权
# 2. 最小权限原则，只给需要的命令
# 3. 尽量不要用 NOPASSWD: ALL
# 4. 配置日志审计
# 5. 限制可使用 sudo 的用户/组
# 6. 设置合适的超时时间
# 7. 定期审查 sudoers 配置
```

> ⚠️ **sudo 安全警告**：
> - `NOPASSWD: ALL` 风险很高，等于给了用户无密码的完整 root 权限
> - 通配符和命令参数要小心，可能被绕过
> - sudo 配置错误可能导致提权漏洞
> - 编辑 sudoers 务必用 `visudo`（有语法检查，防止改错了所有人都用不了 sudo）

### 6.3 SSH 密钥认证

```bash
# ===== 生成密钥对 =====
# 推荐 Ed25519
ssh-keygen -t ed25519 -C "alice@example.com"

# RSA 4096 位（兼容性好）
ssh-keygen -t rsa -b 4096 -C "alice@example.com"

# 生成时会问：
#   保存位置（默认 ~/.ssh/id_ed25519）
#   密码（passphrase，推荐设置，保护私钥）

# ===== 公钥分发 =====
# 方法 1：ssh-copy-id（推荐）
ssh-copy-id user@server.example.com
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@server

# 方法 2：手动
cat ~/.ssh/id_ed25519.pub | ssh user@server 'mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys'

# ===== sshd 配置（服务器端） =====
# 配置文件：/etc/ssh/sshd_config
# ⚠️ 修改前备份：cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak

# 启用公钥认证
PubkeyAuthentication yes
AuthorizedKeysFile .ssh/authorized_keys

# 禁用密码认证（确认密钥登录可用后再改！）
PasswordAuthentication no

# 禁止 root 直接登录
PermitRootLogin no
# 或者允许密钥登录但禁止密码
PermitRootLogin prohibit-password

# 其他安全配置
UsePAM yes
PermitEmptyPasswords no
MaxAuthTries 3
ClientAliveInterval 300
ClientAliveCountMax 2
X11Forwarding no
AllowUsers alice bob
AllowGroups ops team-a

# 重启 sshd（保持一个会话不关闭！）
systemctl restart sshd

# ===== 密钥权限检查 =====
# 这些权限不对的话 SSH 会拒绝公钥认证
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519          # 私钥 600
chmod 644 ~/.ssh/id_ed25519.pub      # 公钥 644
chmod 600 ~/.ssh/authorized_keys      # 授权文件 600
chmod 644 ~/.ssh/known_hosts

# ===== SSH Agent =====
eval $(ssh-agent -s)      # 启动 agent
ssh-add ~/.ssh/id_ed25519  # 添加密钥
ssh-add -l                # 列出已添加的密钥
ssh-add -D                # 删除所有密钥

# ===== 故障排查 =====
# 客户端加 -v 看详细调试信息
ssh -v user@server
ssh -vv user@server       # 更详细
ssh -vvv user@server      # 最详细

# 常见问题：
# - 权限不对（.ssh 目录或文件权限太宽）
# - 公钥没加到 authorized_keys
# - 服务器禁用了公钥认证
# - SELinux 问题
# - 家目录权限不对
```

> ⚠️ **SSH 安全警告**：
> - 禁用密码登录之前，务必先测试密钥登录是否正常！
> - 保持一个 SSH 会话不关闭，从另一个终端测试通过后再关
> - 私钥一定要设置密码（passphrase），防止私钥泄露后直接被使用
> - 定期轮换密钥

### 6.4 ACL（文件访问控制列表）

传统的 Unix 权限（u/g/o 三组）不够灵活时，用 ACL 可以给特定用户或组设置独立权限。

```bash
# ===== 安装 ACL 工具 =====
# Debian/Ubuntu: apt install acl
# RHEL/CentOS: yum install acl
# 挂载时需要 acl 选项（默认一般已开启）

# ===== 查看 ACL =====
getfacl file.txt
getfacl -d directory/          # 查看默认 ACL（目录的）

# ===== 设置 ACL =====
# 给用户 alice 读写权限
setfacl -m u:alice:rw file.txt

# 给组 ops 只读权限
setfacl -m g:ops:r file.txt

# 给其他用户设置
setfacl -m o::--- file.txt    # 其他人无权限

# 设置多个条目（逗号分隔）
setfacl -m u:alice:rw,g:ops:rx,o::--- file.txt

# ===== 目录的默认 ACL =====
# 新创建的文件/子目录会继承默认 ACL
setfacl -m d:u:alice:rwx directory/
setfacl -m d:g:ops:rx directory/
setfacl -m d:o::--- directory/

# ===== 删除 ACL =====
# 删除特定用户的 ACL
setfacl -x u:alice file.txt

# 删除所有 ACL
setfacl -b file.txt
setfacl -b -k directory/     # 同时删除默认 ACL

# ===== 复制 ACL =====
getfacl file1.txt | setfacl --set-file=- file2.txt

# ===== 示例 =====
# 场景：一个项目目录，团队成员读写，其他人不能看
mkdir /project
chown root:project-team /project
chmod 770 /project

# 再给实习生 bob 只读权限（不用改组）
setfacl -m u:bob:r-x /project
setfacl -d -m u:bob:r-x /project

# 查看
getfacl /project
# # file: project
# # owner: root
# # group: project-team
# user::rwx
# user:bob:r-x
# group::rwx
# mask::rwx
# other::---
# default:user::rwx
# default:user:bob:r-x
# default:group::rwx
# default:mask::rwx
# default:other::---
```

## 七、常见问题与加固

### 7.1 常见认证安全问题

| 问题 | 风险 | 防御措施 |
|------|------|---------|
| **弱密码** | 容易被暴力破解/字典攻击 | 强密码策略、密码复杂度要求、MFA |
| **密码复用** | 一个泄露处处遭殃 | 密码管理器、SSO、安全培训 |
| **密码明文存储** | 数据库泄露 = 全部密码泄露 | 加盐慢哈希（bcrypt/scrypt/Argon2） |
| **暴力破解** | 不断试密码猜出来 | 账号锁定、速率限制、验证码、MFA |
| **凭证填充** | 用别处泄露的账号密码来试 | 风控系统、异常登录检测、MFA |
| **钓鱼攻击** | 骗用户输入密码 | 安全培训、邮件网关、MFA（防钓鱼的） |
| **会话劫持** | 窃取 session ID 冒充用户 | HTTPS、HttpOnly + Secure Cookie、会话超时 |
| **CSRF** | 利用用户已登录身份发起请求 | CSRF Token、SameSite Cookie |
| **中间人攻击** | 窃取/篡改通信内容 | TLS/SSL 加密、证书验证 |
| **凭据泄露** | 数据库/代码泄露了密码/密钥 | 加密存储、最小权限、密钥管理 |

### 7.2 认证加固清单

```
认证安全加固清单：

1. 密码策略
   □ 最小长度 ≥ 8 位（建议 12 位以上）
   □ 复杂度要求（多类字符）
   □ 密码历史（不能重复最近 5 次）
   □ 密码有效期（90 天，按合规要求）
   □ 禁止使用常见弱密码
   □ 首次登录强制改密码

2. 登录安全
   □ 失败锁定（5 次失败锁定 30 分钟）
   □ 速率限制（防暴力破解）
   □ 验证码（登录/重置等关键操作）
   □ 异常登录检测（异地/新设备告警）
   □ 会话超时（闲置自动登出）
   □ 单点登录限制（并发会话数）

3. 多因素认证
   □ 管理员账号必须启用 MFA
   □ 关键系统必须启用 MFA
   □ VPN 必须启用 MFA
   □ 优先使用防钓鱼的 MFA（U2F/WebAuthn）

4. 密码存储
   □ 绝对不能明文存储
   □ 不能用可逆加密
   □ 使用加盐慢哈希（bcrypt/Argon2/scrypt）
   □ 密钥/盐值单独管理，不和数据库放一起

5. 账号管理
   □ 最小权限原则
   □ 定期权限审计
   □ 离职账号及时停用/删除
   □ 共享账号禁止使用
   □ 服务账号单独管理、定期轮换

6. 传输安全
   □ 所有登录页面和认证接口用 HTTPS
   □ Cookie 设置 HttpOnly 和 Secure 标志
   □ Cookie 设置 SameSite 属性
   □ 禁用不安全的 TLS 版本

7. 审计与监控
   □ 记录所有登录事件（成功/失败）
   □ 记录所有权限变更
   □ 集中日志管理
   □ 异常行为告警
   □ 定期审计账号和权限
```

### 7.3 访问控制加固

```
访问控制加固清单：

1. 原则
   □ 最小权限原则
   □ 默认拒绝（Deny by default）
   □ 按需知道原则
   □ 职责分离
   □ 定期权限审计

2. 实现
   □ 基于角色的访问控制（RBAC）
   □ 细粒度权限控制（必要时 ABAC）
   □ 统一权限管理（集中式）
   □ 权限申请/审批流程
   □ 权限定期回收

3. Linux 系统
   □ 禁用 root 直接登录，用 sudo
   □ sudo 最小权限配置（不给 ALL）
   □ 文件目录权限检查（755/644 基准）
   □ 特殊权限审计（SUID/SGID/Sticky）
   □ 必要时用 ACL 精细化控制
   □ umask 合理配置（如 027）

4. 应用系统
   □ 每接口鉴权
   □ 水平越权检查（A 用户不能看 B 用户数据）
   □ 垂直越权检查（普通用户不能用管理员功能）
   □ 接口级别的权限控制
   □ 管理后台二次认证/单独的访问控制
```

### 7.4 常见排查思路

```
认证/权限问题排查思路：

1. 认证失败
   → 用户名/密码对不对？
   → 账号被锁定了吗？（faillock / pam_tally2）
   → 账号过期了吗？（chage -l）
   → PAM 配置对吗？
   → 日志里有什么错误？（/var/log/auth.log 或 secure）
   → LDAP/AD 连通吗？
   → SSH 的话，密钥权限对吗？（.ssh 目录权限）

2. 权限不足
   → 用户属于什么组？（id / groups）
   → 文件/目录权限是什么？（ls -l）
   → ACL 配置了吗？（getfacl）
   → sudo 配置对吗？（sudo -l）
   → SELinux/AppArmor 阻止了吗？
   → 应用层权限配置对吗？

3. 单点登录问题
   → SSO 服务器可达吗？
   → 证书有效吗？
   → 时钟同步吗？（Kerberos/SAML 对时间很敏感）
   → 回调地址配置对吗？（OAuth/OIDC）
   → 日志里有什么错误？

4. 密码策略不生效
   → PAM 配置对吗？
   → 模块顺序对吗？（password 类的顺序很重要）
   → 是哪个服务不生效？（ssh/login/su 各自的 PAM 配置）
   → 配置文件语法对吗？
```
