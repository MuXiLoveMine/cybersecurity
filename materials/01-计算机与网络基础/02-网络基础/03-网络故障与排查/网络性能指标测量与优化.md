## 一、网络性能定义与目标

### 1.1 什么是网络性能

**网络性能（Network Performance）**：衡量网络传输数据的速度、质量和效率的综合指标。它不是单一的数字，而是一组指标的集合。

```
用户感受到的"网络快不快" = 函数（带宽, 延迟, 丢包, 抖动, 协议效率, ...）

  例子：
    - 大文件下载 → 主要看带宽
    - 网页打开 → 主要看延迟和连接建立时间
    - 视频会议 → 主要看抖动和丢包
    - 在线游戏 → 主要看延迟和稳定性
```

### 1.2 五大性能维度

| 维度 | 英文 | 含义 | 业务影响 |
|------|------|------|---------|
| **性能 / 速度** | Performance | 数据传输有多快 | 用户体验、页面加载时间 |
| **容量 / 带宽** | Capacity / Bandwidth | 最多能传多少 | 能支撑多少用户、是否会拥塞 |
| **可用性** | Availability | 网络是否可用 | 业务是否能正常访问 |
| **可靠性** | Reliability | 传输是否可靠（丢包、错误） | 数据完整性、重传开销 |
| **可扩展性** | Scalability | 增长时能否扩容 | 业务增长时的支撑能力 |

### 1.3 用户体验与业务指标

```
技术指标 → 用户感知 → 业务指标

  低延迟     →  页面秒开   →  转化率高
  高带宽     →  视频不卡   →  用户留存高
  低丢包     →  通话清晰   →  通话质量好
  高可用     →  服务不中断 →  收入不损失
  可扩展     →  高峰不崩   →  活动顺利
```

| 业务指标 | 关联的网络性能指标 |
|---------|-----------------|
| 页面加载时间 | RTT、带宽、TCP 连接建立时间、TLS 握手时间 |
| API 响应时间 | 延迟、丢包、重传率 |
| 视频卡顿率 | 抖动、丢包、带宽 |
| 通话 MOS 分 | 延迟、抖动、丢包 |
| 并发用户数 | 带宽、PPS、连接数、会话数 |
| 下载速度 | 带宽、丢包、RTT（带宽时延积） |

## 二、核心性能指标

### 2.1 带宽与吞吐量

| 指标 | 英文 | 定义 | 单位 | 正常范围 | 异常含义 | 测量工具 |
|------|------|------|------|---------|---------|---------|
| **带宽** | Bandwidth | 链路的最大传输能力（理论上限） | bps、Kbps、Mbps、Gbps | 取决于物理链路 | — | ethtool |
| **吞吐量** | Throughput | 实际传输速率 | bps、MB/s | 接近带宽为好 | 远低于带宽说明有瓶颈 | iperf3、netperf |
| **有效吞吐** | Goodput | 实际有效数据的传输速率（扣除协议开销/重传） | bps | 比吞吐量略低 | 比吞吐量低很多说明重传/开销大 | tcpdump、Wireshark |
| **PPS** | Packets Per Second | 每秒处理的数据包数量 | pps | 取决于设备能力 | 接近设备上限会丢包 | sar -n、nstat |
| **QPS / TPS** | Queries/Transactions Per Second | 每秒请求/事务数 | qps/tps | 取决于应用+网络 | 上不去可能有网络瓶颈 | 应用监控、curl |

> **带宽 ≠ 吞吐量**：带宽是路有多宽，吞吐量是实际每秒过了多少辆车。吞吐量通常低于带宽，因为有协议开销、拥塞、丢包等。

### 2.2 延迟与抖动

| 指标 | 英文 | 定义 | 单位 | 正常范围 | 异常含义 | 测量工具 |
|------|------|------|------|---------|---------|---------|
| **RTT** | Round Trip Time | 往返时间（发出去到收到响应） | ms | 局域网 < 1ms；同城 < 20ms；跨省 < 50ms；跨国 < 200ms | 过高影响交互式应用 | ping、traceroute、mtr |
| **单向延迟** | One-way Latency | 从一端到另一端的时间 | ms | 约为 RTT 的一半 | 不对称路由 | 精确测量需要时钟同步 |
| **抖动** | Jitter | 延迟的变化量（不稳定程度） | ms | < 10ms 很好；< 30ms 可接受 | 高抖动影响实时音视频 | mtr、ping -f、iperf3 |
| **连接建立时间** | Connection Setup Time | TCP 三次握手的时间 | ms | ≈ 一个 RTT | 过高说明网络延迟大或 SYN 丢包 | curl -w、tcpdump |
| **TLS 握手时间** | TLS Handshake Time | TLS 握手耗时 | ms | TLS 1.2 ≈ 2-RTT；TLS 1.3 ≈ 1-RTT | 过慢影响 HTTPS 体验 | curl -w、openssl s_client |
| **首字节时间** | TTFB / Time to First Byte | 发请求到收到第一个字节的时间 | ms | 越短越好 | 高说明网络+服务器处理慢 | curl -w |
| **DNS 解析时间** | DNS Resolution Time | 域名解析耗时 | ms | < 100ms 好；100~500ms 一般 | 慢影响所有依赖 DNS 的应用 | dig、curl -w |

```
HTTP 请求的时间分解（一个请求的时间去哪儿了）：

  DNS 解析 ──► TCP 连接 ──► TLS 握手 ──► 请求发送 ──► 服务器处理 ──► 响应接收
  │           │           │          │            │              │
  └─ 1ms ────┴─ 20ms ─────┴─ 40ms ───┴─ 1ms ──────┴─ 100ms ───────┘
        总时间 ≈ 162ms
```

### 2.3 丢包与质量

| 指标 | 英文 | 定义 | 单位 | 正常范围 | 异常含义 | 测量工具 |
|------|------|------|------|---------|---------|---------|
| **丢包率** | Packet Loss Rate | 丢失的包占总包数的比例 | % | < 0.1% 很好；< 1% 可接受；> 1% 有问题 | 高丢包导致重传、吞吐下降、卡顿 | ping、mtr、iperf3 |
| **重传率** | Retransmission Rate | 重传的包占总包数的比例 | % | < 1% 正常；> 5% 严重 | 高重传说明网络质量差 | nstat、ss -ti、tcpdump |
| **乱序率** | Reordering Rate | 数据包到达顺序混乱的比例 | % | 越低越好 | 乱序影响性能（触发不必要重传） | tcpdump、iperf3 |
| **错误率** | Error Rate | CRC 等错误包比例 | % | 接近 0 | 高错误率说明物理层有问题 | netstat -s、ethtool -S |

### 2.4 连接与队列

| 指标 | 英文 | 定义 | 单位 | 正常范围 | 异常含义 | 测量工具 |
|------|------|------|------|---------|---------|---------|
| **并发连接数** | Concurrent Connections | 同时存在的连接数 | 个 | 取决于系统能力 | 接近上限会拒绝新连接 | ss、netstat |
| **ESTABLISHED** | Established Connections | 已建立的连接数 | 个 | — | 突增可能是攻击或异常 | ss -s |
| **TIME_WAIT 数** | TIME_WAIT Count | TIME_WAIT 状态的连接数 | 个 | 几千以内正常 | 过多可能耗尽端口资源 | ss -s |
| **队列长度** | Queue Length | 等待处理的数据包/连接数 | 个 | 接近 0 最好 | 队列长说明有瓶颈（CPU/带宽/应用） | ss -l、netstat -s、tc |
| **缓冲区使用** | Buffer Usage | 发送/接收缓冲区占用 | % | 正常波动 | 持续满说明应用收/发慢 | ss -m、/proc/sys/net/core |
| **带宽时延积** | BDP / Bandwidth-Delay Product | 带宽 × 延迟 = 管道容量 | bytes | — | 缓冲区小于 BDP 则跑不满带宽 | 计算得出 |

**带宽时延积（BDP）计算**：

```
BDP = 带宽(bps) × 延迟(s) / 8 = 字节数

例子：
  1Gbps 链路，RTT 50ms
  BDP = 1,000,000,000 bps × 0.05 s / 8 = 6,250,000 bytes ≈ 6MB

含义：
  "管道"里能同时装 6MB 的数据
  如果 TCP 窗口只有 1MB，那么最多只能跑 1MB/50ms = 160Mbps
  要跑满 1Gbps，TCP 窗口至少要 6MB
```

### 2.5 指标速查表

| 场景 | 最关注的指标 | 经验值 |
|------|------------|--------|
| **大文件传输** | 带宽、丢包、重传率 | 丢包 < 0.1% 才能跑满带宽 |
| **Web/API** | RTT、连接时间、TTFB、丢包 | RTT 越短越好，TLS 尽量复用 |
| **视频/直播** | 带宽、抖动、丢包 | 抖动 < 30ms，丢包 < 1% |
| **语音通话** | 延迟、抖动、丢包 | 单向延迟 < 150ms，抖动 < 30ms |
| **在线游戏** | RTT、抖动、丢包 | RTT < 50ms 很好，抖动 < 10ms |
| **数据库** | RTT、丢包 | RTT 越短越好，丢包接近 0 |
| **高并发服务** | PPS、连接数、队列长度 | 关注设备 PPS 上限和连接上限 |

## 三、性能影响因素

### 3.1 物理与网络设备

| 层面 | 因素 | 对性能的影响 |
|------|------|-------------|
| **物理链路** | 介质类型（光纤/双绞线）、距离、信号质量 | 决定带宽上限和错误率 |
| **网卡（NIC）** | 速率（1G/10G/25G/100G）、多队列、硬件卸载 | 决定 PPS 和吞吐量上限 |
| **交换机** | 背板带宽、转发能力、缓冲区大小 | 拥塞时的丢包和延迟 |
| **路由器** | 转发性能、路由表大小、QoS 能力 | 跨网段时的瓶颈 |
| **防火墙** | 处理性能、并发连接数、吞吐量 | 安全功能影响性能（状态检测/IPS） |
| **负载均衡** | 吞吐能力、并发连接数、算法开销 | 流量汇聚点，可能成为瓶颈 |

### 3.2 协议与参数

| 因素 | 影响 |
|------|------|
| **TCP 拥塞控制算法** | BBR 比 CUBIC 在高丢包/长肥管道下表现好 |
| **TCP 窗口大小** | 窗口不够则跑不满带宽（受限于 BDP） |
| **MTU / MSS** | MTU 越大，协议开销比例越小；但太大可能分片 |
| **TCP 快速打开（TFO）** | 减少连接建立的 RTT |
| **SACK / DSACK** | 更高效的重传，减少不必要的重传 |
| **Nagle 算法** | 合并小包减少开销，但增加延迟 |
| **延迟确认（Delayed ACK）** | 减少 ACK 包数量，但可能增加延迟 |
| **TLS 版本** | TLS 1.3 比 1.2 少一个 RTT 的握手 |
| **HTTP 版本** | HTTP/2 多路复用；HTTP/3 基于 UDP 更快 |

### 3.3 应用与架构

| 因素 | 影响 |
|------|------|
| **Keep-Alive** | 复用连接，避免重复建连开销 |
| **连接池** | 预建连接，减少请求时的连接建立时间 |
| **HTTP/2 多路复用** | 一个连接并发多个请求，减少连接数和队头阻塞 |
| **HTTP/3 / QUIC** | 基于 UDP，队头阻塞更少，连接迁移更快 |
| **压缩（gzip/brotli）** | 减少传输数据量，节省带宽 |
| **缓存** | 减少重复请求，降低延迟和带宽 |
| **CDN** | 就近访问，降低延迟，减少回源带宽 |
| **负载均衡** | 水平扩展，提高总容量和可用性 |

### 3.4 虚拟化与云

| 因素 | 影响 |
|------|------|
| **虚拟化网络** | 虚拟化有额外开销（网桥/OVS/vSwitch） |
| **容器网络** | overlay 网络有封装开销（VXLAN 等） |
| **云网络** | 共享带宽、有性能上限（按规格） |
| **可用区/地域** | 跨 AZ/地域的延迟和带宽成本 |
| **网络服务链** | 多层服务（LB/NAT/FW）叠加增加延迟 |
| **SR-IOV / DPDK** | 绕过内核，接近物理网卡性能 |

## 四、测量与监控方法

### 4.1 主动测量 vs 被动测量

| 类型 | 原理 | 优点 | 缺点 | 典型工具 |
|------|------|------|------|---------|
| **主动测量** | 主动发测试包，测量响应 | 可控、精确、灵活 | 会产生额外流量，可能影响业务 | ping、mtr、iperf3、traceroute、curl |
| **被动测量** | 观察真实流量，不主动发包 | 不影响业务，反映真实情况 | 只能看已有的流量，测量项有限 | tcpdump、ss、sar、iftop、netstat |

### 4.2 主动测量工具

#### （1）ping — 基础连通性和延迟

```bash
# 基本用法
ping 8.8.8.8
ping -c 10 8.8.8.8              # 发 10 个包就停
ping -i 0.2 8.8.8.8            # 间隔 0.2 秒（默认 1 秒）
ping -s 1400 8.8.8.8           # 指定包大小（1400 字节数据）
ping -f 8.8.8.8                # Flood ping（尽可能快，需 root🔑）
ping -D 8.8.8.8                # 每个包打印时间戳

# 统计模式（发 N 个包后输出统计）
ping -c 100 -q 8.8.8.8         # 静默模式，只输出统计

# 输出解读：
#   rtt min/avg/max/mdev = 10.123/12.456/15.789/2.345 ms
#   min  最小延迟
#   avg  平均延迟
#   max  最大延迟
#   mdev 延迟的标准差（反映抖动，越大越不稳定）
```

#### （2）traceroute / mtr — 路径探测

```bash
# traceroute - 跟踪路由路径
traceroute 8.8.8.8
traceroute -I 8.8.8.8          # 用 ICMP（默认 UDP）
traceroute -T -p 443 8.8.8.8   # 用 TCP 443 端口（绕过防火墙）
traceroute -n 8.8.8.8          # 不解析域名（更快）
traceroute -m 30 8.8.8.8       # 最大跳数 30

# mtr - 综合了 ping 和 traceroute，持续监控每一跳
mtr 8.8.8.8                    # 交互模式
mtr -r 8.8.8.8                 # 报告模式（跑一轮输出报告）
mtr -rw -c 100 8.8.8.8         # 宽格式 + 100 个包 + 报告模式
mtr --tcp --port 443 8.8.8.8   # TCP 443 端口探测

# mtr 输出列解读：
#   Loss%   丢包率
#   Snt     发送包数
#   Last    最后一个包的延迟
#   Avg     平均延迟
#   Best    最好延迟
#   Wrst    最差延迟
#   StDev   标准差（抖动）
```

#### （3）iperf3 — 带宽测试

```bash
# ⚠️ 压测会占满带宽，仅限授权环境，建议在维护窗口进行

# 服务端（接收端）
iperf3 -s                      # 启动服务端，监听默认 5201 端口
iperf3 -s -p 8080              # 指定端口
iperf3 -s -D                   # 后台守护进程方式运行🔑

# 客户端（发送端）
iperf3 -c server-ip            # 基本测试（默认 10 秒）
iperf3 -c server-ip -t 60      # 测试 60 秒
iperf3 -c server-ip -b 100M    # 限制带宽 100Mbps（默认尽可能跑满）
iperf3 -c server-ip -P 8       # 8 个并发流
iperf3 -c server-ip -R         # 反向测试（服务器发，客户端收）
iperf3 -c server-ip -u         # UDP 测试（看抖动和丢包）
iperf3 -c server-ip -u -b 1G   # UDP 1Gbps 测试
iperf3 -c server-ip -M 1400    # 指定 MSS
iperf3 -c server-ip -N         # 禁用 Nagle 算法
iperf3 -c server-ip -Z         # 使用 zerocopy（更高性能）
iperf3 -c server-ip -J         # JSON 格式输出（便于解析）

# 常见测试组合：
# 单流 TCP 测试（看单连接最大带宽）
iperf3 -c server-ip -t 30

# 多流 TCP 测试（看总带宽，更接近实际）
iperf3 -c server-ip -P 8 -t 30

# UDP 测试（看抖动和丢包率）
iperf3 -c server-ip -u -b 500M -t 30

# 双向同时测试
iperf3 -c server-ip --bidir -t 30
```

#### （4）curl — 应用层性能测试

```bash
# 测试 HTTP 请求的各阶段耗时
curl -o /dev/null -s -w "
  DNS 解析: %{time_namelookup}s
  TCP 连接: %{time_connect}s
  TLS 握手: %{time_appconnect}s
  首字节:   %{time_starttransfer}s
  总时间:   %{time_total}s
  下载速度: %{speed_download} bytes/s
  HTTP 状态: %{http_code}
" https://example.com

# 常见选项：
curl -w "格式"            # 指定输出格式
curl -o /dev/null         # 不保存响应体
curl -s                   # 静默模式
curl -k                   # 跳过证书验证（⚠️ 仅测试用）
curl -v                   # 详细输出
curl --connect-timeout 5  # 连接超时 5 秒
curl --resolve example.com:443:1.2.3.4 https://example.com  # 指定 IP（绕过 DNS）
curl -H "Host: example.com" http://1.2.3.4  # 指定 Host 头
```

### 4.3 被动测量工具

#### （1）ss / netstat — 连接状态

```bash
ss -s                          # 连接统计汇总
ss -ti                         # TCP 内部信息（重传、RTT、cwnd 等）🔑
ss -tlnp                       # 监听端口
ss -ant                        # 所有 TCP 连接
ss -ant state time-wait | wc -l   # TIME_WAIT 数量

# 详细 TCP 信息（非常有用！）
ss -ti state established
# 输出包含：
#   rtt     平滑往返时间
#   rto     重传超时
#   cwnd    拥塞窗口
#   ssthresh 慢启动阈值
#   bytes_acked   已确认字节数
#   bytes_received 接收字节数
#   segs_out 发送段数
#   segs_in  接收段数
#   data_segs_out  数据段数
#   delivery_rate  传输速率
#   busy      忙碌时间
```

#### （2）sar — 系统性能统计

```bash
# 安装
apt install sysstat
yum install sysstat
# 需要启用：/etc/default/sysstat 中 ENABLED="true"

# 网络统计
sar -n DEV 1 10               # 网卡统计，每 1 秒一次，共 10 次
sar -n EDEV 1 10              # 网卡错误统计
sar -n TCP 1 10               # TCP 统计
sar -n ETCP 1 10              # TCP 错误统计
sar -n SOCK 1 10              # 套接字使用
```

### 4.4 基准测试与基线

```
性能基线（Baseline）：正常情况下的性能数据，作为对比的参考。

为什么需要基线？
  - 出问题时，知道"正常"是什么样，才能判断哪里不正常
  - 容量规划的依据
  - 优化效果的对比标准

怎么建立基线？

1. 选择指标
   - 带宽利用率、延迟、丢包、重传率
   - 并发连接数、PPS
   - 错误率、队列长度

2. 收集数据
   - 至少收集 1~4 周的数据
   - 覆盖业务高峰和低谷
   - 覆盖工作日和周末

3. 分析统计
   - 平均值、峰值、95 百分位（95th percentile）
   - 正常范围（均值 ± 标准差）
   - 周期性规律（白天高峰、深夜低谷）

4. 建立基线
   - 正常范围：平均值 ± X%
   - 告警阈值：基于基线设定（如 > 峰值的 80%）
   - 定期更新基线（业务在变，基线也要更新）
```

### 4.5 监控与告警设计

| 指标 | 告警建议 | 说明 |
|------|---------|------|
| 带宽利用率 | > 80% 警告，> 90% 严重 | 看峰值，持续高说明需要扩容 |
| 丢包率 | > 1% 警告，> 5% 严重 | 影响传输质量和速度 |
| 重传率 | > 2% 警告，> 5% 严重 | 高重传说明网络质量差 |
| 延迟 | 比基线高 50% | 突然升高说明有问题 |
| 抖动 | > 30ms 警告 | 影响实时应用 |
| 连接数 | 接近上限 80% | 可能耗尽连接资源 |
| 错误包 | > 0.01% | 物理层问题（网线、光模块、网卡） |
| PPS | 接近设备上限 | 小包场景的瓶颈 |

### 5.4 tc 流量控制

**tc（Traffic Control）**：Linux 内核的流量控制工具，可以做限流、整形、排队规则、QoS 等。

```bash
# ⚠️ tc 规则错误配置可能导致网络中断或性能严重下降
# 生产环境务必先在测试环境验证，并有回滚方案

# ===== 基本概念 =====
# qdisc（队列规程）：每个网卡有一个发送队列，决定数据包怎么排队发送
# class（类）：qdisc 内的分类，不同类有不同的带宽限制
# filter（过滤器）：决定数据包属于哪个 class

# 常见 qdisc 类型：
#   pfifo_fast    默认，简单先进先出
#   tbf          令牌桶过滤器（限速用）
#   htb          分层令牌桶（分层限速，最常用）
#   fq_codel     Fair Queuing + CoDel（抗缓冲膨胀）
#   netem        网络模拟器（模拟延迟/丢包/乱序）

# ===== 查看当前配置 =====
tc qdisc show dev eth0          # 查看队列规程
tc class show dev eth0          # 查看类
tc filter show dev eth0         # 查看过滤器
tc -s qdisc show dev eth0       # 显示统计（发送、丢包等）🔑

# ===== 简单限速（TBF） =====
# 给整个网卡限速 100Mbps
tc qdisc add dev eth0 root tbf rate 100mbit burst 10kb latency 50ms

# 删除限速
tc qdisc del dev eth0 root

# ===== HTB 分层限速 =====
# 1. 添加根 qdisc
tc qdisc add dev eth0 root htb default 20

# 2. 添加根 class（总带宽 1000Mbps）
tc class add dev eth0 parent 1: classid 1:1 htb rate 1000mbit ceil 1000mbit

# 3. 子 class（不同业务不同带宽）
# 业务 A：保证 500Mbps，最高可到 800Mbps
tc class add dev eth0 parent 1:1 classid 1:10 htb rate 500mbit ceil 800mbit prio 0
# 业务 B：保证 200Mbps，最高可到 500Mbps
tc class add dev eth0 parent 1:1 classid 1:20 htb rate 200mbit ceil 500mbit prio 2

# 4. 用 filter 把流量分到不同 class
# 按源 IP
tc filter add dev eth0 parent 1: protocol ip prio 1 u32 match ip src 192.168.1.0/24 flowid 1:10
# 按目的端口
tc filter add dev eth0 parent 1: protocol ip prio 2 u32 match ip dport 80 0xffff flowid 1:20

# ===== netem 网络模拟（测试用） =====
# 模拟 100ms 延迟
tc qdisc add dev eth0 root netem delay 100ms

# 模拟延迟 + 抖动（100ms ± 20ms）
tc qdisc add dev eth0 root netem delay 100ms 20ms

# 模拟丢包 1%
tc qdisc add dev eth0 root netem loss 1%

# 模拟乱序（10% 的包延迟 50ms）
tc qdisc add dev eth0 root netem delay 10ms reorder 10%

# 模拟重复包
tc qdisc add dev eth0 root netem duplicate 1%

# 模拟损坏包
tc qdisc add dev eth0 root netem corrupt 0.1%

# 组合使用
tc qdisc add dev eth0 root netem delay 50ms 10ms loss 2%

# ===== 删除所有 tc 规则 =====
tc qdisc del dev eth0 root
```

> ⚠️ **tc 操作警告**：
> - 配置错误可能导致网络严重变慢或不通
> - 远程操作时，先设置定时回滚（如 sleep 60 && tc qdisc del dev eth0 root）
> - 先在测试环境验证，再到生产操作
> - netem 只能用于测试，不要在生产用（除非你就是要模拟差网络）

### 5.5 内核网络参数调优

```bash
# ⚠️ 内核参数调整有风险！
# - 先在测试环境验证
# - 修改前备份原始值
# - 逐步调整，观察效果
# - 临时调整改 /proc/sys，永久调整改 /etc/sysctl.conf

# ===== 查看当前值 =====
sysctl net.ipv4.tcp_congestion_control
cat /proc/sys/net/ipv4/tcp_congestion_control

# ===== 临时调整（重启失效） =====
sysctl -w net.ipv4.tcp_congestion_control=bbr

# ===== 永久调整 =====
# 编辑 /etc/sysctl.conf，然后 sysctl -p 生效

# ========== 核心调优参数 ==========

# 1. TCP 拥塞控制算法
net.ipv4.tcp_congestion_control = bbr
# 可选：cubic（默认）、bbr、reno、htcp 等
# BBR 在高带宽长延迟链路和一定丢包率下表现更好

# 2. 发送/接收缓冲区
net.core.rmem_max = 16777216     # 最大接收缓冲区（16MB）
net.core.wmem_max = 16777216     # 最大发送缓冲区（16MB）
net.ipv4.tcp_rmem = 4096 87380 16777216  # TCP 接收缓冲区（min default max）
net.ipv4.tcp_wmem = 4096 65536 16777216  # TCP 发送缓冲区
# 根据 BDP 调整，建议 max ≥ BDP
# 千兆网络 + 50ms RTT → BDP ≈ 6MB → 设 16MB 留余量

# 3. 连接队列
net.core.somaxconn = 65535       # 最大待处理连接数（listen backlog）
net.ipv4.tcp_max_syn_backlog = 65535  # SYN 半连接队列大小
# 高并发服务需要调大，不然 SYN 会丢

# 4. TIME_WAIT 相关
net.ipv4.tcp_tw_reuse = 1        # 允许重用 TIME_WAIT socket 用于新连接（客户端）
net.ipv4.tcp_fin_timeout = 30    # FIN-WAIT-2 超时时间
net.ipv4.tcp_max_tw_buckets = 262144  # 最大 TIME_WAIT 数量
# ⚠️ tcp_tw_recycle 已在 Linux 4.10+ 移除，不要用了

# 5. SYN Cookies（防 SYN Flood）
net.ipv4.tcp_syncookies = 1      # 启用 SYN Cookies
# 攻击时用正常连接也会受影响，但比拒绝服务强

# 6. TCP 快速打开
net.ipv4.tcp_fastopen = 3        # 3 = 启用客户端和服务端 TFO
# 减少连接建立的 RTT

# 7. 选择确认
net.ipv4.tcp_sack = 1            # 启用 SACK
net.ipv4.tcp_dsack = 1           # 启用 DSACK
# 有助于更高效的重传

# 8. 窗口缩放
net.ipv4.tcp_window_scaling = 1  # 启用窗口缩放（支持大窗口）
# 高带宽长延迟链路必须开

# 9. 反向路径过滤（防 IP 欺骗）
net.ipv4.conf.all.rp_filter = 1
# 1 = 严格模式，0 = 禁用，2 = 宽松模式

# 10. ICMP 相关
net.ipv4.icmp_echo_ignore_all = 0    # 是否忽略 ping（0=响应，1=忽略）
net.ipv4.icmp_echo_ignore_broadcasts = 1  # 忽略广播 ping（防 Smurf）

# 11. 源路由
net.ipv4.conf.all.accept_source_route = 0  # 不接受源路由
net.ipv6.conf.all.accept_source_route = 0

# 12. 网卡队列
net.core.netdev_max_backlog = 5000   # 网卡接收队列
# 高 PPS 场景需要调大

# 13. BBR 相关（用 BBR 时才需要）
net.core.default_qdisc = fq          # BBR 建议用 fq 队列
# fq_codel 也是好选择，抗 bufferbloat

# ===== 查看和应用 =====
sysctl -p                        # 应用 sysctl.conf 中的配置🔑
sysctl -a | grep tcp             # 查看所有 tcp 参数

# ===== 调优原则 =====
# 1. 不要盲目抄"网上最优配置"，每个场景不一样
# 2. 先了解当前值和瓶颈在哪里，再针对性调整
# 3. 一次只改几个参数，观察效果
# 4. 基准测试 + 对比测试，量化优化效果
# 5. 保留原始配置，随时可以回滚
```

> ⚠️ **内核参数调优警告**：
> - 不是所有参数都越大越好，太大可能浪费内存或有其他副作用
> - 不同内核版本参数行为可能不同，注意版本差异
> - 调优前先做基准测试，有基线才能比较优化效果
> - 生产环境修改务必在维护窗口进行，并有回滚方案

### 5.6 网卡高级特性

| 特性 | 英文 | 作用 | 查看/配置 |
|------|------|------|----------|
| **多队列** | RSS（Receive Side Scaling） | 接收时分发到多个 CPU 核，提升 PPS | `ethtool -l eth0` / `ethtool -L eth0 combined 8` |
| **RPS** | Receive Packet Steering | 软件实现的接收多队列（RSS 的软件版） | `/sys/class/net/eth0/queues/rx-0/rps_cpus` |
| **RFS** | Receive Flow Steering | 把同一流的包发到同一个 CPU，提高缓存命中率 | `/sys/class/net/eth0/queues/rx-0/rps_flow_cnt` |
| **XPS** | Transmit Packet Steering | 发送时选择 CPU，对应接收队列 | `/sys/class/net/eth0/queues/tx-0/xps_cpus` |
| **硬件卸载** | Offloading | 把校验和、分片、GSO 等交给网卡硬件做 | `ethtool -k eth0` / `ethtool -K eth0` |
| **GRO/LRO** | Generic/Large Receive Offload | 接收时合并小包，减少内核处理 | `ethtool -k eth0` |
| **TSO/GSO** | TCP/Generic Segmentation Offload | 发送时由网卡分片，提升大文件性能 | `ethtool -k eth0` |
| **XDP** | eXpress Data Path | 内核网络栈之前处理包（可编程、极高性能） | `ip link set dev eth0 xdp obj program.o` |
| **DPDK** | Data Plane Development Kit | 绕过内核，用户态直接驱动网卡，最高性能 | 需要 DPDK 支持的应用 |

```bash
# ===== 查看网卡特性 =====
ethtool -l eth0                 # 多队列数量
ethtool -k eth0                 # 硬件卸载特性
ethtool -g eth0                 # 环形缓冲区大小
ethtool -S eth0                 # 详细统计（每队列等）🔑

# ===== 调整多队列数量 =====
ethtool -L eth0 combined 8      # 设置 8 个队列（RX+TX 各 8）🔑
ethtool -L eth0 rx 8 tx 8       # 分别设置 RX 和 TX 队列数🔑

# ===== 调整环形缓冲区 =====
ethtool -G eth0 rx 4096 tx 4096  # 调大接收/发送环形缓冲区🔑
# 高 PPS 场景可能需要调大，减少丢包
# 但太大也不好，增加延迟和内存使用

# ===== 开关硬件卸载 =====
ethtool -K eth0 tso on gso on gro on rx on tx on sg on  # 开启常用特性🔑
# 一般默认都是开启的，关闭会降低性能

# ===== XDP 示例 =====
# XDP 是比较高级的功能，需要编程和特定内核版本支持
# 简单测试：xdp-loader（需要 xdp-tools 包）
```

## 六、优化方向

### 6.1 优化方法论

```
性能优化五步法：

  1. 建立基线
     → 了解当前性能水平
     → 确定关键指标和正常值

  2. 识别瓶颈
     → 测量和分析，找到瓶颈在哪里
     → 是带宽不够？还是延迟太高？还是丢包太多？
     → 瓶颈在哪个层面？物理/网络/协议/应用？

  3. 制定方案
     → 针对瓶颈提出优化方案
     → 预估优化效果和成本
     → 评估风险

  4. 实施和验证
     → 先在测试环境验证
     → 小范围灰度
     → 对比优化前后的性能数据

  5. 持续监控
     → 优化后持续监控
     → 确认没有副作用
     → 定期回顾和调整
```

### 6.2 各层优化方向

| 层面 | 优化方向 | 具体措施 | 适用场景 |
|------|---------|---------|---------|
| **物理层** | 链路升级 | 1G → 10G → 25G → 100G | 带宽瓶颈 |
| | 介质优化 | 铜缆换光纤、缩短距离 | 长距离、高带宽 |
| | 设备升级 | 换更高性能的交换机/路由器 | 设备性能瓶颈 |
| **链路层** | 网卡优化 | 多队列、硬件卸载、调大缓冲区 | 高 PPS、高并发 |
| | MTU 调整 | 增大 MTU（巨帧），减少协议开销 | 内部大流量场景 |
| | 链路聚合 | LACP 绑定多条链路，增加带宽和冗余 | 单链路不够用 |
| **网络层** | 路由优化 | 选更短的路径、BGP 调优 | 跨网/跨运营商 |
| | CDN | 内容分发到就近节点 | Web/视频/静态资源 |
| | 负载均衡 | 流量分散到多台服务器 | 单点带宽/连接不够 |
| **传输层** | 拥塞控制 | 换 BBR（高延迟/丢包场景） | 长肥管道、无线 |
| | 调大窗口 | 增加 TCP 缓冲区，匹配 BDP | 高带宽长延迟链路 |
| | 连接复用 | Keep-Alive、连接池 | Web/API 类应用 |
| | TCP 快速打开 | TFO 减少连接建立 RTT | 短连接多的场景 |
| **应用层** | 协议优化 | HTTP/2 → HTTP/3 | Web 应用 |
| | 数据压缩 | gzip/brotli 压缩 | 文本类内容 |
| | 缓存 | CDN、浏览器缓存、服务端缓存 | 重复请求多的 |
| | 协议效率 | 二进制协议（gRPC/Protobuf） | 高并发 API |
| | 优化请求数 | 合并请求、减少资源数 | Web 页面 |
| **架构层** | 就近部署 | 多地域部署、边缘计算 | 用户分布广 |
| | 横向扩展 | 加机器、负载均衡 | 单机不够 |
| | 网络优化 | VPC  peering、专线 | 云/多机房 |

### 6.3 常见瓶颈定位

```
常见网络性能瓶颈排查思路：

  问题：带宽跑不满？
    → 检查 RTT 和窗口大小（BDP 计算）
    → 检查丢包和重传率（高丢包跑不满）
    → 检查 CPU（软中断/用户态是否跑满）
    → 检查网卡 PPS 上限（小包场景）
    → 检查是不是应用本身处理不过来

  问题：延迟太高？
    → 用 traceroute/mtr 看哪一跳延迟高
    → 是物理距离远（正常）还是中间节点有问题
    → 检查是不是有拥塞（队列长、丢包）
    → 检查应用处理时间（TTFB 高可能是应用慢）

  问题：丢包严重？
    → 看是哪一段丢（用 mtr）
    → 带宽拥塞（队列满了丢包）
    → 设备性能不够（PPS 上限）
    → 物理层问题（错误包、CRC 错误）
    → 防火墙/安全设备丢包

  问题：连接建立慢？
    → RTT 高（物理距离远）
    → SYN 丢包（SYN 队列满、攻击）
    → DNS 解析慢
    → TLS 握手慢（证书链、计算慢）

  问题：时好时坏（抖动大）？
    → 网络拥塞（高峰期更严重）
    → 路由不稳定（路径变化）
    → 无线/移动网络（信号变化）
    → 中间设备性能波动
```

### 6.4 容量规划

```
容量规划步骤：

1. 了解当前
   - 当前流量：峰值/均值/增长趋势
   - 当前利用率：带宽/连接数/PPS/设备 CPU
   - 业务增长预测

2. 设定目标
   - 性能目标（延迟、丢包、可用性）
   - 业务目标（用户数、流量增长）
   - 预算范围

3. 计算需求
   - 带宽需求 = 峰值流量 × 冗余系数（1.5~2 倍）
   - 连接数 = 并发用户 × 每用户连接数
   - PPS = 带宽 / 平均包大小

4. 选型和架构
   - 设备选型（端口、带宽、性能）
   - 架构设计（冗余、负载均衡、多链路）
   - 升级路线（分阶段扩容）

5. 验证和调整
   - 压测验证
   - 上线后监控
   - 定期回顾和调整
```

## 七、安全与风险

### 7.1 性能测试的风险

| 风险 | 说明 | 防范措施 |
|------|------|---------|
| **业务中断** | 压测占满带宽/连接，正常业务受影响 | 维护窗口进行、限制速率、先小后大 |
| **触发告警** | 异常流量触发安全设备告警 | 提前通知安全团队，加白名单 |
| **设备过载** | 压测超过设备能力，导致丢包/宕机 | 逐步加压、监控设备状态 |
| **误伤其他业务** | 共享链路上影响其他业务 | 确认链路独享或协调时间 |
| **违反规定** | 未授权的网络测试可能违规 | 明确授权、在批准的范围内测试 |

### 7.2 抓包的风险

| 风险 | 说明 | 防范措施 |
|------|------|---------|
| **隐私泄露** | 抓包内容可能包含密码、个人信息等敏感数据 | 最小化原则、加密存储、及时删除 |
| **合规风险** | 个人数据/通信受法律保护，随意抓包可能违法 | 授权、匿名化、仅限必要范围 |
| **性能影响** | 抓包本身消耗 CPU 和磁盘 IO | 控制抓包范围、用过滤表达式、专用设备 |
| **数据泄露** | 抓包文件泄露造成更大范围信息泄露 | 加密存储、权限控制、用完即删 |

### 7.3 内核参数调整的风险

| 风险 | 说明 | 防范措施 |
|------|------|---------|
| **系统不稳定** | 参数设置不当导致系统崩溃/性能下降 | 先测试、逐步调、监控状态 |
| **内存耗尽** | 缓冲区/队列设太大，占太多内存 | 计算内存使用，不要超出物理内存 |
| **配置不持久** | 只改了 /proc/sys，重启就没了 | 同步更新 /etc/sysctl.conf |
| **兼容性问题** | 不同内核版本参数行为不同 | 查文档、确认内核版本支持 |
| **副作用** | 解决一个问题引出另一个问题 | 全面测试，不只看单一指标 |

### 7.4 安全操作原则

```
网络性能测试与调优安全操作原则：

1. 授权原则
   □ 明确的书面授权
   □ 批准的范围（IP、时间、带宽）
   □ 指定的负责人

2. 最小影响原则
   □ 优先在测试环境做
   □ 生产环境选低峰/维护窗口
   □ 从低强度开始，逐步加大
   □ 设置停止条件（影响业务立即停）

3. 备份与回滚
   □ 修改前备份原始配置
   □ 准备好回滚方案和脚本
   □ 远程操作设置定时回滚
   □ 保持备用连接不关闭

4. 监控与验证
   □ 全程监控性能和业务指标
   □ 前后对比，量化效果
   □ 确认没有副作用
   □ 文档化操作和结果

5. 合规与隐私
   □ 抓包遵守隐私法规
   □ 敏感数据妥善处理
   □ 测试数据安全存储和删除
   □ 不超出授权范围
```
