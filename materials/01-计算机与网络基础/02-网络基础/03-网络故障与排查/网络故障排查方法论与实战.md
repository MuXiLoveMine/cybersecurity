## 一、故障排查的定义与目标

### 1.1 什么是网络故障排查

**网络故障排查（Network Troubleshooting）**：当网络出现问题时，通过系统的方法收集信息、分析现象、定位原因、修复问题并防止再次发生的过程。

```
故障排查不是"碰运气"，而是一门系统性的科学——
  收集信息 → 分析假设 → 验证假设 → 定位根因 → 修复验证 → 复盘改进
```

### 1.2 排查的四大目标

| 目标 | 优先级 | 说明 |
|------|--------|------|
| **快速恢复业务** | P0 最高 | 先止损，再排查。业务恢复是第一优先级 |
| **定位根本原因** | P1 | 不只是解决现象，要找到根因（Root Cause） |
| **防止再次发生** | P2 | 加固、监控、告警，避免同样的问题再来一次 |
| **沉淀知识** | P3 | 记录到知识库，让其他人也能快速解决 |

### 1.3 相关概念辨析

| 概念 | 英文 | 说明 | 关系 |
|------|------|------|------|
| **故障** | Incident / Outage | 服务不可用或性能下降的事件 | 最严重，需要立即处理 |
| **问题** | Problem | 反复出现或潜在的故障根源 | 一个问题可能导致多个故障 |
| **变更** | Change | 任何配置/代码/环境的改变 | 70%+ 的故障由变更引起 |
| **事件** | Event | 任何值得注意的事情 | 不一定是故障（也可能是正常的） |

> **经验数据**：约 70%~80% 的生产故障是由变更引起的（发布、配置修改、扩容、基础设施变更等）。所以排查的第一问往往是：**"最近改了什么？"**

## 二、排查原则与方法论

### 2.1 分层排查法（OSI 七层模型）

这是最经典也是最有效的排查方法——从最底层开始，逐层往上验证，哪层出了问题就在哪一层重点排查。

```
OSI 七层排查顺序（从下到上）：

  7. 应用层   ← 最后查（DNS/HTTP/应用程序）
  6. 表示层
  5. 会话层
  4. 传输层   ← 端口/TCP/UDP/连接状态
  3. 网络层   ← IP/路由/ICMP/ping/traceroute
  2. 数据链路层 ← MAC/ARP/VLAN/交换机
  1. 物理层   ← 最先查（线缆/光模块/网卡/指示灯）

  原则：下面的层出问题，上面的肯定不通
        先确保下层是好的，再查上层
```

| 排查方向 | 适用场景 | 优点 | 缺点 |
|---------|---------|------|------|
| **从下到上** | 完全不通的场景 | 系统、不遗漏 | 慢，要一层一层查 |
| **从上到下** | 应用有问题但网络似乎通的 | 直接关联业务现象 | 可能漏掉底层问题 |
| **中间切入** | 有一定经验，先猜最可能的层 | 快 | 依赖经验，可能漏 |
| **分而治之** | 范围大的故障（两端中间切） | 快速缩小范围 | 需要多点信息 |

### 2.2 核心排查原则

| 原则 | 说明 |
|------|------|
| **先查变更** | 70%+ 的故障由变更引起，先问"最近改了什么" |
| **先查链路** | 物理层是基础，线断了啥都白搭 |
| **先近后远** | 先查本地（自己的机器），再查远端 |
| **先易后难** | 先检查容易验证的，再查复杂的 |
| **最小改动验证** | 每次只改一个变量，不然不知道是哪个起作用了 |
| **止损优先** | 先恢复业务，再慢慢查根因（能切流量先切流量） |
| **对比法** | 好的和坏的对比，找差异 |
| **复现法** | 能复现的问题最好查，尝试复现 |
| **二分法** | 每次排除一半的可能性，快速缩小范围 |
| **假设-验证** | 提出假设 → 设计验证方法 → 验证或排除 |

### 2.3 排查的常见误区

| 误区 | 问题 | 正确做法 |
|------|------|---------|
| **盲目试错** | 乱改一通，问题没解决还引入新问题 | 先收集信息，有假设再验证 |
| **只看表象** | 重启/切流量解决了就完事了 | 一定要找根因，防止再发 |
| **上来就抓包** | 抓了一大堆包不知道看什么 | 先定位大概范围，再有针对性地抓 |
| **忽略最近变更** | 不查变更记录，埋头排查 | 第一时间问"最近改了什么" |
| **同时改多个地方** | 改了一堆配置，不知道哪个有用哪个有害 | 每次只改一个变量，改完验证 |
| **不记录过程** | 排查完了记不住做了什么 | 边查边记，最后写排查报告 |
| **过早下结论** | 看到一点线索就认定是根因 | 多问几个"为什么"，验证清楚 |

## 三、标准排查流程

### 3.1 六步排查法

```
┌─────────────────────────────────────────────────────────┐
│                                                         │
│  1. 信息收集  →  搞清楚发生了什么                         │
│      现象是什么？什么时候开始的？影响范围多大？             │
│      最近有什么变更？是持续的还是间歇性的？                 │
│                                                         │
│  2. 范围界定  →  搞清楚影响多大                           │
│      单点还是多点？单用户还是全量？                       │
│      一个业务还是多个业务？一个机房还是多个？              │
│                                                         │
│  3. 分层验证  →  逐层排查定位问题层                        │
│      物理层 → 链路层 → 网络层 → 传输层 → 应用层           │
│      每层用对应的工具和方法验证                            │
│                                                         │
│  4. 假设与验证 → 提出假设，逐个验证排除                     │
│      可能的原因有哪些？怎么验证？                          │
│      每次验证一个假设，排除或确认                          │
│                                                         │
│  5. 修复与验证 → 修复并确认业务恢复                        │
│      修复方案是什么？回滚方案是什么？                      │
│      修复后验证业务确实恢复了                              │
│                                                         │
│  6. 复盘与改进 → 总结经验，防止再发生                      │
│      根因是什么？怎么避免下次再出？                        │
│      加监控/告警？加自动化恢复？                           │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 3.2 第一步：信息收集（5W2H）

| 维度 | 问题 | 为什么重要 |
|------|------|-----------|
| **What（什么现象）** | 具体是什么故障现象？报错信息是什么？ | 明确问题是什么 |
| **When（什么时候）** | 什么时候开始的？持续了多久？是一直坏还是时好时坏？ | 和什么事件时间上吻合（变更/流量高峰） |
| **Where（哪里）** | 哪些地方有问题？哪些地方正常？ | 界定范围，判断是局部还是全局 |
| **Who（谁受影响）** | 哪些用户/业务受影响？谁没受影响？ | 定位范围，找共同特征 |
| **Why（可能原因）** | 最近有什么变更？有什么异常事件？ | 70% 的故障由变更引起 |
| **How（怎么表现）** | 怎么表现的？错误码/错误信息是什么？ | 具体的报错是线索 |
| **How much（影响多大）** | 影响多少用户/多少业务？损失多大？ | 评估优先级，决定投入多少资源 |

**关键问题清单**：
```
□ 故障现象描述（越具体越好）
□ 开始时间（精确到分）
□ 影响范围（哪些用户、哪些业务、多大比例）
□ 是持续的还是间歇的？
□ 是越来越严重还是稳定的？
□ 正常的时候是什么样的？（有基线吗？）
□ 最近有没有变更（发布/配置/扩容/基础设施）？
□ 有没有相关的告警？
□ 有没有日志/报错信息？
□ 能复现吗？怎么复现？
```

### 3.3 第二步：范围界定

| 判断维度 | 方法 | 意义 |
|---------|------|------|
| **单点 vs 多点** | 多台机器测试 | 单点问题查本地，多点问题查网络/服务端 |
| **单用户 vs 全用户** | 不同用户/账号测试 | 单用户可能是账号问题，全用户是系统问题 |
| **单业务 vs 多业务** | 测试其他业务是否正常 | 单业务查应用，多业务查基础设施 |
| **内网 vs 外网** | 分别在内网和外网测试 | 判断是不是边界/出口问题 |
| **单向 vs 双向** | A 到 B 通不通？B 到 A 呢？ | 不对称说明有防火墙/路由问题 |
| **间歇性 vs 持续性** | 观察一段时间 | 间歇性可能是抖动/拥塞/负载相关 |

### 3.4 第三步：分层验证（快速决策树）

```
网络不通？
  │
  ├─ 先看本地：网卡灯亮不亮？ip 地址有没有？
  │     │
  │     ├─ 网卡没地址 → DHCP/静态配置问题
  │     └─ 有地址 → 继续
  │
  ├─ ping 网关通不通？
  │     │
  │     ├─ 不通 → 本地到网关之间有问题（链路/交换机/网关本身）
  │     └─ 通 → 继续
  │
  ├─ ping 外网 IP（如 8.8.8.8）通不通？
  │     │
  │     ├─ 不通 → 路由或出口问题（查路由表、traceroute）
  │     └─ 通 → 继续
  │
  ├─ ping 域名（如 example.com）通不通？
  │     │
  │     ├─ 不通（IP 能 ping 通但域名不行）→ DNS 问题
  │     └─ 通 → 继续
  │
  ├─ telnet/nc 端口通不通？
  │     │
  │     ├─ 不通 → 端口没开 / 防火墙拦截 / 服务没启动
  │     └─ 通 → 继续
  │
  └─ 应用层（curl/浏览器）通不通？
        │
        ├─ 不通（端口通但应用不通）→ 应用本身问题
        └─ 通 → 网络没问题，问题在更上层
```

### 3.5 第四步：假设与验证

```
假设验证法：

  1. 列出可能的原因（根据现象和经验）
     - 可能是网线坏了
     - 可能是防火墙加了新规则
     - 可能是 DNS 挂了
     - 可能是服务进程挂了
     - ...

  2. 按可能性排序（最可能的先验证）
     优先级参考：
       - 最近变更相关的 → 概率高，先查
       - 容易验证的 → 先查（快）
       - 影响范围匹配的 → 先查

  3. 逐个验证（每次只验证一个！）
     验证方法：
       - 直接检查（配置对不对？进程在不在？）
       - 对比法（好的和坏的比）
       - 替换法（换个东西试试）
       - 隔离法（去掉某个因素看看）

  4. 排除或确认
     - 验证了不是 → 排除，继续下一个
     - 验证了是 → 找到根因，进入修复

  关键：每次只改一个变量！
    同时改多个变量，就算好了也不知道是哪个起作用的
```

### 3.6 第五步：修复与验证

```
修复原则：

  1. 止损优先
     - 能切流量先切流量
     - 能回滚先回滚
     - 先恢复业务再说

  2. 最小化改动
     - 改最少的东西修复问题
     - 避免修复一个问题引入新问题

  3. 有回滚方案
     - 改之前想好怎么改回来
     - 备份原配置

  4. 充分验证
     - 功能验证：问题现象消失了吗？
     - 业务验证：业务真正恢复了吗？
     - 影响范围：有没有影响其他功能？
     - 持续观察：观察一段时间确保稳定
```

### 3.7 第六步：复盘与改进

**故障复盘（Postmortem）核心要素**：

| 要素 | 说明 |
|------|------|
| **时间线** | 故障从发生到恢复的完整时间线 |
| **现象** | 故障表现、影响范围和程度 |
| **根因** | 根本原因（不是表面原因，要多问几个为什么） |
| **处理过程** | 做了什么、什么时候做的、效果如何 |
| **改进措施** | 怎么防止下次再发生（技术+流程） |
| **经验教训** | 学到了什么、哪里做得好、哪里做得不好 |

> **5 Whys 分析法**：连续问 5 个"为什么"，挖到真正的根因。
>
> 例：网站打不开 → 为什么？服务 503 → 为什么？后端超时 → 为什么？数据库慢 → 为什么？慢查询 → 为什么？索引没建 → **根因：缺少索引导致慢查询，拖垮数据库**

## 四、分层排查与工具

### 4.1 物理层

| 检查项 | 工具/方法 | 说明 |
|--------|----------|------|
| **指示灯** | 看网卡/交换机端口的灯 | Link 灯亮不亮？Activity 灯闪不闪？ |
| **网线/光纤** | 换线测试、光功率计 | 物理介质损坏是常见原因 |
| **网卡状态** | `ip link show`、`ethtool` | 网卡状态、速度、双工模式 |
| **网卡统计** | `ethtool -S`、`ip -s link` | 错误包、丢弃包、CRC 错误 |
| **内核日志** | `dmesg`、`journalctl -k` | 网卡驱动报错、link up/down |
| **交换机端口** | 登录交换机查看 | 端口状态、错误统计、VLAN 配置 |

```bash
# ===== 物理层排查命令 =====

# 查看接口状态
ip link show eth0
ip -s link show eth0            # 带统计（收发包、错误、丢弃、CRC 等）🔑

# ethtool 查看网卡详细信息
ethtool eth0                    # 速度、双工、自动协商等
ethtool -i eth0                 # 驱动信息
ethtool -S eth0                 # 详细统计（每个队列的收发包、错误等）🔑
ethtool -g eth0                 # 环形缓冲区大小
ethtool -m eth0                 # 光模块信息（数字诊断）🔑

# 查看内核日志（网卡相关）
dmesg | grep -i eth
dmesg | grep -i link
dmesg | grep -i error

journalctl -k | grep -i eth     # systemd 系统
```

### 4.2 数据链路层

| 检查项 | 工具/方法 | 说明 |
|--------|----------|------|
| **ARP 表** | `ip neigh`、`arp -a` | IP → MAC 映射对不对？ |
| **MAC 地址** | `ip link`、`ifconfig` | 有没有冲突？ |
| **VLAN** | `ip link show`、交换机配置 | VLAN 配置对不对？Tag/Untag? |
| **交换机** | 登录交换机 | MAC 地址表、端口状态、VLAN |
| **抓包看二层** | `tcpdump -e` | 源/目的 MAC、VLAN tag |

```bash
# ===== 数据链路层排查命令 =====

# ARP 表
ip neigh show                   # 查看 ARP 表
ip neigh show 192.168.1.1       # 查看指定 IP 的 ARP
arp -a                          # 经典命令（net-tools）

# 清空/添加 ARP
ip neigh flush all              # 清空 ARP 表🔑
ip neigh add 192.168.1.1 lladdr 00:11:22:33:44:55 dev eth0  # 静态 ARP🔑

# 查看 MAC 地址
ip link show eth0
cat /sys/class/net/eth0/address

# 抓包看二层信息
tcpdump -i eth0 -e -n           # -e 显示链路层信息🔑
tcpdump -i eth0 -e arp          # 只看 ARP 报文🔑

# VLAN 信息
ip -d link show                 # 查看 VLAN 设备
cat /proc/net/vlan/config       # VLAN 配置（如果有）
```

### 4.3 网络层

| 检查项 | 工具/方法 | 说明 |
|--------|----------|------|
| **IP 地址** | `ip addr`、`ifconfig` | 地址对不对？掩码对不对？ |
| **路由表** | `ip route`、`route -n` | 默认网关在不在？路由对不对？ |
| **连通性** | `ping` | 能不能 ping 通？丢包率？延迟？ |
| **路径** | `traceroute`、`mtr` | 到哪一跳不通/丢包？ |
| **DNS** | `dig`、`nslookup`、`host` | 域名解析对不对？ |
| **路由环路** | `traceroute` 看跳数 | 跳来跳去就是环路了 |

```bash
# ===== 网络层排查命令 =====

# IP 地址和接口
ip addr show
ip addr show eth0

# 路由表
ip route show
ip route show table all
ip route get 8.8.8.8            # 查某个地址走哪条路由
route -n                        # 经典命令（net-tools）

# ping 测试
ping 8.8.8.8
ping -c 100 8.8.8.8             # 发 100 个包
ping -i 0.2 8.8.8.8             # 间隔 0.2 秒
ping -s 1400 -M do 8.8.8.8     # 1400 字节 + 不分片（测 MTU）
ping -f 192.168.1.1             # Flood ping（需 root🔑，压力测试用）

# 路由跟踪
traceroute 8.8.8.8
traceroute -I 8.8.8.8           # 用 ICMP
traceroute -T -p 443 8.8.8.8    # 用 TCP 443（绕过防火墙）
traceroute -n 8.8.8.8           # 不解析域名（更快）
traceroute -m 30 8.8.8.8        # 最大跳数 30

# mtr（综合 ping + traceroute，持续监控）
mtr 8.8.8.8                     # 交互模式
mtr -r 8.8.8.8                  # 报告模式
mtr -rw -c 100 8.8.8.8          # 100 个包后输出报告
mtr --tcp --port 443 8.8.8.8    # TCP 443 端口

# DNS 测试
dig example.com
dig @8.8.8.8 example.com        # 指定 DNS 服务器
dig +trace example.com          # 跟踪完整解析过程
dig -x 8.8.8.8                  # 反向解析
nslookup example.com
host example.com
```

### 4.4 传输层

| 检查项 | 工具/方法 | 说明 |
|--------|----------|------|
| **端口监听** | `ss -tulnp`、`netstat -ano` | 服务有没有在监听？ |
| **连接状态** | `ss -ant`、`netstat -an` | 连接建没建立？在什么状态？ |
| **端口连通性** | `nc -vz`、`telnet` | 端口能不能连上？ |
| **TCP 状态统计** | `ss -s` | 各种状态的连接数 |
| **TCP 详情** | `ss -ti` | RTT、重传、拥塞窗口等 |
| **防火墙** | `iptables -L`、`firewall-cmd` | 有没有被防火墙挡了？ |
| **抓包分析** | `tcpdump`、Wireshark | 握手过程、重传、丢包 |

```bash
# ===== 传输层排查命令 =====

# 查看监听端口
ss -tulnp                       # 所有监听的 TCP/UDP 端口 + 进程🔑
ss -tlnp                        # 只看 TCP
ss -ulnp                        # 只看 UDP
netstat -tulnp                  # 经典命令

# 查看所有连接
ss -ant                         # 所有 TCP 连接
ss -anu                         # 所有 UDP
ss -ant state established       # 已建立的连接
ss -ant state time-wait         # TIME_WAIT 状态
ss -ant state close-wait        # CLOSE_WAIT 状态
ss -ant state syn-recv          # SYN_RECV（半连接）

# 连接统计
ss -s                           # 连接统计摘要

# TCP 内部信息（非常有用！）
ss -ti                          # 所有连接的 TCP 内部信息🔑
ss -ti state established | head -20
# 包含：rtt、cwnd、retrans、bytes_acked 等

# 端口连通性测试
nc -vz 192.168.1.100 22         # 测试 TCP 22 端口
nc -vz -u 192.168.1.100 53      # 测试 UDP 53 端口
nc -vz -w 3 192.168.1.100 22    # 超时 3 秒
telnet 192.168.1.100 80         # 经典 telnet 测试

# 防火墙检查
iptables -L -n -v               # iptables 规则🔑
iptables -t nat -L -n -v
nft list ruleset                # nftables 规则🔑
firewall-cmd --list-all         # firewalld🔑
ufw status verbose              # ufw

# 抓包分析（TCP 层）
tcpdump -i eth0 -n 'tcp port 80'
tcpdump -i eth0 -n 'tcp[tcpflags] & (tcp-syn|tcp-fin) != 0'  # SYN/FIN
```

## 五、常见故障与排查思路

### 5.1 物理层故障

| 故障 | 现象 | 可能原因 | 排查命令 | 修复建议 |
|------|------|---------|---------|---------|
| **链路完全断开** | ping 不通，网卡灯不亮 | 网线断了/没插好、光模块坏了、端口坏了 | `ip link`、`ethtool`、`dmesg` | 换线、换端口、换光模块 |
| **双工不匹配** | 通但很慢，大量错误和丢包 | 一端半双工一端全双工 | `ethtool eth0`、`ethtool -S` | 都设为自动协商，或两边手动设一致 |
| **CRC 错误多** | `errors` 计数增长 | 网线质量差、干扰、光功率低 | `ip -s link`、`ethtool -S` | 换线、检查光功率、排查干扰源 |
| **速率协商失败** | 协商成很低的速率 | 网线不行、兼容性问题 | `ethtool eth0` | 换合格的线、强制指定速率 |
| **网卡频繁 up/down** | 时断时续 | 驱动问题、硬件故障、电源 | `dmesg`、`journalctl -k` | 更新驱动、更换网卡 |

### 5.2 数据链路层故障

| 故障 | 现象 | 可能原因 | 排查命令 | 修复建议 |
|------|------|---------|---------|---------|
| **IP 冲突** | 时通时不通，两个机器一样的 IP | 静态 IP 重复、DHCP 分配冲突 | `arping`、`ip neigh`、抓包 | 改 IP、查 DHCP 地址池 |
| **ARP 欺骗** | 流量走了错误的网关，时断时续 | 局域网内 ARP 攻击/欺骗 | `arp`、`arping`、抓包 | 静态 ARP、DAI、端口安全 |
| **VLAN 配置错误** | 同 VLAN 不通，或不同 VLAN 能通 | 端口 VLAN 配错、Trunk 配置错 | 交换机查看、`tcpdump -e` 看 tag | 修正 VLAN 配置 |
| **MAC 地址表溢出** | 交换机性能下降，大量泛洪 | MAC 攻击、网络太大 | 交换机查看 MAC 表 | 端口安全、限制 MAC 数量 |

### 5.3 网络层故障

| 故障 | 现象 | 可能原因 | 排查命令 | 修复建议 |
|------|------|---------|---------|---------|
| **IP 地址配置错** | 同网段不通，ping 不通自己网关 | IP/掩码/网关配错了 | `ip addr`、`ip route` | 修正 IP 配置 |
| **网关不可达** | 只能访问同网段，上不了外网 | 网关挂了、链路不通 | `ping 网关`、`arp` | 排查网关设备和链路 |
| **路由错误** | 某些网段不通，或走了错误的路径 | 静态路由配错、动态路由异常 | `ip route`、`traceroute`、`mtr` | 修正路由配置 |
| **路由环路** | traceroute 看到 IP 重复出现，TTL 耗尽 | 路由配置错误、动态路由收敛问题 | `traceroute`、`mtr` | 修正路由配置 |
| **DNS 解析失败** | IP 能 ping 通，域名不行 | DNS 服务器挂了、配置错了、污染 | `dig`、`nslookup`、`/etc/resolv.conf` | 检查 DNS 配置、换 DNS 服务器 |
| **MTU 问题** | 小包通，大包不通；能 ping 通但传文件卡 | 链路上 MTU 不一致，PMTUD 被挡 | `ping -s 1472 -M do`、`tracepath` | 调小 MTU、确保 ICMP 可达、MSS 钳制 |

### 5.4 传输层故障

| 故障 | 现象 | 可能原因 | 排查命令 | 修复建议 |
|------|------|---------|---------|---------|
| **端口不通** | telnet/nc 连不上 | 服务没启动、防火墙挡了、监听地址错了 | `ss -tulnp`、`nc -vz`、iptables | 启动服务、放通防火墙、改监听地址 |
| **连接建立慢** | 要等很久才能连上 | RTT 高、SYN 丢包、DNS 慢 | `curl -w`、抓包看握手 | 看是哪一步慢，针对性优化 |
| **TCP 重传高** | 速度慢、卡顿、时断时续 | 丢包、拥塞、链路质量差 | `nstat`、`ss -ti`、抓包 | 排查丢包原因、换拥塞控制 |
| **TIME_WAIT 过多** | 新连接建立不了，端口耗尽 | 短连接太多，端口不够用 | `ss -s`、`ss -ant state time-wait \| wc -l` | 开启 tcp_tw_reuse、长连接、调大端口范围 |
| **CLOSE_WAIT 堆积** | 连接数越来越多，服务越来越慢 | 应用没关闭连接（代码 bug） | `ss -ant state close-wait \| wc -l` | 修复应用代码，确保关闭连接 |
| **SYN Flood** | 大量 SYN_RECV，服务响应慢 | SYN 攻击、正常突发 | `ss -ant state syn-recv \| wc -l`、`netstat -s` | SYN Cookies、调大 syn_backlog、DDoS 防护 |
| **防火墙拦截** | 端口不通，SYN 没人回 | iptables/firewalld/安全组加了拒绝规则 | `iptables -L`、`firewall-cmd`、抓包看 SYN | 放通对应端口/IP |

### 5.5 应用层故障

| 故障 | 现象 | 可能原因 | 排查命令 | 修复建议 |
|------|------|---------|---------|---------|
| **DNS 解析慢/失败** | 打开网页慢，或直接解析失败 | DNS 服务器挂了、超时、污染、缓存 | `dig`、`nslookup`、`/etc/resolv.conf` | 换 DNS、检查 DNS 服务、配置多个 DNS |
| **HTTP 4xx 错误** | 400/401/403/404 等 | 客户端问题（权限、路径、参数） | `curl -v`、应用日志 | 检查请求参数、权限、URL |
| **HTTP 5xx 错误** | 500/502/503/504 等 | 服务端问题（挂了、超时、错误） | `curl -v`、应用日志、服务状态 | 查后端服务状态、错误日志 |
| **TLS 握手失败** | HTTPS 连不上，证书错误 | 证书过期、域名不匹配、协议不支持 | `openssl s_client` | 更换证书、检查域名、调整 TLS 配置 |
| **DHCP 获取失败** | 拿不到 IP，169.254.x.x | DHCP 服务器挂了、没地址了、网络不通 | `dhclient`、抓包看 DHCP | 检查 DHCP 服务器、地址池、链路 |
| **连接被重置** | RST 包，连接突然断开 | 服务端主动断开、防火墙 reset | 抓包看 RST | 查服务端日志、防火墙配置 |

### 5.6 性能类故障

| 故障 | 现象 | 可能原因 | 排查命令 | 修复建议 |
|------|------|---------|---------|---------|
| **带宽跑不满** | 传输速度远低于带宽 | 丢包高、RTT 大窗口不够、CPU 瓶颈 | `iperf3`、`ss -ti`、`sar -n DEV` | 排查丢包、调大缓冲区、换 BBR |
| **延迟高** | ping 延迟高，操作卡顿 | 物理距离远、链路拥塞、路由绕远 | `mtr`、`traceroute` | 选更近的节点、CDN、路由优化 |
| **丢包严重** | 速度慢、卡顿、重传多 | 链路拥塞、设备故障、攻击 | `mtr`、`ping`、`nstat` 重传率 | 扩容、排查故障点、DDoS 防护 |
| **抖动大** | 视频/语音卡顿，游戏跳ping | 网络拥塞、队列波动 | `mtr`、`ping -f`（看延迟分布） | QoS、队列管理（fq_codel） |
| **PPS 瓶颈** | 小包场景下 CPU 高，带宽还没用满 | 小包太多，处理不过来 | `sar -n DEV`、`top`（看软中断） | 多队列/RSS、DPDK/XDP、调大队列 |

### 6.3 抓包排查

抓包是排查疑难杂症的利器，但要知道**什么时候抓**、**在哪抓**、**抓什么**。

```bash
# ===== 什么时候需要抓包？ =====
# - 其他工具都排查不出来时
# - 需要看协议细节时（握手、重传、应用协议）
# - 不确定是客户端还是服务端的问题时

# ===== 在哪抓？ =====
# - 客户端 + 服务端 两边同时抓（对比分析）
# - 防火墙/负载均衡两端（看有没有被改）
# - 尽量靠近故障点

# ===== 常用过滤表达式 =====

# 按主机
tcpdump host 192.168.1.100
tcpdump src host 192.168.1.100
tcpdump dst host 192.168.1.100

# 按端口
tcpdump port 80
tcpdump port 80 or 443
tcpdump src port 22
tcpdump dst port 443

# 按协议
tcpdump tcp
tcpdump udp
tcpdump icmp
tcpdump arp
tcpdump 'ip proto 6'  # TCP

# 组合
tcpdump 'tcp port 443 and host 192.168.1.100'
tcpdump 'icmp and src host 192.168.1.1'
tcpdump 'port 53 or port 80'

# TCP 标志位
tcpdump 'tcp[tcpflags] & tcp-syn != 0'     # SYN
tcpdump 'tcp[tcpflags] & tcp-rst != 0'     # RST
tcpdump 'tcp[tcpflags] & tcp-fin != 0'     # FIN
tcpdump 'tcp[tcpflags] == tcp-syn'         # 只有 SYN（连接请求）

# HTTP 相关（简单看内容）
tcpdump -A -s 0 'tcp port 80'              # ASCII 方式看 HTTP
tcpdump -X -s 0 'tcp port 80'              # 十六进制 + ASCII

# ===== 实用技巧 =====
# 只抓头（不抓数据内容），减少包大小
tcpdump -s 100 -w capture.pcap

# 按大小分割文件（避免单个文件太大）
tcpdump -w capture.pcap -C 100            # 每 100MB 一个文件
tcpdump -w capture.pcap -G 3600           # 每小时一个文件

# 后台抓包（不占用终端）
nohup tcpdump -i eth0 -w capture.pcap &

# 读取保存的文件
tcpdump -r capture.pcap
tcpdump -r capture.pcap -n 'tcp port 80'
tcpdump -r capture.pcap -c 100            # 只看前 100 个
```

> ⚠️ **抓包注意事项**：
> - 抓包可能包含敏感信息，注意合规和隐私
> - 生产环境抓包注意性能影响
> - 用过滤表达式减少抓包量
> - 抓包文件妥善保管，用完删除

### 6.5 性能排查

```bash
# ===== 快速性能检查 =====

# apt install nethogs / yum install nethogs

nstat -az | grep -i drop          # 内核协议栈丢弃
ss -s                             # 套接字丢弃
```

## 七、自动化与知识库

### 7.1 排查脚本示例

```bash
#!/bin/bash
# 快速网络健康检查脚本
# 用法：./network-health-check.sh [目标IP]

TARGET=${1:-8.8.8.8}
GATEWAY=$(ip route | grep default | awk '{print $3}')

echo "===== 网络健康检查 ====="
echo "目标: $TARGET"
echo "网关: $GATEWAY"
echo "时间: $(date)"
echo ""

# 1. 本地接口
echo "[1] 本地接口检查"
if ip link show | grep -q "state UP"; then
  echo "  ✅ 有接口是 UP 的"
  ip -br link show | grep UP
else
  echo "  ❌ 没有 UP 的接口！"
fi
echo ""

# 2. 网关连通性
echo "[2] 网关连通性检查"
if [ -n "$GATEWAY" ]; then
  if ping -c 3 -W 1 $GATEWAY > /dev/null 2>&1; then
    echo "  ✅ 网关 $GATEWAY 可达"
  else
    echo "  ❌ 网关 $GATEWAY 不可达！"
  fi
else
  echo "  ⚠️  没有找到默认网关"
fi
echo ""

# 3. DNS 检查
echo "[3] DNS 检查"
if dig +short +time=2 +tries=2 www.baidu.com > /dev/null 2>&1; then
  echo "  ✅ DNS 解析正常"
  echo "  www.baidu.com → $(dig +short www.baidu.com | head -1)"
else
  echo "  ❌ DNS 解析失败！"
  echo "  配置文件: $(cat /etc/resolv.conf | grep nameserver)"
fi
echo ""

# 4. 外网连通性
echo "[4] 外网连通性检查"
if ping -c 3 -W 1 $TARGET > /dev/null 2>&1; then
  loss=$(ping -c 10 -W 1 $TARGET 2>&1 | grep "packet loss" | awk '{print $6}')
  rtt=$(ping -c 10 -W 1 $TARGET 2>&1 | grep "rtt" | awk -F/ '{print $5}')
  echo "  ✅ $TARGET 可达"
  echo "  丢包率: $loss"
  echo "  平均延迟: ${rtt}ms"
else
  echo "  ❌ $TARGET 不可达"
  echo "  尝试 traceroute 看哪一跳不通："
  traceroute -n -m 10 -w 1 $TARGET 2>&1 | head -15
fi
echo ""

# 5. 监听端口
echo "[5] 监听端口"
ss -tulnp 2>/dev/null | head -20
echo ""

# 6. 连接统计
echo "[6] 连接统计"
ss -s 2>/dev/null | head -10
echo ""

echo "===== 检查完成 ====="
```

## 八、安全与风险

### 8.1 高风险操作警示

| 操作 | 风险 | 防范措施 |
|------|------|---------|
| `iptables -F`（清空规则） | 如果默认策略是 DROP，清空后立即断网 | 先 `iptables -P INPUT ACCEPT` 再清空，或设置定时回滚 |
| `ip link set down` | 接口关闭，网络中断 | 远程操作绝对不要关自己连的那个接口 |
| 修改路由（`ip route`） | 路由错了可能全网不通 | 先加新路由再删旧的，设置定时回滚 |
| 重启网络服务 | 网络短暂中断，可能起不来 | 维护窗口操作，准备好回退方案 |
| `ifconfig down` / `ip addr flush` | 清除 IP 地址，直接断网 | 远程操作禁用，或用控制台 |
| `tc qdisc add`（流量控制） | 配置错了网络变慢或不通 | 先测试，设置定时回滚 |
| 生产环境抓包 | 性能影响、隐私合规 | 过滤表达式减少抓包量，授权操作 |
| 压测（iperf3 等） | 占满带宽，影响正常业务 | 维护窗口、限速、授权 |
| 端口扫描（nmap） | 可能被当作攻击，触发告警 | 授权范围、低强度、通知安全团队 |
| 修改内核参数 | 系统不稳定、性能下降 | 先测试、逐步调、可回滚 |

### 8.2 生产环境操作原则

```
生产环境网络操作安全原则：

1. 授权原则
   □ 有明确的变更授权
   □ 在批准的时间窗口内操作
   □ 指定操作人和审核人

2. 备份原则
   □ 修改前备份原配置
   □ 记录当前状态（ip addr/route/iptables 等）
   □ 准备好回滚脚本

3. 最小影响原则
   □ 优先在测试环境验证
   □ 灰度操作（先一台/一部分）
   □ 低峰/维护窗口操作
   □ 准备好随时停止和回滚

4. 双验证原则
   □ 操作前两人确认命令
   □ 操作后两人确认结果
   □ 关键操作有复核人

5. 监控原则
   □ 操作过程中持续监控
   □ 确认没有异常影响
   □ 操作后观察一段时间再离开

6. 远程操作保命技巧
   □ 用 screen/tmux 防止 SSH 断开
   □ 设置定时回滚（at/cron）
   □ 保持一个备用连接不关闭
   □ 永远不要直接关自己正在用的接口
```

```
抓包和网络测试合规要点：

   □ 不对未授权的系统/网络进行测试
```

> **总结**：网络故障排查不是碰运气，而是有方法、有流程、有工具的系统性工作。从信息收集到范围界定，从分层验证到假设验证，从修复验证到复盘改进，形成完整的闭环。OSI 七层模型是排查的骨架——从物理层到应用层，逐层验证，哪层出问题就在哪层深入。ping、traceroute、mtr、ss、tcpdump、dig、curl 这些是排查的手术刀，要熟练掌握。而最重要的是排查的思维方式——先止损、再排查，先易后难、分层验证、每次只改一个变量、用数据说话。最后，故障不是坏事——每次故障都是一次学习和改进的机会，做好复盘、沉淀知识、加固监控，才能让系统越来越稳定。
