## 一、密码学概述

### 1.1 密码学的定义与目标

**密码学（Cryptography）** 是研究如何在有敌手的环境中安全通信和保护信息的学科。它来源于希腊语 kryptós（隐藏）和 gráphein（书写）。

| 核心目标 | 英文 | 说明 | 示例 |
|---------|------|------|------|
| **机密性** | Confidentiality | 只有授权方才能读取信息 | 加密消息，第三方截获也看不懂 |
| **完整性** | Integrity | 信息在传输/存储中不被篡改 | 收到消息后验证哈希，确保没被改过 |
| **认证** | Authentication | 确认对方身份是真实的 | 数字签名、证书验证 |
| **不可否认性** | Non-repudiation | 发送方无法否认自己发送过 | 数字签名，签了就赖不掉 |

> 记忆口诀：**CIA + N**（Confidentiality, Integrity, Authentication, Non-repudiation）

### 1.2 密码学在网络安全中的位置

```
网络安全体系
├── 应用安全
├── 网络安全
├── 系统安全
├── 数据安全
└── 密码学 ← 底层基础技术，支撑各层安全
    ├── 加密：保护数据机密性
    ├── 哈希：保护数据完整性
    ├── 签名：认证与不可否认
    ├── 协议：TLS、SSH、IPsec 等
    └── 密钥管理：密码学的"阿喀琉斯之踵"
```

密码学是网络安全的**底层基础技术**。TLS/SSL、VPN、磁盘加密、数字签名、区块链、HTTPS……几乎所有安全技术都建立在密码学之上。

### 1.3 密码学发展简史

| 时代 | 时间 | 代表 | 特点 |
|------|------|------|------|
| **古典密码** | 古代 ~ 19 世纪 | 凯撒密码、维吉尼亚密码、恩尼格玛机 | 手工/机械加密，基于字符替换和置换，安全性依赖算法保密 |
| **现代密码** | 1970s ~ 至今 | DES、AES、RSA、SHA、ECC | 计算机实现，Kerckhoffs 原则（安全依赖密钥而非算法），有严格的数学证明 |
| **后量子密码** | 2010s ~ 未来 | CRYSTALS-Kyber、CRYSTALS-Dilithium | 抗量子计算攻击，基于格/编码/哈希/多变量 |

**几个关键里程碑**：
- **1949**：香农发表《保密系统的通信理论》，密码学成为科学
- **1976**：Diffie-Hellman 密钥交换，公钥密码学诞生
- **1977**：DES 成为美国联邦加密标准
- **1977**：RSA 算法发表
- **2001**：AES 取代 DES 成为新标准
- **2015**：NIST 启动后量子密码标准化
- **2024**：NIST 发布首批后量子密码标准（CRYSTALS-Kyber 等）

### 1.4 密码学分支

```
密码学 (Cryptology)
├── 密码编码学 (Cryptography) — 如何加密
│   ├── 对称密码 (Symmetric)
│   │   ├── 分组密码 (Block Cipher)：AES、DES
│   │   └── 流密码 (Stream Cipher)：ChaCha20、RC4
│   ├── 非对称密码 (Asymmetric / Public-key)
│   │   ├── 加密：RSA、ElGamal
│   │   ├── 密钥交换：DH、ECDH
│   │   └── 数字签名：RSA、ECDSA、Ed25519
│   ├── 哈希函数 (Hash Function)：SHA-2、SHA-3、MD5
│   ├── 消息认证码 (MAC)：HMAC、CMAC
│   └── 密码协议 (Protocol)：TLS、SSH、IPsec
└── 密码分析学 (Cryptanalysis) — 如何破解
    ├── 唯密文攻击
    ├── 已知明文攻击
    ├── 选择明文攻击
    └── 侧信道攻击（时序、功耗、电磁）
```

> **Kerckhoffs 原则（柯克霍夫原则）**：
> 一个密码系统的安全性应该只依赖于密钥，而不依赖于算法的保密。
> 即使攻击者知道加密算法，只要不知道密钥，系统仍然是安全的。
> 这是现代密码学的基本原则——所有现代加密算法都是公开的。

## 二、对称加密

### 2.1 基本原理

**对称加密（Symmetric Encryption）**：加密和解密使用**同一个密钥**。

```
明文 (Plaintext)
    │
    ▼
┌─────────────┐
│  加密算法   │ ← 密钥 (Key)
└─────────────┘
    │
    ▼
密文 (Ciphertext)
    │
    ▼ （传输）
┌─────────────┐
│  解密算法   │ ← 相同的密钥
└─────────────┘
    │
    ▼
明文 (Plaintext)
```

**优点**：
- 速度快（通常比非对称加密快 100~1000 倍）
- 适合加密大量数据
- 硬件加速支持好（AES-NI 指令集）

**缺点**：
- **密钥分发问题**：如何安全地把密钥发给对方？
- 密钥数量多：N 个人两两通信需要 N×(N-1)/2 个密钥
- 不能提供不可否认性（双方都有密钥，说不清是谁发的）

### 2.2 常见对称加密算法

| 算法 | 密钥长度 | 块大小 | 状态 | 说明 |
|------|---------|--------|------|------|
| **DES** | 56 位 | 64 位 | ❌ 已淘汰 | 数据加密标准，太短，已被暴力破解 |
| **3DES** | 112/168 位 | 64 位 | ⚠️ 逐步淘汰 | 三重 DES，慢且不安全，NIST 2023 年弃用 |
| **AES-128** | 128 位 | 128 位 | ✅ 推荐 | 高级加密标准，安全高效 |
| **AES-192** | 192 位 | 128 位 | ✅ 可用 | 更高安全级别 |
| **AES-256** | 256 位 | 128 位 | ✅ 推荐（高安全） | 最高安全级别，政府/军事级 |
| **ChaCha20** | 256 位 | 流密码 | ✅ 推荐 | 流密码，软件性能好，移动设备友好 |

> **算法选择建议**：
> - 新系统优先用 **AES-256-GCM** 或 **ChaCha20-Poly1305**
> - 有 AES 硬件加速（AES-NI）的环境用 AES-GCM
> - 移动端/嵌入式等没有硬件加速的用 ChaCha20-Poly1305
> - **绝对不要**用 DES、3DES、RC4、Blowfish 等旧算法

### 2.3 工作模式

分组密码（如 AES）每次只能加密一个固定大小的数据块（128 位）。要加密任意长度的数据，需要**工作模式（Mode of Operation）**。

| 模式 | 全称 | 安全性 | 说明 |
|------|------|--------|------|
| **ECB** | Electronic Codebook | ❌ 极不安全 | 每个块独立加密，相同明文得到相同密文，泄露模式 |
| **CBC** | Cipher Block Chaining | ⚠️ 中等 | 每个明文块和前一个密文块异或，需要 IV；Padding Oracle 攻击 |
| **CFB** | Cipher Feedback | ⚠️ 中等 | 自同步流密码模式 |
| **OFB** | Output Feedback | ⚠️ 中等 | 流密码模式，错误不传播 |
| **CTR** | Counter | ✅ 好 | 计数器模式，并行加密，不需要 padding |
| **GCM** | Galois/Counter Mode | ✅✅ 推荐 | 认证加密（AEAD），同时提供机密性和完整性 |
| **CCM** | Counter with CBC-MAC | ✅ 好 | 另一种认证加密模式，IoT 常用 |

#### ECB 模式为什么不安全？

```
明文：AAA BBB AAA CCC
      │   │   │   │
ECB加密  │   │   │   │
      ▼   ▼   ▼   ▼
密文：XXX YYY XXX ZZZ
      ↑       ↑
    相同的明文块 → 相同的密文块
```

> 经典例子：ECB 模式加密的 Linux 企鹅图片，虽然加密了，但企鹅的轮廓依然清晰可见。因为相同颜色的像素块加密后还是相同的。

#### 认证加密（AEAD）

**AEAD（Authenticated Encryption with Associated Data）**：同时提供加密（机密性）和认证（完整性 + 数据源认证），还能保护关联数据（AD，不需要加密但需要完整性保护的数据）。

**推荐的 AEAD 算法**：
- **AES-256-GCM**：最常用，性能好，有硬件加速
- **ChaCha20-Poly1305**：软件性能好，移动端友好
- **AES-256-CCM**：资源受限环境（IoT）

```
AEAD 输入：
  - 明文 (Plaintext)
  - 密钥 (Key)
  - Nonce (一次性使用的随机数，GCM 中 12 字节)
  - 关联数据 (Associated Data, AD) — 不加密但要认证

AEAD 输出：
  - 密文 (Ciphertext)
  - 认证标签 (Tag) — 用于验证完整性
```

> **⚠️ 重要：Nonce（IV）绝对不能重用！**
> - GCM 模式下，同一个密钥 + 同一个 nonce = 灾难性后果
> - 攻击者可以计算出密钥流，伪造密文和标签
> - nonce 不需要保密，但必须唯一（96 位随机 nonce 对于随机生成来说碰撞概率极低）

### 2.4 密钥分发问题与解决方案

对称加密最大的问题是：**怎么安全地把密钥交给对方？**

| 解决方案 | 说明 | 适用场景 |
|---------|------|---------|
| **当面交换** | 物理方式传递密钥（U盘、纸质） | 安全级别极高、通信方少 |
| **Diffie-Hellman 密钥交换** | 在不安全信道上协商出共享密钥 | 大部分场景，TLS 用的就是这个 |
| **公钥加密对称密钥** | 用对方公钥加密对称密钥，发给对方 | 混合加密系统（HTTPS 等） |
| **密钥分发中心（KDC）** | 可信第三方分发密钥（如 Kerberos） | 企业内部、域环境 |
| **量子密钥分发（QKD）** | 利用量子力学原理分发密钥 | 高安全需求（理论上绝对安全） |

### 2.5 常见误区与安全建议

| 误区 | 问题 | 正确做法 |
|------|------|---------|
| 用 ECB 模式 | 相同明文块产生相同密文块，泄露模式 | 用 GCM 或 CBC 模式 |
| 固定 IV / 重用 IV | 可预测的 IV 导致安全问题 | IV 随机生成，每个消息唯一 |
| 加密但不认证 | 攻击者可以篡改密文 | 用 AEAD（GCM），同时加密和认证 |
| 自己实现加密算法 | 极易出错，有各种侧信道漏洞 | 用经过验证的库（OpenSSL、ring 等） |
| 用密码直接当密钥 | 密码熵不够，可暴力破解 | 用密钥派生函数（KDF）如 PBKDF2、Argon2 |
| 密钥硬编码在代码里 | 反编译就能拿到密钥 | 用 KMS、环境变量、配置文件加密 |

## 三、非对称加密

### 3.1 基本原理

**非对称加密（Asymmetric Encryption）**，也叫**公钥密码学（Public-key Cryptography）**，使用一对密钥：**公钥（Public Key）**和**私钥（Private Key）**。

```
密钥对生成：
    密钥生成算法 → 公钥 (PK) + 私钥 (SK)
    公钥可以公开，私钥必须保密
```

**两种用法**：

| 用法 | 操作 | 作用 |
|------|------|------|
| **公钥加密，私钥解密** | 发送方用接收方公钥加密 | 机密性：只有接收方的私钥能解密 |
| **私钥签名，公钥验证** | 发送方用自己私钥签名 | 认证 + 不可否认性：任何人都能用公钥验证 |

#### 公钥加密（机密性）

```
Alice 想给 Bob 发秘密消息：

1. Bob 生成密钥对，公钥公开，私钥自己保留
2. Alice 用 Bob 的公钥加密消息
3. 密文通过网络传输
4. Bob 用自己的私钥解密
5. 其他人即使截获密文，没有私钥也解不开
```

#### 数字签名（认证 + 不可否认性）

```
Alice 想让别人相信消息确实是她发的：

1. Alice 生成密钥对，公钥公开
2. Alice 用自己的私钥对消息签名
3. 消息 + 签名一起发送
4. Bob 用 Alice 的公钥验证签名
5. 验证通过 = 消息确实是 Alice 发的，且没被篡改
6. Alice 无法否认是她发的（只有她有私钥）
```

**优点**：
- 解决了密钥分发问题（公钥可以公开）
- 支持数字签名（认证 + 不可否认性）
- N 个人只需要 N 对密钥

**缺点**：
- 速度慢（比对称加密慢 100~1000 倍）
- 不适合加密大量数据
- 需要公钥基础设施（PKI）来管理公钥信任

### 3.2 常见非对称加密算法

| 算法 | 类型 | 安全密钥长度 | 速度 | 用途 |
|------|------|------------|------|------|
| **RSA** | 大整数分解 | 2048 位（最低）、3072 位（推荐）、4096 位（高安全） | 较慢 | 加密、签名、密钥交换 |
| **ECC** | 椭圆曲线 | 256 位 ≈ RSA 3072 位 | 较快 | 加密、签名、密钥交换 |
| **ECDSA** | 椭圆曲线签名 | P-256、P-384、ed25519 | 快 | 数字签名 |
| **Ed25519** | 椭圆曲线签名 | 256 位 | 很快 | 数字签名（高安全、高性能） |
| **DH** | 密钥交换 | 2048 位+ | 中 | 密钥协商 |
| **ECDH** | 椭圆曲线密钥交换 | P-256、X25519 | 快 | 密钥协商 |
| **ElGamal** | 离散对数 | 2048 位+ | 慢 | 加密（较少直接用） |

> **密钥长度安全性对比**（等效安全强度）：
>
> | 对称密钥 | RSA / DH | ECC |
> |---------|---------|-----|
> | 80 位 | 1024 位 | 160 位 |
> | 128 位 | 3072 位 | 256 位 |
> | 192 位 | 7680 位 | 384 位 |
> | 256 位 | 15360 位 | 521 位 |
>
> ECC 用更短的密钥达到同样的安全性，所以在移动和嵌入式设备上更有优势。

> **重要提醒**：GitHub 已于 2026 年 10 月起要求新上传的 RSA SSH 密钥至少 3072 位。低于 2048 位的 RSA 密钥已被认为不安全。

### 3.3 RSA 算法原理简介

RSA 基于**大整数分解难题**：把两个大质数相乘很简单，但把乘积分解回两个质数非常困难。

```
密钥生成：
1. 选两个大质数 p 和 q（如 2048 位）
2. 计算 n = p × q
3. 计算 φ(n) = (p-1) × (q-1)
4. 选 e，使得 1 < e < φ(n)，且 gcd(e, φ(n)) = 1（通常 e=65537）
5. 计算 d = e⁻¹ mod φ(n)（模逆元）

公钥：(n, e)
私钥：(n, d)

加密：c = m^e mod n
解密：m = c^d mod n

安全性基于：知道 n 和 e，很难算出 d（因为需要分解 n = p × q）
```

> 这只是概念性理解。实际中 RSA 有各种 padding 方案（PKCS#1 v1.5、OAEP），没有 padding 的原始 RSA 是不安全的。

### 3.4 混合加密（Hybrid Encryption）

实际系统中几乎从不单独使用非对称加密来加密大量数据（太慢了），而是用**混合加密**：

```
1. 生成一个随机的对称密钥（会话密钥）
2. 用对称加密（如 AES-256-GCM）加密大量数据
3. 用接收方的公钥加密这个对称密钥
4. 把"加密后的对称密钥 + 加密的数据"一起发给对方
5. 接收方用私钥解密出对称密钥，再用对称密钥解密数据
```

**为什么这样做？**
- 非对称加密（慢）只加密很短的对称密钥（256 位）
- 对称加密（快）加密大量数据
- 兼具安全性和性能

> 几乎所有实际的加密系统都是混合加密：
> - TLS/SSL：非对称加密交换密钥，对称加密传输数据
> - PGP/GPG：同上
> - 微信/WhatsApp 等加密聊天：同上
> - 磁盘加密：通常只用对称加密（密钥由密码派生或 TPM 保护）

## 四、哈希函数与消息认证

### 4.1 哈希函数基础

**哈希函数（Hash Function）**，也叫散列函数，把任意长度的输入转换成固定长度的输出（哈希值/摘要）。

```
任意长度输入 → 哈希函数 → 固定长度输出（哈希值/摘要）
  "hello"   →  SHA-256  →  2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

| 性质 | 说明 | 重要性 |
|------|------|--------|
| **确定性** | 相同输入总是得到相同输出 | ⭐⭐⭐⭐⭐ |
| **快速计算** | 能快速算出哈希值 | ⭐⭐⭐⭐ |
| **单向性（抗原像）** | 给定哈希值，很难反推出输入 | ⭐⭐⭐⭐⭐ |
| **抗第二原像** | 给定输入，很难找到另一个不同的输入有相同哈希 | ⭐⭐⭐⭐⭐ |
| **抗碰撞性** | 很难找到任意两个不同的输入有相同哈希 | ⭐⭐⭐⭐⭐ |
| **雪崩效应** | 输入微小变化导致输出巨大变化 | ⭐⭐⭐ |

### 4.2 常见哈希算法

| 算法 | 输出长度 | 状态 | 说明 |
|------|---------|------|------|
| **MD5** | 128 位 | ❌ 已破解 | 碰撞攻击可行，只能用于非安全场景（如文件去重） |
| **SHA-1** | 160 位 | ❌ 已破解 | 2017 年被攻破碰撞，不要再用于安全用途 |
| **SHA-224** | 224 位 | ✅ 安全 | SHA-2 家族，截断版本 |
| **SHA-256** | 256 位 | ✅ 推荐 | SHA-2 家族，最常用 |
| **SHA-384** | 384 位 | ✅ 安全 | SHA-2 家族，高安全 |
| **SHA-512** | 512 位 | ✅ 安全 | SHA-2 家族，最高安全 |
| **SHA3-256** | 256 位 | ✅ 推荐（新系统） | SHA-3 家族，基于 Keccak，结构不同更安全 |

> **算法选择建议**：
> - 新系统优先用 **SHA-256** 或 **SHA3-256**
> - 高安全需求用 **SHA-512** 或 **SHA3-512**
> - **绝对不要**用 MD5、SHA-1 做安全用途（签名、证书、密码哈希等）
> - MD5 和 SHA-1 可以用于非安全用途（如文件完整性校验、数据去重），但不推荐

### 4.3 消息认证码（MAC）

**MAC（Message Authentication Code）**：用一个密钥和消息生成一个认证标签，接收方用同一个密钥验证，确保消息的完整性和来源真实性。

| 类型 | 算法 | 说明 |
|------|------|------|
| **HMAC** | HMAC-SHA256、HMAC-SHA512 | 基于哈希函数的 MAC，最常用 |
| **CMAC** | AES-CMAC | 基于分组密码的 MAC |
| **GMAC** | AES-GMAC | GCM 模式的认证部分（只认证不加密） |
| **Poly1305** | ChaCha20-Poly1305 | 与 ChaCha20 配合的认证算法 |

**HMAC 原理**：
```
HMAC(K, m) = H((K ⊕ opad) || H((K ⊕ ipad) || m))

其中：
  K = 密钥
  m = 消息
  H = 哈希函数（如 SHA-256）
  ipad = 内部填充（0x36 重复）
  opad = 外部填充（0x5C 重复）
```

> HMAC vs 普通哈希 + 密钥：
> - 简单的 `hash(key + message)` 有长度扩展攻击等问题
> - HMAC 通过两次哈希 + 内外填充避免了这些问题
> - HMAC 是安全的，只要底层哈希函数是安全的

### 4.4 密码存储（密码哈希）

> **⚠️ 重要：密码绝对不能加密存储，必须哈希存储！**
> 加密是可逆的（有密钥就能解密），哈希是单向的。数据库被拖库后，加密的密码能被解密，哈希的密码（如果算法好）很难被还原。

| 算法 | 类型 | 状态 | 说明 |
|------|------|------|------|
| **MD5** | 普通哈希 | ❌ 极不安全 | 秒破，彩虹表/暴力破解 |
| **SHA-1** | 普通哈希 | ❌ 不安全 | 很快，可暴力破解 |
| **SHA-256** | 普通哈希 | ❌ 不安全（存密码） | 太快，GPU 每秒几十亿次 |
| **SHA-256 + 盐** | 加盐哈希 | ⚠️ 不够安全 | 还是太快，可针对单个用户暴力破解 |
| **PBKDF2** | KDF（密钥派生函数） | ✅ 可用 | 迭代很多次，故意变慢，NIST 推荐 |
| **bcrypt** | 专门的密码哈希 | ✅ 推荐 | 自适应，可调整 cost，有盐 |
| **scrypt** | 内存难函数 | ✅ 推荐 | 不仅慢还吃内存，抗 GPU/ASIC 攻击 |
| **Argon2** | 内存难函数 | ✅✅ 首选 | 密码哈希竞赛冠军，三种模式，最推荐 |

**密码哈希的核心要求**：
1. **单向**：不能从哈希反推出密码
2. **带盐**：每个密码用不同的盐，防止彩虹表
3. **慢**：计算要足够慢，让暴力破解成本太高
4. **可配置**：算力提升后可以调慢（迭代次数/内存/线程）

```
密码存储流程：
1. 用户注册 / 改密码时：
   - 生成一个随机盐（salt）
   - 用密码 + 盐 + 算法参数 计算哈希
   - 把 算法名 + 参数 + 盐 + 哈希值 存到数据库

2. 用户登录时：
   - 取出数据库中的哈希记录
   - 用同样的算法、参数、盐 + 用户输入的密码 计算哈希
   - 比较两个哈希是否相同
```

> **常见误区**：
> - ❌ 用 MD5/SHA-1 存密码（太不安全）
> - ❌ 用 SHA-256 不加盐存密码（彩虹表秒破）
> - ❌ 用 SHA-256 加固定盐（盐泄露后还是能批量破解）
> - ❌ 自己设计密码哈希算法（大概率有漏洞）
> - ✅ 用 bcrypt / scrypt / Argon2 这些专门的密码哈希算法

### 4.5 常见误区与安全建议

| 误区 | 问题 | 正确做法 |
|------|------|---------|
| MD5 用于密码存储 | 秒破 | 用 Argon2 / bcrypt / scrypt |
| 哈希不加盐 | 彩虹表攻击 | 每个用户单独的随机盐 |
| 用普通哈希存密码 | 太快，可暴力破解 | 用专门的密码哈希算法（慢哈希） |
| 密钥硬编码 | 反编译就能拿到 | 用 KMS、环境变量、配置加密 |
| 自己实现加密 | 极易出错 | 用经过验证的密码学库 |
| 用哈希代替加密 | 哈希是单向的，不能解密 | 需要解密的用加密，不需要解密的用哈希 |

## 五、数字签名与 PKI

### 5.1 数字签名原理

**数字签名（Digital Signature）**：私钥持有者对消息生成签名，任何人都可以用公钥验证签名的有效性。

```
签名过程（发送方 Alice）：
  消息 + Alice 的私钥 → 签名算法 → 数字签名
  （消息 + 签名）一起发送

验证过程（接收方 Bob）：
  消息 + 签名 + Alice 的公钥 → 验证算法 → 有效/无效
```

**数字签名提供的安全保证**：
1. **认证（Authentication）**：消息确实是签名者发的
2. **完整性（Integrity）**：消息在传输中没被篡改
3. **不可否认性（Non-repudiation）**：签名者不能否认自己签过

**常见数字签名算法**：

| 算法 | 安全级别 | 速度 | 说明 |
|------|---------|------|------|
| **RSA-PSS** | 2048 位（最低）/ 3072 位（推荐） | 慢 | RSA 签名，PSS padding 更安全 |
| **ECDSA P-256** | 128 位安全 | 较快 | 椭圆曲线数字签名算法，NIST 标准曲线 |
| **Ed25519** | 128 位安全 | 很快 | Edwards 曲线签名，高性能高安全，推荐 |
| **Ed448** | 224 位安全 | 快 | 更高安全级别的 Ed 系列 |

### 5.2 公钥基础设施（PKI）

**PKI（Public Key Infrastructure）** 是一套创建、管理、分发、使用、存储和撤销数字证书的体系，解决的核心问题是：**这个公钥真的是那个人的吗？**

```
信任模型：
  你信任 CA → CA 给 Alice 颁发证书 → 你信任 Alice 的公钥
```

#### PKI 组成

| 组件 | 英文 | 作用 |
|------|------|------|
| **证书颁发机构** | CA (Certificate Authority) | 颁发和管理数字证书（信任的根） |
| **注册机构** | RA (Registration Authority) | 验证申请者身份，代 CA 处理注册 |
| **证书库** | Certificate Repository | 存储和分发证书 |
| **证书吊销列表** | CRL (Certificate Revocation List) | 已吊销证书的列表 |
| **OCSP** | Online Certificate Status Protocol | 在线证书状态查询协议 |
| **终端实体** | End Entity | 证书的使用者（用户、服务器、设备） |

#### X.509 证书

X.509 是数字证书的标准格式，TLS/SSL 用的就是 X.509 证书。

```
X.509 证书包含：
  - 版本号（X.509 v3）
  - 序列号（CA 内唯一）
  - 签名算法（如 SHA256withRSA）
  - 颁发者（Issuer，CA 的名字）
  - 有效期（Not Before / Not After）
  - 主体（Subject，证书拥有者的名字）
  - 主体公钥信息（公钥 + 算法）
  - 扩展（SAN、密钥用法、基本约束等）
  - CA 的数字签名
```

#### 证书链与信任模型

```
根 CA (Root CA) — 自签名，最顶层，预装在操作系统/浏览器中
    ↑ 签发
中间 CA (Intermediate CA) — 由根 CA 签发，实际用于签发终端证书
    ↑ 签发
服务器证书 (End-entity Certificate) — 网站的证书

验证过程：
  服务器证书 → 用中间 CA 公钥验证 → 中间 CA 证书 → 用根 CA 公钥验证 → 根 CA（信任）
  整条链都验证通过，证书才可信
```

### 5.3 数字签名的应用场景

| 场景 | 说明 | 示例 |
|------|------|------|
| **TLS/SSL 证书** | 验证网站身份，加密传输 | HTTPS |
| **代码签名** | 验证软件来源和完整性 | Windows 驱动签名、iOS 应用签名 |
| **文档签名** | 电子文档签名，替代手写签名 | PDF 签名、电子合同 |
| **邮件签名** | S/MIME 邮件签名和加密 | Outlook S/MIME |
| **区块链** | 交易签名、钱包地址 | Bitcoin、Ethereum |
| **SSH 密钥** | 服务器认证、用户认证 | SSH 登录 |
| **DNSSEC** | DNS 记录签名，防篡改 | DNS 安全扩展 |

## 六、安全协议

### 6.1 TLS/SSL

**TLS（Transport Layer Security）** 是目前最重要的安全协议，用于在不可信网络上提供安全的通信通道。HTTPS 就是 HTTP over TLS。

| 版本 | 发布时间 | 状态 |
|------|---------|------|
| SSL 1.0 | 内部版本 | 从未发布 |
| SSL 2.0 | 1995 | ❌ 已淘汰 |
| SSL 3.0 | 1996 | ❌ 已淘汰（POODLE 漏洞） |
| TLS 1.0 | 1999 | ❌ 不推荐 |
| TLS 1.1 | 2006 | ❌ 不推荐 |
| **TLS 1.2** | 2008 | ✅ 仍广泛使用 |
| **TLS 1.3** | 2018 | ✅✅ 推荐（最新） |

#### TLS 1.2 握手流程（简化版）

```
Client                                              Server
  │                                                   │
  │ 1. ClientHello                                    │
  │    (支持的密码套件、随机数、扩展)                   │
  │ ────────────────────────────────────────────────▶ │
  │                                                   │
  │ 2. ServerHello                                    │
  │    (选定的密码套件、随机数)                         │
  │ 3. Certificate                                    │
  │    (服务器证书)                                    │
  │ 4. ServerKeyExchange (可选)                       │
  │    (DHE/ECDHE 密钥交换参数)                        │
  │ 5. ServerHelloDone                                │
  │ ◀──────────────────────────────────────────────── │
  │                                                   │
  │ 6. ClientKeyExchange                              │
  │    (预主密钥/密钥交换参数)                         │
  │ 7. ChangeCipherSpec                               │
  │ 8. Finished (加密)                                │
  │ ────────────────────────────────────────────────▶ │
  │                                                   │
  │ 9. ChangeCipherSpec                               │
  │ 10. Finished (加密)                               │
  │ ◀──────────────────────────────────────────────── │
  │                                                   │
  │ 握手完成，开始加密传输数据                           │
```

#### TLS 1.2 vs TLS 1.3

| 特性 | TLS 1.2 | TLS 1.3 |
|------|---------|---------|
| 握手往返次数 | 2-RTT | 1-RTT（0-RTT 恢复） |
| 支持的密码套件 | 几十个（很多不安全的） | 只有 5 个（全是安全的） |
| 不安全的算法 | 支持（RC4、3DES 等） | 全部移除 |
| 密钥交换 | RSA、DH、ECDH 等 | 仅支持 (EC)DHE（前向保密） |
| 握手消息加密 | 大部分明文 | 证书等消息加密 |
| 性能 | 较慢 | 更快（握手少一个 RTT） |
| 安全性 | 高（配置得当） | 更高（移除了很多坑） |

#### TLS 1.3 密码套件（只有 5 个）

```
TLS_AES_256_GCM_SHA384
TLS_CHACHA20_POLY1305_SHA256
TLS_AES_128_GCM_SHA256
TLS_AES_128_CCM_8_SHA256
TLS_AES_128_CCM_SHA256
```

> 全部是 AEAD（认证加密），全部支持前向保密。没有 RSA 密钥交换（不支持前向保密的都被移除了）。

#### OpenSSL 常用命令

```bash
# 生成 RSA 私钥
openssl genrsa -out private.key 2048

# 从私钥提取公钥
openssl rsa -in private.key -pubout -out public.key

# 生成证书签名请求（CSR）
openssl req -new -key private.key -out cert.csr

# 自签名证书
openssl req -x509 -newkey rsa:2048 -keyout key.pem \
  -out cert.pem -days 365 -nodes

# 查看证书信息
openssl x509 -in cert.pem -text -noout

# 测试网站 TLS 配置
openssl s_client -connect example.com:443

# 计算文件哈希
openssl dgst -sha256 file.txt

# 对称加密文件
openssl enc -aes-256-cbc -salt -in file.txt -out file.enc

# 对称解密文件
openssl enc -d -aes-256-cbc -in file.enc -out file.txt
```

### 6.2 SSH

**SSH（Secure Shell）** 是远程登录和安全传输的协议，替代了不安全的 Telnet、FTP、rlogin 等。

```
SSH 连接过程：
1. 版本协商：客户端和服务器协商 SSH 版本
2. 密钥交换：协商并生成会话密钥（DH/ECDH）
3. 服务器认证：客户端验证服务器主机密钥
4. 用户认证：服务器验证用户身份（密码/公钥/...）
5. 会话建立：加密通道建立，可以传输数据
```

**SSH 用户认证方式**：
- 密码认证（最不安全，容易暴力破解）
- 公钥认证（推荐，用非对称加密）
- 主机认证
- 多因素认证

```bash
# 生成 SSH 密钥对（ed25519，推荐）
ssh-keygen -t ed25519 -C "your_email@example.com"

# 生成 RSA 密钥对（2048 位最低，推荐 4096 位）
ssh-keygen -t rsa -b 4096

# 复制公钥到服务器
ssh-copy-id user@server

# SSH 登录
ssh user@server

# 安全配置建议（sshd_config）：
#   PermitRootLogin no          # 禁止 root 直接登录
#   PasswordAuthentication no   # 禁用密码登录
#   PubkeyAuthentication yes    # 启用公钥认证
#   Port 22 改为非默认端口       # 减少被扫描概率（安全通过隐匿，只是辅助）
```

### 6.3 IPsec

**IPsec（Internet Protocol Security）** 是在 IP 层提供安全通信的协议套件，常用于 VPN。

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **传输模式** | 只加密 IP 包的数据部分，IP 头不变 | 端到端通信（主机到主机） |
| **隧道模式** | 整个 IP 包被加密，再加一个新的 IP 头 | VPN（网关到网关） |

| 协议 | 作用 |
|------|------|
| **AH (Authentication Header)** | 提供认证和完整性，不加密 |
| **ESP (Encapsulating Security Payload)** | 提供加密 + 认证 + 完整性 |

### 6.4 DNSSEC

**DNSSEC（DNS Security Extensions）** 给 DNS 响应加上数字签名，确保 DNS 数据的完整性和真实性，防止 DNS 欺骗和缓存投毒。

```
DNSSEC 验证链：
  根 → TLD（.com/.net 等）→ 二级域名 → ... → 目标域名
  每一级都用父级的公钥验证签名
```

### 6.5 后量子密码（Post-Quantum Cryptography, PQC）

**量子计算的威胁**：Shor 算法可以在多项式时间内分解大整数和求解离散对数，这意味着 RSA、ECC、DH 这些目前主流的非对称算法在量子计算机面前都是不安全的。

**后量子密码**：抵抗量子计算攻击的密码算法，基于量子计算机也很难解决的数学问题。

| 类别 | 数学基础 | 代表算法 |
|------|---------|---------|
| **格密码** | 格上的最短向量问题（SVP/LWE） | CRYSTALS-Kyber（密钥封装）、CRYSTALS-Dilithium（签名） |
| **哈希基** | 哈希函数的安全性 | SPHINCS+（签名） |
| **编码基** | 纠错码译码问题 | Classic McEliece（密钥封装） |
| **多变量** | 多变量二次方程组 | Rainbow（签名，已被攻破） |
| **同源** | 椭圆曲线同源 | SIKE（已被攻破） |

**NIST 后量子标准化（2024 年发布首批标准）**：
- **密钥封装（KEM）**：CRYSTALS-Kyber（通用）、Classic McEliece（高安全）
- **数字签名**：CRYSTALS-Dilithium（通用）、SPHINCS+（基于哈希，无结构风险）、FALCON

**迁移策略**：
- 现在就开始准备：评估系统、升级库、做 POC
- **混合模式**：同时使用传统算法 + 后量子算法（一个被攻破还有另一个）
- 优先升级有"harvest now, decrypt later"风险的系统（数据需要保密几十年的）
- TLS 1.3 已经在集成后量子密钥交换（X25519 + Kyber）

> **"现在加密的数据，量子计算机出来后能解密吗？"**
> - 对称加密：AES-256 对量子计算机还是安全的（Grover 算法只是平方根加速，256 位变成 128 位安全，还是够的）
> - 非对称加密：RSA、ECC 会被 Shor 算法快速攻破
> - 所以：如果数据需要保密 10 年以上，现在就要考虑后量子安全
> - TLS 已经在向混合密钥交换迁移（X25519 + Kyber）

## 七、密钥管理

### 7.1 密钥管理的重要性

> **"密码系统中 90% 的问题是密钥管理问题。"**
>
> 密码学算法再强，如果密钥管理做得不好，整个系统还是不安全的。

```
密码系统安全性 = min(算法强度, 密钥管理强度)
```

最弱的环节决定了整体安全水平。

### 7.2 密钥生命周期

```
生成 → 分发 → 存储 → 使用 → 轮换 → 归档 → 销毁
  ↑                                               │
  └───────────────────────────────────────────────┘
              审计与监控贯穿整个生命周期
```

| 阶段 | 关键活动 | 安全要点 |
|------|---------|---------|
| **生成** | 使用密码学安全的随机数生成器（CSPRNG）生成密钥 | 足够的熵、不能用弱随机数 |
| **分发** | 安全地把密钥送到需要的地方 | 加密传输、身份认证、完整性验证 |
| **存储** | 安全地保存密钥 | 不能明文存在代码/数据库里，用 KMS/HSM |
| **使用** | 用密钥加密/解密/签名 | 最小权限、审计日志、内存中用完清零 |
| **轮换** | 定期更换密钥 | 限制单次密钥的暴露面 |
| **归档** | 旧密钥的安全归档 | 用于解密历史数据，安全存储 |
| **销毁** | 不再需要的密钥彻底销毁 | 不可恢复（特别是云存储中的密钥） |

### 7.3 密钥存储方案

| 方案 | 安全性 | 成本 | 适用场景 |
|------|--------|------|---------|
| 硬编码在代码里 | ❌ 极低 | 极低 | ❌ 绝对不要用 |
| 配置文件明文 | ❌ 低 | 极低 | ❌ 不推荐 |
| 环境变量 | ⚠️ 中 | 低 | 开发/测试环境 |
| 配置文件加密 | ✅ 较好 | 中 | 中小规模 |
| 密钥管理服务（KMS） | ✅✅ 好 | 中 | 生产环境推荐 |
| 硬件安全模块（HSM） | ✅✅✅ 最高 | 高 | 金融、政府、高安全需求 |
| 硬件令牌 / 智能卡 | ✅✅ 高 | 中 | 用户密钥、签名密钥 |

#### KMS（密钥管理服务）

KMS 是专门用于管理密钥的服务，通常提供：
- 密钥生成、存储、轮换
- 加密/解密 API（密钥永不离开 KMS）
- 访问控制（谁能用哪个密钥）
- 审计日志（谁什么时候用了密钥做什么）
- 高可用、容灾

**主流 KMS 产品**：
- 云厂商：AWS KMS、阿里云 KMS、Azure Key Vault、Google Cloud KMS
- 开源：HashiCorp Vault
- 商业：Thales、Entrust

#### HSM（硬件安全模块）

HSM 是专门的硬件设备，用于生成、存储和使用加密密钥，密钥永远不会离开 HSM 硬件。

- 物理防篡改（拆机会自毁）
- 经过认证（FIPS 140-2 Level 3/4）
- 性能高（有专门的加密芯片）
- 金融、政府、CA 等场景必须用 HSM

### 7.4 常见密钥管理错误

| 错误 | 风险 | 正确做法 |
|------|------|---------|
| 密钥硬编码在代码里 | 反编译/代码泄露 = 密钥泄露 | 用 KMS / 环境变量 / 加密配置 |
| 密钥和数据存在一起 | 数据库被拖库 = 密钥也丢了 | 密钥和数据物理分离 |
| 从不轮换密钥 | 密钥泄露后，所有数据都不安全 | 定期轮换，支持自动轮换 |
| 用密码直接当密钥 | 密码熵低，可暴力破解 | 用 KDF（PBKDF2/Argon2）从密码派生密钥 |
| 密钥备份不安全 | 备份泄露 = 密钥泄露 | 备份加密，分开存储，访问控制 |
| 没有审计日志 | 出了问题不知道谁用了密钥 | 所有密钥操作都有审计日志 |
| 权限过大 | 任何人都能访问密钥 | 最小权限原则，按需授权 |
| 自己实现密钥管理 | 极易出错 | 用成熟的 KMS / HSM |

## 十一、安全与合规

### 11.1 适用边界

- ✅ **学习研究**：学习密码学原理、算法和协议
- ✅ **安全加固**：在自己的系统中正确使用密码学保护数据
- ✅ **授权测试**：在获得明确书面授权的系统上进行密码学安全测试
- ✅ **防御研究**：研究密码学攻击是为了更好地防御
- ❌ **未授权破解**：破解他人的密码、加密文件、通信
- ❌ **恶意使用**：用密码学技术从事违法活动
- ❌ **自制算法用于生产**：自己设计的加密算法未经充分审查不要用在生产环境
- ❌ **弱算法用于新系统**：在新系统中使用已经不安全的算法（DES、MD5、SHA-1 等）

### 11.2 密码学安全使用原则

1. **不要自己实现密码学算法**
   - 使用经过广泛审查和验证的库（OpenSSL、ring、BoringSSL 等）
   - 自己实现的密码学算法几乎肯定有漏洞（包括侧信道漏洞）

2. **不要自己设计密码协议**
   - 使用标准协议（TLS 1.3、SSH 等）
   - 密码协议设计是专家的事，哪怕是专家也经常出错

3. **使用安全的算法和模式**
   - 对称加密：AES-256-GCM 或 ChaCha20-Poly1305
   - 非对称加密：RSA-3072+ 或 ECC（P-256/X25519）
   - 签名：Ed25519 或 RSA-PSS-3072+
   - 哈希：SHA-256 / SHA3-256
   - 密码存储：Argon2 / bcrypt / scrypt

4. **密钥管理是关键**
   - 密钥和数据分开存储
   - 用 KMS/HSM 管理密钥
   - 定期轮换密钥
   - 最小权限原则

5. **永远不要假设，要验证**
   - 不要自己觉得安全，要用工具和审计验证
   - 密码学安全的反面是"我觉得安全"

### 11.4 高风险操作警告

| 操作 | 风险 | 安全建议 |
|------|------|---------|
| 生成和管理根 CA 密钥 | 根密钥泄露 = 整个 PKI 沦陷 | 离线生成、HSM 存储、多人共管、冷备 |
| openssl 加密文件 | 弱密码/弱算法导致被破解 | 用强密码、AES-256-GCM、PBKDF2 迭代足够多次 |
| 密码破解（hashcat 等） | 违法风险 | 仅在授权环境使用，用于测试自己系统的密码强度 |
| 自签名证书用于生产 | 信任问题、无法吊销 | 生产环境用正规 CA 签发的证书 |
| 在线加密工具 | 敏感数据可能被记录 | 敏感数据不要用在线工具加密，用本地可信工具 |
| 密钥硬编码 | 代码泄露 = 密钥泄露 | 用 KMS、环境变量、加密配置 |
