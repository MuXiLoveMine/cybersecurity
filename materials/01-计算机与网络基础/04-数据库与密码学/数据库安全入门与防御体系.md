## 一、数据库安全概述

### 1.1 数据库安全的定义与目标

**数据库安全（Database Security）** 是指保护数据库及其数据免受未经授权的访问、使用、泄露、篡改和破坏的技术、流程和控制措施的集合。

| 核心目标（CIA 三要素 + 其他） | 说明 |
|-------------------------------|------|
| **机密性（Confidentiality）** | 只有授权用户才能访问敏感数据 |
| **完整性（Integrity）** | 数据在存储和传输过程中不被篡改 |
| **可用性（Availability）** | 授权用户在需要时能正常访问数据 |
| **不可否认性（Non-repudiation）** | 操作可追溯，用户无法否认自己的行为 |
| **合规性（Compliance）** | 满足法律法规和行业标准要求 |

数据库安全不仅是技术问题，也是管理问题和合规问题。

### 1.2 数据库安全在网络安全中的位置

```
应用层安全
  ├── Web 安全（前端/后端）
  ├── API 安全
  └── 数据库安全 ← 数据最后一道防线
      ├── 访问控制
      ├── 数据加密
      ├── 审计监控
      └── 漏洞防御
网络层安全
  ├── 防火墙
  ├── 网络隔离
  └── 传输加密
物理层安全
  ├── 机房安全
  └── 存储介质安全
```

> **关键地位**：数据库是数据的"金库"，是攻击者的最终目标之一。大量数据泄露事件的核心就是数据库被攻破。应用层防线被突破后，数据库安全是数据的最后一道防线。

### 1.3 与相关概念的关系

| 概念 | 说明 | 与数据库安全的关系 |
|------|------|-------------------|
| **数据安全** | 保护数据全生命周期的安全（采集、传输、存储、处理、销毁） | 数据库安全是数据安全的重要组成部分（存储和访问环节） |
| **应用安全** | 保护应用程序的安全（代码、配置、逻辑等） | 应用是访问数据库的入口，应用漏洞（如 SQL 注入）直接威胁数据库 |
| **网络安全** | 保护网络基础设施和通信的安全 | 网络层防护是数据库安全的外围防线（防火墙、隔离等） |
| **云安全** | 云计算环境下的安全 | 云数据库安全是数据库安全在云环境的延伸（RDS、云原生数据库） |
| **隐私保护** | 保护个人隐私信息 | 数据库中的个人信息保护是隐私保护的核心场景 |

|------|-----------|------|---------|

## 二、数据库面临的核心威胁

### 2.1 SQL 注入（SQL Injection）

**原理**：攻击者通过在输入中插入恶意 SQL 代码，欺骗数据库执行非预期的 SQL 操作。

**根本原因**：将用户输入直接拼接到 SQL 语句中，没有使用参数化查询。

```python
# ❌ 危险：字符串拼接（SQL 注入漏洞）
sql = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'"
cursor.execute(sql)

# 如果 username = admin' --
# SQL 变成：
# SELECT * FROM users WHERE username = 'admin' --' AND password = 'xxx'
# -- 后面被注释掉，直接绕过密码验证！

# ✅ 安全：参数化查询
sql = "SELECT * FROM users WHERE username = %s AND password = %s"
cursor.execute(sql, (username, password))
```

#### SQL 注入类型

| 类型 | 英文 | 原理 | 利用条件 | 难度 |
|------|------|------|---------|------|
| **联合注入** | UNION Injection | 用 UNION 拼接额外查询结果 | 页面回显查询结果 | ⭐⭐ 入门 |
| **报错注入** | Error-based | 构造错误使数据库报错并带出数据 | 错误信息显示在页面 | ⭐⭐⭐ 中级 |
| **布尔盲注** | Boolean-based Blind | 根据页面真假判断数据 | 页面有真假两种状态 | ⭐⭐⭐ 中级 |
| **时间盲注** | Time-based Blind | 根据响应时间判断数据 | 任何情况都能用，但慢 | ⭐⭐⭐⭐ 高级 |
| **堆叠注入** | Stacked Queries | 一次执行多条 SQL 语句 | 数据库支持多语句执行 | ⭐⭐⭐⭐ 高级 |

#### 注入点识别

| 位置 | 说明 |
|------|------|
| GET 参数 | URL 中的查询参数，如 `?id=1` |
| POST 参数 | 表单提交的参数 |
| Cookie | Cookie 中的值 |
| HTTP 头 | User-Agent、Referer、X-Forwarded-For 等 |
| JSON 字段 | JSON 格式请求体中的字段 |

#### 影响

| 影响级别 | 具体表现 |
|---------|---------|
| **数据泄露** | 获取数据库中的所有数据（用户信息、密码、业务数据） |
| **数据篡改** | 修改、删除数据（UPDATE、DELETE、DROP） |
| **权限提升** | 获取数据库管理员权限，进而控制服务器 |
| **命令执行** | 某些数据库支持执行系统命令（如 MySQL 的 UDF、xp_cmdshell） |

#### 防御措施

| 防御层级 | 措施 | 说明 |
|---------|------|------|
| **核心** | 参数化查询（预编译） | ✅ 必选，从根源上解决注入问题 |
| **辅助** | 输入验证与过滤 | 白名单验证，辅助但不能替代参数化 |
| **架构** | ORM 安全使用 | 使用 ORM 时也要注意，避免 raw SQL 拼接 |
| **兜底** | 最小权限原则 | 数据库账号只授予必要权限，限制危害范围 |
| **补充** | WAF / 数据库防火墙 | 网络层防护，可拦截已知攻击模式 |
| **检测** | 数据库审计与监控 | 发现异常查询行为，及时告警 |

### 2.2 访问控制缺陷

#### 弱口令与暴力破解

| 问题 | 说明 | 影响 |
|------|------|------|
| 默认账号密码 | 安装后未修改默认密码（如 root/root、admin/admin） | 直接被登录 |
| 弱密码 | 密码太短、太简单（123456、password） | 暴力破解 |
| 密码复用 | 多数据库使用相同密码 | 一个泄露全部沦陷 |

**检测**：
- 检查是否存在默认/弱口令（授权环境下）
- 查看用户表中的密码哈希强度

**防御**：
```sql
-- MySQL：强密码策略（需安装 validate_password 组件）
INSTALL COMPONENT 'file://component_validate_password';
SET GLOBAL validate_password.length = 12;
SET GLOBAL validate_password.number_count = 2;
SET GLOBAL validate_password.special_char_count = 1;

-- 修改弱密码
ALTER USER 'root'@'localhost' IDENTIFIED BY 'StrongP@ssw0rd!';
```

#### 权限过大与越权访问

| 问题 | 说明 |
|------|------|
| 应用使用 DBA 账号 | 应用连接数据库用 root / sa 等超级管理员账号 |
| 权限授予过多 | 普通用户拥有 DROP、ALTER、FILE 等危险权限 |
| 列级/行级权限缺失 | 用户能看到不该看的列和行 |
| 权限继承问题 | 角色/组权限传递失控 |

**防御：最小权限原则（Principle of Least Privilege）**

```sql
-- MySQL：创建专用应用账号，只授予必要权限
CREATE USER 'app_user'@'localhost' IDENTIFIED BY 'StrongAppP@ss!';
GRANT SELECT, INSERT, UPDATE ON mydb.* TO 'app_user'@'localhost';
-- 不给 DROP、ALTER、DELETE（按需）
FLUSH PRIVILEGES;

-- PostgreSQL：创建只读角色
CREATE ROLE readonly;
GRANT CONNECT ON DATABASE mydb TO readonly;
GRANT USAGE ON SCHEMA public TO readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO readonly;
```

### 2.3 配置错误

| 配置问题 | 说明 | 风险 |
|---------|------|------|
| **端口公网暴露** | 数据库端口（3306/5432/1433/6379/27017）直接暴露在公网 | 被扫描、暴力破解、未授权访问 |
| **默认配置未修改** | 绑定 0.0.0.0、允许远程 root 登录等 | 增加攻击面 |
| **未启用认证** | 如 Redis、MongoDB 安装后默认无密码 | 未授权访问，数据泄露/被删 |
| **危险功能开启** | FILE 权限、UDF、xp_cmdshell、LOAD DATA 等 | 命令执行、文件读写 |
| **测试数据未清理** | 生产库中保留测试数据、测试账号 | 敏感信息泄露 |
| **备份文件泄露** | 数据库备份文件可通过 Web 访问 | 整库泄露 |

#### 典型案例：Redis 未授权访问

```
风险场景：
  - Redis 绑定 0.0.0.0 且无密码
  - 端口 6379 暴露在公网

攻击后果：
  - 读取内存中所有数据
  - 写入 SSH 公钥 → 登录服务器
  - 写入 crontab → 定时任务反弹 shell
  - 主从复制 RCE

防御配置（redis.conf）：
  bind 127.0.0.1          # 只监听本地
  requirepass strongpass  # 设置密码
  rename-command FLUSHALL ""   # 禁用危险命令
  rename-command CONFIG ""
  protected-mode yes      # 开启保护模式
```

> **⚠️ 重要警告**：Redis、MongoDB、Elasticsearch 等 NoSQL 数据库安装后默认配置往往不安全（无认证、监听所有地址）。生产环境必须手动加固！

### 2.4 数据泄露

| 泄露途径 | 说明 | 防护措施 |
|---------|------|---------|
| **敏感数据明文存储** | 密码、身份证、银行卡明文存储 | 密码哈希（bcrypt/Argon2）、敏感字段加密 |
| **备份未加密** | 数据库备份文件未加密，存储位置不安全 | 备份加密、安全存储、定期验证 |
| **日志泄露** | 日志中包含敏感数据（密码、身份证号） | 日志脱敏、日志访问控制 |
| **SQL 错误信息泄露** | 详细错误信息暴露给用户 | 生产环境关闭详细错误回显 |
| **云存储配置错误** | 备份存到公开的 S3/OSS 存储桶 | 存储桶私有、访问控制、加密 |
| **供应链泄露** | 第三方服务商、SaaS 平台数据泄露 | 供应商安全评估、数据最小化 |

```sql
-- ✅ 密码安全存储：使用专门的密码哈希算法
-- 不要用 MD5/SHA1，不要自己加盐
-- 推荐：bcrypt, Argon2, PBKDF2

-- MySQL 8.0 内置密码哈希（用于数据库账号）
-- 应用层用户密码应在应用代码中用 bcrypt/argon2 处理
```

### 2.5 内部威胁

| 威胁类型 | 说明 | 防护措施 |
|---------|------|---------|
| **DBA 滥用权限** | 数据库管理员越权查看/修改敏感数据 | 特权账号管理、操作审计、双人审批 |
| **权限提升** | 普通用户通过漏洞或配置提升为管理员 | 最小权限、定期审计权限、漏洞修复 |
| **数据导出/拷贝** | 内部人员批量导出敏感数据带走 | 数据防泄漏（DLP）、导出审计、脱敏 |
| **逻辑删除后门** | 离职 DBA 留下后门账号 | 离职流程、账号审计、权限清理 |

### 2.6 供应链与第三方组件风险

| 风险 | 说明 | 示例 |
|------|------|------|
| **数据库自身漏洞** | 数据库软件的安全漏洞 | MySQL 权限提升、PostgreSQL SQL 注入、Redis RCE |
| **驱动/客户端漏洞** | 数据库驱动和客户端库的漏洞 | JDBC 驱动反序列化、ORM 框架注入 |
| **第三方插件/扩展** | 数据库插件、UDF、存储过程中的漏洞 | MySQL UDF、PostgreSQL 扩展 |
| **依赖库漏洞** | 应用依赖的 ORM、数据库连接池漏洞 | MyBatis、Hibernate、Druid 的安全问题 |

**防御**：
- 及时打补丁（数据库软件、驱动、ORM 框架）
- 定期漏洞扫描
- 最小化安装（只装需要的组件和扩展）
- 关注安全公告（CVE、厂商安全公告）

## 三、数据库安全防御体系

### 3.1 认证与访问控制

#### 强认证

| 措施 | MySQL | PostgreSQL | SQL Server |
|------|-------|-----------|------------|
| 强密码策略 | validate_password 组件 | passwordcheck 扩展 | 密码策略（GPO/策略） |
| 账户锁定 | connection_control 插件 | auth_delay | 登录失败锁定 |
| 多因素认证 | MySQL Enterprise | pg_hba 配置 + 外部 | Azure AD / MFA |
| 证书认证 | SSL 证书认证 | cert 认证方式 | 证书认证 |

#### 最小权限原则

```
权限分层模型：
  超级管理员（DBA）
    ↓ 仅极少数人
  数据库管理员
    ↓ 按需
  应用管理员
    ↓ 按应用
  只读用户 / 普通读写用户
    ↓ 按业务
  列级 / 行级权限控制
```

#### 行级安全（Row-Level Security, RLS）

行级安全让不同用户只能看到自己应该看到的数据行。

```sql
-- PostgreSQL 行级安全示例
-- 启用行级安全
ALTER TABLE users ENABLE ROW LEVEL SECURITY;

-- 创建策略：用户只能看到自己的数据
CREATE POLICY user_isolation_policy ON users
    FOR SELECT USING (username = current_user);

-- 这样每个用户查询时，数据库自动过滤行
-- 不需要应用层写 WHERE user_id = ?
```

#### 动态数据脱敏（Dynamic Data Masking）

敏感数据在查询时自动脱敏，只有授权用户能看到完整数据。

```sql
-- SQL Server 动态数据脱敏
CREATE TABLE Users (
    ID INT IDENTITY(1,1) PRIMARY KEY,
    Name NVARCHAR(50) NOT NULL,
    Email NVARCHAR(100) MASKED WITH (FUNCTION = 'email()'),
    Phone NVARCHAR(20) MASKED WITH (FUNCTION = 'partial(0,"XXX-XXX-",4)'),
    CreditCard NVARCHAR(20) MASKED WITH (FUNCTION = 'partial(0,"XXXX-XXXX-XXXX-",4)')
);

-- 普通用户查询看到的是脱敏后的数据
-- 授权用户（UNMASK 权限）看到完整数据
GRANT UNMASK TO privileged_user;
```

### 3.2 加密与保护

#### 三层加密模型

```
┌─────────────────────────────────────────┐
│  应用层加密                               │
│  （应用代码中加密，数据库存密文）           │
│  粒度：字段级 / 自定义算法 / 端到端加密      │
├─────────────────────────────────────────┤
│  数据库层加密                             │
│  （TDE 透明数据加密 / 列级加密）           │
│  粒度：数据库级 / 表空间级 / 列级           │
├─────────────────────────────────────────┤
│  存储层加密                               │
│  （磁盘加密 / 文件系统加密）               │
│  粒度：整个磁盘 / 卷                      │
└─────────────────────────────────────────┘
```

#### 传输加密（TLS/SSL）

```sql
-- MySQL：强制使用 SSL
-- my.cnf
[mysqld]
ssl-ca=/path/to/ca.pem
ssl-cert=/path/to/server-cert.pem
ssl-key=/path/to/server-key.pem
require_secure_transport = ON

-- 用户强制 SSL 连接
ALTER USER 'user'@'%' REQUIRE SSL;
```

```sql
-- PostgreSQL：启用 SSL
-- postgresql.conf
ssl = on
ssl_cert_file = 'server.crt'
ssl_key_file = 'server.key'

-- pg_hba.conf 强制 SSL
hostssl all all 0.0.0.0/0 md5
```

#### 透明数据加密（Transparent Data Encryption, TDE）

TDE 在数据库层面自动加密数据文件，对应用透明。

| 数据库 | TDE 功能 |
|--------|---------|
| SQL Server | Transparent Data Encryption（企业版） |
| Oracle | Transparent Data Encryption（高级安全选项） |
| MySQL | MySQL Enterprise TDE（企业版） |
| PostgreSQL | pgcrypto / 第三方扩展 / 云厂商实现 |
| 云数据库 | 各大云厂商 RDS 一般都支持存储加密 |

#### 列级加密（Column-Level Encryption）

对敏感列单独加密，即使数据库被攻破，敏感字段也是密文。

```sql
-- PostgreSQL 使用 pgcrypto 扩展
CREATE EXTENSION pgcrypto;

-- 加密存储
INSERT INTO users (name, email, ssn)
VALUES (
    'Alice',
    'alice@example.com',
    pgp_sym_encrypt('123-45-6789', 'encryption_key')
);

-- 解密查询（需要密钥）
SELECT name, email, pgp_sym_decrypt(ssn::bytea, 'encryption_key') AS ssn
FROM users;
```

#### 密钥管理（Key Management）

| 层级 | 方案 | 适用场景 |
|------|------|---------|
| 入门 | 应用配置文件存密钥 | ❌ 不推荐，不安全 |
| 进阶 | 密钥管理服务（KMS） | ✅ 推荐，云厂商 KMS / HashiCorp Vault |
| 高级 | 硬件安全模块（HSM） | 金融、政务等高安全要求 |

> **密钥管理原则**：
> - 密钥和数据分开存储
> - 定期轮换密钥
> - 谁也不能直接看到根密钥（零知识）
> - 审计密钥使用记录

### 3.3 SQL 注入纵深防御

```
第 1 层（核心）：参数化查询 / 预编译语句
  │  从根源解决注入问题，必选
  ▼
第 2 层（辅助）：输入验证与过滤
  │  白名单验证输入格式，辅助但不能替代参数化
  ▼
第 3 层（架构）：ORM 安全使用
  │  优先用 ORM，避免 raw SQL；用 raw SQL 时必须参数化
  ▼
第 4 层（兜底）：数据库最小权限
  │  即使被注入，也只能做有限的操作
  ▼
第 5 层（补充）：WAF / 数据库防火墙
  │  拦截已知攻击模式，零日攻击可能绕过
  ▼
第 6 层（检测）：审计与异常检测
  │  发现异常查询，及时告警和响应
```

#### 参数化查询各语言示例

| 语言/框架 | 正确写法（参数化） |
|----------|-------------------|
| **Python (pymysql)** | `cursor.execute("SELECT * FROM users WHERE id=%s", (user_id,))` |
| **Java (JDBC)** | `PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE id=?"); ps.setInt(1, userId);` |
| **C# (ADO.NET)** | `SqlCommand cmd = new SqlCommand("SELECT * FROM Users WHERE Id=@Id", conn); cmd.Parameters.AddWithValue("@Id", userId);` |
| **PHP (PDO)** | `$stmt = $pdo->prepare("SELECT * FROM users WHERE id=:id"); $stmt->execute(['id' => $id]);` |
| **Go (database/sql)** | `db.Query("SELECT * FROM users WHERE id=?", id)` |
| **Node.js (mysql)** | `db.query("SELECT * FROM users WHERE id=?", [id])` |

#### ORM 安全使用注意事项

| ORM | 安全用法 | 危险用法（可能注入） |
|-----|---------|-------------------|
| **MyBatis** | `#{param}`（预编译） | `${param}`（字符串拼接，⚠️ 注入风险） |
| **Hibernate** | HQL 参数绑定 | 字符串拼接 HQL |
| **SQLAlchemy** | ORM 查询 / text() + bindparam | 直接拼接 SQL 字符串 |
| **Django ORM** | ORM 方法（filter/get） | raw() + 字符串拼接 |
| **GORM** | 链式调用 / ? 占位符 | 字符串拼接 Exec/Raw |

```java
// MyBatis 示例
// ✅ 安全：#{} 会生成预编译语句
<select id="getUserById" resultType="User">
    SELECT * FROM users WHERE id = #{id}
</select>

// ❌ 危险：${} 是字符串拼接，有注入风险
<select id="getUserById" resultType="User">
    SELECT * FROM users WHERE id = ${id}
</select>
```

#### 数据库活动监控（DAM）

### 3.5 安全基线与加固

#### 网络隔离

```
安全部署架构：
  互联网 → 防火墙 → Web/应用服务器 → 数据库防火墙 → 数据库
                    │                    │
                  DMZ 区            内部数据库区
                    │                    │
                对外服务             仅应用服务器可访问
```

- 数据库不直接暴露在公网
- 使用防火墙/安全组限制来源 IP
- 数据库与应用服务器在独立网络区域
- 使用 VPC / 内网访问

#### 配置加固清单

| 检查项 | 说明 | 加固建议 |
|--------|------|---------|
| 端口监听地址 | bind-address 只绑定内网 | `bind-address = 127.0.0.1` 或内网 IP |
| 默认账号 | 删除/禁用默认测试账号 | DROP USER ''@'localhost'; |
| 匿名用户 | 删除匿名用户 | DROP USER ''@'%'; |
| root 远程登录 | 禁止 root 远程登录 | 只允许 root 本地登录 |
| 密码策略 | 启用强密码策略 | validate_password / passwordcheck |
| 登录失败锁定 | 启用账户锁定 | connection_control 插件 |
| SSL/TLS | 启用传输加密 | require_secure_transport = ON |
| 文件权限 | 数据目录权限 | 只有数据库用户可读 |
| 危险功能 | 禁用 FILE、UDF 等危险权限 | 不给普通用户 FILE 权限 |
| 审计日志 | 启用审计 | 配置审计插件和日志 |
| 补丁更新 | 及时更新安全补丁 | 定期检查并打补丁 |

#### 定期巡检

- 每月：用户权限审计、弱密码检查、日志审查
- 每季度：漏洞扫描、配置基线检查、备份恢复演练
- 每半年：渗透测试（授权）、安全评估、应急演练

## 八、安全与合规

### 8.1 适用边界

- ✅ **授权测试**：在获得明确书面授权的系统上进行安全测试
- ✅ **漏洞研究**：在隔离的实验环境中研究漏洞原理和防御方法
- ✅ **安全加固**：对自己管理的数据库进行安全配置和加固
- ✅ **代码审计**：审计自己或授权的代码，发现和修复 SQL 注入等漏洞
- ❌ **未授权扫描**：对任何未授权的数据库进行扫描或探测
- ❌ **SQL 注入攻击**：对任何未授权的系统进行 SQL 注入测试
- ❌ **数据窃取**：利用漏洞获取或泄露他人数据
- ❌ **数据破坏**：删除、篡改他人数据库数据

### 8.2 相关法律法规（中国）

| 法律法规 | 相关内容 |
|---------|---------|
| **《中华人民共和国网络安全法》** | 禁止非法侵入他人网络、干扰网络功能、窃取网络数据 |
| **《中华人民共和国数据安全法》** | 数据处理活动的安全规范，重要数据保护 |
| **《中华人民共和国个人信息保护法》** | 个人信息处理的安全要求，敏感个人信息保护 |

### 8.3 高风险操作警告

| 操作 | 风险 | 安全建议 |
|------|------|---------|
| sqlmap 扫描 | 可能对数据库造成压力甚至破坏 | 仅在授权环境使用，限制速度，有备份 |
| DROP / TRUNCATE | 误删数据，难以恢复 | 生产环境操作前必须备份，双人确认 |
| 修改权限 / GRANT ALL | 权限过大，安全风险 | 遵循最小权限原则，定期审计权限 |
| 启用危险功能 | FILE、UDF、xp_cmdshell 等 | 非必要不开启，开启后严格控制权限 |
| 数据导出 / 备份 | 数据泄露风险 | 加密存储，限制访问，脱敏处理 |
| 公网暴露端口 | 被扫描、暴力破解、未授权访问 | 内网部署，防火墙限制，VPN 访问 |
| 修改系统表 | 数据库不稳定、安全机制失效 | 除非完全清楚后果，否则不要操作 |

### 8.4 安全编码责任

作为开发者或 DBA，我们有责任：
1. **使用参数化查询**，不让 SQL 注入成为可能
2. **遵循最小权限**，不给多余的权限
3. **加密敏感数据**，保护用户隐私
4. **开启审计日志**，出了问题能追溯
5. **及时打补丁**，修复已知漏洞
6. **定期安全检查**，发现问题及时整改
