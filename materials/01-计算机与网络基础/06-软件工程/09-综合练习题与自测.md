## 二、判断题（正确打✓，错误打✗）

1. 软件就是程序，文档不重要。（ ）

2. 瀑布模型适合需求明确稳定的项目。（ ）

3. 敏捷开发就是不用写文档。（ ）

4. 需求分析阶段，我们需要详细讨论系统怎么实现。（ ）

5. 用例图中，参与者一定在系统边界之外。（ ）

6. 耦合是模块内部的紧密程度，内聚是模块之间的依赖程度。（ ）

7. 设计模式是银弹，所有问题都可以用设计模式解决。（ ）

8. 测试只能证明程序有bug，不能证明程序没有bug。（ ）

9. 白盒测试不需要看代码，只看输入输出。（ ）

10. 单元测试通常由测试人员来写。（ ）

11. TDD 就是先写测试再写代码。（ ）

12. Scrum Master 就是项目经理，负责管理团队。（ ）

13. CI 和 CD 是一个意思。（ ）

14. 微服务架构一定比单体架构好。（ ）

15. Git Flow 是最规范的 Git 工作流，所有团队都应该用。（ ）

```python
        if shape_type == "circle":
            radius = args[0]
            return 3.14 * radius * radius
        elif shape_type == "rectangle":
            width, height = args
            return width * height
        elif shape_type == "triangle":
            base, height = args
            return 0.5 * base * height
        else:
            raise ValueError("未知形状")
    
    def calculate_perimeter(self, shape_type, *args):
        if shape_type == "circle":
            radius = args[0]
            return 2 * 3.14 * radius
        elif shape_type == "rectangle":
            width, height = args
            return 2 * (width + height)
        # ... 更多形状
        else:
            raise ValueError("未知形状")
    
    def draw(self, shape_type, x, y, *args):
        # 绘制图形的代码，又是一大段 if-else
        pass
```

要求：
1. 指出违反了哪些 SOLID 原则
2. 给出重构后的代码

## 四、名词解释（参考答案要点）

1. **软件危机**：软件开发和维护过程中遇到的一系列严重问题，如进度延误、成本超支、质量低下、难以维护等。

2. **软件生命周期**：软件从提出开发要求开始，直到报废为止的整个时期，包括问题定义、可行性研究、需求分析、设计、编码、测试、维护、退役等阶段。

3. **需求工程**：应用已证实有效的原理、方法、技术和工具，来确定、分析、规格说明和验证需求的系统方法。包括需求获取、分析、规格说明、验证、管理。

4. **耦合与内聚**：耦合是模块之间相互依赖的紧密程度，目标是低耦合；内聚是模块内部各元素结合的紧密程度，目标是高内聚。"高内聚、低耦合"是软件设计的追求目标。

5. **SOLID**：面向对象设计五大原则的缩写——S单一职责、O开闭、L里氏替换、I接口隔离、D依赖倒置。

6. **黑盒测试**：把测试对象看作黑盒子，不考虑内部结构，只检查输入输出是否符合要求。也叫功能测试。

7. **白盒测试**：把测试对象看作透明的盒子，了解内部结构，根据代码逻辑设计测试用例。也叫结构测试。

8. **TDD**：Test-Driven Development，测试驱动开发。先写测试代码，再写功能代码，由测试驱动开发。核心循环是"红-绿-重构"。

9. **设计模式**：软件开发中针对常见问题的、经过验证的、可复用的解决方案。是前人经验的总结。

10. **单例模式**：保证一个类只有一个实例，并提供全局访问点的设计模式。属于创建型模式。

11. **观察者模式**：定义对象间一对多的依赖关系，当一个对象状态改变时，所有依赖它的对象都会收到通知并自动更新。也叫发布-订阅模式。

12. **Scrum**：最流行的敏捷开发框架，包括三个角色（PO、SM、开发团队）、三个工件（产品待办、冲刺待办、产品增量）、五个事件（Sprint、规划会、每日站会、评审会、回顾会）。

13. **CI/CD**：CI是持续集成（Continuous Integration），CD是持续交付（Continuous Delivery）或持续部署（Continuous Deployment）。是DevOps的核心实践。

14. **DevOps**：Development + Operations，是一种重视开发和运维沟通合作的文化、运动和实践，目标是实现快速、可靠的软件交付。

15. **微服务**：一种架构风格，把单体应用拆分成多个小服务，每个服务独立部署、独立运行，服务之间通过轻量级机制通信。

## 五、简答题（参考答案要点）

### 概述部分

1. **软件工程**是应用计算机科学理论和技术以及工程管理原则和方法，按预算和进度实现满足用户要求的软件产品的定义、开发、发布和维护的工程。
   
   **和编程的区别**：编程只是软件工程中的一个环节（编码阶段）。软件工程还包括需求分析、设计、测试、维护、项目管理等。编程关注"写代码"，软件工程关注"如何按时、按质、按预算地做出有用的软件"。

2. **瀑布 vs 敏捷**：
   - 瀑布：计划驱动、线性顺序、阶段分明、文档驱动、一次性交付。适合需求明确稳定的项目。
   - 敏捷：价值驱动、迭代增量、持续交付、轻量文档、拥抱变化。适合需求不确定、需要快速验证的项目。

### 需求部分

3. **需求工程**是系统地确定、分析、规格说明和验证需求的过程。
   包括：需求获取、需求分析、需求规格说明、需求验证、需求管理。

4. **用例 vs 用户故事**：
   - 相同点：都是描述功能需求的方法，都从用户视角出发。
   - 不同点：用例详细完整（有事件流、前置后置条件），文档驱动；用户故事简洁轻量，细节靠对话补充，适合敏捷。
   - 用例适合瀑布/增量模型；用户故事适合敏捷开发。

### 设计部分

5. **高内聚**：每个模块功能单一明确，易于理解、维护和复用。
   **低耦合**：模块之间依赖少，修改一个模块不容易影响其他模块，系统更稳定、更灵活。
   两者相辅相成：高内聚往往带来低耦合，低内聚往往带来高耦合。最终目标是让系统"好理解、好修改、好维护"。

6. **SOLID 原则**：
   - **S 单一职责**：一个类只做一件事，只有一个引起变化的原因。
   - **O 开闭原则**：对扩展开放，对修改关闭。
   - **L 里氏替换**：子类必须能替换父类。
   - **I 接口隔离**：接口要小而专，客户端不应该依赖它不需要的接口。
   - **D 依赖倒置**：依赖抽象，不依赖具体实现。

7. **分层架构优点**：职责清晰、易于开发、各层可独立替换、降低复杂度。
   **缺点**：性能开销（请求经过每一层）、层级限制（严格分层可能不必要）、对复杂业务不够灵活。
   **适用场景**：传统企业应用、业务逻辑清晰的系统、团队分工明确的项目。

8. **微服务优点**：独立部署、技术灵活、扩展性好、容错性好、团队自治。
   **缺点**：复杂度高、运维成本高、数据一致性难、调用链长、服务治理复杂。
   **适用场景**：大型复杂系统、需要快速迭代的系统、团队规模较大的项目。小项目不适合。

### UML 部分

9. 类之间的关系（从强到弱）：
   泛化（继承）→ 实现 → 组合 → 聚合 → 关联 → 依赖

10. **时序图**：描述对象之间消息传递的时间顺序。关注"谁给谁发了什么消息，按什么顺序"。适合描述对象交互、接口调用流程。
    **活动图**：描述工作流程和活动流转。关注"做什么事情，按什么流程做"。适合描述业务流程、用例实现流程。

### 测试部分

11. 软件测试基本原则：
    - 测试显示存在缺陷，不能证明没有缺陷
    - 穷尽测试是不可能的
    - 测试尽早介入
    - 缺陷集群效应（80%缺陷在20%模块）
    - 杀虫剂悖论（同样的用例发现不了新bug）
    - 测试依赖上下文
    - 没有缺陷的谬论（没有bug不等于产品有用）

12. 四个测试级别：
    - **单元测试**：测试最小的功能单元（函数、类）。验证单元是否正确实现。开发人员做。
    - **集成测试**：测试模块之间的接口和交互。验证组装后是否正常工作。开发/测试做。
    - **系统测试**：测试整个系统。验证是否符合需求规格说明。测试人员做。
    - **验收测试**：由用户进行。验证是否满足业务需求，决定是否验收。用户做。

13. **等价类划分**：把输入分成若干等价类，从每个类选代表性数据。目的是减少用例数量，覆盖各类情况。
    **边界值分析**：在等价类的边界上选数据。因为边界最容易出问题。
    **联系**：两种方法经常结合使用。等价类划分是基础，边界值是补充和强化。

14. **测试覆盖率**：衡量测试充分程度的指标，如语句覆盖率、分支覆盖率、需求覆盖率等。
    **不是越高越好**：
    - 覆盖率是手段不是目的
    - 100%覆盖率不代表没有bug
    - 追求过高的覆盖率成本很高，边际效益递减
    - 关键是测试的质量，不是数量

### 设计模式部分

15. 设计模式分为三大类：
    - **创建型**（5种）：关注对象的创建过程。单例、工厂方法、抽象工厂、建造者、原型。
    - **结构型**（7种）：关注类和对象的组合结构。适配器、装饰器、代理、外观、桥接、组合、享元。
    - **行为型**（11种）：关注对象之间的交互和职责分配。策略、观察者、模板方法、迭代器、责任链等。

16. **策略模式 vs 状态模式**：
    - 相同点：都封装了行为，都有 Context 和多个策略/状态类。
    - 不同点：
      - 策略模式封装的是"算法"，算法之间是平级的，可以互相替换，客户端知道所有策略
      - 状态模式封装的是"状态和状态行为"，状态之间有流转关系，客户端不需要知道状态细节
      - 策略模式的切换是客户端主动切换；状态模式的切换是内部自动流转

17. **适配器模式 vs 装饰器模式**：
    - 相同点：都有一个包装类，都持有被包装对象的引用。
    - 不同点：
      - 目的不同：适配器是为了"改接口"，让不兼容的能一起工作；装饰器是为了"加功能"，动态增强对象
      - 接口不同：适配器改变了接口；装饰器保持相同的接口
      - 时机不同：适配器是事后补救（接口不兼容了才用）；装饰器是事前设计（为了灵活增加功能）

### 项目管理与 DevOps 部分

18. **铁三角**：范围、时间、成本。
    关系：三者相互制约，构成三角形。任何一个变化都会影响其他两个。质量是三者共同作用的结果。比如范围增加，要么延长时间，要么增加成本（或者降低质量）。

19. **Scrum 工件**：产品待办列表（Product Backlog）、冲刺待办列表（Sprint Backlog）、产品增量（Increment）。
    **Scrum 事件**：Sprint（迭代）、Sprint 规划会议、每日站会、Sprint 评审会议、Sprint 回顾会议。

20. **DevOps** 是一种文化、运动和实践，强调开发和运维的协作，目标是快速可靠地交付软件。
    **CI/CD** 是 DevOps 的核心实践和工具，是实现 DevOps 的重要手段。
    关系：DevOps 是思想/文化，CI/CD 是技术/实践。有了 DevOps 的思想，再用 CI/CD 工具来落地。

21. **蓝绿发布**：两套完全一样的环境，发布时切换流量。
    - 优点：零停机、回滚快、安全可控
    - 缺点：需要两套环境，成本高
    - 适用：重要系统、小项目
    
    **金丝雀发布**：先让少量用户用新版本，没问题再逐步扩大。
    - 优点：风险小（只影响少量用户）、真实环境验证
    - 缺点：发布过程长、流量控制复杂
    - 适用：互联网产品、大用户量系统

## 七、综合论述题（提示）

> 论述题没有标准答案，关键是要有自己的思考，言之有理即可。以下提供思路方向。

1. **不同意**。敏捷不是没有计划和文档，而是：
   - 计划是迭代式的，不是一次性的
   - 文档是轻量的、够用就好，不是大而全
   - 敏捷有严格的纪律（Scrum的各种会议、工件）
   - 敏捷的核心是"响应变化"，不是"随便乱来"

2. **不能保证没有bug**。因为：
   - 输入组合是无限的，不可能穷尽测试
   - 测试只能证明有bug，不能证明没有bug
   - 测试用例本身也可能有遗漏
   
   **测试的意义**：
   - 发现尽可能多的bug，降低上线风险
   - 提高对软件质量的信心
   - 提供质量反馈，指导改进
   - 测试是质量保障的重要手段（虽然不是唯一手段）

3. **不是万能的**。
   **应该用的时候**：
   - 遇到了模式能解决的典型问题
   - 代码有坏味道（大量if-else、重复代码、高耦合）
   - 需要提高代码的可扩展性和可维护性
   - 重构的时候
   
   **不应该用的时候**：
   - 简单的问题，用简单方式就能解决
   - 为了用模式而用模式（炫技）
   - 需求不稳定，可能很快就变
   - 团队成员都不懂，用了反而增加复杂度

4. 因为缺陷修复成本随阶段呈指数增长：
   - 需求阶段发现：只需要改需求文档，成本 1x
   - 设计阶段发现：需要改设计，成本 5x
   - 编码阶段发现：需要改代码，成本 10x
   - 测试阶段发现：改代码+重新测试，成本 50x
   - 上线后发现：改代码+测试+部署+用户赔偿，成本 100x+
   
   需求是源头，需求错了，后面全错。所以需求错误是最昂贵的错误。

5. **不是所有系统都应该用微服务**。
   微服务有很多优点，但也有很多缺点（复杂度高、运维成本高、分布式问题）。
   
   **适合微服务的情况**：
   - 系统规模大、复杂度高
   - 团队规模大，需要拆分团队
   - 需要独立部署和扩展
   - 业务领域清晰，可以拆分
   
   **不适合的情况**：
   - 小型项目、创业初期
   - 团队小，没能力运维复杂系统
   - 业务还在探索期，边界不清晰
   
   经典建议："除非你有一个单体搞不定的系统，否则不要用微服务。"

6. 这句话的意思是：质量是内建的，不是事后检查出来的。
   
   解释：
   - 如果需求一塌糊涂，测试再怎么测也救不了
   - 如果设计很糟糕，测试只能发现bug，不能提升设计质量
   - 如果代码写得很乱，测试发现bug改了又会引入新bug
   - 测试是质量的"最后一道防线"，但不是质量的来源
   
   正确的做法：
   - 质量要从需求、设计、编码各环节抓起
   - 每个人都对质量负责（开发的代码质量、产品的需求质量）
   - 测试是质量保障的一环，但不是全部
